|#|知识点|核心内容|面试追问|FlowPulse 拆分实例|
|---|---|---|---|---|
|**3.1.1**|**微服务 vs 单体 vs 模块化单体**|单体(所有功能在一个进程) → 模块单体(分层清晰但共部署) → 微服务(独立部署/独立技术栈) → Serverless(FaaS)|"什么时候该从单体拆成微服务？什么情况下不应该拆？"|FlowPulse选择**微服务**：10个服务独立部署，因为需要独立扩展(流程引擎高负载vs日志服务低负载)|
|**3.1.2**|**按业务能力拆分 (Business Capability)**|面向业务的垂直拆分；每个服务拥有独立的业务领域和数据存储；DDD限界上下文是理论基础|"按业务能力拆和按技术层拆有什么区别？"|**FlowPulse的10个服务就是按业务能力拆的**：认证域(auth) / 流程域(workflow) / 调度域(scheduler) / 文件域(file)...|
|**3.1.3**|**DDD驱动拆分 (Domain-Driven Design)**|先识别限界上下文(Bounded Context) → 确定聚合根(Aggregate Root) → 划定聚合边界 → 一个聚合对应一个服务的核心数据模型|"怎么识别限界上下文？事件风暴怎么做的？"|工作流引擎是一个完整的**限界上下文**：ProcessDefinition(聚合根)→ Instance → Task → Pointer|
|**3.1.4**|**康威定律 (Conway's Law)**|"软件系统的结构受制于产生这个系统的组织的沟通结构"；团队沟通方式决定系统架构|"康威定律对架构设计的实际指导意义？如果团队就3个人怎么办？"|FlowPulse先由1个人开发，所以初期可**模块化单工程多Module部署**，后期再物理拆分为独立服务|
|**3.1.5**|**数据拆分策略 (Database per Service)**|每个服务独占数据库(库或Schema)；禁止跨服务Join；通过API/MQ获取其他服务数据|"一个查询需要关联3个服务的表，怎么办？"|auth-service用`flowpulse_auth`库 / workflow-service用`flowpulse_wf`库 / 各服务数据库独立|
|**3.1.6**|**拆分反模式与陷阱**|细粒度微服务(一个表一个服务) → 分布式 monolith(所有调用都走RPC) → 共享数据库(伪微服务)|"共享数据库算不算微服务？"|避免：不把每个Handler做成独立服务；不跨库Join；保持服务粒度适中|
