## 第一章 排查方法论总纲

### 1.1 线上问题分类全景图

```
线上问题
├── 系统层面
│   ├── CPU 飙高（死循环 / 频繁 GC / 加密计算）
│   ├── 内存溢出（OOM / 堆外内存泄漏）
│   ├── 磁盘满（日志 / dump 文件 / 临时文件）
│   ├── 网络异常（超时 / 连接拒绝 / DNS 解析失败）
│   └── 负载高（load average 飙升）
│
├── JVM 层面
│   ├── GC 频繁（Young GC 过频 / Full GC 不停）
│   ├── 线程问题（死锁 / 线程池满 / 线程泄漏）
│   ├── 类加载异常（ClassNotFoundException / OOM:Metaspace）
│   └── 堆外内存（DirectBuffer / Native Memory 泄漏）
│
├── 应用层面
│   ├── 响应慢（接口超时 / RT 飙升）
│   ├── 错误率升高（500 / 空指针 / 异常飙升）
│   ├── 功能异常（业务逻辑错误 / 数据不一致）
│   └── 启动失败（依赖不可用 / 配置错误）
│
├── 中间件层面
│   ├── 数据库（慢查询 / 死锁 / 连接池满 / 主从延迟）
│   ├── 缓存（大 key / 热点 key / 集群脑裂 / 缓存雪崩）
│   ├── 消息队列（消息积压 / 消费者宕机 / 重复消费）
│   └── 注册中心（服务下线 / 心跳超时 / 推送延迟）
│
└── 基础设施层面
    ├── 容器（OOM Killed / CPU Limit / 镜像问题）
    ├── 网络（NAT 超时 / SLB 异常 / DNS 故障）
    └── 宿主机（邻居噪音 / 硬件故障）
```

### 1.2 排查六步法（万能框架）

无论什么问题，都遵循以下六步：

```
┌─────────────────────────────────────────────────────────┐
│  第一步：确认现象 ─→ 告警内容是什么？影响面多大？         │
│  第二步：快速止血 ─→ 回滚？重启？限流？降级？扩容？       │
│  第三步：定位方向 ─→ CPU？内存？网络？数据库？           │
│  第四步：深入根因 ─→ jstack？jmap？慢查询日志？抓包？     │
│  第五步：修复验证 ─→ 改代码？调参数？发版？              │
│  第六步：复盘总结 ─→ 为什么发生？如何避免？监控补充？     │
└─────────────────────────────────────────────────────────┘
```

#### 第一步：确认现象

```
问自己 / 问值班同事：
1. 告警内容是什么？（CPU > 90%？接口 500？OOM？）
2. 什么时候开始的？（精确到分钟）
3. 影响范围多大？（全量用户？部分接口？单个实例？）
4. 最近有什么变更？（发版？配置修改？扩缩容？流量突增？）
5. 错误率多少？响应时间多少？
```

#### 第二步：快速止血

| 手段 | 适用场景 | 操作 |
|------|----------|------|
| **回滚** | 刚发版就出问题 | 回到上一稳定版本 |
| **重启** | OOM、死锁、线程泄漏 | 重启大法好，但不解决根因 |
| **限流降级** | 流量突增、下游不可用 | Sentinel / Hystrix 降级 |
| **扩容** | CPU/内存不够用 | 加实例、加资源 |
| **摘除故障节点** | 单节点问题 | 从负载均衡摘除 |

> **原则**：先恢复服务，再排查根因。止血不等于解决。

#### 第三步：定位方向

```
根据现象快速锁定排查方向：

CPU > 90%        → 第二章（CPU 飙高）
OOM 报错          → 第三章（内存问题）
GC 停顿频繁       → 第四章（GC 问题）
接口超时 / 慢     → 第六章（响应慢）+ 第七章（数据库）
线程死锁           → 第五章（线程问题）
502/504           → 第八章（网络问题）
磁盘使用率 > 90%  → 第九章（磁盘 IO）
```

#### 第四步 ~ 第六步：见后续各章

|------|------|----------|

## 第二章 CPU 飙高排查

### 2.1 CPU 飙高的常见原因

```
CPU 飙高
├── 业务代码
│   ├── 死循环（while(true) 没退出条件）
│   ├── 频繁正则匹配（正则回溯爆炸）
│   ├── 大量序列化/反序列化
│   ├── 高 CPU 计算逻辑（加密/压缩/排序大集合）
│   └── 锁自旋（synchronized / CAS 空转）
│
├── GC 导致
│   ├── 频繁 Young GC（对象分配过快）
│   ├── Full GC 不停（内存泄漏 / 大对象）
│   └── GC 线程占满 CPU
│
├── 外部因素
│   ├── 流量突增（大促 / 爬虫 / 被攻击）
│   ├── 被其他进程影响（容器邻居噪音）
│   └── 病毒 / 挖矿木马
│
└── JVM 本身
    ├── JIT 编译（预热阶段 CPU 高）
    ├── 类加载（启动阶段）
    └── 线程数过多（上下文切换开销）
```

### 2.2 标准排查流程（⭐面试必问）

```
top → top -Hp → printf %x → jstack → 分析线程栈
```

#### 步骤一：top 找到 CPU 最高的进程

```bash
$ top
# 看 CPU 列，找到 CPU 最高的 Java 进程
# 假设 PID = 12345

PID    USER    PR  NI    VIRT    RES    SHR S  %CPU  %MEM   TIME+    COMMAND
12345  app     20   0  3.5g    1.2g   20m  S  98.6   15.2  120:30   java -jar app.jar
```

#### 步骤二：top -Hp 找到 CPU 最高的线程

```bash
# -H 显示线程，-p 指定进程
$ top -Hp 12345

# 找到 CPU 最高的线程，假设 TID = 12378
PID    USER    PR  NI    VIRT    RES    SHR S  %CPU  %MEM   TIME+    COMMAND
12378  app     20   0  3.5g    1.2g   20m  R  95.2   15.2   60:15   java -jar app.jar
12379  app     20   0  3.5g    1.2g   20m  R   2.1   15.2    1:20   java -jar app.jar
```

#### 步骤三：线程 ID 转十六进制

```bash
# Java 线程栈中的 nid 是十六进制
$ printf "%x\n" 12378
305a
```

#### 步骤四：jstack 导出线程快照并搜索

```bash
# 导出线程栈
$ jstack 12345 > thread_dump.txt

# 搜索对应线程
$ grep "305a" thread_dump.txt -A 30

# 输出示例：
"http-nio-8080-exec-3" #23 daemon prio=5 os_prio=0 tid=0x00007f8b0c0a8800 nid=0x305a runnable [0x00007f8af01e9000]
   java.lang.Thread.State: RUNNABLE
        at com.example.service.OrderService.calculatePrice(OrderService.java:156)
        at com.example.controller.OrderController.createOrder(OrderController.java:42)
        ...
```

#### 步骤五：分析线程栈

- **RUNNABLE 且 CPU 高** → 死循环 / 正则回溯 / 密集计算 → 看代码行号
- **BLOCKED** → 锁竞争 → 看锁信息
- **WAITING / TIMED_WAITING** → 线程在等待，不占 CPU → 可能是线程池空闲
- **GC 线程 CPU 高** → 不是业务线程问题，是内存问题 → 转第三章

### 2.3 一键脚本（背下来）

```bash
# 完整一键排查 CPU 飙高
# 用法: ./find_cpu_hot.sh <pid>
#!/bin/bash
PID=$1
# 找到 CPU 最高的线程
TID=$(top -Hp $PID -bn1 | grep java | head -1 | awk '{print $1}')
# 转十六进制
NID=$(printf "%x\n" $TID)
# 导出 jstack 并过滤
jstack $PID | grep "$NID" -A 30
```

### 2.4 使用 Arthas 排查（更强大）

```bash
# 启动 Arthas
$ java -jar arthas-boot.jar

# 查看最忙的线程
[arthas@12345]$ thread -n 5

# 查看特定线程的栈
[arthas@12345]$ thread <thread_id>

# 反编译看代码（确认线上代码与预期一致）
[arthas@12345]$ jad com.example.service.OrderService
```

### 2.5 GC 导致 CPU 高的判断

```bash
# 观察 GC 频率
$ jstat -gcutil <pid> 1000 10

# 输出：
  S0     S1     E      O      M     CCS    YGC   YGCT   FGC  FGCT   GCT
  0.00  85.42  73.22  89.15  94.12  91.34  152  3.456   28  5.670  9.126
  0.00  85.42  85.33  89.15  94.12  91.34  153  3.478   28  5.670  9.148

# FGC (Full GC 次数) 在增长 → GC 导致 CPU 高
# 看 FGCT (Full GC 时间) 如果很长 → STW 导致应用暂停
```

**判断**：如果 `jstack` 中大量线程状态为 `RUNNABLE`，但 `top -Hp` 显示 CPU 最高的线程名是 `GC task thread` → **GC 导致 CPU 高**，转第四章。

### 2.6 常见 CPU 高场景与解决

#### 场景一：正则回溯导致 CPU 100%

```java
// 危险正则： catastrophic backtracking
String regex = "(a+)+b";
Pattern.compile(regex).matcher("aaaaaaaaaaaaaaaaaaaaaaa!").matches();
// 输入不匹配时指数级回溯，CPU 直接拉满
```

**排查**：jstack 中看到 `Pattern.matcher` / `Matcher.match` 在栈顶。

**解决**：
1. 避免嵌套量词 `(a+)+`
2. 使用占有量词 `(a++)+`（Java 支持）
3. 设置正则超时（不太可行，Java 原生不支持）
4. 改用其他方式校验

#### 场景二：死循环

```java
// 经典 bug：并发修改导致 Iterator 死循环
List<String> list = new ArrayList<>();
// 线程 A 遍历 list，线程 B 同时 remove
// ArrayList 内部 cursor 和 size 关系错乱 → hasNext() 永远为 true → 死循环
```

**排查**：jstack 中看到 `ArrayList$Itr.hasNext` 在栈顶，线程状态 `RUNNABLE`。

**解决**：使用 `CopyOnWriteArrayList` 或加锁。

#### 场景三：序列化/反序列化

```java
// Jackson 反序列化超大的 JSON
ObjectMapper mapper = new ObjectMapper();
MyObject obj = mapper.readValue(hugeJsonString, MyObject.class);
// 如果 JSON 有几 MB，且嵌套很深，CPU 会飙高
```

**排查**：jstack 中看到 `Jackson` / `Gson` / `Fastjson` 在栈顶。

**解决**：限制 JSON 大小、使用流式解析、异步处理。

#### 场景四：锁自旋

```java
// CAS 自旋（AQS 中的逻辑）
// 高并发下大量线程争抢同一把锁，CAS 不断失败重试
// 表现为 CPU 高但没有明显死循环代码
```

**排查**：jstack 中大量线程状态为 `RUNNABLE`，栈顶是 `Unsafe.compareAndSwapInt`。

**解决**：减小锁粒度（分段锁 / 读写锁）、限流、异步化。

## 第三章 内存问题排查（OOM / 内存泄漏）

### 3.1 OOM 的六种类型

| OOM 类型 | 含义 | 常见原因 |
|----------|------|----------|
| `Java heap space` | 堆内存不足 | 大对象、内存泄漏、堆太小 |
| `GC overhead limit` | GC 花费 > 98% 时间但回收 < 2% | 频繁 GC 但几乎回收不了 |
| `Metaspace` | 元空间不足 | 动态生成类太多（CGLIB/反射） |
| `Direct buffer memory` | 堆外内存不足 | NIO DirectBuffer 泄漏 |
| `Unable to create new native thread` | 无法创建线程 | 线程数超限 / 内存不足 |
| `StackOverflowError` | 栈溢出 | 递归太深 / 栈帧太大 |

### 3.2 OOM 自动 Dump 配置

```bash
# 启动参数加上（务必配置！）
-Xmx2g -Xms2g
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dumps/oom_%p_%t.hprof
-XX:+HeapDumpAfterFullGC    # Full GC 后也 dump（可选）
-XX:HeapDumpPath=/data/dumps/
```

**生产建议**：所有线上 JVM 必须配置 `-XX:+HeapDumpOnOutOfMemoryError`。

### 3.3 堆内存排查流程

#### 步骤一：确认是否 OOM

```bash
# 查看系统日志
$ dmesg -T | grep -i "out of memory"
$ dmesg -T | grep -i "killed process"

# 查看 JVM 日志
$ grep "OutOfMemoryError" /path/to/app.log
```

#### 步骤二：查看堆内存概况

```bash
# jmap 查看堆使用情况
$ jmap -heap <pid>

# 输出示例：
Heap Configuration:
   MinHeapFreeRatio = 40
   MaxHeapFreeRatio = 70
   MaxHeapSize      = 2147483648 (2048.0MB)  ← 堆大小
Heap Usage:
PS Young Generation
   Eden Space: 45% used
   Survivor Space: 30% used
PS Old Generation
   Old Generation: 92% used  ← 老年代快满了！
```

#### 步骤三：查看对象统计

```bash
# 查看堆中对象统计（按大小排序）
$ jmap -histo:live <pid> | head -20

# 输出示例：
 num     #instances         #bytes  class name
   1:       15234567      731259216  [B                    ← byte 数组占 700MB！
   2:        3456789      221234176  java.lang.String
   3:        1234567      118378432  java.util.HashMap$Node
   4:         567890       45431200  com.example.OrderItem  ← 业务对象多
```

**注意**：`jmap -histo:live` 会触发 Full GC，生产环境谨慎使用！

#### 步骤四：Dump 堆内存

```bash
# 手动 dump（不触发 GC）
$ jmap -dump:format=b,file=heap.hprof <pid>

# 或用 Arthas（推荐，更安全）
[arthas@12345]$ heapdump /data/dumps/heap.hprof
```

#### 步骤五：MAT 分析

使用 **Eclipse MAT**（Memory Analyzer Tool）分析 `.hprof` 文件：

1. **Histogram**：按类统计对象数量和大小
2. **Dominator Tree**：按支配关系展示谁持有最多内存
3. **Leak Suspects Report**：自动分析可疑泄漏点
4. **Path to GC Roots**：找到对象到 GC Roots 的引用链（为什么无法回收）

**MAT 关键概念**：
- **Shallow Heap**：对象自身占用的内存
- **Retained Heap**：对象被回收后能释放的总内存（包括其引用的所有对象）
- **Dominator**：如果一个对象到 GC Roots 必须经过另一个对象，后者就是前者的 Dominator

#### 步骤六：定位泄漏代码

在 MAT 中找到 Retained Heap 最大的对象 → 右键 `Path to GC Roots` → `exclude weak/soft references` → 查看引用链 → 定位到具体代码中的集合 / 缓存 / 静态变量。

### 3.4 常见内存泄漏场景

#### 场景一：静态集合无限增长

```java
// 最经典的内存泄漏
public class CacheManager {
    private static final Map<String, Object> CACHE = new HashMap<>();

    public static void put(String key, Object value) {
        CACHE.put(key, value);  // 只放不清 → 内存泄漏
    }
    // 忘记写 remove / 没有过期机制
}
```

**排查**：MAT 中看到 `HashMap` 占据大量内存，且引用链指向静态变量。

**解决**：使用 `WeakHashMap`、`Caffeine`（带过期）、或定期清理。

#### 场景二：ThreadLocal 泄漏

```java
// 线程池中 ThreadLocal 不 remove
executor.submit(() -> {
    ThreadLocal<UserContext> ctx = new ThreadLocal<>();
    ctx.set(currentUser);
    // 使用 ctx ...
    // 忘记 ctx.remove() → 线程复用，ThreadLocal 中的对象无法回收
});
```

**排查**：jmap -histo 中 `ThreadLocal$ThreadLocalMap$Entry` 大量存在，且 value 持有大对象。

**解决**：使用完务必 `threadLocal.remove()`，或用 `try-finally` 保证清理。

#### 场景三：连接 / 资源未关闭

```java
// InputStream 未关闭
public void readFile(String path) {
    InputStream is = new FileInputStream(path);
    // 读到一半抛异常 → is 没有关闭 → 文件句柄泄漏 + 内存泄漏
    // 最终可能导致 "Too many open files"
}
```

**解决**：使用 `try-with-resources`。

#### 场景四：监听器 / 回调未注销

```java
// 注册了监听器但没注销
public class MyService implements Listener {
    public MyService(EventBus eventBus) {
        eventBus.register(this);  // 注册
    }
    // 服务停止时没有 eventBus.unregister(this)
    // → EventBus 持有 MyService 引用 → 无法回收
}
```

**解决**：生命周期结束时注销。

#### 场景五：内部类持有外部类引用

```java
// 非静态内部类隐式持有外部类引用
public class Outer {
    class Inner {
        // Inner 隐式持有 Outer.this
        // 如果 Inner 被放入静态集合 → Outer 也无法回收
    }
}
```

**解决**：内部类改为 `static class`。

### 3.5 堆外内存泄漏排查

**症状**：进程 RES 内存远大于堆大小，但 jmap / MAT 看不到大对象。

#### 排查方法

```bash
# 方法一：NMT (Native Memory Tracking)
# 启动参数加 -XX:NativeMemoryTracking=detail
$ jcmd <pid> VM.native_memory summary

# 输出示例：
Total: reserved=5678MB, committed=3234MB
-                 Java Heap:  reserved=2048MB, committed=2048MB
-                     Class:  reserved=1064MB, committed=456MB    ← Metaspace
-                    Thread:  reserved=500MB, committed=300MB     ← 线程栈
-                      Code:  reserved=245MB, committed=245MB
-                        GC:  reserved=300MB, committed=300MB
-                  Internal:  reserved=890MB, committed=678MB    ← 堆外！
```

```bash
# 方法二：查看 DirectBuffer 统计
$ jcmd <pid> VM.native_memory detail | grep -i direct

# 方法三：jmx 查看 DirectBuffer 池
[arthas@12345]$ dashboard  # 查看 NonHeapMemoryUsage
```

#### 常见原因

1. **Netty 的 PooledByteBufAllocator 泄漏**：ByteBuf 未 release
2. **NIO DirectByteBuffer 泄漏**：分配了堆外内存未释放
3. **JNI Native 内存泄漏**：C/C++ 代码 malloc 不 free
4. **线程栈**：线程数太多导致线程栈占用过多

#### Netty 堆外泄漏排查

```java
// 启用 Netty 泄漏检测（生产用 ADVANCED，排查用 PARANOID）
-Dio.netty.leakDetection.level=PARANOID

// 日志中会出现：
// LEAK: ByteBuf.release() was not called before it's garbage-collected
```

### 3.6 Metaspace OOM

```bash
# 查看 Metaspace 使用
$ jstat -gcutil <pid> 1000
#  M 列 = Metaspace 使用率，如果接近 100% → Metaspace OOM

# 查看 Metaspace 参数
$ jinfo -flag MetaspaceSize <pid>
$ jinfo -flag MaxMetaspaceSize <pid>
```

**常见原因**：
1. 动态生成类太多（CGLIB 代理、反射、Groovy 脚本）
2. 类加载器泄漏（Tomcat 热部署不清理旧的 ClassLoader）

**解决**：
- 增大 `-XX:MaxMetaspaceSize=512m`
- 排查动态类生成
- 排查 ClassLoader 泄漏

### 3.7 "Unable to create new native thread" 排查

```bash
# 查看线程数
$ jstack <pid> | grep "java.lang.Thread.State" | wc -l

# 查看系统线程限制
$ ulimit -u        # 用户最大进程/线程数
$ cat /proc/sys/kernel/threads-max  # 系统最大线程数

# 查看每个线程的栈大小
$ jinfo -flag ThreadStackSize <pid>
# 默认 1MB，2000 个线程 = 2GB 内存
```

**常见原因**：
1. 线程池配置过大（`new ThreadPoolExecutor(10000, 10000, ...)`）
2. 每次请求创建新线程（没用线程池）
3. 线程泄漏（创建后不销毁）

**解决**：
- 合理配置线程池大小
- 减小 `-Xss`（如 `-Xss256k`）
- 排查线程泄漏

## 第四章 GC 问题排查

### 4.1 GC 问题分类

```
GC 问题
├── Young GC 过频
│   ├── 对象分配速率过高（循环内创建大量临时对象）
│   ├── Eden 区太小（-Xmn 设太小）
│   └── TLAB 不够用
│
├── Full GC 频繁
│   ├── 老年代空间不足（内存泄漏 / 大对象晋升）
│   ├── Metaspace 不足（类加载触发）
│   ├── System.gc() 被调用（代码 / 框架触发）
│   ├── CMS 的 Concurrent Mode Failure
│   └── 大对象直接进老年代（-XX:PretenureSizeThreshold）
│
├── GC 停顿过长（STW）
│   ├── 老年代太大（一次 Full GC 扫描很久）
│   ├── G1 的 Mixed GC 暂停过长
│   └── CMS 的 Remark 阶段慢
│
└── GC 吞吐量低
    ├── GC 频率太高 → 应用工作时间少
    └── 单次 GC 时间太长
```

### 4.2 jstat 实时监控 GC

```bash
# 每秒打印一次 GC 统计，共 10 次
$ jstat -gcutil <pid> 1000 10

  S0     S1     E      O      M     CCS    YGC   YGCT   FGC  FGCT   GCT
  0.00  85.42  73.22  45.15  94.12  91.34  152  3.456   2   0.234  3.690
  0.00  85.42  85.33  45.15  94.12  91.34  153  3.478   2   0.234  3.712
  0.00  85.42  96.44  45.15  94.12  91.34  154  3.501   2   0.234  3.735
 85.42   0.00   5.22  45.15  94.12  91.34  155  3.523   2   0.234  3.757
```

**列含义**：

| 列 | 含义 | 关注点 |
|----|------|--------|
| S0/S1 | Survivor 0/1 使用率 | — |
| E | Eden 使用率 | 持续在 90%+ → YGC 频繁 |
| O | 老年代使用率 | 持续增长 → 可能内存泄漏 |
| M | Metaspace 使用率 | 接近 100% → Metaspace OOM |
| YGC | Young GC 次数 | 增长快 → 对象分配快 |
| YGCT | Young GC 总时间 | — |
| FGC | Full GC 次数 | **增长快 = 严重问题** |
| FGCT | Full GC 总时间 | 单次 > 1s → STW 严重影响 |
| GCT | GC 总时间 | — |

**判断标准**：
- `FGC` 持续增长 → Full GC 频繁，转 4.4
- `O` 持续增长不回落 → 内存泄漏，转第三章
- `YGC` 增长快但 `FGC` 不增长 → Young GC 频繁，转 4.3

### 4.3 Young GC 过频排查

**原因**：Eden 区太小 / 对象分配太快。

```bash
# 查看堆配置
$ jmap -heap <pid> | grep -i eden
# Eden Size 小 → 增大 -Xmn 或调整 Eden/Survivor 比例
```

**常见代码问题**：

```java
// 问题1：循环内创建大量临时对象
for (int i = 0; i < 100000; i++) {
    String s = new String("item" + i);  // 每次创建新对象
    list.add(s);
}
// 解决：用 StringBuilder 或 String.valueOf

// 问题2：日志中拼接大字符串
log.debug("data: " + hugeJson);  // 即使日志级别不输出，也会拼接字符串
// 解决：log.debug("data: {}", hugeJson);  // 占位符，级别不够不拼接

// 问题3：大 List 频繁创建
List<Integer> list = new ArrayList<>();
for (int i = 0; i < 1000000; i++) {
    list.add(i);  // ArrayList 扩容创建大量数组
}
// 解决：new ArrayList<>(1000000);  // 预分配容量
```

### 4.4 Full GC 频繁排查

#### 原因一：老年代空间不足

```bash
# 确认老年代使用率
$ jstat -gcutil <pid> 1000
# O 列持续 > 90% 且 FGC 增长 → 老年代不够用
```

**排查**：
1. 是否内存泄漏 → jmap -histo:live 看大对象 → 第三章
2. 是否大对象直接进老年代 → 检查 `-XX:PretenureSizeThreshold`
3. 是否 Survivor 太小导致对象过早晋升 → 调大 `-XX:SurvivorRatio`

#### 原因二：System.gc() 被调用

```bash
# 查看是否禁用了 System.gc()
$ jinfo -flag DisableExplicitGC <pid>
# 如果没设置 → 添加 -XX:+DisableExplicitGC
```

**检查代码**：
```bash
# 搜索代码中是否有 System.gc() 调用
$ grep -rn "System.gc()" /path/to/source/
```

**常见来源**：
- RMI 框架（默认 1 小时调用一次 `System.gc()`）
- DirectByteBuffer 分配时（内存不足时触发）
- 第三方库（如某些序列化库）

#### 原因三：CMS Concurrent Mode Failure

```
CMS 回收期间老年代空间不足 → 退化为 Serial Old（单线程 Full GC）→ STW 很长
```

**排查**：
```bash
# 查看 GC 日志
$ grep "concurrent mode failure" gc.log
```

**解决**：
- 降低 CMS 触发阈值：`-XX:CMSInitiatingOccupancyFraction=70`（老年代 70% 就开始 CMS）
- 增大老年代

#### 原因四：Metaspace 触发 Full GC

```bash
$ jstat -gcutil <pid> 1000
# M 列接近 100% → Metaspace 不足触发 Full GC
```

**解决**：`-XX:MaxMetaspaceSize=512m` 增大上限。

### 4.5 GC 日志分析

#### 启用 GC 日志

```bash
# JDK 8
-XX:+PrintGCDetails
-XX:+PrintGCDateStamps
-Xloggc:/data/logs/gc.log
-XX:+UseGCLogFileRotation
-XX:NumberOfGCLogFiles=10
-XX:GCLogFileSize=50M

# JDK 11+
-Xlog:gc*:file=/data/logs/gc.log:time,uptime:filecount=10,filesize=50M
```

#### GC 日志关键字

| 日志关键字 | 含义 | 是否问题 |
|------------|------|----------|
| `GC pause (G1 Evacuation Pause) (young)` | G1 Young GC | 正常 |
| `GC pause (G1 Evacuation Pause) (mixed)` | G1 Mixed GC | 正常 |
| `Full GC` | Full GC | ⚠️ 关注频率 |
| `concurrent mode failure` | CMS 失败退化为串行 | ❌ 严重 |
| `concurrent mode interrupted` | CMS 被中断 | ⚠️ |
| `Allocation Failure` | 分配失败触发 GC | 正常 |
| `Promotion Failed` | 晋升失败 | ❌ 严重 |
| `To-space exhausted` | Survivor 空间不足 | ⚠️ |
| `Metaspace GC` | Metaspace 触发 GC | ⚠️ |

#### 使用 GCEasy / GCViewer 分析

上传 GC 日志到 [gceasy.io](https://gceasy.io) 在线分析，关注：
- **吞吐量**：应用运行时间占比（应 > 95%）
- **平均 GC 停顿**（应 < 200ms）
- **最大 GC 停顿**（应 < 1s）
- **Full GC 频率**（应极少或为 0）

### 4.6 GC 参数调优建议

| 场景 | 推荐 GC | 参数建议 |
|------|---------|----------|
| 低延迟（< 100ms STW） | G1 | `-XX:+UseG1GC -XX:MaxGCPauseMillis=100` |
| 大堆（> 8GB） | ZGC / Shenandoah | `-XX:+UseZGC` |
| 高吞吐 | Parallel GC（默认 JDK 8） | `-XX:+UseParallelGC` |
| 老系统不想改 | CMS（JDK 8） | `-XX:+UseCMSInitiatingOccupancyOnly -XX:CMSInitiatingOccupancyFraction=70` |

**G1 调优关键参数**：

```bash
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200        # 期望最大停顿时间
-XX:G1HeapRegionSize=16m        # Region 大小（1/2/4/8/16/32m）
-XX:InitiatingHeapOccupancyPercent=45  # 堆使用率到 45% 开始并发标记
-XX:G1ReservePercent=15         # 保留空间防止晋升失败
```

## 第五章 线程问题排查（死锁 / 阻塞 / 线程泄漏）

### 5.1 线程状态一览

```
Java 线程六种状态：
NEW          → 新建未启动
RUNNABLE     → 运行中 / 就绪（包含 OS 层的 Running 和 Ready）
BLOCKED      → 等待 synchronized 监视器锁
WAITING      → 无限等待（wait / join / LockSupport.park 无超时）
TIMED_WAITING→ 限时等待（sleep / wait(timeout) / join(timeout)）
TERMINATED   → 终止
```

**jstack 中常见状态与含义**：

| 状态 | 含义 | 是否问题 |
|------|------|----------|
| `RUNNABLE` | 正在执行 / 等待 CPU | 正常（但 CPU 高要注意） |
| `BLOCKED (on object monitor)` | 等待 synchronized 锁 | ⚠️ 可能锁竞争 |
| `waiting on condition` | 等待某个条件（Lock / IO） | 看场景 |
| `WAITING (on object monitor)` | `Object.wait()` | 看场景 |
| `TIMED_WAITING (sleeping)` | `Thread.sleep()` | 正常 |
| `TIMED_WAITING (parking)` | `LockSupport.parkNanos()` | 线程池空闲 |

### 5.2 死锁排查

#### 经典死锁代码

```java
// 线程 1：先锁 A 再锁 B
new Thread(() -> {
    synchronized (lockA) {
        synchronized (lockB) {
            // do something
        }
    }
}).start();

// 线程 2：先锁 B 再锁 A
new Thread(() -> {
    synchronized (lockB) {
        synchronized (lockA) {
            // do something
        }
    }
}).start();
```

#### 排查步骤

```bash
# 方法一：jstack 自动检测死锁
$ jstack <pid>
# 如果有死锁，会在输出末尾打印：
# Found one Java-level deadlock:
# =============================
# "Thread-1":
#   waiting to lock monitor 0x00007f8b0c00a880 (object 0x000000076b6a4a98, a java.lang.Object),
#   which is held by "Thread-0"
# "Thread-0":
#   waiting to lock monitor 0x00007f8b0c00b880 (object 0x000000076b6a4aa8, a java.lang.Object),
#   which is held by "Thread-1"
```

```bash
# 方法二：jcmd 检测
$ jcmd <pid> Thread.print

# 方法三：Arthas
[arthas@12345]$ thread -b   # 找出阻塞其他线程的线程
[arthas@12345]$ thread --state BLOCKED  # 查看 BLOCKED 线程
```

#### 死锁的四个必要条件

```
1. 互斥：资源同一时刻只能被一个线程使用
2. 持有并等待：线程持有资源同时等待另一个资源
3. 不可剥夺：资源不能被强制抢占
4. 循环等待：线程形成环形等待链
```

#### 解决死锁

| 方案 | 做法 |
|------|------|
| 破坏循环等待 | 统一锁的获取顺序（所有线程先锁 A 再锁 B） |
| 破坏持有并等待 | 一次性获取所有锁 |
| 破坏不可剥夺 | 使用 `tryLock(timeout)` 超时放弃 |
| 避免嵌套锁 | 尽量不嵌套加锁 |

### 5.3 线程阻塞排查

**现象**：接口响应变慢，但 CPU 不高。

```bash
# 查看线程状态分布
$ jstack <pid> | grep "java.lang.Thread.State" | sort | uniq -c | sort -rn

# 输出示例：
  150 RUNNABLE                ← 正常
   80 TIMED_WAITING (parking) ← 线程池空闲，正常
   45 BLOCKED                 ← 45 个线程被阻塞！有问题
   12 WAITING (on object monitor) ← 在 wait，可能正常
    3 TIMED_WAITING (sleeping) ← sleep，看场景
```

**如果大量 BLOCKED**：

```bash
# 查看哪个线程持有了锁
$ jstack <pid> | grep -B5 "waiting to lock"
# 找到持有锁的线程，分析它为什么长时间不释放
```

**常见原因**：
1. 某段代码 `synchronized` 块内有耗时操作（如 DB 查询、远程调用）
2. 锁粒度过大
3. 某个线程持锁后阻塞在 IO 上

**解决**：
- 缩小锁范围（只在必要部分加锁）
- 使用读写锁 `ReentrantReadWriteLock`
- 使用 `ConcurrentHashMap` 等并发容器替代 `synchronized HashMap`

### 5.4 线程池问题排查

#### 线程池满了

```java
// 现象：RejectedExecutionException
java.util.concurrent.RejectedExecutionException: ...
```

**排查**：

```bash
# 查看线程池运行状态（Arthas）
[arthas@12345]$ ognl '@com.example.config.ThreadPoolConfig@executor'
# 查看 activeCount、queueSize、completedTaskCount
```

**常见原因**：
1. 任务执行太慢（下游慢 / 大量 IO）
2. 队列太小
3. 线程数太少

**解决**：
- 调大 `corePoolSize` / `maxPoolSize`
- 调大队列容量
- 设置合理的拒绝策略（`CallerRunsPolicy` 回压）
- 排查任务执行慢的根因

#### 线程泄漏

```java
// 每次请求创建新线程，不复用
new Thread(() -> {
    // 处理请求
}).start();
// 线程数持续增长 → 最终 "Unable to create new native thread"
```

**排查**：
```bash
# 统计线程数
$ jstack <pid> | grep "java.lang.Thread.State" | wc -l

# 如果持续增长 → 线程泄漏
```

**解决**：用线程池替代 `new Thread()`。

### 5.5 线程 CPU 使用率排查

```bash
# 找出 CPU 使用最高的线程
$ top -Hp <pid>

# 转换线程 ID
$ printf "%x\n" <tid>

# jstack 查看该线程在做什么
$ jstack <pid> | grep <nid> -A 30
```

**或用 Arthas**：

```bash
# 查看最忙的 5 个线程
[arthas@12345]$ thread -n 5

# 查看 CPU 使用率 > 10% 的线程
[arthas@12345]$ thread --cpu 10
```

### 5.6 jstack 分析技巧

#### 抓多次 jstack 对比

```bash
# 连续抓 3 次，间隔 5 秒
$ jstack <pid> > t1.txt
$ sleep 5
$ jstack <pid> > t2.txt
$ sleep 5
$ jstack <pid> > t3.txt

# 对比哪些线程一直在同一个位置 → 可能卡住
$ diff t1.txt t2.txt
```

**关键原则**：
- 如果同一个线程在多次 jstack 中停在**同一段代码** → 很可能卡住了
- 如果线程在不同代码行 → 正常执行中

#### 使用在线工具分析

- [fastthread.io](https://fastthread.io)：上传 jstack 文件在线分析
- [jstack.review](https://jstack.review)：可视化线程状态

## 第六章 响应慢排查（全链路）

### 6.1 响应慢的可能原因

```
接口 RT 飙升
├── 应用层
│   ├── CPU 高（转第二章）
│   ├── GC 频繁（转第四章）
│   ├── 线程阻塞（转第五章）
│   ├── 锁竞争
│   └── 序列化/反序列化慢
│
├── 数据库层
│   ├── 慢查询（转第七章）
│   ├── 连接池耗尽
│   ├── 死锁
│   └── 主从延迟
│
├── 缓存层
│   ├── 缓存击穿/雪崩
│   ├── 大 Key / 热点 Key
│   └── Redis 单线程阻塞
│
├── 网络层
│   ├── 带宽不足
│   ├── DNS 解析慢
│   ├── TCP 重传
│   └── 连接池耗尽
│
├── 下游服务
│   ├── 下游服务慢
│   ├── 超时设置不合理
│   └── 重试风暴
│
└── JVM 层
    ├── JIT 未预热（冷启动慢）
    ├── 大对象分配触发 GC
    └── 锁偏向撤销
```

### 6.2 全链路排查步骤

#### 第一步：确认是哪个接口慢

```bash
# 查看应用日志中 RT 高的接口
$ grep "rt" /path/to/access.log | sort -t'=' -k2 -rn | head -20

# 或在 APM 系统（SkyWalking / Pinpoint / Jaeger）中看
```

#### 第二步：确认是单实例还是全局

```
- 单实例慢 → 可能是该实例资源问题（CPU/内存/GC）
- 全局慢 → 共同依赖问题（DB / Redis / 下游服务）
```

#### 第三步：分层排查

```
应用层：
  1. top -Hp <pid> → CPU 高的线程在做什么？
  2. jstat -gcutil <pid> 1000 → GC 频繁吗？
  3. jstack <pid> → 线程在 BLOCKED / WAITING 吗？

数据库层：
  1. 慢查询日志开启了吗？
  2. SHOW PROCESSLIST → 有没有慢 SQL？
  3. 连接池监控 → 连接数够吗？

缓存层：
  1. redis-cli --latency → Redis 延迟正常吗？
  2. redis-cli --bigkeys → 有大 Key 吗？
  3. Redis slowlog → 有慢命令吗？

网络层：
  1. ping / traceroute → 网络延迟
  2. netstat → 连接状态
```

#### 第四步：APM 链路追踪

在 **SkyWalking / Pinpoint / Jaeger** 中找到慢请求的 Trace ID，查看每一段耗时：

```
Trace: abc-123
  ├─ Gateway:          2ms
  ├─ Service-A:        5ms
  │   ├─ Redis get:    1ms
  │   ├─ MySQL query:  850ms  ← 卡在这里！
  │   └─ Service-B:    10ms
  └─ Response:         867ms
```

### 6.3 数据库连接池排查

```java
// HikariCP 监控
HikariPoolMXBean pool = ...;
log.info("Active: {}, Idle: {}, Wait: {}",
    pool.getActiveConnections(),
    pool.getIdleConnections(),
    pool.getThreadsAwaitingConnection());
```

**如果 `threadsAwaitingConnection > 0`**：连接池不够用，可能是：
- 慢 SQL 占用连接太久
- 连接泄漏（忘记关闭）
- 连接池配置太小

**排查连接泄漏**：

```bash
# 查看 totalConnections / activeConnections / idleConnections

# 查看哪些线程在等待连接

# 看到大量 "HikariPool-1 - Connection available" 的 WAITING 线程
```

```bash
# 大 Key 扫描
```

**常见 Redis 慢的原因**：

| 原因 | 排查 | 解决 |
|------|------|------|
| 大 Key（value 几 MB） | `--bigkeys` | 拆分 / 删除 |
| 热点 Key | `redis-cli --hotkeys` | 本地缓存 / 多副本 |
| KEYS 命令 | `slowlog get` | 用 SCAN 替代 |

### 6.5 下游调用慢排查

```java
// 检查 HTTP 客户端超时配置
HttpClient client = HttpClient.newBuilder()
    .connectTimeout(Duration.ofSeconds(3))   // 连接超时
    .build();

HttpRequest request = HttpRequest.newBuilder()
    .timeout(Duration.ofSeconds(5))           // 读取超时
    .uri(URI.create(url))
    .build();
```

**常见问题**：
- 没设超时 → 线程被永久阻塞
- 超时太长 → 下游慢拖垮自己
- 重试太多 → 雪崩放大

**解决**：
- 所有外部调用必须设超时
- 超时时间 = 正常 RT 的 3~5 倍
- 使用熔断器（Sentinel / Hystrix / Resilience4j）

### 7.1 慢查询排查

#### 开启慢查询日志

```sql
-- MySQL 动态开启
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;  -- 超过 1 秒记录

```

#### 使用 EXPLAIN 分析

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 12345 AND status = 'PAID';
```

**重点关注的列**：

| 列 | 关注点 |
|----|--------|
| `type` | `ALL`（全表扫描）❌ / `index`（全索引扫描）⚠️ / `ref`（索引查找）✓ / `eq_ref` ✓ |
| `key` | 实际使用的索引，`NULL` = 没用索引 |
| `rows` | 预估扫描行数，越大越慢 |
| `Extra` | `Using filesort`（额外排序）⚠️ / `Using temporary`（临时表）⚠️ / `Using index`（覆盖索引）✓ |

#### 慢查询优化方向

```
慢查询优化优先级：

1. 加索引（最直接有效）
   - WHERE 条件字段加索引
   - JOIN 关联字段加索引
   - ORDER BY 字段加索引

2. 优化查询
   - 避免 SELECT *，只查需要的列
   - 避免 LEFT JOIN 多表
   - 用 LIMIT 分页
   - 避免子查询，改为 JOIN

3. 避免索引失效
   - 避免在索引列上做运算：WHERE DATE(create_time) = '2024-01-01' → 改为范围查询
   - 避免类型隐式转换：WHERE phone = 13800138000（字符串字段传数字）
   - 避免 != / NOT IN / OR
   - 模糊查询 LEFT LIKE '%xxx' 无法用索引

4. 分库分表（数据量极大时）
```

### 7.2 死锁排查

#### 查看死锁日志

```sql
-- 查看最近一次死锁信息
SHOW ENGINE INNODB STATUS\G

-- 在输出中找 LATEST DETECTED DEADLOCK 部分：
-- *** (1) TRANSACTION:
-- TRANSACTION 12345, ACTIVE 2 sec starting index read
-- mysql tables in use 1, locked 1
-- LOCK WAIT 3 lock struct(s), heap size 1136, 2 row lock(s)
-- MySQL thread id 10, OS thread handle 140123456, query id 100 updating
-- UPDATE account SET balance = balance - 100 WHERE id = 1
-- *** (1) WAITING FOR THIS LOCK TO BE GRANTED:
-- RECORD LOCKS space id 50 page no 3 n bits 72 index PRIMARY of table `test`.`account`
-- *** (2) TRANSACTION:
-- TRANSACTION 12346, ACTIVE 2 sec starting index read
-- UPDATE account SET balance = balance - 100 WHERE id = 2
-- *** (2) HOLDS THE LOCK(S):
-- RECORD LOCKS ... index PRIMARY ... WHERE id = 1
-- *** (2) WAITING FOR THIS LOCK TO BE GRANTED:
-- RECORD LOCKS ... WHERE id = 2
```

**分析死锁日志**：
1. 事务 1 在等 `id=1` 的行锁
2. 事务 2 持有 `id=1` 的行锁，在等 `id=2` 的行锁
3. 事务 1 持有 `id=2` 的行锁 → 循环等待 → 死锁

#### 当前锁等待

```sql
-- 查看当前锁等待
SELECT * FROM information_schema.INNODB_LOCKS;
SELECT * FROM information_schema.INNODB_LOCK_WAITS;

-- MySQL 8.0+
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;

-- 查看当前事务
SELECT * FROM information_schema.INNODB_TRX;

-- 杀掉死锁事务
KILL <trx_id>;
```

#### 死锁常见场景

**场景一：不同顺序更新**

```java
// 事务 A：先更新 1 再更新 2
@Transactional
public void transferA() {
    accountMapper.update(1, -100);
    accountMapper.update(2, +100);
}

// 事务 B：先更新 2 再更新 1
@Transactional
public void transferB() {
    accountMapper.update(2, -100);
    accountMapper.update(1, +100);
}
// → 死锁
```

**解决**：统一更新顺序（所有事务先更新 ID 小的再更新 ID 大的）。

**场景二：间隙锁死锁**

```sql
-- 事务 A
SELECT * FROM orders WHERE id BETWEEN 100 AND 200 FOR UPDATE;
-- 锁定了 (100, 200) 的间隙

-- 事务 B
INSERT INTO orders (id, ...) VALUES (150, ...);
-- 被间隙锁阻塞

-- 如果此时事务 A 也想 INSERT → 死锁
```

**解决**：缩小事务范围、使用 RC 隔离级别（但有幻读风险）。

**场景三：唯一键冲突死锁**

```sql
-- 并发 INSERT 同一唯一键 → 唯一索引冲突 → 死锁
INSERT INTO users (email, name) VALUES ('a@b.com', 'A');
INSERT INTO users (email, name) VALUES ('a@b.com', 'B');
```

**解决**：先 SELECT 再 INSERT，或使用 `INSERT ... ON DUPLICATE KEY UPDATE`。

### 7.3 连接数飙升

```sql
-- 查看当前连接数
SHOW STATUS LIKE 'Threads_connected';

-- 查看最大连接数
SHOW VARIABLES LIKE 'max_connections';

-- 查看活跃连接
```

**常见原因**：
1. 连接泄漏（未关闭）
2. 应用实例太多 / 连接池太大
3. 慢查询占住连接

### 7.4 主从延迟排查

```sql
-- 在从库执行
SHOW SLAVE STATUS\G

-- 关注：
-- Seconds_Behind_Master: 0  ← 正常
-- Seconds_Behind_Master: 300 ← 延迟 5 分钟！
```

**常见原因**：
1. 大事务（一次更新百万行）
2. 从库性能差
3. 网络延迟
4. 从库单线程回放（MySQL 5.6 及之前）

**解决**：
- 拆分大事务
- 使用并行复制（MySQL 5.7+ `slave_parallel_workers`）
- 读非实时数据走从库，实时数据走主库

### 8.2 连接相关排查

```bash
# 查看各状态连接数
$ netstat -an | awk '/tcp/ {print $NF}' | sort | uniq -c | sort -rn

# 输出示例：
  345 ESTABLISHED    ← 正常连接
  128 TIME_WAIT       ← 主动关闭后的等待，太多会有问题
   12 CLOSE_WAIT      ← 被动关闭后未关闭，⚠️ 可能泄漏
    3 LISTEN
```

**TIME_WAIT 过多**：

```bash
# 大量 TIME_WAIT 说明短连接太多

# 2. 调整内核参数

$ sysctl -w net.ipv4.tcp_max_tw_buckets=5000  # 限制数量
```

**CLOSE_WAIT 过多**：

```
CLOSE_WAIT = 对方关闭了连接，但本地应用没有 close()
→ 通常是代码 bug：连接/流没有正确关闭
→ 排查 jstack 中的 Socket 相关栈
```

## 第十一章 日志排查与告警体系

### 11.1 日志排查原则

#### 日志等级使用规范

| 等级 | 使用场景 | 生产环境 |
|------|----------|----------|
| ERROR | 系统异常 / 影响功能 | 必须输出 + 告警 |
| WARN | 可预期异常 / 降级 | 输出，关注 |
| INFO | 关键业务节点（下单/支付） | 输出 |
| DEBUG | 调试信息 | **默认关闭** |
| TRACE | 极细粒度调试 | **默认关闭** |

#### 日志排查技巧

```bash
# 1. 按时间过滤
$ grep "2024-01-01 10:00:5" app.log  # 精确到秒

# 2. 按 Trace ID 过滤
$ grep "traceId=abc123" app.log  # 全链路

# 3. 按异常类型过滤
$ grep "NullPointerException" app.log

# 4. 统计错误频率
$ grep "ERROR" app.log | wc -l

# 5. 提取异常堆栈（grep -A 后续行）
$ grep -A 20 "Exception" app.log

# 6. 实时查看日志
$ tail -f app.log | grep "ERROR"

# 7. 多日志合并查询
$ grep "traceId=abc123" *.log
```

#### 关键日志规范

```java
// ❌ 错误：日志没有上下文
log.error("error occurred");

// ❌ 错误：日志直接打印大对象
log.info("order: " + order);  // order 可能几 MB

// ✅ 正确：关键信息 + Trace ID + 异常堆栈
log.error("创建订单失败, userId={}, orderId={}, amount={}",
    userId, orderId, amount, e);  // e 是异常对象，log 框架会打印堆栈
```

### 11.2 告警体系

#### 告警分级

| 级别 | 含义 | 响应时间 | 通知方式 |
|------|------|----------|----------|
| P0 | 系统不可用 | 立即 | 电话 + 短信 + 钉钉 |
| P1 | 核心功能受损 | 5 分钟 | 短信 + 钉钉 |
| P2 | 部分功能异常 | 15 分钟 | 钉钉 |
| P3 | 告警但可容忍 | 30 分钟 | 邮件 / 钉钉 |

#### 关键告警指标

```
基础设施告警：
  - CPU > 80% 持续 5 分钟
  - 内存使用率 > 90%
  - 磁盘使用率 > 85%
  - 网络丢包率 > 1%

JVM 告警：
  - Full GC 次数 > 5 次/小时
  - GC 停顿 > 1 秒
  - 堆内存使用率 > 85%
  - 线程数 > 1000

应用告警：
  - 接口错误率 > 1%
  - 接口 P99 RT > 500ms
  - QPS 异常下降 > 30%
  - 熔断 / 限流触发

中间件告警：
  - 数据库慢查询 > 1 秒
  - Redis 延迟 > 10ms
  - MQ 消息积压 > 10000
  - 连接池使用率 > 80%
```

## 第十二章 经典线上故障复盘案例

### 案例 1：Full GC 导致接口超时（CPU 飙高）

**现象**：接口大面积超时，CPU 90%+，服务不可用。

**排查过程**：

```bash
# 1. top 确认 CPU 高的进程
top → PID 12345 CPU 95%

# 2. jstat 看是否 GC 问题
jstat -gcutil 12345 1000
#  FGC 每秒+1，FGCT 持续增长 → Full GC 不停

# 3. jmap 看老年代
jmap -heap 12345
#  Old Generation: 95% used → 老年代快满了

# 4. jmap -histo:live 看大对象
jmap -histo:live 12345 | head -10
#  byte[] 占了 800MB！

# 5. dump + MAT 分析
heapdump → MAT → 发现 HashMap 中有 500 万个 Entry
# 引用链 → 静态缓存类，put 后从不 remove
```

**根因**：静态 `HashMap` 缓存无限增长，撑满老年代。

**修复**：
1. 紧急：重启服务 + 扩容堆内存
2. 根本：缓存改用 Caffeine，设置 maximumSize + expireAfterWrite
3. 预防：增加缓存大小监控告警

### 案例 2：死锁导致接口全部超时

**现象**：接口 RT 从 50ms 飙到 30s，但 CPU 不高。

**排查过程**：

```bash
# 1. jstack 查看线程状态
jstack <pid> | grep "java.lang.Thread.State" | sort | uniq -c
#  200 BLOCKED  ← 200 个线程全部阻塞！

# 2. jstack 查看死锁
jstack <pid>
#  Found one Java-level deadlock:
#  "http-nio-8080-exec-1" waiting to lock 0x1234 (held by "http-nio-8080-exec-2")
#  "http-nio-8080-exec-2" waiting to lock 0x5678 (held by "http-nio-8080-exec-1")
```

**根因**：两个接口加锁顺序不一致导致死锁。

**修复**：统一所有接口的加锁顺序。

### 案例 3：ThreadLocal 内存泄漏

**现象**：服务运行几天后 OOM。

**排查过程**：

```bash
# 1. dump 后 MAT 分析
# 发现 ThreadLocalMap$Entry 占了 1.5GB

# 2. Path to GC Roots
# 引用链：ThreadLocalMap$Entry → value → UserContext (持有大量数据)
# 线程池中线程复用，ThreadLocal 从不 remove
```

**根因**：线程池中 ThreadLocal 使用后未 remove，线程复用导致对象无法回收。

**修复**：使用 `try-finally` 保证 `ThreadLocal.remove()`。

```java
try {
    UserContext ctx = new UserContext(user);
    CONTEXT.set(ctx);
    // 业务逻辑
} finally {
    CONTEXT.remove();  // 必须！
}
```

### 案例 4：数据库慢查询拖垮连接池

**现象**：接口偶发超时，但服务正常。

**排查过程**：

```bash
# 1. jstack 发现大量线程在等待数据库连接
jstack <pid> | grep "HikariPool" -A 3
#  500 个线程 waiting for connection

# 2. 查看 HikariCP 状态
#  activeConnections = 50（全部占满）
#  idleConnections = 0
#  threadsAwaitingConnection = 500

# 3. 数据库 SHOW PROCESSLIST
#  发现 50 个连接都在执行同一条慢 SQL（3秒+）

# 4. EXPLAIN 分析
#  type: ALL（全表扫描）
#  rows: 500万
#  原因：缺少索引
```

**修复**：
1. 加索引
2. 优化 SQL
3. 连接池增加 `leakDetectionThreshold` 配置

### 案例 5：Redis 大 Key 导致服务卡顿

**现象**：服务偶发卡顿，RT 从 10ms 飙到 500ms。

**排查过程**：

```bash
# 1. Redis slowlog 查看慢命令
redis-cli slowlog get 10
#  发现 GET large_key 耗时 200ms+

# 2. 查看大 Key
redis-cli --bigkeys
#  Found big key "config:all" with 50000 个 field (Hash 类型，10MB)

# 3. 代码中一次取出整个 Hash
Map<String, String> config = redis.hgetAll("config:all");  // 200ms
```

**修复**：
1. 大 Hash 拆分为小 Hash
2. 按需 `hget` / `hmget` 取部分字段
3. 本地缓存配置减少 Redis 访问

### 案例 6：正则回溯导致 CPU 100%

**现象**：某个接口 CPU 飙到 100%，其他接口正常。

**排查过程**：

```bash
# 1. top -Hp 找到高 CPU 线程
top -Hp <pid> → TID 12378 CPU 98%

# 2. jstack 查看线程栈
jstack <pid> | grep <nid> -A 10
#  at java.util.regex.Pattern$Curly.match(Pattern.java:4148)
#  at java.util.regex.Pattern$GroupHead.match(Pattern.java:4672)
#  → 正则回溯！
```

**根因**：正则 `(a+)+b` 对输入 `aaaaaaa...!`（不匹配时）触发指数级回溯。

**修复**：
1. 正则改为占有量词 `(a++)+b`
2. 或改用其他方式校验

### 案例 7：DNS 解析超时导致偶发慢

**现象**：接口偶发慢 5-10 秒，频率约每分钟 1-2 次。

**排查过程**：

```bash
# 1. Arthas trace 发现卡在 HttpClient 调用
trace com.example.RemoteService call '#cost > 5000'
#  → HttpClient.execute() 耗时 5 秒

# 2. 但下游服务 RT 正常
# 3. 怀疑 DNS
dig www.downstream.com
#  Query time: 5000ms  ← DNS 解析 5 秒！

# 4. 检查 DNS 配置
cat /etc/resolv.conf
#  nameserver 10.0.0.53  ← 内部 DNS 偶发慢
```

**修复**：
1. JVM 设置 DNS 缓存：`-Dnetworkaddress.cache.ttl=300`
2. 使用本地 DNS 缓存（dnsmasq）
3. 配置多 DNS 服务器

### 案例 8：OOM Killed（容器被杀）

**现象**：Java 进程突然消失，应用日志中断。

**排查过程**：

```bash
# 1. 查看系统日志
dmesg -T | grep -i "killed process"
#  Killed process 12345 (java) total-vm:5g, anon-rss:2g

# 2. 原因：容器内存限制 2GB，Java 进程 RES 超过限制
#   JVM 堆 1.5GB + Metaspace 256MB + 线程栈 256MB + DirectBuffer = 超过 2GB

# 3. 检查容器配置
docker inspect <container_id> | grep Memory
#  "Memory": 2147483648  ← 2GB 限制
```

**修复**：
1. 增大容器内存限制
2. 使用 `-XX:MaxRAMPercentage=75` 让 JVM 自动感知容器限制
3. 限制堆外内存使用

```bash
# JDK 8 推荐容器化配置
-XX:+UseContainerSupport              # 感知容器限制（8u191+）
-XX:MaxRAMPercentage=75.0             # 堆使用 75% 的容器内存
-XX:InitialRAMPercentage=50.0
```

## 第十四章 面试高频题

### Q1：线上 CPU 100% 怎么排查？

**答**：标准五步走：
1. `top` 找到 CPU 最高的 Java 进程 PID
2. `top -Hp <pid>` 找到 CPU 最高的线程 TID
3. `printf "%x\n" <tid>` 将线程 ID 转为十六进制
4. `jstack <pid>` 导出线程栈，搜索十六进制线程 ID
5. 分析线程栈：如果栈顶是业务代码 → 死循环 / 密集计算；如果是 GC 线程 → 转为排查 GC 问题（`jstat -gcutil` 看 Full GC 频率）；如果是 `Unsafe.compareAndSwap` → 锁自旋

### Q2：线上 OOM 怎么排查？

**答**：分四步：
1. 确认 OOM 类型（`Java heap space` / `Metaspace` / `Direct buffer` / `GC overhead`）
2. 如果有 HeapDump（配置了 `-XX:+HeapDumpOnOutOfMemoryError`），用 MAT 分析
3. MAT 中查看 Dominator Tree 找 Retained Heap 最大的对象，Path to GC Roots 找引用链
4. 根据引用链定位到代码中的静态变量 / 集合 / 缓存 / ThreadLocal，通常是"只进不出"导致泄漏

如果没有 dump 文件，用 `jmap -histo:live <pid>` 查看对象统计，结合代码分析。

### Q3：线上接口响应慢怎么排查？

**答**：分层排查：
1. **确认范围**：单实例还是全局？单个接口还是所有接口？
2. **应用层**：`top -Hp` 看 CPU，`jstat` 看 GC，`jstack` 看线程状态（是否 BLOCKED）
3. **数据库层**：慢查询日志 + EXPLAIN + 连接池监控
4. **缓存层**：Redis slowlog + bigkeys + 延迟检测
5. **下游服务**：APM 链路追踪看每一段耗时
6. **网络层**：ping / tcpdump 看网络延迟和丢包

核心是找到**耗时在哪一层**，而不是盲目排查。

### Q4：如何排查死锁？

**答**：三种方法：
1. `jstack <pid>`：如果有死锁，会在末尾自动打印 "Found one Java-level deadlock" 和死锁详情
2. `jcmd <pid> Thread.print`：同 jstack
3. Arthas `thread -b`：找出阻塞其他线程最多的线程

死锁日志中会显示每个线程持有什么锁、等待什么锁，据此定位到代码中的加锁位置。解决方法是统一加锁顺序或使用 `tryLock` 超时机制。

### Q5：Full GC 频繁怎么排查？

**答**：`jstat -gcutil <pid> 1000` 观察 FGC 是否在增长。Full GC 常见原因：
1. **老年代空间不足**：`O` 列接近 100%，排查内存泄漏（`jmap -histo:live`）
2. **System.gc() 被调用**：检查代码 + 添加 `-XX:+DisableExplicitGC`
3. **Metaspace 不足**：`M` 列接近 100%，增大 `-XX:MaxMetaspaceSize`
4. **CMS Concurrent Mode Failure**：降低 `-XX:CMSInitiatingOccupancyFraction`
5. **大对象直接进老年代**：检查 `-XX:PretenureSizeThreshold` 配置

### Q6：如何排查内存泄漏？

**答**：
1. 配置 `-XX:+HeapDumpOnOutOfMemoryError`，让 OOM 时自动 dump
2. 用 MAT 打开 dump 文件，查看 Leak Suspects 报告
3. 查看 Dominator Tree，找 Retained Heap 最大的对象
4. 右键 Path to GC Roots → exclude weak/soft references，查看引用链
5. 引用链会指向代码中的静态变量 / 集合 / 缓存，定位到具体代码
6. 常见泄漏：静态 Map 只 put 不 remove、ThreadLocal 不 remove、监听器不 unregister、内部类持有外部引用

### Q7：Arthas 用过哪些功能？

**答**：常用功能：
1. `thread -n 5`：查看 CPU 最高的线程
2. `trace <class> <method>`：方法调用链耗时分析，快速定位慢在哪一层
3. `watch <class> <method>`：查看方法入参、返回值、异常
4. `jad <class>`：反编译确认线上代码版本
5. `ognl`：查看静态变量、调用静态方法、查看线程池状态
6. `logger --level debug`：动态修改日志级别不用重启
7. `heapdump`：导出堆 dump
8. `profiler`：生成火焰图分析 CPU

### Q8：线程池满了怎么排查？

**答**：
1. 确认现象：`RejectedExecutionException` 异常飙升
2. 查看线程池状态：`Arthas ognl` 查看 `activeCount`、`queueSize`、`completedTaskCount`
3. 如果 `activeCount == maxPoolSize` 且 `queueSize` 满了 → 任务处理太慢
4. jstack 查看线程在做什么：是否在等 DB / Redis / 下游
5. 如果是下游慢导致 → 排查下游
6. 如果是任务本身计算量大 → 调大线程数或拆分任务
7. 临时措施：调大队列 + 拒绝策略改为 `CallerRunsPolicy` 回压

### Q9：线上频繁 Full GC 但没有内存泄漏，可能是什么原因？

**答**：排查方向：
1. **大对象分配**：每次创建大数组/大字符串直接进老年代，检查 `-XX:PretenureSizeThreshold`
2. **Survivor 太小**：对象在 Minor GC 后放不下 Survivor 直接晋升老年代，调大 `-XX:SurvivorRatio`
3. **System.gc()**：搜索代码或框架调用，添加 `-XX:+DisableExplicitGC`
4. **Metaspace 不足**：动态生成类（CGLIB / 反射），增大 `-XX:MaxMetaspaceSize`
5. **显式调用 finalize()**：finalize 方法会被 JVM 特殊处理，可能导致 Full GC
6. **RMI**：RMI 默认每小时触发一次 `System.gc()`，添加 `-XX:+DisableExplicitGC`

### Q10：容器中 Java 进程被 OOM Killed 怎么解决？

**答**：
1. **确认原因**：`dmesg -T | grep -i "killed process"` 确认是容器 OOM Killer
2. **原因**：JVM 内存使用（堆 + Metaspace + 线程栈 + 堆外内存）超过容器内存限制
3. **解决**：
   - JDK 8u191+ 使用 `-XX:+UseContainerSupport` 让 JVM 感知容器限制
   - 使用 `-XX:MaxRAMPercentage=75.0` 替代 `-Xmx`（自动按容器内存比例分配）
   - 限制堆外内存：`-XX:MaxDirectMemorySize=256m`
   - 限制 Metaspace：`-XX:MaxMetaspaceSize=256m`
   - 限制线程数：控制线程池大小（每个线程默认 1MB 栈）
4. **监控**：容器内存使用率告警，提前预警

---

> **最后建议**：
> 1. **排查方法论的核心是分层定位**：从现象出发，逐层缩小范围，不要盲目操作
> 2. **工具要熟练**：`top/jstack/jmap/jstat` 是基础，`Arthas` 是利器，务必在测试环境多练
> 3. **生产环境必配**：HeapDumpOnOutOfMemoryError + GC 日志 + APM 链路追踪
> 4. **面试核心三题**：CPU 100% 排查、OOM 排查、Full GC 排查，务必能流畅说出完整步骤
> 5. **止血优先**：线上先恢复服务（重启/回滚/限流），再排查根因，排查不阻塞恢复
