|#|知识点|核心机制|设计要点|面试追问|FlowPulse 实现|
|---|---|---|---|---|---|
|**7.5.1**|**事件风暴 Event Storming**|Alberto Brandolini发明；**最好的DDD建模方法**：用便利贴(橙色=命令/蓝色=事件/黄色=用户角色/绿色=策略/红色=热点/紫色=外部/灰色=疑虑) 在墙上协作建模|从事件开始逆向推导：发生了什么→谁触发的→需要什么前置条件→涉及哪些聚合|"事件风暴的标准颜色体系？一次典型的Event Storming怎么做？"|FlowPulse工作流引擎设计就源于事件风暴：**提交申请(命令)** → **流程启动事件(蓝色)** → **任务创建事件** → **待办通知事件**|
|**7.5.2**|**领域事件设计规范**|过去式命名(`OrderPlacedEvent`) / 不可变(`@Value`) / 全局唯一ID(`eventId`) / 时间戳 + 版本号 / 携带足够上下文(但不携带聚合全部数据)|事件粒度：细粒度(每次属性变化都发) vs 粗粒度(只在重要业务时刻发)|"领域事件应该携带多少数据？只带ID还是带完整快照？"|FlowPulse事件粒度选择**粗粒度**：只在流程生命周期关键节点(TaskCreated/Completed/Rejected)发事件|
|**7.5.3**|**事件存储与最终一致性**|事件溯源(Event Sourcing): 只存事件不存当前状态，重放事件还原状态；CQRS: 命令端写/查询端读分离|ES优点: 天然审计/时间旅行调试/完美事件源。ES缺点: 复杂度高/查询不便/事件版本演化难|"事件溯源和CQRS一定要一起用吗？各自适用什么场景？"|FlowPulse V1.0不做ES(V1.0用传统持久化+事件通知) / V2.0规划CQRS(查询走ES索引)|

> **🔥 FlowPulse 领域事件流转图（事件风暴成果转化）**
> 
> ```
> [用户角色]                    [命令]                  [领域事件]                    [下游处理]
> 
> 申请人  ──提交申请──→  SubmitProcessCmd  ──→  ProcessStartedEvent  ──→  MessageService(站内信)
>                                                         ├─→  AuditLogService(审计记录)
>                                                         └─→  MonitorService(指标统计)
> 
> 系统   ──自动分配──→  CreateTaskCmd      ──→  TaskCreatedEvent     ──→  MessageService(通知审批人)
>                                                         └─→  RealtimeService(WsPush)
> 
> 审批人  ──同意──→     CompleteTaskCmd    ──→  TaskCompletedEvent   ──→  Engine(推进到下一节点)
>                                                         ├─→  MessageService(通知下一环节)
>                                                         └─→  HistoryService(记录历史)
> 
> 审批人  ──驳回──→     RejectTaskCmd      ──→  TaskRejectedEvent    ──→  Engine(退回/终止/回退)
>                                                         └─→  MessageService(通知申请人)
> 
> 系统   ──结束判定──→  CompleteProcessCmd  ──→  ProcessCompletedEvent ──→  全链路清理
> ```
