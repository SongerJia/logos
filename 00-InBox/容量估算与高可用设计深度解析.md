# 第一篇：容量估算

## 第一章 容量估算方法论

### 1.1 为什么需要容量估算

```
❌ 常见误区："先上线再说，扛不住再加机器"
✅ 正确思路：容量估算决定架构选型 → 架构决定代码 → 代码决定运维

如果容量估算做错了：
  - QPS估小了 → 上线即崩溃，用户体验灾难
  - 存储估小了 → 半年跑满磁盘，紧急扩容风险大
  - 带宽估小了 → CDN回源雪崩，全站不可用
  - QPS估大了 → 资源浪费，成本翻倍
```

**容量估算的三个时机**：

| 时机 | 目的 | 精度要求 |
|------|------|----------|
| 系统设计阶段 | 决定架构选型（单机/分布式/微服务） | ±30% |
| 上线前压测 | 验证估算，决定初始机器数 | ±10% |
| 运营期扩容 | 精确计算，决定加多少机器 | ±5% |

### 1.2 容量估算四步法

```
Step 1：明确业务指标（用户量、DAU、读写比例）
Step 2：推导技术指标（QPS、带宽、存储、连接数）
Step 3：选择架构方案（单机能扛？需要分库分表？需要缓存？）
Step 4：压测验证与调整
```

### 1.3 核心估算公式

#### 1.3.1 QPS 估算

```
┌─────────────────────────────────────────────────────────────┐
│                    QPS 估算推导链                              │
│                                                              │
│  注册用户数 → DAU → 每用户操作数 → 峰值倍数 → QPS             │
│                                                              │
│  示例：                                                       │
│  总注册用户 = 1000万                                          │
│  DAU = 总注册 × 活跃率(10~30%) = 100万                       │
│  每人每日操作 = 平均30次请求                                   │
│  日总请求 = 100万 × 30 = 3000万                               │
│  平均QPS = 3000万 / 86400 ≈ 347                              │
│                                                              │
│  峰值QPS = 平均QPS × 峰值倍数                                 │
│  ┌──────────────────────────────────────┐                    │
│  │ 业务类型         │ 峰值倍数           │                    │
│  │──────────────────────────────────────│                    │
│  │ 社交/资讯        │ 3~5倍              │                    │
│  │ 电商/秒杀        │ 10~30倍            │                    │
│  │ 视频直播         │ 5~10倍             │                    │
│  │ 金融交易         │ 2~3倍（更平稳）     │                    │
│  └──────────────────────────────────────┘                    │
│                                                              │
│  社交系统峰值QPS = 347 × 5 ≈ 1735                            │
│  秒杀系统峰值QPS = 347 × 30 ≈ 10410                          │
│                                                              │
│  ⚠️ 重要：还要考虑突发超峰值（如热点事件）                      │
│  最终设计QPS = 峰值QPS × 1.5（安全系数）                      │
└─────────────────────────────────────────────────────────────┘
```

#### 1.3.2 读写比例估算

```
读写比例决定架构方向：

  读多写少（90:10） → Redis缓存 + 主从分离
    例：社交动态浏览、商品详情页

  读写均衡（50:50） → 分库分表 + 读写分离
    例：订单系统、消息系统

  写多读少（10:90） → MQ削峰 + 异步落库
    例：日志收集、监控上报、IoT数据
```

#### 1.3.3 带宽估算

```
带宽 = QPS × 平均请求大小 × 8（bit/byte转换）

示例（图片社交系统）：
  读QPS = 5000
  平均响应大小：
    - API JSON：10KB（占20%）
    - 图片缩略图：50KB（占60%）
    - 原图：500KB（占20%）
  平均大小 = 10×0.2 + 50×0.6 + 500×0.2 = 122KB

  出带宽 = 5000 × 122KB × 8 / 1024 ≈ 4.77 Gbps

  ⚠️ CDN能扛70~80%的读流量，回源带宽 ≈ 4.77 × 20% ≈ 0.95 Gbps
```

#### 1.3.4 存储估算

```
┌─────────────────────────────────────────────────────┐
│                存储估算推导链                          │
│                                                      │
│  日增数据量 = 日写QPS × 平均记录大小 × 86400秒         │
│                                                      │
│  示例（社交系统）：                                    │
│  日写QPS = 50                                         │
│  平均记录大小 = 1KB                                    │
│  日增 = 50 × 1KB × 86400 = 4.32 GB/天               │
│                                                      │
│  年增 = 4.32 × 365 ≈ 1.58 TB/年                     │
│                                                      │
│  三年总存储 = 1.58 × 3 = 4.74 TB                     │
│                                                      │
│  加上索引/日志/备份开销 ≈ 4.74 × 3 ≈ 14.2 TB         │
│  （索引约1倍，日志约0.5倍，备份约0.5倍）                │
│                                                      │
│  存储选择：                                           │
│  < 500GB  → 单机MySQL                                 │
│  500GB~5TB → MySQL分库分表                             │
│  > 5TB    → HBase/ClickHouse/Elasticsearch            │
└─────────────────────────────────────────────────────┘
```

#### 1.3.5 内存估算

```
内存主要用于缓存，估算方法：

  缓存容量 = 需要缓存的数据总量 × 缓存命中率设计

  示例：
  商品总数 = 100万
  每个商品缓存对象 ≈ 2KB（JSON序列化后）
  全量缓存 = 100万 × 2KB = 2GB

  缓存策略：
  - 全量缓存（99.9%命中率）→ 2GB + 30%冗余 ≈ 2.6GB
  - 热点缓存（80%命中率，LRU淘汰）→ 2GB × 20% ≈ 400MB

  Redis配置：每个实例建议 ≤ 10GB（避免RDB持久化阻塞）
  2.6GB → 单实例足够，但为高可用至少2实例（主从）
```

#### 1.3.6 连接数估算

```
连接数估算：

  TCP连接数 = QPS × 平均处理时间（秒）

  示例：
  QPS = 5000
  平均处理时间 = 50ms = 0.05s
  连接数 = 5000 × 0.05 = 250

  但实际需要考虑：
  - 长连接（WebSocket/推送）：DAU × 同时在线率 × 30%
  - 数据库连接池：应用实例数 × 每实例池大小
  - Redis连接池：应用实例数 × 每实例池大小

  MySQL连接池：
  应用实例 = 10
  每实例最大连接 = 20
  总最大连接 = 200（MySQL默认max_connections=151不够！需调整）
```

### 1.4 机器数量估算

#### 1.4.1 单机容量基准

```
┌───────────────────────────────────────────────────────────┐
│              单机容量参考（4核8G标准机型）                    │
│                                                            │
│  ┌─────────────┬──────────────┬─────────────────────┐     │
│  │ 类型         │ 单机QPS上限   │ 说明                 │     │
│  │─────────────│──────────────│─────────────────────│     │
│  │ 简单查询     │ 500~1000     │ 单表索引查询          │     │
│  │ 复杂查询     │ 100~200      │ 多表JOIN/聚合         │     │
│  │ 写操作       │ 300~500      │ 单行插入              │     │
│  │ 批量写入     │ 50~100       │ 批量插入/更新          │     │
│  │ 计算密集     │ 50~200       │ 排序/聚合计算          │     │
│  │ 静态API      │ 3000~5000    │ 纯读+缓存             │     │
│  └─────────────┴──────────────┴─────────────────────┘     │
│                                                            │
│  ⚠️ 以上为健康水位（CPU<70%，RT<200ms）                     │
│  实际压测数据才是金标准                                      │
└───────────────────────────────────────────────────────────┘
```

#### 1.4.2 机器数计算

```
机器数 = 设计QPS / 单机QPS × 安全系数(1.3~1.5)

示例：
  设计QPS = 5000（峰值 × 1.5安全系数）
  单机QPS = 800（压测得出）
  机器数 = 5000 / 800 × 1.3 ≈ 8.1 → 9台

  加上高可用冗余（至少2副本）→ 9 + 备用 ≈ 12台

  注意：
  - 最少部署 = 2台（1主1备，防止单点故障）
  - 实际部署 ≥ 3台（滚动升级需要）
```

## 第二章 经典容量估算实战

### 2.1 秒杀系统容量估算

```
┌─────────────────────────────────────────────────────────────┐
│                  秒杀系统容量估算全链路                         │
│                                                              │
│  业务参数：                                                   │
│  - 商品：100件 iPhone                                        │
│  - 参与用户：10万人                                           │
│  - 秒杀时间窗口：5分钟                                        │
│                                                              │
│  Step 1：QPS估算                                              │
│  - 活跃秒杀QPS = 10万 × 刷新频率(2次/秒) = 20万              │
│  - 下单请求QPS = 10万 / 300秒 ≈ 333（真正下单的）             │
│  - 设计峰值 = 20万 × 1.5 = 30万（含机器人刷接口）             │
│                                                              │
│  Step 2：架构分层削峰                                         │
│  ┌──────────────────────────────────────┐                    │
│  │ 层级       │ 削峰手段       │ 剩余QPS  │                    │
│  │──────────────────────────────────────│                    │
│  │ CDN+前端   │ 静态化+验证码  │ 15万     │                    │
│  │ Nginx      │ IP限流(1/秒)   │ 5万      │                    │
│  │ 应用层     │ Sentinel+本地  │ 1万      │                    │
│  │ Redis      │ Lua原子扣减    │ 333      │                    │
│  │ MQ         │ 异步下单       │ ~100     │                    │
│  │ MySQL      │ 乐观锁下单     │ ~100     │                    │
│  └──────────────────────────────────────┘                    │
│                                                              │
│  Step 3：各层机器数                                           │
│  Nginx：5万/2万 ≈ 3台（每台2万QPS）                           │
│  应用层：1万/800 ≈ 13台 → 15台                               │
│  Redis：333QPS → 1台就够，但高可用需要3台哨兵                  │
│  MySQL：100QPS → 1台就够，但需要主从2台                        │
│                                                              │
│  Step 4：带宽估算                                             │
│  - 秒杀页面 ≈ 50KB静态资源，CDN全覆盖，回源忽略                │
│  - 下单接口 ≈ 1KB JSON                                      │
│  - 峰值带宽 = 5万 × 1KB × 8 ≈ 400 Mbps                      │
│                                                              │
│  Step 5：Redis内存                                            │
│  - 库存 = 100 × 16字节 ≈ 1.6KB                              │
│  - 用户资格标记 = 10万 × 8字节 ≈ 800KB                       │
│  - 总计 < 1MB → 内存不是瓶颈                                  │
│                                                              │
│  ❗ 关键结论：秒杀瓶颈是QPS不是存储/内存                        │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 电商系统容量估算（京东/淘宝级）

```
业务参数：
- 注册用户：1亿
- DAU：3000万（30%活跃率）
- GMV（日交易额）：10亿
- 客单价：200元 → 日订单 = 500万

QPS推导：
  读QPS（浏览商品/搜索/详情页）：
    3000万用户 × 30次浏览/天 = 9亿次/天
    平均读QPS = 9亿/86400 ≈ 10416
    峰值读QPS = 10416 × 10 = 104160 → 加CDN后回源 ≈ 2万

  写QPS（下单/支付/评价）：
    500万订单/天 → 平均写QPS ≈ 58
    峰值写QPS = 58 × 10 ≈ 580 → MQ削峰后MySQL ≈ 100

存储估算：
  订单表：
    500万/天 × 1KB ≈ 5GB/天
    年增 ≈ 1.8TB → 分库分表（按用户ID 16库×16表）

  商品表：
    10亿SKU × 2KB ≈ 200GB → MySQL + Redis缓存热点

带宽估算：
  读出带宽 = 2万QPS × 100KB（图片为主）× 8 ≈ 16 Gbps
  CDN扛80% → 回源 ≈ 3.2 Gbps

机器估算：
  应用层（读）：2万/500 ≈ 40台 + 冗余 ≈ 50台
  应用层（写）：100/500 ≈ 1台 + 冗余 ≈ 4台
  Redis集群：50台（分片+副本）
  MySQL集群：16组主从 = 32台
```

### 2.3 社交系统容量估算（微博/Twitter级）

```
业务参数：
- 注册用户：5亿
- DAU：1亿（20%活跃率）
- 每人日均发博：3条
- 每人日均浏览：50条动态

QPS推导：
  写QPS = 1亿 × 3 / 86400 ≈ 3470（发博）
  读QPS = 1亿 × 50 × 10(每条动态含多个请求) / 86400 ≈ 57870
  峰值读QPS = 57870 × 5 ≈ 289350 → Redis缓存扛90%后 ≈ 2.9万

存储估算：
  动态表：1亿×3 = 3亿条/天 × 500字节 ≈ 150GB/天 → HBase+Redis
  关系表：5亿用户 × 平均200关注 = 100亿关系 ≈ 200GB → Redis+MySQL
  年增 ≈ 55TB → 必须冷热分离（热数据3个月Redis/MySQL，冷数据HBase）

带宽估算：
  图片+视频为主：平均200KB/条动态
  读带宽 = 2.9万 × 200KB × 8 ≈ 46.4 Gbps → CDN必须

架构选择：
  读多写少 → Feed流推模式（写扩散） + 拉模式（读扩散）结合
  大V推模式：粉丝量大，写时推到粉丝收件箱
  普通用户拉模式：读时实时拉取关注人的动态
```

## 第三章 性能指标体系 SLI/SLO/SLA

### 3.1 三者关系

```
┌──────────────────────────────────────────────────────────┐
│                                                          │
│  SLI (Service Level Indicator) — 指标                    │
│  "用什么度量？" → 可量化的指标                              │
│  例：P99延迟、可用性百分比、错误率                          │
│                                                          │
│  SLO (Service Level Objective) — 目标                    │
│  "目标是什么？" → SLI的目标值                              │
│  例：P99延迟 < 200ms、可用性 > 99.9%                      │
│                                                          │
│  SLA (Service Level Agreement) — 协议                    │
│  "违约怎么办？" → SLO + 违约赔偿条款                       │
│  例：可用性 < 99.9% → 赔付月费用10%                       │
│                                                          │
│  关系：SLI 是尺子，SLO 是刻度，SLA 是合同                  │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 3.2 四大黄金信号 + RED + USE

```
四大黄金信号（Google SRE）：
1. Latency（延迟）：请求响应时间，区分成功vs失败延迟
2. Traffic（流量）：QPS/TPS/并发数
3. Errors（错误）：错误率（5xx/4xx/超时）
4. Saturation（饱和度）：资源使用率（CPU/内存/连接数）

RED 方法（服务层）：
  Rate（请求速率） + Errors（错误率） + Duration（延迟）
  适合微服务HTTP API监控

USE 方法（资源层）：
  Utilization（使用率） + Saturation（饱和度） + Errors（错误）
  适合CPU/内存/磁盘/网络等基础设施监控
```

### 3.3 延迟指标详解

```
为什么看 P99/P95 而不是平均值？

  假设100个请求：
  - 95个在50ms完成
  - 5个在5000ms完成
  平均 = (95×50 + 5×5000)/100 = 297.5ms ← 看起来还行
  P99 = 5000ms ← 1%用户体验极差！

┌──────────────────────────────────────┐
│ 指标    │ 含义          │ 面试建议    │
│──────────────────────────────────────│
│ P50     │ 50%请求的延迟  │ 基础参考    │
│ P95     │ 5%用户体验差   │ 一般要求    │
│ P99     │ 1%用户体验差   │ 核心指标    │
│ P99.9   │ 0.1%用户极差   │ 金融级要求  │
│ Max     │ 最差情况       │ 不作目标    │
│ Avg     │ 易被长尾拉高   │ 不单独看    │
└──────────────────────────────────────┘

延迟分级标准：
  P99 < 100ms  → 优秀（缓存命中率高的读请求）
  P99 < 200ms  → 良好（常规API）
  P99 < 500ms  → 一般（涉及数据库复杂查询）
  P99 < 1000ms → 较差（需要优化）
  P99 > 1000ms → 不可接受
```

### 3.4 可用性百分比与停机时间

```
┌──────────────────────────────────────────────────────┐
│ 可用性     │ 年停机时间    │ 日停机时间   │ 适用场景    │
│──────────────────────────────────────────────────────│
│ 99%       │ 3天15小时     │ 14.4分钟    │ 内部工具    │
│ 99.9%     │ 8小时46分     │ 1.44分钟    │ 一般业务    │
│ 99.99%    │ 52.6分钟      │ 8.6秒      │ 核心业务    │
│ 99.999%   │ 5.26分钟      │ 0.86秒     │ 金融/支付   │
│ 99.9999%  │ 31.5秒        │ 0.086秒    │ 电信级      │
└──────────────────────────────────────────────────────┘

从99.9%到99.99%：
  可用性提升0.09% = 停机从8.46小时降到52.6分钟
  需要的投入：冗余+自动故障转移+容灾演练 = 成本翻3~5倍

从99.99%到99.999%：
  可用性提升0.009% = 停机从52.6分钟降到5.26分钟
  需要的投入：异地多活+混沌工程+全链路容灾 = 成本再翻3~5倍

⚠️ 面试关键：不要盲目追求99.999%，成本指数级增长
  应该根据业务SLA需求决定可用性等级
```

## 第四章 压测与容量验证

### 4.1 压测类型

```
┌─────────────────────────────────────────────────────────┐
│ 压测类型     │ 范围          │ 目的          │ 风险       │
│─────────────────────────────────────────────────────────│
│ 基准压测     │ 单接口        │ 找单机极限     │ 低         │
│ 集成压测     │ 多接口联动    │ 验证链路容量   │ 中         │

│ 容量基线     │ 定期重复      │ 确定水位线     │ 低         │
└─────────────────────────────────────────────────────────┘
```

### 4.2 全链路压测方案

```
全链路压测三大难题：
1. 数据隔离：压测数据不能污染生产数据
2. 流量标记：压测流量要能识别和路由
3. 影子库：写入要走影子表/影子库

方案：流量标签透传

  ┌─ Client ──→ Gateway ──→ Service A ──→ Service B ──→ DB ─┐
  │  标记压测    header透传     标签染色      识别标签    影子表  │
  │  X-Traffic   跨线程传递     路由到影子     透传到MQ    写影子 │
  │  = stress    MDC+Interceptor                header     表     │
  └─────────────────────────────────────────────────────────┘

  实现方式：
  - HTTP Header：X-Traffic-Source: stress
  - Dubbo RPC：Attachment 透传
  - MQ消息：Property 标记
  - 线程池：TaskDecorator 包装 MDC
```

### 4.4 压测报告关键指标

```
压测报告必须包含：

  1. 场景描述（接口/参数/数据量）
  2. QPS曲线（随并发数增长的曲线，找到拐点）
  3. RT曲线（P50/P95/P99随并发数变化）
  4. 错误率曲线
  5. 资源水位（CPU/内存/网络/磁盘）
  6. 容量水位线定义

  ┌─────────────────────────────────────────────┐
  │        QPS vs 并发数 曲线                     │
  │                                              │
  │  QPS ────┐                                  │
  │          │          ← 线性增长区             │
  │          │     ┌─── ← 拐点（最佳并发数）      │
  │          │    /                               │
  │          │   / ← 压力区（QPS不再增长）        │
  │          │  /                                 │
  │          └── ← 饱和/崩溃区                    │
  │          ╱                                    │
  │  ─────────────── 并发数 ──────→               │
  │                                              │
  │  拐点对应的并发数 = 最佳并发数                  │
  │  拐点对应的QPS = 单机最大安全QPS               │
  └─────────────────────────────────────────────┘

  水位线定义：
  - 安全水位：CPU < 50%, RT < 100ms
  - 警告水位：CPU 50~70%, RT 100~200ms
  - 危险水位：CPU > 70%, RT > 200ms
  - 极限水位：CPU > 90%, RT > 500ms（不稳定）
```

## 第五章 高可用基础概念

### 5.1 高可用定义与度量

```
高可用 = 系统在部分组件故障时仍能提供可接受的服务

度量公式：
  Availability = MTBF / (MTBF + MTTR)

  MTBF = Mean Time Between Failures（平均故障间隔时间）
  MTTR = Mean Time To Recovery（平均恢复时间）

  提高 Availability 的两个方向：
  ┌─ 提高 MTBF：减少故障发生频率 ─┐
  │  - 冗余设计                      │
  │  - 故障隔离                      │
  │  - 代码质量                      │
  │  - 变更管控                      │
  └──────────────────────────────────┘

  ┌─ 降低 MTTR：加快故障恢复速度 ─┐
  │  - 自动故障检测                  │
  │  - 自动故障转移                  │
  │  - 快速回滚                      │
  │  - 灰度发布                      │
  │  - 监控告警                      │
  └──────────────────────────────────┘
```

### 5.2 RPO 与 RTO

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  RPO (Recovery Point Objective) — 数据恢复点目标              │
│  "最多能容忍丢失多长时间的数据"                                │
│                                                              │
│  RTO (Recovery Time Objective) — 恢复时间目标                 │
│  "故障后多久必须恢复服务"                                      │
│                                                              │
│  ┌──────────────────────────────────┐                        │
│  │ 故障发生                          │                        │
│  │  │                                │                        │
│  │  │◄─ RTO ─►│                     │                        │
│  │  │         恢复完成                │                        │
│  │  │                                │                        │
│  │  │◄ RPO ►│                       │                        │
│  │  数据丢失窗口                      │                        │
│  └──────────────────────────────────┘                        │
│                                                              │
│  不同业务的 RPO/RTO 要求：                                    │
│  ┌──────────────────────────────────┐                        │
│  │ 业务       │ RPO     │ RTO      │                        │
│  │──────────────────────────────────│                        │
│  │ 金融交易   │ 0       │ < 5分钟  │                        │
│  │ 支付       │ 0       │ < 15分钟 │                        │
│  │ 电商订单   │ < 1分钟 │ < 30分钟 │                        │
│  │ 社交动态   │ < 5分钟 │ < 1小时  │                        │
│  │ 日志/监控  │ < 1小时 │ < 4小时  │                        │
│  └──────────────────────────────────┘                        │
│                                                              │
│  RPO=0 → 同步复制（强一致性，性能牺牲）                       │
│  RPO>0 → 异步复制（最终一致性，数据可能丢失）                  │
└──────────────────────────────────────────────────────────────┘
```

### 5.3 故障分类与影响

```
┌─────────────────────────────────────────────────────────────┐
│ 故障类型         │ 频率  │ 影响      │ 恢复难度              │
│─────────────────────────────────────────────────────────────│
│ 网络抖动/超时    │ 高    │ 单请求     │ 低（重试即可）         │
│ 进程崩溃         │ 中    │ 单节点     │ 低（自动重启）         │
│ 磁盘故障         │ 中    │ 单节点数据 │ 中（主从切换）         │
│ 机架/交换机故障  │ 低    │ 多节点     │ 中（跨机架冗余）       │
│ 机房故障         │ 极低  │ 整机房     │ 高（异地容灾）         │
│ 地域故障         │ 极低  │ 整地域     │ 极高（异地多活）       │
│ 人为操作失误     │ 中    │ 全局       │ 高（需回滚）           │
│ DNS故障          │ 低    │ 全局       │ 极高（外部依赖）       │
└─────────────────────────────────────────────────────────────┘

故障黄金法则：
  单点故障 = 系统最脆弱环节 = 最优先消除的目标
```

### 6.2 同城双活架构

```
┌──────────────────────────────────────────────────────────────┐
│                    同城双活架构                                │
│                                                              │
│   ┌─────── 用户 ───────┐                                     │
│   │       ↓             │                                     │

│   │ ┌──┐      ┌──┐     │                                     │
│   │ │GW│      │GW│     │ ← 网关层双活                         │
│   │ └──┘      └──┘     │                                     │
│   │ ┌──┐      ┌──┐     │                                     │
│   │ │Svc│     │Svc│    │ ← 服务层双活                         │
│   │ └──┘      └──┘     │                                     │
│   │ ┌──┐      ┌──┐     │                                     │
```

### 7.2 Bulkhead 隔舱设计

```
┌──────────────────────────────────────────────────────────────┐
│              Bulkhead 隔舱模式                                 │
│                                                              │
│  类比：船的隔舱设计 — 一个舱进水不影响其他舱                   │
│                                                              │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐                        │
│  │舱室A │ │舱室B │ │舱室C │ │舱室D │                        │
│  │      │ │      │ │进水! │ │      │                        │
│  │  ✓   │ │  ✓   │ │  ✗   │ │  ✓   │                        │
│  └──────┘ └──────┘ └──────┘ └──────┘                        │
│                                                              │
│  软件实现三种方式：                                           │
│                                                              │
│  1. 线程池隔离（最常用）                                      │
│     不同业务用不同线程池，慢请求不拖垮全部                     │
│                                                              │
│     ┌─ 主线程池 ─┐ ┌─ 支付线程池 ─┐ ┌─ 搜索线程池 ─┐        │
│     │  core=50   │ │  core=20     │ │  core=30     │        │
│     │  max=100   │ │  max=40      │ │  max=60      │        │
│     │  queue=200 │ │  queue=100   │ │  queue=150   │        │
│     └────────────┘ └──────────────┘ └──────────────┘        │
│                                                              │
│  2. 信号量隔离（轻量级）                                      │
│     限制并发数但不创建线程池，适用于本地调用                   │
│                                                              │
│     Semaphore paymentSem = new Semaphore(20);                │
│     // 支付最多20并发，超出的快速失败                         │
│                                                              │
│  3. 进程隔离（最彻底）                                        │
│     不同服务拆为独立进程/容器，一个崩不影响另一个              │
│     微服务架构本身就是进程级隔舱                              │
└──────────────────────────────────────────────────────────────┘
```

**Hystrix/Sentinel 隔舱实现**：

```java
// Sentinel 线程池隔离配置
SentinelThreadPoolExecutor executor = new SentinelThreadPoolExecutor(
    20,        // corePoolSize
    40,        // maxPoolSize  
    100,       // queueCapacity
    "payment-thread-pool"
);

// 信号量隔离配置（Sentinel）
FlowRule rule = new FlowRule("paymentResource")
    .setCount(20)                // 最大并发20
    .setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_RATE_LIMITER);
// 信号量模式：不排队，超并发直接拒绝

// 线程池隔离 vs 信号量隔离
┌─────────────────────────────────────────────────────────┐
│ 维度         │ 线程池隔离       │ 信号量隔离              │
│─────────────────────────────────────────────────────────│
│ 额外线程开销 │ 有（线程池开销） │ 无                      │
│ 响应延迟     │ 有线程切换开销   │ 无                      │
│ 超时控制     │ 支持（线程超时） │ 不支持（依赖调用方超时）│
│ 适用场景     │ 远程调用/慢IO   │ 本地计算/快速调用        │
│ 隔离彻底性   │ 彻底            │ 限并发但不隔离线程       │
└─────────────────────────────────────────────────────────┘
```

### 7.3 慢调用隔离

```
慢调用拖垮系统的原理：

  1. 慢调用占用线程 → 线程池满 → 新请求排队/拒绝
  2. 排队请求等超时 → 连续超时 → 上游也超时 → 级联故障
  3. 线程池满 → 其他业务也受阻（共享线程池时）

解决方案：
  ┌─ 独立线程池：慢调用用小线程池，快速拒绝不影响主流程 ─┐
  │  - 核心服务：大线程池（200线程）                        │
  │  - 非核心服务：小线程池（20线程）+ 大队列超时快速失败   │
  └────────────────────────────────────────────────────────┘

  ┌─ 超时分层：不同层级不同超时 ─┐
  │  Gateway：3秒超时              │
  │  Service调用：2秒超时          │
  │  Redis：200ms超时              │
  │  MySQL：1秒超时                │
  │  下游HTTP：1.5秒超时           │
  └────────────────────────────────┘
```

## 第八章 限流与降级熔断

### 8.1 限流（承接限流算法文档）

```
限流 = 在容量估算基础上主动拒绝超量请求

限流位置选择：
  ┌──────────────────────────────────────────────────────┐
  │ 位置        │ 优势            │ 劣势                  │
  │──────────────────────────────────────────────────────│
  │ CDN/WAF    │ 最前端防御       │ 无法区分业务           │
  │ Nginx      │ 细粒度IP限流     │ 无法区分用户           │
  │ Gateway    │ 路由+服务级限流   │ 单层可能不够           │
  │ 服务内部   │ 最细粒度资源限流 │ 过晚（已消耗线程）     │
  │ 下游调用   │ 保护被调用方     │ 自身视角              │
  └──────────────────────────────────────────────────────┘

  最佳实践：多层限流，逐层收紧
  CDN → Nginx → Gateway → Service → Resource

  Nginx 限流配置示例：
  limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
  limit_req zone=api burst=20 nodelay;
  # 每IP 10请求/秒，burst 20，不延迟排队

  Gateway 限流（Spring Cloud Gateway + Sentinel）：
  @Bean
  public GatewayFilter sentinelFilter() {
      return new SentinelGatewayFilter();
  }
  // 配置路由级限流规则
  FlowRule rule = new FlowRule("route_order_api")
      .setCount(1000)  // 1000 QPS
      .setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_WARM_UP)
      .setWarmUpPeriodSec(10);
```

### 8.2 降级策略

```
降级 = 主动牺牲非核心功能保核心功能可用

降级分级：
┌──────────────────────────────────────────────────────────────┐
│ 级别   │ 触发条件         │ 降级措施           │ 影响        │
│──────────────────────────────────────────────────────────────│
│ L1     │ CPU>70%/RT>300ms │ 读缓存代替读DB     │ 数据可能旧  │
│ L2     │ CPU>80%/RT>500ms │ 关闭非核心功能     │ 体验降级    │
│ L3     │ CPU>90%/RT>1s    │ 返回静态兜底数据   │ 功能缺失    │
│ L4     │ 服务不可用        │ 页面降级/跳转     │ 基本可用    │
└──────────────────────────────────────────────────────────────┘

降级场景设计：

  1. 商品详情页降级链：
     正常 → 库存实时查询
     L1  → 库存读Redis缓存（可能延迟）
     L2  → 库存显示"暂无"（不查了）
     L3  → 整个详情页返回静态HTML兜底

  2. 搜索降级链：
     正常 → ES全文搜索 + 个性化排序
     L1  → ES搜索 + 默认排序（跳过个性化）
     L2  → 返回热搜关键词列表（不搜索了）
     L3  → 返回静态热门商品页面

  3. 推荐降级链：
     正常 → 算法推荐 + 实时特征
     L1  → 算法推荐 + 离线特征
     L2  → 返回热门/新品列表
     L3  → 返回空（页面隐藏推荐位）

  Sentinel 降级代码：
  @SentinelResource(value = "getProductDetail",
      blockHandler = "getProductDetailBlock",
      fallback = "getProductDetailFallback")
  public Product getProductDetail(Long id) {
      return productService.getById(id);
  }

  // 流量控制触发（限流/熔断）
  public Product getProductDetailBlock(Long id, BlockException ex) {
      return cachedProductService.getById(id);  // L1：读缓存
  }

  // 异常触发（业务异常）
  public Product getProductDetailFallback(Long id, Throwable ex) {
      return defaultProductService.getDefault();  // L2：兜底数据
  }
```

### 8.3 熔断器设计

```
┌──────────────────────────────────────────────────────────────┐
│              熔断器三态模型                                    │
│                                                              │
│   ┌─────────┐  错误率超阈值    ┌──────────┐                  │
│   │  CLOSED │───────────────→ │   OPEN    │                  │
│   │  正常    │                │  熔断      │                  │
│   │  全部通过 │               │  全部拒绝  │                  │
│   └─────────┘                └──────────┘                  │
│        ↑                          │                        │
│        │ 探测成功                  │ 冷却时间结束            │
│        │                          ↓                        │
│        │                    ┌───────────┐                   │
│        │                    │HALF-OPEN  │                   │
│        │                    │ 半开      │                   │
│        │                    │ 放少量    │                   │
│        │                    │ 探测请求  │                   │
│        └────────────────────└───────────┘                   │
│                                                              │
│  三态转换条件：                                               │
│  CLOSED → OPEN：    错误率 ≥ 阈值（如50%）在时间窗口内       │
│  OPEN → HALF-OPEN： 冷却时间到期（如5秒）                    │
│  HALF-OPEN → CLOSED：探测请求成功率达标                      │
│  HALF-OPEN → OPEN：  探测请求仍然失败                        │
└──────────────────────────────────────────────────────────────┘
```

**Sentinel 熔断规则配置**：

```java
// 慢调用比例熔断
DegradeRule slowRule = new DegradeRule("orderService")
    .setGrade(CircuitBreakerStrategy.SLOW_REQUEST_RATIO.getType())
    .setCount(0.5)        // 慢调用阈值：RT > 500ms 判定为慢调用
    .setSlowRatioThreshold(0.6)  // 慢调用比例 ≥ 60% 时熔断
    .setTimeWindow(10)    // 熔断持续时间10秒
    .setMinRequestAmount(5)    // 最少5个请求才计算比例
    .setStatIntervalMs(1000);  // 统计时间窗口1秒

// 异常比例熔断
DegradeRule errorRule = new DegradeRule("paymentService")
    .setGrade(CircuitBreakerStrategy.ERROR_RATIO.getType())
    .setCount(0.5)        // 异常比例 ≥ 50% 时熔断
    .setTimeWindow(10)
    .setMinRequestAmount(5);

// 异常数熔断
DegradeRule countRule = new DegradeRule("inventoryService")
    .setGrade(CircuitBreakerStrategy.ERROR_COUNT.getType())
    .setCount(10)         // 异常数 ≥ 10 时熔断
    .setTimeWindow(60)    // 熔断持续60秒
    .setMinRequestAmount(5);

// ⚠️ 关键参数解释：
// minRequestAmount：避免样本太少误熔断（如2个请求1个失败就50%了）
// statIntervalMs：统计窗口，太短容易误判，太长反应慢
// timeWindow：熔断恢复时间，太短可能反复熔断，太长恢复慢
```

### 8.4 级联故障与雪崩预防

```
级联故障传播链：

  下游服务C慢 → 占用服务B线程 → 服务B也慢 → 占用服务A线程 → 全站不可用

  ┌─ A ──→ B ──→ C（慢） ─┐
  │ A线程被B占满           │
  │ B线程被C占满           │
  │ 全链路雪崩             │
  └─────────────────────────┘

预防三板斧：

  1. 限流：每层限制最大并发，超量快速拒绝
     - 不会因下游慢而积累过多等待线程

  2. 熔断：下游错误率超阈值直接断开
     - 不再调用故障下游，快速失败+兜底

  3. 超时：每层设置超时，超时即失败
     - 不会永远等待无响应的下游

  三板斧协同：
  ┌──────────────────────────────────────────┐
  │ 正常时    │ 限流保障不过载               │
  │ 下游慢时  │ 超时快速失败 + 熔断保护      │
  │ 下游挂时  │ 熔断快速失败 + 降级兜底      │
  │ 流量突增  │ 限流拒绝 + 排队削峰          │
  └──────────────────────────────────────────┘
```

## 第九章 超时与重试

### 9.1 超时设计原则

```
超时是高可用的第一道防线 — "宁可错杀不可长等"

超时设计三大原则：

  1. 每个外部调用必须设超时
     ❌ 没有 timeout 的 HTTP/RPC/DB/Redis 调用 = 埋雷
     ✅ 所有调用都设超时，超时即失败，走降级/熔断

  2. 超时时间要有层次
     上层超时 > 下层超时 + 重试时间

     ┌──────────────────────────────────────────┐
     │ Gateway  │ 3s超时                        │
     │ Service  │ 2s超时（含1次重试1.5s+0.5s）  │
     │ Redis    │ 200ms超时                     │
     │ MySQL    │ 1s超时                        │
     │ HTTP下游 │ 1.5s超时                      │
     └──────────────────────────────────────────┘

     如果Service调用下游HTTP=1.5s，Gateway必须 > 1.5s+网络开销

  3. 超时后必须有兜底
     超时 → 降级 → 返回缓存/默认值 → 不能让用户看到500
```

**各组件超时推荐值**：

```
┌──────────────────────────────────────────────────────────┐
│ 组件          │ 推荐超时      │ 说明                       │
│──────────────────────────────────────────────────────────│
│ Redis GET     │ 50~200ms     │ 本机房内网，应该很快       │
│ Redis MGET    │ 100~500ms    │ 批量操作稍慢               │
│ MySQL 单查询 │ 200ms~1s     │ 简单查询200ms，复杂1s      │
│ MySQL 批量   │ 5~10s        │ 批量导入/导出              │
│ HTTP下游调用 │ 1~3s         │ 内网调用                   │
│ HTTP外部API  │ 3~10s        │ 外部依赖不可控             │
│ Dubbo RPC    │ 1~3s         │ 内部RPC调用                │
│ MQ发送       │ 3~5s         │ 发送消息超时               │
│ 连接池获取   │ 100~500ms    │ 连接池耗尽时快速失败       │
│ DNS解析      │ 1~3s         │ DNS可能很慢               │
└──────────────────────────────────────────────────────────┘
```

### 9.2 重试策略

```
重试 = 失败后自动再次尝试，但必须谨慎

┌─────────────────────────────────────────────────────────┐
│              重试决策矩阵                                 │
│                                                          │
│  ┌────────────┬────────────┬──────────────────────┐     │
│  │ 错误类型    │ 是否重试    │ 原因                  │     │
│  │────────────│────────────│──────────────────────│     │
│  │ 网络超时    │ ✅ 重试     │ 可能瞬时网络抖动      │     │
│  │ 连接拒绝    │ ✅ 重试     │ 服务可能正在重启      │     │
│  │ 429限流     │ ✅ 延迟重试 │ 等限流窗口过去        │     │
│  │ 500内部错误 │ ✅ 重试     │ 可能瞬时故障          │     │
│  │ 400参数错误 │ ❌ 不重试   │ 参数错了重试也错      │     │
│  │ 404不存在   │ ❌ 不重试   │ 资源不存在重试没用    │     │
│  │ 403权限错误 │ ❌ 不重试   │ 权限问题重试也过不了  │     │
│  │ 业务异常    │ ❌ 不重试   │ 余额不足等业务错误    │     │
│  └────────────┴────────────┴──────────────────────┘     │
│                                                          │
│  ⚠️ 重试三大风险：                                       │
│  1. 重试放大流量（1次变3次 → 下游更扛不住）               │
│  2. 重试导致重复操作（非幂等接口重复扣款）                 │
│  3. 重试拖长总耗时（重试3次 × 2秒 = 6秒才最终失败）       │
└─────────────────────────────────────────────────────────┘
```

**指数退避重试**：

```java
// Spring Retry 指数退避配置
@Retryable(
    value = {SocketTimeoutException.class, ConnectException.class},
    maxAttempts = 3,                      // 最多重试3次（含首次）
    backoff = @Backoff(
        delay = 100,                      // 首次重试间隔100ms
        multiplier = 2,                   // 每次间隔翻倍
        maxDelay = 2000                   // 最大间隔2秒
    )
)
public Order createOrder(OrderRequest request) {
    return orderService.create(request);
}

// 重试时间线：
// 首次调用 → 失败 → 100ms后重试 → 失败 → 200ms后重试 → 失败 → 返回异常
// 总耗时 ≈ 原调用时间 + 100 + 200 + 2次调用时间

// ❌ 线性退避（间隔固定）：
// 失败 → 1s → 失败 → 1s → 失败 → 1s → ...
// 问题：如果下游正在恢复，大量请求同时在1s后同时涌入

// ✅ 指数退避（间隔翻倍）：
// 失败 → 1s → 失败 → 2s → 失败 → 4s → ...
// 优势：请求逐渐分散，给下游恢复时间

// ✅✅ 指数退避+随机抖动（最佳）：
// 失败 → 1s+random(0~1s) → 失败 → 2s+random(0~2s) → ...
// 优势：避免所有客户端同步重试（Thundering Herd）
```

### 9.3 重试与幂等的关系

```
重试的前提：操作必须是幂等的

幂等性 = 同一操作执行一次和多次的效果相同

┌───────────────────────────────────────────────────────────┐
│ 操作类型      │ 幂等性   │ 重试安全性  │ 说明               │
│───────────────────────────────────────────────────────────│
│ GET查询       │ ✅ 幂等  │ ✅ 安全     │ 查询不影响数据      │
│ PUT全量更新   │ ✅ 幂等  │ ✅ 安全     │ 用最新值覆盖        │
│ DELETE删除    │ ✅ 幂等  │ ✅ 安全     │ 删除不存在也OK      │
│ POST创建      │ ❌ 非幂等 │ ❌ 危险     │ 重试会创建多条      │
│ POST扣款      │ ❌ 非幂等 │ ❌ 极危险   │ 重试会多扣款        │
│ PATCH部分更新 │ ❌ 非幂等 │ ❌ 危险     │ 重试会多次追加      │
└───────────────────────────────────────────────────────────┘

非幂等操作的重试方案 → 见第十章幂等设计
```

## 第十章 幂等设计

### 10.1 什么是幂等性

```
幂等性定义：
  f(f(x)) = f(x)
  执行一次和执行多次的效果完全相同

为什么幂等对高可用至关重要：
  - 分布式系统中网络超时是常态 → 必须重试 → 重试必须幂等
  - 消息队列可能重复投递 → 消费必须幂等
  - 用户可能双击/重复提交 → 请求必须幂等
```

### 10.2 四种幂等实现方案

```
┌──────────────────────────────────────────────────────────────┐
│ 方案              │ 原理         │ 适用场景     │ 缺点        │
│──────────────────────────────────────────────────────────────│
│ 唯一ID+去重表      │ 插入唯一键    │ 创建类操作   │ 需额外表    │
│ 状态机             │ 状态只往前    │ 订单类流程   │ 需状态定义  │
│ Token机制          │ 预发一次性Token│ 表单提交    │ 需两次请求  │
│ 乐观锁             │ version匹配   │ 更新类操作   │ 并发冲突时  │
│                   │              │             │ 需重试      │
└──────────────────────────────────────────────────────────────┘
```

**方案一：唯一ID + 去重表**

```java
// 幂等Key设计：业务类型 + 业务唯一标识
String idempotentKey = "PAY:" + orderId;

// 方案1：Redis SETNX（推荐，高性能）
public boolean checkIdempotent(String key) {
    return redis.setnx(key, "1", 24 * 3600);  // 24小时过期
    // true = 首次执行，false = 重复请求
}

// 方案2：MySQL唯一索引（强一致）
@Transactional
public Payment pay(PaymentRequest request) {
    String idempotentKey = "PAY:" + request.getOrderId();
    try {
        // 插入去重表（唯一索引幂等Key）
        idempotentMapper.insert(idempotentKey);
        // 执行支付逻辑
        return doPay(request);
    } catch (DuplicateKeyException e) {
        // 唯一索引冲突 = 重复请求
        log.warn("重复支付请求: {}", idempotentKey);
        return queryExistingPayment(request.getOrderId());
    }
}
```

**方案二：状态机幂等**

```java
// 订单状态只允许单向流转
public enum OrderStatus {
    CREATED(0),     // 创建
    PAID(1),        // 已支付
    DELIVERING(2),  // 配送中
    COMPLETED(3),   // 完成
    CANCELLED(4);   // 取消
}

// 更新时检查状态前置条件（乐观锁+状态约束）
@Transactional
public boolean pay(Long orderId) {
    // 只允许 CREATED → PAID 的转换
    int updated = orderMapper.updateStatus(
        orderId,
        OrderStatus.CREATED,   // 期望当前状态
        OrderStatus.PAID       // 目标状态
    );
    // updated=1 → 成功（首次）
    // updated=0 → 状态已变（重复/非法）→ 幂等返回
    if (updated == 0) {
        Order order = orderMapper.getById(orderId);
        if (order.getStatus() == OrderStatus.PAID) {
            return true;  // 已支付，幂等成功
        }
        throw new BizException("订单状态非法");
    }
    return true;
}

// ⚠️ 状态机幂等的关键：
// 所有状态转换都是单向的，不可回退
// 更新SQL带 WHERE status = 期望状态 条件
```

**方案三：Token 机制（防重复提交）**

```java
// 步骤1：前端先请求获取Token
@GetMapping("/token")
public String getToken() {
    String token = UUID.randomUUID().toString();
    redis.setex("TOKEN:" + token, 600, "1");  // 10分钟有效
    return token;
}

// 步骤2：提交时携带Token
@PostMapping("/submit")
public Result submit(@RequestHeader("X-Idempotent-Token") String token,
                     SubmitRequest request) {
    // 删除Token（原子操作，只有第一次能删成功）
    Boolean deleted = redis.del("TOKEN:" + token);
    if (!deleted) {
        return Result.fail("重复提交或Token过期");
    }
    return doSubmit(request);
}
```

```java
// 更新时携带版本号
```

### 10.3 MQ消费幂等

```java

public class PayConsumer implements RocketMQListener<MessageExt> {
    
    @Override
    public void onMessage(MessageExt msg) {
        String msgId = msg.getMsgId();  // 全局唯一消息ID
        String bizKey = "MQ_CONSUME:" + msgId;
        
        // 幂等检查
        if (!redis.setnx(bizKey, "1", 3600)) {
            log.info("重复消费，跳过: {}", msgId);
            return;  // 已消费过，直接跳过
        }
        
        try {
            doPay(msg);
        } catch (Exception e) {
            redis.del(bizKey);  // 失败时清除标记，允许重试
            throw e;            // 抛异常让MQ重投
        }
    }
}

// ⚠️ 注意：msgId在极端情况下可能重复（MQ broker重启等）
//    更安全的幂等Key = 业务ID（如订单号），而非msgId
```

```
└──────────────────────────────────────────────────────────────┘
```

### 11.3 回滚策略

```
回滚 = 发布失败后恢复到旧版本

四种回滚方式：

  1. 流量回滚（最快，秒级）
     切流量回到旧版本 → 蓝绿/金丝雀发布的天生优势
     适合：蓝绿部署、金丝雀发布

  2. 版本回滚（分钟级）
     重新部署上一个已知稳定版本
     kubectl rollout undo deployment/order-service
     适合：滚动发布

  3. 数据回滚（复杂）
     数据库变更需要逆向操作：
     - 增表 → 删表
     - 加列 → 删列（要先迁移数据）
     - 改类型 → 改回（可能数据丢失）

     ⚠️ 最佳实践：数据库变更与代码变更分开发布
     - 先发布兼容新旧两版代码的中间版本
     - 再做数据库变更
     - 最后发布依赖新表结构的新版本
     → 回滚时只需回滚代码，数据库兼容旧版本

  4. 配置回滚（秒级）
     配置中心版本回退
     Apollo/Nacos 都支持配置版本管理和一键回滚
```

## 第十二章 容灾与 Chaos Engineering

### 12.1 混沌工程定义

```
混沌工程 = 在生产环境中故意注入故障，验证系统韧性

Netflix Chaos Monkey → Chaos Kong → Chaos Engineering 全体系

核心思想：
  "如果不在生产中测试，那你不是在验证系统韧性，而是在猜测"

混沌工程不是：
  ❌ 破坏性测试（在测试环境做）
  ❌ Bug发现工具（那是QA的事）
  ❌ 性能压测（那是容量验证）

混沌工程是：
  ✅ 在生产中验证假设："如果X故障了，系统会怎样？"
  ✅ 发现隐藏的系统脆弱点
  ✅ 建立对系统韧性的信心
```

### 12.2 混沌实验设计流程

```
┌──────────────────────────────────────────────────────────────┐
│              混沌实验四步法                                    │
│                                                              │
│  Step 1：定义稳态假设                                        │
│  "系统正常时，我们期望看到什么？"                              │
│  例：P99延迟<200ms，错误率<0.1%，订单成功率>99.5%             │
│                                                              │
│  Step 2：设计实验变量                                        │
│  "改变什么来打破稳态？"                                      │
│  ┌──────────────────────────────────────┐                    │
│  │ 变量类型      │ 实验示例              │                    │
│  │──────────────────────────────────────│                    │
│  │ 网络故障      │ 模拟机房间网络断开    │                    │
│  │ 资源耗尽      │ CPU打满/内存耗尽      │                    │
│  │ 服务宕机      │ Kill某个服务进程      │                    │
│  │ 依赖故障      │ Redis/MySQL不可用     │                    │
│  │ 状态异常      │ 磁盘IO延迟100ms       │                    │
│  │ 时间偏移      │ NTP时钟偏移5分钟      │                    │
│  │ 流量异常      │ QPS突增3倍            │                    │
│  └──────────────────────────────────────┘                    │
│                                                              │
│  Step 3：运行实验                                            │
│  在生产中注入变量，观察稳态指标变化                            │
│                                                              │
│  Step 4：分析结果                                            │
│  稳态被打破 → 发现脆弱点 → 修复 → 重新实验                   │
│  稳态未打破 → 系统韧性验证通过 → 设计更大实验                 │
│                                                              │
│  ⚠️ 安全原则：                                               │
│  - 先在非生产环境做                                          │
│  - 生产实验在低流量时段                                      │
│  - 有紧急回滚方案                                            │
│  - 监控告警实时观察                                          │
│  - 一次只变一个变量                                          │
└──────────────────────────────────────────────────────────────┘
```

## 第十五章 10 道面试高频题

### Q1：如何估算一个系统的QPS？

```
标准回答：

  四步推导法：
  1. 确定总用户数和DAU（DAU = 总用户 × 活跃率10~30%）
  2. 计算平均QPS = DAU × 每人每日操作数 / 86400
  3. 计算峰值QPS = 平均QPS × 峰值倍数（社交3~5x，电商10~30x）
  4. 设计QPS = 峰值QPS × 安全系数1.5

  示例：1000万注册用户，DAU 100万，每人30次操作
  平均QPS ≈ 347，峰值 ≈ 1735（社交5x），设计 ≈ 2600

  还需要区分读写比例：
  读多写少 → Redis缓存为主
  读写均衡 → 分库分表+读写分离
  写多读少 → MQ削峰+异步
```

### Q2：99.9% 和 99.99% 可用性差距多大？需要什么投入？

```
标准回答：

  99.9% = 年停机8.76小时    → 主从+自动故障转移+限流降级
  99.99% = 年停机52.6分钟   → 同城双活+全链路熔断+混沌工程

  差距0.09%，但从8.76小时到52.6分钟，停机时间缩短17倍

  成本差距：
  - 99.9%：成本2~3倍于单机（主从+基础冗余）
  - 99.99%：成本4~6倍于单机（双机房+完整可观测性+容灾演练）

  关键：不要盲目追求更高可用性，应根据业务停机损失计算ROI
  如果1小时停机损失<双机房成本 → 99.9%就够了
```

### Q3：什么是Bulkhead隔舱设计？Java怎么实现？

```
标准回答：

  Bulkhead源自船舶隔舱设计——一个舱进水不影响其他舱。
  软件中：不同业务用独立资源池，慢请求/故障不影响其他业务。

  三种实现：
  1. 线程池隔离——最彻底，不同业务不同线程池
     Sentinel/Hystrix 的 ThreadPoolIsolation
     适合：远程调用（HTTP/RPC），可控制超时

  2. 信号量隔离——轻量级，只限制并发数不创建线程池
     Semaphore(20) 限制最大并发20
     适合：本地调用/快速操作，不创建额外线程

  3. 进程隔离——最彻底，微服务架构本身就是进程级Bulkhead

  面试追问：线程池隔离vs信号量隔离？
  线程池隔离可超时控制但有线程开销，信号量隔离无开销但无法超时控制
```

### Q4：熔断器三态模型怎么工作？参数怎么调？

```
标准回答：

  三态：CLOSED(正常) → OPEN(熔断) → HALF-OPEN(半开探测)
  
  CLOSED→OPEN：时间窗口内错误率/慢调用率≥阈值
  OPEN→HALF-OPEN：冷却时间到期
  HALF-OPEN→CLOSED：探测请求成功
  HALF-OPEN→OPEN：探测请求仍失败

  关键参数：
  - 错误比例阈值：50%（过低容易误熔断，过高反应慢）
  - 最小请求数：5（避免样本太少误判，如2个请求1个失败就50%）
  - 统计时间窗口：1秒（太短容易误判，太长反应慢）
  - 熔断持续时间：5~10秒（太短反复熔断，太长恢复慢）

  Sentinel支持三种熔断策略：
  慢调用比例、异常比例、异常数——根据业务特征选择
```

### Q5：超时设计为什么要有层次？怎么设计？

```
标准回答：

  超时层次确保上层超时能涵盖下层处理+重试时间，避免上层提前断开

  设计原则：
  Gateway超时 > Service超时 + 重试次数 × 重试间隔
  Service超时 > 下游HTTP超时 + 网络开销
  下游HTTP > Redis超时 + MySQL超时

  推荐值：
  Gateway: 3~5s
  Service: 2~3s
  HTTP下游: 1~2s
  Redis: 50~200ms
  MySQL: 200ms~1s

  面试追问：超时后怎么办？
  → 超时即失败 → 走降级（缓存/兜底） → 不能让用户等
```

### Q6：重试策略有哪些？什么是指数退避+随机抖动？

```
标准回答：

  重试决策：只重试可能瞬时恢复的故障（超时/连接拒绝/429/500）
  不重试确定性的错误（400/404/403/业务异常）

  重试间隔策略：
  - 固定间隔：所有请求同步重试 → Thundering Herd问题
  - 指数退避：1s→2s→4s→8s，给下游恢复时间
  - 指数退避+随机抖动：1s+random(0~1s)→2s+random(0~2s)
    → 最佳方案，避免所有客户端同步涌入

  Spring Retry配置：
  @Retryable(maxAttempts=3, backoff=@Backoff(delay=100, multiplier=2, maxDelay=2000))

  重试前提：操作必须幂等（否则可能重复扣款/创建多条数据）
```

### Q7：幂等性怎么实现？四种方案对比？

```
标准回答：

  四种方案：
  1. 唯一ID+去重表——插入唯一键，DuplicateKeyException=重复
     适合创建类操作，Redis SETNX或MySQL唯一索引实现

  2. 状态机——订单状态单向流转(CREATED→PAID→DELIVERING)
     更新SQL带WHERE status=期望状态，updated=0=重复/非法

  3. Token机制——预发一次性Token，提交时消费Token
     适合表单防重复提交，前端先获取Token再提交

  4. 乐观锁——version或字段条件更新
     UPDATE SET stock=stock-1 WHERE stock>=1

  MQ消费幂等：用Redis SETNX标记msgId或业务ID
```

### Q8：金丝雀发布流程是什么？发现问题怎么回滚？

```
标准回答：

  金丝雀发布五阶段：
  1. 部署新版本到1台机器，分配1%流量
  2. 观察监控5~15分钟（错误率/P99延迟/业务指标）
  3. 指标正常→扩大到10%→50%
  4. 全量切换100%
  5. 保留旧版本1小时作为回滚窗口

  发现问题回滚：
  流量切回旧版本（秒级）→ 分析问题 → 修复 → 重新发布

  数据库变更回滚更复杂：
  最佳实践——代码变更与数据库变更分离发布
  先发兼容新旧两版的中间版本 → 再做数据库变更 → 最后发新版本
```

### Q9：异地多活的核心难题是什么？怎么解决？

```
标准回答：

  核心难题：跨地域数据同步延迟（北京↔上海延迟30~50ms）

  解决思路：不追求强一致，而是最终一致+业务补偿

  关键设计：
  1. 单元化架构——每个用户固定路由到一个机房（单元）
     单元内数据自包含，避免跨机房数据依赖

  2. 写流量本地优先——用户只能写本地机房数据
     异步同步到其他机房（Canal+MQ方案，延迟1~3秒）

  3. 读流量就近——读本地机房副本
     可能读到1~3秒旧数据，对用户透明处理

  4. 冲突解决——最后写入优先（LWW）或业务规则仲裁

  5. 故障单元迁移——用户路由切到其他机房
     需要数据同步完成才能切（或接受RPO损失）

  成本极高：异地多活成本10~15倍于单机房，只有金融/支付等99.999%业务才需要
```

### Q10：容量估算和压测的关系是什么？怎么做全链路压测？

```
标准回答：

  容量估算是理论计算，压测是实践验证——两者形成闭环

  关系：
  1. 容量估算 → 决定架构选型和初始机器数
  2. 压测 → 验证估算准确性，找到真实单机QPS
  3. 压测结果 → 修正容量基线，确定安全水位线
  4. 运营扩容 → 基于容量基线计算需要加多少机器

  全链路压测三大难题：
  1. 数据隔离——压测数据不能污染生产
     方案：影子表/影子库，压测流量写影子表

  2. 流量标记——压测流量能被识别和路由
     方案：HTTP Header X-Traffic-Source=stress + 全链路透传

  3. 影响控制——压测不能影响正常用户
     方案：低流量时段 + 逐步加压 + 监控告警 + 随时可终止

  压测结果关键：
  找到QPS拐点——QPS随并发增长的拐点 = 最佳并发数
  拐点对应QPS = 单机最大安全QPS（CPU<70%, RT<200ms）
```
