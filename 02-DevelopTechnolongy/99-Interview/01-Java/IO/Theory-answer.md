## 一、IO 模型基础

### **Q1** 什么是同步/异步？什么是阻塞/非阻塞？这四个概念两两组合，分别对应什么 IO 模型？给一个生活化的例子说清楚。
?
1. 同步和异步的区别在于谁来完成数据从内核空间到用户空间的拷贝。同步 IO 是用户线程主动去读数据，不管数据有没有就绪，拷贝这个动作都是用户线程自己发起的。异步 IO 是内核在数据就绪后自动完成拷贝并通知用户线程，用户线程不需要参与拷贝过程。
2. 阻塞和非阻塞的区别在于数据没准备好时线程的行为。阻塞 IO 下，数据没准备好线程就挂起等着，CPU 干不了别的事。非阻塞 IO 下，数据没准备好立即返回，线程可以去干别的，过一会儿再来问。
3. 四者两两组合：同步阻塞就是 BIO，线程一直在那里等着直到数据来了读完才走，好比你去餐厅点餐，站在窗口一直等菜做好。同步非阻塞就是 NIO 的多路复用模式，线程注册了感兴趣的事件，数据没准备好就去处理别的连接，等数据就绪了内核通知你再来读，好比你在餐厅取了号然后去逛街，叫号了再回来取餐，但取餐的动作还是你自己去窗口端。异步非阻塞就是 AIO，你把回调告诉内核，数据准备加拷贝全由内核完成，完事了通知你，好比你在外卖平台下单，骑手取餐送到你手上，你全程不用管。异步阻塞理论上存在但实践中基本不用，因为异步的初衷就是让你不阻塞，再去阻塞等待没意义。

### **Q2** BIO（Blocking IO）的工作方式是什么？一个连接一个线程有什么问题？`ServerSocket.accept()` 和 `Socket.read()` 分别阻塞在哪？
?
1. BIO 的工作方式是：服务端用 ServerSocket 绑定端口，然后循环调用 accept 等待客户端连接。accept 是阻塞的，没有新连接进来主线程就一直卡着。一旦 accept 返回了一个 Socket，通常服务端会为这个 Socket 分配一个新的线程去处理。这个工作线程调用 Socket 的 read 方法读取数据，read 也是阻塞的，客户端不发数据线程就一直卡着。这就是一个连接一个线程的模式。
2. 这种方式的问题很明显。第一，线程是操作系统资源，每个线程默认占用约 1MB 栈空间，一万个连接就需要约 10GB 内存，这种开销几乎无法接受。第二，大部分连接并不是时刻都在传输数据，线程大部分时间在阻塞等待，造成严重的资源浪费。第三，线程数过多会导致频繁的上下文切换，CPU 大量时间花在切换上而不是真正的业务处理上。第四，线程的创建和销毁也有开销，虽然可以用线程池缓解，但核心矛盾——一个线程只能服务一个连接——没有改变。
3. accept 阻塞在内核的等待队列上，等待新的 TCP 连接请求到来。read 阻塞在内核的接收缓冲区上，等待数据从网卡到达、协议栈处理完毕后放入接收缓冲区。

### **Q3** NIO（Non-blocking IO / New IO）和 BIO 的本质区别是什么？NIO 的三个核心组件（`Channel` / `Buffer` / `Selector`）分别起什么作用？
?
1. 本质区别有两个层面。第一个是 IO 模型层面：BIO 是面向流的，数据读写必须顺序执行，流是单向的；NIO 是面向块的，数据先读入 Buffer 再处理，而且通道是双向的，可以同时读写。第二个是并发模型层面：BIO 一个连接一个线程，NIO 用一个线程通过 Selector 管理多个连接，这就是 IO 多路复用。
2. 三个核心组件的作用：Channel 代表一个到实体设备的连接，比如 SocketChannel 对应一个 TCP 连接，FileChannel 对应一个文件。它负责实际的 IO 操作，但数据不直接从 Channel 读写，而是通过 Buffer 中转。Buffer 是一块内存区域，NIO 中所有数据读写都要经过它——读数据时从 Channel 读到 Buffer，写数据时从 Buffer 写到 Channel。Selector 是多路复用的核心，它允许一个线程监控多个 Channel 的事件，比如哪些 Channel 可读了、哪些可写了。线程调用 select 方法阻塞等待，一旦有 Channel 就绪，Selector 就返回就绪的 Channel 集合，线程再逐个处理。

### **Q4** AIO（Asynchronous IO）和 NIO 的区别？异步 IO 的「回调」和「Future」两种模式分别怎么用？AIO 在 Linux 上依托什么内核机制？
?
1. AIO 和 NIO 的区别在于数据就绪后谁来拷贝。NIO 下，Selector 通知你 Channel 可读了，但你还得自己调用 read 方法把数据从内核缓冲区拷贝到用户空间的 Buffer，这个拷贝过程是同步的。AIO 下，你发起一个读操作并传入一个 Buffer 和回调，内核在数据就绪后自动把数据拷贝到 Buffer 里，拷贝完了再通知你，用户线程完全不参与拷贝。简单说，NIO 是"数据好了，你来读吧"，AIO 是"数据读好了，给你放这里了"。
2. 回调模式的使用方式：调用 read 时传入一个 CompletionHandler，里面实现 completed 和 failed 两个方法。当 IO 操作真正完成时，系统自动回调 completed 方法，传给你读到的字节数。这种模式的代码结构是非线性的，逻辑分散在多个回调里。
3. Future 模式的使用方式：调用 read 时返回一个 Future 对象，你可以继续做别的事，需要结果时调用 Future.get 方法。如果 IO 还没完成，get 会阻塞等待。
4. 在 Linux 上，AIO 在内核层面对应的是真正的异步 IO 接口，早期是 POSIX AIO，但它是用线程池模拟的假异步。真正可靠的 Linux 异步 IO 是 io_uring 机制，JDK 后续版本也在探索基于 io_uring 实现 AIO。所以严格来说，Linux 上生产级的 AIO 目前主要依赖 IO 多路复用框架的进一步封装，或者直接上 io_uring。

### **Q5** 五种 IO 模型（阻塞 IO / 非阻塞 IO / IO 多路复用 / 信号驱动 IO / 异步 IO）的演进脉络是什么样的？画图说清楚各阶段数据流。
?
1. 五种 IO 模型的演进本质上是不断把等待和拷贝两个阶段做优化的过程。
2. 阻塞 IO 是最原始的。调用 recvfrom 后，如果数据没就绪，进程就挂起。数据就绪后，内核把数据拷贝到用户空间，函数返回。整个过程两个阶段都是阻塞的。
3. 非阻塞 IO 是第一次改进。调用 recvfrom 时，如果数据没就绪，不挂起而是立即返回一个错误码。用户进程可以轮询重试，直到数据就绪，然后内核拷贝数据，函数返回。这解决了等待阶段的阻塞，但拷贝阶段还是阻塞的，而且轮询浪费 CPU。
4. IO 多路复用是第二次改进。通过 select 或 epoll 一个系统调用同时等待多个连接，任意一个就绪就返回。然后对就绪的连接调用 recvfrom，内核拷贝数据，函数返回。它在等待阶段可以等多个连接，但拷贝阶段还是一个一个做的。
5. 信号驱动 IO 是另一条路线。先用 sigaction 注册信号处理函数，然后继续执行其他逻辑。数据就绪后内核发 SIGIO 信号，信号处理函数里调用 recvfrom 拷贝数据。它解决了等待阶段的阻塞，但拷贝阶段还是同步的。
6. 异步 IO 是终极形态。调用 aio_read 时，把数据就绪和数据拷贝两件事全交给内核。内核在数据就绪后自动拷贝到用户空间，然后通知进程。进程拿到通知时数据已经在用户空间的 Buffer 里了，直接使用。整个等待和拷贝都是异步的。
7. 所以五者的核心区别在于：哪些操作在发起 IO 请求的线程里同步完成，哪些由内核异步完成。这是区分它们的分水岭。

## 二、IO 多路复用（select / poll / epoll）

### **Q6** `select` 的工作原理是什么？它有哪些缺陷（FD_SETSIZE 限制、O(n) 遍历、内核态-用户态拷贝开销）？
?
1. select 的工作流程是这样的。用户进程先构建一个 fd_set 位图，把要监控的所有文件描述符放进去，然后调用 select 系统调用。内核收到后，把 fd_set 从用户空间拷贝到内核空间，然后遍历所有描述符，检查哪些有事件就绪。如果有就绪的，select 返回并把 fd_set 写回用户空间，用户进程再遍历整个 fd_set 找到就绪的描述符去处理。如果没有就绪的，进程挂起，直到超时或有事件发生。
2. select 有几个先天缺陷。第一个是 FD_SETSIZE 限制，默认是 1024，因为内核用位图表示描述符集合，一个进程最多监控 1024 个连接。这在万级连接面前完全不够看。第二个是 O(n) 的遍历开销。每次 select 调用，内核需要遍历整个 fd_set 检查每个描述符的状态。当监控的描述符数量很大时，即使只有一两个就绪，也要全部遍历一遍，效率很低。第三个是频繁的内核态用户态拷贝。每次调用 select，都要把整个 fd_set 从用户空间拷贝到内核空间，返回时再拷贝回来。连接越多，这个拷贝的开销越大。

### **Q7** `poll` 相比 `select` 改进了什么？还有什么没解决？
?
1. poll 做了两件事。第一，用 pollfd 结构体数组代替了 select 的位图，解除了 1024 的文件描述符数量限制。pollfd 结构体里包含 fd、要监控的事件和返回的事件，通过数组大小来支持任意数量的描述符。第二，把输入事件和返回事件分开了。select 的 fd_set 既是输入也是输出，每次调用完会被修改，下次调用前必须重建。poll 的 events 和 revents 是两个独立字段，内核只修改 revents，用户不用每次重建。
2. 但是 poll 没有解决根本问题。它和 select 一样，每次调用还是要遍历整个 pollfd 数组，时间复杂度 O(n)。连接数量大时性能依然很差。而且 pollfd 数组的拷贝开销也依然存在，因为每次都要把整个数组从用户空间拷到内核空间再拷回来。

### **Q8** `epoll` 为什么比 `select/poll` 快？`epoll_create` / `epoll_ctl` / `epoll_wait` 三条命令分别做了什么？（红黑树 + 就绪链表 + 回调机制）
?
1. epoll 比 select 和 poll 快的根本原因在于它把"监控"和"获取就绪事件"拆成了两个独立的操作，而且用事件驱动代替了轮询。
2. 三个命令的分工是这样的。epoll_create 在内核创建一个 eventpoll 对象，里面包含一棵红黑树、一个就绪链表和等待队列。红黑树用来存储所有注册的文件描述符，支持快速增删改查。就绪链表用来存放发生事件的文件描述符，是有事件才往里面加，不是每次遍历全体。
3. epoll_ctl 负责维护这棵红黑树。可以往里面添加或删除文件描述符，同时给内核事件表注册一个回调函数。这个回调的作用是——当这个文件描述符上有事件发生时，回调函数被调用，把该文件描述符添加到就绪链表里。这就是事件驱动。对比 select 和 poll，它们是每次调用时被动地去遍历检查，epoll 是事件发生时主动把就绪的 fd 推送到就绪链表。
4. epoll_wait 负责等待事件。它只检查就绪链表是否为空。不为空就直接返回就绪的这些文件描述符，为空就阻塞等待。它不需要遍历全部注册的描述符，只需要取就绪链表里的。所以 epoll_wait 的时间复杂度是 O(1) 级别的，跟监控的描述符总数无关。select 和 poll 每次调用都要 O(n) 遍历。

### **Q9** epoll 的 LT（水平触发）和 ET（边缘触发）区别？ET 模式为什么必须搭配非阻塞 IO？为什么要循环 read 直到 EAGAIN？
?
1. LT 水平触发是 epoll 的默认模式，语义是：只要接收缓冲区里还有数据没读完，epoll_wait 就会反复通知你。这次没读完，下次 epoll_wait 还会返回这个文件描述符，直到缓冲区的数据彻底读完。
2. ET 边缘触发更激进，只在接收缓冲区状态发生变化的那一刻通知一次。从无到有通知一次，之后如果没读完，哪怕缓冲区里还有数据，epoll_wait 也不会再通知了，必须等下一批新数据到达产生新的触发。
3. 所以 ET 模式必须搭配非阻塞 IO，原因很简单：ET 只通知一次，你必须在这个通知的处理循环里把数据全部读完，不能放过任何一个字节。如果用阻塞 IO 去读，读到最后一个字节时再读一次就会阻塞住，因为已经没有数据了，但阻塞 read 不会返回，线程就卡死了。非阻塞 IO 读到没数据时不会阻塞，而是返回零或抛出 EAGAIN，这样就能准确判断"读完了"，然后安全退出读取循环。
4. 循环 read 直到 EAGAIN 就是为了完成这个一次性读完的要求。每次读到数据就继续读，直到返回 -1 或者 EAGAIN 表示缓冲区为空了才停止。这样才能确保这个文件描述符上的数据被完全处理，不遗漏。

### **Q10** epoll 的「惊群效应」是什么？`EPOLLEXCLUSIVE` 怎么解决？Nginx 和 Netty 各自怎么处理惊群的？
?
1. 惊群效应是指多个进程或线程同时监听同一个文件描述符时，一个连接事件到达，所有等待的进程或线程都被唤醒去抢这个连接，但最终只有一个能成功处理，其余的都是白被唤醒。这会造成不必要的 CPU 开销和上下文切换。
2. 早期的典型场景是多个进程都调用 epoll_wait 监听同一个 listen fd。新连接到来时，所有进程都被唤醒，但只有一个 accept 成功，其他的 accept 返回 EAGAIN 又回去睡。这就是惊群。
3. EPOLLEXCLUSIVE 是内核 4.5 版本引入的标志。一个文件描述符注册了 EPOLLEXCLUSIVE 之后，当事件到达时，内核只会唤醒等待队列上的一个进程，而不是全部唤醒。这从内核层面解决了惊群问题。
4. Nginx 通过加锁处理惊群。多个 worker 进程在 accept 之前先抢一把共享锁，抢到的进程才去 accept，没抢到的继续等。这样一次只有一个 worker 去处理新连接，避免了惊群。
5. Netty 的处理方式是：在单个进程内的多线程模型中，Netty 通过一个 BossGroup 线程池服务端 Reactor 线程，如果 bind 同一个端口，也是通过底层 EPOLLEXCLUSIVE 或者 eventLoop 上锁来避免多个线程同时 accept。不过 Netty 推荐的做法是只用一个 BossEventLoopGroup 里的一个线程去 accept，然后在 workerGroup 上均匀分发连接。

## 三、Java NIO 核心

### **Q11** `Buffer` 的三个核心属性 `capacity` / `position` / `limit` 分别是什么？在读写模式下各自指向哪里？`flip()` 和 `clear()` 方法做了什么？
?
1. Buffer 有三个核心属性。capacity 是缓冲区的最大容量，创建后不可变。position 是当前操作的位置指针，读的时候指向下一个要读的字节位置，写的时候指向下一个要写的字节位置。limit 是操作的有效边界，读的时候表示最多能读到哪里，写的时候等于 capacity。
2. 在写模式下，position 指向下一个要写入的位置，初始是 0，每写一个字节 position 加一。limit 等于 capacity，因为写操作可以写满整个缓冲区。
3. 在读模式下，position 指向下一个要读取的位置，初始是 0，每读一个字节 position 加一。limit 指向可读数据的最末尾，表示最多读到哪里。
4. flip 方法的作用是从写模式切换到读模式。它把 limit 设为当前的 position，然后把 position 重置为 0。这样读操作就知道最多读到刚才写了多少，不会读到没写过的垃圾数据。
5. clear 方法的作用是准备重新写入。它把 position 重置为 0，limit 重置为 capacity。注意 clear 并不真正清空数据，只是重置了指针，原来的数据还在内存里，只是下次写操作会覆盖掉。

### **Q12** `ByteBuffer` 的 allocate（堆内存）和 allocateDirect（直接内存）区别？直接内存的优缺点？什么时候用直接内存？
?
1. allocate 分配的是 JVM 堆内存中的字节数组，受 GC 管理。allocateDirect 分配的是堆外直接内存，不归 JVM 堆管理，不受 GC 影响。
2. 直接内存的优点主要有两个。一是减少了一次数据拷贝。如果底层 IO 操作需要把数据从用户空间拷贝到内核空间，堆内存的 ByteBuffer 因为 GC 可能移动对象，不能直接把内存地址传给内核，需要先拷贝到一个临时的堆外缓冲区，多了一次拷贝。直接内存在堆外，地址固定，可以直接把地址交给内核使用，省了这次拷贝。二是避免了 GC 的干扰，对于大数据的场景，不会因为 GC 导致 IO 操作暂停。
3. 直接内存的缺点有三个。一是分配和回收的成本比堆内存高，因为要走操作系统的内存分配。二是可能引发堆外内存泄漏，如果忘记释放，堆外内存不会被 GC 自动回收，因为它的引用对象在堆上可能很小，GC 不容易触发回收。三是需要通过 ByteBuffer 的 Cleaner 或手动释放机制来管理生命周期。
4. 选用原则很简单：如果数据量大、生命周期长、频繁用于 IO 传输，用直接内存。如果是短生命周期的临时数据，或者需要频繁创建销毁，用堆内存。

### **Q13** `Selector` 的 `select()` / `selectNow()` / `select(long timeout)` 区别？Selector 怎么注册 Channel？`SelectionKey` 的四个事件（OP_READ / OP_WRITE / OP_CONNECT / OP_ACCEPT）什么时候触发？
?
1. select 三个方法都是用来获取就绪事件的，区别在于阻塞行为。select 是无参的，会一直阻塞直到至少有一个 Channel 就绪。selectNow 是非阻塞的，不管有没有就绪 Channel 都立即返回，没有就返回 0。select(long timeout) 是带超时的，在超时时间内阻塞，有事件就提前返回，超时到了还没有事件也返回。
2. 注册 Channel 的步骤：先把 Channel 设为非阻塞模式，然后通过调用 Selector 的 open 方法获取一个 Selector 实例，再调用 Channel 的 register 方法，传入 Selector 和感兴趣的事件集合。如果是 ServerSocketChannel，一般注册 OP_ACCEPT。如果是 SocketChannel，一般注册 OP_READ。
3. 四个事件的触发时机：OP_ACCEPT 在 ServerSocketChannel 上触发，表示有新连接进来，可以调用 accept 了。OP_CONNECT 在客户端 SocketChannel 上触发，表示连接操作完成。OP_READ 在 SocketChannel 上触发，表示通道中有数据可读。OP_WRITE 在 SocketChannel 上触发，表示通道的写缓冲区有空闲空间，可以写入数据了。需要注意 OP_WRITE 的特殊性——大部分时间里写缓冲区都是可写的，所以不要一直注册 OP_WRITE，否则 Selector 会频繁被唤醒。通常只有在需要写数据时临时注册，写完立即取消。

### **Q14** `FileChannel` 的 `transferTo()` 和 `transferFrom()` 底层做了什么？这和操作系统零拷贝是什么关系？
?
1. transferTo 是把当前 FileChannel 的数据直接传输到一个可写的目标通道，比如从文件传输到 Socket。transferFrom 是把一个可读的源通道的数据传输到当前 FileChannel，比如从 Socket 传输到文件。
2. 底层的技术支撑就是操作系统的零拷贝。如果操作系统支持 sendfile 系统调用，transferTo 和 transferFrom 底层就会调用 sendfile 来实现。sendfile 允许数据从文件系统页缓存直接通过 DMA 拷贝到网卡，不需要先拷贝到用户空间再拷贝到 Socket 缓冲区。在支持 SG-DMA 的硬件上，甚至不需要把数据从内核缓冲区拷到 Socket 缓冲区——只传递文件描述符和数据长度，DMA 引擎直接从页缓存把数据搬到网卡。这就是真正的零拷贝，数据传输过程中 CPU 不参与拷贝动作。
3. 所以 FileChannel 的 transferTo 在 Java 层面是对操作系统零拷贝能力的一个封装。如果操作系统不支持，会退化为普通的用户态内存拷贝。

### **Q15** Java NIO 的「空轮询」Bug（epoll bug）是什么现象？JDK 是怎么修复的？Netty 又是怎么处理的？
?
1. 空轮询 Bug 是 JDK NIO 中一个经典问题。具体表现是：Selector 的 select 方法本应该在没有任何就绪事件时阻塞等待，但在某些情况下会异常地立即返回，返回值为 0，也就是没有任何就绪事件但是没有阻塞。这就导致 NIO 的事件循环进入死循环，CPU 持续占用百分之百——因为 select 立即返回，循环又立即再次调用 select，无限往复。
2. 这个 Bug 的根源是 Linux epoll 的一个已知问题：在某些情况下，epoll_wait 返回了但没有对应的就绪事件。JDK 底层的 EPollArrayWrapper 没有处理好这种边界情况。
3. JDK 的修复方式是在 select 返回 0 时记录次数，当空轮询次数超过一个阈值——JDK 里设的是 512 次——就认为触发了空轮询 Bug。这时候重建一个 Selector，把原来注册的 Channel 全部重新注册到新的 Selector 上，老的丢给 GC。相当于换了台发动机。
4. Netty 做了更精细的处理。它除了统计空轮询次数，还限制了 select 的阻塞时间。如果 select 在极短的时间内就返回了——比如不到 1 毫秒——并且返回值为 0，就认为发生了空轮询。Netty 的阈值比 JDK 更保守，默认是 512 次，也提供了重建 Selector 的策略。另外 Netty 还用了 selectNow 配合阻塞 select 的方式，通过计算实际等待时间来判断是否发生了空轮询。

## 四、零拷贝

### **Q16** 传统 IO 的一次 `read()` + `write()`，数据在用户态和内核态之间经历了几次拷贝？几次上下文切换？画出完整的数据流向图。
?
1. 传统 IO 从磁盘文件发到网卡，一次完整的 read 加 write 经历了四次数据拷贝和四次上下文切换。
2. 四次拷贝分别是：第一次，通过 DMA 把数据从磁盘读到内核的读缓冲区。第二次，CPU 把数据从内核读缓冲区拷贝到用户空间的缓冲区，这是 read 方法做的事情。第三次，CPU 把数据从用户空间缓冲区拷贝到内核的 Socket 发送缓冲区，这是 write 方法做的事情。第四次，通过 DMA 把数据从 Socket 发送缓冲区拷贝到网卡发送出去。其中有两次是 CPU 直接参与的拷贝——内核到用户和用户到内核——这是性能瓶颈的核心。
3. 四次上下文切换分别是：调用 read 时从用户态切到内核态，read 返回时从内核态切回用户态；调用 write 时从用户态切到内核态，write 返回时从内核态切回用户态。
4. 所以传统 IO 的问题是 CPU 两次参与数据拷贝，加上四次上下文切换。零拷贝的目标就是消除 CPU 参与的拷贝和尽可能减少上下文切换。

### **Q17** Linux 的 `mmap` + `write` 实现了零拷贝吗？它减少了什么？
?
1. mmap 加 write 不算真正的零拷贝，但确实减少了开销。严格来说，零拷贝通常指内核态到用户态的数据拷贝次数为零，而 mmap 加 write 还有一次 CPU 参与的拷贝。
2. mmap 的作用是把内核空间的缓冲区映射到用户空间的地址空间。这样用户进程可以直接通过操作这个映射区来读写内核缓冲区的数据，省掉了 read 时从内核缓冲区到用户缓冲区的那次拷贝。数据从磁盘到内核缓冲区之后，用户进程直接在映射区读取，不需要再做一次拷贝。
3. 然后调用 write 时，数据从内核读缓冲区由 CPU 拷贝到内核的 Socket 发送缓冲区，最后 DMA 拷贝到网卡。总共三次数据拷贝——一次 DMA 磁盘到内核，一次 CPU 从内核到 Socket，一次 DMA 到网卡——比传统 IO 少了那个内核到用户的 CPU 拷贝，但仍然保留了内核到 Socket 的那次 CPU 拷贝。
4. 上下文切换也从四次减少到了两次——少了 read 的两次切换。
5. 所以 mmap 加 write 相比于传统 IO，减少了一次 CPU 拷贝和两次上下文切换，但还算不上零拷贝，因为 CPU 还参与了一次从内核读缓冲区到 Socket 缓冲区的拷贝。

### **Q18** Linux 的 `sendfile()` 零拷贝是怎么做到的？DMA 拷贝、SG-DMA（Scatter-Gather DMA）在这个流程中起了什么作用？
?
1. sendfile 直接在内核态完成数据从文件到网络的传输，完全绕过了用户空间。调用 sendfile 时，指定源文件描述符和目标 Socket 描述符，剩下的全由内核完成。
2. 基本版 sendfile 的流程是两次数据拷贝加两次上下文切换。第一次 DMA 把数据从磁盘拷到内核读缓冲区，第二次 CPU 把数据从内核读缓冲区拷到 Socket 发送缓冲区，第三次 DMA 从 Socket 发送缓冲区拷到网卡。只有一次 CPU 参与拷贝，上下文切换也只有两次——sendfile 调用时一次，返回时一次。已经比传统又少了很多。
3. SG-DMA 版本是真正的零拷贝。SG-DMA 是支持分散聚集的 DMA 引擎，可以从多个不连续的内存位置收集数据并组合起来发送。在 sendfile 流程中，CPU 不再做内核读缓冲区到 Socket 缓冲区的拷贝，而是把文件描述符和数据的地址、长度记录在 Socket 缓冲区的描述符里。SG-DMA 引擎根据这些描述信息，直接从内核读缓冲区把数据读取到网卡，完全绕过 Socket 缓冲区。整个过程只有两次 DMA 拷贝：磁盘到内核，内核到网卡，CPU 不参与任何拷贝动作。这才是真正意义上的零拷贝——CPU 零参与。

### **Q19** Kafka 为什么用零拷贝？它在什么场景下用了零拷贝，什么场景下用了 `mmap`？这跟它的「顺序写盘」策略是什么关系？
?
1. Kafka 用零拷贝是为了最大化消息生产和消费的吞吐量，同时最小化 CPU 开销。Kafka 的设计哲学就是少做不必要的 CPU 操作。
2. 在消息消费场景下，Kafka 用零拷贝。消费者从 Broker 拉取消息时，Broker 需要把磁盘上的消息数据发送到网卡。Kafka 的 FileRecords 的 writeTo 方法底层就是调用 FileChannel 的 transferTo，最终走到 Linux 的 sendfile 系统调用。因为消费者消费的消息通常不需要在 Broker 端做任何处理，只需要把原始字节从磁盘发出去，这就是零拷贝的最佳舞台。数据从页缓存通过 DMA 直接到网卡，CPU 完全不用参与拷贝。
3. 在写入消息到日志的场景下，Kafka 用 mmap。生产者发来的消息写入 Broker 的分区日志，Kafka 通过 mmap 把日志文件映射到内存，写入消息时相当于写内存，由操作系统异步刷盘。这样避免了传统写文件时的用户空间到内核空间的拷贝，写入效率极高。
4. 这和顺序写盘的策略密切相关。Kafka 的日志是追加写的，只追加不修改，顺序写入能充分利用磁盘的连续写入性能，甚至追上了随机写内存的速度。而且顺序写盘配合 mmap，页缓存命中率很高，新写入的数据大概率还在缓存里，消费时直接零拷贝发走，磁盘都不需要读。整个链路从生产者的网络写入到消费者的网络发送，数据在磁盘上只存了一份，靠的是顺序写盘加页缓存加零拷贝这个组合拳。

## 五、Netty（面试标配）

### **Q20** Netty 的线程模型：「主从 Reactor 多线程」，画图说清楚 BossGroup / WorkerGroup 的分工，一个连接从建立到读写的完整流程。
?
1. Netty 的主从 Reactor 多线程模型把任务分成了两个线程池：BossGroup 和 WorkerGroup。BossGroup 负责接受新连接，WorkerGroup 负责处理连接的 IO 读写。
2. 一个连接从建立到读写的完整流程是这样的。第一步，BossGroup 中的一个 NioEventLoop 线程，在它的 Selector 上监听着 ServerSocketChannel 的 OP_ACCEPT 事件。第二步，客户端发起连接，Selector 检测到 OP_ACCEPT 就绪。第三步，Boss NioEventLoop 调用 accept 拿到 SocketChannel，从 WorkerGroup 中选择一个 NioEventLoop——默认是轮询选择——把这个 SocketChannel 注册到选中的 Worker NioEventLoop 的 Selector 上，注册的事件是 OP_READ。第四步，从此之后这个连接的 IO 事件全由这个 Worker NioEventLoop 负责。当客户端发送数据时，Worker NioEventLoop 的 Selector 检测到 OP_READ 事件，然后在 ChannelPipeline 里触发读事件，数据依次经过各个 ChannelHandler 处理。如果需要写回数据，也是在这个 Worker 线程里通过 Pipeline 触发写操作，写完之后再注册 OP_WRITE 事件通知刷出。
3. 这个模型的好处是职责分离——Boss 只管连接的建立，做的是非常轻量的事；Worker 只负责已建立连接的读写，连接数量再多也不影响 Boss。而且每个连接只绑定一个 Worker NioEventLoop，消除了线程安全问题。

### **Q21** Netty 的 `ChannelPipeline` 和 `ChannelHandler` 是什么关系？入站事件（`ChannelInboundHandler`）和出站事件（`ChannelOutboundHandler`）在 Pipeline 中的传播顺序？
?
1. ChannelPipeline 是一条处理器链，由多个 ChannelHandler 串起来组成。每个 Channel 都有自己的 Pipeline，数据和事件在这个管道中流动，经过每一个 Handler 处理。ChannelHandler 是处理逻辑的载体，你实现的编解码、业务处理逻辑都以 Handler 的形式挂在 Pipeline 上。
2. 入站事件是从网络读到数据后触发的，比如 channelRead。入站事件在 Pipeline 中的传播顺序是从链头到链尾依次经过每个 InboundHandler。比如你添加的顺序是：解码器 Handler，然后是业务逻辑 Handler，数据到来时先经过解码器把字节解码成对象，然后传给业务逻辑 Handler 处理。
3. 出站事件是把数据写回网络时触发的，比如 write。出站事件的传播顺序是反向的，从链尾到链头依次经过每个 OutboundHandler。比如你在业务 Handler 中调用 ctx.writeAndFlush 写出一个对象，数据会先经过编码器把这个对象编码成字节，然后再经过其他可能的输出处理器，最终通过链头的网络层发送出去。
4. 这个正反向传播的设计很巧妙：入站像穿衣服，从里到外一件件穿；出站像脱衣服，从外到里一件件脱。同一个 Pipeline 上既有 InboundHandler 又有 OutboundHandler，各自保持各自的传播方向。

### **Q22** Netty 的 `ByteBuf` 和 Java NIO 的 `ByteBuffer` 对比，有哪些优势？（读写双指针 / 零拷贝 / 引用计数 / 池化）
?
1. ByteBuf 在四个维度上完全碾压 ByteBuffer。
2. 第一个，读写双指针。ByteBuffer 只有一个 position 指针，读写模式通过 flip 切换，容易出错且代码不直观。ByteBuf 有独立的 readIndex 和 writeIndex，读操作移动 readIndex，写操作移动 writeIndex，两个操作互不干扰，不需要 flip 就能随时读写。这就是零拷贝 slices 的基础——可以通过 slice 方法创建一个共享底层数据的视图，各自有不同的读写指针。
3. 第二个，零拷贝能力。ByteBuffer 没有内置零拷贝支持。ByteBuf 提供了多种零拷贝方式，比如 slice 可以截取一段不拷贝数据，duplicate 复制一份共享数据的视图，CompositeByteBuf 把多个 ByteBuf 虚拟合并成一个但不拷贝数据。
4. 第三个，引用计数。Netty 的 ByteBuf 实现了引用计数机制，通过 retain 和 release 管理生命周期。当引用计数归零时，底层内存自动回收——堆内存还给 GC，直接内存通过 Cleaner 释放。这解决了直接内存的泄漏风险。
5. 第四个，池化。Netty 提供了 PooledByteBufAllocator，通过对象池复用 ByteBuf。频繁创建销毁的直接内存不再是每次都向操作系统申请释放，而是从池里取和归还，大幅降低了分配回收的开销和 GC 压力。Java NIO 的 ByteBuffer 没有池化机制。

### **Q23** Netty 的零拷贝体现在哪些方面？（CompositeByteBuf / wrap / slice / FileRegion）
?
1. Netty 的零拷贝并不是操作系统意义上的零拷贝，而是指 JVM 层面减少不必要的数据拷贝。
2. CompositeByteBuf 是第一个体现。当你有多个 ByteBuf 想组合在一起发出去时，不用把它们拷贝到一个新的 ByteBuf 里。CompositeByteBuf 只是维护了一个组件列表和对外的读写指针，对外看起来像一个连续的缓冲区，内部分散在各个组件里，读取时自动切换组件。这样省掉了合并拷贝。
3. wrap 操作是把一个字节数组包装成 ByteBuf，不拷贝数据。底层直接引用这个数组，修改 ByteBuf 也会影响原数组。
4. slice 操作是从一个 ByteBuf 中截取一段，返回一个新的 ByteBuf，但底层数据和原始 ByteBuf 共享同一块内存。修改 slice 会反映到原 ByteBuf 上，反之亦然。只是读写指针是独立的。
5. FileRegion 是真操作系统零拷贝。它是通过 FileChannel 的 transferTo 实现的，数据从文件直接到网络，不经过用户空间。在 Netty 中发送文件时，可以直接用 DefaultFileRegion 包装文件，在支持的系统上就是 sendfile 零拷贝。

### **Q24** Netty 的心跳机制（`IdleStateHandler`）怎么用？读空闲 / 写空闲 / 读写空闲分别怎么处理？
?
1. IdleStateHandler 是一个 ChannelHandler，工作方式是根据设定的时间间隔检测连接的读写活动。配置时指定三个时间参数：读空闲时间、写空闲时间、读写空闲时间。当连接在指定时间内没有对应的 IO 活动时，IdleStateHandler 就会触发一个 IdleStateEvent 事件。
2. 这个事件会沿着 Pipeline 向后传播，你需要在后面的 Handler 里捕获并处理它。通常的做法是在自定义 Handler 的 userEventTriggered 方法中判断事件类型，如果是 IdleStateEvent，再判断是读空闲、写空闲还是读写空闲。
3. 读空闲表示指定时间内没有从对端读到任何数据。处理方式通常是关闭这个连接，因为对端可能已经断开了。写空闲表示指定时间内没有向对端发送数据，处理方式通常是主动发送一次心跳消息，表明自己还活着。读写空闲是两者的组合，任意一种空闲时间到达都触发，通常用来做双重保活，既要定期发心跳，也要检测对端是否还活着。

### **Q25** Netty 的拆包粘包问题：`LineBasedFrameDecoder` / `DelimiterBasedFrameDecoder` / `FixedLengthFrameDecoder` / `LengthFieldBasedFrameDecoder` 分别解决什么场景？
?
1. TCP 是流式协议，没有消息边界，发送方连续写了两次数据，接收方可能一次读到打包在一起的消息，也可能读两次才收完一条消息。这分别是粘包和拆包。Netty 的四种解码器就是用来在不同场景下找回消息边界的。
2. LineBasedFrameDecoder 是按行分割。每个消息以换行符结尾，解码器读到换行符就把前面读到的数据作为一个完整帧输出。适合文本协议，比如 HTTP 的请求行。
3. DelimiterBasedFrameDecoder 是按自定义分隔符分割。可以自己指定分隔符，比如用特定字符或者字节序列作为消息结尾标记。适用的范围比行解码器更广，凡是能定义出消息结束标记的协议都能用。
4. FixedLengthFrameDecoder 是按固定长度分割。每个消息的长度是固定的，解码器每读满指定长度就切割出一个完整帧。适合对端发的每条消息都一样长的场景，比如某些硬件通信协议。
5. LengthFieldBasedFrameDecoder 是通用性最强的，基于消息头中的长度字段来分割。协议设计时在消息头部放一个长度字段，表示消息体的长度。解码器先解析这个长度字段，然后根据长度读取对应字节的消息体。这能处理几乎所有自定义二进制协议，也是配合 Protobuf 最常用的解码器。

## 六、序列化（IO 层视角）

### **Q26** Java 原生序列化（`ObjectOutputStream`）的缺陷是什么？（跨语言、版本兼容、性能、安全）为什么分布式场景基本不用它？
?
1. Java 原生序列化有四个致命缺陷。
2. 第一，跨语言不行。序列化的格式是 Java 私有的，只有 Java 能解析。分布式系统往往异构语言混合，没法用。
3. 第二，版本兼容性差。serialVersionUID 稍微对不上就反序列化失败。虽然可以通过定义 serialVersionUID 手动控制，但一旦加了字段或者改了类型，老版本解析新版本的数据就容易出错。
4. 第三，性能差。Java 序列化会携带大量的元数据，包括类的全限定名、字段名、类型信息等，序列化后的体积臃肿。而且序列化和反序列化的过程涉及大量反射操作和对象创建，速度慢。实测中 Protobuf 等序列化框架比 Java 原生快几倍甚至几十倍。
5. 第四，安全性有隐患。反序列化时通过 readObject 可以触发任意类的构造和代码执行，是序列化攻击的入口。很多安全漏洞都是利用 Java 反序列化执行的远程代码执行攻击。
6. 综上，跨语言不行、性能差、体积大、不安全，所以分布式系统基本不用它。RPC 框架里常见的替代方案是 Protobuf、Hessian、Kryo 这些。

### **Q27** Protobuf / Thrift / Avro / Kryo / Hessian / Fastjson 这些序列化框架，从「编解码速度 / 序列化后大小 / 跨语言 / 可读性」四个维度怎么选型？
?
1. 从四个维度分别看。
2. 编解码速度上，Kryo 和 Protobuf 是第一梯队，都很快。Kryo 专为 Java 优化，省掉了反射开销。Protobuf 的编解码本身就是高效的二进制序列化。Thrift 和 Avro 也属于快的那批。Hessian 和 Fastjson 相对较慢，Fastjson 因为是文本格式，解析开销大。
3. 序列化后大小上，Protobuf 是最小的，因为用了紧凑的二进制编码和变长整型。Kryo、Avro、Thrift 也都很小。Hessian 稍大一些因为是自描述的二进制格式。Fastjson 最大因为它是 JSON 文本，有很多冗余的字段名字符串。
4. 跨语言上，Protobuf、Thrift、Avro 都原生支持多语言，这三种都是语言无关的 IDL 定义加代码生成，多语言生态很完善。Fastjson 也是跨语言的，但 JSON 本身的类型表达能力弱于 IDL。Kryo 和 Hessian 都是 Java 中心的，Kryo 主要就是 Java 生态，Hessian 虽然有多语言支持但不如前三者完善。
5. 可读性上，只有 Fastjson 是直接可读的，因为 JSON 就是文本格式。其他五种都是二进制格式，人类不可直接阅读。
6. 选型建议是这样的：对性能要求极高并且需要跨语言的，选 Protobuf，尤其在 gRPC 生态下是最佳选择。纯 Java 内部高性能通信的，选 Kryo，比如 Dubbo 默认序列化就是 Hessian 但很多团队切到了 Kryo。需要跨语言但不想维护 IDL 文件的，考虑 Avro 的动态模式。需要调试友好或者对接前端的，用 JSON。

### **Q28** 为什么 Netty + Protobuf 是高性能 RPC（如 gRPC）的标配？`LengthFieldBasedFrameDecoder` + `ProtobufDecoder` 怎么组合解决拆包？
?
1. Netty 加 Protobuf 成为高性能 RPC 的标配，是因为两者在各自层面都是极致优化的选择。Netty 的网络 IO 层提供了高效的 NIO 多路复用和零拷贝，Protobuf 提供了高效紧凑的序列化。两者组合就是一条从头到尾高性能的数据通道。
2. 在具体流水线上，LengthFieldBasedFrameDecoder 和 ProtobufDecoder 配合解决拆包问题。工作流程是这样的：LengthFieldBasedFrameDecoder 先解码，它根据协议头里定义的长度字段——比如头部偏移多少字节开始是长度字段，长度字段本身占几个字节——来识别出完整的一帧。它把属于一个消息的所有字节聚合成一个完整的 ByteBuf 传给下一个 Handler。然后 ProtobufDecoder 接收这个完整的 ByteBuf，把它反序列化为 Protobuf 消息对象。这里的关键是顺序和分工——LengthFieldBasedFrameDecoder 解决 TCP 层面的帧边界问题，ProtobufDecoder 解决字节到对象的序列化问题。两者各司其职，一个把流切成帧，一个把帧还原成对象。

## 七、实战场景

### **Q29** 你要设计一个百万长连接的 IM 系统，为什么用 Netty？BossGroup 和 WorkerGroup 分别设几个线程？心跳间隔设多少？什么情况下连接数高但 QPS 低，怎么排查？
?
1. 用 Netty 而不是自己写 NIO，是因为 Netty 把 NIO 的复杂性封装好了。内存管理有池化 ByteBuf 和引用计数避免泄漏，线程模型有主从 Reactor 开箱即用，编解码有丰富的 Pipeline 机制，而且 Netty 在百万连接级别已经有很多成熟的实践验证。
2. BossGroup 线程数设定：Boss 只负责 accept，非常轻量，一般设 1 到 2 个线程就够了。如果端口数多于一个可以适当增加。WorkerGroup 设定：Worker 负责所有连接的读写和业务处理，线程数通常设为 CPU 核心数的两倍。对于百万连接 IM 这种 IO 密集型场景，可以更激进一些设为核心数的两倍到四倍，但不宜太多，否则线程上下文切换开销反而拖低性能。
3. 心跳间隔一般设在 30 秒到 60 秒之间。太短了心跳包太频繁会占带宽和 CPU，太长了不能及时发现死连接。具体数值根据业务容忍度定，如果业务要求尽快检测对端断线就设短一些比如 30 秒。
4. 连接数高但 QPS 低的原因和排查方向有这几个。第一，绝大部分连接是空闲的。百万长连接并不代表百万活跃连接，IM 场景大部分连接就是挂着等消息，这是正常的。第二，IO 线程阻塞了。某个 Handler 里做了耗时操作，比如同步访问数据库，把 IO 线程堵住了，其他连接的读写得不到及时处理。排查方法是检查 Worker EventLoop 的阻塞时间。第三，堆内存配置不合理或者 GC 频繁。百万连接本身内存占用不小，如果 GC 频繁会导致短暂的停顿影响吞吐。排查时可以看 GC 日志，确认是否 Full GC 频繁。第四，如果是 Epoll 空轮询 Bug 导致 CPU 打满但没做实际工作，可以通过检查 CPU 使用率和 Netty 的 Selector 事件循环来定位。

### **Q30** 大文件上传（2GB+）不用 OOM，服务端怎么设计？`HttpServletRequest.getInputStream()` 是会把整个文件读进内存吗？分片上传断点续传怎么做？
?
1. 大文件上传服务端不 OOM 的核心原则是流式处理，边读边写，不把整个文件放在内存里。
2. HttpServletRequest.getInputStream 本身不会把整个文件读进内存，它返回的是一个流，可以分次读取。问题在于很多服务端框架的默认实现，比如 Spring Boot 的 MultipartFile，会把整个文件内容先存到临时目录或者内存中，再交给 Controller 处理。如果文件 2GB，内存或者磁盘空间都可能撑不住。正确的做法是直接用 getInputStream，分段读取，每次读比如 8KB 或 16KB 的缓冲，读一段写一段到目标存储，读完全部就处理完了。还可以通过设置 Content-Type 和边界参数，不使用框架的 Multipart 解析，自己解析流中的文件部分。
3. 分片上传和断点续传的设计思路是：客户端把大文件切成多个小分片，比如每个分片 5MB。上传时，客户端先请求服务端分配一个上传 ID，然后把分片逐个上传，每个分片带上上传 ID 和分片序号。服务端把每个分片存成临时文件，用上传 ID 加序号命名。全部分片上传完毕后，客户端发起合并请求，服务端把所有的分片按序号拼接成完整文件。如果中间某个分片上传失败了，客户端只需要重新上传那个失败的分片，其他的不动。断点续传的关键是客户端在上传前先查一下服务端已有的分片列表，只上传缺失的分片。
4. 存储层面，分片可以存在本地临时目录，也可以存在对象存储里，对象存储一般都原生支持分片上传 API，比如 AWS S3 的 Multipart Upload。这样实现更简单，而且对象存储天然没有单机磁盘容量的限制。
