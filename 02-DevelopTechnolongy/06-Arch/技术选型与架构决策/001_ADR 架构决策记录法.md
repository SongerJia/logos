|---|---|---|---|---|---|
|**8.1.1**|**ADR 是什么？**|Architecture Decision Record：轻量级架构决策文档；记录**做了什么决策、为什么这么做、后果是什么**；替代传统Word式"架构设计文档"(写完就过时)|标题 + 状态(提议/已采纳/已废弃/被替代) + 上下文 + 决策 + 后果|"ADR和普通技术文档的区别？为什么不用Wiki？"|每个 FlowPulse 关键选型都有对应 ADR 文件（见下方完整列表）|
|**8.1.2**|**ADR 标准模板**|Michael Nygard 提出的经典格式，6个核心字段：①Title(标题) ②Status(状态) ③Context(上下文/背景问题) ④Decision(决策内容) ⑤Consequences(正面+负面后果) ⑥Alternatives(考虑过的备选方案)|Context = 问题是什么；Decision = 选了什么；Consequences = 好处和代价；Alternatives = 为什么不选别的|"ADR需要多详细？每行代码的决策都记录吗？"|**只记录关键且不可逆(或难逆)的决策**——如选择 Dubbo 而非 gRPC、自研引擎而非 Activiti|
|**8.1.3**|**ADR 的可逆性分类 ★**|**可逆决策(Reversible)**：两扇门决策，选错了可以低成本回头 → 应快速决策，不必过度分析。**不可逆决策(Irreversible)**：一扇门决策，选了就不能回头的 → 必须充分分析|Jeff Bezos 的"一扇门 vs 两扇门"理论：80%的决策应该是两扇门决策(可逆)，应该快速执行|"举几个可逆和不可逆的技术决策例子？"|可逆：选Redis做缓存(换Memcached不难) / 不可逆：选Java作为主力语言(重写成本极高) / **半不可逆**：选Dubbo做RPC(迁移gRPC有成本但可行)|
|**8.1.4**|**ADR 的生命周期管理**|Proposed(提议) → Accepted(采纳) → Deprecated(废弃) → Superseded(被替代)；ADR一旦写入**不能删除只能标记废弃**；新版本决策替代旧版时保留历史链|"ADR多了之后怎么管理？怎么查找某个决策的历史演变？"|Git管理的Markdown文件：`docs/adr/NNN-标题.md` (编号递增) / 目录索引 `README.md`||
|**8.1.5**|**ADR 与团队协作**|ADR不是架构师一个人的事！重大ADR需要：①提出(任何人) ②Review(TechLead+相关开发者) ③决策会议(必要时) ④记录归档 ⑤定期回顾(季度ADR Review)|"如果团队成员对ADR有异议怎么办？决策僵局怎么打破？"|FlowPulse 规则：P0级选型(语言/框架/数据库)需全员Review / P1级(TeamLead审批) / P2级(自行记录)||
