## 第一章 项目故事的核心价值

### 1.1 为什么面试要讲项目

面试中考查项目经验，面试官真正想了解的是：

| 考查维度 | 面试官想确认的问题 |
|---------|------------------|
| **技术深度** | 你是否真正理解所用技术，而非只会调 API？ |
| **架构能力** | 你能否从全局视角理解系统设计，而非只关注自己的一亩三分地？ |
| **问题解决** | 遇到技术难题时，你的分析思路和解决方法是什么？ |
| **业务理解** | 你是否理解技术背后的业务价值，而非只是"接需求写代码"？ |
| **团队协作** | 你在团队中的角色和贡献是什么？ |
| **成长反思** | 你能否从项目中总结经验教训，持续改进？ |

```
简历筛选（关键词匹配）
    ↓
项目深挖（验证真实性 + 技术深度）  ← 最核心环节
    ↓
技术追问（八股 + 场景题）
    ↓
综合评估（文化匹配 + 潜力）
```

### 1.2 好的项目故事 vs 差的项目故事

**差的项目故事**（流水账式）：

> "我做了一个电商系统，用了 Spring Boot + MySQL + Redis。负责订单模块的 CRUD，用 Redis 做缓存，用 RabbitMQ 发消息。系统上线后运行正常。"

**问题**：
- 没有业务背景：做什么的电商？多大体量？
- 没有技术难点：CRUD 没有技术含量
- 没有量化结果："运行正常"不是结果
- 没有个人贡献：你做了什么？团队做了什么？
- 没有深度可挖：面试官无从追问

**好的项目故事**（STAR 结构）：

> "我们做的是一个 B2C 电商平台的订单系统，日均订单 10 万单，大促峰值 QPS 3000。
>
> **背景**：原来订单系统是单体架构，下单链路同步调用库存、营销、物流等 6 个服务，P99 响应时间 800ms，大促时经常超时。业务方要求把下单响应降到 200ms 以内。
>
> **我的角色**：我是订单系统负责人，主导了整个异步化改造方案。
>
> **行动**：
> 1. 引入 RocketMQ 将下单链路从同步改为异步——订单创建后发消息通知下游，响应时间从 800ms 降到 120ms
> 2. 用 RocketMQ 事务消息保证订单和消息的一致性——半消息 + 本地事务 + 回查机制
> 3. 引入 Seata AT 模式处理订单和库存的分布式事务
> 4. Redis Lua 脚本做库存原子扣减防超卖
> 5. Sentinel 做限流熔断，大促时自动降级非核心链路
>
> **结果**：P99 从 800ms 降到 120ms（降低 85%），大促零超时，系统稳定支撑了双 11 的 50 万峰值 QPS。"

**好在哪里**：
- ✅ 有明确的业务背景和数据量级
- ✅ 有清晰的技术难点和解决方案
- ✅ 有量化的结果指标
- ✅ 有个人角色和贡献
- ✅ 有丰富的追问点（事务消息/Seata/Lua/限流）

### 1.3 项目故事的三个层次

```
第一层：做了什么（What）     → 功能描述
第二层：怎么做的（How）       → 技术方案
第三层：为什么这样做（Why）   → 架构决策与技术权衡
```

面试中，**第三层才是加分项**。能讲清楚"为什么选 A 不选 B"，才能证明你有架构思维。

| 层次 | 示例 | 面试官评价 |
|------|------|-----------|
| 只讲 What | "我用 Redis 做了缓存" | "只会用，不理解" |
| 讲到 How | "我用 Redis 的 ZSet 做排行榜，用 Lua 脚本保证原子性" | "用得不错" |
| 讲到 Why | "排行榜选 Redis ZSet 而非 MySQL ORDER BY，是因为 ZSet 的跳表结构 O(log N) 插入+排名，而 MySQL 每次查询需要全表排序 O(N log N)，在 10 万用户量级下性能差 100 倍" | "有深度，有架构思维" |

## 第二章 选材原则——什么项目值得讲

### 2.1 选材六大原则

#### 原则一：有技术深度

> 选的项目必须能挖出技术深度，而不是纯 CRUD。

**有深度的项目特征**：
- 涉及分布式/高并发/高可用等复杂场景
- 有技术难题需要解决（性能瓶颈/数据一致性/可用性等）
- 用了有一定门槛的技术（消息队列/分布式事务/缓存策略等）
- 有架构设计或重构经历

**没深度的项目特征**：
- 纯增删改查的后台管理系统
- 简单的接口对接和数据搬运
- 用框架默认配置，没有任何定制化
- 没有遇到任何技术挑战

| 判断标准 | 有深度 ✅ | 无深度 ❌ |
|---------|---------|---------|
| 缓存使用 | 缓存穿透/击穿/雪崩方案 + 分布式锁 | 简单 set/get 缓存 |
| 消息队列 | 事务消息 + 顺序消息 + 消费幂等 | 简单发消息 |
| 数据库 | 分库分表 + 读写分离 + 慢查询优化 | 简单 CRUD |
| 并发处理 | 锁/原子操作/线程池调优 | 无并发场景 |
| 架构设计 | 微服务拆分/网关设计/服务治理 | 单体 MVC |

#### 原则二：有量化结果

> 选的项目必须有可量化的成果，能证明你的工作产生了实际价值。

**量化维度**：

| 维度 | 示例 |
|------|------|
| 性能提升 | "P99 延迟从 800ms 降到 120ms" |
| 吞吐量提升 | "QPS 从 500 提升到 5000" |
| 成本降低 | "服务器从 20 台降到 5 台" |
| 效率提升 | "部署时间从 2 小时降到 10 分钟" |
| 故障减少 | "年故障从 20 次降到 2 次" |
| 业务增长 | "支持了双 11 百万 QPS" |
| 代码质量 | "单元测试覆盖率从 20% 提升到 80%" |

**没有量化结果的修复方法**：
- 回忆当时的监控数据/埋点数据
- 估算大致量级（"大约提升了 3~5 倍"）
- 从业务价值角度量化（"用户体验提升，转化率提升 X%"）

#### 原则三：有个人贡献

> 选的项目中，你的角色必须清晰，贡献必须明确。

**好的个人贡献描述**：

| 角色 | 描述方式 |
|------|---------|
| 项目负责人 | "我主导了整个方案设计和实施" |
| 核心开发 | "我负责了最核心的 XX 模块设计和开发" |
| 技术攻关 | "我解决了 XX 技术难题" |
| 架构师 | "我设计了整体技术架构" |

**避免的说法**：
- ❌ "我们团队做了..." → 你做了什么？
- ❌ "我参与了..." → 参与到什么程度？
- ❌ "我负责写代码..." → 太笼统

#### 原则四：真实性

> 选的项目必须是你亲身经历的，能经得起追问。

**真实性验证标准**：

```
□ 能画出系统架构图
□ 能说出核心表结构
□ 能解释每个技术选型的理由
□ 能描述遇到的问题和解决过程
□ 能回答"如果重新做你会怎么改"
□ 能说出线上出过什么问题、怎么处理的
```

**注意**：不要编造或夸大。面试官追问几个问题就能判断你是否真正做过。一旦被发现造假，直接淘汰。

**如果项目经历不够"亮眼"怎么办**：

| 情况 | 策略 |
|------|------|
| 项目体量小 | 重点讲技术方案和思考过程，而非数据量 |
| 只做了模块开发 | 深挖模块中的技术细节 |
| 项目简单 | 重点讲你对项目的思考和改进建议 |
| 没有分布式经验 | 从单体项目中挖掘并发/性能/设计模式的亮点 |

#### 原则五：时效性

> 优先选择近 2 年内的项目。太老的项目可能技术栈过时，面试官兴趣不大。

| 时效 | 建议 | 说明 |
|------|------|------|
| 近 1 年 | ⭐⭐⭐⭐⭐ 优先选 | 最新经验，最鲜活 |
| 1~2 年 | ⭐⭐⭐⭐ 可选 | 经验仍有参考价值 |
| 2~3 年 | ⭐⭐⭐ 谨慎选 | 技术可能过时 |
| 3 年以上 | ⭐☆ 不推荐 | 除非是特别有深度的项目 |

#### 原则六：匹配目标岗位

> 选的项目要匹配目标岗位的技术栈和业务领域。

**示例**：

| 目标岗位 | 推荐选材 | 不推荐选材 |
|---------|---------|-----------|
| 电商后端 | 电商交易/库存/营销系统 | 内部 OA 系统 |
| 金融后端 | 支付/清结算/风控系统 | 游戏后端 |
| 中间件开发 | 自研框架/SDK/组件 | 业务 CRUD 系统 |
| 大数据开发 | 数仓/实时计算/ETL | 纯后端 CRUD |
| 架构师 | 系统重构/架构演进 | 单模块开发 |

### 2.2 项目素材盘点表

列出你所有参与过的项目，用以下表格评估：

| 项目名称 | 时间 | 角色 | 技术栈 | 技术深度 | 量化结果 | 个人贡献 | 时效性 | 岗位匹配 | 综合 |
|---------|------|------|--------|---------|---------|---------|--------|---------|------|
| 项目A | 2024.06 | 负责人 | SpringCloud+Redis+RocketMQ | ⭐⭐⭐⭐⭐ | QPS 3000→5000 | 主导设计 | 近1年 | ✅ 匹配 | **优先选** |
| 项目B | 2023.08 | 核心开发 | SpringBoot+MySQL+Redis | ⭐⭐⭐⭐ | P99 降60% | 核心模块 | 1~2年 | ✅ 匹配 | **备选** |
| 项目C | 2022.03 | 开发 | SpringBoot+MySQL | ⭐⭐ | 无量化 | 模块开发 | 3年+ | ⚠️ 部分匹配 | **不推荐** |
| 项目D | 2023.12 | 负责人 | SpringCloud+Nacos+Sentinel | ⭐⭐⭐⭐ | 可用性99.99% | 主导架构 | 近1年 | ✅ 匹配 | **优先选** |

**选材策略**：
- 准备 **2~3 个核心项目**（优先选），每个项目准备 15~20 分钟的深度讲解
- 准备 **1~2 个备选项目**，在核心项目与岗位不完全匹配时补充
- 每个项目准备 **1~2 个技术亮点**，作为深入讲解的切入点

## 第三章 选材策略——如何匹配目标岗位

### 3.1 目标岗位画像分析

在选材之前，先分析目标岗位需要什么样的人：

**JD（Job Description）关键词提取**：

```
示例 JD：
"负责电商平台后端服务开发，要求：
  - 3 年以上 Java 开发经验
  - 熟悉 Spring Cloud 微服务架构
  - 熟悉 MySQL 调优、Redis 缓存设计
  - 有消息队列（Kafka/RocketMQ）使用经验
  - 有高并发系统设计经验
  - 了解分布式事务、分布式锁
  - 有电商/支付领域经验优先"
```

**提取出的关键词**：

| 类别 | 关键词 | 对应选材方向 |
|------|--------|------------|
| 技术栈 | Spring Cloud / MySQL / Redis / RocketMQ | 选用了这些技术的项目 |
| 能力要求 | 高并发 / 分布式事务 / 分布式锁 | 有这些场景的项目 |
| 业务领域 | 电商 / 支付 | 电商或支付相关项目 |
| 经验要求 | 3 年+ / 高并发经验 | 能体现这些经验的项目 |

### 3.2 项目与岗位匹配矩阵

| JD 关键词 | 项目A（电商交易） | 项目B（支付系统） | 项目C（内部OA） |
|---------|----------------|----------------|--------------|
| Spring Cloud | ✅ | ✅ | ❌ |
| MySQL 调优 | ✅ | ✅ | ⚠️ |
| Redis 缓存 | ✅ | ✅ | ❌ |
| RocketMQ | ✅ | ❌ | ❌ |
| 高并发 | ✅ | ✅ | ❌ |
| 分布式事务 | ✅ | ✅ | ❌ |
| 电商/支付 | ✅ | ✅ | ❌ |
| **匹配度** | **95%** | **90%** | **20%** |

→ 选项目A和项目B作为核心项目。

### 3.3 不同年限的选材策略

| 工作年限 | 选材策略 | 项目数量 | 重点 |
|---------|---------|---------|------|
| 1~3 年 | 选 1~2 个最有亮点的项目 | 1~2 个 | 技术深度 + 学习能力 |
| 3~5 年 | 选 2~3 个有技术深度的项目 | 2~3 个 | 技术深度 + 架构能力 + 业务理解 |
| 5~8 年 | 选 2~3 个有架构/重构经历的项目 | 2~3 个 | 架构设计 + 技术决策 + 团队影响力 |
| 8 年+ | 选 1~2 个有技术影响力的项目 | 1~2 个 | 技术战略 + 团队建设 + 技术文化 |

### 3.4 针对不同面试场景的选材

| 面试场景 | 选材策略 | 讲解重点 |
|---------|---------|---------|
| 一面（技术面） | 选技术深度最强的项目 | 技术方案 + 实现细节 |
| 二面（架构面） | 选有架构设计/重构的项目 | 架构决策 + 技术权衡 |
| 三面（交叉面） | 选有业务价值的项目 | 业务理解 + 团队协作 |
| HR 面 | 选有成长/挑战的项目 | 个人成长 + 职业规划 |
| 高管面 | 选有影响力的项目 | 技术视野 + 商业理解 |

### 3.5 不同公司类型的选材偏好

| 公司类型 | 偏好项目类型 | 考查重点 |
|---------|------------|---------|
| 大厂（阿里/字节/美团） | 高并发/大规模/分布式 | 技术深度 + 系统设计 |
| 中厂（有赞/叮咚/米哈游） | 完整项目经验 + 技术深度 | 技术方案 + 落地能力 |
| 创业公司 | 全栈能力 + 快速交付 | 技术广度 + 业务理解 |
| 外企（微软/亚马逊） | 系统设计 + 工程能力 | 架构思维 + 最佳实践 |
| 金融科技 | 强一致性/高可靠 | 事务/可靠性/合规 |

## 第四章 项目分类与讲法

### 4.1 六大项目类型

根据技术特征，项目可以分为六类，每类的讲法侧重点不同：

#### 类型一：高并发系统

**特征**：QPS 高（1000+）、需要应对流量峰值

**讲解重点**：

| 要点 | 说明 |
|------|------|
| 流量量级 | QPS / 日活 / 峰值流量 |
| 架构设计 | 多级缓存 / 异步化 / 削峰填谷 |
| 性能优化 | 压测 / 瓶颈分析 / 优化手段 |
| 稳定性保障 | 限流 / 熔断 / 降级 / 容灾 |
| 扩展能力 | 水平扩展 / 数据库分片 |

**技术关键词**：Redis 缓存 / 消息队列 / 限流熔断 / 读写分离 / 分库分表 / 异步化

**讲解框架**：
```
背景：什么业务？QPS 多少？峰值多少？
挑战：系统瓶颈在哪里？为什么要改造？
方案：怎么解决的？（缓存/异步/分片/限流）
结果：性能提升了多少？稳定性如何？
```

#### 类型二：高可用系统

**特征**：对系统可用性要求极高（99.99%+），不能宕机

**讲解重点**：

| 要点 | 说明 |
|------|------|
| 可用性目标 | SLA 等级 / RPO / RTO |
| 故障场景 | 可能的故障点 / 影响范围 |
| 容灾设计 | 多活 / 故障转移 / 灰度发布 |
| 监控告警 | 监控体系 / 告警策略 |
| 故障演练 | 混沌工程 / 容灾演练 |

**技术关键词**：主从切换 / 多活部署 / 灰度发布 / 监控告警 / 混沌工程 / 自动恢复

#### 类型三：分布式系统

**特征**：微服务架构、跨服务事务、数据一致性

**讲解重点**：

| 要点 | 说明 |
|------|------|
| 服务拆分 | 怎么拆的？拆分依据？ |
| 服务治理 | 注册发现 / 配置管理 / 网关 |
| 分布式事务 | 一致性方案 / Seata / 消息事务 |
| 数据一致性 | 缓存一致性 / 数据同步 |
| 链路追踪 | 全链路监控 / 问题定位 |

**技术关键词**：Spring Cloud / Dubbo / Seata / 分布式锁 / 链路追踪 / 服务治理

#### 类型四：性能优化项目

**特征**：针对已有系统的性能瓶颈进行优化

**讲解重点**：

| 要点 | 说明 |
|------|------|
| 性能问题 | 什么问题？如何发现的？ |
| 分析过程 | 怎么定位的？用了什么工具？ |
| 优化方案 | 怎么解决的？为什么选这个方案？ |
| 量化结果 | 优化前后的数据对比 |
| 持续优化 | 后续还做了什么？ |

## 第五章 大纲框架——STAR/SPARK

### 5.1 STAR 框架

最经典的项目讲述框架，适用于大多数面试场景。

```
S - Situation（情境）
    业务背景 + 团队规模 + 技术栈

T - Task（任务）
    你的角色 + 面临的挑战 + 目标

A - Action（行动）
    你做了什么 + 技术方案 + 实现细节

R - Result（结果）
    量化成果 + 业务价值 + 个人成长
```

**STAR 框架详细模板**：

#### S - Situation（情境）

```
我们的系统是________，服务于________业务。
团队规模________人，技术栈是________。
日均________，峰值________。
系统当时的状态是________（正常运行的/存在问题的/正在重构的）。
```

**示例**：
> "我们的系统是一个电商平台的订单中心，服务于 B2C 交易业务。团队 8 人，技术栈是 Spring Cloud + MySQL + Redis + RocketMQ。日均订单 10 万单，大促峰值 QPS 3000。系统当时是单体架构，下单链路同步调用 6 个下游服务，P99 响应 800ms。"

#### T - Task（任务）

```
我的角色是________。
面临的挑战是________。
目标是将________从________优化到________。
时间节点是________。
```

**示例**：
> "我是订单系统的负责人。面临的挑战是：大促时下单经常超时，业务方要求把 P99 从 800ms 降到 200ms 以内，同时保证数据一致性。时间节点是双 11 前 2 个月内完成改造。"

#### A - Action（行动）

这是最重要的部分，需要按层次展开：

```
第一层：方案总览
    整体思路是________。

第二层：关键技术方案
    1. ________（做了什么 + 为什么这样做 + 怎么做的）
    2. ________
    3. ________

第三层：技术细节（面试官追问时展开）
    - 选型理由：为什么选 A 不选 B？
    - 实现细节：核心代码逻辑 / 数据结构 / 算法
    - 踩坑经验：遇到了什么问题？怎么解决的？
```

**示例**：
> "整体思路是将同步调用改为异步化，同时保证数据一致性。
>
> 第一，引入 RocketMQ 将下单链路异步化。订单创建后发消息通知库存、营销、物流等下游服务，响应时间从 800ms 降到 120ms。之所以选 RocketMQ 而非 Kafka，是因为需要事务消息保证订单和消息的一致性。
>
> 第二，用 RocketMQ 事务消息保证一致性。先发半消息 → 执行本地事务（创建订单）→ 根据本地事务结果提交或回滚半消息。如果超时未确认，RocketMQ 会回查本地事务状态。
>
> 第三，Redis Lua 脚本做库存原子扣减。用 DECR 原子扣减 + Lua 脚本检查库存 + 标记用户防重复购买。之所以用 Lua 而非分布式锁，是因为 Lua 脚本在 Redis 中原子执行，性能远优于分布式锁。
>
> 第四，Sentinel 限流熔断。大促时自动限流非核心接口，降级营销推荐等非核心链路。"

#### R - Result（结果）

```
量化结果：
    - 性能：________从________优化到________（提升________%）
    - 稳定性：________
    - 成本：________

业务价值：
    - ________

个人收获：
    - ________
```

**示例**：
> "P99 从 800ms 降到 120ms，降低 85%。大促零超时，稳定支撑了双 11 的 50 万峰值 QPS。 RocketMQ 事务消息保证了订单和消息的一致性，上线后没有发生过数据不一致的故障。
>
> 个人收获：深入理解了分布式事务的各种方案和适用场景，也积累了高并发系统设计的经验。"

### 5.2 SPARK 框架

STAR 的进阶版，更适合有架构决策的项目。

```
S - Situation（情境）
    业务背景 + 系统现状

P - Problem（问题）
    核心痛点 + 技术挑战

A - Approach（方案）
    方案设计 + 技术选型 + 权衡分析

R - Result（结果）
    量化成果 + 业务价值

K - Knowledge（收获）
    经验总结 + 反思改进
```

**SPARK vs STAR 的区别**：

| 维度 | STAR | SPARK |
|------|------|-------|
| 问题分析 | Task 中简单描述 | Problem 单独深入分析 |
| 方案设计 | Action 偏实现细节 | Approach 包含技术选型 + 权衡 |
| 经验反思 | 无 | Knowledge 单独总结 |
| 适用场景 | 常规项目 | 架构设计/重构项目 |
| 深度 | 中 | 深 |

## 第七章 常见项目类型大纲示例

### 7.1 示例一：电商交易系统（高并发 + 分布式事务）

```markdown
## 项目：电商平台交易系统

### 一、项目概览
- 业务领域：B2C 电商平台
- 项目时间：2023.06 ~ 2024.06
- 团队规模：12 人（后端 8 人）
- 我的角色：订单系统负责人
- 技术栈：Spring Cloud Alibaba / MySQL / Redis / RocketMQ / Seata / Sentinel

### 二、业务背景
- 日均订单 10 万单，大促峰值 QPS 3000
- 下单链路涉及 6 个下游服务：库存/营销/物流/积分/通知/风控
- 原系统单体架构，同步调用，P99 响应 800ms

### 三、技术挑战
1. 性能瓶颈：同步调用链路太长，大促时超时严重
2. 数据一致性：异步化后如何保证订单与下游数据一致
3. 防超卖：高并发下库存扣减的原子性
4. 流量洪峰：大促瞬时流量是平时的 50 倍

### 四、技术方案

#### 方案一：异步化改造（核心）
- 目标：P99 从 800ms 降到 200ms
- 思路：将同步调用改为 MQ 异步通知
- 选型：RocketMQ（而非 Kafka），因为需要事务消息
- 实现：
  - 订单创建后发 RocketMQ 消息通知下游
  - 用事务消息保证"订单创建 + 消息发送"的原子性
  - 半消息 → 本地事务（创建订单）→ 提交/回滚
  - 超时回查：RocketMQ 回查本地事务状态
- 结果：P99 从 800ms 降到 120ms

#### 方案二：防超卖
- 目标：高并发下库存不超卖
- 方案：Redis Lua 脚本原子扣减
- 实现：
  - 库存预热到 Redis
  - Lua 脚本：检查库存 + DECR + 标记用户（原子操作）
  - MySQL 兜底：WHERE stock > 0 乐观锁
- 结果：零超卖

#### 方案三：流量管控
- 目标：应对大促 50 倍流量洪峰
- 方案：Sentinel 限流 + 降级 + 熔断
- 实现：
  - 网关层：QPS 限流
  - 服务层：慢调用熔断 + 异常比例熔断
  - 降级策略：非核心接口返回默认值
- 结果：大促零超时

### 五、量化结果
| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| P99 延迟 | 800ms | 120ms | 85%↓ |
| 峰值 QPS | 500 | 3000 | 6x↑ |
| 超时率 | 15% | 0% | 100%↓ |
| 系统可用性 | 99.5% | 99.99% | - |

### 六、踩坑经验
1. RocketMQ 事务消息回查超时
   - 现象：部分订单状态长时间为"处理中"
   - 原因：回查接口超时，RocketMQ 默认 60s 后放弃
   - 解决：增加回查接口超时配置 + 对账补偿任务

2. Redis 主从同步延迟导致超卖
   - 现象：主从切换瞬间出现 2 笔超卖
   - 原因：主从同步是异步的，切换瞬间数据不一致
   - 解决：MySQL 乐观锁兜底 + 双写 Redis 主从

### 七、反思与收获
- 做得好：异步化方案设计合理，事务消息保证了一致性
- 可改进：应该提前做全链路压测，而非上线后发现问题
- 如果重来：会考虑用 Seata TCC 模式替代事务消息，减少对 MQ 的强依赖
```

### 7.2 示例二：微服务架构演进（单体→微服务）

```markdown
## 项目：系统微服务架构演进

### 一、项目概览
- 业务领域：SaaS 企业服务平台
- 项目时间：2023.01 ~ 2023.12
- 团队规模：15 人
- 我的角色：架构组成员，主导服务拆分
- 技术栈：Spring Cloud Alibaba / Nacos / Gateway / Sentinel / SkyWalking

### 二、业务背景
- 原系统：PHP 单体应用，运行 5 年，代码 50 万行
- 痛点：发布耦合（改一个 Bug 全量发布）、性能瓶颈（PHP-FPM 连接数限制）
- 目标：迁移到 Java 微服务架构

### 三、技术挑战
1. 服务拆分：怎么拆？拆多细？
2. 数据迁移：PHP 和 Java 双运行期间数据怎么同步？
3. 平滑迁移：怎么保证迁移过程中业务不中断？
4. 团队转型：PHP 开发转 Java，学习成本

### 四、技术方案

#### 方案一：DDD 领域驱动拆分
- 思路：按业务领域拆分，而非按技术层拆分
- 拆分结果：用户服务/订单服务/商品服务/支付服务/通知服务
- 拆分依据：限界上下文 + 团队组织结构（康威定律）
- 关键决策：先拆用户和商品（变更最频繁），后拆支付（最复杂）

#### 方案二：双写迁移方案
- 阶段一：PHP 继续服务，Java 新服务同步开发
- 阶段二：PHP 写 MySQL → Canal → Java 服务读（数据双读）
- 阶段三：Java 服务写 → Canal → PHP 服务读（灰度切写流量）
- 阶段四：全量切到 Java，PHP 下线
- 关键点：每一步都可回滚

#### 方案三：微服务基础设施
- 注册中心+配置中心：Nacos
- API 网关：Spring Cloud Gateway
- 限流熔断：Sentinel
- 链路追踪：SkyWalking（字节码增强，无侵入）
- 分布式事务：Seata AT 模式

### 五、量化结果
| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| 发布频率 | 每月 1 次 | 每天 3~5 次 | 100x↑ |
| 部署时间 | 2 小时 | 10 分钟 | 12x↓ |
| 系统可用性 | 99.5% | 99.95% | - |
| P99 延迟 | 500ms | 100ms | 80%↓ |

### 六、踩坑经验
1. 分布式事务性能问题
   - 现象：Seata AT 模式下部分接口响应变慢
   - 原因：全局锁竞争 + undo_log 表成为瓶颈
   - 解决：将强一致场景用 AT 模式，其他场景用消息事务

2. 服务拆分过细
   - 现象：拆了 20 个微服务，运维成本暴增
   - 原因：拆得太细，一个简单功能跨 5 个服务调用
   - 解决：合并了 6 个小服务，最终 14 个服务
```

### 7.3 示例三：性能优化专项（JVM + 数据库）

```markdown
## 项目：核心系统性能优化专项

### 一、项目概览
- 业务领域：金融支付系统
- 项目时间：2024.03 ~ 2024.06
- 我的角色：性能优化负责人
- 技术栈：Spring Boot / MySQL / Redis / JVM

### 二、业务背景
- 系统运行 2 年，随着业务增长性能持续恶化
- P99 延迟从 200ms 恶化到 800ms
- 每周 2~3 次 Full GC，每次停顿 3~5 秒
- 慢查询告警每天 10+ 次

### 三、技术挑战
1. JVM 频繁 Full GC：内存泄漏？
2. 数据库慢查询：索引失效？SQL 不合理？
3. 接口响应慢：是 GC 还是 DB 还是网络？
4. 定位困难：问题偶发，难以复现

### 四、技术方案

#### 方案一：JVM 调优
- 排查过程：
  1. jstat 观察 GC 频率和各区域大小
  2. jmap dump 堆内存 → MAT 分析
  3. 定位：ThreadLocal 未清理导致内存泄漏
  4. Arthas 确认：watch 命令观察 ThreadLocal 使用
- 解决方案：
  - 修复 ThreadLocal 泄漏（使用后 remove）
  - 调整 JVM 参数：-Xmx 4G → 8G，G1 收集器
  - -XX:MaxGCPauseMillis=200
- 结果：Full GC 从每周 2~3 次降到每月 0~1 次

#### 方案二：数据库优化
- 排查过程：
  1. 开启慢查询日志，收集 TOP 10 慢 SQL
  2. EXPLAIN 分析执行计划
  3. 定位问题：type=ALL（全表扫描）、Using filesort
- 解决方案：
  - 重建索引：覆盖索引消除回表
  - SQL 重写：子查询改 JOIN
  - 分页优化：深分页用游标方案
- 结果：慢查询从每天 10+ 降到 0~1 次

#### 方案三：接口性能优化
- 排查过程：
  1. SkyWalking 链路追踪定位耗时分布
  2. 发现 60% 耗时在 Redis（大 Key）
  3. Arthas trace 命令定位具体方法
- 解决方案：
  - 拆分大 Key（Hash 拆成多个小 Hash）
  - 批量操作改 Pipeline
  - 本地缓存（Caffeine）减少 Redis 访问
- 结果：P99 从 800ms 降到 150ms

### 五、量化结果
| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| P99 延迟 | 800ms | 150ms | 81%↓ |
| Full GC | 每周 2~3 次 | 每月 0~1 次 | 90%↓ |
| 慢查询 | 每天 10+ | 每天 0~1 | 90%↓ |
| CPU 使用率 | 85% | 40% | 53%↓ |

### 六、踩坑经验
1. ThreadLocal 泄漏定位花了 2 天
   - 教训：应该第一时间用 jmap + MAT 分析
2. 大 Key 问题
   - 教训：设计阶段就应该限制 Key 大小
```

## 第八章 追问防线设计

### 8.1 为什么要设计追问防线

面试官听完你的项目介绍后，一定会追问。追问的目的是验证你是否真正做过、是否真正理解。

```
项目讲解（你主动讲）→ 追问环节（面试官主导）→ 深度评估
```

**追问防线的核心思路**：在讲解时埋下"钩子"，引导面试官追问你准备好的亮点。

### 8.2 钩子设计

**什么是钩子**：在讲解中故意提到一个技术点，但不展开，等面试官追问。

```
讲解："我用 Redis Lua 脚本做库存扣减..."
          ↑
         钩子：面试官可能追问"Lua 脚本怎么写的？"

准备好的回答：
"Lua 脚本逻辑是：
 1. 检查库存是否足够
 2. 检查用户是否已购买
 3. 扣减库存
 4. 标记用户已购买
 这四步在一个 Lua 脚本中原子执行，避免了分布式锁的性能开销..."
```

**钩子设计原则**：
- 钩子必须是你**有准备**的技术点
- 钩子要有足够的**技术深度**可挖
- 不要埋太多钩子（2~3 个足够）
- 钩子之间要有**层次**（浅层 → 深层）

### 8.3 追问防线分层

```
第一层防线：方案概述（讲解时已覆盖）
    ↓ 面试官追问
第二层防线：技术选型理由（为什么选 A 不选 B）
    ↓ 面试官继续追问
第三层防线：实现细节（核心代码/数据结构/算法）
    ↓ 面试官深入追问
第四层防线：踩坑经验（遇到的问题和解决方案）
    ↓ 面试官极限追问
第五层防线：延伸思考（如果重新做/更大规模怎么办）
```

### 8.4 追问防线示例

以"RocketMQ 事务消息"为例：

| 防线层级 | 可能的追问 | 准备的回答 |
|---------|-----------|-----------|
| 第一层 | "事务消息是什么？" | 半消息 + 本地事务 + 回查机制，保证消息和本地事务的原子性 |
| 第二层 | "为什么不用 Kafka + 本地消息表？" | Kafka 无原生事务消息，本地消息表需要额外的定时任务扫描，增加系统复杂度和延迟。RocketMQ 原生支持，回查机制可靠性更高 |
| 第三层 | "回查机制怎么实现的？" | RocketMQ Broker 存储半消息 → 超时（60s）未确认 → 回查 Producer 的 `checkLocalTransaction` 方法 → 根据返回值提交或回滚 |
| 第四层 | "遇到过什么问题？" | 回查接口超时导致部分订单状态卡住。原因是回查时查询 DB 太慢，加了索引后解决。还加了兜底对账任务 |
| 第五层 | "如果 QPS 再翻 10 倍怎么办？" | 事务消息有性能瓶颈（半消息存储 + 回查），更高 QPS 可以考虑用本地消息表 + 异步对账方案，牺牲一些实时性换吞吐量 |

## 第九章 常见误区与反模式

### 9.1 误区一：流水账式讲解

**症状**：按时间顺序讲开发过程，没有重点。

```
❌ "我先做了需求分析，然后设计了数据库表，
    然后写了 Controller、Service、Mapper，
    最后联调测试上线。"
```

**问题**：没有技术亮点，面试官无法追问。

**改进**：用 STAR/SPARK 框架，突出挑战和方案，而非开发流程。

### 9.2 误区二：只讲 What 不讲 Why

**症状**：只说用了什么技术，不说为什么选这个技术。

```
❌ "我们用了 Redis 做缓存，用了 RocketMQ 做消息队列。"

✅ "我们选 RocketMQ 而非 Kafka，是因为需要事务消息保证
    订单和消息的一致性。Kafka 没有原生事务消息，
    需要自建本地消息表方案，增加系统复杂度。"
```

### 9.3 误区三：夸大个人贡献

**症状**：把团队的成果说成自己的，或者说"我设计了架构"但实际上只是执行者。

**问题**：面试官追问架构设计细节时露馅。

**改进**：诚实描述个人角色。"我负责了 XX 模块的设计和开发"比"我主导了整个系统架构"更可信。

### 9.4 误区四：没有量化数据

**症状**：只说"性能提升了""系统稳定了"，没有具体数据。

```
❌ "优化后系统性能提升了很多，运行也很稳定。"

✅ "P99 从 800ms 降到 120ms，降低了 85%。
    大促零超时，系统可用性从 99.5% 提升到 99.99%。"
```

### 9.5 误区五：技术细节太多太少

**症状**：要么讲得太笼统没有细节，要么讲得太细像念代码。

```
❌ 太少："我用了 Redis 缓存。"（然后呢？）

❌ 太多："我先写了 RedisTemplate 的配置类，
    然后写了 @Cacheable 注解，然后..."
    （不需要讲代码细节）

✅ 恰当："我用 Redis 做了多级缓存——Caffeine 做本地缓存
    挡第一层，Redis 做分布式缓存挡第二层。
    缓存一致性用 Cache-Aside 模式：先更新 DB，再删除缓存。
    对于强一致场景，用延迟双删策略。"
```

### 9.6 误区六：忽视业务价值

**症状**：只讲技术方案，不讲业务价值。

```
❌ "我做了分库分表，用了 ShardingSphere。"

✅ "业务量增长到单表 5000 万行，查询性能恶化。
    我做了分库分表，查询性能提升了 5 倍，
    支撑了业务从日活 10 万到 50 万的增长。"
```

### 9.7 误区七：不会说"不知道"

**症状**：被追问到不熟悉的知识点时，强行编造答案。

**问题**：面试官一听就知道你在编，比说"不知道"更减分。

**改进**：

```
"这个我确实不太了解细节。但我的理解是...（说出你的推测）。
 如果要深入了解，我会从...方向去研究。"
```

这样既诚实，又展示了思考能力和学习方向。

### 9.8 误区八：项目太多没有重点

**症状**：面试官问"讲一个你的项目"，你讲了 5 个项目每个 2 分钟。

**问题**：每个都浅尝辄止，没有深度。

**改进**：选 1~2 个重点项目，每个讲 15~20 分钟，讲深讲透。

### 9.9 误区九：不会引导面试官

**症状**：被动等面试官提问，不主动引导到自己的优势领域。

**改进**：在讲解中埋钩子，引导面试官追问你准备好的亮点。

```
"在这个过程中，我深入研究了 RocketMQ 事务消息的实现原理..."
                                       ↑
                              钩子：引导追问事务消息
```

### 9.10 误区十：准备不充分

**症状**：讲项目时卡壳、数据记不清、技术细节说不清楚。

**改进**：面试前做充分准备。

**准备清单**：

```
□ 能画出系统架构图（白板画）
□ 能说出核心数据量级（QPS/数据量/用户量）
□ 能解释每个技术选型的理由
□ 能说出 2~3 个踩坑经历
□ 能回答"如果重新做你会怎么改"
□ 能说出 1~2 个量化结果
□ 准备了 2~3 个追问防线
□ 对每个技术点准备了 What → Why → How 三层回答
```

## 第十章 面试高频题

### Q1：请介绍一下你最得意的项目

**回答策略**：

> 用黄金三段式快速切入，然后等面试官追问展开。

**示例回答**：

> "我最得意的项目是电商平台交易系统的异步化改造。
>
> **背景**：日订单 10 万，大促峰值 QPS 3000，原系统同步调用 6 个下游服务，P99 800ms，大促经常超时。
>
> **方案**：我主导了异步化改造——用 RocketMQ 事务消息将同步调用改为异步，P99 降到 120ms。同时用 Redis Lua 脚本做库存原子扣减防超卖，Sentinel 做限流熔断。
>
> **结果**：P99 降 85%，大促零超时，支撑了双 11 的 50 万峰值 QPS。
>
> 这个项目中我深入研究了 RocketMQ 事务消息和分布式事务方案，可以详细展开讲。"

### Q2：你在这个项目中遇到最大的技术挑战是什么？

**回答策略**：

> 选一个有深度的技术挑战，按"问题 → 分析 → 方案 → 结果"展开。

**示例回答**：

> "最大的挑战是保证异步化后的数据一致性。
>
> 原来的同步调用中，如果库存扣减失败可以直接回滚订单。但改成异步后，订单先创建成功，再异步通知库存扣减，如果库存扣减失败就出现数据不一致。
>
> 我评估了三种方案：
> 1. **RocketMQ 事务消息**：半消息 + 本地事务 + 回查。可靠性高，但有回查延迟。
> 2. **本地消息表 + 定时任务**：简单可靠，但定时任务有延迟，且需要额外的表。
> 3. **Seata TCC**：强一致，但侵入性强，需要写 Try/Confirm/Cancel 三个方法。
>
> 最终选了事务消息方案，因为：可靠性满足要求、侵入性低、RocketMQ 原生支持。同时对超时未确认的订单加了兜底对账任务，每天凌晨跑一次确保数据一致。
>
> 上线后没有发生过数据不一致的故障。"

### Q3：如果让你重新做这个项目，你会怎么改进？

**回答策略**：

> 展示反思能力和持续改进意识。不要说"没有需要改进的"。

**示例回答**：

> "有几个方面我会改进：
>
> 1. **全链路压测**：当时是上线后才发现一些性能问题，如果重来我会提前做全链路压测，在上线前发现瓶颈。
>
> 2. **分布式事务方案**：当时用事务消息，对 MQ 有强依赖。如果重来我会考虑 Seata TCC 模式，虽然侵入性强但一致性更强，且不依赖 MQ。对于非核心场景，用本地消息表 + 异步对账就够了。
>
> 3. **可观测性**：当时监控不够完善，排查问题效率低。如果重来我会从一开始就接入 SkyWalking 链路追踪 + Prometheus 指标监控，建立完善的告警体系。
>
> 4. **库存方案**：当时用 Redis Lua + MySQL 乐观锁。如果数据量更大，会考虑用 Redis Cluster + 分片库存方案，把库存拆到多个 Key 降低热点。"

### Q4：你们系统的 QPS 是多少？怎么扛住的？

**回答策略**：

> 先说量级，再说架构设计，最后说优化手段。

**示例回答**：

> "大促峰值 QPS 3000，日常 QPS 200~500。
>
> 扛住高并发主要靠分层设计：
> 1. **CDN + Nginx 层**：静态资源走 CDN，Nginx 做限流（limit_req）挡住异常流量
> 2. **网关层**：Spring Cloud Gateway 做统一限流（Sentinel）和鉴权
> 3. **应用层**：Redis 缓存挡 95% 的读请求，RocketMQ 异步化降低写链路响应时间
> 4. **数据层**：MySQL 主从读写分离 + 分库分表
>
> 关键优化：
> - 缓存：Caffeine 本地缓存 + Redis 分布式缓存，多级缓存减少 Redis 访问
> - 异步：非核心链路全异步化，RocketMQ 削峰填谷
> - 限流：Sentinel 三层限流（网关/接口/资源），大促自动降级非核心功能
> - 库存：Redis Lua 原子扣减，单 Redis 实例扛 3 万 QPS 没问题"

### Q7：项目中用到了哪些设计模式？

**回答策略**：

> 结合实际场景讲设计模式，不要只背概念。

**示例回答**：

> "几个典型的：
>
> 1. **策略模式**：限流策略——根据接口重要性选择不同策略。普通接口用单机限流，核心接口用分布式限流，大促接口用多级限流。用 Spring 的 @Qualifier + Map 注入策略实现。
>
> 2. **模板方法**：下单流程——抽象父类定义流程骨架（校验 → 创建订单 → 扣库存 → 发消息），子类实现具体步骤。普通下单、秒杀下单、团购下单共用同一套骨架。
>
> 3. **观察者模式**：Spring ApplicationEvent——订单创建后发布 OrderCreatedEvent，库存/营销/物流服务监听处理。解耦了订单和下游服务。
>
> 4. **工厂模式**：Spring FactoryBean 创建支付渠道——支付宝/微信/银联不同支付方式，通过工厂统一创建。
>
> 5. **责任链模式**：风控校验——用户风控 → 设备风控 → IP 风控 → 行为风控，按顺序校验，任一环节不通过即拦截。"

### Q8：项目上线后出过什么线上故障？怎么处理的？

**回答策略**：

> 讲一个真实的故障案例，展示问题定位和解决能力。

**示例回答**：

> "有一次大促期间出现了接口超时告警，P99 从 100ms 飙到 2000ms。
>
> **定位过程**：
> 1. 先看 Grafana 监控，发现是订单创建接口慢
> 2. 看 SkyWalking 链路追踪，发现 60% 耗时在 Redis
> 3. 用 Redis slowlog 发现有个 ZADD 命令耗时 500ms
> 4. 定位到是某个排行榜 ZSet 元素过多（100 万+），变成了大 Key
>
> **根因**：排行榜 ZSet 没有做截断，数据持续增长导致大 Key。
>
> **紧急处理**：手动删除大 Key（UNLINK 异步删除），恢复服务
>
> **长期修复**：
> 1. ZSet 只保留 TOP 1000，定时清理
> 2. 大 Key 告警：Redis Exporter + Prometheus 配置大 Key 告警
> 3. 代码层面加 ZSet 大小限制
>
> **复盘**：
> - 教训：设计阶段就应该考虑数据增长边界
> - 改进：增加了 Redis 大 Key 巡检任务，每天扫描告警"

### Q9：你怎么评估技术方案的好坏？

**回答策略**：

> 从多维度展示评估能力。

**示例回答**：

> "我会从五个维度评估：
>
> 1. **是否解决问题**：方案是否真正解决了核心问题，而非绕过问题？
> 2. **复杂度**：方案引入的复杂度是否与问题匹配？不要用大炮打蚊子。
> 3. **可维护性**：方案是否容易理解和维护？是否需要额外的运维成本？
> 4. **可扩展性**：方案能否应对未来的业务增长？
> 5. **风险**：方案有什么风险？有没有降级/回滚方案？
>
> 评估方法：
> - 对比 2~3 个候选方案，列优缺点
> - 做 POC 验证关键假设
> - 请团队评审，收集不同意见
> - 考虑迁移成本和运维成本"

### Q10：你的项目和其他公司的类似系统相比，有什么优势和不足？

**回答策略**：

> 展示技术视野和自我认知能力。

**示例回答**：

> "和阿里、京东的电商交易系统相比：
>
> **优势**：
> - 架构设计思路类似（异步化/缓存/限流），说明我们的方向是对的
> - 我们的方案在中等规模（QPS 3000）下性价比高，没有过度设计
>
> **不足**：
> - **异地多活**：我们只做了同城双活，大厂做了异地多活（单元化），容灾能力更强
> - **全链路压测**：我们只做了接口级压测，大厂有全链路压测平台（影子库+流量标记）
> - **容量规划**：我们靠经验估算，大厂有自动化的容量评估和弹性伸缩
> - **稳定性**：我们的 SLA 是 99.99%，大厂是 99.999%，差距在一个数量级
>
> 这些差距主要源于规模和投入。如果是更大规模的系统，我会参考大厂的方案做异地多活和全链路压测。"

## 附录：项目准备 Checklist

### A. 选材检查

```
□ 列出了所有候选项目并评分
□ 选了 2~3 个核心项目
□ 每个项目评分 ≥ 32 分
□ 项目覆盖不同技术维度（不重复）
□ 项目匹配目标岗位
□ 每个项目有 1~2 个技术亮点
```

### B. 大纲检查

```
□ 每个项目用了 STAR/SPARK 框架
□ 背景清晰（业务+规模+痛点）
□ 技术方案有 What + Why + How 三层
□ 有 2~3 个量化结果
□ 有 1~2 个踩坑经验
□ 有反思和改进建议
```

### C. 追问防线检查

```
□ 每个项目设计了 2~3 个钩子
□ 每个钩子准备了 5 层追问防线
□ 能画出系统架构图
□ 能解释每个技术选型理由
□ 能回答"如果重新做"
□ 对不熟悉的问题准备了应对策略
```

### D. 面试演练检查

```
□ 5 分钟版本（快速介绍）
□ 15 分钟版本（标准介绍）
□ 30 分钟版本（深度展开）
□ 能在白板上画架构图
□ 能在白板上写核心代码片段
□ 模拟面试练习过
□ 录音回放检查表达流畅度
```

---

> **总结**：项目故事是面试中最核心的环节。好的项目故事 = 精心选材 + 结构化大纲 + 分层追问防线 + 充分演练。选材要选有技术深度、有量化结果、有个人贡献、匹配岗位的项目。大纲用 STAR/SPARK 框架，讲清楚 What → How → Why 三个层次。追问防线要设计钩子，引导面试官追问你的优势领域。最后，充分演练——把 5 分钟、15 分钟、30 分钟版本都练熟，面试时才能从容应对。
>
> 记住：**面试官不是在考你背了多少八股，而是在验证你是否真正解决过问题。项目故事就是你最好的证明。**
