## 1 单例模式（Singleton）

### 1.1 一句话定义

> **确保一个类只有一个实例，并提供全局访问点。**

### 1.2 核心原理

```
实现要点：
  1. 私有构造器 → 外部不能 new
  2. 类内部持有唯一实例 → private static
  3. 公开静态获取方法 → getInstance()
  4. 防止反射/序列化破坏单例

三种实现路线：
  饿汉式 → 类加载时创建 → 简单但可能浪费资源
  懒汉式 → 首次使用时创建 → 需处理并发安全
  枚举式 → 天然防反射/序列化 → 最佳实践
```

### 1.3 手写代码（面试必写）

#### ① 饿汉式（简单但不够灵活）

```java
public class EagerSingleton {
    // 类加载时就创建 → 线程安全（JVM保证类加载线程安全）
    private static final EagerSingleton INSTANCE = new EagerSingleton();
    
    private EagerSingleton() {} // 私有构造
    
    public static EagerSingleton getInstance() {
        return INSTANCE;
    }
}
// 缺点：不管用不用都创建 → 如果初始化耗资源则浪费
```

#### ② 懒汉式 — DCL 双重检查锁（面试最常考）

```java
public class DCLSingleton {
    // volatile 防止指令重排序！
    // new 对象 = 3 步：①分配内存 ②初始化 ③赋值引用
    // 不加 volatile 可能 ①③② → 其他线程拿到未初始化的对象
    private volatile static DCLSingleton INSTANCE;
    
    private DCLSingleton() {}
    
    public static DCLSingleton getInstance() {
        // 第一重检查：避免不必要的同步
        if (INSTANCE == null) {
            synchronized (DCLSingleton.class) {
                // 第二重检查：防止多个线程同时通过第一重检查后重复创建
                if (INSTANCE == null) {
                    INSTANCE = new DCLSingleton(); // volatile 保证此处不重排序
                }
            }
        }
        return INSTANCE;
    }
}
```

> **面试追问**："为什么 volatile？不加会怎样？"
> - `new DCLSingleton()` 在字节码层面分三步：分配内存(ref) → 调用构造初始化 → 赋值给 INSTANCE
> - JVM 可能重排序为 分配 → 赋值 → 初始化（②③颠倒）
> - 线程 A 执行到赋值但未初始化 → 线程 B 第一重检查 INSTANCE != null → 返回半成品对象 → **崩溃**
> - volatile 写操作前插入 StoreStore 屏障 → 禁止 ②③ 重排序 → 安全

#### ③ 静态内部类（懒加载+线程安全，推荐）

```java
public class InnerClassSingleton {
    private InnerClassSingleton() {}
    
    // 静态内部类 → 外部类加载时不会加载内部类 → 懒加载
    // 内部类加载时 JVM 保证线程安全 → 天然 DCL 效果
    private static class Holder {
        static final InnerClassSingleton INSTANCE = new InnerClassSingleton();
    }
    
    public static InnerClassSingleton getInstance() {
        return Holder.INSTANCE; // 触发 Holder 加载 → 创建实例
    }
}
// 优点：懒加载 + 线程安全 + 无锁开销
// 缺点：无法防止反射破坏
```

#### ④ 枚举单例（最佳实践，防反射+防序列化）

```java
public enum EnumSingleton {
    INSTANCE;
    
    public void doSomething() {
        System.out.println("singleton method");
    }
}

// 使用：EnumSingleton.INSTANCE.doSomething();
```

> **为什么枚举防反射？**
> - 反射 `Constructor.newInstance()` 源码中有判断：`if (clazz == Enum.class) throw IllegalArgumentException("Cannot reflectively create enum objects")`
> - 枚举类的构造器在 JVM 层面被标记为不可反射调用
> 
> **为什么枚举防序列化？**
> - `ObjectInputStream.readObject()` 对枚举有特殊处理：每次反序列化都返回已有的枚举常量引用
> - 不会创建新对象 → 天然防序列化破坏

#### 防止反射破坏单例（非枚举方案）

```java
public class AntiReflectSingleton {
    private static boolean initialized = false;
    private volatile static AntiReflectSingleton INSTANCE;
    
    private AntiReflectSingleton() {
        // 反射防护：构造器内检查
        if (!initialized) {
            initialized = true;
        } else {
            throw new RuntimeException("单例不允许反射创建");
        }
    }
    
    public static AntiReflectSingleton getInstance() {
        if (INSTANCE == null) {
            synchronized (AntiReflectSingleton.class) {
                if (INSTANCE == null) {
                    INSTANCE = new AntiReflectSingleton();
                }
            }
        }
        return INSTANCE;
    }
}
// 注意：initialized 也可能被反射修改 → 不完美 → 枚举才是终极方案
```

### 1.4 项目映射

```
Spring 中的单例：
  ┌──────────────────────────────────────────────────────┐
  │ Spring Bean 默认 scope = singleton                    │
  │                                                       │
  │ 实现方式：ConcurrentHashMap + 三级缓存                │
  │                                                       │
  │ // DefaultSingletonBeanRegistry                       │
  │ private final Map<String, Object> singletonObjects    │
  │     = new ConcurrentHashMap<>(256); // 一级缓存       │
  │                                                       │
  │ // 创建流程：                                         │
  │ getBean(name) → singletonObjects.get(name)            │
  │   → 有？直接返回                                      │
  │   → 无？earlySingletonObjects → singletonFactories    │
  │   → 三级缓存解决循环依赖后 → 放入 singletonObjects     │
  │                                                       │
  │ Spring 单例 ≠ JVM 单例：                              │
  │   Spring 单例是容器级别的（一个 ApplicationContext    │
  │   中一个 BeanName 对应一个实例）                       │
  │   JVM 单例是类加载器级别的（一个 ClassLoader 一个实例） │
  │   → 两个 ApplicationContext → 同一个类有2个实例       │
  └──────────────────────────────────────────────────────┘

JDK 中的单例：
  Runtime.getRuntime() → 饿汉式单例
    private static Runtime currentRuntime = new Runtime();
  
  IntegerCache（-128~127）→ 享元模式，类似单例池
    static final Integer cache[] = new Integer[-(-128) + 127 + 1];
  
  Collections.EMPTY_LIST / EMPTY_MAP → 饿汉式单例

MyBatis 中的单例：
  SqlSessionFactory → 通常一个应用只创建一个 → Builder 创建后单例使用
  MapperProxyFactory → 每个 Mapper 接口一个工厂实例 → 类单例
```

### 1.5 面试追问防线

```
Q: Spring 单例和 JVM 单例有什么区别？
  → Spring 单例是容器级（同 ApplicationContext 内唯一）
    JVM 单例是类加载器级（同 ClassLoader 内唯一）

Q: 单例如何防止反射破坏？
  → 枚举天然防反射（Constructor.newInstance 内部检查）
    非枚举可在构造器中加 initialized 标记

Q: 单例如何防止序列化破坏？
  → 枚举天然防序列化（readObject 特殊处理）
    非枚举可实现 readResolve() 返回已有实例

Q: DCL 为什么要 volatile？
  → new 对象的三步指令可能重排序 → volatile 禁止重排

Q: 饿汉式 vs 懒汉式 vs 枚举 选哪个？
  → 简单场景选饿汉；需要懒加载选静态内部类；
    需要防反射/序列化选枚举（最佳实践）
```

## 2 工厂模式（Simple Factory / Factory Method / Abstract Factory）

### 2.1 一句话定义

> **将对象创建逻辑封装起来，客户端不需要知道具体创建了哪个类。**

三种工厂的区别：
- **简单工厂**：一个工厂类，静态方法，根据参数返回不同产品 → 不符合开闭原则
- **工厂方法**：每个产品对应一个工厂子类 → 符合开闭，但类多
- **抽象工厂**：创建产品族（一组相关产品）→ 符合开闭，但新增产品类型困难

### 2.2 手写代码

#### ① 简单工厂（Static Factory）

```java
// 产品接口
public interface Message {
    void send(String content);
}

// 具体产品
public class EmailMessage implements Message {
    @Override
    public void send(String content) {
        System.out.println("Email发送: " + content);
    }
}

public class SmsMessage implements Message {
    @Override
    public void send(String content) {
        System.out.println("SMS发送: " + content);
    }
}

// 简单工厂 → 一个工厂方法根据参数决定创建哪种产品
public class MessageFactory {
    public static Message create(String type) {
        switch (type) {
            case "email": return new EmailMessage();
            case "sms":   return new SmsMessage();
            default: throw new IllegalArgumentException("未知消息类型: " + type);
        }
    }
}

// 客户端：不关心具体类
Message msg = MessageFactory.create("email");
msg.send("Hello");
```

> **缺点**：新增 WechatMessage → 需修改工厂类 switch → 违反开闭原则
> **适用**：产品种类少且稳定不变的场景

#### ② 工厂方法（Factory Method）

```java
// 产品接口
public interface Logger {
    void log(String msg);
}

// 具体产品
public class FileLogger implements Logger {
    @Override
    public void log(String msg) { System.out.println("File日志: " + msg); }
}

public class DatabaseLogger implements Logger {
    @Override
    public void log(String msg) { System.out.println("DB日志: " + msg); }
}

// 工厂接口 → 定义创建方法
public interface LoggerFactory {
    Logger createLogger();
}

// 具体工厂 → 每种产品对应一个工厂
public class FileLoggerFactory implements LoggerFactory {
    @Override
    public Logger createLogger() { return new FileLogger(); }
}

public class DatabaseLoggerFactory implements LoggerFactory {
    @Override
    public Logger createLogger() { return new DatabaseLogger(); }
}

// 客户端
LoggerFactory factory = new FileLoggerFactory();
Logger logger = factory.createLogger();
logger.log("info");

// 新增产品：只需新增 ConsoleLogger + ConsoleLoggerFactory → 不改现有代码
// → 符合开闭原则！
```

#### ③ 抽象工厂（Abstract Factory）— 创建产品族

```java
// 产品族：UI组件（Button + TextField）
// 两个族：Windows风格 / Mac风格

// 产品接口
public interface Button { void render(); }
public interface TextField { void render(); }

// Windows族
public class WindowsButton implements Button {
    @Override public void render() { System.out.println("Windows按钮"); }
}
public class WindowsTextField implements TextField {
    @Override public void render() { System.out.println("Windows文本框"); }
}

// Mac族
public class MacButton implements Button {
    @Override public void render() { System.out.println("Mac按钮"); }
}
public class MacTextField implements TextField {
    @Override public void render() { System.out.println("Mac文本框"); }
}

// 抽象工厂 → 创建一组相关产品
public interface UIFactory {
    Button createButton();
    TextField createTextField();
}

// 具体工厂 → Windows族
public class WindowsFactory implements UIFactory {
    @Override public Button createButton() { return new WindowsButton(); }
    @Override public TextField createTextField() { return new WindowsTextField(); }
}

// 具体工厂 → Mac族
public class MacFactory implements UIFactory {
    @Override public Button createButton() { return new MacButton(); }
    @Override public TextField createTextField() { return new MacTextField(); }
}

// 客户端 → 使用抽象工厂
UIFactory factory = new MacFactory();
Button btn = factory.createButton();
TextField tf = factory.createTextField();
// 保证一族产品风格一致 → Windows族不会混入Mac组件
```

### 2.3 项目映射

```
Spring 中的工厂模式：
  ┌──────────────────────────────────────────────────────┐
  │ 1. BeanFactory → IoC 容器本身就是一个大工厂           │
  │    getBean(name) → 根据配置创建/返回 Bean              │
  │    → 简单工厂 + 工厂方法的组合                         │
  │                                                       │
  │ 2. FactoryBean → 工厂方法模式的经典应用                │
  │    // FactoryBean 接口                                 │
  │    T getObject();     // 创建对象                      │
  │    Class<?> getObjectType(); // 返回类型               │
  │    boolean isSingleton(); // 是否单例                  │
  │                                                       │
  │    // 示例：Mybatis SqlSessionFactoryBean              │
  │    public class SqlSessionFactoryBean                  │
  │        implements FactoryBean<SqlSessionFactory> {      │
  │        @Override                                       │
  │        public SqlSessionFactory getObject() {           │
  │            return new SqlSessionFactoryBuilder()        │
  │                .build(configuration);                   │
  │        }                                               │
  │    }                                                   │
  │    // Spring 容器调用 factoryBean.getObject() 创建实例 │
  │    // 而不是直接 new SqlSessionFactory                 │
  │                                                       │
  │ 3. ApplicationContext = BeanFactory 子接口             │
  │    → 增加了事件发布、国际化、AOP等功能                  │
  │    → 工厂方法模式：子接口提供更丰富的产品               │
  └──────────────────────────────────────────────────────┘

JDK 中的工厂模式：
  java.util.Collections → 简单工厂
    Collections.singletonList() → 返回特定实现
    Collections.unmodifiableList() → 返回装饰后的实现
  
  java.util.Calendar → 简单工厂
    Calendar.getInstance() → 根据Locale返回不同Calendar
  
  java.util.logging.Logger → 工厂方法
    Logger.getLogger(name) → 创建/获取Logger
  
  java.sql.Connection → 报工厂方法（Driver返回Connection）
    Driver.connect(url, props) → 工厂方法
```

### 2.4 面试追问防线

```
Q: 三种工厂模式有什么区别？
  → 简单工厂：一个类，switch/参数，不符合开闭
    工厂方法：每个产品一个工厂子类，符合开闭
    抽象工厂：创建产品族，族内产品风格一致

Q: Spring FactoryBean 和普通 Bean 有什么区别？
  → 普通 Bean：Spring 直接实例化并注册
    FactoryBean：Spring 先实例化 FactoryBean，
      再调用 getObject() 创建真正的 Bean
    → 实际注册的是 getObject() 返回的对象
    → FactoryBean 本身也可通过 &factoryBeanName 获取

Q: 什么时候用抽象工厂？
  → 需要保证一组产品风格一致（UI主题、数据库方言族）
    不适合产品种类频繁新增的场景

Q: 简单工厂违反开闭原则怎么办？
  → 用反射+配置替代 switch：
    Class.forName(config).newInstance() → 不改工厂代码
    但这样失去了编译时类型安全
```

## 3 策略模式（Strategy）

### 3.1 一句话定义

> **定义一系列算法，将每个算法封装起来，使它们可以互相替换。**

### 3.2 核心原理

```
┌─────────────┐        ┌─────────────────┐
│  Context     │───────→│  Strategy        │  ← 接口/抽象类
│  (策略持有者) │        │  + algorithm()   │
│  + setStrategy│        ├─────────────────┤
│  + execute    │        │ StrategyA        │ ← 具体策略
└─────────────┘        │ StrategyB        │
                        │ StrategyC        │
                        └─────────────────┘

关键设计点：
  - Context 持有 Strategy 接口引用 → 运行时可切换
  - 算法实现独立变化 → 新增策略不影响 Context
  - 消除 Context 中的 if-else / switch 分支
```

### 3.3 手写代码

```java
// 策略接口
public interface DiscountStrategy {
    double calculate(double originalPrice);
}

// 具体策略
public class FullReductionStrategy implements DiscountStrategy {
    @Override
    public double calculate(double price) {
        // 满100减20
        return price >= 100 ? price - 20 : price;
    }
}

public class PercentageStrategy implements DiscountStrategy {
    private double rate; // 如 0.8 = 八折
    
    public PercentageStrategy(double rate) { this.rate = rate; }
    
    @Override
    public double calculate(double price) {
        return price * rate;
    }
}

public class NoDiscountStrategy implements DiscountStrategy {
    @Override
    public double calculate(double price) {
        return price; // 无折扣
    }
}

// Context → 策略持有者
public class Order {
    private DiscountStrategy strategy;
    
    public void setStrategy(DiscountStrategy strategy) {
        this.strategy = strategy;
    }
    
    public double getFinalPrice(double originalPrice) {
        return strategy.calculate(originalPrice);
    }
}

// 客户端 → 运行时动态切换策略
Order order = new Order();
order.setStrategy(new FullReductionStrategy());
System.out.println(order.getFinalPrice(120)); // 100

order.setStrategy(new PercentageStrategy(0.8));
System.out.println(order.getFinalPrice(120)); // 96
```

#### 策略模式消除 if-else

```java
// ❌ 反模式：if-else 堆叠
public double calculate(String type, double price) {
    if ("full_reduction".equals(type)) return price >= 100 ? price - 20 : price;
    else if ("percentage".equals(type)) return price * 0.8;
    else return price;
}
// 新增折扣类型 → 改这个方法 → 违反开闭

// ✅ 策略模式：用 Map 注册策略
public class DiscountStrategyFactory {
    private static final Map<String, DiscountStrategy> strategies = new HashMap<>();
    
    static {
        strategies.put("full_reduction", new FullReductionStrategy());
        strategies.put("percentage_8", new PercentageStrategy(0.8));
        strategies.put("no_discount", new NoDiscountStrategy());
    }
    
    public static DiscountStrategy getStrategy(String type) {
        return strategies.get(type);
    }
}

// 客户端 → 一行代码，无 if-else
DiscountStrategy strategy = DiscountStrategyFactory.getStrategy("full_reduction");
```

### 3.4 项目映射

```
Spring 中的策略模式：
  ┌──────────────────────────────────────────────────────┐
  │ 1. Resource 接口 → 不同资源加载策略                    │
  │    UrlResource       → URL加载                        │
  │    ClassPathResource → classpath加载                  │
  │    FileSystemResource → 文件系统加载                  │
  │    ServletContextResource → Web应用加载               │
  │    → ApplicationContext 根据配置选择 Resource 实现     │
  │                                                       │
  │ 2. HandlerMapping → 不同路由映射策略                   │
  │    BeanNameUrlHandlerMapping → Bean名做URL             │
  │    SimpleUrlHandlerMapping  → 配置映射                 │
  │    RequestMappingHandlerMapping → @RequestMapping     │
  │    → DispatcherServlet 持有 List<HandlerMapping>      │
  │                                                       │
  │ 3. BeanCreationStrategy → 不同实例化策略               │
  │    SimpleInstantiationStrategy → 反射创建              │
  │    CglibSubclassingInstantiationStrategy → CGLIB创建   │
  │                                                       │
  │ 4. Spring Security FilterChain → 策略链                │
  │    不同 Filter 处理不同安全场景                        │
  │                                                       │
  │ 5. @Conditional → 条件策略                             │
  │    @ConditionalOnClass / @ConditionalOnProperty / ...  │
  │    → 不同条件决定是否加载 Bean → 策略选择              │
  └──────────────────────────────────────────────────────┘

JDK 中的策略模式：
  Comparator → 策略接口
    Collections.sort(list, comparator) → comparator 是排序策略
    不同 Comparator 实现不同排序规则 → 策略切换
  
  ThreadPoolExecutor.RejectedExecutionHandler → 拒绝策略
    AbortPolicy        → 抛异常（默认）
    CallerRunsPolicy   → 调用者自己执行
    DiscardPolicy      → 直接丢弃
    DiscardOldestPolicy → 丢弃最老任务
    → 不同策略处理线程池满的不同行为

  Comparator / RejectedExecutionHandler → 都是策略接口
  → 构造时注入 → 运行时不可切换（与经典策略的 setStrategy 不同）
```

```

  → 工厂模式：关注"创建哪个对象" → 创建逻辑
    策略模式：关注"用哪种算法" → 行为逻辑
    → 常组合使用：工厂创建策略对象，Context 使用策略
```

## 4 观察者模式（Observer）

### 4.1 一句话定义

> **定义对象间一对多的依赖关系，当一个对象状态改变时，所有依赖它的对象都收到通知并自动更新。**

### 4.2 核心原理

```
┌──────────────┐          ┌──────────────────┐
│  Subject      │─────────→│  Observer         │ ← 接口
│  (被观察者)    │  notify  │  + update(data)   │
│  + attach()   │          ├──────────────────┤
│  + detach()   │          │ ObserverA         │ ← 具体观察者
│  + notify()   │          │ ObserverB         │
│  observers=[] │          │ ObserverC         │
└──────────────┘          └──────────────────┘

流程：
  1. 观察者 attach(subject) → subject.observers.add(this)
  2. subject 状态变化 → notify() → 遍历 observers 调用 update()
  3. 观察者 detach(subject) → subject.observers.remove(this)

推模型 vs 拉模型：
  推：subject.notify(data) → 主动推送变化数据
  拉：subject.notify() → observer 自己调 subject.getData()
  → 推模型更常见（数据更精准）
```

### 4.3 手写代码

#### 手写版（面试重点）

```java
// 观察者接口
public interface Observer {
    void update(String event, Object data);
}

// 被观察者（Subject）
public class EventPublisher {
    private List<Observer> observers = new ArrayList<>();
    
    public void attach(Observer observer) {
        observers.add(observer);
    }
    
    public void detach(Observer observer) {
        observers.remove(observer);
    }
    
    public void notify(String event, Object data) {
        for (Observer observer : observers) {
            observer.update(event, data);
        }
    }
    
    // 业务方法 → 状态变化时触发通知
    public void publishEvent(String event, Object data) {
        System.out.println("发布事件: " + event);
        notify(event, data); // 推模型
    }
}

// 具体观察者
public class EmailNotifier implements Observer {
    @Override
    public void update(String event, Object data) {
        System.out.println("Email通知: " + event + " → " + data);
    }
}

public class LogNotifier implements Observer {
    @Override
    public void update(String event, Object data) {
        System.out.println("日志记录: " + event + " → " + data);
    }
}

// 客户端
EventPublisher publisher = new EventPublisher();
publisher.attach(new EmailNotifier());
publisher.attach(new LogNotifier());
publisher.publishEvent("ORDER_CREATED", "订单#123");
// 输出：
// 发布事件: ORDER_CREATED
// Email通知: ORDER_CREATED → 订单#123
// Log通知: ORDER_CREATED → 订单#123
```

## 5 装饰器模式（Decorator）

### 5.1 一句话定义

> **动态地给对象添加额外职责，比生成子类更灵活。**

### 5.2 核心原理

```
┌──────────────────────┐
│  Component (接口)     │ ← 被装饰者和装饰器共同实现
│  + operation()        │
├──────────────────────┤
│  ConcreteComponent    │ ← 核心实现（被装饰者）
│  + operation()        │
├──────────────────────┤
│  Decorator (抽象)     │ ← 持有 Component 引用
│  - component          │
│  + operation()        │   → 调用 component.operation()
├──────────────────────┤
│  ConcreteDecoratorA   │ ← 具体装饰器
│  + operation()        │   → 先调 component.operation() → 再添加A功能
│  + addedBehavior()    │
│  ConcreteDecoratorB   │ ← 另一个装饰器
│  + operation()        │   → 先调 component.operation() → 再添加B功能
└──────────────────────┘

关键设计点：
  - 装饰器和被装饰者实现同一接口 → 对客户端透明
  - 装饰器持有被装饰者引用 → 像一层套一层
  - 可以多层装饰 → A装饰B装饰Core → operation() 递归调用链
  - 新增功能不需修改核心类 → 符合开闭原则

与继承对比：
  继承 → 静态扩展 → 编译时确定 → 类爆炸
  装饰 → 动态扩展 → 运行时组合 → 按需叠加
```

### 5.3 手写代码

```java
// Component 接口
public interface DataSource {
    String readData();
    void writeData(String data);
}

// ConcreteComponent → 核心实现
public class FileDataSource implements DataSource {
    private String filename;
    
    public FileDataSource(String filename) { this.filename = filename; }
    
    @Override
    public String readData() {
        System.out.println("从文件读取: " + filename);
        return "原始数据";
    }
    
    @Override
    public void writeData(String data) {
        System.out.println("写入文件: " + filename + " → " + data);
    }
}

// Decorator 基类 → 持有 Component 引用，默认委托
public class DataSourceDecorator implements DataSource {
    protected DataSource wrappee; // 被装饰者
    
    public DataSourceDecorator(DataSource source) {
        this.wrappee = source;
    }
    
    @Override
    public String readData() { return wrappee.readData(); }
    
    @Override
    public void writeData(String data) { wrappee.writeData(data); }
}

// ConcreteDecorator → 加密装饰
public class EncryptionDecorator extends DataSourceDecorator {
    public EncryptionDecorator(DataSource source) { super(source); }
    
    @Override
    public String readData() {
        String data = wrappee.readData(); // 先读原始
        return decrypt(data); // 解密后返回
    }
    
    @Override
    public void writeData(String data) {
        wrappee.writeData(encrypt(data)); // 加密后写入
    }
    
    private String encrypt(String data) { return "加密(" + data + ")"; }
    private String decrypt(String data) { return data.replace("加密(", "").replace(")", ""); }
}

// ConcreteDecorator → 压缩装饰
public class CompressionDecorator extends DataSourceDecorator {
    public CompressionDecorator(DataSource source) { super(source); }
    
    @Override
    public String readData() {
        String data = wrappee.readData();
        return decompress(data);
    }
    
    @Override
    public void writeData(String data) {
        wrappee.writeData(compress(data));
    }
    
    private String compress(String data) { return "压缩(" + data + ")"; }
    private String decompress(String data) { return data.replace("压缩(", "").replace(")", ""); }
}

// 客户端 → 多层装饰，动态组合
DataSource source = new FileDataSource("data.txt");
DataSource encrypted = new EncryptionDecorator(source);
DataSource compressedAndEncrypted = 
    new CompressionDecorator(new EncryptionDecorator(source));

// 写入：先压缩 → 再加密 → 再写文件
compressedAndEncrypted.writeData("Hello");
// 输出链路：压缩(加密(Hello)) → 写入文件

// 读取：先读文件 → 再解密 → 再解压
String data = compressedAndEncrypted.readData();
```

### 5.5 装饰器 vs 代理

```
面试高频对比：

┌────────────┬──────────────────────┬──────────────────────┐

├────────────┼──────────────────────┼──────────────────────┤
│ 目的        │ 增强功能(加职责)      │ 控制访问(加控制层)     │
│ 对象创建    │ 客户端组合装饰链      │ 代理内部创建/获取      │
│ 层次        │ 可多层嵌套装饰        │ 通常一层代理           │

│ 关系        │ 装饰器与被装饰者同级   │ 代理代表被代理者       │
│ 典型应用    │ Java IO流             │ Spring AOP            │
└────────────┴──────────────────────┴──────────────────────┘

核心区别：
  装饰器 → 你主动选择给对象加什么功能 → 多层组合 → 强调"增加"
  代理   → 代理替你管理对象 → 你不知道有代理 → 强调"控制"
  
  → Spring AOP 名义上是代理，但 @Cacheable 装饰了缓存功能
    → 实际上是代理+装饰器的混合
```

```

    装饰器：动态组合，运行时决定，按需叠加 → 灵活
  → 例：3种功能 × 各有/无 → 继承需要 2^3=8个子类 → 装饰器只需3个装饰器类

Q: 装饰器和代理有什么区别？
  → 装饰器：增强功能，客户端主动组合，可多层嵌套
    代理：控制访问，代理内部管理，通常一层
  → Spring AOP = 代理框架，但 @Cacheable = 装饰行为 → 混合

Q: Java IO 为什么用装饰器？
  → 不同功能组合太多 → 继承类爆炸
    装饰器可自由组合 → 缓冲+压缩+加密 随意叠加
```

## 6 代理模式（Proxy）

### 6.1 一句话定义

> **为其他对象提供代理以控制对这个对象的访问。**

### 6.2 三种代理对比

```
┌────────────┬──────────────────────────────────────────┐
│ 类型        │ 特点                                     │
├────────────┼──────────────────────────────────────────┤
│ 静态代理    │ 代理类在编译前就存在 → 手写代理类          │
│ JDK动态代理 │ 运行时生成代理类 → 基于接口 → Proxy+IH    │
│ CGLIB代理   │ 运行时生成代理类 → 基于子类继承 → Enhancer│
└────────────┴──────────────────────────────────────────┘
```

### 6.3 手写代码

#### ① 静态代理

```java
// 接口
public interface UserService {
    void createUser(String name);
}

// 被代理类
public class UserServiceImpl implements UserService {
    @Override
    public void createUser(String name) {
        System.out.println("创建用户: " + name);
    }
}

// 静态代理 → 手写代理类
public class UserServiceProxy implements UserService {
    private UserService target; // 持有被代理对象
    
    public UserServiceProxy(UserService target) { this.target = target; }
    
    @Override
    public void createUser(String name) {
        // 前置增强
        System.out.println("[Proxy] 前置: 检查权限...");
        // 调用目标方法
        target.createUser(name);
        // 后置增强
        System.out.println("[Proxy] 后置: 记录日志...");
    }
}

// 缺点：每个接口都要写一个代理类 → 接口多则代理类爆炸
```

#### ② JDK 动态代理（面试必写核心）

```java
// 接口
public interface OrderService {
    String createOrder(String productId);
    void cancelOrder(String orderId);
}

// 目标类
public class OrderServiceImpl implements OrderService {
    @Override
    public String createOrder(String productId) {
        System.out.println("创建订单: " + productId);

        System.out.println("取消订单: " + orderId);

// InvocationHandler → 代理逻辑
public class LogInvocationHandler implements InvocationHandler {
    private Object target; // 被代理对象
    
    public LogInvocationHandler(Object target) { this.target = target; }
    
    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        // 前置通知
        System.out.println("[JDK Proxy] before: " + method.getName());
        
        // 执行目标方法 → 反射调用
        Object result = method.invoke(target, args);
        
        // 后置通知
        System.out.println("[JDK Proxy] after: " + method.getName() + " → " + result);
        
        return result;
    }
}

// 创建代理对象
OrderService target = new OrderServiceImpl();
OrderService proxy = (OrderService) Proxy.newProxyInstance(
    target.getClass().getClassLoader(),  // 目标类的类加载器
    target.getClass().getInterfaces(),    // 目标类实现的接口
    new LogInvocationHandler(target)      // InvocationHandler
);

proxy.createOrder("P001");
// 输出：
// [JDK Proxy] before: createOrder
// 创建订单: P001
// [JDK Proxy] after: createOrder → ORDER-P001
```

> **JDK 动态代理原理**：
> - `Proxy.newProxyInstance()` 在运行时生成一个实现了目标接口的代理类字节码
> - 代理类内部持有一个 InvocationHandler 引用
> - 每个接口方法在代理类中都会调用 `handler.invoke(proxy, method, args)`
> - `method.invoke(target, args)` 通过反射调用目标方法
> - **限制**：目标类必须实现接口 → 不能代理没有接口的类

#### JDK 动态代理生成的代理类结构（反编译）

```java
// Proxy.newProxyInstance 生成的代理类大致结构：
public class $Proxy0 extends Proxy implements OrderService {
    private static Method m1; // createOrder Method对象
    private static Method m2; // cancelOrder Method对象

    public $Proxy0(InvocationHandler h) { super(h); }
    
    @Override
    public String createOrder(String productId) {
        // 每个方法 → 都调用 h.invoke()
        return (String) h.invoke(this, m1, new Object[]{productId});
    }
    
    @Override
    public void cancelOrder(String orderId) {
        h.invoke(this, m2, new Object[]{orderId});
    }
}
// → 所有方法调用都委托给 InvocationHandler.invoke()
// → invoke() 内部：前置逻辑 + method.invoke(target, args) + 后置逻辑
```

#### ③ CGLIB 动态代理

```java
// CGLIB → 基于继承，不需要接口
// 目标类（没有接口也可以）
public class PaymentService {
    public String pay(String orderId) {
        System.out.println("支付: " + orderId);
        return "PAID-" + orderId;
    }
}

// MethodInterceptor → CGLIB 的拦截器
public class LogMethodInterceptor implements MethodInterceptor {
    @Override
    public Object intercept(Object obj, Method method, Object[] args,
                           MethodProxy proxy) throws Throwable {
        System.out.println("[CGLIB] before: " + method.getName());
        
        // 注意：用 proxy.invokeSuper 而不是 method.invoke
        // proxy.invokeSuper → 直接调用父类方法（FastClass机制，比反射快）
        Object result = proxy.invokeSuper(obj, args);
        
        System.out.println("[CGLIB] after: " + method.getName());
        return result;
    }
}

// 创建代理
Enhancer enhancer = new Enhancer();
enhancer.setSuperclass(PaymentService.class); // 设置父类
enhancer.setCallback(new LogMethodInterceptor());
PaymentService proxy = (PaymentService) enhancer.create(); // 创建代理子类

proxy.pay("O001");
```

> **CGLIB 原理**：
> - `Enhancer.create()` 在运行时生成一个继承目标类的子类字节码
> - 子类重写所有非 final 方法 → 在重写方法中调用 `MethodInterceptor.intercept()`
> - `intercept()` 内部用 `MethodProxy.invokeSuper()` → 通过 FastClass 机制直接调用父类方法
> - FastClass = 为每个方法生成索引 → 方法调用通过索引而非反射 → **比 JDK 反射更快**
> - **限制**：不能代理 final 类/方法（无法继承/重写）

```
  JDK 动态代理 = 基于接口 + 反射调用 → 有接口优先选
```

### 6.6 面试追问防线

```
Q: JDK 动态代理为什么只能代理接口？
  → 生成的代理类 extends Proxy + implements 目标接口
  → Java 不允许多继承 → 代理类已经继承了 Proxy → 只能通过接口添加类型
  → 没有接口的类 → Proxy 无法实现它的方法 → 无法代理

Q: CGLIB 为什么不能代理 final 类/方法？
  → CGLIB 通过继承目标类创建子类 → final 类不能被继承
  → final 方法不能被重写 → 子类中无法拦截 final 方法调用

Q: Spring AOP 的拦截器链是怎么执行的？
  → ReflectiveMethodInvocation.proceed() → 递归调用
  → currentInterceptorIndex++ → 调用当前 interceptor
  → interceptor 调用 invocation.proceed() → 递归下一个
  → 全部 interceptor 执行完 → method.invoke(target) → 目标方法

Q: JDK 动态代理生成的代理类结构是什么样的？
  → extends Proxy + implements 目标接口
  → 每个方法 → h.invoke(this, method对象, args)
  → h = InvocationHandler → 代理逻辑
```

## 7 模板方法模式（Template Method）

### 7.1 一句话定义

> **在父类中定义算法骨架，将某些步骤延迟到子类实现。**

### 7.2 核心原理

```
┌─────────────────────────────────────────┐
│ AbstractClass (抽象父类)                  │
│                                           │
│ // 模板方法 → 定义算法骨架（final防止覆写）│
│ + final templateMethod() {               │
│     step1();       // 固定步骤（父类实现）│
│     step2();       // 可变步骤（子类实现）│
│     step3();       // 固定步骤            │
│     hook();        // 钩子方法（可选覆盖）│
│ }                                         │
│                                           │
│ + step1() { ... }  // 固定实现            │
│ + step3() { ... }  // 固定实现            │
│                                           │
│ # abstract step2(); // 子类必须实现       │
│ # hook() {}        // 空实现，子类可选覆盖│
├─────────────────────────────────────────┤
│ ConcreteClassA                           │
│ + step2() { A的实现 }                    │
│                                           │
│ ConcreteClassB                           │
│ + step2() { B的实现 }                    │
└─────────────────────────────────────────┘

关键设计点：
  - templateMethod() 用 final → 防止子类改变算法结构
  - 可变步骤用 abstract → 强制子类实现
  - 钩子方法(Hook)用 protected 空/默认实现 → 子类可选覆盖
  → 父类控制流程，子类填充细节 → 逆变（框架调用应用）
```

### 7.3 手写代码

```java
// 抽象父类 → 定义查询模板
public abstract class AbstractDataParser {
    
    // 模板方法 → final 防止子类覆写骨架
    public final void parse(String source) {
        openSource(source);    // 步骤1：打开数据源（固定）
        String rawData = readData();  // 步骤2：读取数据（可变）
        Data data = processData(rawData); // 步骤3：处理数据（可变）
        closeSource();         // 步骤4：关闭数据源（固定）
        if (shouldLog()) {     // 钩子：是否记录日志（可选）
            logResult(data);
        }
    }
    
    // 固定步骤 → 所有子类共用
    private void openSource(String source) {
        System.out.println("打开数据源: " + source);
    }
    
    private void closeSource() {
        System.out.println("关闭数据源");
    }
    
    private void logResult(Data data) {
        System.out.println("记录结果: " + data);
    }
    
    // 可变步骤 → 子类必须实现
    protected abstract String readData();
    protected abstract Data processData(String rawData);
    
    // 钩子方法 → 子类可选覆盖
    protected boolean shouldLog() { return true; } // 默认记录日志
}

// 子类A → CSV解析器
public class CsvDataParser extends AbstractDataParser {
    @Override
    protected String readData() {
        System.out.println("从CSV文件读取");
        return "csv-raw-data";
    }
    
    @Override
    protected Data processData(String rawData) {
        System.out.println("解析CSV格式");
        return new Data(rawData);
    }
    
    @Override
    protected boolean shouldLog() { return false; } // CSV不记录日志
}

// 子类B → JSON解析器
public class JsonDataParser extends AbstractDataParser {
    @Override
    protected String readData() {
        System.out.println("从JSON文件读取");
        return "json-raw-data";
    }
    
    @Override
    protected Data processData(String rawData) {
        System.out.println("解析JSON格式");
        return new Data(rawData);
    }
    // shouldLog() 不覆盖 → 使用默认值 true
}

// 客户端 → 只调模板方法，不关心具体步骤
AbstractDataParser parser = new JsonDataParser();
parser.parse("data.json"); // 自动执行完整流程
```

```
  │    → 同样是模板方法：连接管理=固定，具体操作=可变      │

JDK 中的模板方法：
  AbstractList → 模板方法
    add(), remove(), set() → 抛 UnsupportedOperationException → 子类覆盖
    → ArrayList 覆盖了这些方法
  
  AbstractMap → 模板方法
    → HashMap 覆盖了 put/get/remove
  
  InputStream.read(byte[], off, len)
    → 默认实现循环调 read() → 子类只需实现单字节 read()
```

### 7.5 面试追问防线

```
Q: 模板方法模式和策略模式有什么区别？
  → 模板方法：继承关系 → 父类定义骨架，子类实现步骤
    → 通过子类扩展 → 编译时确定
  → 策略模式：组合关系 → Context 持有策略接口引用
    → 运行时切换 → 动态选择
  → 模板方法强调"算法结构不变，细节可变"
    策略模式强调"整体算法可替换"

Q: 模板方法模式的钩子方法是什么？
  → 钩子(Hook) = 父类提供的空/默认实现方法 → 子类可选覆盖
  → 作用：提供扩展点但不强制 → shouldLog() 是典型钩子
  → 父类模板方法中用 if (hook()) → 条件执行

Q: JdbcTemplate 是模板方法模式吗？
  → 是！execute() 是模板方法：连接获取/释放=固定步骤
    SQL执行和结果映射=可变步骤(由callback/RowMapper决定)
  → 但 JdbcTemplate 不用继承实现可变步骤 → 用 callback 接口
    → 模板方法 + 策略模式的组合

Q: 模板方法用 final 修饰有什么意义？
  → 防止子类覆写模板方法 → 保证算法骨架不被破坏
  → 这是模板方法模式的核心约束
```

## 8 建造者模式（Builder）

### 8.1 一句话定义

> **将复杂对象的构建与表示分离，使同样的构建过程可以创建不同的表示。**

### 8.2 核心原理

```
适用场景：
  - 对象有大量可选参数 → 构造器参数爆炸
  - 需要分步构建 → 某些参数有先后约束
  - 创建后不可变 → 防止中途被修改

两种实现方式：
  1. 经典四角色版（Builder接口 + Director）→ 过于复杂，面试不常写
  2. 简化版（静态内部类 Builder）→ Lombok @Builder 原理 → 面试必写

简化版核心思路：
  1. 目标类构造器私有 → 只能通过 Builder 创建
  2. Builder 类有与目标类相同的属性 + setter方法返回 this → 链式调用
  3. Builder.build() → 调用目标类私有构造器 → 传入 Builder 自身
  4. 目标类从 Builder 取值 → 创建不可变对象
```

### 8.3 手写代码

#### 手写 Builder（面试标准版）

```java
// 目标类 → 不可变对象
public class HttpRequest {
    // 必填参数
    private final String url;
    private final String method;
    
    // 可选参数 → 大量可选 → 构造器爆炸问题
    private final String contentType;
    private final int timeout;
    private final Map<String, String> headers;
    private final String body;
    private final boolean followRedirects;
    
    // 私有构造 → 只能通过 Builder 创建
    private HttpRequest(Builder builder) {
        this.url = builder.url;
        this.method = builder.method;
        this.contentType = builder.contentType;
        this.timeout = builder.timeout;
        this.headers = builder.headers;
        this.body = builder.body;
        this.followRedirects = builder.followRedirects;
    }
    
    // 静态内部类 Builder
    public static class Builder {
        // 必填 → 无默认值
        private String url;
        private String method;
        
        // 可选 → 有默认值
        private String contentType = "application/json";
        private int timeout = 30000;
        private Map<String, String> headers = new HashMap<>();
        private String body = null;
        private boolean followRedirects = true;
        
        // 必填参数通过 Builder 构造器传入
        public Builder(String url, String method) {
            this.url = url;
            this.method = method;
        }
        
        // 可选参数 → setter 返回 this → 链式调用
        public Builder contentType(String contentType) {
            this.contentType = contentType;
            return this;
        }
        
        public Builder timeout(int timeout) {
            this.timeout = timeout;
            return this;
        }
        
        public Builder header(String key, String value) {
            this.headers.put(key, value);
            return this;
        }
        
        public Builder body(String body) {
            this.body = body;
            return this;
        }
        
        public Builder followRedirects(boolean follow) {
            this.followRedirects = follow;
            return this;
        }
        
        // build() → 创建不可变的目标对象
        public HttpRequest build() {
            // 校验逻辑 → 构建前检查约束
            if (url == null || url.isEmpty()) {
                throw new IllegalStateException("URL不能为空");
            }
            return new HttpRequest(this);
        }
    }
    
    // getter...（无setter → 不可变）
}

// 客户端 → 链式调用，清晰可读
HttpRequest request = new HttpRequest.Builder("https://api.example.com", "POST")
    .contentType("application/json")
    .timeout(5000)
    .header("Authorization", "Bearer xxx")
    .body("{\"name\":\"test\"}")
    .followRedirects(false)
    .build();

// 对比构造器方式 → 参数顺序混乱、可读性差
// new HttpRequest("url", "POST", "json", 5000, headers, body, false)
// → 第3个参数是 contentType 还是 timeout？可读性差
```

#### Lombok @Builder 原理

```java
// @Builder 注解生成的代码 = 上面的手写版
@Builder
public class HttpRequest {
    private String url;
    private String method;
    private String contentType;
    private int timeout;
    // ...
}

// Lombok 自动生成：
// 1. private HttpRequest(HttpRequest.Builder builder) 构造器
// 2. HttpRequest.Builder 静态内部类
// 3. Builder 的链式 setter 方法
// 4. Builder.build() 方法
// 5. HttpRequest.builder() 静态入口方法

// 使用：
HttpRequest request = HttpRequest.builder()
```

### 8.5 建造者 vs 工厂

```
┌────────────┬──────────────────────┬──────────────────────┐
│ 维度        │ 建造者模式           │ 工厂模式              │
├────────────┼──────────────────────┼──────────────────────┤
│ 关注点      │ 怎么构建(分步+配置)   │ 创建哪个类型           │
│ 对象复杂度  │ 多可选参数的复杂对象   │ 简单对象               │
│ 创建过程    │ 分步链式设置 → build  │ 一次调用直接创建       │
│ 返回类型    │ 通常单一类型          │ 多种不同类型           │
│ 是否可变    │ 通常创建不可变对象     │ 创建的对象可变         │
│ 典型场景    │ HttpRequest配置      │ Message 创建(多种类型) │
└────────────┴──────────────────────┴──────────────────────┘

一句话区分：
  工厂 → "创建哪种产品" → 类型选择
  建造者 → "怎么配置这个产品" → 参数配置
  → 常组合使用：工厂选类型 → 建造者配参数
```

### 8.6 面试追问防线

```
Q: 建造者模式和工厂模式有什么区别？
  → 工厂关注"创建哪个类型" → 一次调用返回完整对象
    建造者关注"怎么配置" → 分步链式设置 → build()才创建
  → 建造者适合多可选参数的复杂对象

Q: StringBuilder 是建造者模式吗？
  → 不是！StringBuilder 没有 build() 创建不可变对象
    → 它是简单累积器/缓冲器模式
    → 名字容易误导 → 面试别混淆

Q: Lombok @Builder 的原理？
  → 自动生成 Builder 静态内部类 + 链式 setter + build()
  → 目标类构造器私有 → Builder.build() 调私有构造器
  → 创建的是不可变对象

Q: 建造者模式如何保证参数约束？
  → Builder.build() 中添加校验逻辑
    → 如 url 为空 → throw IllegalStateException
    → 如 timeout < 0 → throw IllegalArgumentException
  → 校验在构建时而非使用时 → 更早发现问题
```

### 9.2 相似模式辨析

```
创建型三兄弟：
  单例 → "只有一个" → 全局唯一
  工厂 → "谁来创建" → 类型选择
  建造者 → "怎么创建" → 参数配置
  → 单例保证唯一，工厂保证类型，建造者保证配置

结构型双胞胎：
  装饰器 → 增强功能 → 客户端主动组合 → 多层嵌套
  代理 → 控制访问 → 代理内部管理 → 通常一层
  → 装饰器强调"加什么"，代理强调"替谁管"

行为型三剑客：
  策略 → 算法互换 → 组合关系 → 运行时切换
  模板方法 → 骨架不变 → 继承关系 → 编译时确定
  观察者 → 一对多通知 → 松耦合 → 事件驱动
  → 策略替换算法，模板方法固定流程，观察者松耦合通知
```

### 9.3 实际项目中的模式组合

```
常见组合模式：

  1. 工厂 + 策略 → 工厂创建策略对象
     // Spring HandlerMapping → 工厂创建不同路由策略
     // 策略模式消除if-else + 工厂模式封装创建

  2. 代理 + 装饰器 → Spring AOP
     // 代理框架(JDK/CGLIB) + 装饰行为(@Cacheable/@Transactional)
     // AOP本质是代理，但切面逻辑是装饰行为

  3. 单例 + 工厂 → Spring Bean 默认scope
     // BeanFactory 创建 Bean → 默认 singleton → 单例+工厂组合

  4. 建造者 + 工厂 → Netty Bootstrap
     // Builder配置参数 → bind()创建Channel → 建造者配置+工厂创建

  5. 模板方法 + 策略 → JdbcTemplate
     // 模板骨架(连接获取/释放) + 策略接口(StatementCallback/RowMapper)

  6. 观察者 + 策略 → Spring Event + Handler
     // 事件通知 → 不同监听器用不同策略处理

  面试一句话总结：
    设计模式不是单独使用 → 真实项目都是组合拳
    → 识别每个模式解决什么问题 → 按需组合
```

## 10 十道面试高频题

### Q1：谈谈你对设计模式的理解？项目中用了哪些？

**回答**：设计模式是面向对象设计中反复出现问题的经典解决方案。GoF 定义了 23 种，但面试核心掌握 8 种即可：单例、工厂、策略、观察者、装饰器、代理、模板方法、建造者。我在项目中使用的主要有：Spring AOP 用了代理模式（JDK/CGLIB 动态代理），IoC 容器本质是工厂模式+单例模式组合，JdbcTemplate 用了模板方法+策略模式组合，@EventListener 用了观察者模式，@Builder 用了建造者模式。设计模式的核心价值不是记住类图，而是理解每个模式解决什么痛点，在什么场景该用、不该用。

---

### Q2：写一个线程安全的单例模式？为什么 DCL 要 volatile？

**回答**：线程安全单例推荐三种方式：①静态内部类（懒加载+天然线程安全）；②DCL 双重检查锁+volatile；③枚举单例（最佳实践，防反射+防序列化）。DCL 中 volatile 的作用是禁止 new 对象时的指令重排序：`new Singleton()` 字节码分三步——分配内存、初始化、赋值引用，不加 volatile 时 JVM 可能将赋值和初始化重排序，导致线程 A 赋值了引用但未初始化，线程 B 第一重检查发现不为 null 就返回了半成品对象。volatile 通过内存屏障禁止 ②③ 重排序，保证对象完全初始化后才赋值给 INSTANCE。

---

### Q3：JDK 动态代理和 CGLIB 代理有什么区别？Spring AOP 用哪个？

**回答**：JDK 动态代理基于接口——生成的代理类 extends Proxy implements 目标接口，每个方法调用 InvocationHandler.invoke()，通过反射调用目标方法。CGLIB 代理基于继承——生成的代理类 extends 目标类，重写所有非 final 方法，调用 MethodInterceptor.intercept()，通过 FastClass 索引直接调用父类方法（比反射快）。JDK 代理要求目标类必须实现接口，CGLIB 要求目标类不能是 final。Spring AOP 的选择策略：有接口用 JDK 动态代理，无接口用 CGLIB；设置 proxyTargetClass=true 强制全部用 CGLIB。

---

### Q4：策略模式如何消除 if-else？与工厂模式怎么配合？

**回答**：策略模式将每种分支逻辑封装为独立的策略类，通过 Map<策略名, 策略实现> 注册所有策略，客户端只需 map.get(type) 一行代码选择策略，完全消除 if-else。新增策略只需新增一个策略类并注册到 Map，不改客户端代码——符合开闭原则。与工厂模式配合：工厂负责创建策略对象（封装创建逻辑），Context 使用策略对象（封装行为逻辑），客户端只传参数给工厂，工厂返回策略，Context 执行策略——客户端既不需要 if-else 也不需要知道具体策略类。

---

### Q5：Spring 的事件机制是观察者模式吗？和 Pub-Sub 有什么区别？

**回答**：Spring 的 ApplicationEvent + @EventListener 是观察者模式的实现，但更接近发布-订阅模式。经典观察者模式中 Subject 直接持有 Observer 引用并调用 update()，两者耦合；而 Spring 通过 ApplicationEventMulticaster 作为事件总线解耦——发布者不知道有哪些监听者，监听者也不知道谁发布了事件，只通过事件类型匹配。这与通过消息队列的 Pub-Sub 模式思想一致。Spring multicastEvent 默认同步（同线程执行所有 listener），可配置 TaskExecutor 实现异步通知。

---

### Q6：装饰器模式和代理模式有什么区别？Java IO 用的是哪个？

**回答**：装饰器模式强调动态增强功能——客户端主动组合装饰链，可多层嵌套，装饰器与被装饰者同级；代理模式强调控制访问——代理内部管理被代理对象，通常一层，客户端不知道有代理存在。Java IO 用的是装饰器模式：BufferedInputStream 装饰 FileInputStream 加缓冲功能，GZIPInputStream 装饰加解压缩功能，客户端自由组合多层装饰。Spring AOP 名义上是代理模式，但 @Cacheable/@Transactional 等切面本质是在原方法上装饰了额外行为——实际是代理框架+装饰行为的混合。

---

### Q7：模板方法模式在 Spring 中有哪些应用？

**回答**：Spring 中模板方法模式的经典应用：①JdbcTemplate.execute()——连接获取和释放是固定步骤，SQL执行和结果映射由 StatementCallback/RowMapper 决定（可变步骤）；②AbstractApplicationContext.refresh()——容器启动的12步流程是固定骨架，onRefresh() 是钩子方法供子类覆盖；③HttpServlet.service()——根据请求方法分发到 doGet/doPost，子类只需覆盖对应方法。模板方法的核心是父类用 final 定义算法骨架，子类通过 abstract 方法或钩子方法填充可变步骤。JdbcTemplate 还结合了策略模式——可变步骤不是通过继承而是通过 callback 接口实现。

---

### Q8：建造者模式适合什么场景？和工厂模式有什么区别？

**回答**：建造者模式适合多可选参数的复杂对象构建——如 HttpRequest 有 url（必填）、method、timeout、headers、body 等大量可选参数，用构造器创建参数顺序混乱、可读性差，用 Builder 链式调用 `.url().timeout().header().build()` 清晰直观。与工厂模式的区别：工厂关注"创建哪种类型"——一次调用直接返回对象；建造者关注"怎么配置这个对象"——分步链式设置参数后 build() 才创建。工厂适合简单对象的类型选择，建造者适合复杂对象的参数配置。注意 StringBuilder 不是建造者模式——它没有 build() 创建不可变对象，只是字符串累积器。

---

### Q9：Spring FactoryBean 和普通 Bean 有什么区别？

**回答**：普通 Bean：Spring 直接实例化并注册到容器。FactoryBean：Spring 先实例化 FactoryBean 本身，然后调用 getObject() 创建真正的 Bean 对象注册到容器——容器中BeanName 对应的是 getObject() 返回的对象而非 FactoryBean 本身。如果需要获取 FactoryBean 本身，在 BeanName 前加 & 前缀。FactoryBean 是工厂方法模式的实现——每个 FactoryBean 创建一种类型的对象。典型应用：MyBatis 的 SqlSessionFactoryBean，它实现了 FactoryBean<SqlSessionFactory>，getObject() 中调用 SqlSessionFactoryBuilder.build(configuration) 创建 SqlSessionFactory 实例。

---

### Q10：设计模式在 Spring 源码中最核心的三种是什么？

**回答**：Spring 源码中最核心的三种设计模式是工厂、代理和模板方法。①工厂模式：BeanFactory/ApplicationContext 本身就是工厂，负责创建和管理所有 Bean；FactoryBean 是工厂方法模式的实现，让用户自定义 Bean 创建逻辑。②代理模式：Spring AOP 的 JDK 动态代理和 CGLIB 代理是整个 AOP 体系的基石——@Transactional、@Cacheable、@Async 都基于代理实现。③模板方法模式：JdbcTemplate、RestTemplate、RedisTemplate 统一了资源获取/释放的固定流程，只暴露操作接口给用户；AbstractApplicationContext.refresh() 定义了容器启动的固定12步骨架。这三种模式的组合构成了 Spring 框架的核心骨架。
