## 一、索引底层结构（必问硬核）

### **Q1** 为什么 MySQL InnoDB 用 B+ 树而不是 B 树？B+ 树比 B 树多了哪些关键特性？（从数据存储位置、叶子节点连接、IO 效率三个维度对比）
?
B+ 树和 B 树有三个关键区别。第一，数据存储位置不同。B 树是每个节点都存数据，包括非叶子节点。B+ 树只有叶子节点存数据，非叶子节点只存索引键值。这意味着 B+ 树的非叶子节点能存的索引条目远多于 B 树，同样高度的 B+ 树能索引更多数据，树更矮，磁盘 IO 次数更少。第二，叶子节点是否连接。B 树的叶子节点之间没有指针连接，做范围查询时需要在中序遍历中不断回溯父节点。B+ 树的所有叶子节点用双向链表串联在一起，范围查询时定位到起点后直接顺着链表往后扫就行，效率高出一个量级。第三，IO 效率。B 树的非叶子节点存了数据，每个节点能存的键值少，树更高，IO 次数多。B+ 树非叶子节点只存键值不存数据，扇出能力大，树更矮，且叶子节点链表适合磁盘顺序读。综合来看，B+ 树在范围查询和全表扫描上全面优于 B 树，所以数据库几乎都用 B+ 树。

### **Q2** B+ 树为什么比红黑树更适合做数据库索引？从磁盘 IO、树的高度、范围查询三个角度分析。
?
从三个角度看。磁盘 IO 角度：红黑树是二叉树，每个节点最多两个子节点，树的高度是 O(log₂n)——一百万数据大约 20 层，每次比较可能跨一个磁盘页，最坏情况一次查询 20 次 IO。B+ 树是多叉树，每个节点可以存成百上千个键值，一百万数据可能只要两到三层，一次查询只需两到三次 IO，差距是数量级的。树的高度角度：B+ 树的出度取决于磁盘页大小和键值大小。InnoDB 默认页 16KB，假设一个键值加指针占 16 字节，一个非叶子节点能存约 1000 个键值，那么三层 B+ 树理论上能索引 1000³ = 10 亿行数据。红黑树存同样数据需要约 30 层。范围查询角度：红黑树做范围查询需要在中序遍历里跳来跳去，节点之间不连续，随机 IO 严重。B+ 树叶子节点是双向链表，范围查询就是一次定位加上顺序扫描，磁盘顺序读写速度远快于随机读写。这就是数据库用 B+ 树的根本原因：磁盘 IO 主导性能，而 B+ 树是专门为磁盘优化设计的结构。

### **Q3** 为什么建议 InnoDB 表必须有主键？如果你不指定主键，InnoDB 会怎么做？`ROW_ID` 是什么？自增主键 vs UUID 做索引的性能差异？
?
InnoDB 的数据是按聚簇索引组织的，也就是数据本身存储在 B+ 树的叶子节点里，必须有一个排序的依据。如果用户指定了主键，就用主键作为聚簇索引的键。如果没指定主键，InnoDB 会找第一个 unique not null 的列作为聚簇索引键。如果连 unique 列都没有，InnoDB 会在后台自动生成一个隐藏的 6 字节的 ROW_ID 作为聚簇索引键。这个 ROW_ID 是全局递增的，但对用户不可见，也无法在查询中使用。为什么不推荐依赖自动生成的 ROW_ID 呢？因为它是隐藏的，你没法在查询里利用它，而且它在主从复制时可能不一致。自增主键和 UUID 的性能差异非常大。自增主键的值是递增的，每次插入新数据都在 B+ 树的最后一个叶子节点追加，不会引起页分裂和页内数据移动，写入性能高，且聚簇索引的页填充率高。UUID 是随机的，插入位置在 B+ 树中不确定，频繁触发页分裂——InnoDB 需要把满页的一半数据移到新页，产生大量随机 IO，而且分裂后的页填充率只有约 50%，空间利用率低。另外 UUID 占 36 字符或 16 字节（binary），比自增 bigint 的 8 字节大，二级索引叶子节点存的是主键值，主键越大会导致所有二级索引都变大，内存中能缓存的索引数据变少。所以强烈建议用自增 bigint 做主键。

### **Q4** 聚簇索引和非聚簇索引的区别？回表是什么意思？覆盖索引如何避免回表？写一条覆盖索引的 SQL 示例。
?
1. 聚簇索引就是数据本身按索引顺序存储，叶子节点存的是完整的行数据。InnoDB 的主键索引就是聚簇索引。非聚簇索引也叫二级索引，叶子节点存的是索引列的值加上主键值，不存完整行数据。
2. 回表指的是：通过二级索引查找时，先在二级索引的 B+ 树里找到对应的主键值，然后再拿着这个主键值回到聚簇索引的 B+ 树里查完整的行数据。这个过程要多扫描一棵 B+ 树，多了随机 IO，所以回表是性能损耗的主要来源。
3. 覆盖索引就是让查询需要的所有列都在索引里，不需要回表。比如表有字段 id、name、age、phone，建了联合索引 (name, age)，执行 SELECT name, age FROM user WHERE name = '张三'，查询需要的 name 和 age 都在索引里，直接从二级索引的叶子节点就能拿到，不用回表。EXPLAIN 的 Extra 列会显示 Using index，这就是覆盖索引的效果。

### **Q5** 联合索引 `(a, b, c)` 的最左前缀原则：以下查询哪些能走索引？`WHERE a=1`、`WHERE a=1 AND b=2`、`WHERE b=2`、`WHERE a=1 AND c=3`、`WHERE b=2 AND c=3`、`WHERE a>1 AND b=2`、`ORDER BY b`？
?
1. 联合索引 (a, b, c) 构建的 B+ 树先按 a 排序，a 相同再按 b 排序，b 相同再按 c 排序。所以最左前缀原则的本质是：只有从最左开始的连续匹配才能利用索引的有序性。
2. WHERE a=1：能用，匹配 a 列，走索引。
3. WHERE a=1 AND b=2：能用，匹配 a 和 b 两列。
4. WHERE b=2：不能用。索引是先按 a 排序的，没有 a 的约束，b 在索引里是乱序的，无法利用索引定位。
5. WHERE a=1 AND c=3：能部分用。能用索引定位到 a=1 的所有行，然后在这些行中过滤 c=3，但 c 这一列没法用索引过滤——因为 a=1 条件下 c 不是连续的（b 在中间跳过了），所以 key_len 只显示 a 的长度，Extra 会显示 Using index condition。
6. WHERE b=2 AND c=3：不能用。缺失 a，无法利用索引有序性。
7. WHERE a>1 AND b=2：能部分用。a>1 走范围扫描，但 b=2 没法用索引——因为 a 是一个范围，在这个范围内 b 不是有序的。索引只能用到 a 列，Extra 会出现 Using index condition。
8. ORDER BY b：不能用索引排序。没有 a 的等值约束，b 在整体索引里不是有序的，会出现 Using filesort。
9. 总结下来就是：最左前缀有等值匹配时，后续列才能利用索引。一旦中间列是范围查询，后续列的索引就会失效——这是最左前缀原则的延伸规则。

### **Q6** 索引失效的常见场景，至少说 8 种。`WHERE name LIKE '%abc'` 为什么不行？`!=`/`<>` 一定不走索引吗？
?
1. 常见索引失效场景有以下几种。第一，LIKE 以 % 开头——B+ 树按前缀排序，不知道 % 前面是什么就无法定位。第二，联合索引不满足最左前缀——跳过了最左列。第三，在索引列上使用函数——例如 WHERE YEAR(create_time) = 2024，索引里存的是原始值，函数转换后的值没法直接匹配。第四，隐式类型转换——varchar 列和数字比较时，MySQL 会把字符串转数字，等同于在列上应用了函数。第五，使用 OR 连接——如果 OR 的两边有一个列没建索引，整个查询可能就不走索引。第六，不等于操作——不是绝对不走，取决于优化器的判断。第七，IS NULL 和 IS NOT NULL——不是绝对不走，但大量 NULL 值时优化器可能选择全表扫描。第八，NOT IN 和 NOT EXISTS——通常不走索引。
2. WHERE name LIKE '%abc' 不走索引是因为 B+ 树的叶子节点按字典序排列，索引查找依赖前缀匹配来定位。'%abc' 表示任意字符开头，末尾是 abc，无法利用 B+ 树的有序性定位起点，只能全表扫描。而 'abc%' 可以——系统可以定位到以 abc 开头的第一条记录然后顺序扫描。
3. != 和 <> 不一定不走索引，取决于数据分布。如果某个不等于条件排除了大部分数据，只返回很少的行，优化器可能选择走索引。如果排除后还剩下大量数据，优化器认为回表代价太高会选全表扫描。这是基于统计信息的成本计算，不是绝对规则。

### **Q7** 字符串字段不加引号会发生什么？`WHERE phone = 13800000000`（phone 是 `varchar`）会走索引吗？隐式类型转换底层是怎么执行的？
?
1. 字符串字段不加引号会触发隐式类型转换。varchar 类型的 phone 列和整数 13800000000 比较时，MySQL 不是把整数转成字符串，而是把字符串转成数字——相当于在 phone 列上隐式执行了 CAST(phone AS UNSIGNED)。这就等同于在索引列上使用了函数，索引失效。所以这条 SQL 不会走 phone 列的索引，EXPLAIN 的 type 会是 ALL（全表扫描）。
2. 隐式类型转换的底层：MySQL 的类型转换规则是当字符串和数字比较时，将字符串按数字解析。如果字符串开头是数字，就截取前面的数字部分；如果开头不是数字，就转为 0。比如 '138abc' 转成 138，'abc' 转成 0。这个转换发生在 phone 列上，而不是比较值上，所以索引失效。把 SQL 改成 WHERE phone = '13800000000' 就能走索引了，因为两边都是字符串，直接按字符串比较。

### **Q8** `ORDER BY a, b` 和 `ORDER BY b, a` 在使用联合索引 `(a, b)` 时有什么区别？`ORDER BY` 怎么也讲究最左前缀？
?
1. 联合索引 (a, b) 的叶子节点按 a 排序，a 相同再按 b 排序。ORDER BY a, b 和索引的排序顺序完全一致，可以直接利用索引的有序性，不需要额外排序，Extra 不会有 Using filesort。ORDER BY b, a 与索引顺序不一致——在整体索引中 b 不是有序的（b 只在 a 相同时才有序），MySQL 无法利用索引顺序，必须把数据取出来在内存中重新排序，Extra 会出现 Using filesort。
2. ORDER BY 讲究最左前缀的原因和 WHERE 一样：索引的有序性是从最左列开始逐层保证的。ORDER BY 要想利用索引排序，必须满足：排序列的顺序和索引列顺序一致，中间不能跳过，且 ORDER BY 前的 WHERE 条件必须对前面的列有等值约束。比如 WHERE a=1 ORDER BY b，这可以用索引——因为 a=1 把数据锁定在一个连续范围内，在这个范围内 b 是有序的。如果 WHERE a>1 ORDER BY b，就不能用索引排序，因为 a 是一个范围，不同 a 值对应的 b 是分开排序的，整体不连续。

## 三、事务 ACID & 隔离级别

### **Q9** ACID 四个特性分別由什么技术保证？（undo log → 原子性、redo log → 持久性、MVCC+锁 → 隔离性、约束+事务 → 一致性）
?
1. 原子性由 undo log 保证。事务执行过程中每做一次修改，undo log 就记录修改前的旧值。如果事务回滚，MySQL 读取 undo log 把数据恢复到事务开始前的状态。undo log 的逻辑是"逆向操作"——insert 对应的 undo 是 delete，update 对应的 undo 是反向 update。
2. 持久性由 redo log 保证。事务提交时，修改的数据页不会立即刷盘，而是先把 redo log 写到磁盘（顺序写，很快）。即使系统崩溃，重启后重放 redo log 就能恢复已提交事务的修改。redo log 配合 WAL 机制（Write-Ahead Logging，先写日志再写数据），用顺序写替代随机写，同时保证崩溃恢复。
3. 隔离性由 MVCC 和锁共同保证。MVCC 通过 Read View 和 undo log 版本链实现快照读，让读不阻塞写、写不阻塞读。锁机制（行锁、间隙锁、临键锁）保证当前读的隔离，防止并发写冲突和幻读。
4. 一致性是 AID 三个特性共同保证的最终结果——原子性保证事务要么全做要么全不做，隔离性保证并发事务互不干扰，持久性保证提交后数据不丢。此外，外键约束、唯一约束、触发器等也在应用层面辅助保证业务一致性。

### **Q10** 四个隔离级别各自解决什么问题？脏读、不可重复读、幻读分别是什么？InnoDB 的可重复读能解决幻读吗？（能，但不完全能）
?
1. 四个隔离级别从低到高。READ UNCOMMITTED：啥也没解决，三个问题都存在。READ COMMITTED：解决了脏读。REPEATABLE READ：解决了脏读和不可重复读。SERIALIZABLE：三个全解决，但并发性能最差。
2. 脏读就是一个事务读到了另一个未提交事务修改的数据，后来那个事务回滚了，读到的数据其实是"脏"的、不存在的。不可重复读是同一个事务内两次相同的查询，读到的数据不一样——因为中间有其他事务修改并提交了。幻读是同一个事务内两次相同的范围查询，第二次多出了几行或少了几行——因为中间有其他事务 insert 或 delete 了范围内的数据并提交了。
3. InnoDB 的可重复读能解决大部分的幻读。快照读层面：MVCC 的 Read View 在事务第一次快照读时生成，之后整个事务期间都用这个 Read View，所以快照读不会看到其他事务提交的新数据，不会幻读。当前读层面：SELECT FOR UPDATE 和 UPDATE/DELETE 使用的是临键锁（Next-Key Lock），会在查询范围上加间隙锁，阻止其他事务在这个范围内插入数据，从而防止幻读。
4. 但有一个场景是解决不了的：事务 A 先快照读，事务 B insert 并提交，事务 A 再当前读（UPDATE 了 B 插入的那行）。此时快照读没看到新数据，但当前读把它更新了。之后事务 A 再快照读，发现多了一行自己更新的数据——这严格来说也符合幻读的定义。所以结论是：InnoDB RR 在绝大多数场景下解决了幻读，但极端情况仍有漏洞。

### **Q11** 什么是"当前读"和"快照读"？`SELECT`、`SELECT ... FOR UPDATE`、`INSERT`/`UPDATE`/`DELETE` 分别属于哪种？为什么 `FOR UPDATE` 能防止幻读但普通 `SELECT` 不行？
?
1. 当前读是读取数据的最新提交版本，并且读取时加锁，保证在事务结束前这个数据不会被其他事务修改。快照读是读取事务开始时的数据版本，基于 MVCC 的 Read View 和 undo log，不加锁，读的是历史快照。
2. 普通 SELECT 是快照读。SELECT FOR UPDATE 和 SELECT FOR SHARE 是当前读——会加排他锁或共享锁。INSERT、UPDATE、DELETE 都是当前读——插入前要检查唯一约束，修改前要读到最新数据来更新。
3. FOR UPDATE 能防止幻读是因为它加了临键锁。当事务执行 SELECT * FROM t WHERE id > 10 FOR UPDATE 时，InnoDB 不仅锁住了 id > 10 的已有行，还把这些行之间的间隙也锁住了。其他事务没法在这些间隙里插入数据，自然就幻读不了。而普通 SELECT 是快照读，不加锁也不阻塞其他事务的插入，所以不防止幻读——但在 RR 级别下，快照读基于事务开始时的 Read View，本身也读不到新的插入数据，所以快照读层面也不会出现幻读。

### **Q12** `READ COMMITTED` 和 `REPEATABLE READ` 在 MVCC 层面，`Read View` 的生成时机有什么区别？（RC：每次快照读生成 / RR：事务第一次快照读生成）
?
1. RC 级别下，每次执行快照读（普通 SELECT）都生成一个新的 Read View。这意味着每次 SELECT 都能看到其他事务已提交的最新数据。所以同一个事务内两次相同的 SELECT 可能返回不同结果，这就是不可重复读产生的原因。
2. RR 级别下，Read View 只在事务第一次执行快照读时生成一次，之后这个事务内的所有快照读都复用这个 Read View。这意味着整个事务期间读到的数据版本是一致的，不管其他事务怎么提交，本事务的快照读都看不到——这就是可重复读的实现原理。
3. 这个区别在源码层面就是 ReadView 对象创建和使用的时机：RC 级别每次调用快照读方法时创建新的 ReadView 并立即使用，RR 级别第一次创建后缓存起来，后续复用。

## 四、MVCC（必问源码级）

### **Q13** MVCC 依赖哪三个隐藏列？`DB_TRX_ID`、`DB_ROLL_PTR`、`DB_ROW_ID` 分别在什么时候写入？
?
1. InnoDB 每行数据有三个隐藏列。DB_TRX_ID 占 6 字节，记录最后一次修改（insert 或 update）这行数据的事务 ID。每次事务修改一行时，都会把这行的 DB_TRX_ID 更新为当前事务 ID。
2. DB_ROLL_PTR 占 7 字节，回滚指针，指向 undo log 中这行数据的上一个版本。当你更新一行时，旧版本被写入 undo log，新行里的 ROLL_PTR 指向这个 undo log 记录，形成版本链。这条链从当前最新版本一直串到最老版本，MVCC 就是顺着这条链找可见版本的。
3. DB_ROW_ID 占 6 字节，行 ID。只有当表没有显式主键也没有唯一非空索引时，InnoDB 才自动生成这个 ROW_ID 作为聚簇索引键。如果表有主键，这个隐藏列就不存在。ROW_ID 在 insert 时写入，此后不再改变。

### **Q14** `Read View` 的四个关键字段是什么？`m_ids`、`min_trx_id`、`max_trx_id`、`creator_trx_id`，一条 undo log 版本记录的可见性判断规则说清楚。
?
1. Read View 有四个关键字段。m_ids 是创建 Read View 时，当前系统中所有活跃的（未提交的）事务 ID 列表。min_trx_id 是 m_ids 中最小的那个事务 ID。max_trx_id 是系统下一个要分配的事务 ID，也就是已创建的最大事务 ID 加 1。creator_trx_id 是创建这个 Read View 的事务自己的 ID。
2. 一条 undo log 版本记录的可见性判断三步。第一步，如果版本的 DB_TRX_ID 等于 creator_trx_id，说明这个版本是当前事务自己修改的，可见。第二步，如果版本的 DB_TRX_ID 小于 min_trx_id，说明修改这个版本的事务在 Read View 创建前就已经提交了，可见。第三步，如果版本的 DB_TRX_ID 大于等于 max_trx_id，说明修改这个版本的事务是在 Read View 创建之后才开始的，不可见。如果 DB_TRX_ID 在 min_trx_id 和 max_trx_id 之间，就需要查 m_ids 列表：如果在活跃列表中，说明事务还没提交，不可见；如果不在活跃列表中，说明事务已经提交了，可见。
3. 如果当前版本不可见，就沿着 DB_ROLL_PTR 指向的 undo log 版本链往前找上一个版本，重复上述判断，直到找到一个可见的版本为止。

### **Q15** 如果事务 A 先插入一条记录（未提交），事务 B 用快照读能查到吗？事务 B 用当前读呢？undo log 版本链在插入时也会生成吗？
?
1. 事务 A 插入一条记录但未提交，这条记录上虽然有 DB_TRX_ID 标记为事务 A 的 ID，但行上的隐藏字段中还有一个 delete_flag 或通过 undo log 标记这个插入尚未提交。事务 B 的快照读：在 RR 级别下，如果事务 B 的 Read View 在事务 A 插入之前就生成了，那这条记录的 DB_TRX_ID 大于 B 的 max_trx_id，不可见。即使在 RC 级别下，由于事务 A 未提交，其事务 ID 在 m_ids 活跃列表中，也不可见。所以无论什么隔离级别，快照读都看不到未提交的插入。
2. 事务 B 的当前读：比如 SELECT FOR UPDATE，它也要遵循隔离级别。在 RC 和 RR 下，当前读看到的是已提交的最新版本——事务 A 还没提交，所以也看不到。但如果事务 B 执行的是无条件的 UPDATE（不加 WHERE 或 WHERE 条件覆盖了 A 插入的这行），那 UPDATE 本身是当前读，但会被事务 A 的行锁阻塞，直到 A 提交或回滚。
3. undo log 在插入时也会生成。INSERT 也会产生 undo log，但和 UPDATE 产生的 undo log 不同——INSERT 的 undo log 只在事务回滚时使用，事务提交后就可以立即删除，不需要给 MVCC 用。原因很简单：其他事务的快照读本来就不会看到未提交的插入数据，所以不需要保留 delete undo。而 UPDATE 的 undo log 在事务提交后不能立即删除，因为可能有其他活跃事务的快照读还需要看到旧版本。

## 五、日志系统（redo / undo / binlog）

### **Q16** `redo log` 和 `binlog` 的区别？（所属层、记录内容、写入时机、用途四个维度对比）
?
四个维度对比。所属层：redo log 是 InnoDB 存储引擎层独有的，binlog 是 MySQL Server 层的，所有存储引擎共用。记录内容：redo log 是物理日志，记录的是"在哪个数据页的哪个偏移量上做了什么修改"，比如"把表空间 0 第 7 页的偏移 200 处的值改为 1"。binlog 是逻辑日志，记录的是 SQL 语句或行的变更，比如"把 id=1 的 name 从'张三'改成'李四'"。写入时机：redo log 在事务执行过程中持续写入，binlog 在事务提交时一次性写入。用途：redo log 用于崩溃恢复——数据库挂了重启后重放 redo log 恢复已提交事务的修改。binlog 用于主从复制和数据恢复——从库重放 binlog 实现同步，也可以按时间点恢复数据。

### **Q17** 两阶段提交（2PC）的流程：`redo log prepare` → `binlog write` → `redo log commit`，如果每一步之间崩溃了，怎么恢复？为什么能保证一致性？
?
1. 两阶段提交保证的是 redo log 和 binlog 的数据一致性。流程分三步：第一步，事务执行时 redo log 先写入但不标记 commit，状态为 prepare。第二步，写入 binlog。第三步，把 redo log 的状态从 prepare 改为 commit，事务提交完成。
2. 崩溃恢复逻辑：如果崩溃发生在 redo log prepare 之后、binlog 写入之前：重启时扫描 redo log，发现处于 prepare 状态但没有对应的 binlog，说明 binlog 还没写，事务回滚。如果崩溃发生在 binlog 写入之后、redo log commit 之前：重启发现 redo log 处于 prepare 状态，且存在对应的 binlog（通过 XID 事件匹配），说明 binlog 已写成功，提交事务，把 redo log 改为 commit 状态。
3. 为什么能保证一致性？因为在任何时刻崩溃，恢复后 redo log 和 binlog 的状态都是一致的——要么都记录了（commit），要么都没记录（rollback）。这个机制保证了主库和从库数据一致：主库的 binlog 是主从数据同步的媒介，只要 binlog 和 redo log 同步，从库重放 binlog 就能和主库数据一致。

### **Q18** `undo log` 的两个作用？事务回滚和 MVCC 哪个依赖 `undo log`？`undo log` 什么时候被删除？（并不是事务结束就删）
?
1. undo log 有两个作用。第一，事务回滚——事务执行过程中每次修改前把旧值写入 undo log，如果事务回滚，按照 undo log 把数据恢复到修改前的状态。第二，MVCC——读取已提交数据时，通过 undo log 版本链找到对本事务可见的历史版本。
2. 两个功能都依赖 undo log。事务回滚依赖 insert undo 和 update undo 的前半部分（修改前值）。MVCC 只依赖 update undo，不依赖 insert undo——因为在 MVCC 的规则下，其他事务本来就不应该看到未提交的插入数据。
3. undo log 的删除时机分两种：INSERT 类型的 undo log 在事务提交后就可以删除——因为其他事务的不需要用它做 MVCC。UPDATE 类型的 undo log 不能立即删除，必须等所有可能引用它的事务都结束后才能清理——具体来说，InnoDB 有后台的 purge 线程，它会定期扫描 undo log，只有当某个 undo log 对应的 DB_TRX_ID 比当前所有活跃 Read View 中最老的 min_trx_id 还小时，才说明没有任何事务需要这个历史版本了，才会清理。所以一个频繁更新的大事务提交后，undo log 可能要很久才会被清理。

## 六、SQL 优化 & EXPLAIN

### **Q19** `EXPLAIN` 输出的 `type` 字段从好到坏依次是什么？`const`、`eq_ref`、`ref`、`range`、`index`、`ALL` 分别对应什么查询？
?
1. 从好到坏依次是：system > const > eq_ref > ref > range > index > ALL。system 和 const 是一个级别的特例。
2. const：通过主键或唯一索引的等值查询，最多返回一行。比如 WHERE id = 1。eq_ref：联表查询时，被驱动表使用主键或唯一索引做等值关联，每次关联只匹配一行。比如 JOIN ON a.id = b.id，b.id 是主键。ref：非唯一索引的等值查询，可能返回多行。比如 WHERE name = '张三'，name 有普通索引。range：索引范围扫描，比如 >、<、BETWEEN、IN、LIKE 'abc%'。index：全索引扫描，把整个索引树扫描一遍。比 ALL 好是因为索引通常比数据小，但仍然是全扫描。ALL：全表扫描，逐行遍历聚簇索引的所有叶子节点。
3. 通常优化目标是至少达到 range 级别，最好是 ref 或 const。出现 ALL 就需要重点关注了。

### **Q20** `EXPLAIN` 的 `Extra` 字段中，`Using index`、`Using index condition`（索引下推 ICP）、`Using where`、`Using filesort`、`Using temporary` 分别说明什么问题？哪个是一定要优化的？
?
1. Using index：发生了覆盖索引——查询需要的所有列都在索引里，不需要回表。这是最好的情况，说明索引设计合理。
2. Using index condition：索引下推（ICP）。意思是 MySQL 在存储引擎层对索引中的列做了条件过滤，而不是把所有匹配索引的行都返回 Server 层再过滤。比如 WHERE a=1 AND c=3 配合 (a, b) 索引，a=1 可以用索引定位，c 不在索引里，但 MySQL 5.6 之后会把 c=3 这个条件下推到存储引擎层，在回表之前先过滤一遍，减少回表次数。
3. Using where：Server 层对返回的行做了 WHERE 条件过滤。说明索引没能完全覆盖查询条件，部分过滤在 Server 层完成。
4. Using filesort：无法利用索引排序，需要在内存或磁盘中对结果集做排序。filesort 不一定用到磁盘文件，数据少时在内存中排序。但如果数据量大就会用到磁盘临时文件，性能会明显下降。
5. Using temporary：查询需要创建临时表来存储中间结果，通常是 GROUP BY、DISTINCT、UNION 或者 ORDER BY 和 GROUP BY 的列不一致时。Using filesort 和 Using temporary 这两个是必须优先优化的，因为它们意味着 MySQL 无法利用索引的有序性，需要额外的内存或磁盘操作，数据量一大就是性能杀手。

### **Q21** 深度分页 `LIMIT 1000000, 10` 为什么慢？延迟关联（子查询 + JOIN）怎么优化？游标分页（CURSOR）和传统分页有什么区别？
?
1. LIMIT 1000000, 10 慢的原因是 MySQL 必须扫描前 1000010 行，然后把前 1000000 行丢弃，只返回最后 10 行。offset 越大，需要扫描和丢弃的行越多，性能线性下降。即使走了索引，也要扫描索引中对应的行然后回表获取完整数据再丢弃。
2. 延迟关联的优化思路是：先在二级索引上定位到需要的主键，只取 10 个，然后用这 10 个主键去聚簇索引查完整数据。具体做法是，先 SELECT id FROM t WHERE 条件 ORDER BY id LIMIT 1000000, 10，拿到 10 个 id，然后 SELECT * FROM t WHERE id IN (那 10 个 id)。或者写成子查询加 JOIN 的形式。如果覆盖索引能包含排序和过滤条件就更优——索引扫描比回表快，避免了大量无用回表。
3. 游标分页和传统 offset 分页的区别：传统分页用 page 和 pageSize 算 offset，每次翻页都是重新扫描并跳过。游标分页用上一页最后一条记录的排序字段值作为起点，每次查询用 WHERE id > last_id ORDER BY id LIMIT 10，不需要跳过，直接定位。游标分页的优点是性能恒定，不受翻页深度影响。缺点是只能顺序翻页，不能跳页，而且排序字段必须是唯一且有序的（通常是自增主键或带唯一索引的时间戳）。实际项目中，APP 的滚动加载就用游标分页，后台管理的精确跳页才用 offset 分页。

### **Q22** 一个慢 SQL 的排查思路：从发现到优化，你完整的操作流程是什么？
?
完整流程分六步。第一步，确认慢 SQL，通过慢查询日志（slow_query_log）、performance_schema、或者监控系统（如 Prometheus + Grafana）找到耗时长的 SQL。第二步，用 EXPLAIN 分析执行计划，重点看 type 是否 ALL 或 index，key 是否为空，rows 是否过大，Extra 是否有 Using filesort 或 Using temporary。第三步，检查索引使用情况，看 WHERE、ORDER BY、GROUP BY、JOIN 的列是否都有合适的索引，联合索引的列顺序是否满足最左前缀原则，是否存在索引失效场景（函数、类型转换、前缀模糊匹配等）。第四步，分析数据量和数据分布，用 SHOW INDEX 看索引区分度（Cardinality），区分度太低的列不适合单独建索引；检查是否存在大量 NULL 值或数据倾斜。第五步，评估 SQL 写法本身——是否 SELECT * 导致无法覆盖索引，是否存在子查询可改写为 JOIN，是否有多余的 DISTINCT 或 ORDER BY，是否有隐式类型转换。第六步，优化后验证：用 EXPLAIN 对比优化前后的执行计划，实际执行看耗时是否下降，同时关注锁等待和 CPU 使用情况。如果单表优化已经到极限，再考虑分库分表、读写分离、缓存等架构层面的优化。

## 七、锁机制（InnoDB 锁深入）

### **Q23** InnoDB 的行锁实际上锁的是什么？为什么说"如果没有索引，行锁会升级为表锁"？
?
1. InnoDB 的行锁不是锁数据行本身，而是锁索引记录。当执行 UPDATE WHERE id = 1 时，InnoDB 在 id 索引上找到对应的索引记录，给这条索引记录加锁。如果有多个索引，行锁会加在所有使用到的索引上。
2. 如果没有索引，InnoDB 无法通过索引定位到具体的行——它必须扫描整个聚簇索引的所有记录来找到匹配的行。在扫描过程中，每扫描一条记录就加锁。但由于没有索引提供精确的过滤条件，最终所有记录都会被扫描并被加锁，实际效果等同于表锁。严格来说不是"升级"，而是"退化成表锁的效果"——因为扫描并锁住了所有行。这就是为什么不带索引的 UPDATE/DELETE 非常危险：它们会锁住全表，导致所有其他写操作阻塞。

### **Q24** 共享锁、排他锁、意向锁的区别？为什么需要意向锁（IS/IX）？它解决了什么问题？
?
1. 共享锁（S 锁）也叫读锁，允许多个事务同时持有共享锁，持有共享锁时可以读数据但不允许修改。排他锁（X 锁）也叫写锁，只允许一个事务持有，持有排他锁时可以读也可以写，其他事务不能获取任何锁。
2. 意向锁是表级锁，分意向共享锁（IS）和意向排他锁（IX）。在给一行加 S 锁之前，InnoDB 先给表加 IS 锁。在给一行加 X 锁之前，先给表加 IX 锁。
3. 为什么需要意向锁？想象一下，如果没有意向锁，一个事务要对整个表加 X 锁（比如 ALTER TABLE），它必须遍历表中的每一行检查是否有行级锁——在大表里这效率非常低。有了意向锁之后，事务只需检查表上是否有冲突的意向锁——如果表上有 IX 锁，说明有事务持有了行级排他锁，当前的表级 X 锁请求就加不上。这个检查是 O(1) 的，不需要遍历行。所以意向锁本质上是一个快速兼容性检查标记，解决了表锁和行锁共存的效率问题。

### **Q25** 记录锁（Record Lock）、间隙锁（Gap Lock）、临键锁（Next-Key Lock）分别锁什么范围？在哪个隔离级别下生效？
?
1. 记录锁锁的是单行索引记录，精确锁定一行。比如 WHERE id = 1 时，在 id=1 的索引记录上加锁，其他事务不能修改或删除这行。
2. 间隙锁锁的是索引记录之间的间隙，但不锁记录本身。比如有 id 为 1、5、10 三条记录，间隙锁可以锁住 (1,5)、(5,10) 这样的区间。间隙锁的作用是阻止其他事务在这些间隙中插入数据，用来防止幻读。
3. 临键锁是记录锁和间隙锁的组合，锁住一个左开右闭的区间，既锁住记录本身又锁住它前面的间隙。比如对 id=5 加临键锁，锁住的是 (1,5] 这个区间——id 在 1 到 5 之间（不含 1）的插入不允许，id=5 这一行也不能修改。
4. 记录锁在所有隔离级别下都可能使用（任何时候修改数据都加记录锁）。间隙锁和临键锁只在 RR 隔离级别下生效——因为 RR 需要解决幻读。RC 级别下只有记录锁，没有间隙锁和临键锁。

### **Q26** RR 隔离级别下，间隙锁如何防止幻读？如果是 RC 隔离级别，还有间隙锁吗？这个区别对你的项目选型有什么影响？
?
1. RR 级别下，间隙锁的工作原理：当一个事务执行 SELECT FOR UPDATE WHERE id > 5 AND id < 10 时，InnoDB 会在这个范围内加临键锁。如果 id 索引中 5 到 10 之间有记录 7，那它会锁住 (5,7] 和 (7,10) 两个区间——既锁住了现有的记录 7，又锁住了 5 到 7 和 7 到 10 之间的间隙。另一个事务想 INSERT id=8 时，发现 (7,10) 间隙被锁，阻塞等待。第一个事务提交后锁释放，第二个事务才能插入。这就防止了幻读。
2. RC 级别没有间隙锁。原因是间隙锁虽然防止了幻读，但降低了并发性能——间隙锁之间也会冲突，容易导致死锁和锁等待。RC 级别的设计就是在并发性能和隔离性之间选择了前者——接受可能发生幻读（不过对很多业务来说幻读的影响小于脏读和不可重复读）。
3. 选型影响：如果你的业务强依赖数据一致性，比如金融交易系统、账户余额变更，用 RR 配合间隙锁防止幻读。如果你的业务以高并发读写为主，对幻读不敏感，比如社交动态、日志记录，用 RC 更好——减少了间隙锁带来的死锁和锁等待。互联网项目多用 RC + 乐观锁/分布式锁来控制并发安全，而不是依赖数据库间隙锁。

### **Q27** 死锁是怎么产生的？`SHOW ENGINE INNODB STATUS` 怎么看死锁日志？两个事务分别 `UPDATE t SET c=1 WHERE id=1` 和 `UPDATE t SET c=2 WHERE id=2` 会死锁吗？什么情况下会？
?
1. 死锁产生的经典场景是两个事务互相持有对方需要的锁。事务 A 持有锁 L1，等待锁 L2；事务 B 持有锁 L2，等待锁 L1——谁都不让步，形成循环等待。
2. SHOW ENGINE INNODB STATUS 的输出中有一段 LATEST DETECTED DEADLOCK 部分，它显示了最近一次死锁的详细信息：包括死锁发生的时间、涉及的两个事务、每个事务持有的锁和等待的锁、被回滚的是哪个事务、最后执行的 SQL 是什么。根据这些信息可以还原死锁的形成过程。
3. 刚才那个例子里，两个事务分别 UPDATE 不同的行，互不影响，不会死锁。死锁需要访问顺序不一致。比如：事务 A 先 UPDATE id=1 再 UPDATE id=2，事务 B 先 UPDATE id=2 再 UPDATE id=1。执行顺序如下：A 锁了 id=1，B 锁了 id=2；A 试图锁 id=2，发现被 B 锁了，等待；B 试图锁 id=1，发现被 A 锁了，等待——死锁。InnoDB 检测到后，回滚其中一个事务（通常是持有锁较少的事务），另一个继续执行。
4. 避免死锁的方法：访问资源的顺序保持一致（所有事务都先操作 id 小的再操作 id 大的）；缩小事务粒度，尽快提交释放锁；尽量使用索引减少锁范围；在 RR 级别下考虑降级到 RC 去掉间隙锁。

## 八、Buffer Pool & Change Buffer

### **Q28** Buffer Pool 里有什么？Free List、LRU List（young/old 分区）、Flush List 分别干什么？
?
1. Buffer Pool 是 InnoDB 的内存缓存区，用来缓存数据页和索引页，避免每次读写都访问磁盘。它里面维护了三个关键的链表。
2. Free List：存放空闲的缓冲页。当需要读取一个新页面到内存时，从 Free List 中取一个空闲页来装载。如果 Free List 空了，就需要从 LRU List 中淘汰页面腾出空间。
3. LRU List：管理已被使用的缓冲页，按最近使用时间排序。InnoDB 的 LRU 做了 young/old 分区优化——链表前 5/8 是 young 区（热数据），后 3/8 是 old 区（冷数据）。新读入的页面先放入 old 区的头部，只有当这个页面在 old 区中被再次访问时，才移入 young 区。这样做是为了防止一次全表扫描把热数据全部挤出缓存——全表扫描的页面只会短暂停留在 old 区然后被淘汰，不影响 young 区的热数据。
4. Flush List：管理已被修改但还没写入磁盘的脏页。这些页按它们第一次被修改的时间（oldest_modification）排序。后台线程定期从 Flush List 中取出最老的脏页写入磁盘，完成后再移回 LRU List 并标记为干净页。Checkpoint 机制也依赖 Flush List 来确定哪些 redo log 可以被覆盖。

### **Q29** Change Buffer 是什么？对什么类型的操作有优化效果？为什么唯一索引的写操作用不了 Change Buffer？
?
1. Change Buffer 是 Buffer Pool 的一部分，用来缓存对二级索引的修改操作。当更新一个二级索引页时，如果这个页不在 Buffer Pool 中，InnoDB 不会立即从磁盘读入这个页，而是先把修改操作记录在 Change Buffer 里。等将来这个页因为其他原因被读入 Buffer Pool 时，再应用 Change Buffer 中的修改，把两者合并。这样就避免了一次磁盘随机读，提升了写入性能。
2. 对写多读少的场景效果最好——比如日志表、历史记录表，插入频繁但查询少，大量的二级索引页可能很久都不会被读到内存中，用 Change Buffer 就能省下大量磁盘 IO。
3. 唯一索引用不了 Change Buffer 的原因是唯一性约束。插入或更新一条数据时，必须检查唯一索引的值是否已存在。这个检查必须读取索引页——如果页在内存中就检查；不在内存就必须从磁盘读入。既然索引页已经被读入内存了，就没必要再用 Change Buffer 缓存了。所以唯一索引的修改操作直接绕过 Change Buffer，该读盘就读盘。这也是为什么在写密集场景下，非必须的唯一索引可以适当去掉。

## 九、MySQL 8.0 新特性（拉开分差）

### **Q30** MySQL 8.0 的原子 DDL（Atomic DDL）是什么？`ALTER TABLE` 中途失败了，会半途留下脏字段吗？
?
原子 DDL 是 MySQL 8.0 引入的特性，保证 DDL 操作的原子性——要么完整执行，要么完全回滚，不会处于中间状态。在 8.0 之前，如果 ALTER TABLE 中途失败（比如磁盘满了），可能会留下一个半修改的表结构——字段加了一半、索引建了一半，非常难处理。8.0 之后，ALTER TABLE 的整体操作被封装在了一个事务中，InnoDB 的数据字典表来记录 DDL 的状态。如果 DDL 失败，MySQL 会自动回滚所有已执行的步骤，表结构恢复到 DDL 执行前的状态，不会留下中间产物。比如 ALTER TABLE ADD COLUMN 失败了，新字段不会残留；RENAME TABLE 失败了，表名恢复原样。

### **Q31** MySQL 8.0 的不可见索引（Invisible Index）和降序索引（Descending Index）各有什么作用？不可见索引用在什么场景？
?
1. 不可见索引：创建索引时可以指定 INVISIBLE 关键字，这个索引对优化器不可见——查询不会自动使用它。但索引本身仍然会被维护（INSERT/UPDATE/DELETE 时索引依旧更新）。主要用在两个场景。第一，安全删除索引：想删一个索引但不确定对性能的影响，先设为不可见观察，确认没有查询变慢后再真正删除。反悔了随时改回可见，不需要重建索引。第二，测试索引效果：想验证新建的索引是否真正改善了查询，先创建为不可见，然后通过 USE INDEX 或 SET optimizer_switch 强制走这个索引做测试对比。
2. 降序索引：MySQL 8.0 之前，虽然 SQL 语法支持索引列指定 DESC，但实际存储都是升序的，DESC 只是被忽略。8.0 真正支持了降序索引，创建索引可以指定列是升序还是降序。这带来的好处是：配合 ORDER BY a ASC, b DESC 的查询时，如果索引是 (a ASC, b DESC)，索引的排序方向和查询完全一致，避免额外的 filesort 排序。这在多列混合排序的场景中能显著提升性能。

### **Q32** MySQL 8.0 窗口函数（`ROW_NUMBER()`/`RANK()`/`DENSE_RANK()`）和 CTE（`WITH AS` 公用表表达式）有什么用？写一个"每个部门工资前三名"的 SQL。
?
1. 窗口函数可以在不改变结果集行数的情况下，对每一行做基于分组窗口的计算。ROW_NUMBER() 给每个分组内的行分配唯一序号，有相同值也不跳号。RANK() 相同值给相同序号，下一个不同值跳过被占用的号。DENSE_RANK() 相同值给相同序号，下一个不同值连续不跳号。
2. CTE 是公用表表达式，用 WITH AS 定义临时的结果集，可以在后续查询中像表一样引用。优点是让复杂 SQL 的结构更清晰——把多步计算拆成多个 CTE 分步定义，比嵌套多层子查询可读性好得多。而且 CTE 支持递归，可以用来查树形结构（比如组织架构、评论嵌套）。
3. 每个部门工资前三名的 SQL：
4. WITH ranked AS (
	SELECT 
    department_id, 
    employee_name, 
    salary,
    DENSE_RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rk
	FROM employee
	)
5. SELECT department_id, employee_name, salary, rk FROM ranked WHERE rk `<= 3;
6. 这里用 DENSE_RANK 而不是 ROW_NUMBER 的原因是：如果第二和第三工资一样，DENSE_RANK 会让它们并列第二，第三名变成第四名；ROW_NUMBER 则会把相同工资的人随机排先后，可能漏掉同名次的。具体用哪个取决于业务需求。

## 十、实战场景

### **Q33** 一个 5000 万行的大表，要加一个字段（`ALTER TABLE ADD COLUMN`），直接执行会锁表吗？如何安全地在线上加字段？
?
1. 直接执行 ALTER TABLE ADD COLUMN 的行为取决于 MySQL 版本和具体操作。MySQL 5.6 之前，ALTER TABLE 会锁表——创建一个新表，把数据从旧表复制过去，期间整个表不可写。5.6 引入了 Online DDL，部分操作支持在线执行不锁表。ADD COLUMN（不加默认值或默认值为 NULL）在 5.6+ 是 Online DDL，只需在开始和结束时有短暂的元数据锁，主体过程允许读写。但 ADD COLUMN 如果设置了非 NULL 默认值且不是常量，仍需锁表复制数据。5000 万行的表，就算 Online DDL 也会产生大量的磁盘 IO、redo log 和主从延迟，对线上服务影响依然很大。
2. 安全方案有三种。第一种，用 MySQL 自带 Online DDL，配合 ALGORITHM=INPLACE, LOCK=NONE 参数，同时用 pt-online-schema-change 或 gh-ost 来分担风险。第二种，pt-online-schema-change 工具：它创建一个新表，在新表上执行 ALTER 操作，然后在旧表上建触发器，把增量数据同步到新表，最后在低峰期做一次切换——RENAME TABLE 原子操作替换表名。过程中有短暂的写锁但非常快，对业务影响极小。第三种，gh-ost：和 pt-osc 类似但不用触发器，而是把自己伪装成从库读取 binlog 来同步增量，对主库负载更友好。
3. 生产环境强烈建议用 pt-osc 或 gh-ost，它们有更完善的限速、暂停和回滚机制。最稳妥的流程是：先在测试环境验证 → 业务低峰期执行 → 设置合理的限速值 → 监控主从延迟。

### **Q34** 分库分表后，跨分片的 `ORDER BY time DESC LIMIT 10` 怎么实现？如果按 `user_id` 分片，现在要按 `order_time` 排序查所有用户的最近 10 单，怎么办？
?
1. 跨分片排序的本质问题是：数据分散在多个分片上，每个分片只能保证自己内部的有序性，无法保证全局有序。ORDER BY time DESC LIMIT 10 的典型解法是：从每个分片各取满足条件的 time 最大的 10 条记录（共 N 个分片就是 N×10 条），然后在应用层或中间层对这 N×10 条记录做归并排序，取最终的 top 10。这个方案的问题在于，如果某个分片没有满足条件的数据，可能遗漏——需要确保每个分片都返回了数据。
2. 如果按 user_id 分片但需要按 order_time 排序，这是典型的"分片键和查询维度不一致"问题。解法有几种。第一，建立一个按 order_time 组织的冗余表或索引表，用 order_time 作为分片键，但这会导致数据双写和一致性维护成本。第二，用 Elasticsearch 或 ClickHouse 等搜索引擎+分析引擎做宽表同步——写入时把订单数据同时写入 ES，查询时走 ES 做分页排序，ES 天然支持跨分片排序。第三，如果数据量不是特别大，用分布式数据库的中间件（如 ShardingSphere）它可以自动完成上述的归并排序逻辑。第四，业务上避规——如果最近 10 单的场景非常高频，可以考虑用 Redis 的 sorted set 维护每个用户的最近订单，按 order_time 排名，跨用户场景再做归并。这个场景没有完美的通用解，通常从架构层面用异构索引（ES/Redis）来支撑非分片键的查询。

### **Q35** 主从延迟的原因有哪些？你怎么监控主从延迟？如果业务能容忍 500ms 延迟，但偶尔会到 5 秒，你怎么做"读写分离"下的兜底？
?
1. 主从延迟的原因有几种。第一，主库写入并发高，从库单线程回放 binlog 跟不上——这是最常见的瓶颈，MySQL 5.7 后可以用并行复制（基于组提交）缓解。第二，大事务——一个事务修改几百万行，主库执行快，但从库回放慢，延迟突然飙升。第三，从库硬件差或共享资源——从库和主库配置不同，或者从库还承担了部分读流量导致 IO/CPU 争抢。第四，网络延迟——主从跨机房部署，binlog 传输有延迟。第五，DDL 操作或表锁——ALTER TABLE 在主库执行导致大量 binlog，从库回放时阻塞了其他事务的回放。
2. 监控主从延迟：常用的指标是 SHOW SLAVE STATUS 中的 Seconds_Behind_Master 字段。但要注意，这个值是从库的 IO 线程读到的主库 binlog 时间戳和从库 SQL 线程当前回放到的 binlog 时间戳的差值，它是近似值，不能精确到毫秒。更精确的做法是用 pt-heartbeat，它在主库写入心跳记录（带时间戳），在从库读取这个时间戳和当前时间对比。还可以通过业务监控——写入一条测试数据看从库多久能读到。
3. 读写分离的兜底策略：正常情况下读写分离没问题。当延迟超过阈值（比如 500ms）时，有几种兜底手段。第一，关键业务强制走主库——刚写入的数据立即查询的场景，用一个 ThreadLocal 标记，标记期间所有读走主库。第二，设置从库访问的超时和降级——如果从库查询超过一定时间没返回，切换到主库重试。第三，应用层延迟感知——写操作返回时把主库的 binlog 位点或时间戳带给客户端，后续查询从库时带上这个标记，检查从库是否已同步到该位点，没到就等待或切主库。第四，对于对延迟不敏感的业务（比如历史订单查询、报表），继续走从库但提示"可能有短暂延迟"。

### **Q36** 一个交易系统的核心表，QPS 10000，UPDATE 占 60%，怎么做高并发下的库存扣减？（`UPDATE ... SET stock = stock - 1 WHERE stock > 0` → 乐观锁、Redis 预热扣减 + 异步写 MySQL）
?
1. 这个场景的核心瓶颈不是 MySQL 扛不住 10000 QPS——单机 MySQL 纯 update 十几万 QPS 没问题——真正的问题是行锁竞争。UPDATE SET stock = stock - 1 WHERE stock > 0 会在这行加排他锁，所有对这个商品的扣减请求串行化，一个时刻只有一个线程能执行，吞吐量受限于单行处理的延迟。热点商品会把这个问题放大到极致。
2. 方案设计分三层。第一层，Redis 预扣减。把库存预热加载到 Redis。扣库存时在 Redis 中执行 DECR 原子操作，先判断库存是否大于 0。Redis 单线程模型天然串行化扣减，不存在锁竞争。这一层能扛住极高并发。第二层，异步同步到 MySQL。扣减成功后，不立即更新 MySQL，而是写入一个扣减流水到消息队列（Kafka 或 RocketMQ）。消费者异步批量更新 MySQL——比如每 100ms 把累积的扣减量合并成一次 UPDATE。这样 MySQL 的压力大幅降低，热点问题也转移到 Redis 了。第三层，MySQL 作为最终数据源。定时任务周期性把 Redis 中的库存量和 MySQL 对比校准，防止因 Redis 故障或消费延迟导致数据偏差。下单时真正扣减走的还是 Redis，只有退款、补货等低频操作直接操作 MySQL。
3. MySQL 层面也需要优化。库存表拆分为库存流水表和库存余量表，余量表只存储当前库存量，流水表记录每次变更明细。余量表不用索引或者只用主键，减少写放大。UPDATE 时加乐观锁版本号或时间戳防止并发覆盖。如果商品特别多，可以按商品 ID 分库分表，把热点分散到多个库上。
4. 总结：这套方案把热点行锁从 MySQL 剥离到 Redis，MySQL 只做异步批量写入和最终对账。极端流量下还可以在 Redis 前面加本地缓存（Caffeine 或 Guava Cache），进一步减少 Redis 的网络开销，但这会引入更大的数据一致性问题，需要仔细评估。
