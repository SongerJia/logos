### 为什么这个模块重要

**SPI（Service Provider Interface）是 Dubbo 可扩展性的灵魂**，不理解 SPI 就看不懂 Dubbo 的源码设计。同时，Dubbo 的整体架构决定了你对所有 RPC 框架的理解深度。

### 知识点表

|序号|知识点|重要度|笔记三层建议|跨模块关联|
|---|---|---|---|---|
|1.1|**Dubbo 整体架构（十层模型）**|🔴必背|① 十层：service→config→proxy→registry→cluster→monitor→protocol→exchange→transport→serialize ② 核心流程：消费者引用服务→生成代理→注册到注册中心→发起调用→负载均衡→调用提供者→返回结果 ③ 面试：画一下 Dubbo 的整体架构图，并解释各层职责|→ Spring Cloud 架构（对标学习）|
|1.2|**Dubbo SPI vs Java SPI**|🔴必背|① Java SPI 缺点：全部加载（浪费）、无排序/优先级、无AOP/IoC支持 ② Dubbo SPI 改进：按需加载（@SPI注解 + META-INF/dubbo/接口全限定名）、@Adaptive自适应扩展、@Activate自动激活、IOC/AOP支持 ③ 面试：Dubbo SPI 和 Java SPI 有什么区别？为什么 Dubbo 不用 Java SPI？|→ Java SPI（M4 Java基础）/ Spring Factories（类似机制）|
|1.3|**@SPI & @Adaptive & @Activate 三注解**|🔴必背|① @SPI：标记扩展点，value指定默认实现 ② @Adaptive：自适应扩展，运行时动态选择实现（如 Transport 选 Netty 还是 Mina） ③ @Activate：自动激活（如 Filter 按 Group 自动加载） ④ 面试：解释这三个注解的作用和使用场景|→ Spring 条件注解（@Conditional 类比）|
|1.4|**ExtensionLoader 加载机制**|🟡应掌握|① 加载流程：读取配置文件→缓存实现类→按需实例化→IOC注入依赖→AOP包装 ② 双检查锁保证线程安全 ③ 面试：Dubbo 的 ExtensionLoader 是怎么实现按需加载的？|→ 单例模式（Double-Check）/ Spring BeanFactory（类比）|
|1.5|**Dubbo 与 Spring Cloud 技术栈对比**|🟡应掌握|① **服务调用方式**：Dubbo（RPC，基于 Netty）+ Feign（REST，基于 HTTP） ② **注册中心**：Dubbo（ZK/Nacos/Consul）vs Spring Cloud（Eureka/Nacos/Consul） ③ **配置方式**：Dubbo（XML/API/注解）vs Spring Cloud（纯注解/Boot风格） ④ 面试：你们项目为什么选 Dubbo 不选 Spring Cloud？或者反过来？|→ Spring Cloud Alibaba（技术选型）/ Nacos（注册中心）|

> **🏗️ 架构追问**：如果让你设计一个"更好的 SPI 机制"，你会增加什么能力？提示：Dubbo SPI 目前不支持热卸载/热更新，能改进吗？
