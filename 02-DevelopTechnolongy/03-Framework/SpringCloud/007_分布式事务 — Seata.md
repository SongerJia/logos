|知识点|笔记时重点写什么|
|---|---|
|**分布式事务问题来源**|热 单机数据库的事务 ACID 只在本地有效，跨服务调用时每个服务各自提交自己的事务，无法保证整体原子性。经典例子：订单扣款但库存没扣（或反过来）|
|**Seata AT 模式（默认 & 最常用）**|热 **核心考点**。一阶段：执行业务 SQL 并解析 SQL 记录 before image 和 after image（ undo log ）→ 提交本地事务并释放锁。二阶段：正常情况异步删除 undo log；异常情况回滚（用 undo log 反向还原）。**无锁设计，性能好，但有脏写风险**|
|**Seata TCC 模式**|核 Try（预留资源：冻结金额 / 冻结库存）→ Confirm（确认使用预留资源）→ Cancel（释放预留资源）。侵入性强（需要改造业务接口），但性能和可靠性优于 AT。适用于强一致性和高并发场景|
|**Seata SAGA 模式**|长事务解决方案。每个事务参与者正向操作 + 补偿操作。编排式（中央协调器调度）vs 协作式（事件驱动，各自通知）。适用于业务流程长的场景（如订票：机票+酒店+租车）|
|**Seata XA 模式**|强一致性，基于数据库 XA 两阶段提交协议。性能最差（持有数据库锁时间长），但对业务零侵入。适用于传统遗留系统迁移|
|**Seata Server（TC）架构**|TM（事务管理器，发起方）→ RM（资源管理器，参与者）→ TC（事务协调器，Seata Server）。TC 负责协调全局事务的提交/回滚，维护全局锁|
|**AT 模式的脏写问题与全局锁**|热 AT 的一阶段释放了本地锁，如果此时另一个全局事务修改同一行数据就会产生脏写。Seata 用**全局锁**解决这个问题（TC 端维护的全局锁表）。但全局锁也有性能代价|
|**Seata 高可用部署**|TC 需要 DB 或 Redis 存储（存储事务会话/全局锁）。至少部署 3 个 TC 节点 + MySQL 集群 / Redis Cluster。HA 模式支持|

> **笔记技巧**：Seata AT 的一阶段和二阶段流程必须画成两张交互时序图。一阶段画清楚「SQL 解析 → undo log 记录 → 本地提交」的过程，二阶段画清楚「正常提交删除 undo log」和「异常回滚反向还原」两条路径。这是分布式事务中最常考的图。
