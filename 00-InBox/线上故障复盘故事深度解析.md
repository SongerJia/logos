# 第一章 故障复盘方法论

## 1.1 什么是故障复盘

**定义**：故障复盘（Post-mortem / Incident Review）是在故障修复后，对故障发生过程进行系统性回顾、根因分析和改进措施制定的活动。

### 故障复盘的核心公式

```
故障复盘 = 时间线还原 + 根因分析 + 改进措施 + 知识沉淀
```

**关键原则**：

| 原则 | 含义 | 反面示例 |
|------|------|----------|
| **无指责文化** | 找系统漏洞，不找人背锅 | "谁写的这Bug？" |
| **数据驱动** | 用监控/日志/链路追踪说话，不凭感觉 | "我觉得是Redis的问题" |
| **5 Why 追问** | 连续追问5层找到真正根因 | "CPU高→重启就好了" |
| **可执行改进** | 每条改进必须有人负责、有deadline | "以后注意点" |
| **全量公开** | 故障报告全员可见，避免同类故障再犯 | 只在小组内口头传达 |

## 1.2 故障复盘标准流程

### 六步复盘法

```
┌──────────┐    ┌──────────┐    ┌──────────┐
│ 1.确认事实 │ → │ 2.还原时间 │ → │ 3.根因分析 │
│  收集日志   │    │  线（Timeline）│    │  5 Why追问  │
└──────────┘    └──────────┘    └──────────┘
                                       ↓
┌──────────┐    ┌──────────┐    ┌──────────┐
│ 6.知识沉淀 │ ← │ 5.复盘会议 │ ← │ 4.改进措施 │
│  文档/培训  │    │  团队Review │    │  Action Item│
└──────────┘    └──────────┘    └──────────┘
```

**Step 1 — 确认事实**：
- 收集告警记录、监控图表、日志文件、用户反馈
- 确认故障影响面：影响用户数、影响时长、业务损失
- 确认恢复时间点：何时发现、何时响应、何时止血、何时完全恢复

**Step 2 — 还原时间线**：
- 按分钟级还原从"第一个异常信号"到"完全恢复"的全过程
- 格式：`HH:MM — 事件描述 — 操作人 — 处理动作 — 结果`

**Step 3 — 根因分析（5 Why）**：

```
现象：订单接口超时率飙升
  ↓ Why1: 为什么超时？→ 数据库连接池耗尽
  ↓ Why2: 为什么连接池耗尽？→ 大量慢查询占住连接
  ↓ Why3: 为什么有大量慢查询？→ 新上线的查询缺少索引
  ↓ Why4: 为什么缺少索引没被发现？→ Code Review没检查SQL
  ↓ Why5: 为什么CR不检查SQL？→ 没有SQL审查规范和自动化检查工具
  ✓ 根因：缺乏SQL审查规范 + 缺少自动化索引检查工具
```

**Step 4 — 改进措施（Action Item）**：
- 每条改进必须有：**负责人 + Deadline + 验证方式**
- 分层改进：立即修复 → 短期加固 → 长期架构优化

**Step 5 — 复盘会议**：
- 参与人：故障处理人 + 相关系统负责人 + 架构师 + 业务方
- 重点讨论：时间线是否完整？根因是否到位？改进是否可执行？
- 产出：故障复盘报告文档

**Step 6 — 知识沉淀**：
- 故障复盘报告存入知识库（Wiki/Confluence）
- 关键教训纳入团队培训
- 技术改进纳入架构演进路线
- 告警规则补充到监控系统

## 1.4 故障等级分级标准

| 等级 | 定义 | 影响面 | 响应要求 | 示例 |
|------|------|--------|----------|------|
| **P0** | 核心业务完全不可用 | 全量用户/核心交易 | 5分钟响应，30分钟恢复 | 支付接口全挂 |
| **P1** | 核心业务部分受损 | 大量用户/重要功能 | 15分钟响应，1小时恢复 | 下单成功率降至50% |
| **P2** | 非核心业务受损 | 少量用户/次要功能 | 30分钟响应，4小时恢复 | 搜索结果延迟 |
| **P3** | 体验性降级 | 极少用户/不影响主流程 | 当日处理 | 日志显示异常 |

## 1.5 故障复盘的面试价值

**为什么面试官爱问故障**：

```
面试官思维链：
  你经历过线上故障 → 你真的在生产环境工作过
  你能复盘故障 → 你有系统性思维，不是只会重启
  你有改进措施 → 你能从错误中学习，推动团队进步
  你讲得清晰 → 你的沟通能力和技术深度都OK
```

**面试回答框架**：

```
一句话概述 → 时间线(发现→止血→根因→修复) → 根因分析(5 Why) → 改进措施 → 个人反思
```

> **黄金法则**：讲故障时，永远把"我学到了什么"放在"故障有多严重"后面。面试官想知道的是你的成长，不是你的灾难。

| **缓存问题** | 穿透/击穿/雪崩/不一致 | DB压力飙升/数据错 | 监控/日志 | ⭐⭐⭐⭐ |

| **业务逻辑** | 数据状态不一致/幂等失败/流程死循环 | 数据异常/业务投诉 | 日志/链路追踪 | ⭐⭐⭐⭐ |

## 2.2 故障传播链

**大多数线上故障不是单一原因，而是连锁反应**：

```
真实故障传播示例：

新功能上线（缺少索引）
    ↓
慢查询增多（单次3s→15s）
    ↓
数据库连接池耗尽（200连接全被占）
    ↓
订单接口超时（等不到连接）
    ↓
用户重试加剧（前端5秒超时自动重试）
    ↓
流量翻倍→雪崩（更多请求→更多慢查询→更多连接占满）
    ↓
全局不可用（Redis/MySQL/应用全层雪崩）
```

**关键洞察**：找到传播链上的**第一个环节**，而不是最后一个表现。CPU飙高可能是结果，不是原因。

## 3.1 故障故事一：Full GC 导致支付接口间歇性超时

### 一句话概述

支付系统在高峰期出现间歇性超时，根因是本地缓存的大Value对象频繁晋升老年代触发Full GC，每次GC暂停0.5~2秒导致接口超时。

### 故障背景

- **系统**：电商支付系统，日均50万笔订单
- **架构**：Spring Boot + Redis集群 + MySQL主从 + 本地Caffeine缓存
- **正常指标**：支付接口P99 < 200ms，TPS峰值2000

### 时间线

```
14:00 — 业务高峰开始，支付量从800 TPS逐步上升
14:15 — 监控告警：支付接口P99从200ms跳到800ms
14:20 — 告警升级：P99突破2s，超时率5%
14:25 — 运维查看：应用CPU正常，Redis/MySQL正常，但GC日志显示每隔30秒一次Full GC
14:30 — 初步定位：每次Full GC暂停1.5s，与接口超时时间完美吻合
14:35 — 开发介入：jstat确认Eden区4MB→老年代每次GC增长50MB，大对象直接进老年代
14:40 — 分析堆内存：jmap -histo 发现 Top 1 对象是 LocalCacheValue（4KB~50KB不等）
14:45 — 根因确认：Caffeine缓存存了大Value（完整订单详情JSON 50KB），年轻代4MB放不下直接进老年代
14:50 — 紧急止血：关闭本地缓存开关（Nacos配置中心），全走Redis，超时率立即回落
15:00 — 完全恢复：P99回到200ms，业务正常
```

### 5 Why 根因分析

```
现象：支付接口间歇性超时，P99达2s
  ↓ Why1: 为什么超时？→ JVM Full GC暂停1.5s，STW期间所有线程阻塞
  ↓ Why2: 为什么频繁Full GC？→ 老年代快速增长，每30s触发一次
  ↓ Why3: 为什么老年代增长快？→ 大对象跳过年轻代直接进老年代
  ↓ Why4: 为什么有大对象？→ Caffeine本地缓存存储了完整订单详情JSON（50KB/条）
  ↓ Why5: 为什么本地缓存存50KB的Value？→ 缓存设计时没考虑Value大小，直接把整个对象塞进去
  ✓ 根因：本地缓存Value过大（50KB），超出年轻代容量，直接晋升老年代触发频繁Full GC
```

### 修复与改进

| # | 改进项 | 类型 | 负责人 | Deadline | 状态 |
|---|--------|------|--------|----------|------|
| 1 | 关闭本地缓存开关（Nacos配置） | 立即止血 | 运维 | 当日 | ✅ |
| 2 | Caffeine只缓存轻量摘要（key字段，<1KB） | 短期修复 | 开发A | 3天 | ✅ |
| 3 | JVM参数调优：年轻代从4MB扩到256MB | 短期修复 | 开发B | 3天 | ✅ |
| 4 | 缓存Value大小限制注解（@CacheMaxSize 1KB） | 中期 | 架构组 | 2周 | ✅ |
| 5 | GC监控告警：Full GC频率>2次/min告警 | 中期 | 运维 | 1周 | ✅ |
| 6 | 代码规范：本地缓存Value不超过4KB | 长期 | 技术委员会 | 1月 | ✅ |

### 面试讲法（3分钟版本）

```
"我经历过一次支付接口间歇性超时的故障。高峰期P99从200ms飙升到2s，超时率5%。

排查过程：首先确认CPU、Redis、MySQL都正常，但GC日志发现每30秒一次Full GC，
暂停1.5s，与超时时间完全吻合。进一步用jstat发现年轻代只有4MB，大对象（50KB的
订单详情JSON）直接跳过年轻代晋升老年代，导致频繁Full GC。

根因：Caffeine本地缓存设计时没考虑Value大小，把完整订单JSON 50KB直接缓存，
超出4MB年轻代容量直接进老年代。

止血：通过Nacos配置中心关闭本地缓存，全走Redis，5分钟恢复。
长期修复：本地缓存只存轻量摘要（<1KB），年轻代扩到256MB，增加GC频率告警，
并制定了缓存Value大小规范不超过4KB。

这次故障让我深刻理解：本地缓存不是'啥都往里塞'，Value大小直接影响GC行为。
后面我们团队还做了缓存规范的代码检查工具。"
```

## 3.2 故障故事二：MySQL 死锁导致批量下单失败

### 一句话概述

秒杀活动期间批量下单失败，根因是两个批量 INSERT 事务在唯一索引上形成交叉锁依赖，触发 InnoDB 死锁检测自动回滚其中一个事务。

### 故障背景

- **系统**：电商秒杀系统，秒杀活动每分钟10万次下单请求
- **架构**：Spring Cloud + RocketMQ异步下单 + MySQL主从
- **订单表**：`order` 表有唯一索引 `UNIQUE idx_user_sku(user_id, sku_id)` 防重复下单

### 时间线

```
10:00:00 — 秒杀活动开始，流量涌入
10:00:30 — MQ消费端批量处理下单请求，每批50条
10:01:00 — 告警：下单成功率从95%降到70%
10:01:30 — 日志发现大量 DeadlockException：try restarting transaction
10:02:00 — 运维查看MySQL死锁日志：LATEST DETECTED DEADLOCK显示两个事务交叉锁
10:02:30 — 分析：事务A INSERT (user_1, sku_2) 持有(user_1,sku_1)间隙锁，
            等待(user_1,sku_2)的行锁；事务B INSERT (user_1, sku_1) 持有(user_1,sku_2)间隙锁，
            等待(user_1,sku_1)的行锁 → 死锁
10:03:00 — 紧急方案：消费端改为逐条INSERT（非批量），避免交叉锁依赖
10:05:00 — 死锁消失，下单成功率恢复到95%
10:30:00 — 完全稳定
```

### 死锁日志解读

```
LATEST DETECTED DEADLOCK
------------------------
Transaction 1 (ACTIVE 0.2 sec):
  HOLDING THE LOCK: RECORD LOCKS space id 58 page no 4 ... idx_user_sku
  WAITING FOR LOCK: RECORD LOCKS ... (user_1, sku_2)

Transaction 2 (ACTIVE 0.1 sec):
  HOLDING THE LOCK: RECORD LOCKS ... idx_user_sku (user_1, sku_2)
  WAITING FOR LOCK: RECORD LOCKS ... (user_1, sku_1)

WE ROLL BACK Transaction 2
```

**死锁原理图**：

```
唯一索引 idx_user_sku 的间隙锁：

已有数据：(user_1, sku_1)

事务A INSERT (user_1, sku_2):
  Step1: 对 (user_1, sku_1)~(user_1, sku_2) 区间加间隙锁 ✓
  Step2: 等待 (user_1, sku_2) 的行锁（被事务B持有）... BLOCKED

事务B INSERT (user_1, sku_1):
  Step1: 对 (user_1, sku_1)~(user_1, sku_2) 区间加间隙锁 ✓（与A的间隙锁兼容？不！
         INSERT的间隙锁是"插入意向锁"，不兼容！）
  Step2: 等待 (user_1, sku_1) 的行锁（被事务A持有）... BLOCKED

  → A等B，B等A = 死锁！
```

### 5 Why 根因分析

```
现象：秒杀下单成功率骤降，大量DeadlockException
  ↓ Why1: 为什么死锁？→ 两个事务在唯一索引上形成交叉锁依赖
  ↓ Why2: 为什么会交叉锁依赖？→ 批量INSERT时，同一批次内的不同记录在同一索引区间
  ↓ Why3: 为什么批量INSERT导致交叉锁？→ 批量提交时事务内多条INSERT对同一间隙加锁
  ↓ Why4: 为什么同一批次有同一索引区间的记录？→ 消费端按MQ批次直接批量INSERT
  ↓ Why5: 为什么没有考虑死锁风险？→ 设计时只考虑性能（批量INSERT快），没考虑并发锁冲突
  ✓ 根因：批量INSERT在唯一索引上产生间隙锁交叉依赖 + 缺少并发冲突检测
```

### 修复与改进

| # | 改进项 | 类型 | 负责人 | Deadline |
|---|--------|------|--------|----------|
| 1 | 消费端改为逐条INSERT+自动重试（死锁时重试3次） | 立即止血 | 开发A | 当日 |
| 2 | 批量INSERT改为按user_id分组，同用户同事务 | 短期 | 开发B | 3天 |
| 3 | 下幂等检查前置：先SELECT检查再INSERT | 中期 | 开发C | 1周 |

## 3.3 故障故事三：ThreadLocal 泄漏导致 OOM

### 一句话概述

### 时间线

```
Day2 — 内存缓慢增长到600MB，无人关注
Day3 — 内存增长到1.2GB，运维注意但未告警
```

### ThreadLocal泄漏原理图

```
线程池中线程复用 → ThreadLocal.Entry[] 不断累积

Thread-1 的 ThreadLocalMap.Entry[]:
  [0] = Entry(key=traceCtxTL, value=TraceCtx_任务1)   ← Day1 set
  [1] = Entry(key=traceCtxTL, value=TraceCtx_任务2)   ← Day2 set（没remove！）
  [2] = Entry(key=traceCtxTL, value=TraceCtx_任务3)   ← Day3 set
  ...
  [N] = Entry(key=traceCtxTL, value=TraceCtx_任务N)   ← 累积10万次

  每个 TraceCtx = 2KB
  60个线程 × 10万次 × 2KB = 1.2GB → OOM!

注意：ThreadLocal 的弱引用key会被GC回收，但value是强引用不会！
  Entry(key=null弱引用已回收, value=TraceCtx_任务1) ← 内存泄漏的经典模式！
  这些"key=null的value"永远不会被访问，也永远不会被回收（除非Thread死亡）
```

### SafeThreadLocal 工具类

```java
/**
 * 安全的ThreadLocal封装：任务执行完毕自动清理
 * 用法：替换所有 ThreadLocal<X> 为 SafeThreadLocal<X>
 */
public class SafeThreadLocal<T> extends ThreadLocal<T> {

    /**
     * 在Runnable中自动清理ThreadLocal
     * 用法：executor.execute(SafeThreadLocal.wrap(task));
     */
    public static Runnable wrap(Runnable task) {
        return () -> {
            try {
                task.run();
            } finally {
                // 清理当前线程的所有ThreadLocal
                cleanUpCurrentThread();
            }
        };
    }

    /**
     * 在Callable中自动清理ThreadLocal
     */
    public static <V> Callable<V> wrap(Callable<V> task) {
        return () -> {
            try {
                return task.call();
            } finally {
                cleanUpCurrentThread();
            }
        };
    }

    private static void cleanUpCurrentThread() {
        ThreadLocalMap map = Thread.currentThread().threadLocals;
        if (map != null) {
            map.cleanUp(); // 清除所有key=null的泄漏Entry
        }
    }
}

// 使用示例
executor.execute(SafeThreadLocal.wrap(() -> {
    traceCtxThreadLocal.set(ctx);
    try {
        processLog(ctx);
    } finally {
        traceCtxThreadLocal.remove(); // 双重保障
    }
}));
```

```bash
# 每次HSCAN扫描500个field，逐批HDEL

KEY="user:profile:batch"
COUNT=500

while true; do
    # HSCAN游标遍历
    cursor=$(redis-cli HSCAN "$KEY" "$cursor" COUNT "$COUNT" | head -1)
    fields=$(redis-cli HSCAN "$KEY" "$cursor" COUNT "$COUNT" | tail -n +2)

    if [ -z "$fields" ]; then

    fi

    sleep 0.1
done

# 最后DEL剩余骨架（此时已经很小）
redis-cli DEL "$KEY"
```

```java
// Java版本：大Key分批删除
public class BigKeySafeDeleter {

    private final JedisCluster jedisCluster;
    private static final int SCAN_COUNT = 500;

    /**
     * 安全删除Hash大Key：分批HSCAN + HDEL
     */
    public void safeDeleteHash(String key) {
        String cursor = "0";
        ScanParams params = new ScanParams().count(SCAN_COUNT);

        do {
            ScanResult<Map.Entry<String, String>> scanResult =
                jedisCluster.hscan(key, cursor, params);
            cursor = scanResult.getCursor();

            List<String> fields = scanResult.getResult()
                .stream()
                .map(Map.Entry::getKey)
                .collect(Collectors.toList());

            if (!fields.isEmpty()) {
                jedisCluster.hdel(key, fields.toArray(new String[0]));
            }

            // 每批间隔50ms
            Thread.sleep(50);

        } while (!"0".equals(cursor));

        // 最后DEL（此时key已经为空或极小）
        jedisCluster.del(key);
    }
}
```

```java
/**
 * 正则回溯风险检测器
 * 检测嵌套量词、重叠量词等回溯陷阱模式
 */
public class RegexSafetyChecker {

    // 危险模式：嵌套量词
    private static final Pattern NESTED_QUANTIFIER =
        Pattern.compile("\\([^)]*[*+][^)]*\\)[*+]");

    // 危险模式：重叠量词（如 a*a*）
    private static final Pattern OVERLAPPING_QUANTIFIER =
        Pattern.compile("([\\\\w\\\\d][*+?][{][\\d,]+[}])[^\\\\]*\\1");

    /**
     * 检测正则是否存在回溯风险
     * @return RiskLevel: SAFE / WARNING / DANGER
     */
    public static RiskLevel check(String regex) {
        if (NESTED_QUANTIFIER.matcher(regex).find()) {
            return RiskLevel.DANGER;  // 套量词 → 指数级回溯
        }
        if (OVERLAPPING_QUANTIFIER.matcher(regex).find()) {
            return RiskLevel.WARNING; // 重叠量词 → 多项式级回溯
        }
        return RiskLevel.SAFE;
    }

    public enum RiskLevel { SAFE, WARNING, DANGER }
}

// 使用：CI流水线中自动检测
// RegexSafetyChecker.check("^(a+)+$") → DANGER
// RegexSafetyChecker.check("^a+$") → SAFE
```

```java
/**
 * 自定义DNS解析器：本地缓存 + IP直连降级
 */
public class ResilientDnsResolver implements DnsResolver {

    private final ConcurrentHashMap<String, String> dnsCache =
        new ConcurrentHashMap<>();

    // 缓存TTL：5分钟（远大于JVM默认30秒）
    private final ConcurrentHashMap<String, Long> cacheExpire =
        new ConcurrentHashMap<>();

    private static final long CACHE_TTL_MS = 5 * 60 * 1000;

    // 降级IP映射（配置中心动态管理）
    @NacosValue("${dns.fallback.ip-map:}")
    private Map<String, String> fallbackIpMap;

    @Override
    public String resolve(String hostname) throws UnknownHostException {
        // 1. 检查本地缓存
        Long expireTime = cacheExpire.get(hostname);
        if (expireTime != null && System.currentTimeMillis() < expireTime) {
            String cachedIp = dnsCache.get(hostname);
            if (cachedIp != null) return cachedIp;
        }

        // 2. 正常DNS解析（带超时）
        try {
            String ip = resolveWithTimeout(hostname, 500); // 500ms超时
            dnsCache.put(hostname, ip);
            cacheExpire.put(hostname, System.currentTimeMillis() + CACHE_TTL_MS);
            return ip;
        } catch (Exception e) {
            log.warn("DNS解析失败: {}, 降级到IP直连", hostname);
        }

        // 3. 降级：IP直连
        String fallbackIp = fallbackIpMap.get(hostname);
        if (fallbackIp != null) {
            return fallbackIp;
        }

        throw new UnknownHostException("DNS解析失败且无降级IP: " + hostname);
    }

    private String resolveWithTimeout(String hostname, long timeoutMs) {
        // 异步解析 + 超时控制
        Future<String> future = dnsExecutor.submit(
            () -> InetAddress.getByName(hostname).getHostAddress());
        try {
            return future.get(timeoutMs, TimeUnit.MILLISECONDS);
        } catch (TimeoutException e) {
            future.cancel(true);
            throw new RuntimeException("DNS解析超时: " + hostname);
        }
    }
}
```

### 缓存TTL随机偏移实现

```java
/**
 * 缓存TTL随机偏移工具
 * 防止批量Key同时过期导致雪崩
 */
public class CacheTTLUtil {

    private static final Random RANDOM = new Random();

    /**
     * 计算带随机偏移的TTL
     * @param baseSeconds 基础TTL（秒）
     * @param maxOffsetSeconds 最大偏移量（秒）
     * @return 实际TTL（秒）
     */
    public static int randomTTL(int baseSeconds, int maxOffsetSeconds) {
        int offset = RANDOM.nextInt(maxOffsetSeconds * 2) - maxOffsetSeconds;
        return baseSeconds + offset;
    }

    // 使用示例
    // 原来：redis.setex(key, 86400, value)  // 24h = 86400s
    // 现在：redis.setex(key, CacheTTLUtil.randomTTL(86400, 7200), value)  // 24h ± 2h
}

/**
 * 缓存异步刷新方案（永不过期）
 * 后台线程定时刷新，用户请求始终命中缓存
 */
@Component
public class CacheRefresher {

    @Scheduled(fixedRate = 6 * 60 * 60 * 1000) // 每6小时刷新一次
    public void refreshProductCache() {
        List<Product> products = productDao.findAll();
        for (Product p : products) {
            // 缓存永不过期，后台定时刷新
            redis.set("product:" + p.getId(), toJSON(p));
        }
        log.info("缓存刷新完成: {} 条商品", products.size());
    }
}
```

### 容器OOM原理

```
JVM内存模型 vs 容器内存限制：

                    JVM视角                    容器视角
               ┌───────────────┐          ┌───────────────┐
               │   Heap 16GB   │          │  Limit 1GB    │
               │  (default)    │          │               │
               │               │          │  JVM实际使用  │
               │ Metaspace 256 │          │  16.5GB       │
               │ ThreadStacks  │          │               │
               │ DirectBuffer  │          │  超出limit    │
               │ JNI/native    │          │  → OOMKilled  │
               └───────────────┤          │  (exitCode    │
               │  Total ≈16.5GB│          │   137)        │
               └───────────────┘          └───────────────┘

关键问题：JVM默认看不到容器内存限制！
  - JVM8u191之前：按宿主机64GB计算 → -Xmx=16GB
  - JVM8u191之后：支持容器感知(Experimental) → 需手动开启
  - JVM10+：默认容器感知 → 按容器限制计算

  但即使容器感知，也需要留堆外内存空间：
    容器1GB → JVM堆700MB + 堆外300MB ≈ 合计1GB（刚好不超）
```

### 5 Why 根因分析

```
现象：Java服务在K8s上反复OOMKilled重启
  ↓ Why1: 为什么OOMKilled？→ 容器内存1GB限制，JVM实际使用16.5GB
  ↓ Why2: 为什么JVM使用16.5GB？→ 默认-Xmx=宿主机64GB的1/4=16GB
  ↓ Why3: 为什么默认-Xmx这么大？→ JVM未感知容器内存限制，按宿主机计算
  ↓ Why4: 为什么没设置JVM参数？→ Docker/K8s部署时未配置JVM内存参数
  ↓ Why5: 为什么缺少JVM配置？→ 部署规范中缺少容器JVM参数配置指南
  ✓ 根因：容器部署未配置JVM内存参数 + JVM默认按宿主机计算堆大小
```

```java
// 布隆过滤器防止不存在的ID穿透缓存直击DB
@Component
public class ProductQueryService {

    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    // 布隆过滤器：存所有合法商品ID
    private BloomFilter<Long> productBloomFilter;

    @PostConstruct
    public void init() {
        // 从DB加载所有合法ID，初始化布隆过滤器
        List<Long> allIds = productDao.findAllIds();
        productBloomFilter = BloomFilter.create(
            Funnels.longFunnel(), allIds.size(), 0.01); // 1%误判率
        allIds.forEach(id -> productBloomFilter.put(id));
    }

    public Product getProduct(Long id) {
        // 1. 布隆过滤器判断：不存在直接返回null
        if (!productBloomFilter.mightContain(id)) {
            return null; // 99%确定不存在，不查DB
        }

        // 2. 查Redis缓存
        String cached = redisTemplate.opsForValue().get("product:" + id);
        if (cached != null) {
            return parseProduct(cached);
        }

        // 3. 查DB + 回写缓存
        Product product = productDao.findById(id);
        if (product != null) {
            redisTemplate.opsForValue().set("product:" + id,
                toJSON(product), CacheTTLUtil.randomTTL(3600, 300));
        } else {
            // 缓存空值5分钟防穿透（布隆过滤器1%误判场景）
            redisTemplate.opsForValue().set("product:" + id, "NULL", 300);
        }
        return product;
    }
}
```

```java
/**
 * 热Key检测 + 本地缓存兜底
 * 当某个Key的访问频率超过阈值时，自动缓存到本地Caffeine
 */
@Component
public class HotKeyDetector {

    // 热Key访问计数（滑动窗口）
    private final SlidingWindowCounter counter = new SlidingWindowCounter(10, 1000);

    // 本地热Key缓存
    private final Cache<String, String> localCache = Caffeine.newBuilder()
        .maximumSize(1000)
        .expireAfterWrite(5, TimeUnit.SECONDS)  // 热Key本地缓存5秒
        .build();

    // 热Key阈值：1秒内访问>100次
    private static final int HOT_KEY_THRESHOLD = 100;

    public String getWithHotKeyProtection(String key) {
        // 1. 本地缓存优先
        String localValue = localCache.getIfPresent(key);
        if (localValue != null) return localValue;

        // 2. Redis缓存
        String redisValue = redisTemplate.opsForValue().get(key);
        if (redisValue != null) {
            // 3. 热Key检测
            counter.increment(key);
            if (counter.getCount(key) > HOT_KEY_THRESHOLD) {
                // 标记为热Key → 缓存到本地
                localCache.put(key, redisValue);
                log.warn("热Key发现: {}, 本地缓存兜底", key);
            }
            return redisValue;
        }

        // 4. 查DB + 回写Redis
        String dbValue = dao.findValue(key);
        if (dbValue != null) {
            redisTemplate.opsForValue().set(key, dbValue, CacheTTLUtil.randomTTL(3600, 300));
        }
        return dbValue;
    }
}
```

```java
        return RocketMQLocalTransactionState.ROLLBACK;   // 订单不存在 → 回滚
    }
}
```

```java
/**
 * MQ消费幂等：业务唯一键去重表 + Redis分布式锁双重保障
 */
@Component
@RocketMQMessageListener(topic = "order-topic", consumerGroup = "order-consumer-group")
public class OrderConsumer implements RocketMQListener<Order> {

    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    @Autowired
    private DedupDao dedupDao;

    @Override
    public void onMessage(Order order) {
        String bizId = order.getId(); // 业务唯一键

        // 第一层保障：Redis去重（快速判断）
        String redisKey = "dedup:order:" + bizId;
        Boolean isFirst = redisTemplate.opsForValue().setIfAbsent(redisKey, "1", 24, TimeUnit.HOURS);
        if (Boolean.FALSE.equals(isFirst)) {
            log.info("Redis去重命中，跳过: {}", bizId);
            return;
        }

        // 第二层保障：DB去重表（持久化保证）
        if (dedupDao.exists(bizId)) {
            log.info("DB去重命中，跳过: {}", bizId);
            // 补偿：删除Redis标记（因为之前可能Redis过期了被重复设置）
            redisTemplate.delete(redisKey);
            return;
        }

        try {
            // 执行业务
            processOrder(order);

            // 记录去重表
            dedupDao.insert(bizId);
        } catch (Exception e) {
            // 业务失败 → 清除Redis标记，允许下次重试
            redisTemplate.delete(redisKey);
            throw e; // 抛异常触发MQ重试
        }
    }
}
```

```java
/**
 * Redis可重入分布式锁：SET+EX+NX + Lua解锁 + 可重入计数
 */
@Component
public class RedisDistributedLock {

    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    private static final String LOCK_PREFIX = "lock:";
    private static final long DEFAULT_EXPIRE = 30; // 30秒自动过期

    // 加锁Lua脚本：不存在则设置+计数1，存在且同一owner则计数+1
    private static final String LOCK_LUA =
        "if redis.call('exists', KEYS[1]) == 0 then " +
        "  redis.call('hset', KEYS[1], 'owner', ARGV[1], 'count', 1) " +
        "  redis.call('expire', KEYS[1], ARGV[2]) " +
        "  return 1 " +
        "elseif redis.call('hget', KEYS[1], 'owner') == ARGV[1] then " +
        "  redis.call('hincrby', KEYS[1], 'count', 1) " +
        "  redis.call('expire', KEYS[1], ARGV[2]) " +
        "  return 1 " +
        "else " +
        "  return 0 " +
        "end";

    // 解锁Lua脚本：计数-1，减到0则删除Key
    private static final String UNLOCK_LUA =
        "if redis.call('hget', KEYS[1], 'owner') ~= ARGV[1] then " +
        "  return 0 " +
        "elseif redis.call('hincrby', KEYS[1], 'count', -1) > 0 then " +
        "  return 1 " +
        "else " +
        "  redis.call('del', KEYS[1]) " +
        "  return 1 " +
        "end";

    public boolean tryLock(String resource, String owner, long expireSeconds) {
        DefaultRedisScript<Long> script = new DefaultRedisScript<>(LOCK_LUA, Long.class);
        Long result = redisTemplate.execute(script,
            Collections.singletonList(LOCK_PREFIX + resource),
            owner, String.valueOf(expireSeconds));
        return result != null && result == 1;
    }

    public boolean unlock(String resource, String owner) {
        DefaultRedisScript<Long> script = new DefaultRedisScript<>(UNLOCK_LUA, Long.class);
        Long result = redisTemplate.execute(script,
            Collections.singletonList(LOCK_PREFIX + resource),
            owner);
        return result != null && result == 1;
    }
}

// 使用示例（可重入）

    String owner = UUID.randomUUID().toString();
```

```java
/**
 * Redis Lua原子扣减库存 + 防超卖 + 防重复购买标记
 * 一次Lua执行完成三步原子操作：检查库存 → 扣减库存 → 标记已购买
 */
@Component
public class StockService {

    // Lua脚本：检查库存 > 0 → 扣减 → 标记已购买 → 返回剩余库存
    private static final String DEDUCT_LUA =
        "-- 检查是否已购买（防重复）\n" +
        "if redis.call('sismember', KEYS[2], ARGV[2]) == 1 then\n" +
        "  return -2  -- 已购买\n" +
        "end\n" +
        "-- 检查库存是否充足\n" +
        "local stock = tonumber(redis.call('get', KEYS[1]))\n" +
        "if stock == nil or stock < tonumber(ARGV[1]) then\n" +
        "  return -1  -- 库存不足\n" +
        "end\n" +
        "-- 扣减库存\n" +
        "redis.call('decrby', KEYS[1], ARGV[1])\n" +
        "-- 标记已购买\n" +
        "redis.call('sadd', KEYS[2], ARGV[2])\n" +
        "-- 返回剩余库存\n" +
        "return redis.call('get', KEYS[1])\n";

    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    /**
     * 原子扣减库存
     * @param skuId 商品ID
     * @param quantity 购买数量
     * @param userId 用户ID（防重复购买）
     * @return 剩余库存，-1库存不足，-2已购买
     */
    public long deductStock(String skuId, int quantity, String userId) {
        DefaultRedisScript<Long> script = new DefaultRedisScript<>(DEDUCT_LUA, Long.class);
        return redisTemplate.execute(script,
            Arrays.asList("stock:" + skuId, "bought:" + skuId),
            String.valueOf(quantity), userId);
    }
}
```

```java
    void setNext(RiskCheckHandler next);

    private RiskCheckHandler next;
```

```java
 * 金丝雀灰度发布：新版本先给5%用户，逐步放大
 * 基于请求头/用户ID标签路由到不同版本

public class GrayRouteFilter implements GlobalFilter {

    @NacosValue(value = "${gray.rules:}", autoRefreshed = true)
    private List<GrayRule> grayRules;

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String userId = exchange.getRequest().getHeaders().getFirst("X-User-Id");
        String userTag = exchange.getRequest().getHeaders().getFirst("X-User-Tag");

        for (GrayRule rule : grayRules) {
            if (rule.getUserTags().contains(userTag) ||
                shouldGrayByWeight(rule.getWeight(), userId)) {
                // 路由到灰度版本
                exchange.getRequest().mutate()
                    .header("X-Service-Version", rule.getVersion())
                    .build();
            }
        }
        return chain.filter(exchange);
    }

    private boolean shouldGrayByWeight(int weight, String userId) {
        return Math.abs(userId.hashCode() % 100) < weight;
    }
}
```

### 片段18：Snowflake分布式ID

```java
/**
 * Snowflake分布式ID生成器
 * 41位时间 + 10位机器ID + 12位序列号
 * 单机每秒4096个ID，全局唯一
 */
@Component
public class SnowflakeIdGenerator {

    // 起始时间戳（2026-01-01）
    private static final long EPOCH = 1735689600000L;

    private static final long SEQUENCE_BITS = 12;
    private static final long MACHINE_BITS = 10;

    private static final long MAX_SEQUENCE = (1 << SEQUENCE_BITS) - 1; // 4095
    private static final long MAX_MACHINE = (1 << MACHINE_BITS) - 1;   // 1023

    private final long machineId; // 机器ID（0~1023）
    private long sequence = 0;
    private long lastTimestamp = -1;

    public SnowflakeIdGenerator(@Value("${snowflake.machine-id:0}") long machineId) {
        if (machineId < 0 || machineId > MAX_MACHINE) {
            throw new IllegalArgumentException("machineId超出范围");
        }
        this.machineId = machineId;
    }

    public synchronized long nextId() {
        long currentTimestamp = System.currentTimeMillis();

        // 时钟回拨检测
        if (currentTimestamp < lastTimestamp) {
            throw new RuntimeException("时钟回拨！拒绝生成ID");
        }

        if (currentTimestamp == lastTimestamp) {
            sequence = (sequence + 1) & MAX_SEQUENCE;
            if (sequence == 0) {
                // 序列号溢出 → 等到下一毫秒
                currentTimestamp = waitNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0;
        }

        lastTimestamp = currentTimestamp;

        return ((currentTimestamp - EPOCH) << (SEQUENCE_BITS + MACHINE_BITS))
             | (machineId << SEQUENCE_BITS)
             | sequence;
    }

    private long waitNextMillis(long lastTimestamp) {
        long timestamp = System.currentTimeMillis();
        while (timestamp <= lastTimestamp) {
            timestamp = System.currentTimeMillis();
        }
        return timestamp;
    }
}
```

**追问防线**：
- Q: 时钟回拨怎么办？→ 拒绝生成ID / 借未来时间 / RingBuffer预生成
- Q: machineId怎么分配？→ ZK自增 / Nacos配置 / K8s Pod序号
- Q: ID能否反推信息？→ 能：时间戳+机器ID可反推，敏感场景需加密

## 4.10 限流降级片段

### 片段21：Lua滑动窗口限流

```java
/**
 * Redis Lua滑动窗口限流
 * Sorted Set存储请求时间戳，ZRANGEBYSCORE清理过期+ZCARD统计数量
 */
@Component
public class SlidingWindowRateLimiter {

    private static final String LUA_SCRIPT =
        "-- 清理过期窗口\n" +
        "redis.call('zremrangebyscore', KEYS[1], 0, ARGV[1])\n" +
        "-- 统计当前窗口请求数\n" +
        "local count = redis.call('zcard', KEYS[1])\n" +
        "-- 判断是否超限\n" +
        "if count < tonumber(ARGV[2]) then\n" +
        "  -- 未超限：记录本次请求\n" +
        "  redis.call('zadd', KEYS[1], ARGV[3], ARGV[3])\n" +
        "  redis.call('expire', KEYS[1], ARGV[4])\n" +
        "  return 1\n" +
        "else\n" +
        "  -- 超限：拒绝\n" +
        "  return 0\n" +
        "end\n";

    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    /**
     * 滑动窗口限流
     * @param key 限流键（如IP或用户ID）
     * @param maxRequests 窗口内最大请求数
     * @param windowSeconds 窗口时长（秒）
     * @return true=通过, false=限流
     */
    public boolean allowRequest(String key, int maxRequests, int windowSeconds) {
        long now = System.currentTimeMillis();
        long windowStart = now - windowSeconds * 1000;

        DefaultRedisScript<Long> script = new DefaultRedisScript<>(LUA_SCRIPT, Long.class);
        Long result = redisTemplate.execute(script,
            Collections.singletonList("rate_limit:" + key),
            String.valueOf(windowStart),  // ARGV1: 窗口起始时间
            String.valueOf(maxRequests),  // ARGV2: 最大请求数
            String.valueOf(now),          // ARGV3: 当前时间戳（作为score和member）
            String.valueOf(windowSeconds) // ARGV4: 窗口时长（设置expire）
        );

        return result != null && result == 1;
    }
}
```

**追问防线**：
- Q: 为什么用Lua？→ ZREM+ZCARD+ZADD必须原子执行
- Q: 和固定窗口区别？→ 滑动窗口无临界突发效应，更平滑
- Q: 性能开销？→ 每次请求一次Redis RTT，ZCARD O(1)很轻

### 片段22：超时分层设计

```java
/**
 * 超时分层设计：不同层设置不同超时，避免级联超时
 * 原则：下游超时 < 上游超时（留buffer给上游处理）
 */
@Configuration
public class TimeoutConfig {

    // ===== 超时分层原则 =====
    // Gateway超时 > Service超时 > DB/Redis超时
    // 具体：Gateway 10s > Service 5s > Redis 2s > MySQL 1s

    // Gateway层超时
    @Bean
    public RouteLocator customRouteLocator(RouteLocatorBuilder builder) {
        return builder.routes()
            .route("order-service", r -> r.path("/api/order/**")
                .filters(f -> f.requestTimeout(Duration.ofSeconds(10)))  // 10s
                .uri("lb://order-service"))
            .build();
    }

    // Service层HTTP调用超时（RestTemplate）
    @Bean
    public RestTemplate restTemplate() {
        SimpleClientHttpRequestFactory factory = new SimpleClientHttpRequestFactory();
        factory.setConnectTimeout(2000);  // 连接超时2s
        factory.setReadTimeout(5000);     // 读超时5s
        return new RestTemplate(factory);
    }

    // Redis超时
    @Bean
    public LettuceConnectionFactory redisConnectionFactory() {
        LettuceConnectionFactory factory = new LettuceConnectionFactory();
        factory.setTimeout(2000);  // 2s
        return factory;
    }

    // MySQL连接池超时（HikariCP）
    @Bean
    public HikariDataSource dataSource() {
        HikariConfig config = new HikariConfig();
        config.setMaximumPoolSize(200);
        config.setConnectionTimeout(1000);    // 等连接超时1s
        config.setConnectionTimeout(500);     // 连接建立超时500ms
        config.setValidationTimeout(1000);    // 连接验证超时1s
        config.setLeakDetectionThreshold(30000); // 连接泄漏检测30s
        return new HikariDataSource(config);
    }
}
```

**追问防线**：
- Q: 为什么上游超时要比下游大？→ 留buffer，避免上游先超时断开，下游还在等
- Q: 超时和重试的关系？→ 超时+重试=流量翻倍，必须限流+退避配合
- Q: 怎么动态调整超时？→ Nacos配置中心autoRefreshed实时生效

# 第六章 面试高频题

> 每道题含**标准回答框架** + **加分回答**

---

## Q1: 你经历过的最严重的线上故障是什么？

**标准回答框架**：
```
一句话概述 → 时间线(发现→止血→根因→修复) → 根因分析(5 Why) → 改进措施 → 个人反思
```

**加分回答**：
> 讲完故障后，主动说"后来我做了X改进，这类故障再没发生过"，展现从错误中学习的成长思维。不要只讲故障有多惨，要讲你从中学到了什么。

## Q2: 线上CPU飙高怎么排查？

**标准回答**：
```
5步法：top确认进程 → top -Hp确认线程 → printf %x转十六进制 → jstack看堆栈 → Arthas深入分析
常见原因：死循环/正则回溯/加密运算/锁自旋/GC频繁
```

**加分回答**：
> 补充Arthas火焰图(profiler)方法，能从统计视角找到瓶颈，比单次jstack更全面。

## Q3: 线上OOM怎么排查？

**标准回答**：
```
确认OOM类型 → jmap导出堆 → MAT分析 → 定位泄漏对象 → 5 Why根因
常见类型：Java heap space(堆)/Metaspace(类加载)/Direct buffer(堆外)/unable to create thread(线程数)
```

**加分回答**：
> 补充NMT追踪堆外内存 + 容器OOMKilled(exitCode=137)的排查差异。

## Q4: 你怎么做故障复盘？

**标准回答**：
```
六步法：确认事实 → 还原时间线 → 5 Why根因 → 改进措施(Action Item) → 复盘会议 → 知识沉淀
核心原则：无指责文化/数据驱动/可执行改进/全量公开
```

**加分回答**：
> 补充"每条改进必须有负责人+Deadline+验证方式"，不是"以后注意点"这种空话。

## Q5: 怎么防止缓存雪崩？

**标准回答**：
```
三个防御：TTL加随机偏移(24h±2h) + 缓存永不过期+异步刷新 + 多级缓存(Caffeine本地兜底)
雪崩原因：批量Key同时过期 → 穿透缓存直击DB → 连接池耗尽 → 雪崩
```

**加分回答**：
> 补充DB限流保护(HikariCP使用率>80%限流) + 缓存空值防穿透 + 自动缓存预热。

## Q6: 怎么防止缓存穿透？

**标准回答**：
```
两种方案：布隆过滤器(不存在直接返回) + 缓存空值(5分钟TTL)
穿透原因：大量查询不存在的Key → Redis命中率0% → DB压力飙升
```

**加分回答**：
> 布隆过滤器误判率1% → 缓存空值兜底。数据量大用Redis布隆过滤器模块(RBFPFILTER)。

## Q7: Redis大Key怎么处理？

**标准回答**：
```
发现：redis-cli --bigkeys / MEMORY USAGE key
删除：UNLINK(异步) / 分批HSCAN+HDEL(每批500field)
设计：Hash按前缀分片 / List截断 / Set拆分
告警：单Key内存>10MB告警
```

**加分回答**：
> 补充大Key删除的具体脚本 + 原理（Hash DEL O(N)逐field释放阻塞主线程）。

## Q8: MySQL死锁怎么排查和预防？

**标准回答**：
```
排查：SHOW ENGINE INNODB STATUS → LATEST DETECTED DEADLOCK分析
预防：缩短事务/按固定顺序加锁/降低隔离级别/逐条INSERT替代批量/死锁自动重试
```

**加分回答**：
> 补充具体死锁场景（唯一索引间隙锁交叉）+ Spring Retry死锁自动重试框架。

## Q9: MQ消息堆积怎么处理？

**标准回答**：
```
发现：Dashboard堆积量+消费延迟
止血：临时增加消费线程/增加消费者实例/跳过非核心消息
根因：消费速度<生产速度（线程数错误/消费逻辑慢/下游故障）
预防：消费延迟告警(>30s) + 堆积量告警(>10万) + 消费者自检
```

**加分回答**：
> 补充"堆积处理策略"——临时扩容消费端 + 非核心消息降级 + 堆积消化后回填。

## Q10: 怎么保证线上发布不出问题？

**标准回答**：
```
发布流程：灰度发布(5%→10%→50%→100%) + 监控观察(1小时) + 回滚方案
流程防线：Code Review + SQL审查 + 压测验证 + 变更审批
技术防线：健康检查 + 灰度路由 + 监控告警 + 自动回滚
```

**加分回答**：
> 补充数据库变更分离原则（DDL先执行，代码后上线，回滚时不回滚DDL）+ 发布Checklist。

>

> 3. **面试讲法重成长轻灾难**——把"我学到了什么"放在"故障有多严重"后面
