## 第一章 技术选型的核心思想

### 1.1 什么是技术选型

技术选型，是指在特定业务场景和约束条件下，从多个候选技术方案中选择最合适方案的系统化决策过程。

它不是简单的"哪个技术更好"，而是"哪个技术**最适合当前场景**"。

```
技术选型 = 业务需求 × 技术能力 × 约束条件 × 团队现状 × 时间窗口
```

### 1.2 技术选型的本质

技术选型的本质是**权衡（Trade-off）**。没有完美的技术，只有适合的方案。每一个选择都意味着得到一些东西，同时放弃一些东西。

| 你得到的 | 你放弃的 |
|---------|---------|
| 高性能 | 可维护性（复杂的数据分片逻辑） |
| 强一致性 | 可用性（CAP 约束） |
| 快速开发 | 灵活性（框架约束） |
| 零成本 | 运维能力（自研需投入） |
| 前沿技术 | 稳定性（社区不成熟） |

### 1.3 技术选型五大核心原则

#### 原则一：业务驱动，而非技术驱动

> "不要为了用 Kafka 而去找一个适合 Kafka 的场景。"

技术选型的起点永远是**业务需求**，而非技术本身。先搞清楚业务痛点，再找匹配的技术。

```
✅ 正确路径：业务需求 → 技术能力要求 → 候选方案 → 评估选择
❌ 错误路径：新技术 → 找场景套用 → 强行适配 → 勉强上线
```

**经典反例**：一个日活 500 人的内部管理系统，用 Kafka + Flink + ClickHouse 搭建实时数仓，投入 3 个人 2 个月，最后发现一个 MySQL 定时任务就够了。

#### 原则二：合适的，而非最好的

> "杀鸡不用牛刀，但也不能用指甲刀。"

选型要匹配**当前阶段**的业务规模和发展预期，不要过度设计也不要欠设计。

| 阶段 | 日活/QPS | 选型策略 |
|------|---------|---------|
| MVP 阶段 | < 1万 DAU / < 100 QPS | 单机 + 单库 + Redis 即可 |
| 成长期 | 1万~50万 DAU / 100~1000 QPS | 主从分离 + 读写分离 + 缓存 |
| 成熟期 | > 50万 DAU / > 1000 QPS | 分库分表 + 微服务 + 消息队列 |
| 平台期 | > 千万 DAU / > 万级 QPS | 异地多活 + 单元化 + 全链路压测 |

#### 原则三：成熟优先，而非追新优先

> "做第一个吃螃蟹的人，代价可能是被螃蟹夹。"

技术选型应优先考虑**经过生产验证**的成熟方案，而非最新最酷的技术。

| 维度 | 成熟技术 | 新技术 |
|------|---------|--------|
| 社区活跃 | 有大量踩坑经验和解决方案 | 文档少、最佳实践缺失 |
| 稳定性 | 经过大规模验证 | 可能有未知 Bug |
| 人才市场 | 容易招到有经验的人 | 招人难、培训成本高 |
| 运维工具 | 监控/告警/部署工具齐全 | 需要自研运维工具 |
| 风险 | 低 | 高（可能项目停止维护） |

**判断标准——技术成熟度评估表**：

| 指标 | ⭐ 一星 | ⭐⭐ 二星 | ⭐⭐⭐ 三星 | ⭐⭐⭐⭐ 四星 |
|------|--------|---------|----------|----------|
| GitHub Star | < 1k | 1k~5k | 5k~20k | > 20k |
| 生产案例 | 无知名案例 | 有案例但少 | 多家大厂验证 | 广泛生产使用 |
| 社区活跃度 | 月提交 < 10 | 月提交 10~50 | 月提交 50~200 | 月提交 > 200 |
| 文档完整度 | 基本无文档 | 有基础文档 | 文档较完善 | 文档+最佳实践+案例 |
| 版本稳定性 | 频繁 Breaking Change | 偶尔不兼容 | 基本兼容 | 严格语义化版本 |
| 商业支持 | 无 | 社区支持 | 有商业版 | 大厂背书+商业版 |

**建议**：核心系统选四星以上，非核心系统可选三星，一星二星仅供技术研究。

#### 原则四：可运维，而非仅可开发

> "能跑起来只是开始，能运维好才是关键。"

选型不能只考虑开发体验，更要考虑**运维成本**。一个开发爽但运维痛苦的技术，最终会成为团队的负担。

**运维考量清单**：

```
□ 是否有成熟的监控方案？
□ 是否支持优雅上下线？
□ 是否支持配置热更新？
□ 是否有备份恢复方案？
□ 是否支持水平扩展？
□ 是否有成熟的 CI/CD 集成？
□ 故障排查工具是否齐全？
□ 是否需要专门的运维人员？
□ License 是否允许商用？
□ 长期维护成本如何？
```

#### 原则五：团队匹配，而非理想最优

> "最好的技术交给不会用的团队，不如一般的技术交给会用的人。"

技术选型必须考虑团队的**技术栈匹配度**和**学习曲线**。

| 考量点 | 说明 |
|--------|------|
| 团队现有技能 | 是否有相关经验？学习成本多高？ |
| 招聘难度 | 市场上是否容易招到该技术的人才？ |
| 培训成本 | 需要多长时间让团队上手？ |
| 人员流动风险 | 如果核心人员离职，其他人能否接手？ |

**经验法则**：
- 团队不熟悉的技术，至少要有 **1~2 个月** 的学习适应期
- 核心系统不建议用团队完全陌生的技术
- 如果一定要引入新技术，先在非核心系统试点

### 1.4 技术选型的时机

不是所有时候都需要做技术选型。以下场景需要正式选型：

| 场景 | 是否需要正式选型 | 说明 |
|------|----------------|------|
| 新项目从零开始 | ✅ 是 | 全栈技术栈选型 |
| 系统重构 | ✅ 是 | 需要评估新旧方案迁移成本 |
| 引入新中间件 | ✅ 是 | 评估与现有系统的兼容性 |
| 架构升级（单体→微服务） | ✅ 是 | 影响深远，需充分评估 |
| 技术栈升级（如 Spring Boot 2→3） | ⚠️ 视情况 | 大版本升级需评估兼容性 |
| 日常开发选个库 | ❌ 否 | 团队内部约定即可 |
| 修复一个 Bug | ❌ 否 | 直接修复，不涉及选型 |

## 第二章 评估维度体系——七大维度

### 2.1 七大评估维度总览

技术选型需要从**七个维度**系统评估，任何一个维度的缺失都可能导致后期踩坑。

```
                    ┌─────────────┐
                    │  功能适配度  │ ← 业务需求是否满足？
                    ├─────────────┤
                    │   性能表现   │ ← 能否扛住预期负载？
                    ├─────────────┤
                    │   可靠性     │ ← 故障率/恢复能力如何？
                    ├─────────────┤
                    │   可维护性   │ ← 运维/升级/扩展成本？
                    ├─────────────┤
                    │   成本       │ ← License/人力/资源成本？
                    ├─────────────┤
                    │  团队匹配度  │ ← 团队能否驾驭？
                    ├─────────────┤
                    │   生态成熟度 │ ← 社区/文档/工具链？
                    └─────────────┘
```

### 2.2 维度一：功能适配度

**核心问题**：这个技术能否满足业务需求？

这是最基础的维度。如果一个技术连基本功能都不满足，其他维度再好也没用。

**评估清单**：

| 评估点 | 说明 | 权重 |
|--------|------|------|
| 核心功能覆盖 | 是否支持业务必需的所有功能？ | 高 |
| 功能扩展性 | 未来业务变化时能否扩展？ | 中 |
| 功能边界 | 有哪些功能不支持或需要二次开发？ | 高 |
| 兼容性 | 与现有系统的集成能力如何？ | 高 |
| 定制化能力 | 是否支持自定义插件/扩展？ | 中 |

**评分方法**：

```
功能适配度 = (核心功能覆盖率 × 0.4 + 兼容性 × 0.3 + 扩展性 × 0.2 + 定制化 × 0.1) × 100
```

**示例——消息队列功能适配度评估**：

| 功能 | Kafka | RocketMQ | RabbitMQ | Pulsar |
|------|-------|----------|----------|--------|
| 顺序消息 | ✅ 分区内有序 | ✅ 分区内有序 | ❌ 不保证 | ✅ 分区内有序 |
| 事务消息 | ❌ 仅幂等 | ✅ 原生支持 | ❌ 不支持 | ✅ 原生支持 |
| 延时消息 | ❌ 需自建 | ✅ 原生支持 | ✅ 插件支持 | ✅ 原生支持 |
| 死信队列 | ❌ 需自建 | ✅ 原生支持 | ✅ 原生支持 | ✅ 原生支持 |
| 消息回溯 | ✅ 按时间/偏移 | ✅ 按时间 | ❌ 不支持 | ✅ 原生支持 |
| 消费模式 | 拉模式 | 推+拉 | 推模式 | 推+拉 |
| 广播消费 | ✅ | ✅ | ✅ | ✅ |
| 消费者组 | ✅ | ✅ | ✅ | ✅ |

### 2.3 维度二：性能表现

**核心问题**：在预期负载下，技术能否满足性能要求？

**评估指标**：

| 指标 | 说明 | 评估方法 |
|------|------|---------|
| 吞吐量 (TPS/QPS) | 每秒处理的事务/查询数 | 压测验证 |
| 延迟 (Latency) | P50/P95/P99 响应时间 | 压测验证 |
| 资源利用率 | CPU/内存/网络/磁盘占用 | 监控对比 |
| 扩展能力 | 水平/垂直扩展的线性度 | 逐步加压验证 |
| 极限能力 | 瓶颈在哪里？能扛多大？ | 压到崩溃验证 |

**性能评估流程**：

```
1. 确定性能基线需求（当前QPS + 未来3年增长预期 × 3~5倍安全冗余）
2. 搭建测试环境（与生产环境等比缩放）
3. 设计压测场景（正常负载/峰值负载/极限负载）
4. 执行压测，记录关键指标
5. 对比候选方案的性能数据
6. 评估性能瓶颈和扩展方案
```

**示例——缓存选型性能对比**：

| 指标 | Redis (单线程) | Memcached (多线程) | Caffeine (本地) |
|------|----------------|-------------------|-----------------|
| 单实例 QPS | 10万+ | 50万+ | 千万级 |
| 平均延迟 | < 1ms | < 1ms | < 0.01ms |
| P99 延迟 | 1~2ms | 0.5~1ms | < 0.1ms |
| 内存利用率 | ~70% | ~90% | ~80% |
| 水平扩展 | Cluster模式 | 客户端分片 | 不适用 |
| 瓶颈 | 单线程CPU | 内存容量 | 堆内存 |

### 2.4 维度三：可靠性

**核心问题**：系统出故障的概率多大？故障后恢复有多快？

**评估指标**：

| 指标 | 说明 | 标准 |
|------|------|------|
| 可用性 (Availability) | 正常运行时间占比 | 核心系统 ≥ 99.9% |
| MTBF | 平均无故障时间 | 越大越好 |
| MTTR | 平均恢复时间 | 越小越好 |
| 数据持久性 | 数据丢失风险 | RPO = 0 最优 |
| 故障恢复机制 | 自动/手动恢复 | 优先自动恢复 |
| 数据一致性保证 | 强一致/最终一致 | 按业务需求选择 |

**可靠性评估清单**：

```
□ 是否支持主从复制/集群？
□ 是否支持自动故障转移？
□ 是否支持数据备份恢复？
□ 是否支持跨机房/跨可用区部署？
□ 是否有数据校验机制？
□ 是否支持事务（如需要）？
□ 是否有消息确认/重试机制（如MQ）？
□ 是否有限流/熔断/降级机制？
□ 是否有幂等性保证？
□ 是否有监控告警能力？
```

### 2.5 维度四：可维护性

**核心问题**：长期的运维、升级、扩展成本有多高？

**评估指标**：

| 指标 | 说明 |
|------|------|
| 部署复杂度 | 单机/集群部署难度 |
| 配置管理 | 配置项是否合理？是否支持热更新？ |
| 版本升级 | 升级是否平滑？是否有兼容性保证？ |
| 监控能力 | 是否有现成的监控方案？ |
| 故障排查 | 是否有完善的日志/诊断工具？ |
| 日常运维 | 日常运维操作量多大？是否需要专人？ |
| 文档质量 | 官方文档是否完善？社区资料是否丰富？ |
| 扩展能力 | 是否支持插件化扩展？ |

**可维护性评分标准**：

```
可维护性 = 部署简便度 × 0.2 + 配置管理 × 0.15 + 版本兼容性 × 0.2 
         + 监控完备度 × 0.15 + 故障排查 × 0.15 + 文档质量 × 0.15
```

**示例——注册中心可维护性对比**：

| 指标 | Nacos | Eureka | Consul | Zookeeper | etcd |
|------|-------|-------|--------|-----------|------|
| 部署方式 | 单体/集群 | 单体/集群 | 单体/集群 | 集群(ZAB) | 集群(Raft) |
| 配置管理 | Web控制台 | 无 | Web UI | 无 | 无 |
| 运维复杂度 | ★☆☆☆☆ 低 | ★☆☆☆☆ 低 | ★★☆☆☆ 中 | ★★★★☆ 高 | ★★★☆☆ 中高 |
| 版本升级 | 平滑 | 已停止维护 | 平滑 | 需停服 | 平滑 |
| 监控支持 | 内置+Prometheus | 无 | 内置 | 四字命令 | 内置 |
| 故障排查 | 日志+控制台 | 日志 | 日志+UI | 日志+四字命令 | 日志 |
| 文档质量 | 优秀(中文) | 一般 | 优秀 | 一般 | 优秀 |

### 2.6 维度五：成本

**核心问题**：引入这个技术的总拥有成本（TCO）是多少？

**成本构成**：

```
TCO（总拥有成本） = 人力成本 + 资源成本 + License成本 + 培训成本 + 运维成本 + 迁移成本
```

| 成本类型 | 说明 | 评估方法 |
|---------|------|---------|
| License 费用 | 商业授权费用 | 查看官网定价 |
| 人力成本 | 开发+运维人力 | 人月 × 人力单价 |
| 资源成本 | 服务器/存储/网络 | 实例规格 × 数量 × 单价 |
| 培训成本 | 团队学习投入 | 培训天数 × 人数 × 日薪 |
| 迁移成本 | 从旧系统迁移 | 迁移人力 + 双写期间额外成本 |
| 运维成本 | 长期运维投入 | 年运维人力 + 工具费用 |

**License 类型对比**：

| License | 说明 | 代表技术 | 商用风险 |
|---------|------|---------|---------|
| Apache 2.0 | 最宽松，可商用、修改、闭源 | Kafka, Spring, gRPC | 极低 |
| MIT | 宽松，可商用 | Redis, jQuery | 极低 |
| BSD | 宽松，需保留版权声明 | Nginx, PostgreSQL | 低 |
| GPL | 传染性，衍生作品必须开源 | MySQL(社区版) | ⚠️ 高 |
| AGPL | 网络服务也需开源 | MongoDB(旧版) | ⚠️ 高 |
| 商业 License | 需购买授权 | Oracle DB | 需付费 |
| SSPL | 云厂商不能直接提供服务 | MongoDB(新版) | 中 |

**成本决策矩阵**：

| 场景 | 策略 |
|------|------|
| 初创公司 | 优先开源免费方案 |
| 大厂内部系统 | 开源自建为主 |
| 金融/医疗等强合规 | 商业版+商业支持 |
| 云上部署 | 优先云厂商托管服务 |
| 对数据主权要求高 | 自建集群 |

### 2.7 维度六：团队匹配度

**核心问题**：团队是否有能力驾驭这个技术？

**评估维度**：

| 维度 | 评估问题 |
|------|---------|
| 技术栈匹配 | 团队是否熟悉该技术栈？ |
| 学习曲线 | 需要多长时间上手？ |
| 招聘难度 | 市场上该技术人才是否充足？ |
| 人员储备 | 团队是否有该技术的专家？ |
| 培训成本 | 培训一个新人需要多久？ |
| 社区支持 | 遇到问题能否快速找到答案？ |

**团队匹配度评分**：

| 2分 | 团队完全陌生，但相关技术有经验 | 需 1~2 个月学习期 |
| 1分 | 团队完全陌生，且无相关经验 | 不建议引入或需长期准备 |

## 第三章 选型方法论框架——六步法

### 3.1 六步选型法

```
Step 1: 需求分析    → 搞清楚要解决什么问题
     ↓
Step 2: 候选方案    → 收集所有可能的方案
     ↓
Step 3: 维度评估    → 用七大维度逐一打分
     ↓
Step 4: POC 验证   → 关键方案做原型验证
     ↓
Step 5: 决策评审    → 团队评审+利益相关方确认
     ↓
Step 6: 落地计划    → 制定迁移和上线计划
```

### 3.2 Step 1：需求分析

**目标**：明确要解决的核心问题，输出需求清单。

**需求分析模板**：

```markdown
## 选型需求分析

### 业务背景
- 业务场景描述：______
- 当前痛点：______
- 预期目标：______

1. ______
2. ______
3. ______

### 性能需求
- 当前 QPS：______ | 预期 QPS（1年内）：______ | 预期 QPS（3年内）：______
- 当前数据量：______ | 预期数据量（1年内）：______ | 预期数据量（3年内）：______
- 延迟要求：P99 < ______ms

### 可靠性需求
- 可用性目标：______（如 99.9%）
- 数据一致性要求：______（强一致 / 最终一致）
- RPO / RTO 要求：______

### 约束条件
- 团队技术栈：______
- 预算限制：______
- 上线时间要求：______
- 合规要求：______

### 非目标（明确不做什么）

```

**示例——消息队列选型需求分析**：

```markdown
### 业务背景
- 场景：电商订单系统异步解耦（订单创建 → 通知库存/物流/积分）
- 痛点：当前同步调用，下单响应慢（500ms+），耦合严重
- 目标：引入 MQ 解耦，下单响应 < 100ms

### 功能需求
1. 事务消息（保证订单与消息的一致性）
2. 延时消息（30分钟未支付自动取消）
3. 死信队列（消费失败的消息不丢失）
4. 消息回溯（故障恢复后能重新消费）

### 性能需求
- 当前订单量：5万/天 | 峰值：5000/小时 | QPS：~200
- 1年内预期：20万/天 | 峰值：2万/小时 | QPS：~600
- 3年内预期：100万/天 | 峰值：10万/小时 | QPS：~3000

### 约束条件
- 团队：Java 技术栈，熟悉 Spring Cloud
- 预算：不购买商业版
- 上线时间：2 个月内
```

### 3.3 Step 2：候选方案收集

**目标**：尽可能全面地收集候选方案，避免遗漏。

**收集渠道**：

| 渠道 | 说明 |
|------|------|
| 技术调研报告 | CNCF Landscape, ThoughtWorks Technology Radar |
| 同行交流 | 了解同行业其他公司的选择 |
| 开源社区 | GitHub Trending, Apache 项目列表 |
| 技术博客 | 美团/阿里/字节的技术博客 |
| 云厂商方案 | AWS/Azure/阿里云的推荐方案 |
| 面试题库 | 了解行业主流选择 |

**筛选原则**：

1. **初筛**：从功能适配度快速排除明显不满足的方案
2. **复筛**：从生态成熟度和团队匹配度排除不现实的方案
3. **终选**：保留 2~3 个候选方案进入详细评估

### 3.4 Step 3：维度评估

**目标**：用七大维度对候选方案逐一打分，形成量化对比。

**评估表模板**：

| 维度 | 权重 | 方案A得分 | 方案B得分 | 方案C得分 | 说明 |
|------|------|---------|---------|---------|------|
| 功能适配度 | 20% | 8/10 | 9/10 | 7/10 | |
| 性能表现 | 20% | 7/10 | 8/10 | 9/10 | |
| 可靠性 | 15% | 8/10 | 9/10 | 7/10 | |
| 可维护性 | 15% | 9/10 | 7/10 | 6/10 | |
| 成本 | 10% | 9/10 | 6/10 | 8/10 | |
| 团队匹配度 | 10% | 8/10 | 5/10 | 7/10 | |
| 生态成熟度 | 10% | 9/10 | 7/10 | 6/10 | |
| **加权总分** | 100% | **8.15** | **7.75** | **7.05** | |

**注意事项**：
- 打分要有**依据**，不能凭感觉
- 每个维度的打分都要有**数据支撑**（压测数据/社区数据/文档链接）
- 要记录**扣分原因**，便于后续讨论

### 3.5 Step 4：POC 验证

## 第四章 数据库选型实战

### 4.1 数据库选型决策树

```
                    ┌─ 关系型数据？──→ ┌─ 强一致性要求？──→ MySQL / PostgreSQL
                    │                  └─ 最终一致性可接受？──→ TiDB / OceanBase
                    │
  数据模型？────────┼─ 文档型数据？──────→ MongoDB / CouchDB
                    │
                    ├─ 键值型数据？──────→ Redis / DynamoDB
                    │
                    ├─ 列式存储？────────→ HBase / ClickHouse
                    │
                    ├─ 图数据？──────────→ Neo4j / JanusGraph
                    │
                    ├─ 时序数据？────────→ InfluxDB / TDengine / Prometheus
                    │
                    ├─ 全文搜索？────────→ Elasticsearch / OpenSearch
                    │
                    └─ 宽列存储？────────→ Cassandra / HBase
```

### 4.2 关系型数据库对比

| 维度 | MySQL | PostgreSQL | TiDB | OceanBase |
|------|-------|-----------|------|-----------|
| **定位** | 通用 OLTP | 功能丰富的 OLTP | 分布式 NewSQL | 金融级分布式 |
| **一致性** | 强一致 | 强一致 | 强一致 | 强一致 |
| **扩展方式** | 主从+分库分表 | 主从+Citus | 自动水平扩展 | 自动水平扩展 |
| **单机性能** | 高 | 高 | 中（分布式开销） | 中高 |
| **分布式事务** | ❌ 需XA | ❌ 需XA | ✅ 原生支持 | ✅ 原生支持 |
| **存储引擎** | InnoDB | 多种可选 | TiKV(RocksDB) | 自研 |
| **SQL兼容** | 高 | 高 | 高（兼容MySQL） | 高（兼容MySQL） |
| **运维复杂度** | ★☆☆ 低 | ★☆☆ 低 | ★★★ 中高 | ★★★★ 高 |
| **License** | GPL(社区) | PostgreSQL License | Apache 2.0 | 商业 |
| **适用场景** | 通用Web应用 | 复杂查询/GIS | 大规模OLTP | 金融核心 |
| **大厂背书** | Oracle | 开源社区 | PingCAP | 蚂蚁集团 |

### 4.3 MySQL vs PostgreSQL 深度对比

这两个是关系型数据库最常见的选型之争。

| 维度 | MySQL | PostgreSQL |
|------|-------|-----------|
| **架构** | 单进程多线程 | 多进程 |
| **存储引擎** | 可插拔（InnoDB/MyISAM） | 单一（但功能丰富） |
| **JSON支持** | JSON 类型（5.7+） | JSONB（更强大，可索引） |
| **GIS支持** | 基础空间函数 | PostGIS（业界最强） |
| **全文搜索** | 基础全文索引 | 内置全文搜索+中文分词 |
| **窗口函数** | 8.0+ 支持 | 早已支持 |
| **CTE递归** | 8.0+ 支持 | 早已支持 |
| **物化视图** | ❌ 不支持 | ✅ 支持 |
| **序列对象** | AUTO_INCREMENT | SEQUENCE |
| **并发控制** | MVCC + 行锁 | MVCC + 更丰富的锁 |
| **复制** | 主从复制 | 流复制+逻辑复制 |
| **分区表** | 5.1+ 支持 | 10+ 原生声明式 |
| **扩展性** | 插件有限 | 丰富的扩展生态 |
| **性能调优** | 参数较少，简单 | 参数多，更灵活 |
| **运维工具** | 生态成熟 | 生态较少 |
| **国内人才** | 极多 | 较少 |

**选型建议**：

| 场景 | 推荐 | 原因 |
|------|------|------|
| 通用 Web 应用 | MySQL | 生态成熟，人才多 |
| 复杂查询/分析 | PostgreSQL | 功能强大，查询优化好 |
| GIS/地理位置 | PostgreSQL + PostGIS | 业界最强 GIS 支持 |
| JSON 密集型 | PostgreSQL | JSONB 性能和功能优势 |
| 金融级强一致 | MySQL + XA / TiDB | 成熟稳定 |
| 大规模分布式 | TiDB | 原生分布式，兼容 MySQL 协议 |
| 初创项目 | MySQL | 上手快，运维简单 |

### 4.4 NoSQL 数据库对比

| 类型 | 代表 | 数据模型 | 一致性 | 适用场景 |
|------|------|---------|--------|---------|
| 键值型 | Redis | Key-Value | 最终一致 | 缓存/计数器/排行榜 |
| 文档型 | MongoDB | JSON文档 | 可调一致 | 内容管理/CMS/用户画像 |
| 列族型 | HBase | 列族 | 强一致 | 海量数据/时间线/日志 |
| 列族型 | Cassandra | 列族 | 可调一致 | 写多读少/时序数据 |
| 图数据库 | Neo4j | 节点+边+属性 | ACID | 社交关系/推荐/反欺诈 |
| 时序型 | InfluxDB | 时间序列 | 强一致 | 监控/IoT/指标 |

### 4.5 MongoDB 适用场景分析

**适合**：
- 内容管理系统（灵活的文档结构）
- 用户画像/标签系统（JSON 天然适配）
- 物联网设备数据（海量、结构不固定）
- 实时分析（内置聚合管道）

**不适合**：
- 强事务场景（跨文档事务性能差）
- 复杂 JOIN 查询（不支持 JOIN）
- 数据一致性要求极高（默认最终一致）
- 小数据量场景（杀鸡用牛刀）

| 海量日志/时序 | HBase / TDengine | InfluxDB |
| 全文搜索 | Elasticsearch | OpenSearch |

## 第五章 缓存选型实战

### 5.1 缓存选型决策树

```
                ┌─ 本地缓存？──→ ┌─ 需要持久化？──→ Ehcache / Caffeine（支持持久化）
                │                └─ 不需要持久化──→ Caffeine（性能最佳）
                │
  缓存类型？─────┤
                │                ┌─ 数据结构简单？──→ Memcached（多线程高性能）
                └─ 分布式缓存？──┤
                                 ├─ 需要丰富数据结构？──→ Redis
                                 │
                                 └─ 云上部署？──→ 云托管 Redis（AWS ElastiCache / 阿里云 Tair）
```

### 5.2 Redis vs Memcached 深度对比

| 维度 | Redis | Memcached |
|------|-------|-----------|
| **数据结构** | String/List/Hash/Set/ZSet/Stream/HyperLogLog/Geo | 仅 Key-Value(String) |
| **线程模型** | 单线程（6.0+ 多线程IO） | 多线程 |
| **单实例QPS** | 10万+ | 50万+ |
| **内存管理** | 自主管理（jemalloc） | Slab Allocation |
| **持久化** | RDB + AOF | ❌ 纯内存 |
| **主从复制** | ✅ 支持 | ❌ 不支持 |
| **集群** | Cluster模式 | 客户端分片 |
| **过期策略** | 惰性+定期 | 惰性 |
| **LRU/LFU** | ✅ 支持 | ✅ LRU |
| **事务** | MULTI/EXEC | ❌ 不支持 |
| **Lua脚本** | ✅ 支持 | ❌ 不支持 |
| **发布订阅** | ✅ 支持 | ❌ 不支持 |
| **最大单Value** | 512MB | 1MB |
| **内存利用率** | ~70%（有元数据开销） | ~90%（高效） |
| **运维工具** | 丰富（监控/管理） | 基础 |

**选型建议**：

| 场景 | 推荐 | 原因 |
|------|------|------|
| 需要丰富数据结构 | Redis | List/Hash/ZSet 等 |
| 需要持久化 | Redis | RDB + AOF |
| 需要高可用 | Redis Cluster | 主从+哨兵 |
| 纯KV缓存+追求极致性能 | Memcached | 多线程无锁 |
| 需要发布订阅 | Redis | 内置 Pub/Sub |

### 6.3 详细选型分析

#### Kafka 适用场景

```
✅ 日志收集与分析（Log → Kafka → Flink/Spark → ES/数仓）
✅ 用户行为追踪（埋点数据 → Kafka → 实时计算）
✅ 流式数据处理（Kafka Streams / Flink source）
✅ 事件溯源（Event Sourcing）
✅ CDC 数据同步（Canal/Debezium → Kafka → 下游）

❌ 不适合：事务消息、延时消息、复杂路由
```

**优势**：
- 吞吐量极高（百万级 TPS）
- 生态完善（Kafka Connect/Streams/KSQL）
- LinkedIn 背景，大厂验证
- 零拷贝 + 顺序写磁盘，性能极致

**劣势**：
- 无事务消息
- 无延时消息（需自建多层 Topic 模拟）
- 无死信队列（需自建）
- Topic 数量过多时性能下降
- 运维较复杂（依赖 ZK / KRaft 仍在过渡期）

#### RocketMQ 适用场景

```
✅ 电商交易系统（事务消息保证最终一致）
✅ 订单超时取消（延时消息）
✅ 分布式事务可靠消息方案
✅ 金融消息通知
✅ 削峰填谷

❌ 不适合：超大规模数据管道（不如Kafka）、微秒级低延迟
```

**优势**：
- 原生事务消息（半消息 + 回查）
- 原生延时消息（18 个级别，5.0+ 支持任意时间）
- 原生死信队列
- 运维简单（NameServer 轻量）
- 阿里大规模验证

**劣势**：
- 吞吐量不如 Kafka
- 生态不如 Kafka 丰富
- 国际化程度不如 Kafka

#### RabbitMQ 适用场景

```
✅ 复杂路由场景（Topic Exchange 模式匹配）
✅ 任务分发（Work Queue / Fair Dispatch）
✅ RPC 异步调用（Reply Queue）
✅ 发布订阅（Fanout Exchange）
✅ IoT 消息推送（MQTT 协议）

❌ 不适合：超高吞吐量、消息堆积场景
```

**优势**：
- 路由模型极其灵活（Direct/Topic/Fanout/Headers）
- 延迟极低（微秒级）
- 协议丰富（AMQP/MQTT/STOMP）
- 消息确认机制完善
- Web 管理界面好用

**劣势**：
- 吞吐量最低（万级 TPS）
- Erlang 语言门槛高（二次开发难）
- 消息堆积性能急剧下降
- 集群扩展性不如 Kafka

#### Pulsar 适用场景

```
✅ 海量 Topic 场景（百万级 Topic）
✅ 多租户隔离
✅ 计算存储分离架构
✅ 需要同时支持队列和流
✅ 云原生架构

❌ 不适合：运维能力不足的团队、需要快速上线的项目
```

### 6.4 消息队列选型检查清单

```
□ 吞吐量需求是多少？（万级 → RabbitMQ，十万级 → RocketMQ，百万级 → Kafka/Pulsar）
□ 是否需要事务消息？（是 → RocketMQ / Pulsar）
□ 是否需要延时消息？（是 → RocketMQ / Pulsar / RabbitMQ+插件）
□ 是否需要顺序消息？（是 → Kafka / RocketMQ / Pulsar）
□ 是否需要消息回溯？（是 → Kafka / RocketMQ / Pulsar）
□ 是否需要复杂路由？（是 → RabbitMQ）
□ Topic 数量预估？（> 10万 → Pulsar）
□ 运维团队能力？（弱 → RocketMQ，强 → Kafka）
□ 是否需要云原生多租户？（是 → Pulsar）
□ 协议要求？（AMQP → RabbitMQ，自定义 → Kafka/RocketMQ）
```

### 9.3 Spring Cloud Gateway 核心架构

```
请求 → RoutePredicate → Filter(pre) → Proxy → 目标服务 → Filter(post) → 响应
         (路由匹配)      (前置过滤)   (转发)                    (后置过滤)
```

**核心概念**：

**选型 Spring Cloud Gateway 的理由**：

- 基于 Reactor 非阻塞，性能优于 Zuul 1.x
- 与 Spring Cloud 生态深度集成
- 丰富的 Predicate 和 Filter

### 11.3 Dubbo 3.x vs gRPC 架构对比

```

  Consumer → Triple协议(HTTP/2) → Provider

  + 丰富的服务治理（路由/负载/限流/熔断）

  Client → gRPC Stub → HTTP/2 → gRPC Server
  + 需要额外注册中心（Consul/etcd）
  + 需要额外治理（Istio/Linkerd）
```

| 对比项 | Dubbo 3.x | gRPC |
|--------|-----------|------|

| 流控 | Sentinel | 需额外集成 |
| 代码生成 | Dubbo IDL | Protobuf |
| 多语言 | Triple 多语言支持 | 原生多语言 |

## 第十六章 常见误区与反模式

### 16.1 误区一：简历驱动开发（Resume-Driven Development）

**症状**：选技术不是为了解决问题，而是为了简历好看。

```
❌ "我们用了 K8s + Istio + Kafka + Flink + ClickHouse"
    → 实际日活 1000 人，一个 MySQL 就够

✅ "我们用 MySQL + Redis + Spring Boot"
    → 日活 5 万，这个技术栈完全匹配
```

**危害**：
- 过度设计，浪费人力和资源
- 运维成本远超收益
- 团队学习曲线陡峭，效率降低
- 系统复杂度增加，故障概率上升

**对策**：始终回到业务需求，用数据说话。

### 16.2 误区二：Not Invented Here（NIH 综合征）

**症状**：不信任开源/现成方案，什么都要自己造。

```
❌ "Redis 的分布式锁不可靠，我们自己用 ZK 写一个"
    → 投入 2 个人 1 个月，最终还不如 Redisson

✅ "我们评估了 Redisson 的 RedLock，满足我们的需求"
    → 1 天接入，稳定运行
```

**危害**：
- 重复造轮子，浪费资源
- 自研组件质量往往不如社区维护的开源项目
- 维护成本长期累积

**对策**：优先使用成熟开源方案，自研仅在核心差异化领域。

### 16.3 误区三：盲目追新

**症状**：新技术一出就用，不顾风险。

```
❌ "Rust 写的服务性能最好，我们用 Rust 重写"
    → 团队无 Rust 经验，2 个月写不完，Bug 频出

✅ "我们评估了 Rust，但团队是 Java 栈，先用 Java 做好"
    → 1 个月上线，后续性能不够再优化
```

**对策**：新技术先在非核心系统试点 3~6 个月，验证后再推广。

### 16.4 误区四：只看功能不看运维

**症状**：选型时只关注功能是否满足，忽略了运维成本。

```
❌ "Cassandra 支持多数据中心，我们用它"
    → 运维团队 0 经验，故障时无人能排查

✅ "我们选了 MySQL 主从，运维成熟，故障处理快"
    → 虽然功能不是最优，但运维成本低
```

**对策**：选型时运维负责人必须参与评审。

### 16.5 误区五：不考虑团队能力

**症状**：选了一个技术上最优但团队完全不会的方案。

```
❌ "Go 的性能比 Java 好，微服务全用 Go"
    → 团队全是 Java 开发，Go 项目延期 3 个月

✅ "我们评估了 Go，决定核心服务用 Java，性能瓶颈点用 Go"
    → 充分利用团队现有能力
```

**对策**：评估团队匹配度，必要时安排培训和过渡期。

### 16.6 误区六：一步到位的架构

**症状**：一开始就按终态架构设计，导致过度设计。

```
❌ "我们要支持千万级用户，直接上分库分表 + 微服务 + Kafka"
    → 实际用户 500 人，80% 资源闲置

✅ "先单体应用上线，3 个月内验证业务模式"
    → 业务跑通后再逐步拆分
```

**对策**：架构要预留扩展空间，但实现要匹配当前阶段。

### 16.7 误区七：忽视 License 风险

**症状**：不看 License 就引入，上线后才发现合规问题。

```
❌ "MySQL 社区版是免费的，直接用"
    → GPL 协议有传染性，如果修改了 MySQL 源码并分发，需要开源

❌ "MongoDB 也免费"
    → SSPL 协议，云厂商不能直接提供服务

✅ "我们评估了 License，MySQL GPL 对我们不构成风险（只是使用不修改源码）"
    → 合规先行
```

**对策**：法务参与核心组件 License 评估。

### 16.8 误区八：忽视迁移成本

**症状**：只评估新技术的好处，忽略了从旧系统迁移的代价。

```
❌ "从 MySQL 迁移到 PostgreSQL 只需要改配置"
    → 实际 SQL 方言差异、存储过程、ORM 兼容性一堆问题

✅ "迁移方案需要 3 个月：数据双写 → 数据校验 → 灰度切流 → 旧系统下线"
    → 充分评估迁移成本
```

**对策**：选型时必须包含迁移方案和成本评估。

### 16.9 误区九：忽视监控可观测性

**症状**：选了技术但没配套监控方案。

```
❌ "用了 RocketMQ 就行了"
    → 消息堆积了不知道，消费者挂了不知道，等用户投诉才发现

✅ "RocketMQ + Prometheus Exporter + Grafana Dashboard + 告警规则"
    → 消息延迟 > 5s 自动告警
```

**对策**：任何技术引入都要配套监控、告警、Dashboard。

### 16.10 误区十：技术选型一锤定音

**症状**：认为选了就不能换，过度纠结。

```
❌ 选型纠结 3 个月，业务等不了先用了简单方案

✅ 选型 1 周确定，预留架构扩展点，后续可平滑替换
```

**对策**：架构设计要遵循**依赖倒置原则**，通过接口隔离具体实现，降低替换成本。

```
// 好的设计：面向接口编程
public interface MessageQueue {
    void send(String topic, Object message);
}

// 实现 A：RocketMQ
public class RocketMQMessageQueue implements MessageQueue { ... }

// 实现 B：Kafka（需要切换时只需替换实现）
public class KafkaMessageQueue implements MessageQueue { ... }
```

| 监控 | Prometheus / Zabbix | Prometheus+Grafana | 云原生标配 |
| 日志 | ELK / PLG | ELK | 全文搜索 |
| 链路追踪 | SkyWalking / Jaeger | SkyWalking | 字节码增强无侵入 |

**决策依据**：
1. 团队 Java 技术栈 → Spring Cloud Alibaba 一体化方案
2. 电商核心需求 → 事务消息 + 延时消息 → RocketMQ
3. 小团队 → 运维简单的方案优先（Nacos 一体化）
4. 预留扩展 → MySQL 后续可平滑迁移 TiDB

### 17.2 案例二：日志平台选型演进

**背景**：某中型公司，日均日志 500GB，需要日志检索和分析。

**阶段一（MVP）**：ELK
```
Filebeat → Logstash → Elasticsearch → Kibana
```
- 优点：开箱即用，功能完善
- 痛点：ES 存储成本高，500GB/天 = 15TB/月

**阶段二（降本）**：EFK + 冷热分离
```
Fluent Bit → Elasticsearch(热7天) → Elasticsearch(冷30天) → S3(归档)
```
- 优点：冷热分离降低成本
- 痛点：ES 运维复杂

**阶段三（替代方案评估）**：

| 方案 | 存储成本 | 查询能力 | 运维复杂度 | 迁移成本 |
|------|---------|---------|-----------|---------|
| 继续 ELK | 高 | 强 | 中 | - |
| 迁移 Loki | 低 1/10 | 弱(标签过滤) | 低 | 中 |
| 混合方案 | 中 | 中 | 中 | 中 |

**最终方案**：混合
```
实时日志（7天）→ Loki + Grafana    → 快速查询，低成本
审计日志（90天）→ Elasticsearch     → 全文搜索
归档日志（1年）→ S3 + Athena        → 按需查询
```

### 17.3 案例三：从单体到微服务的选型演进

**阶段一：单体应用**
```
Spring Boot + MySQL + Redis
→ 日活 1 万，QPS 100，足够
```

**阶段二：垂直拆分**
```
用户服务 + 订单服务 + 商品服务（独立部署）
共享 MySQL（不同库）
→ 日活 10 万，QPS 500
```

**阶段三：微服务化**
```
引入 Spring Cloud Alibaba：
  Nacos（注册+配置）
  OpenFeign（服务间调用）
  Gateway（API 网关）
  Sentinel（限流熔断）
  RocketMQ（异步解耦）
  Seata（分布式事务）
  SkyWalking（链路追踪）
→ 日活 50 万，QPS 5000
```

**阶段四：进一步优化（按需）**
```
高流量服务 → Dubbo RPC 替代 HTTP
搜索服务 → Elasticsearch 独立集群
数据分析 → ClickHouse OLAP
→ 日活百万级
```

**关键决策**：不是一步到位，而是按业务规模逐步演进。每一步都有充分的业务驱动，而非技术驱动。

### 17.4 案例四：数据库选型——MySQL 到 TiDB 的迁移

**背景**：某 SaaS 平台，单表数据量 5 亿行，MySQL 分库分表后运维痛苦。

**选型分析**：

| 维度 | MySQL + ShardingSphere | TiDB |
|------|----------------------|------|
| 运维 | 分库分表规则复杂 | 自动分片，透明 |
| 扩展 | 需停服扩容 | 在线扩容 |
| 分布式事务 | XA 性能差 | 原生支持 |
| SQL 兼容 | 100% | 95%+ |
| 学习成本 | 低 | 中 |
| 性能 | 单机高 | 分布式开销 |

**迁移方案**：
```
阶段一：双写（MySQL 主 → TiDB 同步）
阶段二：读流量切 TiDB（灰度 10%→50%→100%）
阶段三：写流量切 TiDB
阶段四：MySQL 降级为备库
```

**经验教训**：
- TiDB 单机性能不如 MySQL（分布式开销）
- 适合数据量大、需要水平扩展的场景
- 小数据量（< 1000 万行）不需要 TiDB

## 第十八章 面试高频题

### Q1：如何做技术选型？请描述你的方法论

**标准回答**：

> 技术选型我会遵循"六步法"：
> 
> **第一步需求分析**：明确业务场景、性能要求、可靠性要求、约束条件，形成需求文档。
> 
> **第二步候选方案收集**：通过技术调研、同行交流、社区调研等渠道收集候选方案，初筛后保留 2~3 个。
> 
> **第三步维度评估**：从功能适配度、性能表现、可靠性、可维护性、成本、团队匹配度、生态成熟度七个维度逐一打分，量化对比。不同场景下各维度权重不同——比如金融系统可靠性权重最高，社交系统性能权重最高。
> 
> **第四步 POC 验证**：对 Top 1~2 方案搭建测试环境做原型验证，重点验证关键功能和性能指标。
> 
> **第五步决策评审**：组织架构师、技术负责人、运维负责人评审，达成共识后形成选型文档。
> 
> **第六步落地计划**：制定分阶段迁移方案，包括培训、试点、推广、回滚预案。
> 
> 核心原则是"业务驱动、合适优先、成熟优先、可运维、团队匹配"，避免过度设计和盲目追新。

### Q2：Kafka 和 RocketMQ 怎么选？

**标准回答**：

> 核心看**业务场景**和**功能需求**：
> 
> **选 Kafka**：大数据场景、日志收集、流式处理。Kafka 吞吐量最高（百万级 TPS），生态完善（Kafka Connect/Streams/KSQL），适合做数据管道。但 Kafka 不支持事务消息、延时消息、死信队列，这些需要自建。
> 
> **选 RocketMQ**：电商交易场景、金融场景。RocketMQ 原生支持事务消息（半消息+回查）、延时消息（18 个级别）、死信队列、消息回溯。运维也更简单（NameServer 轻量无状态）。吞吐量十万级 TPS，比 Kafka 低但够用。
> 
> **实际选择**：如果是电商系统（订单→库存→物流），我会选 RocketMQ，因为需要事务消息保证订单和消息的一致性，需要延时消息做超时取消。如果是日志收集或用户行为埋点，选 Kafka。
> 
> 如果两者都需要，可以混用：交易用 RocketMQ，日志用 Kafka。

### Q3：你们项目的微服务技术栈是怎么选的？为什么选 Spring Cloud Alibaba？

**标准回答**：

> 我们选的是 Spring Cloud Alibaba 全家桶：
> - **Nacos**：注册中心 + 配置中心
> - **Gateway**：API 网关
> - **OpenFeign**：服务间调用
> - **Sentinel**：限流熔断降级
> - **Seata**：分布式事务
> - **RocketMQ**：消息队列
> - **SkyWalking**：链路追踪
> 
> 选型理由：
> 1. **一体化方案**：Nacos 同时做注册和配置，减少技术栈数量
> 2. **Spring 生态**：与 Spring Boot 无缝集成，开发体验好
> 3. **阿里大规模验证**：双 11 级别验证，可靠性有保障
> 4. **团队匹配**：团队 Java 技术栈，学习成本低
> 5. **中文社区活跃**：遇到问题容易找到解决方案
> 
> 也考虑过 Dubbo，但当时 Spring Cloud Alibaba 生态更完整，且 HTTP 通信虽然性能不如 RPC，但更通用、调试更方便。如果后续某些服务性能成为瓶颈，可以用 Dubbo 替换特定服务的通信。

### Q4：MySQL 和 MongoDB 怎么选？

**标准回答**：

> 核心看**数据模型**和**事务需求**：
> 
> **选 MySQL**：数据是关系型的、需要强事务（ACID）、需要复杂 JOIN 查询、数据一致性要求高。比如订单、支付、账户系统。
> 
> **选 MongoDB**：数据结构灵活多变、不需要复杂 JOIN、写多读少、需要水平扩展。比如内容管理、用户画像、IoT 设备数据、日志存储。
> 
> **关键区别**：MongoDB 的跨文档事务性能远不如 MySQL 的单机事务。虽然 MongoDB 4.0+ 支持多文档事务，但性能下降明显。所以强事务场景一定选 MySQL。
> 
> **实际建议**：如果不确定，先用 MySQL。MySQL 的 JSON 字段类型可以存储文档数据，在数据量不大的情况下可以兼顾关系型和文档型需求。如果确实需要 MongoDB 的灵活性，可以在特定模块引入，而非全盘替换。

### Q5：如何评估一个技术的成熟度？

**标准回答**：

> 我会从六个维度评估：
> 
> 1. **GitHub 指标**：Star 数、Fork 数、Issue 处理速度、PR 合并频率。Star > 5k 算有一定社区基础，> 20k 算主流。
> 
> 2. **生产案例**：是否有知名公司在生产环境使用？比如 Kafka 有 LinkedIn，RocketMQ 有阿里。
> 
> 3. **版本稳定性**：是否频繁 Breaking Change？是否遵循语义化版本？是否有 LTS（长期支持）版本？
> 
> 4. **文档质量**：官方文档是否完善？是否有最佳实践？是否有从入门到精通的完整教程？
> 
> 5. **工具链**：是否有成熟的开发、测试、部署、监控工具？比如 Prometheus 有丰富的 Exporter 生态。
> 
> 6. **商业支持**：是否有商业公司背书？出问题能否找到商业支持？比如 Kafka 有 Confluent，Redis 有 Redis Labs。
> 
> 核心系统选四星以上（GitHub > 20k、多家大厂验证、文档完善、有商业支持），非核心可选三星。

### Q6：技术选型时如何考虑团队能力？

**标准回答**：

> 团队能力是技术选型的**约束条件**，不是可选项。我会从四个方面评估：
> 
> 1. **技术栈匹配度**：团队是否有相关经验？比如团队是 Java 栈，引入 Go 需要评估学习成本。
> 
> 2. **学习曲线**：评估团队需要多长时间上手。简单技术 1~2 周，复杂技术 1~2 个月。核心系统不建议用完全陌生的技术。
> 
> 3. **招聘难度**：市场上该技术的人才是否充足？比如 Java 开发容易招，Rust 开发难招。
> 
> 4. **人员流动风险**：如果核心人员离职，其他人能否接手？是否有文档和知识传递机制？
> 
> **实践策略**：
> - 核心系统用团队熟悉的技术
> - 非核心系统可以试点新技术
> - 引入新技术前安排培训和 PoC
> - 确保至少 2~3 人掌握，避免单点风险

### Q7：Redis 和 Memcached 怎么选？

**标准回答**：

> **绝大多数场景选 Redis**，因为 Redis 功能更全面：
> - 丰富的数据结构（String/List/Hash/Set/ZSet/Stream/HyperLogLog/Geo）
> - 持久化（RDB + AOF）
> - 主从复制 + 哨兵 + Cluster
> - 发布订阅、Lua 脚本、事务
> - 分布式锁（SET NX + RedLock）
> 
> **选 Memcached 的场景**比较少：
> - 纯 KV 缓存 + 追求极致单实例性能（多线程，QPS 50 万+）
> - 不需要持久化
> - 不需要复杂数据结构
> - 内存利用率要求高（Memcached 无元数据开销）
> 
> 实际项目中，如果已经用了 Redis，没有理由再引入 Memcached。Redis 6.0+ 也支持多线程 IO，单线程的 CPU 瓶颈已大幅缓解。

### Q8：如何避免技术选型的过度设计？

**标准回答**：

> 过度设计的本质是"**用未来的可能需求驱动当前的架构决策**"。我会通过以下方式避免：
> 
> 1. **以当前 + 1 年内可预期的规模为基准**设计，不为 3 年后的可能需求过度设计。
> 
> 2. **预留扩展点而非提前实现**。比如设计时面向接口编程，不绑死具体实现。需要切换时只需替换实现类。
> 
> 3. **先单体后微服务**。业务验证阶段用单体快速迭代，业务跑通后再按需拆分。
> 
> 4. **先单机后集群**。QPS 不高时单机够用，性能不够再加集群。
> 
> 5. **用数据说话**。压测验证当前方案能否扛住预期负载，而非凭感觉认为"不够"。
> 
> 6. **遵循 YAGNI 原则**（You Aren't Gonna Need It）。不需要的功能不提前开发。
> 
> 经典反例：日活 1000 的内部系统用了 K8s + Istio + Kafka + 微服务，80% 资源闲置，运维成本远超收益。

### Q9：技术选型后发现选错了怎么办？

**标准回答**：

> 选型后发现不合适是正常情况，关键是如何**平滑迁移**：
> 
> 1. **评估影响范围**：影响多大？是性能不达标、功能缺失、还是运维成本过高？
> 
> 2. **制定迁移方案**：通常采用"双写 → 校验 → 灰度切换 → 旧系统下线"的渐进式迁移：
>    - 阶段一：新系统与旧系统双写，保证数据一致
>    - 阶段二：读流量灰度切换到新系统（10%→50%→100%）
>    - 阶段三：写流量切换到新系统
>    - 阶段四：旧系统降级为备库，观察一段时间后下线
> 
> 3. **准备回滚方案**：每个阶段都有回滚预案，发现问题立即切回旧系统。
> 
> 4. **总结复盘**：分析选错的原因，是需求分析不足、还是评估维度缺失，避免下次重复。
> 
> **预防措施**：选型时做充分的 POC 验证，不要跳过原型验证阶段。

### Q10：如何评估引入新技术的风险？

**标准回答**：

> 我会从五个维度评估风险：
> 
> 1. **技术风险**：是否经过大规模生产验证？是否有已知 Bug？是否有 Breaking Change 的版本计划？
> 
> 2. **运维风险**：是否有成熟的监控/告警/部署方案？故障时能否快速恢复？是否需要专门的运维人员？
> 
> 3. **人员风险**：团队是否有能力驾驭？核心人员离职后能否接手？招聘市场是否充足？
> 
> 4. **集成风险**：与现有系统的集成是否顺畅？是否有兼容性问题？是否需要修改现有系统？
> 
> 5. **商业风险**：开源项目是否会停止维护？是否会修改 License？是否有商业公司持续投入？
> 
> **风险应对策略**：
> - 高风险技术先在非核心系统试点 3~6 个月
> - 通过接口隔离降低替换成本
> - 制定回滚/迁移预案
> - 限制使用范围，不全面铺开
> - 关注社区动态，评估项目健康度

## 附录：技术选型检查清单

### A. 选型前检查

```
□ 业务需求是否已明确？（功能/性能/可靠性/约束）
□ 是否收集了足够多的候选方案？（至少 2~3 个）
□ 是否评估了七个维度？（功能/性能/可靠性/可维护性/成本/团队/生态）
□ 是否做了 POC 验证？（核心功能+性能压测）
□ 是否评估了迁移成本？（从旧系统迁移的代价）
□ 是否评估了运维成本？（长期运维投入）
□ 是否评估了团队匹配度？（学习曲线/招聘/培训）
□ License 是否合规？（GPL/AGPL/SSPL 风险）
□ 是否有监控/告警方案？（可观测性）
□ 是否有回滚/降级方案？（故障预案）
```

### B. 选型后检查

```
□ 是否形成了选型文档？（需求/对比/决策/理由）
□ 是否制定了落地计划？（培训/试点/推广/回滚）
□ 是否有运维手册？（部署/配置/监控/故障排查）
□ 是否有最佳实践文档？（开发规范/常见问题）
□ 是否安排了培训？（团队学习）
□ 是否设定了试点验证标准？（什么算成功/什么算失败）
□ 是否评估了 3 年后的可持续性？（项目是否健康）
```

### C. 技术选型红线

```
❌ 核心系统用团队完全陌生的技术
❌ 核心系统用 GitHub Star < 1k 的项目
❌ 引入无生产案例验证的技术
❌ 忽视 License 合规风险
❌ 选型时无运维人员参与
❌ 过度设计（当前需求 vs 远超需求的技术）
❌ 无 POC 直接全量上线
❌ 无监控方案就上线
❌ 无回滚方案就迁移
❌ 为简历选技术而非为业务选技术
```

---

> **总结**：技术选型不是一次性的决定，而是一个持续评估和演进的过程。没有完美的技术，只有最适合当前阶段的选择。好的架构师不是什么技术都用，而是知道什么场景该用什么，更重要的是知道什么**不该用**。
> 
> 记住：**用合适的技术解决合适的问题，而非用最好的技术解决所有问题。**
