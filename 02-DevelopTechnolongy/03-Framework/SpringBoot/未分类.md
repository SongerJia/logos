### 01 自动配置原理（8 个）— Spring Boot 的核心灵魂

这是面试问 Spring Boot 时**绝对第一题**，没有之一：

|知识点|笔记时重点写什么|
|---|---|
|**@SpringBootApplication 拆解**|热 三个注解的组合：`@SpringBootConfiguration`（= @Configuration，标识配置类）、`@EnableAutoConfiguration`（开启自动配置）、`@ComponentScan`（组件扫描）。**能拆出来就赢了一半**|
|**@EnableAutoConfiguration 工作原理**|热 通过 `@Import(AutoConfigurationImportSelector.class)` 导入选择器，在 `selectImports()` 中读取 `META-INF/spring.factories` 文件，加载所有自动配置类的全限定名。然后经过条件过滤后生效|
|**spring.factories 加载机制**|热 SPI 机制（Service Provider Interface）。Spring Boot 从所有 jar 包的 META-INF/spring.factories 收集 key=value 配置。Spring Boot 2.7+ 开始迁移到 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`（新版方式）|
|**@Conditional 系列条件注解**|核 自动配置的"开关"。最常用的：@ConditionalOnClass（classpath 存在某类才生效）、@ConditionalOnMissingBean（容器中没有某 Bean 才创建——**用户优先原则**）、@ConditionalOnProperty（配置文件中有某属性）、@ConditionalOnWebApplication（是 Web 环境才生效）。建议列一张完整的 @Conditional 族谱表|
|**自动配置完整流程**|核 候选收集（spring.factories 全量读取）→ 排除指定类（exclude 属性）→ 条件过滤（@Conditional 匹配）→ 注册为 BeanDefinition → 最终实例化。**画成流水线图**：从左到右经过每道过滤门，最终存活的才是生效的配置|

> **笔记技巧**：自动配置原理强烈建议画一张**从 @SpringBootApplication 到某个具体 Bean 被创建的全链路图**。以 DataSourceAutoConfiguration 为例：启动 → @EnableAutoConfiguration → spring.factories → 读取到它 → @ConditionalOnClass(HikariDataSource.class) → 检查 classpath 有 HikariCP → 创建 HikariDataSource Bean。这条线画清楚了，整个自动配置就通了。

### 02 启动流程与运行原理（8 个）

|知识点|笔记时重点写什么|
|---|---|
|**SpringApplication.run() 流程**|热 约 15 步，核心可压缩为 6 步：StopWatch 计时开始 → 获取监听器 → prepareEnvironment（加载配置） → createApplicationContext（创建容器） → prepareContext（预刷新） → refreshContext（调用 Spring 的 refresh()）。**refresh() 就是前面 Spring Core 那套十二步**|
|**构造器初始化三件事**|热 ①推断 Web 应用类型（SERVLET / REACTIVE / NONE）②从 spring.factories 加载 ApplicationContextInitializer ③从 spring.factories 加载 SpringApplicationRunListener|
|**run() 核心步骤**|核 prepareContext 阶段做了什么？把 main 方法所在的类注册为 BeanDefinition、加载 primarySources（启动类）、发布 ApplicationContextInitializedEvent。refreshContext 阶段就是调用了 AbstractApplicationContext.refresh()。afterRefresh 阶段执行 CommandLineRunner/ApplicationRunner|
|**内嵌容器原理**|核 在 refresh() 的 onRefresh() 阶段创建 Web 容器。Tomcat 通过 TomcatServletWebServerFactory 创建 Tomcat 对象 → 配置 Connector / Engine / Host → 启动。这就是为什么 `java -jar xxx.jar` 能直接跑 Web 应用——不需要外部 Tomcat 了|
|**SpringApplicationRunListener 与事件**|热 run 过程中发布了 9 个事件：starting → environmentPrepared → contextPrepared → contextLoaded → started → ready 等。每个事件的触发时机要能对应到 run() 方法的哪一行|
|**CommandLineRunner / ApplicationRunner**|热 容器完全启动后执行的回调。区别：ApplicationRunner 的参数是 ApplicationArguments（更强大），CommandLineRunner 是 String[]。@Order 控制多个 Runner 的执行顺序。典型用途：预热缓存 / 初始化数据 / 检查数据库连接|

> **笔记技巧**：run() 流程和前面的 `refresh()` 十二步有重叠部分（refreshContext 内部就是调 refresh()），笔记里可以标注"此处跳转到 Spring Core-06"。不要重复写，用链接串起来。

### 03 Starter 机制（7 个）— 理解约定大于配置

|知识点|笔记时重点写什么|
|---|---|
|**Starter 本质是什么**|热 一个依赖传递器 + 一套自动配置。引入 `spring-boot-starter-web` = 同时引入了 spring-webmvc + jackson + hibernate-validator + tomcat-embed + 对应的 AutoConfiguration。你不用管版本兼容问题，Starter 统一管理了|
|**标准目录结构**|热 官方 Starter 都是双模块设计：`xxx-spring-boot-autoconfigure`（自动配置代码，不含依赖）+ `xxx-spring-boot-starter`（空 jar，只依赖 autoconfigure + 第三方库）。为什么分两个？（因为 autoconfigure 可以被单独引用，starter 只是个聚合器）|
|**自定义 Starter 完整步骤**|核 ①建 autoconfigure 模块 ②写 XxProperties（@ConfigurationProperties 绑定配置）③写 XxAutoConfiguration（@Conditional + @Bean 创建核心组件）④META-INF/spring.factories 注册 ⑤建 starter 模块依赖 autoconfigure ⑥使用方引入 starter 即可用。**这 6 步能手写出来就够用了**|
|**常用 Starter 一览**|热 web（Tomcat+MVC）、data-jpa/MyBatis（ORM）、data-redis（Redis）、amqp（RabbitMQ）、security（安全）、actuator（监控）、test（测试）。每个 Starter 引入的核心依赖要心里有数|

### 04 配置体系（7 个）— 日常开发高频

|知识点|笔记时重点写什么|
|---|---|
|**@ConfigurationProperties vs @Value**|热 **必考对比**。@ConfigurationProperties 支持松散绑定、支持 JSR303 校验、支持复杂类型（Map/List/嵌套对象）；@Value 支持 SpEL 表达式但只能单个字段注入。官方推荐批量配置用前者，个别值用后者|
|**Profile 多环境切换**|热 application.yml（公共配置）→ application-dev.yml / application-prod.yml。激活方式：`spring.profiles.active=dev` 或命令行参数或环境变量。还可以用 @Profile 注解控制 Bean 在特定环境下生效|
|**配置加载优先级**|共 17 种来源（Spring Boot 2.x+），记住前几个关键的就够了：命令行参数 > 环境变量 > application-{profile}.yml > application.yml > @PropertySource > 默认值。高优先级覆盖低优先级|
|**松散绑定 RelaxedBinding**|热 配置文件中 `my.app.user-name` / `my.app.userName` / `my.app.user_name` 都可以绑定到 Java 类的 `userName` 字段。这是 @ConfigurationProperties 特有的能力，@Value 不支持|

> **笔记技巧**：做一个**配置速查卡**：常用配置项按类别整理（Server端口/数据源/日志/JVM/MVC/Actuator），每个配默认值和典型修改值。跳槽前翻一遍就能快速回忆。

### 05 Actuator 监控（6 个）— 运维必备

|知识点|笔记时重点写什么|
|---|---|
|**核心端点一览**|热 `/health`（健康状态，DB/Redis/DiskSpace 等子指标）、`/info`（应用信息）、`/metrics`（JVM内存/GC/线程池/HTTP请求计数等）、`/env`（全部配置信息！**生产环境慎开**）、`/beans`（所有 Bean 列表）、`/mappings`（所有 URL 映射）、`/loggers`（动态调整日志级别）|
|**/health 健康检查**|热 返回 UP / DOWN / OUT_OF_SERVICE / UNKNOWN。Kubernetes 就是通过 /health 做 Pod 存活探测的。可以自定义 HealthIndicator 来加入业务指标（如第三方 API 是否可达）|
|**/metrics 自定义 Metrics**|热 用 MeterRegistry 注册 Counter（计数）/ Gauge（瞬时值）/ Timer（计时）。典型场景：统计订单创建数、接口响应时间分布、当前在线用户数。配合 Prometheus + Grafana 出可视化大盘|
|**安全配置**|默认只开放 `/health` 和 `/info`。需要暴露更多端点：`management.endpoints.web.exposure.include=*`。生产环境一定要配合 Spring Security 限制访问权限，特别是 `/env`（会泄露密钥密码）|

### 06 日志框架（5 个）

|知识点|说明|
|---|---|
|**Logback + SLF4J**|热 Spring Boot 默认组合：SLF4J 作为门面（API层），Logback 作为实现。日志级别：ERROR > WARN > INFO > DEBUG > TRACE。默认输出 INFO 以上。通过 `logging.level.com.xxx=debug` 控制|
|**logback-spring.xml vs logback.xml**|热 推荐 logback-spring.xml，因为它能使用 Spring Boot 的 `<springProfile>` 标签按环境区分日志配置。logback.xml 由 Logback 直接加载，无法感知 Spring Profile|
|**生产环境最佳实践**|分级输出（INFO 写文件 / ERROR 单独报警文件）、滚动策略（按天/按大小归档压缩）、JSON 格式（方便 ELK 解析）、敏感信息脱敏|

### 07 高级特性与扩展（7 个）— 加分项

|知识点|说明|
|---|---|
|**2.x vs 3.x 主要差异**|JDK17 基线、javax → jakarta 命名空间（Servlet/JPA/Validation 全部改名）、原生镜像支持 GraalVM Native Image、javax.servlet.ServletException 变 jakarta.servlet.ServletException（**升级最大的坑在这里**）|
|**内嵌容器切换**|排除 tomcat 引入 jetty（适合长连接/WebSocket 场景）或 undertow（高吞吐低内存）。在 starter-web 中排除 tomcat 即可：`<exclusions><exclusion><groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-tomcat</artifactId></exclusion></exclusions>`|
|**优雅停机 Graceful Shutdown**|`server.shutdown=graceful` + `spring.lifecycle.timeout-per-shutdown-phase=30s`。停机时不再接受新请求，等待进行中的请求处理完毕后再关闭。配合 K8s 的 preStop hook 使用|
|**切片测试**|@SpringBootTest（全量集成测试，启动完整容器）vs @WebMvcTest（只测 Controller 层）vs @DataJpaTest（只测 DAO 层）vs @JsonTest（只测 JSON 序列化）。**切片测试比全量快 10 倍以上，推荐日常开发用**|

## Spring Boot 整体优先级

```
第一梯队（面试必考，必须深入到源码）：
  01 自动配置原理  >  02 启动流程 run()

第二梯队（高频问答 + 工程实践）：
  04 配置体系  >  03 Starter 机制  >  05 Actuator 监控

第三梯队（了解即可，用到再查）：
  06 日志框架  >  07 高级特性
```

**推荐笔记顺序**：`01 → 03 → 02 → 04 → 05 → 06 → 07`

理由：先搞懂自动配置(01)这个核心机制，再看它是怎么被封装成 Starter 交付的(03)，然后理解整个启动过程(02)把前面串联起来，接着是日常用的配置(04)，再到运维需要的监控(05)和日志(06)，最后补充高级特性(07)。

## Spring Boot 与前后模块的关键连接点

```
Spring Core                          Spring Boot
─────────                            ───────────
ApplicationContext.refresh()        → SpringApplication.run() 内部调用了 refresh()
@Bean / @Component                  → @AutoConfiguration + @Conditional 自动装配
Environment / PropertySource        → application.yml 统一管理，支持 Profile 切换
BeanPostProcessor                   → AutoConfigurationImportSelector 也是 BPP 思路
FactoryBean                         → 内嵌容器的 ServletWebServerFactory 就是工厂 Bean

Spring MVC                          Spring Boot
─────────                            ───────────
DispatcherServlet                   → 自动注册到内嵌 Tomcat，不需要 web.xml
ViewResolver                         → 自动配置 Thymeleaf/FreeMarker 解析器
Filter                               → 自动配置 CharacterEncodingFilter（UTF-8）
@RequestBody / @ResponseBody         → 自动配置 Jackson HttpMessageConverter
```
