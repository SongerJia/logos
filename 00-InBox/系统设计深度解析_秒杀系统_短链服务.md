# 第一篇：秒杀系统设计

## 第一章 需求分析与核心挑战

### 1.1 什么是秒杀系统

秒杀系统是一种**限时限量**的极端高并发场景：在极短时间内（通常几秒到几分钟），大量用户抢购极少量商品（库存通常几十到几百）。

**典型场景**：
- 电商大促：618/双11 限时抢购
- 优惠券发放：限量优惠券/红包
- 抢票系统：演唱会/火车票
- 新品首发：限量发售

### 1.2 秒杀系统的三大核心挑战

```
┌─────────────────────────────────────────────────────┐
│              秒杀系统三大核心挑战                      │
├─────────────┬─────────────┬─────────────────────────┤
│   高并发     │   防超卖    │      高可用              │
├─────────────┼─────────────┼─────────────────────────┤
│ 瞬时QPS暴增  │ 多人抢同一  │ 任何节点故障              │
│ 正常100→    │ 库存，必须   │ 不能影响下单              │
│ 秒杀10万+   │ 绝对不能    │ 核心：兜底+降级            │
│             │ 超卖        │ +熔断+限流               │
└─────────────┼─────────────┼─────────────────────────┤
│ 读多写少     │ 库存→0后    │ 避免雪崩效应              │
│ 99%查询     │ 必须立即     │ 挡住无效流量              │
│ 1%下单      │ 拦截后续请求 │ 保护DB不被压垮            │
└─────────────┴─────────────┴─────────────────────────┤
│  核心矛盾：流量极大，但有效请求极少                      │
│  解题思路：层层过滤，把99%的无效流量挡在最外层           │
└─────────────────────────────────────────────────────┘
```

### 1.3 秒杀系统数据特征

| 特征 | 正常系统 | 秒杀系统 |
|------|---------|---------|
| QPS | 100~1000 | 10万~100万 |
| 读写比例 | 7:3 | 99:1 |
| 库存 | 充足 | 极少(几十~几百) |
| 有效请求 | 大部分有效 | 99%无效(库存不足后) |
| 持续时间 | 持续 | 极短(几秒) |
| 超卖容忍 | 低(可补偿) | 零容忍(绝对不能超卖) |

### 1.4 秒杀系统设计原则

1. **层层拦截**：把无效流量挡在最外层，越往后流量越小
2. **读多写少**：尽量读缓存，写操作异步化
3. **兜底优先**：任何环节都有兜底方案，宁可少卖不能超卖
4. **快速失败**：不满足条件的请求快速返回，不占用资源
5. **横向扩展**：无状态服务，方便扩容

### 2.3 核心设计思路

**核心思路 = 分层过滤 + 异步化 + 缓存预热**

|------|---------|---------|---------|

| Nginx | IP限流+Lua预判 | 87.5% | 重复/恶意请求 |
| 应用层 | 风控+本地缓存标记 | 50% | 不合规请求 |
| Redis | 原子扣减+资格标记 | 98% | 库存不足请求 |
| MySQL | 乐观锁兜底 | 0 | 最终一致性保障 |

**秒杀按钮URL动态化**：防止提前刷接口

```java
// 秒杀URL动态生成服务
@Service
public class SeckillUrlService {

    // MD5盐值，防止逆向推算
    private static final String SALT = "seckill_salt_2026";

    /**
     * 生成秒杀URL（含加密校验参数）
     * 只有在秒杀时间窗口内才能获取有效URL
     */
    public String generateSeckillUrl(Long userId, Long goodsId) {
        // 1. 校验秒杀时间窗口
        SeckillGoods goods = seckillGoodsMapper.selectById(goodsId);
        long now = System.currentTimeMillis();
        if (now < goods.getStartTime().getTime()) {
            return null; // 秒杀未开始
        }
        if (now > goods.getEndTime().getTime()) {
            return null; // 秒杀已结束
        }

        // 2. 校验库存
        if (goods.getStockCount() <= 0) {
            return null; // 库存为0
        }

        // 3. 生成加密URL
        String md5 = DigestUtils.md5Hex(userId + "_" + goodsId + "_" + SALT);
        return "/seckill/execute?goodsId=" + goodsId + "&md5=" + md5;
    }

    /**
     * 校验秒杀URL合法性
     */
    public boolean validateSeckillUrl(Long userId, Long goodsId, String md5) {
        String expected = DigestUtils.md5Hex(userId + "_" + goodsId + "_" + SALT);
        return expected.equals(md5);
    }
}
```

## 第四章 Nginx限流层设计

### 4.1 Nginx限流配置

```nginx
# 秒杀接口限流配置
# 1. 按IP限流：每个IP每秒最多1次请求
limit_req_zone $binary_remote_addr zone=seckill_ip:10m rate=1r/s;

# 2. 按接口限流：秒杀接口总体QPS上限
limit_req_zone $server_name zone=seckill_total:10m rate=1000r/s;

server {
    listen 80;
    server_name seckill.example.com;

    # 秒杀接口限流
    location /seckill/execute {
        # IP限流：burst=5允许短时5个排队，nodelay不延迟处理
        limit_req zone=seckill_ip burst=5 nodelay;

        # 总体限流
        limit_req zone=seckill_total burst=100 nodelay;

        # 限流后返回自定义错误
        limit_req_status 429;

        proxy_pass http://seckill_backend;
    }

    # 秒杀URL获取接口（更宽松的限流）
    location /seckill/url {
        limit_req zone=seckill_ip burst=10 nodelay;
        proxy_pass http://seckill_backend;
    }
}
```

## 第五章 应用服务层设计

### 5.1 秒杀服务核心流程

```java
@Service
public class SeckillService {

    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    @Autowired
    private RocketMQTemplate rocketMQTemplate;
    @Autowired
    private SeckillUrlService urlService;

    // 本地库存标记（JVM级别缓存，库存为0快速失败）
    private volatile Map<Long, Boolean> localStockMap = new ConcurrentHashMap<>();

    /**
     * 秒杀执行核心流程
     * 整体思路：校验 → Redis预扣 → 发MQ → 异步下单
     */
    public SeckillResult executeSeckill(Long userId, Long goodsId, String md5) {
        // ========== 第一关：URL校验 ==========
        if (!urlService.validateSeckillUrl(userId, goodsId, md5)) {
            return SeckillResult.fail("非法请求，URL校验失败");
        }

        // ========== 第二关：本地缓存快速失败 ==========
        if (localStockMap.containsKey(goodsId) && !localStockMap.get(goodsId)) {
            return SeckillResult.fail("商品已售罄");
        }

        // ========== 第三关：Redis资格校验（防止重复秒杀）==========
        String seckillFlagKey = "seckill:flag:" + userId + ":" + goodsId;
        Boolean isFirst = redisTemplate.opsForValue().setIfAbsent(
            seckillFlagKey, "1", Duration.ofSeconds(3600)
        );
        if (Boolean.FALSE.equals(isFirst)) {
            return SeckillResult.fail("您已参与过该商品秒杀，不可重复抢购");
        }

        // ========== 第四关：Redis原子扣减库存 ==========
        Long stock = redisTemplate.opsForValue().decrement("seckill:stock:" + goodsId);
        if (stock == null || stock < 0) {
            // 库存不足，回滚Redis扣减
            redisTemplate.opsForValue().increment("seckill:stock:" + goodsId);
            // 设置本地缓存标记，后续请求快速失败
            localStockMap.put(goodsId, false);
            // 删除秒杀资格标记
            redisTemplate.delete(seckillFlagKey);
            return SeckillResult.fail("商品已售罄");
        }

        // ========== 第五关：发送MQ消息，异步创建订单 ==========
        SeckillMessage message = new SeckillMessage(userId, goodsId);
        try {
            // 使用顺序消息保证同一用户请求有序
            SendResult sendResult = rocketMQTemplate.syncSendOrderly(
                "seckill-order-topic",
                MessageBuilder.withPayload(message).build(),
                String.valueOf(userId) // hashKey保证同一用户同一队列
            );
            if (sendResult.getSendStatus() == SendStatus.SEND_OK) {
                return SeckillResult.success("排队中，请稍候查看订单结果");
            }
        } catch (Exception e) {
            // MQ发送失败，需要回滚Redis操作
            redisTemplate.opsForValue().increment("seckill:stock:" + goodsId);
            redisTemplate.delete(seckillFlagKey);
            log.error("MQ发送失败，userId={}, goodsId={}", userId, goodsId, e);
            return SeckillResult.fail("系统繁忙，请稍后重试");
        }

        return SeckillResult.success("排队中，请稍候查看订单结果");
    }
}
```

```java
@PostConstruct
public void initFlowRules() {
    List<FlowRule> rules = new ArrayList<>();

    // 秒杀接口QPS限流：单机最大500
    FlowRule seckillRule = new FlowRule("SeckillService:executeSeckill")
        .setCount(500)
        .setGrade(RuleConstant.FLOW_GRADE_QPS)
        .setLimitApp("default")
        .setStrategy(RuleConstant.STRATEGY_DIRECT);
    rules.add(seckillRule);

    // 秒杀URL获取接口QPS限流：单机最大1000
    FlowRule urlRule = new FlowRule("SeckillUrlService:generateSeckillUrl")
        .setCount(1000)
        .setGrade(RuleConstant.FLOW_GRADE_QPS);
    rules.add(urlRule);

    FlowRuleManager.loadRules(rules);
}

}
```

### 5.3 风控校验

```java
@Service
public class SeckillRiskControlService {

    /**
     * 风控校验：拦截异常请求
     */
    public RiskCheckResult checkRisk(Long userId, Long goodsId, String ip, String deviceId) {
        // 1. 用户资格校验（是否在新用户/黑名单）
        User user = userService.getById(userId);
        if (user == null || user.getStatus() == UserStatus.BLOCKED) {
            return RiskCheckResult.reject("用户状态异常");
        }

        // 2. 频率限制：同一用户5秒内只能请求1次
        String freqKey = "seckill:freq:" + userId;
        Boolean first = redisTemplate.opsForValue().setIfAbsent(freqKey, "1", Duration.ofSeconds(5));
        if (Boolean.FALSE.equals(first)) {
            return RiskCheckResult.reject("操作过于频繁");
        }

        // 3. 设备指纹校验：同一设备1分钟最多3次
        String deviceKey = "seckill:device:" + deviceId;
        Long deviceCount = redisTemplate.opsForValue().increment(deviceKey);
        if (deviceCount != null && deviceCount > 3) {
            return RiskCheckResult.reject("设备请求过多");
        }
        redisTemplate.expire(deviceKey, Duration.ofMinutes(1));

        // 4. IP限流：同一IP 1分钟最多10次
        String ipKey = "seckill:ip:" + ip;
        Long ipCount = redisTemplate.opsForValue().increment(ipKey);
        if (ipCount != null && ipCount > 10) {
            return RiskCheckResult.reject("IP请求过多");
        }
        redisTemplate.expire(ipKey, Duration.ofMinutes(1));

        return RiskCheckResult.pass();
    }
}
```

### 6.2 Redis原子扣减：防超卖的核心

**为什么Redis DECR能防超卖**：

```
DECR是Redis原子操作，核心流程：
┌──────────────────────────────────────────┐
│  请求A: DECR seckill:stock:100           │
│  Redis内部：                              │
│    1. 读取当前值 = 1                      │
│    2. 计算 1 - 1 = 0                      │
│    3. 写入新值 0                           │
│    4. 返回 0 给请求A                       │
│                                          │
│  请求B: DECR seckill:stock:100           │
│  Redis内部（因为原子性，必须等A完成）：     │
│    1. 读取当前值 = 0（A已扣减）            │
│    2. 计算 0 - 1 = -1                     │
│    3. 写入新值 -1                          │
│    4. 返回 -1 给请求B                      │
│                                          │
│  请求B发现返回值 < 0 → 库存不足            │
│  → INCR回滚 + 拦截                        │
└──────────────────────────────────────────┘
```

**关键问题：Redis DECR返回负数怎么办**

```java
// Redis扣减后返回负数 → 说明超卖 → 必须回滚
Long remainingStock = redisTemplate.opsForValue().decrement(stockKey);
if (remainingStock < 0) {
    // 立即回滚！
    redisTemplate.opsForValue().increment(stockKey);
    return SeckillResult.fail("商品已售罄");
}
```

### 6.3 Redis + Lua脚本：更严格的原子扣减

```lua
-- seckill_stock_decr.lua
-- 原子扣减库存：库存不足时不扣减，直接返回失败
-- 解决DECR可能返回负数的问题

local stockKey = KEYS[1]      -- seckill:stock:{goodsId}
local flagKey  = KEYS[2]      -- seckill:flag:{userId}:{goodsId}
local userId   = ARGV[1]
local goodsId  = ARGV[2]
local ttl      = tonumber(ARGV[3])  -- 秒杀资格标记过期时间

-- 1. 检查是否已经秒杀过（防重复）
local exists = redis.call('EXISTS', flagKey)
if exists == 1 then
    return -2  -- 已秒杀过
end

-- 2. 获取当前库存
local stock = tonumber(redis.call('GET', stockKey))
if stock == nil then
    return -3  -- 库存数据不存在（未预热）
end

-- 3. 库存不足，直接返回
if stock <= 0 then
    return 0   -- 库存为0
end

-- 4. 原子扣减库存
redis.call('DECR', stockKey)

-- 5. 设置秒杀资格标记（防重复）
redis.call('SET', flagKey, '1', 'EX', ttl)

-- 6. 返回扣减后的库存
return 1   -- 秒杀成功
```

```java
// Java调用Lua脚本
@Service
public class SeckillRedisLuaService {

    private static final String LUA_SCRIPT =
        "local stockKey = KEYS[1]\n" +
        "local flagKey  = KEYS[2]\n" +
        "local userId   = ARGV[1]\n" +
        "local goodsId  = ARGV[2]\n" +
        "local ttl      = tonumber(ARGV[3])\n" +
        "local exists = redis.call('EXISTS', flagKey)\n" +
        "if exists == 1 then return -2 end\n" +
        "local stock = tonumber(redis.call('GET', stockKey))\n" +
        "if stock == nil then return -3 end\n" +
        "if stock <= 0 then return 0 end\n" +
        "redis.call('DECR', stockKey)\n" +
        "redis.call('SET', flagKey, '1', 'EX', ttl)\n" +
        "return 1\n";

    private DefaultRedisScript<Long> script;

    @PostConstruct
    public void init() {
        script = new DefaultRedisScript<>(LUA_SCRIPT, Long.class);
    }

    public Long seckillDecrStock(Long userId, Long goodsId) {
        String stockKey = "seckill:stock:" + goodsId;
        String flagKey = "seckill:flag:" + userId + ":" + goodsId;

        Long result = redisTemplate.execute(
            script,
            List.of(stockKey, flagKey),
            String.valueOf(userId),
            String.valueOf(goodsId),
            String.valueOf(3600)
        );

        // result: 1=成功, 0=售罄, -2=重复秒杀, -3=未预热
        return result;
    }
}
```

```
│              防超卖三重保障机制                            │
├────────────────┬────────────────┬───────────────────────┤
│    第一重       │    第二重       │      第三重            │
│    Redis扣减    │   Redis Lua    │     MySQL乐观锁        │

├────────────────┼────────────────┼───────────────────────┤

├────────────────┼────────────────┼───────────────────────┤
```

**MySQL乐观锁兜底SQL**：

```sql
-- 库存扣减（乐观锁：WHERE stock > 0）
UPDATE seckill_goods
SET stock_count = stock_count - 1
WHERE id = #{goodsId} AND stock_count > 0;
```

```java
public boolean createOrder(Long userId, Long goodsId) {

        throw new SeckillException("库存不足，秒杀失败");
    }

    // 2. 创建订单
    SeckillOrder order = new SeckillOrder();
    order.setUserId(userId);
    order.setGoodsId(goodsId);
    order.setCreateTime(new Date());
    order.setStatus(OrderStatus.UNPAID);
    seckillOrderMapper.insert(order);

    return true;
}
```

### 7.2 RocketMQ顺序消息保证

```java
// MQ消费者：异步创建订单
@Component
@RocketMQMessageListener(
    topic = "seckill-order-topic",
    consumerGroup = "seckill-order-consumer-group",
    consumeMode = ConsumeMode.ORDERLY  // 顺序消费，保证同一用户请求有序
)
public class SeckillOrderConsumer implements RocketMQListener<SeckillMessage> {

    @Override
    public void onMessage(SeckillMessage message) {
        try {
            createOrder(message.getUserId(), message.getGoodsId());
            log.info("订单创建成功：userId={}, goodsId={}", message.getUserId(), message.getGoodsId());
        } catch (SeckillException e) {
            // 库存不足（DB层兜底拦截）→ 回滚Redis
            rollbackRedis(message.getUserId(), message.getGoodsId());
            log.warn("秒杀失败：userId={}, goodsId={}, reason={}",
                message.getUserId(), message.getGoodsId(), e.getMessage());
        } catch (Exception e) {
            // 其他异常 → 重试（顺序消费会自动重试）
            log.error("订单创建异常，将重试：userId={}, goodsId={}",
                message.getUserId(), message.getGoodsId(), e);
            throw e; // 抛出异常触发MQ重试
        }
    }

    private void rollbackRedis(Long userId, Long goodsId) {
        // Redis库存+1
        redisTemplate.opsForValue().increment("seckill:stock:" + goodsId);
        // 删除秒杀资格标记
        redisTemplate.delete("seckill:flag:" + userId + ":" + goodsId);
        // 重置本地缓存标记
        localStockMap.remove(goodsId); // 允许后续请求再尝试
    }
}
```

## 第九章 秒杀系统面试追问防线

### 9.1 核心面试题

**Q1：秒杀系统如何防止超卖？**

> 三重保障：
> 1. Redis原子扣减（DECR/Lua脚本）—— 快速拦截99%请求
> 2. Redis Lua脚本原子化（检查+扣减+标记一体）—— 严格防超扣
> 3. MySQL乐观锁兜底（WHERE stock > 0）—— 绝对保障
> 关键原则：宁可少卖，不能超卖。DB是最后防线。

**Q2：秒杀系统如何应对瞬时高并发？**

> 五层拦截：
> 1. CDN静态化 —— 拦截80%页面请求
> 2. Nginx限流+Lua预判 —— 拦截87.5%恶意/重复请求
> 3. 应用层风控+本地缓存 —— 拦截50%不合规请求
> 4. Redis原子扣减 —— 拦截98%库存不足请求
> 5. MQ异步化 —— DB只承受几百QPS

**Q3：为什么用MQ异步下单而不是直接写DB？**

> 1. 削峰填谷：10万QPS → MQ排队 → DB匀速消费几百QPS
> 2. 快速响应：Redis扣减5ms → 发MQ5ms → 用户10ms内得到反馈
> 3. 解耦：秒杀服务和订单服务独立，订单服务可以独立扩容
> 4. 容错：MQ消费失败可重试，DB直接写失败只能回滚

**Q4：Redis主从同步延迟导致超卖怎么办？**

> 1. 库存扣减只走Master节点（Lettuce配置readFrom=MASTER）
> 2. Lua脚本原子化操作（读取+判断+扣减一体化）
> 3. MySQL乐观锁兜底（WHERE stock > 0），这是最后防线
> 4. 库存预热时可多放1-2个冗余缓冲

**Q5：秒杀系统中Redis和MySQL的数据如何保证一致性？**

> 1. Redis是预扣减（快速拦截），MySQL是最终确认（乐观锁）
> 2. Redis扣减成功 → 发MQ → 消费者创建DB订单 → 乐观锁扣减
> 3. 如果DB扣减失败（affected rows=0） → 回滚Redis库存
> 4. MQ消费失败 → 重试 → 死信队列 → 人工补偿
> 5. 最终一致性：短期可能Redis显示0但DB还有1，但绝对不会超卖

**Q6：如何防止同一用户重复秒杀？**

> 三重防护：
> 1. Redis SET NX标记：`seckill:flag:{userId}:{goodsId}` —— 一旦设置不可重复
> 2. Lua脚本原子化：检查标记+扣减库存+设置标记一体化
> 3. DB唯一索引：订单表(user_id, goods_id)联合唯一索引 —— 兜底

**Q7：如果MQ消息丢失怎么办？**

> 1. 发送端：RocketMQ事务消息/同步发送+回调确认
> 2. 存储端：RocketMQ同步刷盘（SYNC_FLUSH）
> 3. 消费端：手动ACK，业务成功后才确认
> 4. 兜底：本地消息表，定时扫描补偿
> 5. 死信队列：消费失败16次后进入死信队列，人工处理

**Q8：秒杀结束后库存怎么处理？**

> 1. Redis剩余库存 → MySQL最终库存对账
> 2. 未支付订单超时取消 → 库存回补（Redis+DB双回补）
> 3. 定时任务扫描未支付订单 → 30分钟未支付自动取消
> 4. 最终：Redis缓存失效，数据回归DB常态

## 第十章 需求分析与核心挑战

### 10.1 什么是短链服务

短链服务将**长URL**转换为**短URL**，用户访问短URL时，服务端重定向到原始长URL。

**典型场景**：
- 短信营销：短信有字数限制，短链节省空间
- 社交分享：微博/推特等有字数限制
- 追踪统计：短链可嵌入追踪参数，统计点击来源/次数
- 二维码：短链生成二维码更简洁，扫码更快
- 品牌形象：自定义短域名更显专业

### 11.2 哈希算法方案

**方案1：MD5/SHA256截取**

```
┌──────────────────────────────────────────────────────────┐
│          MD5截取方案                                       │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  1. 对长URL做MD5 → 128bit = 32字符十六进制                │
│  2. 截取前7位作为短码                                     │
│                                                          │
│  问题：                                                  │
│  - 碰撞概率：62^7空间中，10亿URL碰撞概率 ≈ 1%             │
│    （生日攻击：p ≈ n²/(2m)，n=10^9, m=62^7）             │
│  - 同一长URL多次哈希 → 同一短码 ✓（哈希确定性）            │
│  - 不同长URL哈希碰撞 → 需要冲突检测                        │
│                                                          │
│  改进：                                                  │
│  - 碰撞时加salt重新哈希（但破坏确定性）                    │
│  - 保留长URL→短URL映射表，先查是否已存在                   │
│                                                          │
│  结论：简单但碰撞风险高，不适合大规模                       │
└──────────────────────────────────────────────────────────┘
```

### 11.3 自增ID方案

**方案2：分布式自增ID + Base62编码**

```java
/**
 * 自增ID + Base62编码方案
 * 核心思路：
 * 1. 生成全局唯一自增ID（Snowflake或DB自增）
 * 2. 将ID转为Base62编码作为短码
 * 3. 同一长URL → 先查缓存/DB → 已存在则返回已有短码
 */
@Service
public class ShortUrlIdService {

    // Base62字符集
    private static final String BASE62 = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";

    /**
     * Snowflake生成分布式自增ID
     * ID结构：1bit符号 + 41bit时间戳 + 10bit机器ID + 12bit序列号
     * 每秒可生成4096个ID
     */
    public long generateId() {
        return snowflakeIdWorker.nextId();
    }

    /**
     * 将ID转为Base62短码
     * 例：ID=123456789 → Base62短码="8fK2x"
     */
    public String idToShortCode(long id) {
        StringBuilder sb = new StringBuilder();
        while (id > 0) {
            int remainder = (int) (id % 62);
            sb.append(BASE62.charAt(remainder));
            id /= 62;
        }
        // 反转（低位在前，高位在后）
        return sb.reverse().toString();
    }

    /**
     * 将Base62短码转回ID
     * 例："8fK2x" → ID=123456789
     */
    public long shortCodeToId(String shortCode) {
        long id = 0;
        for (char c : shortCode.toCharArray()) {
            id = id * 62 + BASE62.indexOf(c);
        }
        return id;
    }
}
```

**自增ID方案优缺点**：

| 优点 | 缺点 |
|------|------|
| 无碰撞（ID全局唯一） | 短码有序可预测（安全隐患） |
| 简单可靠 | 长URL→短URL需要额外查表 |
| 可扩展性好 | ID泄露可推算总量 |

**安全问题：短码可预测**

```
攻击者知道短码 "1aB3xK" 对应的ID
→ 可以推算ID范围
→ 遍历所有短码访问所有长URL
→ 统计数据被污染

解决方案：
1. ID加随机偏移：shortCode = Base62(id + randomOffset)
2. ID加密：shortCode = Base62(encrypt(id))
3. 预生成随机短码池（见方案3）
```

```
│  1. 预生成大量随机7位短码，存入DB                          │
```

```java
/**
 * 随机短码生成
 */
public String generateRandomShortCode(int length) {
    StringBuilder sb = new StringBuilder(length);
    SecureRandom random = new SecureRandom();
    for (int i = 0; i < length; i++) {
        sb.append(BASE62.charAt(random.nextInt(62)));
    }
    return sb.toString();
}

// 批量预生成（去重用Set）
public Set<String> batchGenerateShortCodes(int count, int length) {
    Set<String> codes = new HashSet<>();
    while (codes.size() < count) {
        codes.add(generateRandomShortCode(length));
    }
    return codes;
}
```

### 12.3 布隆过滤器加速查重

```java
/**
 * 布隆过滤器：判断长URL是否已存在短码
 * 避免每次生成都查DB，先用布隆过滤器快速判断
 */
@Service
public class BloomFilterService {

    // Guava布隆过滤器：预期插入10亿URL，误判率0.01%
    private BloomFilter<String> longUrlFilter = BloomFilter.create(
        Funnels.stringFunnel(Charsets.UTF_8),
        1_000_000_000,  // 预期容量10亿
        0.0001           // 误判率万分之一
    );

    /**
     * 判断长URL是否可能已存在
     * true → 可能存在（需查DB确认）
     * false → 绝对不存在（可以直接生成）
     */
    public boolean mightExist(String longUrl) {
        return longUrlFilter.mightContain(longUrl);
    }

    /**
     * 新短链生成后加入布隆过滤器
     */
    public void put(String longUrl) {
        longUrlFilter.put(longUrl);
    }

    /**
     * 服务启动时从DB加载已有URL到布隆过滤器
     */
    @PostConstruct
    public void init() {
        // 分批加载（避免OOM）
        int batchSize = 10000;
        long offset = 0;
        while (true) {
            List<String> urls = shortUrlMapper.selectLongUrlBatch(offset, batchSize);
            if (urls.isEmpty()) break;
            urls.forEach(this::put);
            offset += batchSize;
        }
        log.info("布隆过滤器初始化完成，加载URL数量：{}", offset);
    }
}
```

### 13.1 302 vs 301选择

```
┌──────────────────────────────────────────────────────────┐
│          301 vs 302 重定向选择                             │
├─────────────────┬────────────────────────────────────────┤
│    301 永久重定向 │    302 临时重定向                       │
├─────────────────┼────────────────────────────────────────┤
│ 浏览器缓存结果   │ 浏览器每次都请求短链服务                  │
│ 后续直接跳转     │ 每次经过服务 → 可以统计点击              │
│ 不经过短链服务   │ 不缓存 → 数据统计完整                    │
├─────────────────┼────────────────────────────────────────┤
│ 速度快（缓存跳转）│ 略慢（每次经过服务）                     │
│ 无法统计点击     │ 可以统计每次点击                         │
├─────────────────┼────────────────────────────────────────┤
│ 适合：永久不变的 │ 适合：需要统计的营销短链                  │
│ 短链（如品牌短链）│ （绝大多数短链场景）                     │
├─────────────────┼────────────────────────────────────────┤
│ ⚠️ 面试陷阱：   │ ✓ 推荐：大多数场景用302                  │
│ "用301更快"     │ 302 + 缓存也能快                        │
│ 但无法统计！    │ 业务需求统计 > 速度优化                   │
└─────────────────┴────────────────────────────────────────┘
```

```java
/**
 * 短链重定向核心服务
 * 302临时重定向 + 缓存优化 + 异步统计
 */
@Service
public class ShortUrlRedirectService {

    /**
     * 重定向：短码 → 长URL
     */
    public String redirect(String shortCode, HttpServletRequest request) {
        // 1. 查缓存
        String longUrl = getFromCache(shortCode);
        if (longUrl != null) {
            // 异步记录统计（不影响重定向速度）
            asyncRecordClick(shortCode, request);
            return longUrl;
        }

        // 2. 查DB
        longUrl = getFromDB(shortCode);
        if (longUrl == null) {
            // 短码不存在或已过期
            return null;
        }

        // 3. 写缓存
        setCache(shortCode, longUrl);

        // 4. 异步统计
        asyncRecordClick(shortCode, request);

        return longUrl;
    }

    /**
     * 异步记录点击统计
     * 不能阻塞重定向主流程！
     */
    private void asyncRecordClick(String shortCode, HttpServletRequest request) {
        ClickRecord record = new ClickRecord();
        record.setShortCode(shortCode);
        record.setIp(request.getRemoteAddr());
        record.setReferer(request.getHeader("Referer"));
        record.setUserAgent(request.getHeader("User-Agent"));

        // 方案1：MQ异步（推荐）
        rocketMQTemplate.asyncSend("short-url-click-topic", record);

        // 方案2：线程池异步
        // clickRecordExecutor.submit(() -> clickRecordService.save(record));
    }
}
```

### 13.3 多级缓存架构

```

│     ├── 命中 → 返回 + 回写L1（<5ms）                      │
│     ├── 未命中 → L3                                       │
│     │                                                    │
│     ▼                                                    │
│  L3: MySQL数据库                                          │
│     ├── 命中 → 返回 + 回写L2+L1（<50ms）                  │
│     ├── 未命中 → 404                                      │
│                                                          │
│  缓存策略：                                               │
│  - L1: Caffeine, 最大10万条, TTL=10分钟                   │
│  - L2: Redis, TTL=1小时, 无容量限制                       │
│  - L3: MySQL, 持久化存储                                  │
│                                                          │
│  热点短链缓存预热：                                       │
│  - 定时扫描最近1小时点击TOP 1000                          │
│  - 主动加载到L1+L2                                       │
```

```java
/**
 * 多级缓存实现
 */
@Service
public class ShortUrlCacheService {

    // L1本地缓存：Caffeine（高性能，支持过期+容量限制）
    private Cache<String, String> localCache = Caffeine.newBuilder()
        .maximumSize(100_000)     // 最大10万条
        .expireAfterWrite(Duration.ofMinutes(10))  // 写入10分钟过期
        .recordStats()           // 记录统计
        .build();

    // L2 Redis缓存
    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    /**
     * 多级缓存读取
     */
    public String getLongUrl(String shortCode) {
        // L1: 本地缓存
        String longUrl = localCache.getIfPresent(shortCode);
        if (longUrl != null) {
            return longUrl;
        }

        // L2: Redis缓存
        longUrl = redisTemplate.opsForValue().get("short:url:" + shortCode);
        if (longUrl != null) {
            // 回写L1
            localCache.put(shortCode, longUrl);
            return longUrl;
        }

        // L3: MySQL（由调用方处理）
        return null;
    }

    /**
     * 写入多级缓存
     */
    public void putLongUrl(String shortCode, String longUrl) {
        // L1
        localCache.put(shortCode, longUrl);
        // L2（TTL=1小时）
        redisTemplate.opsForValue().set("short:url:" + shortCode, longUrl,
            Duration.ofHours(1));
    }

    /**
     * 热点短链预热
     */
    @Scheduled(fixedRate = 300_000)  // 每5分钟
    public void preheatHotUrls() {
        // 查询最近1小时点击TOP 1000
        List<String> hotShortCodes = clickStatService.getTop1000(Duration.ofHours(1));
        for (String shortCode : hotShortCodes) {
            String longUrl = redisTemplate.opsForValue().get("short:url:" + shortCode);
            if (longUrl != null) {
                localCache.put(shortCode, longUrl);
            }
        }
    }
}
```

```
│          CDN缓存短链重定向                                 │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  问题：302不缓存 → 每次都到服务端 → 服务压力大             │
```

```
├──────────────────────────────────────────────────────────┤
│                                                          │

│  - DB标记status=0 → 删除缓存                             │
```

### 15.1 统计数据写入

```java
/**
 * 点击统计异步写入
 * 三级写入：MQ → ClickHouse → 数据报表
 */
@Service
public class ClickStatService {

    /**
     * MQ消费者：接收点击记录
     * 批量写入ClickHouse（列式存储，写入极快）
     */
    @RocketMQMessageListener(
        topic = "short-url-click-topic",
        consumerGroup = "click-stat-consumer-group",
        consumeMode = ConsumeMode.CONCURRENTLY  // 并发消费，统计允许乱序
    )
    public void onMessage(ClickRecord record) {
        // 批量攒数据，每100条或每5秒批量写入ClickHouse
        clickRecordBuffer.add(record);
        if (clickRecordBuffer.size() >= 100 || System.currentTimeMillis() - lastFlushTime > 5000) {
            flushToClickHouse();
        }
    }

    /**
     * 批量写入ClickHouse
     */
    private void flushToClickHouse() {
        List<ClickRecord> batch = new ArrayList<>(clickRecordBuffer);
        clickRecordBuffer.clear();
        lastFlushTime = System.currentTimeMillis();

        // ClickHouse批量插入（列式存储，批量插入极快）
        clickHouseMapper.batchInsert(batch);
    }
}
```

```java
/**
 * Redis实时计数：快速获取最近N分钟/N小时的点击数
 * 用于Dashboard展示 + 告警
 */
@Service
public class ClickCounterService {

    /**
     * 记录点击：Redis计数器
     * 使用HyperLogLog统计UV（去重用户数）
     * 使用INCR统计PV（总点击数）
     */
    public void recordClick(String shortCode, String ip) {
        String today = LocalDate.now().format(DateTimeFormatter.BASIC_ISO_DATE);

        // PV：总点击数（简单计数）
        redisTemplate.opsForValue().increment("click:pv:" + shortCode + ":" + today);

        // UV：去重用户数（HyperLogLog，内存占用极小）
        redisTemplate.opsForHyperLogLog().add("click:uv:" + shortCode + ":" + today, ip);

        // 每小时PV
        String hourKey = String.format("%s:%02d", today, LocalDateTime.now().getHour());
        redisTemplate.opsForValue().increment("click:pv:hour:" + shortCode + ":" + hourKey);
    }

    /**
     * 获取今日统计
     */
    public ClickStatDTO getTodayStat(String shortCode) {
        String today = LocalDate.now().format(DateTimeFormatter.BASIC_ISO_DATE);
        Long pv = redisTemplate.opsForValue().get("click:pv:" + shortCode + ":" + today);
        Long uv = redisTemplate.opsForHyperLogLog().size("click:uv:" + shortCode + ":" + today);
        return new ClickStatDTO(pv != null ? pv : 0, uv != null ? uv : 0);
    }
}
```

## 第十八章 面试高频10题

### Q1：秒杀系统如何防止超卖？

> 三重保障：①Redis DECR/Lua原子扣减（快速拦截）②Lua脚本原子化操作（防超扣+防重复）③MySQL乐观锁WHERE stock>0兜底。核心原则：宁可少卖不能超卖，DB是最后防线。

### Q2：秒杀系统如何应对瞬时高并发？

> 五层拦截层层递减：CDN静态化(80%) → Nginx限流+Lua预判(87.5%) → 应用层风控+本地缓存(50%) → Redis原子扣减(98%) → MQ异步化→DB只承受几百QPS。99.96%的无效流量被挡住。

### Q3：301和302重定向有什么区别？短链服务选哪个？

> 301永久重定向浏览器会缓存，后续不再请求服务端 → 无法统计点击；302临时重定向每次都请求服务端 → 可以统计。短链服务选302，因为业务需求统计点击数据。超大规模可CDN缓存302短时间+日志回传统计。

### Q4：短码生成算法怎么选？

> 三种方案：①MD5截取（简单但碰撞率高）②自增ID+Base62（无碰撞但可预测，需加密或加偏移）③随机码池（不可预测但需维护池）。推荐：自增ID+Base62+布隆过滤器查重+长URL查表保证同一长URL→同一短码。

### Q5：如何保证同一长URL生成同一短码？

> 生成前先查：①布隆过滤器快速判断是否存在（不存在→直接生成）②布隆判断可能存在→查DB确认（已存在→返回已有短码）③DB确认不存在→生成新短码。布隆过滤器避免每次生成都查DB。

### Q6：Redis主从同步延迟导致超卖怎么办？

> ①库存扣减只走Master（Lettuce配置readFrom=MASTER）②Lua脚本原子化（读取+判断+扣减一体，不依赖从库）③MySQL乐观锁兜底（WHERE stock>0）④预热时库存多放1-2个冗余缓冲。

### Q7：MQ消息丢失怎么办？

> 三端保障：①发送端：RocketMQ同步发送+事务消息+本地消息表兜底 ②存储端：SYNC_FLUSH同步刷盘 ③消费端：手动ACK+16次重试+死信队列。最终兜底：本地消息表定时扫描补偿。

### Q8：短链服务如何做到高性能读取？

> 多级缓存+CDN：①L1 Caffeine本地缓存(<1ms) ②L2 Redis分布式缓存(<5ms) ③CDN边缘缓存(就近访问) ④MySQL兜底(<50ms)。热点短链定时预热，统计异步写入不阻塞重定向。

### Q9：秒杀系统如何处理未支付订单？

> ①30分钟未支付自动取消（定时任务扫描）②取消后回补库存（Redis INCR+DB UPDATE+1）③删除秒杀资格标记④释放本地缓存标记⑤MQ消费失败回滚Redis库存。

### Q10：如果数据量达到百亿级，短链存储怎么扩展？

> 分库分表+冷热分离：①映射表按short_code哈希分256个分片②统计表按时间月表③热数据MySQL+Redis缓存④冷数据归档ClickHouse/Hive⑤布隆过滤器使用Redis集群版（可持久化）⑥新URL布隆判断不存在→直接生成不查DB。
