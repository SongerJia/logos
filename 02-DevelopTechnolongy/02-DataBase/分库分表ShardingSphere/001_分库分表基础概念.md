|#|知识点|笔记三层写法建议|关联|
|---|---|---|---|
|1.1|**什么是分库分表**|是什么：数据量/并发超过单机瓶颈时的水平拆解方案；为什么：单表行数超千万、单库QPS超千、磁盘IO成为瓶颈；面试怎么问：「什么场景需要分库分表？你们的数据量到了多少才分的？」|MySQL 索引性能退化|
|1.2|**垂直拆分 vs 水平拆分**|是什么：垂直=按业务域/字段拆（库级别或表级别），水平=按数据行分散到多库多表；为什么：垂直解决单库/单表宽度问题，水平解决单表数据量问题；面试怎么问：「垂直和水平拆分的区别？各自适用场景？」|微服务拆分思想|
|1.3|**垂直分库 / 垂直分表**|是什么：分库=不同业务放不同库，分表=大表拆成窄表（宽表→窄表）；为什么：减少锁竞争/降低IO/按需扩展；面试怎么问：「订单表怎么垂直拆分？拆了之后join怎么办？」|数据库范式 vs 反范式|
|1.4|**水平分库 / 水平分表**|是什么：同一张表的数据按规则分散到多个库/多张表；为什么：突破单机存储上限+提升写入吞吐；面试怎么问：「水平分表的分片键怎么选？」|1.3 → 本条是进阶|
|1.5|**常见分片策略：范围/Hash/取模/一致性哈希**|是什么：四种主流策略的原理和优劣对比表；为什么：没有万能方案——范围利于范围查询但数据倾斜，取模均匀但不支持范围查询；面试怎么问：「为什么不用简单的 id % N 取模？」|Redis Cluster 一致性哈希槽|
|1.6|**分库分表带来的问题（痛点全景）**|是什么：列出全部痛点（跨节点JOIN/跨库事务/全局唯一ID/排序分页/全局函数不支持）；为什么：这是面试官最爱追问的「你用了分库分表遇到了什么问题」；面试：**必背清单**|分布式事务(5.x) / 分布式主键(5.x)|
|1.7|**什么时候该分库分表（判断标准）**|是什么：量化指标——单表>1000万行/单库>500GB/QPS>2000等；为什么：过早优化是大忌——引入复杂度换来的收益可能为负；面试：「你们是怎么决定开始分库分表的？」|MySQL B+树高度/页分裂|
|1.8|**不分库分表的替代方案**|是什么：读写分离/表分区(PARTITION)/归档冷数据/优化SQL加索引/升级硬件；为什么：很多团队的问题其实不需要分库分表就能解决；面试：「除了分库分表，你还考虑过哪些方案？」|MySQL 主从复制 / 表分区|
