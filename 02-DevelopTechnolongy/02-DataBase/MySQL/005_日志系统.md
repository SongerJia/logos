| 知识点                                          | 笔记时重点写什么                                                                                                                                                                                                                              |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **redo log 重做日志**                            | 热 保证事务持久性的核心。WAL（Write-Ahead Logging）机制：**先写日志再写磁盘**。 redo log 是物理日志（记录"某个页面上做了什么修改"，不是逻辑 SQL）。循环写入（固定大小文件组，写满从头覆盖）。刷盘策略 innodb_flush_log_at_trx_commit：=1（每次提交都 fsync，最安全默认值）/=0（每秒写一次）/=2（每次写 OS 缓存不立即 fsync）                       |
| **binlog 归档日志**                              | 热 Server 层的逻辑日志（记录 SQL 语句或行的变更）。三种格式：STATEMENT（记录 SQL，节省空间但可能不确定性行如 NOW()）/ ROW（记录每行变更，最安全但空间大）/ MIXED（混合）。主要用途：主从复制 + 数据恢复 + 审计。`log_bin` 开启，`expire_logs_days` 设置过期清理                                                               |
| **undo log 回滚日志**                            | 核 MVCC 的基础。记录数据修改前的版本（insert 对应 delete undo / update 对应 update undo / delete 对应 insert undo）。形成版本链（通过 DB_ROLL_PTR 串联）。**注意 undo log 不是为了回滚而存在的，更是 MVCC 读旧版本的关键**                                                                      |
| **redo log 与 binlog 两阶段提交（2PC）**             | 热 **高频源码级考点**。为什么要两阶段提交？因为 redo 和 binlog 写入是独立的，崩溃后可能出现 redo 有 binlog 没有（主从不一致）或 binlog 有 redo 没有（数据丢失）。2PC 流程：Prepare 阶段（写 redo log 并标记 prepare 状态）→ 写 binlog → Commit 阶段（将 redo log 标记 commit）。**崩溃恢复时根据 redo 的状态决定是提交还是回滚 binlog** |
| **error log / slow query log / general log** | error log（启动/运行/关闭错误，排障首选）、slow query log（慢 SQL 记录）、general query log（所有 SQL 都记录，**生产环境不要开**，性能影响巨大）                                                                                                                                  |
| **Change Buffer（变更缓冲区）**                     | 核 二级索引的更新操作（INSERT/DELETE/MARK_DELETE）先缓存在内存中（Change Buffer），后续被其他读操作 merge 时再合并到磁盘。减少随机 IO。`innodb_change_buffer_max_size` 控制大小（占 Buffer Pool 百分比）。**写多读少的场景 Change Buffer 效果最好**                                                    |
| **Buffer Pool 缓冲池**                          | 核 InnoDB 内存中最大的一块区域（默认物理内存的 25%~50%，由 `innodb_buffer_pool_size` 控制）。缓存数据页和索引页。LRU 淘汰策略（分为 Young 区和 Old 区，新加载页面先进 Old 区，避免全表扫描污染热点数据）。管理参数：`innodb_buffer_pool_instances`（多实例减少锁竞争）                                                    |

> **笔记技巧**：05 模块的核心是一张图——**redo log + binlog 的两阶段提交流程图**。画出 Prepare → Binlog → Commit 三个阶段，标注每一步写了什么、崩溃恢复时怎么处理。这张图能覆盖至少 3 道高难度面试题。
