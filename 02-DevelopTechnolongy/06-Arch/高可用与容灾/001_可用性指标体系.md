|#|知识点|核心内容|公式/数据|面试追问|FlowPulse 对应|
|---|---|---|---|---|---|
|**4.1.1**|**可用性 Availability**|系统在给定时间内可正常服务的时间占比；核心公式：`Availability = MTBF / (MTBF + MTTR)`|99.9% = 8.76h停机/年；99.99% = 52.56min/年；99.999% = 5.26min/年|"你们系统的SLA目标是多少？怎么计算的？"|**FlowPulse 目标 SLA 99.9%**（初期）/ 99.99%（成熟期）|
|**4.1.2**|**MTBF (平均故障间隔时间)**|Mean Time Between Failures；两次故障之间的平均运行时间；衡量系统**可靠性**的指标|`MTBF = 总运行时间 / 故障次数`；越高越好（目标：数月级）|"MTBF和MTTF有什么区别？"|流程引擎服务目标 MTBF > 720h（30天无故障）|
|**4.1.3**|**MTTR (平均修复时间)**|Mean Time To Repair / Recover；从故障发生到恢复服务的平均时间；衡量系统**可维护性**的指标|`MTTR = 总故障修复时间 / 故障次数`；越低越好（目标：<5min）|"降低MTTR有哪些手段？"|自动故障检测(Prometheus告警) + 自动重启(K8s) + 快速回滚(蓝绿部署) → 目标 MTTR < 10min|
|**4.1.4**|**SLA vs SLO vs SLI 三层模型**|**SLI**(Service Level Indicator) — 具体测量指标(如API响应时间)；**SLO**(Service Level Objective) — 目标值(如P99<200ms)；**SLA**(Service Level Agreement) — 与客户约定的合同承诺|Google SRE经典框架：SLI定义→SLO设定→Error Budget管理→基于预算做发布决策|"SLO设为99.9%，实际只做到99.5%怎么办？Error Budget是什么？"|FlowPulse SLIs: API P99延迟 / 错误率 / QPS吞吐量 → 设定 SLOs → 追踪 Error Budget|
|**4.1.5**|**Error Budget 错误预算**|`Error Budget = 100% - SLO`; 如SLO=99.9%则预算=0.1%；预算用完=不可靠性已达极限，暂停新功能发布专注稳定性|预算消耗率(Burn Rate)：>2x表示快速消耗需紧急响应；<0.5x表示稳定可继续迭代|"错误预算用完了怎么办？怎么和产品团队沟通？"|初期不严格追踪，但建立度量意识；关键接口设定 Error Budget|
