# 不变的点整理汇总

> 整合自「三根柱子落地计划」+「五不变执行方案」
> 
> **核心逻辑**：不变的东西能应对万变的问题。这里所有的点，都是学一次、受益十年以上的知识。

---

## 一、五不变（面试桌上的应答武器）

### 不变一：数据结构模型

每种结构要能脱稿回答两个问题：「底层是什么」+ 「为什么这个场景用它不用另一个」

| 结构 | 核心特性 | 上层映射 |
|------|---------|----------|
| 哈希表 | O(1) 查询，空间换时间；散列函数 + 冲突解决 + 扩容 + 负载因子 | HashMap / HashSet / Redis Hash / 布隆过滤器 |
| 跳表 | O(log n)，实现简单，支持范围查询，天然适合并发 | Redis ZSet / ConcurrentSkipListMap |
| B+Tree | 磁盘友好，范围查询高效 | MySQL InnoDB 索引 |
| LSM Tree | 写入极快，读取稍慢，适合写多读少 | RocksDB / LevelDB / HBase |
| 布隆过滤器 | 可能误判，一定不会漏判 | Redis 缓存穿透防护 |

**关键认知**：理解「哈希表通用模型」= 同时理解了 HashMap / ConcurrentHashMap / Redis Hash / HashSet / 布隆过滤器

**检验标准**：关掉所有资料，白板上画 B+Tree 插入过程并边讲，卡住 = 没会

---

### 不变二：并发三模型

所有并发问题不出这三种模型：

| 模型 | 机制 | 典型实现 |
|------|------|---------|
| 锁模型 | 互斥访问，排队等待 | synchronized / ReentrantLock / 读写锁 / 行锁 / 间隙锁 |
| CAS 模型 | 无锁，自旋重试，乐观 | AtomicInteger / ConcurrentHashMap.sizeCtl / 无锁队列 |
| 消息模型 | 生产者-消费者，队列缓冲 | BlockingQueue / 线程池任务队列 / RocketMQ / Kafka |

**特殊映射**：
- CountDownLatch = AQS 共享锁模型
- Semaphore = AQS 共享锁模型（容量控制）
- ThreadLocal = 线程隔离（每个线程一份，不涉及锁）

**检验标准**：面试官问「CountDownLatch 原理」，能从 AQS 共享锁模型讲起，30 秒说清

---

### 不变三：JVM（唯一的元知识）

JVM 是 Java 面试里唯一的「元知识」，它解释了所有其他知识：

| 概念 | 解释了什么上层问题 |
|------|-----------------|
| 对象头 Mark Word | synchronized 为什么能锁住 |
| 字节码重排序 | DCL 为什么需要 volatile |
| 类加载 + CGLIB | @Transactional 怎么起作用 |
| AQS | 线程池 Worker 为什么继承 AQS |

**必须能默画**：
- JVM 堆结构图（Eden / S0 / S1 / 老年代，含尺寸比例）
- GC 算法演进链：标记-清除 → 标记-整理 → 分代 → G1 → ZGC

**检验标准**：面试官说「线上 FGC 频繁」，能问出 3 个定位问题（堆多大、什么对象多、GC 日志哪阶段耗时最长）

### 不变四：溯源思维（真正的分水岭）

**目标**：任意一个框架设计，能往下追 3 层，最终停在一个「不会变的基础规律」上。

**执行**：在 Obsidian 里维护 `溯源链.md`，每天至少新增一条，格式：
```
## 日期：问题
框架特性 → 中间层 → 底层原理 → 不变的基础规律
```

**两个示例**：
- Spring @Transactional 为什么同类调用失效？→ AOP → 代理对象 → this 不是代理 → 「代理模式」的不变特性
- Redis 集群为什么是 16384 个槽？→ 心跳包大小（2KB）→ 每槽 1bit 位图 → 「网络传输效率」的不变约束

**判断标准**：停在「XXX 就是这样设计的」= 不够深，继续追

---

### 不变五：说人话能力（真正的分水岭）

**目标**：任何知识点，能在 30 秒内讲给非技术人员听

**逻辑**：
- 说得明白 → 面试官觉得你懂 → 追问方向变友好
- 说得混乱 → 面试官觉得你在背 → 追问方向变刁钻

**训练方法**：每天晚上录音 30 秒 → 回听 → 划掉「这里就是这样的」「你懂吧」→ 再讲一遍

**检验标准**：能让你老婆听懂你在说什么

## 二、六块底层地基（知识领域）

### 1. 数据结构与算法（30年未变）

真正要内化的是 trade-off，不是实现：

| 结构 | 核心 trade-off | 上层映射 |
|------|--------------|----------|
| 哈希表 | O(1) 查询，空间换时间 | HashMap / HashSet / Redis Hash |
| 跳表 | O(log n)，实现简单，支持范围查询 | Redis ZSet / ConcurrentSkipListMap |
| B+Tree | 磁盘友好，范围查询高效 | MySQL InnoDB 索引 |
| LSM Tree | 写入极快，读取稍慢，适合写多读少 | RocksDB / LevelDB / HBase |
| 布隆过滤器 | 可能误判，一定不漏判 | Redis 缓存穿透防护 |

**追问示例**：Redis ZSet 为什么用跳表不用红黑树？
→ 跳表实现简单（红黑树旋转复杂）
→ 跳表支持范围查询（ZRANGE），红黑树需要中序遍历
→ 跳表插入层级随机化，天然适合并发

### 2. 操作系统（50年未变）

| 概念 | 核心理解 | 上层映射 |
|------|---------|----------|
| 进程 vs 线程 vs 协程 | 隔离成本递减，调度粒度递减 | Java Thread → goroutine → Kotlin coroutine |
| 虚拟内存 | 每个进程有独立地址空间 | OOM、堆外内存、mmap |
| 文件 IO：阻塞/非阻塞/多路复用 | 一个线程等一个连接 → 一个线程管多个连接 | BIO → NIO → Netty |
| 零拷贝 | CPU 不参与数据搬运 | Kafka sendfile / NIO transferTo |
| CPU 缓存行 | 伪共享导致性能暴跌 | Disruptor / @Contended 注解 |

**追问示例**：Netty 为什么快？→ NIO 多路复用 → epoll → OS 内核中断处理 → DMA

### 3. 计算机网络（40年未变）

| 概念 | 核心理解 | 上层映射 |
|------|---------|----------|
| TCP 三次握手/四次挥手 | 为什么是三次不是两次？防止旧连接请求 | 所有基于 TCP 的协议 |
| TCP 拥塞控制 | 慢启动、拥塞避免、快重传 | 长连接 vs 短连接的选择 |
| HTTP/1.1 → HTTP/2 → HTTP/3 | 队头阻塞 → 多路复用 → QUIC(UDP) | REST → gRPC → WebSocket |
| DNS | 递归查询 + 缓存 | CDN / 服务发现 |

**追问示例**：你写了一个 HTTP 请求，经历了什么？
→ DNS → TCP → TLS → HTTP → 反向代理 → 应用

### 4. 分布式系统（30年未变）

| 概念 | 核心理解 | 上层映射 |
|------|---------|----------|
| CAP 理论 | 三者不可兼得，但可以取舍和妥协 | 所有分布式中间件的架构选择 |
| 共识算法（Paxos/Raft） | 多个节点如何就一个值达成一致 | Zookeeper ZAB / etcd Raft / Redis Sentinel |
| 数据分片 + 复制 | 分片解决容量，复制解决可用性 | Kafka partition / Redis Cluster / MySQL 分库分表 |
| 二阶段提交 / TCC / Saga | 跨节点事务的三种保证级别 | Seata AT/TCC / 分布式事务选型 |
| 限流 / 熔断 / 降级 | 保护系统的三个层次 | Sentinel / Hystrix / Resilience4j |

**每个分布式中间件，问三个问题**：
1. 它在 CAP 里选了哪两个？
2. 它的数据一致性保证到什么级别？
3. 它挂了之后会发生什么？

---

### 5. 数据库原理（40年未变）

| 概念 | 核心理解 | 上层映射 |
|------|---------|----------|
| ACID + MVCC | 隔离级别的实现原理 | MySQL InnoDB 事务 / Spring @Transactional |
| B+Tree 索引 | 聚簇索引 vs 非聚簇索引，最左前缀 | 慢查询优化 / explain |
| WAL（Write-Ahead Log） | 先写日志再写数据，崩溃恢复 | MySQL binlog/redo log / Redis AOF |
| 锁：行锁/间隙锁/临键锁 | 不同隔离级别下锁的范围不同 | 死锁排查 / 乐观锁 vs 悲观锁选型 |
| Buffer Pool | 内存缓存数据页，LRU 淘汰 | MySQL 内存参数调优 |

---

### 6. 编译与运行时（20年未变）

| 概念 | 核心理解 | 上层映射 |
|------|---------|----------|
| 类加载机制 | 双亲委派，加载→链接→初始化 | Spring Boot 启动流程 / 热部署原理 |
| 字节码 | 中间表示，可被改写 | AOP 本质 / Lombok / ASM / CGLIB |
| JIT 编译 | 热点代码编译为本地代码 | 性能优化 / 预热问题 |
| GC 算法 | 标记-清除 → 标记-整理 → 分代 → G1 → ZGC | JVM 调优 / 内存泄漏排查 |

**追问示例**：@Transactional 怎么起作用？→ Spring AOP → CGLIB 动态代理 → 生成子类字节码 → 类加载

## 三、不变的执行规则（方法论层）

这些规则本身也是"不变的点"，一旦掌握，适用于所有技术学习：

### 六步 SOP（学习流水线）

| 步骤 | 做什么 | 关键规则 |
|------|--------|----------|
| 1. 看主干 | 只看核心路径，跳过分支和边界 | 不允许抄代码，只用眼睛看（≤5分钟）|
| 2. 空手写 | 关掉资料，从空白文件从头写 | 卡住 >2 分钟才能偷看（≤15分钟）|
| 3. 回看 | 只看刚才卡住的那个点 | 看完立刻关掉，不能顺手抄（≤2分钟）|
| 4. 再写 | 关掉资料，从空白文件重写 | 必须完整写对，中间不能看 |
| 5. 追问"为什么" | 针对每个设计决策追问到底层原理 | 必须落到六块底层知识之一（10分钟）|
| 6. 口述 | 对着空气/录音，白话讲一遍 | 不能有"这里就是这样的"（5分钟）|

### 排查链路（问题解决肌肉）

**复现 → 定位 → 假设 → 验证 → 修复 → 复盘**

- **复现**：写下「输入是什么、期望输出是什么、实际输出是什么」
- **定位**：从功能 → 方法 → 具体一行，工具：日志 / 断点 / arthas / grep
- **假设**：至少列 2 个可能原因，按「最容易验证」排序，不按「最可能」排序
- **验证**：最小实验，确认原因（不是「加个索引试试」，而是「跑 explain 确认是全表扫描」）
- **修复**：只改一行 → 跑测试 → 观察 → 再改下一行，拒绝「顺便重构一下」
- **复盘**：这个问题的根因是什么？为什么我的第一次假设是错的？

### 面试题目的正确用法

```
正确：先用六步 SOP 学会 → 用「说人话」讲出来 → 再翻题目检验
错误：翻题目 → 看不会的 → 直接搜答案 → 以为会了
```

## 四、一句话总结

> **五不变 = 面试时的输出端；六块地基 = 知识的输入端。**
> 
> 六块地基教你「懂什么」，五不变教你「怎么用出来」。
> 
> 溯源思维和说人话能力是面试真正的分水岭——它们在六块地基里没有独立存在，但缺了它们，地基再扎实也答不好。
