## 第一章 项目故事的核心价值

### 1.1 为什么面试要讲项目

面试中考查项目经验，面试官真正想了解的是：

| 考查维度 | 面试官想确认的问题 |
|---------|------------------|
| **技术深度** | 你是否真正理解所用技术，而非只会调 API？ |
| **架构能力** | 你能否从全局视角理解系统设计，而非只关注自己的一亩三分地？ |
| **问题解决** | 遇到技术难题时，你的分析思路和解决方法是什么？ |
| **业务理解** | 你是否理解技术背后的业务价值，而非只是"接需求写代码"？ |
| **团队协作** | 你在团队中的角色和贡献是什么？ |
| **成长反思** | 你能否从项目中总结经验教训，持续改进？ |

```
简历筛选（关键词匹配）
    ↓
项目深挖（验证真实性 + 技术深度）  ← 最核心环节
    ↓
技术追问（八股 + 场景题）
    ↓
综合评估（文化匹配 + 潜力）
```

### 1.2 好的项目故事 vs 差的项目故事

**差的项目故事**（流水账式）：

> "我做了一个电商系统，用了 Spring Boot + MySQL + Redis。负责订单模块的 CRUD，用 Redis 做缓存，用 RabbitMQ 发消息。系统上线后运行正常。"

**问题**：
- 没有业务背景：做什么的电商？多大体量？
- 没有技术难点：CRUD 没有技术含量
- 没有量化结果："运行正常"不是结果
- 没有个人贡献：你做了什么？团队做了什么？
- 没有深度可挖：面试官无从追问

**好的项目故事**（STAR 结构）：

> "我们做的是一个 B2C 电商平台的订单系统，日均订单 10 万单，大促峰值 QPS 3000。
>
> **背景**：原来订单系统是单体架构，下单链路同步调用库存、营销、物流等 6 个服务，P99 响应时间 800ms，大促时经常超时。业务方要求把下单响应降到 200ms 以内。
>
> **我的角色**：我是订单系统负责人，主导了整个异步化改造方案。
>
> **行动**：
> 1. 引入 RocketMQ 将下单链路从同步改为异步——订单创建后发消息通知下游，响应时间从 800ms 降到 120ms
> 2. 用 RocketMQ 事务消息保证订单和消息的一致性——半消息 + 本地事务 + 回查机制
> 3. 引入 Seata AT 模式处理订单和库存的分布式事务
> 4. Redis Lua 脚本做库存原子扣减防超卖
> 5. Sentinel 做限流熔断，大促时自动降级非核心链路
>
> **结果**：P99 从 800ms 降到 120ms（降低 85%），大促零超时，系统稳定支撑了双 11 的 50 万峰值 QPS。"

**好在哪里**：
- ✅ 有明确的业务背景和数据量级
- ✅ 有清晰的技术难点和解决方案
- ✅ 有量化的结果指标
- ✅ 有个人角色和贡献
- ✅ 有丰富的追问点（事务消息/Seata/Lua/限流）

### 1.3 项目故事的三个层次

```
第一层：做了什么（What）     → 功能描述
第二层：怎么做的（How）       → 技术方案
第三层：为什么这样做（Why）   → 架构决策与技术权衡
```

面试中，**第三层才是加分项**。能讲清楚"为什么选 A 不选 B"，才能证明你有架构思维。

| 层次 | 示例 | 面试官评价 |
|------|------|-----------|
| 只讲 What | "我用 Redis 做了缓存" | "只会用，不理解" |
| 讲到 How | "我用 Redis 的 ZSet 做排行榜，用 Lua 脚本保证原子性" | "用得不错" |
| 讲到 Why | "排行榜选 Redis ZSet 而非 MySQL ORDER BY，是因为 ZSet 的跳表结构 O(log N) 插入+排名，而 MySQL 每次查询需要全表排序 O(N log N)，在 10 万用户量级下性能差 100 倍" | "有深度，有架构思维" |

## 第二章 选材原则——什么项目值得讲

### 2.1 选材六大原则

#### 原则一：有技术深度

> 选的项目必须能挖出技术深度，而不是纯 CRUD。

**有深度的项目特征**：
- 涉及分布式/高并发/高可用等复杂场景
- 有技术难题需要解决（性能瓶颈/数据一致性/可用性等）
- 用了有一定门槛的技术（消息队列/分布式事务/缓存策略等）
- 有架构设计或重构经历

**没深度的项目特征**：
- 纯增删改查的后台管理系统
- 简单的接口对接和数据搬运
- 用框架默认配置，没有任何定制化
- 没有遇到任何技术挑战

| 判断标准 | 有深度 ✅ | 无深度 ❌ |
|---------|---------|---------|
| 缓存使用 | 缓存穿透/击穿/雪崩方案 + 分布式锁 | 简单 set/get 缓存 |
| 消息队列 | 事务消息 + 顺序消息 + 消费幂等 | 简单发消息 |
| 数据库 | 分库分表 + 读写分离 + 慢查询优化 | 简单 CRUD |
| 并发处理 | 锁/原子操作/线程池调优 | 无并发场景 |
| 架构设计 | 微服务拆分/网关设计/服务治理 | 单体 MVC |

#### 原则二：有量化结果

> 选的项目必须有可量化的成果，能证明你的工作产生了实际价值。

**量化维度**：

| 维度 | 示例 |
|------|------|
| 性能提升 | "P99 延迟从 800ms 降到 120ms" |
| 吞吐量提升 | "QPS 从 500 提升到 5000" |
| 成本降低 | "服务器从 20 台降到 5 台" |
| 效率提升 | "部署时间从 2 小时降到 10 分钟" |
| 故障减少 | "年故障从 20 次降到 2 次" |
| 业务增长 | "支持了双 11 百万 QPS" |
| 代码质量 | "单元测试覆盖率从 20% 提升到 80%" |

**没有量化结果的修复方法**：
- 回忆当时的监控数据/埋点数据
- 估算大致量级（"大约提升了 3~5 倍"）
- 从业务价值角度量化（"用户体验提升，转化率提升 X%"）

#### 原则三：有个人贡献

> 选的项目中，你的角色必须清晰，贡献必须明确。

**好的个人贡献描述**：

| 角色 | 描述方式 |
|------|---------|
| 项目负责人 | "我主导了整个方案设计和实施" |
| 核心开发 | "我负责了最核心的 XX 模块设计和开发" |
| 技术攻关 | "我解决了 XX 技术难题" |
| 架构师 | "我设计了整体技术架构" |

**避免的说法**：
- ❌ "我们团队做了..." → 你做了什么？
- ❌ "我参与了..." → 参与到什么程度？
- ❌ "我负责写代码..." → 太笼统

#### 原则四：真实性

> 选的项目必须是你亲身经历的，能经得起追问。

**真实性验证标准**：

```
□ 能画出系统架构图
□ 能说出核心表结构
□ 能解释每个技术选型的理由
□ 能描述遇到的问题和解决过程
□ 能回答"如果重新做你会怎么改"
□ 能说出线上出过什么问题、怎么处理的
```

**注意**：不要编造或夸大。面试官追问几个问题就能判断你是否真正做过。一旦被发现造假，直接淘汰。

**如果项目经历不够"亮眼"怎么办**：

| 情况 | 策略 |
|------|------|
| 项目体量小 | 重点讲技术方案和思考过程，而非数据量 |
| 只做了模块开发 | 深挖模块中的技术细节 |
| 项目简单 | 重点讲你对项目的思考和改进建议 |
| 没有分布式经验 | 从单体项目中挖掘并发/性能/设计模式的亮点 |

#### 原则五：时效性

> 优先选择近 2 年内的项目。太老的项目可能技术栈过时，面试官兴趣不大。

| 时效 | 建议 | 说明 |
|------|------|------|
| 近 1 年 | ⭐⭐⭐⭐⭐ 优先选 | 最新经验，最鲜活 |
| 1~2 年 | ⭐⭐⭐⭐ 可选 | 经验仍有参考价值 |
| 2~3 年 | ⭐⭐⭐ 谨慎选 | 技术可能过时 |
| 3 年以上 | ⭐☆ 不推荐 | 除非是特别有深度的项目 |

#### 原则六：匹配目标岗位

> 选的项目要匹配目标岗位的技术栈和业务领域。

**示例**：

| 目标岗位 | 推荐选材 | 不推荐选材 |
|---------|---------|-----------|
| 电商后端 | 电商交易/库存/营销系统 | 内部 OA 系统 |
| 金融后端 | 支付/清结算/风控系统 | 游戏后端 |
| 中间件开发 | 自研框架/SDK/组件 | 业务 CRUD 系统 |
| 大数据开发 | 数仓/实时计算/ETL | 纯后端 CRUD |
| 架构师 | 系统重构/架构演进 | 单模块开发 |

### 2.2 项目素材盘点表

列出你所有参与过的项目，用以下表格评估：

| 项目名称 | 时间 | 角色 | 技术栈 | 技术深度 | 量化结果 | 个人贡献 | 时效性 | 岗位匹配 | 综合 |
|---------|------|------|--------|---------|---------|---------|--------|---------|------|
| 项目A | 2024.06 | 负责人 | SpringCloud+Redis+RocketMQ | ⭐⭐⭐⭐⭐ | QPS 3000→5000 | 主导设计 | 近1年 | ✅ 匹配 | **优先选** |
| 项目B | 2023.08 | 核心开发 | SpringBoot+MySQL+Redis | ⭐⭐⭐⭐ | P99 降60% | 核心模块 | 1~2年 | ✅ 匹配 | **备选** |
| 项目C | 2022.03 | 开发 | SpringBoot+MySQL | ⭐⭐ | 无量化 | 模块开发 | 3年+ | ⚠️ 部分匹配 | **不推荐** |

**选材策略**：
- 准备 **2~3 个核心项目**（优先选），每个项目准备 15~20 分钟的深度讲解

- 每个项目准备 **1~2 个技术亮点**，作为深入讲解的切入点

## 第三章 选材策略——如何匹配目标岗位

### 3.1 目标岗位画像分析

在选材之前，先分析目标岗位需要什么样的人：

**JD（Job Description）关键词提取**：

```
示例 JD：
"负责电商平台后端服务开发，要求：
  - 3 年以上 Java 开发经验
  - 熟悉 Spring Cloud 微服务架构
  - 熟悉 MySQL 调优、Redis 缓存设计
  - 有消息队列（Kafka/RocketMQ）使用经验
  - 有高并发系统设计经验
  - 了解分布式事务、分布式锁
  - 有电商/支付领域经验优先"
```

**提取出的关键词**：

| 类别 | 关键词 | 对应选材方向 |
|------|--------|------------|
| 技术栈 | Spring Cloud / MySQL / Redis / RocketMQ | 选用了这些技术的项目 |
| 能力要求 | 高并发 / 分布式事务 / 分布式锁 | 有这些场景的项目 |
| 业务领域 | 电商 / 支付 | 电商或支付相关项目 |
| 经验要求 | 3 年+ / 高并发经验 | 能体现这些经验的项目 |

### 3.2 项目与岗位匹配矩阵

| JD 关键词 | 项目A（电商交易） | 项目B（支付系统） | 项目C（内部OA） |
|---------|----------------|----------------|--------------|
| Spring Cloud | ✅ | ✅ | ❌ |
| MySQL 调优 | ✅ | ✅ | ⚠️ |
| Redis 缓存 | ✅ | ✅ | ❌ |
| RocketMQ | ✅ | ❌ | ❌ |
| 高并发 | ✅ | ✅ | ❌ |
| 分布式事务 | ✅ | ✅ | ❌ |
| 电商/支付 | ✅ | ✅ | ❌ |
| **匹配度** | **95%** | **90%** | **20%** |

→ 选项目A和项目B作为核心项目。

### 3.3 不同年限的选材策略

| 工作年限 | 选材策略 | 项目数量 | 重点 |
|---------|---------|---------|------|
| 1~3 年 | 选 1~2 个最有亮点的项目 | 1~2 个 | 技术深度 + 学习能力 |
| 3~5 年 | 选 2~3 个有技术深度的项目 | 2~3 个 | 技术深度 + 架构能力 + 业务理解 |
| 5~8 年 | 选 2~3 个有架构/重构经历的项目 | 2~3 个 | 架构设计 + 技术决策 + 团队影响力 |
| 8 年+ | 选 1~2 个有技术影响力的项目 | 1~2 个 | 技术战略 + 团队建设 + 技术文化 |

### 3.4 针对不同面试场景的选材

| 面试场景 | 选材策略 | 讲解重点 |
|---------|---------|---------|
| 一面（技术面） | 选技术深度最强的项目 | 技术方案 + 实现细节 |
| 二面（架构面） | 选有架构设计/重构的项目 | 架构决策 + 技术权衡 |

| 高管面 | 选有影响力的项目 | 技术视野 + 商业理解 |

### 3.5 不同公司类型的选材偏好

| 公司类型 | 偏好项目类型 | 考查重点 |
|---------|------------|---------|
| 大厂（阿里/字节/美团） | 高并发/大规模/分布式 | 技术深度 + 系统设计 |

| 金融科技 | 强一致性/高可靠 | 事务/可靠性/合规 |

## 第四章 项目分类与讲法

### 4.1 六大项目类型

根据技术特征，项目可以分为六类，每类的讲法侧重点不同：

#### 类型一：高并发系统

**特征**：QPS 高（1000+）、需要应对流量峰值

**讲解重点**：

| 要点 | 说明 |
|------|------|
| 流量量级 | QPS / 日活 / 峰值流量 |
| 架构设计 | 多级缓存 / 异步化 / 削峰填谷 |
| 性能优化 | 压测 / 瓶颈分析 / 优化手段 |
| 稳定性保障 | 限流 / 熔断 / 降级 / 容灾 |
| 扩展能力 | 水平扩展 / 数据库分片 |

## 第五章 大纲框架——STAR/SPARK

### 5.1 STAR 框架

最经典的项目讲述框架，适用于大多数面试场景。

```
S - Situation（情境）
    业务背景 + 团队规模 + 技术栈

T - Task（任务）
    你的角色 + 面临的挑战 + 目标

A - Action（行动）
    你做了什么 + 技术方案 + 实现细节

R - Result（结果）
    量化成果 + 业务价值 + 个人成长
```

**STAR 框架详细模板**：

#### S - Situation（情境）

```
我们的系统是________，服务于________业务。
团队规模________人，技术栈是________。
日均________，峰值________。
系统当时的状态是________（正常运行的/存在问题的/正在重构的）。
```

**示例**：
> "我们的系统是一个电商平台的订单中心，服务于 B2C 交易业务。团队 8 人，技术栈是 Spring Cloud + MySQL + Redis + RocketMQ。日均订单 10 万单，大促峰值 QPS 3000。系统当时是单体架构，下单链路同步调用 6 个下游服务，P99 响应 800ms。"

#### T - Task（任务）

```
我的角色是________。
面临的挑战是________。
目标是将________从________优化到________。
时间节点是________。
```

**示例**：
> "我是订单系统的负责人。面临的挑战是：大促时下单经常超时，业务方要求把 P99 从 800ms 降到 200ms 以内，同时保证数据一致性。时间节点是双 11 前 2 个月内完成改造。"

#### A - Action（行动）

这是最重要的部分，需要按层次展开：

```
第一层：方案总览
    整体思路是________。

第二层：关键技术方案
    1. ________（做了什么 + 为什么这样做 + 怎么做的）
    2. ________
    3. ________

第三层：技术细节（面试官追问时展开）
    - 选型理由：为什么选 A 不选 B？
    - 实现细节：核心代码逻辑 / 数据结构 / 算法
    - 踩坑经验：遇到了什么问题？怎么解决的？
```

**示例**：
> "整体思路是将同步调用改为异步化，同时保证数据一致性。
>
> 第一，引入 RocketMQ 将下单链路异步化。订单创建后发消息通知库存、营销、物流等下游服务，响应时间从 800ms 降到 120ms。之所以选 RocketMQ 而非 Kafka，是因为需要事务消息保证订单和消息的一致性。
>
> 第二，用 RocketMQ 事务消息保证一致性。先发半消息 → 执行本地事务（创建订单）→ 根据本地事务结果提交或回滚半消息。如果超时未确认，RocketMQ 会回查本地事务状态。
>
> 第三，Redis Lua 脚本做库存原子扣减。用 DECR 原子扣减 + Lua 脚本检查库存 + 标记用户防重复购买。之所以用 Lua 而非分布式锁，是因为 Lua 脚本在 Redis 中原子执行，性能远优于分布式锁。
>
> 第四，Sentinel 限流熔断。大促时自动限流非核心接口，降级营销推荐等非核心链路。"

#### R - Result（结果）

```
量化结果：
    - 性能：________从________优化到________（提升________%）
    - 稳定性：________
    - 成本：________

业务价值：
    - ________

个人收获：
    - ________
```

**示例**：
> "P99 从 800ms 降到 120ms，降低 85%。大促零超时，稳定支撑了双 11 的 50 万峰值 QPS。 RocketMQ 事务消息保证了订单和消息的一致性，上线后没有发生过数据不一致的故障。
>
> 个人收获：深入理解了分布式事务的各种方案和适用场景，也积累了高并发系统设计的经验。"

### 5.2 SPARK 框架

STAR 的进阶版，更适合有架构决策的项目。

```
S - Situation（情境）
    业务背景 + 系统现状

P - Problem（问题）
    核心痛点 + 技术挑战

A - Approach（方案）
    方案设计 + 技术选型 + 权衡分析

R - Result（结果）
    量化成果 + 业务价值

K - Knowledge（收获）
    经验总结 + 反思改进
```

**SPARK vs STAR 的区别**：

| 维度 | STAR | SPARK |
|------|------|-------|
| 问题分析 | Task 中简单描述 | Problem 单独深入分析 |
| 方案设计 | Action 偏实现细节 | Approach 包含技术选型 + 权衡 |
| 经验反思 | 无 | Knowledge 单独总结 |
| 适用场景 | 常规项目 | 架构设计/重构项目 |
| 深度 | 中 | 深 |

## 第七章 常见项目类型大纲示例

### 7.1 示例一：电商交易系统（高并发 + 分布式事务）

```markdown
## 项目：电商平台交易系统

### 一、项目概览
- 业务领域：B2C 电商平台
- 项目时间：2023.06 ~ 2024.06
- 团队规模：12 人（后端 8 人）
- 我的角色：订单系统负责人
- 技术栈：Spring Cloud Alibaba / MySQL / Redis / RocketMQ / Seata / Sentinel

### 二、业务背景
- 日均订单 10 万单，大促峰值 QPS 3000
- 下单链路涉及 6 个下游服务：库存/营销/物流/积分/通知/风控
- 原系统单体架构，同步调用，P99 响应 800ms

### 三、技术挑战
1. 性能瓶颈：同步调用链路太长，大促时超时严重
2. 数据一致性：异步化后如何保证订单与下游数据一致
3. 防超卖：高并发下库存扣减的原子性
4. 流量洪峰：大促瞬时流量是平时的 50 倍

### 四、技术方案

#### 方案一：异步化改造（核心）
- 目标：P99 从 800ms 降到 200ms
- 思路：将同步调用改为 MQ 异步通知
- 选型：RocketMQ（而非 Kafka），因为需要事务消息
- 实现：
  - 订单创建后发 RocketMQ 消息通知下游
  - 用事务消息保证"订单创建 + 消息发送"的原子性
  - 半消息 → 本地事务（创建订单）→ 提交/回滚
  - 超时回查：RocketMQ 回查本地事务状态
- 结果：P99 从 800ms 降到 120ms

#### 方案二：防超卖
- 目标：高并发下库存不超卖
- 方案：Redis Lua 脚本原子扣减
- 实现：
  - 库存预热到 Redis
  - Lua 脚本：检查库存 + DECR + 标记用户（原子操作）
  - MySQL 兜底：WHERE stock > 0 乐观锁
- 结果：零超卖

#### 方案三：流量管控
- 目标：应对大促 50 倍流量洪峰
- 方案：Sentinel 限流 + 降级 + 熔断
- 实现：
  - 网关层：QPS 限流
  - 服务层：慢调用熔断 + 异常比例熔断
  - 降级策略：非核心接口返回默认值
- 结果：大促零超时

### 五、量化结果
| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| P99 延迟 | 800ms | 120ms | 85%↓ |
| 峰值 QPS | 500 | 3000 | 6x↑ |
| 超时率 | 15% | 0% | 100%↓ |
| 系统可用性 | 99.5% | 99.99% | - |

### 六、踩坑经验
1. RocketMQ 事务消息回查超时
   - 现象：部分订单状态长时间为"处理中"
   - 原因：回查接口超时，RocketMQ 默认 60s 后放弃
   - 解决：增加回查接口超时配置 + 对账补偿任务

2. Redis 主从同步延迟导致超卖
   - 现象：主从切换瞬间出现 2 笔超卖
   - 原因：主从同步是异步的，切换瞬间数据不一致
   - 解决：MySQL 乐观锁兜底 + 双写 Redis 主从

### 七、反思与收获
- 做得好：异步化方案设计合理，事务消息保证了一致性
- 可改进：应该提前做全链路压测，而非上线后发现问题
- 如果重来：会考虑用 Seata TCC 模式替代事务消息，减少对 MQ 的强依赖
```

### 7.2 示例二：微服务架构演进（单体→微服务）

```markdown
## 项目：系统微服务架构演进

### 一、项目概览
- 业务领域：SaaS 企业服务平台
- 项目时间：2023.01 ~ 2023.12
- 团队规模：15 人
- 我的角色：架构组成员，主导服务拆分
- 技术栈：Spring Cloud Alibaba / Nacos / Gateway / Sentinel / SkyWalking

### 二、业务背景
- 原系统：PHP 单体应用，运行 5 年，代码 50 万行
- 痛点：发布耦合（改一个 Bug 全量发布）、性能瓶颈（PHP-FPM 连接数限制）
- 目标：迁移到 Java 微服务架构

### 三、技术挑战
1. 服务拆分：怎么拆？拆多细？
2. 数据迁移：PHP 和 Java 双运行期间数据怎么同步？
3. 平滑迁移：怎么保证迁移过程中业务不中断？
4. 团队转型：PHP 开发转 Java，学习成本

### 四、技术方案

#### 方案一：DDD 领域驱动拆分
- 思路：按业务领域拆分，而非按技术层拆分
- 拆分结果：用户服务/订单服务/商品服务/支付服务/通知服务
- 拆分依据：限界上下文 + 团队组织结构（康威定律）
- 关键决策：先拆用户和商品（变更最频繁），后拆支付（最复杂）

#### 方案二：双写迁移方案
- 阶段一：PHP 继续服务，Java 新服务同步开发
- 阶段二：PHP 写 MySQL → Canal → Java 服务读（数据双读）
- 阶段三：Java 服务写 → Canal → PHP 服务读（灰度切写流量）
- 阶段四：全量切到 Java，PHP 下线
- 关键点：每一步都可回滚

#### 方案三：微服务基础设施
- 注册中心+配置中心：Nacos
- API 网关：Spring Cloud Gateway
- 限流熔断：Sentinel
- 链路追踪：SkyWalking（字节码增强，无侵入）
- 分布式事务：Seata AT 模式

### 五、量化结果
| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| 发布频率 | 每月 1 次 | 每天 3~5 次 | 100x↑ |
| 部署时间 | 2 小时 | 10 分钟 | 12x↓ |
| 系统可用性 | 99.5% | 99.95% | - |
| P99 延迟 | 500ms | 100ms | 80%↓ |

### 六、踩坑经验
1. 分布式事务性能问题
   - 现象：Seata AT 模式下部分接口响应变慢
   - 原因：全局锁竞争 + undo_log 表成为瓶颈
   - 解决：将强一致场景用 AT 模式，其他场景用消息事务

2. 服务拆分过细
   - 现象：拆了 20 个微服务，运维成本暴增
   - 原因：拆得太细，一个简单功能跨 5 个服务调用
   - 解决：合并了 6 个小服务，最终 14 个服务
```

```markdown

- 业务领域：金融支付系统
- 项目时间：2024.03 ~ 2024.06

- 系统运行 2 年，随着业务增长性能持续恶化

- 慢查询告警每天 10+ 次

### 三、技术挑战
1. JVM 频繁 Full GC：内存泄漏？
2. 数据库慢查询：索引失效？SQL 不合理？
3. 接口响应慢：是 GC 还是 DB 还是网络？
4. 定位困难：问题偶发，难以复现

### 四、技术方案

#### 方案一：JVM 调优
- 排查过程：
  1. jstat 观察 GC 频率和各区域大小
  2. jmap dump 堆内存 → MAT 分析

#### 方案二：数据库优化
- 排查过程：
  1. 开启慢查询日志，收集 TOP 10 慢 SQL
  2. EXPLAIN 分析执行计划
  3. 定位问题：type=ALL（全表扫描）、Using filesort
- 解决方案：
  - 重建索引：覆盖索引消除回表
  - SQL 重写：子查询改 JOIN
  - 分页优化：深分页用游标方案
- 结果：慢查询从每天 10+ 降到 0~1 次

#### 方案三：接口性能优化
- 排查过程：
  1. SkyWalking 链路追踪定位耗时分布
  2. 发现 60% 耗时在 Redis（大 Key）
  3. Arthas trace 命令定位具体方法
- 解决方案：
  - 拆分大 Key（Hash 拆成多个小 Hash）
  - 批量操作改 Pipeline
  - 本地缓存（Caffeine）减少 Redis 访问
- 结果：P99 从 800ms 降到 150ms

### 五、量化结果
| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| P99 延迟 | 800ms | 150ms | 81%↓ |
| Full GC | 每周 2~3 次 | 每月 0~1 次 | 90%↓ |
| 慢查询 | 每天 10+ | 每天 0~1 | 90%↓ |
| CPU 使用率 | 85% | 40% | 53%↓ |

### 六、踩坑经验
1. ThreadLocal 泄漏定位花了 2 天
   - 教训：应该第一时间用 jmap + MAT 分析
2. 大 Key 问题
   - 教训：设计阶段就应该限制 Key 大小

## 第八章 追问防线设计

### 8.1 为什么要设计追问防线

面试官听完你的项目介绍后，一定会追问。追问的目的是验证你是否真正做过、是否真正理解。

```
项目讲解（你主动讲）→ 追问环节（面试官主导）→ 深度评估
```

**追问防线的核心思路**：在讲解时埋下"钩子"，引导面试官追问你准备好的亮点。

### 8.2 钩子设计

**什么是钩子**：在讲解中故意提到一个技术点，但不展开，等面试官追问。

```
讲解："我用 Redis Lua 脚本做库存扣减..."
          ↑
         钩子：面试官可能追问"Lua 脚本怎么写的？"

准备好的回答：
"Lua 脚本逻辑是：
 1. 检查库存是否足够
 2. 检查用户是否已购买
 3. 扣减库存
 4. 标记用户已购买
 这四步在一个 Lua 脚本中原子执行，避免了分布式锁的性能开销..."
```

**钩子设计原则**：
- 钩子必须是你**有准备**的技术点
- 钩子要有足够的**技术深度**可挖
- 不要埋太多钩子（2~3 个足够）
- 钩子之间要有**层次**（浅层 → 深层）

### 8.3 追问防线分层

```
第一层防线：方案概述（讲解时已覆盖）
    ↓ 面试官追问
第二层防线：技术选型理由（为什么选 A 不选 B）
    ↓ 面试官继续追问
第三层防线：实现细节（核心代码/数据结构/算法）
    ↓ 面试官深入追问
第四层防线：踩坑经验（遇到的问题和解决方案）
    ↓ 面试官极限追问
第五层防线：延伸思考（如果重新做/更大规模怎么办）
```

### 8.4 追问防线示例

以"RocketMQ 事务消息"为例：

| 防线层级 | 可能的追问 | 准备的回答 |
|---------|-----------|-----------|
| 第一层 | "事务消息是什么？" | 半消息 + 本地事务 + 回查机制，保证消息和本地事务的原子性 |
| 第二层 | "为什么不用 Kafka + 本地消息表？" | Kafka 无原生事务消息，本地消息表需要额外的定时任务扫描，增加系统复杂度和延迟。RocketMQ 原生支持，回查机制可靠性更高 |
| 第三层 | "回查机制怎么实现的？" | RocketMQ Broker 存储半消息 → 超时（60s）未确认 → 回查 Producer 的 `checkLocalTransaction` 方法 → 根据返回值提交或回滚 |
| 第四层 | "遇到过什么问题？" | 回查接口超时导致部分订单状态卡住。原因是回查时查询 DB 太慢，加了索引后解决。还加了兜底对账任务 |
| 第五层 | "如果 QPS 再翻 10 倍怎么办？" | 事务消息有性能瓶颈（半消息存储 + 回查），更高 QPS 可以考虑用本地消息表 + 异步对账方案，牺牲一些实时性换吞吐量 |

## 第九章 常见误区与反模式

### 9.1 误区一：流水账式讲解

**症状**：按时间顺序讲开发过程，没有重点。

```
❌ "我先做了需求分析，然后设计了数据库表，
    然后写了 Controller、Service、Mapper，
    最后联调测试上线。"
```

**问题**：没有技术亮点，面试官无法追问。

**改进**：用 STAR/SPARK 框架，突出挑战和方案，而非开发流程。

### 9.2 误区二：只讲 What 不讲 Why

**症状**：只说用了什么技术，不说为什么选这个技术。

```
❌ "我们用了 Redis 做缓存，用了 RocketMQ 做消息队列。"

✅ "我们选 RocketMQ 而非 Kafka，是因为需要事务消息保证
    订单和消息的一致性。Kafka 没有原生事务消息，
    需要自建本地消息表方案，增加系统复杂度。"
```

### 9.3 误区三：夸大个人贡献

**症状**：把团队的成果说成自己的，或者说"我设计了架构"但实际上只是执行者。

**问题**：面试官追问架构设计细节时露馅。

**改进**：诚实描述个人角色。"我负责了 XX 模块的设计和开发"比"我主导了整个系统架构"更可信。

### 9.4 误区四：没有量化数据

**症状**：只说"性能提升了""系统稳定了"，没有具体数据。

```
❌ "优化后系统性能提升了很多，运行也很稳定。"

✅ "P99 从 800ms 降到 120ms，降低了 85%。
    大促零超时，系统可用性从 99.5% 提升到 99.99%。"
```

### 9.5 误区五：技术细节太多太少

**症状**：要么讲得太笼统没有细节，要么讲得太细像念代码。

```
❌ 太少："我用了 Redis 缓存。"（然后呢？）

❌ 太多："我先写了 RedisTemplate 的配置类，
    然后写了 @Cacheable 注解，然后..."
    （不需要讲代码细节）

✅ 恰当："我用 Redis 做了多级缓存——Caffeine 做本地缓存
    挡第一层，Redis 做分布式缓存挡第二层。
    缓存一致性用 Cache-Aside 模式：先更新 DB，再删除缓存。
    对于强一致场景，用延迟双删策略。"
```

### 9.6 误区六：忽视业务价值

**症状**：只讲技术方案，不讲业务价值。

```
❌ "我做了分库分表，用了 ShardingSphere。"

✅ "业务量增长到单表 5000 万行，查询性能恶化。
    我做了分库分表，查询性能提升了 5 倍，
    支撑了业务从日活 10 万到 50 万的增长。"
```

### 9.7 误区七：不会说"不知道"

**症状**：被追问到不熟悉的知识点时，强行编造答案。

**问题**：面试官一听就知道你在编，比说"不知道"更减分。

**改进**：

```
"这个我确实不太了解细节。但我的理解是...（说出你的推测）。
 如果要深入了解，我会从...方向去研究。"
```

这样既诚实，又展示了思考能力和学习方向。

### 9.8 误区八：项目太多没有重点

**症状**：面试官问"讲一个你的项目"，你讲了 5 个项目每个 2 分钟。

**问题**：每个都浅尝辄止，没有深度。

**改进**：选 1~2 个重点项目，每个讲 15~20 分钟，讲深讲透。

### 9.9 误区九：不会引导面试官

**症状**：被动等面试官提问，不主动引导到自己的优势领域。

**改进**：在讲解中埋钩子，引导面试官追问你准备好的亮点。

```
"在这个过程中，我深入研究了 RocketMQ 事务消息的实现原理..."
                                       ↑
                              钩子：引导追问事务消息
```

### 9.10 误区十：准备不充分

**症状**：讲项目时卡壳、数据记不清、技术细节说不清楚。

**改进**：面试前做充分准备。

**准备清单**：

```
□ 能画出系统架构图（白板画）
□ 能说出核心数据量级（QPS/数据量/用户量）
□ 能解释每个技术选型的理由
□ 能说出 2~3 个踩坑经历
□ 能回答"如果重新做你会怎么改"
□ 能说出 1~2 个量化结果
□ 准备了 2~3 个追问防线
□ 对每个技术点准备了 What → Why → How 三层回答
```

>

### Q2：你在这个项目中遇到最大的技术挑战是什么？

**回答策略**：

> 选一个有深度的技术挑战，按"问题 → 分析 → 方案 → 结果"展开。

**示例回答**：

> "最大的挑战是保证异步化后的数据一致性。
>
> 原来的同步调用中，如果库存扣减失败可以直接回滚订单。但改成异步后，订单先创建成功，再异步通知库存扣减，如果库存扣减失败就出现数据不一致。
>
> 我评估了三种方案：
> 1. **RocketMQ 事务消息**：半消息 + 本地事务 + 回查。可靠性高，但有回查延迟。
> 2. **本地消息表 + 定时任务**：简单可靠，但定时任务有延迟，且需要额外的表。
> 3. **Seata TCC**：强一致，但侵入性强，需要写 Try/Confirm/Cancel 三个方法。
>

### 11.1 支付系统（金融级强一致 + 高可用）

```markdown
## 项目：支付交易系统

### 一、项目概览
- 业务领域：互联网金融支付
- 项目时间：2024.01 ~ 2024.12
- 团队规模：10 人（后端 6 人）
- 我的角色：支付核心模块负责人
- 技术栈：Spring Boot / MySQL / Redis / RocketMQ / Seata / Sentinel

### 二、业务背景
- 服务于 3 万+商户的聚合支付平台，支持支付宝/微信/银联/快捷支付四渠道
- 日均交易 50 万笔，峰值 QPS 2000（大促时可达 5000）
- 涉及资金流转，对数据一致性要求极高：一分钱都不能错

### 三、技术挑战
1. 强一致性：支付涉及资金，订单状态和渠道返回必须100%一致
2. 渠道异构：4个支付渠道接口格式、回调方式、超时时间完全不同
3. 高可用：支付不可用=商户收不到钱=直接损失，RTO<30秒
4. 对账兜底：即使极端情况出错，也要通过对账发现并修复

### 四、技术方案

#### 方案一：支付流程状态机（核心）
- 目标：支付单状态流转清晰可控，不出现状态不一致
- 思路：用状态机定义所有合法状态转换，非法转换直接拒绝
- 实现：
  ```java
  // 支付单状态定义
  INIT → PAYING → SUCCESS / FAIL / CLOSED
  PAYING → SUCCESS（渠道回调成功）
  PAYING → FAIL（渠道回调失败）
  PAYING → CLOSED（超时关闭或主动关闭）

  // 状态机实现——策略模式 + 枚举
  public enum PayStatus {
      INIT, PAYING, SUCCESS, FAIL, CLOSED;

      // 合法转换表
      public boolean canTransitTo(PayStatus target) {
          switch (this) {
              case INIT:   return target == PAYING || target == CLOSED;
              case PAYING: return target == SUCCESS || target == FAIL || target == CLOSED;
              default:     return false; // 终态不可变
          }
      }
  }
  ```
- 选型原因：不用数据库状态字段直接 update，而是用状态机强制校验，
  防止并发场景下状态被错误覆盖（比如渠道回调成功的同时用户发起了关闭）
- 结果：上线后零状态不一致故障

#### 方案二：渠道异构适配——适配器模式
- 目标：统一4个渠道的差异化接口
- 实现：
  ```java
  // 统一支付接口
  public interface PayChannelAdapter {
      PayResult pay(PayOrder order);           // 发起支付
      PayResult query(PayOrder order);         // 查询支付结果
      RefundResult refund(RefundOrder order);  // 退款
      boolean verifyCallback(Map<String,String> params); // 验签
  }

  // 适配器实现——每个渠道一个
  @Service("alipayAdapter")
  public class AlipayAdapter implements PayChannelAdapter { ... }

  @Service("wechatAdapter")
  public class WechatAdapter implements PayChannelAdapter { ... }

  // 渠道路由——工厂模式 + Spring Map 注入
  @Service
  public class PayChannelRouter {
      @Autowired
      private Map<String, PayChannelAdapter> adapterMap; // Spring自动注入所有实现

      public PayChannelAdapter getAdapter(String channelCode) {
          return adapterMap.get(channelCode + "Adapter");
      }
  }
  ```
- 新增渠道只需实现 Adapter 接口 + 加 @Service 注解，零改动路由代码

#### 方案三：异步回调幂等 + 超时补偿
- 问题：渠道回调可能重复推送、可能丢失、可能延迟
- 三重保障：
  1. **回调幂等**：收到回调后先查支付单状态，终态（SUCCESS/FAIL）直接返回成功，
     非终态才执行状态转换 + 业务逻辑
  2. **主动查询补偿**：支付单 PAYING 超过 30s 未收到回调 → 定时任务主动调渠道查询接口
  3. **分布式锁防并发**：同一支付单的回调 + 主动查询可能并发到达，
     Redis SETNX lock:key 互斥，只有一个线程执行状态转换

#### 方案四：T+1 自动对账
- 每日凌晨跑对账任务：本地支付单表 vs 渠道结算文件
- 差错类型：长款（本地有渠道无→可能渠道漏回调）/ 短款（本地无渠道有→可能本地漏记录）
- 对账结果自动标记差错单 → 人工介入处理
- 实现：
  ```java
  @Scheduled(cron = "0 0 2 * * ?") // 每天凌晨2点
  public void reconcile() {
      // 1. 从渠道下载T+1结算文件（CSV）
      List<ChannelRecord> channelRecords = downloadSettlementFile();

      // 2. 查询本地T日所有SUCCESS/FAIL支付单
      List<PayOrder> localOrders = payOrderMapper.queryByDate(today);

      // 3. 双向比对——用支付单号做key
      Map<String, PayOrder> localMap = localOrders.stream()
          .collect(Collectors.toMap(PayOrder::getOutTradeNo, o -> o));
      Map<String, ChannelRecord> channelMap = channelRecords.stream()
          .collect(Collectors.toMap(ChannelRecord::getOutTradeNo, r -> r));

      // 4. 找出差错
      List<ReconcileDiff> diffs = new ArrayList<>();
      // 长款：本地有，渠道无
      localMap.keySet().stream()
          .filter(k -> !channelMap.containsKey(k))
          .forEach(k -> diffs.add(new ReconcileDiff(k, "LONG", localMap.get(k))));
      // 短款：渠道有，本地无
      channelMap.keySet().stream()
          .filter(k -> !localMap.containsKey(k))
          .forEach(k -> diffs.add(new ReconcileDiff(k, "SHORT", channelMap.get(k))));
      // 金额不一致
      localMap.keySet().stream()
          .filter(k -> channelMap.containsKey(k))
          .filter(k -> !localMap.get(k).getAmount().equals(channelMap.get(k).getAmount()))
          .forEach(k -> diffs.add(new ReconcileDiff(k, "AMOUNT_MISMATCH", ...)));

      // 5. 写入差错表，待人工处理
      reconcileDiffMapper.batchInsert(diffs);
  }
  ```

#### 方案五：高可用保障
- MySQL：主从 + MHA 自动故障转移（30s内完成切换）
- Redis：哨兵模式，主节点宕机自动选举
- 应用：双机房部署，Nginx upstream 做故障转移
- 降级：渠道超时 → 返回"处理中"而非"失败" → 主动查询补偿兜底
- Sentinel：支付接口 QPS 限流 + 渠道调用慢调用熔断

### 五、量化结果
| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| 支付成功率 | 95% | 99.5% | +4.5% |
| 状态不一致率 | 0.5% | 0% | 100%↓ |
| P99 响应 | 500ms | 120ms | 76%↓ |
| RTO（故障恢复） | 5min | 15s | 97%↓ |
| 对账差错率 | 2% | 0.01% | 99%↓ |

### 六、踩坑经验
1. 渠道回调签名验证踩坑
   - 现象：支付宝回调验签偶尔失败
   - 原因：支付宝回调参数用 GET 方式传，URL encode 规则和我们解析不一致
   - 解决：用支付宝 SDK 的验签方法，不要自己手动解析参数

2. Redis 主从切换导致幂等锁失效
   - 现象：切换瞬间两笔并发回调都通过了幂等校验
   - 原因：SETNX 在主节点成功，主从切换后新主节点没有这个 key
   - 解决：幂等校验改为"查 DB 状态 + 状态机校验"，Redis 锁只做辅助

### 七、反思与收获
- 做得好：状态机 + 对账双重保障，金融级一致性确实可靠
- 可改进：回调主动查询补偿应该做成事件驱动而非定时轮询
- 如果重来：对账文件下载改为渠道 API 拉取而非 FTP，实时性更强

### 八、追问防线
| 防线层级 | 追问 | 回答要点 |
|---------|------|---------|
| L1 | 状态机是什么？ | 用枚举定义合法状态转换，非法转换直接拒绝，防止并发覆盖 |
| L2 | 为什么不用分布式锁做幂等？ | 分布式锁在 Redis 主从切换时会失效，改为查 DB 状态更可靠 |
| L3 | 状态机怎么实现并发安全？ | 状态转换前先 SELECT 查当前状态 → 校验 canTransitTo → UPDATE WHERE status=原状态（乐观锁） |
| L4 | 对账发现差错怎么处理？ | 长款→重新调渠道查询确认；短款→查本地日志确认；金额不一致→人工介入 |
| L5 | 如果日交易量到 5000 万怎么对账？ | 对账文件用 Spark 批处理比对 + 差错表分库分表 + 实时对账（渠道 API 拉取替代 FTP） |

### 11.2 社交 Feed 流系统（推拉模式 + 缓存架构）

```markdown
## 项目：社交平台 Feed 流系统

### 一、项目概览
- 业务领域：社交平台（类似微博/小红书）
- 项目时间：2024.03 ~ 2024.09
- 团队规模：6 人
- 我的角色：Feed 流模块负责人
- 技术栈：Spring Boot / Redis / RocketMQ / MySQL / MongoDB

### 二、业务背景
- 注册用户 500 万，日活 80 万，KOL 大V 2000+
- 核心功能：用户发帖 → 粉丝看到帖子出现在自己的 Feed 流中
- 要求：Feed 流刷新延迟 < 500ms，支持无限下拉刷新

### 三、技术挑战
1. 写扩散 vs 读扩散：大V 2000 万粉丝，写扩散要写 2000 万条记录
2. Feed 流排序：按时间排序，但需要实时更新
3. 缓存一致性：新帖子要在 500ms 内出现在粉丝 Feed 中
4. 冷热差异：大V 热帖访问量大，普通用户帖子几乎无人看

### 四、技术方案

#### 方案一：推拉结合模型（核心架构决策）
- 核心问题：纯推模式（写扩散）——大V 发帖给 2000 万粉丝写 2000 万条，成本巨大
  纯拉模式（读扩散）——普通用户刷新时实时拉取所有关注者的帖子，延迟高
- 方案：**推拉结合**
  - 大V（粉丝 > 5 万）：发帖时只写自己的发帖表（推到 Redis Timeline 缓存），
    粉丝刷新时实时拉取（读扩散）
  - 普通用户（粉丝 < 5 万）：发帖时主动推到所有粉丝的收件箱（写扩散）
  - 粉丝刷新时：先读自己的收件箱（推的部分）+ 再实时拉取关注的大V 帖子（拉的部分）→ 合并排序
- 选型原因：
  - 大V 推写成本 = 粉丝数 × 1条，2000万粉丝 → 写 2000万条，不可接受
  - 大V 拉读成本 = 粉丝数 × 读1次，但粉丝刷新时才读，可以缓存
  - 普通用户推写成本 = 粉丝数（< 5万）× 1条，可接受
- 实现：
  ```java
  // 发帖
  public void publishPost(Post post) {
      // 1. 写入发帖表（所有用户都要写）
      postMapper.insert(post);

      // 2. 推/拉分支
      if (post.getAuthor().getFollowerCount() > 50000) {
          // 大V：只写发帖缓存（拉模式）
          redisTemplate.opsForList().leftPush(
              "timeline:outbox:" + post.getAuthorId(), post.getId());
          // 缓存只保留最近 1000 条
          redisTemplate.opsForList().trim(
              "timeline:outbox:" + post.getAuthorId(), 0, 999);
      } else {
          // 普通用户：推到所有粉丝收件箱（推模式）
          List<Long> followerIds = followerMapper.selectByAuthorId(post.getAuthorId());
          for (Long followerId : followerIds) {
              redisTemplate.opsForList().leftPush(
                  "timeline:inbox:" + followerId, post.getId());
              redisTemplate.opsForList().trim(
                  "timeline:inbox:" + followerId, 0, 999);
          }
          // 批量推送用 Redis Pipeline 优化
          // 5万粉丝 Pipeline 约 50ms 完成
      }
  }

  // 读取 Feed 流
  public List<Post> getFeed(Long userId, long lastPostId, int pageSize) {
      // 1. 读自己的收件箱（推的部分）
      List<Long> inboxPostIds = redisTemplate.opsForList().range(
          "timeline:inbox:" + userId, 0, pageSize - 1);

      // 2. 拉取关注的大V 的帖子（拉的部分）
      List<Long> bigVAuthorIds = followerMapper.selectBigVByFollowerId(userId);
      List<Long> outboxPostIds = new ArrayList<>();
      for (Long authorId : bigVAuthorIds) {
          List<Long> ids = redisTemplate.opsForList().range(
              "timeline:outbox:" + authorId, 0, pageSize - 1);
          outboxPostIds.addAll(ids);
      }

      // 3. 合并 + 排序 + 分页
      List<Long> allPostIds = mergeAndSort(inboxPostIds, outboxPostIds);
      allPostIds = paginate(allPostIds, lastPostId, pageSize);

      // 4. 批量查帖子详情
      return batchGetPosts(allPostIds);
  }
  ```
- 结果：大V 发帖延迟从"写 2000 万条需要 10s"降到"写 1 条 < 1ms"

#### 方案二：缓存架构设计
- 多级缓存：
  - L1：Caffeine 本地缓存——帖子详情（热点帖子命中率 80%）
  - L2：Redis Timeline——Feed 流 ID 列表 + 帖子摘要
  - L3：MySQL——帖子完整内容（缓存 miss 时回源）
- 缓存一致性：
  - 新帖 → RocketMQ 消息 → 更新 Timeline + 刷新 Caffeine
  - 帖子修改/删除 → Cache-Aside 模式：先更新 DB → 再删除缓存

#### 方案三：下拉刷新分页
- 问题：传统 offset 分页在数据变化时会漏数据/重复数据
- 方案：游标分页（基于 post_id 时间戳）
  - 客户端传 last_post_id → 服务端返回比这个 id 更小的 pageSize 条
  - 帖子按时间递减排列 → post_id 越大越新 → 分页用 post_id < lastPostId

### 五、量化结果
| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| 大V发帖延迟 | 10s | <1ms | 10000x↓ |
| Feed刷新P99 | 2s | 200ms | 90%↓ |
| Redis内存 | 50GB | 8GB | 84%↓ |
| 缓存命中率 | 60% | 95% | +35% |

### 六、踩坑经验
1. 推拉切换边界问题
   - 现象：某用户从 49999 粉丝涨到 50001 → 从推模式切换到拉模式 → 粉丝突然看不到他的旧帖子
   - 解决：切换时做一次"全量推"——把最近 1000 条帖子推到所有粉丝收件箱，然后切换为拉模式

2. Redis Timeline 内存膨胀
   - 现象：每个用户 Timeline 存储 1000 条 post_id，500万用户 → 5000万条
   - 解决：普通用户 Timeline 只保留最近 200 条（活跃用户才保留 1000 条）+ 冷用户不缓存

### 七、追问防线
| 防线层级 | 追问 | 回答要点 |
|---------|------|---------|
| L1 | 推拉模式是什么？ | 推=写扩散（发帖时推到粉丝），拉=读扩散（刷新时拉取关注者帖子） |
| L2 | 为什么推拉结合而非纯推或纯拉？ | 纯推大V成本巨大（2000万×写），纯拉普通用户刷新延迟高 |
| L3 | 推拉切换边界怎么处理？ | 切换时做一次全量推，把最近帖子写入粉丝收件箱 |
| L4 | Feed流分页为什么用游标？ | offset分页在数据插入时会漏数据/重复数据，游标基于post_id稳定 |
| L5 | 如果用户量到5000万？ | 大V阈值调高到100万+Timeline分片+Redis Cluster+冷热分离存储 |

### 11.3 实时数据平台（Kafka + Flink + ClickHouse）

```markdown
## 项目：实时数据分析平台

### 一、项目概览
- 业务领域：电商运营数据实时分析
- 项目时间：2024.06 ~ 2024.12
- 团队规模：8 人
- 我的角色：实时计算引擎负责人
- 技术栈：Kafka / Flink / ClickHouse / MySQL / Redis / Grafana

### 二、业务背景
- 原方案：T+1 报表——每天凌晨用 Spark 批处理昨天数据，运营看数据要等隔天
- 痛点：运营要做实时决策（促销效果实时监控、异常订单实时告警），T+1 不满足
- 目标：核心指标实时化——订单量/GMV/转化率/UV 延迟 < 30秒

### 三、技术挑战
1. 数据量：日均事件 5 亿条（点击/加购/下单/支付），峰值 10 万条/秒
2. 实时性：指标更新延迟 < 30秒
3. 数据质量：源头脏数据/重复事件/迟到数据如何处理
4. 存储选型：实时指标存储既要写入快又要查询快

### 四、技术方案

#### 方案一：数据流架构
- 整体链路：业务 MySQL → Canal → Kafka → Flink 实时计算 → ClickHouse 存储 → Grafana 展示
- 为什么选这条链路而非直接 CDC 到 Flink：
  - Kafka 做缓冲层：Canal 解析 binlog → Kafka Topic → Flink 消费，
    Kafka 解耦了数据采集和计算，Flink 重启不影响数据采集
  - Kafka 做数据回放：Flink 需要重算历史数据时，调 Kafka offset 即可

#### 方案二：Flink 实时计算核心
- UV 计算——Flink 去重：
  ```java
  // 方案：Redis HyperLogLog 去重 + 滚动窗口聚合
 DataStream<Event> events = env.addSource(new FlinkKafkaConsumer<>("user_events", ...));

  events
      .keyBy(event -> event.getDimensionKey()) // 按维度分组（如"首页-全部用户"）
      .window(TumblingProcessingTimeWindows.of(Time.seconds(30))) // 30秒滚动窗口
      .process(new UVProcessFunction())
      .addSink(new ClickHouseSink());

  // UVProcessFunction
  public class UVProcessFunction extends ProcessWindowFunction<Event, Metric, String, TimeWindow> {
      @Override
      public void process(String key, Context ctx, Iterable<Event> events, Collector<Metric> out) {
          Jedis jedis = new Jedis("redis-host");
          String hllKey = "uv:" + key + ":" + ctx.window().getStart();
          for (Event e : events) {
              jedis.pfadd(hllKey, e.getUserId()); // HyperLogLog 添加
          }
          long uv = jedis.pfcount(hllKey); // 获取UV估算值
          out.collect(new Metric(key, "UV", uv, ctx.window().getStart()));
          jedis.del(hllKey); // 窗口结束清理
      }
  }
  ```
  - 选型原因：HyperLogLog 12KB 内存可估算百万级 UV，误差 < 0.81%，远优于 Set 全量去重
  - GMV 计算——Flink 滚动窗口 SUM：
  ```java
  events
      .filter(e -> e.getType() == "PAY_SUCCESS")
      .keyBy(e -> e.getDimensionKey())
      .window(TumblingProcessingTimeWindows.of(Time.seconds(30)))
      .aggregate(new SumAggregateFunction()) // SUM(amount)
      .addSink(new ClickHouseSink());
  ```

#### 方案三：迟到数据处理
- 问题：用户下单事件可能因为网络延迟，30秒窗口关闭后才到达
- 方案：Flink AllowedLateness + SideOutput
  ```java
  events
      .keyBy(e -> e.getDimensionKey())
      .window(TumblingProcessingTimeWindows.of(Time.seconds(30)))
      .allowedLateness(Time.seconds(60)) // 允许迟到60秒
      .sideOutputLateData(lateTag) // 超过60秒的迟到数据输出到侧输出流
      .process(new UVProcessFunction());

  // 迟到数据单独处理——写入迟到数据表，后续离线修正
  DataStream<Event> lateEvents = mainStream.getSideOutput(lateTag);
  lateEvents.addSink(new MySQLLateEventSink());
  ```

#### 方案四：ClickHouse 存储
- 为什么选 ClickHouse 而非 MySQL/ES/HBase：
  - 写入：ClickHouse 批量写入 10 万行/秒，远优于 MySQL
  - 查询：列式存储 + 向量化执行，聚合查询性能是 MySQL 100 倍
  - 不适合：频繁单条更新（ClickHouse 是追加写入，不支持高频 UPDATE）
  - 实时指标只追加写入 → 完美匹配 ClickHouse 特性
- 表设计：
  ```sql
  CREATE TABLE realtime_metrics (
      dimension_key String,    -- 维度键（如"首页-全部用户"）
      metric_name   String,    -- 指标名（UV/GMV/订单量）
      metric_value  Float64,   -- 指标值
      window_start  DateTime,  -- 窗口开始时间
      window_end    DateTime   -- 窗口结束时间
  ) ENGINE = MergeTree()
  ORDER BY (dimension_key, window_start);
  ```
- Grafana 展示：Prometheus 查询 ClickHouse → 实时曲线图

### 五、量化结果
| 指标 | 优化前（T+1） | 优化后（实时） | 提升 |
|------|-------------|--------------|------|
| 数据延迟 | 24小时 | 15秒 | 5760x↓ |
| 运营决策响应 | 隔天调整 | 15秒内调整 | 实时化 |
| 查询性能 | Spark SQL 5min | ClickHouse 200ms | 1500x↓ |
| 存储 | HDFS 100TB | ClickHouse 30TB | 70%↓ |

### 六、踩坑经验
1. Flink Checkpoint 失败导致数据重复消费
   - 现象：Kafka offset 没有提交成功 → Flink 重启后从旧 offset 开始 → 数据重复
   - 解决：Exactly-Once 语义——Flink Kafka Sink 开启事务，Checkpoint 完成后才提交 offset

2. ClickHouse 写入太频繁导致性能下降
   - 现象：每 30 秒写入一批 → 每小时 120 次 Merge → MergeTask 堆积
   - 解决：改为攒批写入——本地 Buffer 表攒 5000 行或 60 秒后再写入分布式表

### 七、追问防线
| 防线层级 | 追问 | 回答要点 |
|---------|------|---------|
| L1 | 为什么不用 Spark Streaming？ | Spark 是微批处理（最小批间隔1秒），Flink 是真正的逐条处理，延迟更低 |
| L2 | UV去重为什么用HyperLogLog？ | 12KB内存估算百万UV，误差<0.81%，Set全量去重内存不可控 |
| L3 | Flink Exactly-Once怎么实现？ | Kafka Source offset + Flink Checkpoint + Kafka Sink 事务，三者绑定 |
| L4 | 迟到数据怎么处理？ | allowedLateness 允许60秒迟到，超时数据走SideOutput写入离线修正表 |
| L5 | 如果事件量翻100倍到5万条/秒？ | Kafka分区扩容 + Flink并行度提升 + ClickHouse分布式表 + 热指标Redis缓存 |

### 11.4 SaaS 多租户系统（数据隔离 + 权限 + 计费）

```markdown
## 项目：SaaS 企业管理平台

### 一、项目概览

  |------|--------|------|------|------|
  | 独立数据库 | ⭐⭐⭐⭐⭐ | ⭐⭐（3000个DB） | ⭐⭐ | 大客户 |

  | 共享DB+行级隔离 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 小客户(默认) |

- 方案：**默认共享DB+行级隔离，大客户升级到独立DB**
- 行级隔离实现——MyBatis-Plus TenantLineInnerInterceptor：
  ```java
  // 所有 SQL 自动追加 tenant_id 条件
  @Bean
  public MybatisPlusInterceptor mybatisPlusInterceptor() {
      MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
      interceptor.addInnerInterceptor(new TenantLineInnerInterceptor(
          new TenantLineHandler() {
              @Override
              public Expression getTenantId() {
                  // 从ThreadLocal获取当前租户ID
                  Long tenantId = TenantContext.getTenantId();
                  return new LongValue(tenantId);
              }
              @Override
              public String getTenantIdColumn() {
                  return "tenant_id"; // 所有表都有这个字段
              }
              @Override
              public boolean ignoreTable(String tableName) {
                  // 公共表（如系统配置表）不需要租户隔离
                  return IGNORE_TABLES.contains(tableName);
              }
          }
      ));
      return interceptor;
  }

  // TenantContext——ThreadLocal存租户ID
  public class TenantContext {
      private static final ThreadLocal<Long> TENANT_ID = new ThreadLocal<>();

      public static void setTenantId(Long tenantId) { TENANT_ID.set(tenantId); }
      public static Long getTenantId() { return TENANT_ID.get(); }
      public static void clear() { TENANT_ID.remove(); }
  }

  // Web Filter——从Token解析租户ID并放入ThreadLocal
  @Component
  public class TenantFilter implements Filter {
      @Override
      public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) {
          HttpServletRequest httpRequest = (HttpServletRequest) req;
          String token = httpRequest.getHeader("Authorization");
          Long tenantId = JwtUtil.getTenantId(token); // JWT中包含tenantId
          TenantContext.setTenantId(tenantId);
          try {
              chain.doFilter(req, res);
          } finally {
              TenantContext.clear(); // 必须清理，防线程池复用导致租户串号
          }
      }
  }
  ```
- 自动追加效果：
  - `SELECT * FROM order WHERE id = 1`
  - → 自动变成 `SELECT * FROM order WHERE id = 1 AND tenant_id = 100`
  - `INSERT INTO order (name, amount) VALUES ('test', 100)`
  - → 自动变成 `INSERT INTO order (name, amount, tenant_id) VALUES ('test', 100, 100)`
- 选型原因：比手动在每个 SQL 加 tenant_id 更安全——不可能遗漏

#### 方案三：大客户升级到独立DB
- 问题：5000人大客户在共享DB中数据量大，查询性能受其他租户影响
- 方案：ShardingSphere 动态数据源路由

  # ShardingSphere 配置——租户1000使用独立数据库
  shardingRule:

      ds_0: !!org.apache.shardingsphere.datasource   # 共享数据库

### 六、踩坑经验

### 三、技术挑战

2. 复杂约束：骑手位置/技能/工作时段/负载量/客户偏好/订单时效

### 四、技术方案

#### 方案一：调度引擎核心——就近匹配算法
- 思路：不是全局最优（NP-Hard问题），而是就近贪心匹配 + 实时迭代优化
- 算法：
  ```java
  // 第一步：为每个订单找最近的3个骑手候选
  // 用ES geo_distance查询（骑手位置实时上报到ES）
  public List<Courier> findNearbyCouriers(Order order) {
      SearchRequest request = new SearchRequest("courier_location");
      request.source().query(QueryBuilders.boolQuery()
          .must(QueryBuilders.geoDistanceQuery("location")
              .point(order.getLat(), order.getLng())
              .distance("3km"))          // 3公里范围内
          .must(QueryBuilders.termQuery("status", "IDLE")) // 空闲骑手
          .must(QueryBuilders.termQuery("skills", order.getSkill())) // 技能匹配
          .must(QueryBuilders.rangeQuery("currentLoad").lte(3)) // 负载≤3单
      );
      return esClient.search(request).getHits();
  }

  // 第二步：评分排序——综合距离+负载+时效权重
  public CourierScore score(Courier c, Order o) {
      double distanceScore = 1.0 / (c.getDistance() + 0.1); // 越近越好
      double loadScore = 1.0 / (c.getCurrentLoad() + 1);    // 越空闲越好
      double timeScore = o.isUrgent() ? 2.0 : 1.0;          // 急单加权
      return new CourierScore(c, 0.6 * distanceScore + 0.3 * loadScore + 0.1 * timeScore);
  }

  // 第三步：贪心分配——按订单优先级排序，逐个分配最优骑手
  // 急单优先分配，非急单可以稍后
  public void assignOrders(List<Order> pendingOrders) {
      pendingOrders.sort(Comparator.comparing(Order::isUrgent).reversed()
                               .thenComparing(Order::getCreateTime));
      for (Order order : pendingOrders) {
          List<Courier> candidates = findNearbyCouriers(order);
          if (candidates.isEmpty()) continue;
          Courier best = candidates.stream()
              .map(c -> score(c, order))
              .max(Comparator.comparingDouble(CourierScore::getScore))
              .map(CourierScore::getCourier)
              .orElse(null);
          if (best != null) {
              assign(order, best); // 分配
              best.setCurrentLoad(best.getCurrentLoad() + 1); // 更新负载
          }
      }
  }
  ```
- 调度触发：XXL-Job 每 30 秒执行一次 + RocketMQ 新订单事件触发即时调度

#### 方案二：配送状态机 + 实时追踪
- 状态定义：PICKED_UP → IN_TRANSIT → NEAR_DEST → DELIVERED / FAILED / RETURNED
- 状态上报：骑手APP每30秒上报GPS → 写入ES → 触发状态判断逻辑
  ```java
  // 状态判断——自动推进
  if (distance(courier.location, order.pickupLocation) < 100m && status == ASSIGNED) {
      status = PICKED_UP; // 到达取件点 → 自动变"已取件"
  }
  if (distance(courier.location, order.destLocation) < 500m && status == IN_TRANSIT) {
      status = NEAR_DEST; // 接近目的地 → 推送客户"即将到达"
  }
  ```
- 客户通知：状态变化 → RocketMQ → 通知服务 → 推送APP/短信/微信

#### 方案三：骑手位置实时索引
- 骑手APP 每30秒上报GPS → 写入 Elasticsearch geo_point 类型
- ES 支持 geo_distance 查询，3km 范围查询延迟 < 20ms
- 为什么不用 Redis GEO：Redis GEO 只支持简单范围查询，不支持多条件组合

### 四、技术方案

#### 方案一：OAuth2 + JWT SSO
- 认证流程：
  1. 用户访问业务系统A → 未登录 → 302重定向到认证中心
  2. 用户在认证中心登录 → 颁发 JWT + 写入 Redis Session
  3. 302回跳到系统A，带 authorization_code → 系统A用code换token
  4. 后续访问系统B → 认证中心检测已登录（Redis Session）→ 直接颁发code给系统B
- 实现核心：
  ```java
  // 认证中心——登录颁发Token
  @Service
  public class AuthService {
      public TokenResult login(String username, String password) {
          // 1. 校验账号密码
          User user = userMapper.selectByUsername(username);
          if (user == null || !passwordEncoder.matches(password, user.getPassword())) {
              throw new AuthException("账号或密码错误");
          }
          // 2. 生成 JWT
          String accessToken = JwtUtil.generateToken(user.getId(), user.getTenantId(),
              user.getRoleCodes(), 7200); // 2小时过期
          String refreshToken = JwtUtil.generateRefreshToken(user.getId(), 2592000); // 30天
          // 3. 存入 Redis（有状态——支持强制踢人/并发登录控制）
          redisTemplate.opsForValue().set(
              "token:" + accessToken, user.getId().toString(), 7200, TimeUnit.SECONDS);
          // 4. 返回Token
          return new TokenResult(accessToken, refreshToken);
      }

      // Token校验——双重验证
      public boolean validateToken(String token) {
          // JWT本身校验（签名+过期时间）——无状态
          if (!JwtUtil.isTokenValid(token)) return false;
          // Redis存在性校验——有状态（支持主动注销/踢人）
          return redisTemplate.hasKey("token:" + token);
      }

      // 主动踢人——删除Redis中的Token
      public void kickOut(String token) {
          redisTemplate.delete("token:" + token);
          // 踢人后JWT虽然未过期，但Redis已删除 → validateToken返回false
      }
  }
  ```
- 选型：JWT + Redis 双重验证，而非纯 JWT
  - 纯 JWT 无法踢人（Token 签发后无法撤销）
  - 纯 Redis 有状态每次都要查 Redis，性能略差
  - JWT + Redis：JWT 校验签名（快）→ Redis 校验存在性（支持踢人）

#### 方案二：RBAC + 数据权限
- 权限模型：用户 → 角色 → 权限（菜单权限 + API权限 + 数据权限）

  -- 五表RBAC模型
  user → user_role → role → role_permission → permission

  -- permission 细粒度
  permission_type:
    MENU   -- 菜单可见性（如"订单管理"菜单是否可见）
    API    -- API访问权限（如"order:create"是否可调用）
    DATA   -- 数据范围（如"只看本部门订单"）
  ```
- 数据权限实现：
  ```java
  // 数据权限注解
  @Target(ElementType.METHOD)
  @Retention(RetentionPolicy.RUNTIME)
  public @interface DataScope {
      String table();      // 表名
      String deptColumn(); // 部门字段名
      String userColumn(); // 创建人字段名
  }

  // 数据权限拦截器——自动追加SQL条件
  @Aspect
  @Component
  public class DataScopeAspect {
      @Before("@annotation(dataScope)")
      public void doBefore(JoinPoint point, DataScope dataScope) {
          User user = SecurityContext.getCurrentUser();
          String scopeType = user.getDataScopeType();

          String condition = switch (scopeType) {
              case "ALL" -> "";  // 全部数据
              case "DEPT" -> dataScope.deptColumn() + " = " + user.getDeptId(); // 本部门
              case "DEPT_AND_SUB" -> dataScope.deptColumn() + " IN (子部门ID列表)";
              case "SELF" -> dataScope.userColumn() + " = " + user.getId(); // 仅本人
              default -> dataScope.userColumn() + " = " + user.getId();
          };

          // 通过ThreadLocal传递给MyBatis拦截器追加SQL条件
          DataScopeContext.setCondition(condition);
      }
  }
  ```
- 效果：`SELECT * FROM order` → 自动追加 `WHERE dept_id = 5`（本部门数据权限）

#### 方案三：并发登录控制

- 方案：T+1对账

  // 每日凌晨：用离线数据校验实时数据
  @Scheduled(cron = "0 0 3 * * ?")
  public void reconcileMetrics() {
      // 离线：Spark SQL 从Hive查T日GMV（精确值）
      BigDecimal offlineGMV = sparkSQLService.query("SELECT SUM(amount) FROM hive.order WHERE dt = '${yesterday}'");
      // 实时：ClickHouse 查T日GMV（Flink计算值）
      BigDecimal realtimeGMV = clickHouseService.query("SELECT SUM(metric_value) FROM realtime_metrics WHERE metric_name='GMV' AND window_start >= '${yesterdayStart}'");

      // 偏差率
      BigDecimal diffRate = (realtimeGMV.subtract(offlineGMV)).divide(offlineGMV, 4, RoundingMode.HALF_UP);
      if (diffRate.abs().compareTo(new BigDecimal("0.01")) > 0) {
          // 偏差>1% → 告警 + 用离线值覆盖实时值
          alertService.send("实时GMV偏差" + diffRate + "%，已用离线值修正");
          clickHouseService.updateMetric("GMV", yesterday, offlineGMV);
      }
  }
  ```

- 痛点：各业务团队重复实现限流/缓存/日志/幂等/灰度等公共能力
  - 限流：A团队用Guava RateLimiter，B团队用Sentinel，C团队用Redis Lua
  - 缓存：各团队缓存策略不一致，缓存穿透/击穿问题反复出现
  - 幂等：各团队幂等方案各异，有Token机制、有去重表、有状态机
- 目标：统一公共SDK，一个注解搞定限流/缓存/幂等/灰度

### 三、技术挑战
1. 低侵入：业务团队加注解即可使用，不改业务代码
2. 高扩展：不同团队有不同需求，必须支持自定义策略
3. 灰度发布：SDK本身也要灰度发布（不能影响所有业务同时）
4. 可观测：SDK的行为要可观测（限流次数/缓存命中率/幂等拦截率）

### 四、技术方案

- AOP拦截器实现：
  ```java
  @Aspect
  @Component
  public class RateLimitAspect {
      @Autowired
      private Map<String, RateLimitStrategy> strategyMap; // SPI注入所有策略实现

      @Around("@annotation(rateLimit)")
      public Object around(ProceedingJoinPoint pjp, RateLimit rateLimit) throws Throwable {
          // 1. 解析key（支持SpEL表达式）
          String resolvedKey = SpELParser.parse(rateLimit.key(), pjp);

          // 2. 获取策略实现（SPI扩展）
          RateLimitStrategy strategy = strategyMap.get(rateLimit.strategy().name());

          // 3. 执行限流判断
          if (!strategy.tryAcquire(resolvedKey, rateLimit.rate())) {
              // 限流 → 记录指标 + 返回限流响应
              metricsCollector.recordRateLimit(resolvedKey);
              throw new RateLimitException("请求被限流");
          }

          // 4. 通过 → 执行业务方法
          return pjp.proceed();
      }
  }
  ```

- SPI扩展——不同团队可以自定义策略：
  ```java
  // 限流策略接口
  public interface RateLimitStrategy {
      boolean tryAcquire(String key, int rate);
  }

  // 内置实现——单机限流（Caffeine）
  @Component("LOCAL")
  public class LocalRateLimitStrategy implements RateLimitStrategy {
      private final Cache<String, RateLimiter> cache = Caffeine.newBuilder()
          .maximumSize(10000).build();
      @Override
      public boolean tryAcquire(String key, int rate) {
          return cache.get(key, k -> RateLimiter.create(rate)).tryAcquire();
      }
  }

  // 内置实现——分布式限流（Redis Lua）
  @Component("DISTRIBUTED")
  public class DistributedRateLimitStrategy implements RateLimitStrategy {
      @Override
      public boolean tryAcquire(String key, int rate) {
          // Redis Lua滑动窗口限流
          return redisRateLimiter.tryAcquire(key, rate);
      }
  }

  // 业务团队自定义实现——只要加@Component("CUSTOM_NAME")即可自动注册
  ```

public Product getProduct(Long id) {

    if (product != null) return product;

    // L2: Redis分布式缓存（<5ms，命中率90%）

    }
    return product;
}

// 双重防护
public Product getProduct(Long id) {
    // 第一层：布隆过滤器（判断id是否可能存在）
    if (!bloomFilter.mightContain(id)) {
        return null; // 肯定不存在，直接返回（挡掉99%无效请求）
    }

    // 第二层：Redis缓存（含空值缓存）
    Product product = redisCache.get("product:" + id);
    if (product != null) {
        if (product.isNullMarker()) return null; // 空值标记→说明DB不存在
        return product;
    }

    // 第三层：查DB
    product = productMapper.selectById(id);
    if (product != null) {
        redisCache.set("product:" + id, product, 300);
    } else {
        // 空值缓存——防止同一个id反复穿透
        redisCache.set("product:" + id, NULL_MARKER, 60); // 空值短TTL
        bloomFilter.put(id); // 虽然不存在也加入布隆过滤器（下次直接挡掉）
    }
    return product;
}

// 面试追问：

// 热Key发现——Redis HotKeys监控 + 自动本地缓存
// 1. 每10秒用redis-cli --hotkeys扫描当前热点key
// 2. 发现热Key后自动在所有应用节点加入Caffeine本地缓存
// 3. 热Key变更时Redis Pub/Sub通知所有节点更新

@Component
public class HotKeyManager {
    @Scheduled(fixedRate = 10000)
    public void detectHotKeys() {
        // 执行Redis HOTKEYS命令（需开启maxmemory-policy为allkeys-lfu）
        Set<String> hotKeys = redisTemplate.execute((RedisCallback<Set<String>>) conn -> {
            return conn.hotKeys(10); // 获取TOP 10热key
        });

        for (String key : hotKeys) {
            // 自动加入本地缓存
            Object value = redisTemplate.opsForValue().get(key);
            if (value != null) {
                caffeineCache.put(key, value);
                caffeineCache.expire(key, 30, TimeUnit.SECONDS); // 热Key短TTL防不一致
            }
        }
    }

    // Redis键变更时Pub/Sub通知
    @RedisListener(topic = "cache:update")
    public void onCacheUpdate(String key) {
        caffeineCache.invalidate(key); // 收到通知立即清本地缓存
    }
}

// 面试追问：
// Q: 热Key有什么危害？ → 单Key高并发访问导致Redis单节点CPU飙升甚至宕机
// Q: 为什么不只靠本地缓存？ → 本地缓存一致性难保证，只能做热Key临时增强

#### 亮点 7：Redis 分布式锁实战（含可重入）

```java
// Redis分布式锁——Lua脚本实现（含可重入+自动过期+安全释放）
@Component
public class RedisDistributedLock {
    // 加锁Lua脚本：SETNX + 过期时间 + 可重入计数
    private static final String LOCK_SCRIPT =
        "if redis.call('exists', KEYS[1]) == 0 then " +
        "  redis.call('hset', KEYS[1], ARGV[1], 1) " +  // 不存在→加锁，hash存owner+计数
        "  redis.call('pexpire', KEYS[1], ARGV[2]) " +   // 设过期时间
        "  return 1 " +
        "end " +
        "if redis.call('hexists', KEYS[1], ARGV[1]) == 1 then " + // 存在且owner是自己→可重入
        "  redis.call('hincrby', KEYS[1], ARGV[1], 1) " +         // 重入计数+1
        "  redis.call('pexpire', KEYS[1], ARGV[2]) " +             // 重设过期时间
        "  return 1 " +
        "end " +
        "return 0"; // 被别人持有→加锁失败

    // 释放Lua脚本：计数-1，归零时删key
    private static final String UNLOCK_SCRIPT =
        "if redis.call('hexists', KEYS[1], ARGV[1]) == 0 then " +
        "  return nil " +  // 不是自己的锁→不能释放
        "end " +
        "local counter = redis.call('hincrby', KEYS[1], ARGV[1], -1) " + // 重入计数-1
        "if counter > 0 then " +
        "  redis.call('pexpire', KEYS[1], ARGV[2]) " + // 还没归零→重设过期
        "  return 0 " +
        "else " +
        "  redis.call('del', KEYS[1]) " +  // 归零→删除锁
        "  return 1 " +
        "end";

    public boolean tryLock(String lockKey, String ownerId, long expireMs) {
        return redisTemplate.execute(new DefaultRedisScript<>(LOCK_SCRIPT, Long.class),
            List.of(lockKey), ownerId, String.valueOf(expireMs)) == 1;
    }

    public boolean unlock(String lockKey, String ownerId, long expireMs) {
        return redisTemplate.execute(new DefaultRedisScript<>(UNLOCK_SCRIPT, Long.class),
            List.of(lockKey), ownerId, String.valueOf(expireMs)) == 1;
    }
}

// 使用示例
String lockKey = "order:create:" + orderId;
String ownerId = Thread.currentThread().getId() + ":" + UUID.randomUUID();

    try {
        createOrder(orderDTO);
    } finally {
        lock.unlock(lockKey, ownerId, 30000);
    }
}

// 靼试追问：
// Q: 为什么用Lua脚本？ → 保证加锁+设过期原子性，避免SETNX成功但未设过期（死锁）
// Q: 可重入怎么实现？ → Hash结构存{owner: count}，同owner加锁count+1，释放count-1
// Q: 锁过期了业务还没做完怎么办？ → 看门狗续期（后台线程定时检测+续期）或Redisson框架

```java
// 问题：每次Full GC后Old Gen不下降 → 说明有对象泄漏到Old Gen无法回收
// 排查流程：
// Step 1: jstat观察GC → 发现Full GC后Old Gen从2G不下降
// Step 2: jmap -histo:live pid → 发现某类ThreadLocal$ThreadLocalMap$Entry对象特别多
// Step 3: jmap -dump:format=b,file=heap.hprof pid → MAT分析
// Step 4: MAT → Leak Suspects → 发现ThreadLocalMap中Entry的value是UserSession对象
//          → 每个线程的ThreadLocalMap存了一个UserSession（50KB）
//          → 200个线程池线程 × 50KB = 10MB 似乎不大
//          → 但ThreadLocal用后没有remove() → 线程池线程复用 → UserSession不断累积
//          → 某些线程的ThreadLocalMap存了1000+个Entry → 总泄漏200MB+

// 根因代码：
public class UserContextHolder {
    private static ThreadLocal<UserSession> THREAD_LOCAL = new ThreadLocal<>();

    public static void set(UserSession session) {
        THREAD_LOCAL.set(session); // 设置但没remove
    }
}

// 在Filter中设置但没清理：
@Component
public class AuthFilter implements Filter {
    public void doFilter(...) {
        UserContextHolder.set(session); // 设置
        chain.doFilter(req, res);
        // ❌ 缺少 UserContextHolder.remove() → 泄漏！
    }
}

// 修复：
@Component
public class AuthFilter implements Filter {
    public void doFilter(...) {
        try {
            UserContextHolder.set(session);
            chain.doFilter(req, res);
        } finally {
            UserContextHolder.remove(); // ✅ 必须remove
        }
    }
}

// 靼试追问：
// Q: ThreadLocal为什么泄漏？ → 线程池线程复用不死，ThreadLocalMap的Entry弱引用key被GC但value强引用仍存在
// Q: 为什么Entry的key是弱引用？ → ThreadLocal对象被回收后key自动null，但value仍被Entry强引用
// Q: 怎么防泄漏？ → finally中remove()是唯一可靠方案，线程池装饰器传递也要及时清理

// 0 | 41位时间戳 | 10位机器ID | 12位序列号
// 优点：趋势递增、不依赖DB、性能高（单机100万/秒）

    private final long epoch = 1704067200000L; // 2024-01-01起始时间戳

    private final long workerIdBits = 5L;  // 5位数据中心ID
    private final long datacenterIdBits = 5L; // 5位机器ID
    private final long sequenceBits = 12L;  // 12位序列号

    private final long maxWorkerId = ~(-1L << workerIdBits); // 31
    private final long maxDatacenterId = ~(-1L << datacenterIdBits); // 31
    private final long sequenceMask = ~(-1L << sequenceBits); // 4095

    private final long workerIdShift = sequenceBits; // 12
    private final long datacenterIdShift = sequenceBits + workerIdBits; // 17
    private final long timestampShift = sequenceBits + workerIdBits + datacenterIdBits; // 22

    private long workerId;
    private long datacenterId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;

    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis() - epoch;

        // 时钟回拨检测
        if (timestamp < lastTimestamp) {
            long offset = lastTimestamp - timestamp;
            if (offset <= 5) {
                // 小幅回拨（<5ms）→ 等待时钟追上
                try { Thread.sleep(offset * 2); } catch (InterruptedException e) {}
                timestamp = System.currentTimeMillis() - epoch;
            } else {
                // 大幅回拨 → 报错（不能用未来ID）
                throw new RuntimeException("时钟回拨" + offset + "ms，拒绝生成ID");
            }
        }

        if (timestamp == lastTimestamp) {
            // 同一毫秒内 → 序列号递增
            sequence = (sequence + 1) & sequenceMask;
            if (sequence == 0) {
                // 序列号溢出 → 等下一毫秒
                timestamp = tilNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0L; // 新毫秒 → 序列号从0开始
        }

        lastTimestamp = timestamp;
        return ((timestamp << timestampShift)
            | (datacenterId << datacenterIdShift)
            | (workerId << workerIdShift)
            | sequence);
    }

    private long tilNextMillis(long lastTimestamp) {
        long timestamp = System.currentTimeMillis() - epoch;
        while (timestamp <= lastTimestamp) {
            timestamp = System.currentTimeMillis() - epoch;
        }
        return timestamp;
    }
}

// 靼试追问：
// Q: 时钟回拨怎么办？ → 小幅(<5ms)等时钟追上，大幅报错拒绝生成
// Q: 机器ID怎么分配？ → ZooKeeper顺序节点/数据库表/Nacos配置
// Q: ID能保证全局唯一吗？ → 同一毫秒同一机器由sequence保证，跨毫秒由时间戳保证，跨机器由workerId保证
```

#### 亮点 22：双写迁移——不停服数据迁移

```java
// 双写迁移五阶段——从旧系统MySQL迁移到新系统MySQL+分库分表

// Phase 1: 新系统开发，旧系统正常运行
// Phase 2: 旧系统写入 → Canal → 同步到新系统（新系统只读）
//   → Canal解析旧MySQL binlog → 写入新MySQL
//   → 新系统数据从旧系统实时同步，但不服务流量

// Phase 3: 灰度切读流量到新系统
//   → Nacos配置灰度比例5% → 10% → 30% → 50% → 100%
//   → 新系统只读，写操作仍走旧系统 → Canal同步到新系统

// Phase 4: 切写流量到新系统
//   → 新系统开始写入 → Canal反向同步到旧系统（双写）
//   → 同时旧系统也写 → Canal正向同步到新系统
//   → 双写期间两套数据都实时同步

// Phase 5: 验证数据一致 → 关闭旧系统
//   → 对账任务比对两套数据 → 确认100%一致
//   → 停止Canal同步 → 旧系统下线

// 对账代码：
@Scheduled(cron = "0 0 4 * * ?")
public void reconcile() {
    // 旧系统数据
    List<Order> oldOrders = oldOrderMapper.queryByDate(yesterday);
    // 新系统数据
    List<Order> newOrders = newOrderMapper.queryByDate(yesterday);

    // 比对——按orderId
    Map<Long, Order> oldMap = oldOrders.stream().collect(Collectors.toMap(Order::getId, o -> o));
    Map<Long, Order> newMap = newOrders.stream().collect(Collectors.toMap(Order::getId, o -> o));

    // 差异检测
    oldMap.keySet().stream()
        .filter(k -> !newMap.containsKey(k) || !oldMap.get(k).equals(newMap.get(k)))
        .forEach(k -> log.error("数据不一致: orderId={}", k));

    // 差异率 < 0.01% → 可以切流
    double diffRate = diffCount / (double) totalCount;
    if (diffRate < 0.0001) {
        log.info("数据一致率99.99%，可以切流");
    }
}

#### 亮点 23：分布式限流 Redis + Lua 实战

```lua
-- sliding_window_limiter.lua —— 滑动窗口限流
local key = KEYS[1]           -- 限流key
local limit = tonumber(ARGV[1]) -- 限流阈值
local window = tonumber(ARGV[2]) -- 窗口时间（毫秒）
local now = tonumber(ARGV[3])   -- 当前时间戳

-- 1. 移除窗口外的旧记录
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)

-- 2. 统计当前窗口内的请求数
local count = redis.call('ZCARD', key)

-- 3. 判断是否超限
if count < limit then
    -- 未超限 → 记录本次请求 + 设置key过期时间
    redis.call('ZADD', key, now, now .. '-' .. math.random(1000000)) -- member用时间戳+随机数防重复
    redis.call('PEXPIRE', key, window)
    return 1  -- 允许
else
    return 0  -- 限流
end
```
