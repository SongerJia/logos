## 推荐学习顺序

```
01 架构概述（先建立全局认知）
    ↓
02 消息模型（理解基本概念：Topic/Queue/Tag/Message）
    ↓
04 消费者核心 ←→ 03 生产者核心（可并行）
    （这两个是日常开发最常用的，先搞透）
    ↓
05 存储机制（最难也最重要！建议花最多时间）
    ↓
06 高可用（理解集群怎么搭）
    ↓
07 事务消息（招牌功能，深入原理）
    ↓
08 进阶调优（有了项目经验后再深入）
```

> **05 存储机制是 RocketMQ 的"任督二脉"**——搞懂了 CommitLog + ConsumeQueue 两层存储设计，你就能回答80%的深挖问题。

## 🔗 跨模块关联

```
RocketMQ
├── → Spring Cloud Alibaba：
│   └── @RocketMQMessageListener 自动注入 / Nacos配置集成
├── → Seata 分布式事务：
│   ├── RMQ事务消息 vs Seata AT模式：什么时候用哪个？
│   └── 事务消息 = 最终一致性 / Seata AT = 强一致性
├── → Redis：
│   └── 幂等去重（Redis Set / SetNX）← 消息不丢不重的最后一道防线
├── → MySQL：
│   └── 事务消息的"本地事务"通常就是MySQL操作
│   └── 消息落库方案（Producer发消息前先入库，补偿任务扫描）
├── → Java 并发：
│   └── Rebalance时的并发安全 / ThreadPoolExecutor消费线程池
│   └── MappedFile的内存映射（MappedByteBuffer = NIO零拷贝）
├── → JVM：
│   └── Broker堆外内存管理（DirectByteBuffer for MappedFile）
│   └── GC停顿对消息发送延迟的影响（尤其是大消息场景）
├── → Kafka（待学）：
│   ├── CommitLog顺序写 vs Kafka分区日志顺序写 → 思路一样
│   ├── ConsumeQueue索引 vs Kafka稀疏索引 → 实现不同目的相同
│   └── 事务消息 vs Kafka Exactly-Once语义
└── → SkyWalking（待学）：
    └── MQ调用链路追踪（Producer→Broker→Consumer全链路可视化）
```

## 💡 写笔记提醒

- **CommitLog 混合存储设计**是 RocketMQ 最经典的架构决策，一定要写出**为什么不用 Kafka 的分区日志方案**——答案在于 CommitLog 保证了极致的顺序写性能，而 ConsumeQueue 解耦了消费效率
- **Rebalance + 消息堆积 + ACK重试** 这三个是连环坑，面试最爱出场景题："消费者突然变慢了会发生什么？" 能把完整的连锁反应讲清楚就赢了
- **事务消息的两阶段 + 回查机制**要画状态机图，能徒手画出来面试直接加分
- **消息幂等性**虽然不属于 RocketMQ 本身，但是面试官一定会追问"你怎么保证不重复消费"，这个必须准备完整方案
- **不要忽视 Spring Boot 整合**——这是你日常写代码的方式，@RocketMQMessageListener 各参数含义要烂熟
