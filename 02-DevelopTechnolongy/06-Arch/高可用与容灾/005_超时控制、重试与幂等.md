|**4.5.1**|**超时 Timeout 设计原则**|每一层都应有独立的超时设置；**调用链超时递减**原则(总超时 < 各子调用超时之和)；区分连接超时(Connect)和读取超时(Read)|Dubbo RPC: 默认1000ms / Feign: 默认10s / MQ消费: 默认15s / DB连接: 3s / Redis: 2s|"RPC超时应该设多少合适？有没有通用的经验值？"|**Gateway路由超时30s** → Dubbo内部调用**5s** → DB查询**3s** → Redis**500ms** → MQ发送**2s**|
|**4.5.2**|**重试 Retry 策略**|瞬时故障才值得重试(网络抖动/连接断开)；固定次数 + 指数退避(Exponential Backoff) + Jitter(随机抖动避免惊群)；重试次数上限(通常3次)|重试策略：立即重试 / 固定间隔 / 线性退避 / 指数退避(推荐) + 抖动(±20%)|"什么是重试风暴？怎么用Jitter避免？"|Scheduler任务失败重试：指数退避(1s → 2s → 4s → 8s) + 最大3次|
|**4.5.3**|**幂等性 Idempotency 设计**|幂等的本质：**f(f(x)) = f(x)**；同一请求执行一次和多次结果相同；三层防御：(1)唯一索引 (2)分布式锁 (3)状态机防重复|幂等Key设计：请求方生成唯一Token / 服务端基于业务字段组合生成|"POST请求天然不幂等，怎么让它变成幂等的？"|所有写接口幂等：TaskId唯一索引 + Redis Token(过期时间=接口超时的2倍)|
|**4.5.4**|**Dubbo 容错模式**|8种容错模式：Failover(失败自动切换,默认) / Failfast(快速失败) / Failsafe(安全失败,异常吞掉) / Failback(失败自动恢复/异步通知) / Forking(并行调用,只要一个成功就行) / Broadcast(广播调用,逐个通知)|`cluster="failover"` + `retries="2"` + `timeout="3000"`|"Failover和Forking分别适合什么场景？"|**workflow→auth**: Failover(重试2次) / **Scheduler→workflow**: Failfast(调度不重复) / **message**: Failsafe(通知失败不阻塞)|
|**4.5.5**|**线程池隔离 (Bulkhead Pattern)**|不同类型的请求使用不同线程池隔离；一种请求耗尽线程不会影响其他请求；Hystrix的核心思想之一|核心线程数 / 最大线程数 / 队列容量 / 拒绝策略 四要素|"线程池隔离和信号量隔离的区别？"|Gateway用Netty EventLoop(Reactor模型) / Tomcat独立线程池处理HTTP / Dubbo自有线程池|
|**4.5.6**|**优雅降级与Fallback**|当主路径不可用时自动切换到备用方案；Fallback可以是：缓存值 / 默认值 / 静态结果 / 异步补偿|`@SentinelResource(fallback = "queryProcessListFallback")` 返回空列表+提示|"降级返回的数据会不会误导用户？怎么标注这是降级数据？"|流程列表查询DB慢时返回ES缓存(可能延迟5分钟内的新流程看不到)|
