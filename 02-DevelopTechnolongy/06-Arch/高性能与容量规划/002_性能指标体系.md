|---|---|---|---|---|---|
|**5.2.1**|**吞吐量 Throughput (QPS/TPS)**|单位时间内系统处理的请求数/事务数；QPS(Query Per Second)/TPS(Transaction Per Second)；关注系统**处理能力**的上限|`QPS = 并发数 / 平均响应时间` (Little's Law近似) 或直接计数器统计|内部API: 500-2000 QPS；对外API: 100-500 QPS|"QPS上不去可能是什么原因？怎么定位？"|
|**5.2.2**|**响应时间 Latency (RT)**|从客户端发请求到收到完整响应的时间；必须用**分位数**(Percentile)而非平均值(均值掩盖长尾问题)|P50(中位数) / P90 / P99 / P999 / Max；**P99是最重要的指标**|P99 < 200ms(Good) / P99 < 500ms(Acceptable) / P99 > 1s(Need Optimize)|"为什么不能用平均响应时间？平均值有什么问题？"|
|**5.2.3**|**Little's Law 排队论基础**|`L = λW`(系统中平均请求数 = 到达率 × 平均停留时间)；推导出：`QPS = 并发数 / 平均RT`|三变量知二求一；用于估算需要的线程数/连接数/并发容量|"用Little's Law估算一下你们的系统需要多少连接池大小？"|设定线程池大小：CPU密集型=N+1 / IO密集型=2N|

> **💡 面试金句 — 为什么 P99 比 Average 重要**
> 
> ```
> 场景: 某API 100次调用耗时分布：
>   95次: ~20ms (很快)
>   4次: ~80ms (稍慢)
>   1次: 5000ms (极慢! 可能是GC停顿或DB慢查询)
> 
> Average = (95×20 + 4×80 + 1×5000) / 100 = 69.2ms ← 看起来还行!
> P99 = 第99次排序 = 80ms                    ← 还可以
> P999 = 最大 = 5000ms                       ← 问题在这！
> 
> 那1%的慢请求虽然少，但影响的是最关键的客户体验。
> 大厂面试必问："你们系统的P99是多少？" 而不是"平均RT是多少"
> ```
