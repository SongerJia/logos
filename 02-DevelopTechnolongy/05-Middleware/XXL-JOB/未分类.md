```

    ↓
02 整体架构（建立全局认知）
    ↓ （01~02 是地基）
04 Executor 核心 ←→ 05 路由策略（最核心的两个模块）
    （Executor 怎么工作 + 任务怎么分发到哪台机器）
    ↓

    ↓

    ↓

```

> **路由策略 + 分片广播**是 XXL-JOB 区别于其他调度框架的最大亮点。特别是**分片广播**，面试官最爱考——因为它直接对应生产环境的大批量数据处理场景。

## 🔗 跨模块关联

```
XXL-JOB
├── → RocketMQ/Kafka/RabbitMQ：
│   ├── MQ 异步解耦 vs JOB 定时触发：什么时候用哪个？
│   └── 典型组合：JOB 定时扫库 → 发现待处理数据 → 发送 MQ 异步处理
├── → Java 并发：
│   ├── Executor 线程池 = ThreadPoolExecutor 的实战应用
│   ├── 阻塞处理策略 = 线程池拒绝策略的业务化封装
│   └── 分布式锁 = xxl_job_lock 表的 SELECT FOR UPDATE 实现
├── → MySQL：
│   ├── 所有元数据和日志都存在 MySQL 中
│   ├── xxl_job_lock 表 = 基于 DB 行锁的分布式锁（替代 Redisson/ZK）
│   └── 任务执行结果日志 = 可靠性依赖 MySQL 不丢
├── → Spring Cloud：
│   ├── Executor 注册到 Admin 类似于 Service 注册到 Nacos（但用的是DB不是注册中心）
│   └── Admin 多实例 + LB = 微服务的服务发现思路
├── → Elastic-Job / PowerJob（选型对比中提过）：
│   └── XXL-JOB(DB协调) vs EJ(ZK协调) vs PJ(MapReduce)
└── → 架构方向(待学)：
    └── 高可用架构：Admin 无状态多实例 + DB 主从 = 经典无状态服务高可用范式
```

## 💡 写笔记提醒

- **两角色架构（Admin + Executor）**是 XXL-JOB 的灵魂设计——一定要画出完整的部署拓扑图，包括 DB、Admin集群、多个业务服务内嵌 Executor 的关系
- **分片广播**要准备至少一个完整的实战案例（分库分表数据清洗是最经典的），能讲清楚 shardIndex/shardTotal 怎么用、数据怎么切分
- **阻塞处理策略**的三种模式是面试高频——能说出"我们项目用串行因为..."或"我们用丢弃后续因为..."这种有理有据的回答
- **XXL-JOB vs Elastic-Job vs PowerJob** 对比表中，关键差异在于**协调机制**（DB vs ZK vs MapReduce）和**功能侧重**（轻量易用 vs 强一致协调 vs 大规模并行计算）
- **Admin 挂了怎么办**是经典面试题——答案要点：① 已触发任务不受影响 ② 新调度暂停 ③ 恢复后自动补触发过期任务 ④ 所以 Admin 不是单点瓶颈
