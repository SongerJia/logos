## 一、内存区域（必问基础）

### **Q1** JVM 运行时数据区域有哪些？每个区域存什么，线程私有还是共享，会抛什么异常？
?
1. JVM 运行时数据区域分为五个部分。
2. 程序计数器，线程私有，存的是当前线程正在执行的字节码指令地址。它是唯一不会抛出 OOM 的区域。
3. Java 虚拟机栈，线程私有，存的是栈帧，每个方法调用压入一个栈帧，栈帧里有局部变量表、操作数栈、动态链接和方法出口。栈深度超限抛 StackOverflowError，栈大小无法扩展抛 OOM。
4. 本地方法栈，线程私有，跟虚拟机栈类似，不过它是给 Native 方法用的。
5. 堆，线程共享，是最大的一块内存区域，存放对象实例和数组。堆满时抛 OOM: Java heap space。堆是 GC 管理的主要区域。
6. 方法区（JDK8 之后是元空间），线程共享，存放类的元数据信息——类的结构、字段、方法、常量池、静态变量。元空间用的是本地内存，满了会抛 OOM: Metaspace。

### **Q2** 方法区 / 元空间（Metaspace）的区别？JDK8 为什么用元空间替代永久代？元空间有大小限制吗？
?
1. 永久代和元空间的功能是一样的，存储的都是类的元数据信息。核心区别有两点。第一，位置不同。永久代在 JVM 堆内存中，是堆的一部分。元空间在本地内存中，不在堆里。第二，容量限制不同。永久代因为是堆的一部分，受到 -XX:MaxPermSize 的限制，设小了容易 OOM，设大了浪费堆空间。元空间默认不限制上限，可以用完整个本地内存，当然也可以通过 -XX:MaxMetaspaceSize 限制。
2. JDK8 换成元空间的主要原因就是为了消除永久代的 OOM 问题。永久代的大小是固定的，如果在运行期间动态加载了大量类——比如大量使用动态代理、大量 JSP 或者 OSGi——永久代很容易溢出。元空间用本地内存，动态类加载的场景下内存充裕得多，不容易因为方法区溢出而崩溃。另外也简化了 JVM 的内存管理，因为不需要在堆里单独划一块给永久代了。
3. 元空间理论上没有大小限制，受限于本地内存。但可以通过 -XX:MaxMetaspaceSize 设置上限，防止类加载泄漏无限占用本地内存导致机器挂掉。所以生产环境建议设置一个合理的上限。

### **Q3** 字符串常量池在 JDK6、JDK7、JDK8 分别放在哪个区域？为什么要迁移？
?
1. JDK6 的时候，字符串常量池放在永久代中。这带来一个问题：永久代的空间通常不大，而且很少被 GC 回收，如果程序大量使用字符串，比如不断调用 intern 方法，很容易导致永久代 OOM。
2. JDK7 把字符串常量池从永久代移到了堆中。这样常量池里的字符串对象跟普通对象一样受 GC 管理，堆 GC 能清理不再被引用的字符串，不会再出现字符串导致永久代溢出的问题。同时这也为 JDK8 彻底移除永久代做了铺垫，因为常量池如果还放在永久代里，JDK8 去永久代就没法去了。
3. JDK8 元空间替代永久代后，字符串常量池依然在堆中，这一点和 JDK7 完全一致，没有变化。所以本质上是 JDK7 做了一次关键迁移，JDK8 保持了这种设计。

### **Q4** 直接内存（Direct Memory）是什么？属于 JVM 运行时数据区吗？NIO 的 `ByteBuffer.allocateDirect()` 和 Heap Buffer 的区别？怎么回收？
?
1. 直接内存不是 JVM 运行时数据区的一部分，它是堆外的本地内存，不属于 JVM 的五个运行时数据区域。它是操作系统分配给 Java 进程的。
2. allocateDirect 分配的直接内存和 Heap Buffer 的区别在于，直接内存在堆外分配，地址固定，不受 GC 移动对象的影响。底层进行 IO 操作时，可以直接把这块内存的地址传给操作系统的 IO 函数，省掉了从堆内拷贝到堆外缓冲区的过程。Heap Buffer 在堆内，GC 可能移动它，所以 IO 操作前需要先拷贝到一个临时的直接缓冲区，多了一次拷贝。
3. 直接内存的回收不走正常的 GC 路径。每个 DirectByteBuffer 对象里都有一个 Cleaner，Cleaner 继承了虚引用。当 DirectByteBuffer 对象被 GC 回收时，Cleaner 会被放入引用队列，由对应的守护线程调用 Cleaner 的 clean 方法，最终调用 unsafe.freeMemory 释放对应的直接内存。但这个过程依赖 DirectByteBuffer 对象被 GC，如果对象本身很小一直留在老年代没有 GC，直接内存就迟迟不被释放。所以业务上使用直接内存时要特别注意 -XX:MaxDirectMemorySize 的设置和及时释放。

### **Q5** 栈溢出（StackOverflowError）和堆溢出（OutOfMemoryError: Java heap space）分别什么场景触发？`-Xss` 参数设置过小和递归过深有什么区别？
?
1. StackOverflowError 是栈空间用尽时抛出。最典型的场景是递归没有正确终止条件，无限递归导致栈帧不断压入最终撑爆栈空间。线程的栈深度超过了 JVM 允许的最大深度就会抛这个异常。
2. OutOfMemoryError: Java heap space 是堆空间不足时抛出，对象不断被创建且都活着，GC 无法回收出足够空间，最终堆满了。
3. 这两者是不同维度的溢出：一个是方法调用层次太深，另一个是对象太多。
4. -Xss 设置过小和递归过深虽然都抛 StackOverflowError，但原因不同。递归过深是逻辑问题——递归没有终止或者深度确实需要那么深，如果逻辑正确但深度确实大，应该优化算法或者增大 -Xss。-Xss 设置过小则意味着即使方法调用层次不深，但因为每个线程分配的栈空间太小，正常的调用链都可能溢出。比如 -Xss 设成了 128k 甚至更小，几个方法调用加一些局部变量就可能撑爆栈。

## 二、对象创建 & 内存布局

### **Q6** 一个 Java 对象从 `new` 到创建完成经历了哪些步骤？分配内存时"指针碰撞"和"空闲列表"分别对应什么 GC 算法？
?
1. new 一个对象的完整步骤是这样的。第一步，检查这个类是否已经被加载、解析和初始化过，如果没有就先走类加载流程。第二步，分配内存，JVM 需要在堆中找一块足够大的空间给这个对象。第三步，初始化零值，把分配到的内存全部清零，确保对象的实例字段在不赋值的情况下有默认值——int 为 0、boolean 为 false、引用为 null。第四步，设置对象头，包括 Mark Word、Klass Pointer 等元信息。第五步，执行构造方法，即字节码中的 init 方法，给字段赋程序员指定的值。到此对象创建完成。
2. 指针碰撞和空闲列表是两种内存分配方式。指针碰撞的前提是堆内存是规整的——所有用过的和空闲的内存各在一边，中间有一个指针。分配内存时只需要把指针向空闲一侧移动等于对象大小的距离。这种分配方式的前提是堆内存规整，对应的 GC 算法是标记-整理和复制算法，因为这些算法都会把存活对象移动到一起，整理出规整的空闲空间。
3. 空闲列表的前提是堆内存不规整，已使用和未使用的内存交错在一起。JVM 维护一个空闲列表，记录每一块可用内存的位置和大小，分配时从列表中找一块足够大的划分出去。这种分配方式对应的 GC 算法是标记-清除，因为没有整理步骤，内存碎片化，只能用空闲列表来管理。

### **Q7** 对象在堆内存中的布局是怎样的？Mark Word、Klass Pointer、实例数据、对齐填充各自存什么？
?
1. 一个 Java 对象在堆内存中的布局分为四部分，从上到下依次是 Mark Word、Klass Pointer、实例数据和对齐填充。
2. Mark Word 是对象头的第一部分，占用 8 字节（64 位 JVM 下），用来存储对象自身的运行时数据。不同锁状态下存不同内容：无锁时存 hashCode 和分代年龄，偏向锁时存偏向线程 ID，轻量级锁时存指向栈中锁记录的指针，重量级锁时存指向重量级锁的指针。还有 GC 标记也会用到这里。
3. Klass Pointer 是对象头的第二部分，在 64 位 JVM 下默认 8 字节，开启指针压缩后压缩为 4 字节。它指向方法区中这个对象所属的类的元数据，用来确定对象是哪个类的实例。
4. 实例数据是对象的实际字段数据，包括从父类继承的字段和自身定义的字段，按照字段类型和 JVM 的分配策略排列。通常相同宽度的字段放在一起，父类的字段在子类字段前面，这有利于压缩时减少 padding 开销。
5. 对齐填充不是必须的。HotSpot 要求对象起始地址必须是 8 字节的整数倍，所以如果前三部分加起来不是 8 的倍数，就需要填充几个字节来补齐。这是一种以空间换访问速度的优化。

### **Q8** 判断对象是否存活的两种方式？GC Roots 包括哪些？可以作为 GC Roots 的对象类型说全。
?
1. 判断对象是否存活有两种方式。引用计数法是为每个对象维护一个计数器，有引用加一，引用失效减一，计数为零表示可以回收。但引用计数法有致命缺陷——无法解决循环引用，A 引用 B、B 引用 A，双方计数器都不为零但实际都不可达。
2. 主流 JVM 都用可达性分析算法。从一组 GC Roots 对象出发，沿着引用链搜索，能搜索到的都是存活的，搜索不到的就是可以回收的。
3. GC Roots 包含以下几类。第一，虚拟机栈中引用的对象，比如方法里的局部变量。第二，方法区中类的静态属性引用的对象。第三，方法区中常量引用的对象，比如字符串常量池里的引用。第四，本地方法栈中 JNI 引用的对象。第五，Java 虚拟机内部的引用，比如基本数据类型对应的 Class 对象、常驻的异常对象等。第六，被同步锁持有的对象——被 synchronized 持有的对象。第七，JMXBean、JVMTI 回调、本地代码缓存等内部引用。这七类就是完整的 GC Roots 集合。

## 三、引用的四种类型

### **Q9** 强引用、软引用、弱引用、虚引用的区别？各自的回收时机和使用场景？
?
1. 强引用是最普通的引用，只要强引用在，GC 永远不会回收这个对象。即使内存不够抛 OOM 也不回收。日常 new 出来的对象都是强引用。
2. 软引用是内存敏感型引用。正常运行时，GC 不会回收软引用指向的对象。但当内存不够、即将要抛 OOM 之前，JVM 会把所有软引用对象列入回收范围。回收完后内存还不够，才会抛 OOM。所以软引用适合做内存敏感的缓存，比如图片缓存——内存够的时候就留着，内存紧张了自动释放。
3. 弱引用比软引用更弱。只要发生 GC，不管内存够不够，弱引用指向的对象都会被回收。弱引用的典型场景是 ThreadLocal 的 Entry 中的 Key，还有 WeakHashMap 的 Key。用弱引用可以防止不经意间阻止对象被回收。
4. 虚引用是最弱的引用。它不能通过 get 获取到引用对象——get 永远返回 null。虚引用的存在意义不在于访问对象，而在于对象被回收时收到一个通知。虚引用必须配合 ReferenceQueue 使用，当对象被 GC 回收时，虚引用被加入到引用队列中，程序可以知道对象被回收了，做一些资源清理工作。

### **Q10** `WeakHashMap` 里的 Entry 继承了 `WeakReference`，key 被 GC 后 value 会自动清理吗？
?
1. WeakHashMap 的 Entry 继承自 WeakReference，key 用弱引用包装，所以当外部没有强引用指向 key 时，GC 会把 key 回收掉，Entry 里的 key 变成 null。但 value 不会被自动回收，它还是强引用存在 Entry 里面，而 Entry 又被 WeakHashMap 内部的数组引用着。
2. 所以实际情况是：GC 后 Entry 还在，key 已是 null，value 还活着，形成了所谓的废弃 Entry。WeakHashMap 会在每次调用 get、put、size 方法时，触发 expungeStaleEntries 清理方法，遍历 Entry 数组把 key 为 null 的 Entry 清掉，顺带释放 value。但如果一直不操作 WeakHashMap，这些废弃 Entry 和 value 就永远不会被清理。这也是 WeakHashMap 的一个注意点——它依赖操作触发清理，不操作就不清理。

### **Q11** 虚引用（`PhantomReference`）必须和 `ReferenceQueue` 一起用，它到底有什么用？NIO 的 `Cleaner` 是怎么用虚引用管理直接内存的？
?
1. 虚引用的 get 方法永远返回 null，所以它不能用来访问对象。它的作用是一种对象回收的通知机制。创建虚引用时必须传入一个 ReferenceQueue，当引用对象被 GC 回收时，JVM 会把虚引用对象加入到这个引用队列中。程序通过监控这个队列就知道哪些对象被回收了，从而执行相应的资源清理。
2. NIO 中 Cleaner 管理直接内存就是基于这个机制。每个 DirectByteBuffer 创建时，会在内部创建一个 Cleaner 对象，而 Cleaner 继承自 PhantomReference，它所引用的对象就是 DirectByteBuffer 本身。同时 Cleaner 关联了一个 Runnable 任务——释放直接内存的 unsafe.freeMemory 调用——和一个 ReferenceQueue。当 DirectByteBuffer 对象变成不可达被 GC 回收时，JVM 把 Cleaner 加入引用队列。有一个专门的 ReferenceHandler 守护线程会从队列里取出 Cleaner，执行它的 clean 方法，clean 里调用 Runnable 释放对应的直接内存。这就是虚引用在 NIO 直接内存管理中的核心作用——对象释放了但资源还没释放，通过虚引用来补这个后手。

## 四、GC 算法 & 分代模型

### **Q12** 标记-清除、标记-整理、复制算法各自的优缺点？为什么新生代用复制算法，老年代用标记-整理？
?
1. 标记-清除算法分两步：先标记所有存活对象，再统一清除未标记的对象。优点是简单。缺点也很突出，一是执行效率不高，标记和清除都要扫描整个堆；二是清除后产生大量内存碎片，碎片多了分配大对象时可能明明总内存够但找不到连续空间，提前触发 GC。
2. 标记-整理算法在标记存活对象后，把存活对象向一端移动，然后直接清理掉边界以外的内存。优点是整理后内存是规整的，没有碎片；缺点是整理过程需要移动对象，如果存活对象多，移动操作的开销比较大。
3. 复制算法把内存分成两块，每次只用一块。GC 时把存活对象复制到另一块，然后把当前这块全部清空。优点是简单高效，没有碎片；缺点是只能用到一半的内存，浪费严重。IBM 的一项研究表明，大多数新生代对象朝生夕死，98% 的对象在第一次 Minor GC 时就死了，所以没必要保留一半。HotSpot 的实践是把新生代分成一个 Eden 和两个 Survivor，Eden 和 Survivor 的比例默认是 8:1，每次复制时只有 10% 左右的对象需要搬，内存利用率达到 90%。
4. 新生代用复制算法是因为新生代中对象死亡率极高，需要复制的存活对象很少，复制成本很低，而且复制可以快速整理内存。老年代用标记-整理是因为老年代中的对象存活率高，如果还用复制算法，大量存活对象都要搬，复制成本太高，而且老年代本身空间就大，复制的话浪费空间更多。标记-整理虽然搬对象有成本，但老年代 GC 不频繁——只有发生 Full GC 或者 Mixed GC 时才整理——摊下来可以接受。

### **Q13** 分代收集理论中，"跨代引用"是怎么解决的？卡表（Card Table）和写屏障（Write Barrier）是什么？
?
1. 跨代引用是指老年代中的对象引用了新生代中的对象。这在 Minor GC 时会造成问题——新生代 GC 只扫描新生代，但老年代中的引用指向新生代时，光看新生代内的引用链会漏掉这些对象，导致存活对象被误回收。
2. 为了解决这个问题，JVM 引入了卡表。卡表是一个字节数组，把整个老年代按每 512 字节划分成一个"卡"。当老年代中的对象引用了新生代对象时，对应的卡被标记为脏卡。Minor GC 时，不需要扫描整个老年代，只需要扫描标记为脏的那些卡，就能找到所有跨代引用。这大大减少了 Minor GC 时需要扫描的老年代范围。
3. 写屏障是标记脏卡的机制。写屏障不是一道"墙"，而是 JVM 在引用类型字段赋值操作前后插入的一段代码。当执行老年代对象引用新生代对象的赋值时，写屏障中的后置屏障会把对应的卡标记为脏。这个标记操作本身的开销很小，就是一个字节赋值，所以分代收集的性能可以接受。

### **Q14** Minor GC、Major GC、Full GC 的区别？什么时候会触发 Full GC？Full GC 一定是 STW 的吗？
?
1. Minor GC 也叫 Young GC，只发生在新生代。触发条件是 Eden 区满了，需要把存活对象拷贝到 Survivor 区或者晋升到老年代。Minor GC 频率最高，通常几十到几百毫秒就能完成。
2. Major GC 在老年代发生，通常指的是 CMS 的老年代并发收集，或者 G1 的 Mixed GC。Major GC 一般比 Minor GC 慢很多，因为老年代空间大、存活对象多。
3. Full GC 是整个堆加方法区的全局 GC，回收范围最大，耗时最长。触发条件有这几个：一是 System.gc 的调用（虽然不保证一定触发）；二是老年代空间不足；三是方法区空间不足；四是 CMS 的 Concurrent Mode Failure 降级；五是 Minor GC 时向老年代晋升对象，但老年代剩余空间不够的担保失败。
4. 在传统垃圾收集器中，Full GC 基本是全程 STW 的。Serial Old 和 Parallel Old 的 Full GC 都全程暂停，CMS 的 Full GC 也是降级到 Serial Old 后单线程且 STW 的。但在 G1 和 ZGC 这些现代收集器中，所谓 Full GC 的概念已经弱化了。G1 的 Mixed GC 不是全局的而是只回收部分 Region，ZGC 和 Shenandoah 几乎不做全局 Full GC。所以 Full GC 全 STW 主要针对传统收集器，现代收集器已经大幅淡化甚至消除了 Full GC。

## 五、垃圾收集器深度对比

### **Q15** 7 种经典垃圾收集器的组合关系？Serial / ParNew / Parallel Scavenge / Serial Old / Parallel Old / CMS / G1，哪些是新生代，哪些是老年代？
?
1. 七种收集器里，新生代收集器有三个：Serial 是单线程的，ParNew 是 Serial 的多线程版本，Parallel Scavenge 也是多线程但侧重点是吞吐量优先。老年代收集器也有三个：Serial Old 是单线程的，Parallel Old 是多线程的，CMS 是多线程但追求低停顿。G1 比较特殊，它不再分代而是按 Region 划分，但逻辑上它同时涵盖新生代和老年代。
2. 合法的搭配组合是这样的：Serial 配 Serial Old 或 CMS——Serial 配 Serial Old 是客户端模式默认，Serial 配 CMS 是老版本的一种组合；ParNew 配 CMS，这是 CMS 经典组合，因为只有 ParNew 能和 CMS 配合；Parallel Scavenge 配 Parallel Old，这是吞吐量优先组合。G1 自成一体不需要搭配。
3. Serial 和 ParNew 不能配 Parallel Old，Parallel Scavenge 不能配 CMS，这些组合不被支持是因为分代之间的交互协议对不上。

### **Q16** CMS 的四个阶段是什么？哪些阶段 STW？并发标记阶段用了什么算法（三色标记），"漏标"是怎么处理的？（增量更新 Incremental Update）
?
1. CMS 有四个阶段。第一阶段初始标记，STW，只标记 GC Roots 直接关联的对象，速度很快。第二阶段并发标记，不需要 STW，从初始标记的对象出发并发地遍历整个对象图，耗时最长。第三阶段重新标记，STW，修正并发标记期间用户线程继续运行造成的标记变化，比初始标记慢但比并发标记快得多。第四阶段并发清除，不需要 STW，并发清理未标记对象。
2. 所以四个阶段中只有初始标记和重新标记需要 STW，并发标记和并发清除都是和用户线程并行的。这就是 CMS 低停顿的核心——把最耗时的阶段放在并发状态下进行。
3. 并发标记阶段用的是三色标记算法。白色表示还没被扫描到的对象，灰色表示对象本身被扫描到了但它的引用还没扫描完，黑色表示对象本身和它的引用都扫描完了。最终白色对象就是要回收的。
4. 并发标记的漏标问题是这样产生的：在并发标记期间，用户线程还在跑，可能会把一个黑色对象的引用指向一个白色对象，同时删掉了从灰色对象到那个白色对象的所有引用。这就导致白色对象被漏标——标记结束后它是白色的，但实际上还在被黑色对象引用着，是存活对象。CMS 用增量更新解决漏标：当黑色对象新增了对白色对象的引用时，通过写屏障记录这个变化，并发标记结束后重新标记阶段会把这些黑色对象重新扫描一遍，确保被它们新引用的白色对象能被正确标记。增量更新的本质是打破第一个条件——不让黑色对象新增白色引用而不被记录。

### **Q17** CMS 有哪些缺点？（内存碎片 / 浮动垃圾 / Concurrent Mode Failure → 降级 Serial Old）
?
1. CMS 有三个核心缺点。
2. 第一，内存碎片。CMS 用的是标记-清除算法，老年代不会整理，长时间运行后碎片化严重。碎片多了导致大对象无法分配，即使老年代剩余总空间够但没有连续空间，只得提前触发 Full GC，而 CMS 的 Full GC 会降级为单线程的 Serial Old，非常慢。可以通过 -XX:+UseCMSCompactAtFullCollection 在 Full GC 后整理，但这本身又增加了停顿。
3. 第二，浮动垃圾。并发清除阶段，用户线程可能又产生了新的垃圾对象，但这次 GC 已经标记完了，这些新垃圾只能等下一次 GC 才能回收。浮动垃圾占用了老年代空间，可能导致下次 GC 被提前触发。
4. 第三，Concurrent Mode Failure。CMS 在并发收集期间，如果老年代剩余空间不足以满足新晋升对象和新分配的大对象，就会发生 Concurrent Mode Failure。这时候 CMS 会暂停所有用户线程，降级为 Serial Old 单线程去做 Full GC，停顿时间会非常长。这也是 CMS 不能让老年代太满的原因——通常老年代用到 68% 左右就要启动 CMS 了。

### **Q18** G1 的堆内存布局是怎样的？Region 的四种类型？Humongous 大对象的分配规则？
?
1. G1 不再把堆固定分为新生代和老年代两块，而是把整个堆划分成多个大小相等的 Region，每个 Region 默认 2 的 N 次方 MB，在 1MB 到 32MB 之间。这些 Region 在逻辑上可以扮演不同的角色，不再有物理上的连续边界。
2. Region 有四种类型。Eden Region 是新生代的 Eden 区，存放刚创建的对象。Survivor Region 是新生代的 Survivor 区，存放经过 Minor GC 后存活的对象。Old Region 是老年区，存放经过多次 GC 后晋升的对象。Humongous Region 是大对象区，专门存放大对象。
3. Humongous 大对象的判定标准是：大小超过一个 Region 容量的一半。比如 Region 是 4MB，对象超过 2MB 就算大对象。对于 Humongous 对象，分配规则是这样的：如果它的大小刚好小于一个 Region，G1 会从空闲 Region 中分配一个来存，这个 Region 被标记为 H 类型。如果超过了 Region 的大小，G1 会分配连续的多个 Region 来存储，这些 Region 串联在一起。Humongous 对象直接分配在老年代区域，不经过新生代，免去了在新生代复制搬运的开销。但在早期的 G1 版本中，Humongous 对象的回收只能在 Full GC 或者并发标记周期中的 Cleanup 阶段处理，效率不高，这也是 G1 的一个小缺陷。

### **Q19** G1 的回收流程？Young GC（STW）→ 并发标记 → 最终标记（STW）→ 筛选回收（STW）。SATB（Snapshot At The Beginning）和 CMS 的增量更新有什么区别？
?
1. G1 的回收流程分四步。第一步，Young GC，当 Eden Region 满了时触发，STW，把存活对象复制到 Survivor Region 或者晋升到 Old Region。第二步，并发标记，在堆占用达到 IHOP 阈值后启动，和用户线程并发运行，扫描整个堆的对象图。第三步，最终标记，也叫重新标记，STW，处理并发标记期间的 SATB 记录队列中的变化，以及卸载类的标记。第四步，筛选回收，也叫 Cleanup，STW，根据每个 Region 的回收价值和回收成本排序，优先回收垃圾最多的 Region——这也是 G1 名字 Garbage First 的由来——把存活对象复制到空闲 Region 同时清空回收的 Region。
2. SATB 和 CMS 增量更新的区别在于漏标的处理策略不同。CMS 的增量更新关注的是"新增引用"——当黑色对象新增了指向白色对象的引用时，记录并重新扫描黑色对象，防止新增引用导致漏标。SATB 关注的是"删除引用"——在并发标记开始时对对象图做一个快照，标记过程中如果某个灰色对象的引用被删除了，SATB 通过写屏障把这个被删除的引用记录到 SATB 队列里，重新标记阶段再处理这些记录。SATB 的理念是"宁可多标不可漏标"，它会保留快照时刻所有可达对象，即使有些引用在标记过程中被删除了也会被当作存活，这会产生一些浮动垃圾，但避免了漏标导致的活对象被回收。所以卫星：增量更新是打破漏标的"新增引用"条件，SATB 是打破"删除引用"条件。

## 六、ZGC & Shenandoah（低延迟划重点）

### **Q20** ZGC 的核心目标是什么？它凭什么能把 STW 控制在亚毫秒级？染色指针（Colored Pointer）和读屏障（Load Barrier）分别做了什么？
?
1. ZGC 的核心目标是实现超低停顿，STW 时间控制在 10ms 以下，且不随堆大小和存活对象规模的增大而增加。传统垃圾收集器的停顿时间和堆大小成正比，堆越大 STW 越长，但 ZGC 做到停顿时间几乎恒定。
2. ZGC 做到亚毫秒停顿靠的是两个关键技术——染色指针和读屏障。
3. 染色指针不是简单的指针，而是把 64 位指针的高位几个 bit 用来存储 GC 状态标记——包括 Marked0、Marked1、Remapped、Finalizable 等。这些标记位直接编码在指针里，不需要单独维护 Mark Word 或者其他元数据，读取指针的时候就知道对象的状态了。而且因为标记在指针上，并发标记和整理时可以原地修改指针而不用碰对象本身。
4. 读屏障是在每次从堆中读取对象引用时插入的一小段代码。当 ZGC 并发搬移对象时，可能有些线程的引用还指向旧地址。读屏障会检查指针上的染色标记，如果发现对象正在被搬移中，读屏障会帮助完成搬移或者修正引用——把旧地址的引用更新到新地址。这就是 ZGC 的自愈机制：任何线程读到过期引用时，读屏障自动纠正，不需要 STW 去统一更新所有引用。并发搬移加上自愈读屏障，实现了绝大部分 GC 工作和用户线程并发。

### **Q21** ZGC 的分代回收（JDK21）和非分代回收（JDK11-17）有什么区别？为什么要引入分代？
?
1. JDK11 到 JDK17 的 ZGC 是非分代的，不区分新生代和老年代，整个堆平等对待。所有对象都在同一套管理下，一个全局的并发标记和整理周期处理整个堆。
2. JDK21 开始 ZGC 引入了分代回收，把堆分成了新生代和老年代，新生代和老年代的 GC 策略不同。新生代 GC 频率更高但回收对象少时很快，老年代 GC 频率更低。分代 ZGC 的 STW 依然保持在亚毫秒级别，但吞吐量显著提升。
3. 引入分代的原因很简单——非分代 ZGC 在吞吐量上不占优势。非分代的全局标记和整理全量扫描整个堆，虽然停顿低，但 CPU 和内存带宽的开销大，影响吞吐量。引入分代后，大部分 GC 只发生在新生代，新生代大小远小于整个堆，每次 GC 的工作量小很多，整体吞吐量提升明显。这个策略和新老代 GC 的基本原理一致：利用对象的弱分代假说，朝生夕死的对象在新生代快速回收，生命周期长的在老年代低频回收。

### **Q22** 你的项目现在用什么垃圾收集器？如果要升级到 ZGC，需要满足什么条件？有什么风险？
?
1. 如果项目当前运行在 JDK8 或 JDK11 上，大概率用的是 G1 或者 Parallel 收集器。升级到 ZGC 的前提是 JDK 版本至少要 JDK11——JDK11 开始实验性支持，JDK15 正式生产可用，JDK21 分代 ZGC 带来了吞吐量提升。
2. 升级条件有几个。一是 JDK 版本要够，建议直接上 JDK21，用分代 ZGC。二是内存要足，ZGC 需要额外的染色指针开销，而且是三色标记的染色不是传统三色标记，堆外内存消耗比 G1 大。三是应用程序本身不需要做代码改动，大多数情况下只是替换 JVM 启动参数——去掉 G1 相关参数，加上 -XX:+UseZGC 就行。四是要关注操作系统——目前 ZGC 主要在生产级别的 Linux 上表现最好。
3. 风险主要有三个方面。一是吞吐量可能在短期内不如 G1，尤其是 JDK17 之前的非分代 ZGC，吞吐量比 G1 有时候低 10% 到 15%。JDK21 分代 ZGC 好很多。二是 ZGC 需要的内存更多，如果原来资源就紧张，切换后可能因为内存压力反而触发更频繁的回收。三是兼容性和稳定性，ZGC 相比于 G1 的成熟度还是稍低一些，在一些极端场景下可能触发未知问题。所以一般建议先在预发环境充分压测，观察一段时间再上生产。

## 七、类加载 & 双亲委派

### **Q23** 类加载的五个阶段各自做了什么？准备阶段和初始化阶段分别给静态变量赋了什么值？
?
1. 类加载的五个阶段：加载、验证、准备、解析、初始化。
2. 加载阶段是通过类的全限定名获取字节流，然后在方法区创建类的运行时数据结构，并在堆中生成一个 Class 对象作为访问入口。
3. 验证阶段是确保字节码文件符合 JVM 规范，不会危害 JVM 安全。包括文件格式验证、元数据验证、字节码验证和符号引用验证。
4. 准备阶段是为类的静态变量分配内存，并设置默认初始值——int 为 0、boolean 为 false、引用为 null。这个阶段赋的是零值，不是程序员写的初始值。例外是常量——被 static final 修饰的字段——在准备阶段就会被赋程序指定的值，因为它的值在编译时就确定了。
5. 解析阶段是把常量池中的符号引用替换为直接引用，比如把类名、方法名、字段名的字符串替换成内存地址。
6. 初始化阶段是真正执行类构造器 clinit 方法，把程序员写的静态变量赋值代码和静态代码块按照顺序执行。这个阶段才把 count = 10 这样的赋值赋上去。

### **Q24** 双亲委派模型的工作流程？`loadClass()` 源码说清楚。为什么需要双亲委派？
?
1. 双亲委派模型的工作流程是：类加载器收到加载请求时，不会自己先去加载，而是把请求委派给父加载器，一直向上传递，直到顶层的启动类加载器。只有父加载器反馈说找不到这个类，子加载器才会尝试自己加载。
2. loadClass 的源码逻辑体现了这个流程。首先调用 findLoadedClass 检查类是否已经被加载过。如果已经加载直接返回。否则，如果父加载器存在，调用父加载器的 loadClass 方法委派上去；如果父加载器不存在——说明当前就是启动类加载器——调用 findBootstrapClass 尝试启动类加载器加载。如果父加载器加载失败了抛出 ClassNotFoundException，才调用自己的 findClass 方法去自己加载。
3. 需要双亲委派的原因是为了保证 Java 核心类库的安全性。如果没有双亲委派，用户完全可以自己写一个 java.lang.String 类放在 classpath 下，JVM 加载时如果先扫到用户这个类，那整个 Java 的 String 类型就乱套了。双亲委派保证了核心类库总是从根加载器层加载，无法被替换。还有一个原因是避免类的重复加载——父加载器已经加载过的类，子加载器不再加载，保证同一个类在 JVM 中只有一份。

### **Q25** 什么场景需要打破双亲委派？Tomcat 的 `WebappClassLoader` 是怎么打破的？JDBC 的 SPI 又是怎么用线程上下文类加载器打破的？
?
1. 打破双亲委派的核心需求是隔离和反向访问。
2. Tomcat 需要打破双亲委派是因为它要运行多个 Web 应用，每个应用可能有自己的版本库，比如 App1 用 Spring 5、App2 用 Spring 6，如果都按双亲委派走，两个 Spring 的类会被同一个父加载器加载，只会加载一个版本，另一个应用就出错了。Tomcat 的 WebappClassLoader 打破了双亲委派，它重写了 loadClass 方法——优先自己尝试加载，找不到再委派给父加载器。而且每个 Web 应用有独立的 WebappClassLoader 实例，这样不同应用的类就被隔离了。对于 Java 核心类库，Tomcat 还是走父加载器，不允许覆盖。
3. JDBC 的 SPI 打破双亲委派的方式不同。JDBC 的核心接口如 Driver 接口在 java.sql 包中，是由启动类加载器加载的。但具体的数据库驱动实现如 MySQL Driver 是在 classpath 下，由应用程序类加载器加载。启动类加载器没法加载 classpath 下的类，按照双亲委派，启动类加载器委派不下去——因为不认子加载器。这时候就用到了线程上下文类加载器。DriverManager 在加载驱动时，通过 Thread.currentThread().getContextClassLoader() 获取到应用类加载器，用这个类加载器去加载 classpath 下的 MySQL 驱动实现。这就是 SPI 打破双亲委派的方式——借助线程上下文类加载器实现从父加载器向子加载器的反向访问。

## 八、JVM 参数 & 调优

### **Q26** 这些 JVM 参数分别控制什么？`-Xms`、`-Xmx`、`-Xmn`、`-XX:SurvivorRatio`、`-XX:MetaspaceSize`、`-XX:MaxMetaspaceSize`、`-XX:MaxDirectMemorySize`
?
1. -Xms 是堆的初始大小，JVM 启动时分配的堆空间。建议和 -Xmx 设为一样，避免堆动态扩容带来的性能抖动。
2. -Xmx 是堆的最大大小。当堆使用量达到这个值时会触发 OOM。需要根据机器内存和业务需求合理设定。
3. -Xmn 是新生代大小。一般是整个堆的三分之一到二分之一。新生代设太小会导致对象过早晋升到老年代，增加 Full GC 频率；设太大老年代会变小，频繁触发 Full GC。
4. -XX:SurvivorRatio 是 Eden 区和单个 Survivor 区的比例。默认是 8，意味着 Eden:Survivor0:Survivor1 = 8:1:1。如果 Minor GC 后 Survivor 放不下了，对象直接进入老年代，调整这个比例可以控制对象晋升的速率。
5. -XX:MetaspaceSize 是触发元空间 GC 的初始阈值。当元空间使用量超过这个值时会触发一次 Full GC 进行类卸载。可以设大一些避免元空间 GC 过于频繁。
6. -XX:MaxMetaspaceSize 是元空间的最大使用量。防止类加载泄漏无限占用本地内存。生产环境必须设置。
7. -XX:MaxDirectMemorySize 是直接内存的最大使用量。默认和 -Xmx 的堆最大值一样。NIO 大量使用直接内存的场景需要合理设置，防止本地内存被吃光。

### **Q27** `-XX:+UseG1GC`、`-XX:MaxGCPauseMillis`、`-XX:G1HeapRegionSize`、`-XX:InitiatingHeapOccupancyPercent` 分别怎么用的？
?
1. -XX:+UseG1GC 是启用 G1 垃圾收集器。JDK9 之后 G1 已经是默认收集器，不需要显式指定。
2. -XX:MaxGCPauseMillis 是期望的最大 GC 停顿时间，默认 200ms。G1 会根据这个目标来调整新生代大小和回收 Region 的数量，在停顿时间目标内尽可能多地回收垃圾。这个值不是硬限制，只是 G1 尽力接近的目标。设置时不要设得太激进——比如期望 10ms——否则 G1 每次回收的范围太小，可能导致垃圾堆积。
3. -XX:G1HeapRegionSize 是每个 Region 的大小，必须是 2 的 N 次方，在 1MB 到 32MB 之间。Region 小了并行度更高但管理开销大，大了吞吐更高但灵活性降低。一般根据堆大小确定——堆在 4GB 以内用 2MB，4-8GB 用 4MB，8-16GB 用 8MB 或者 16MB，更大的堆用 16MB 或 32MB。目标是让 Region 总数保持在 2048 左右。
4. -XX:InitiatingHeapOccupancyPercent 简称 IHOP，是触发并发标记周期的堆占用阈值，默认 45。当老年代占用超过这个百分比时，G1 启动并发标记周期。设置低一些可以更早开始标记降低 Concurrent Mode Failure 的风险，但标记周期会更频繁；设置高一些可以提高堆利用率但增加降级为 Full GC 的风险。

### **Q28** 一个线上服务：堆 4G、QPS 3000、RT P99 100ms，GC 日志显示 Young GC 频繁且耗时长，你会怎么调优？
?
1. Young GC 频繁说明新生代太小，对象还没来得及死就不得不做 GC。Young GC 耗时长可能因为存活对象太多，复制耗时增加，或者 Survivor 区太小导致对象过早晋升到老年代。
2. 调优思路分几步。第一步，先看 GC 日志中每次 Young GC 后的新生代存活对象量。如果 Survivor 区总能容纳，那说明对象生命周期短，可以把新生代调大一些，比如把 -Xmn 从 1G 调到 1.5G 或 2G。新生代大了，GC 频率自然就降下来了。
3. 第二步，看晋升到老年代的对象量。如果晋升量大，说明 Survivor 区太小或者对象生命周期偏长但还没到该晋升的程度。可以调整 SurvivorRatio 让 Survivor 区大一点——比如从 8 调到 6，让 Survivor 占比从 10% 升到 12.5%。
4. 第三步，如果 Young GC 耗时长是因为新生代太大导致复制时间长，那反而要缩小新生代。这是反直觉的——大了频率低但每次扫描和复制耗时增加，小了频率高但每次都很快。需要根据业务的特点在这两者之间找平衡点。QPS 3000、RT P99 100ms 这个规模不会太大，4G 堆的新生代控制在 1.5G 到 2G 比较合理。
5. 第四步，如果业务特点是对象生命周期短，可以确认是否开启了 G1（JDK9 以上默认是 G1）。G1 对 Young GC 的处理比 Parallel 更灵活，因为在 Mixed GC 中会回收老年代 Region。
6. 最后，如果频繁 Young GC 是因为代码里存在大量短命临时对象，可以考虑在业务层面做优化，比如对象池、StringBuilder 复用这些策略。

## 九、线上排查工具 & 流程

### **Q29** `jps`、`jstat`、`jmap`、`jstack`、`jinfo` 各自的用途？`jstat -gcutil` 输出哪些关键指标？
?
1. jps 列出当前系统里所有 Java 进程的进程 ID 和主类名，排查的第一步通常就是 jps 找到 java 进程的 PID。
2. jstat 是 JVM 统计信息监控工具，可以实时查看堆、GC、类加载、编译等运行数据。最常用的是 jstat -gcutil 每几秒输出一次 GC 信息。
3. jmap 用来查看堆内存信息，可以做堆转储 dump 文件，方便后续用工具分析。也可以查看堆中对象的统计信息。
4. jstack 用来生成线程栈快照，可以看到每个线程在做什么、有没有死锁。线上 CPU 飙高、线程卡死时用它定位。
5. jinfo 用来查看和动态修改 JVM 运行参数，比如查看当前生效的 JVM 参数值，或者动态设置某些可动态调整的参数。
6. jstat -gcutil 输出的关键指标有：S0 和 S1 表示两个 Survivor 区使用率，E 是 Eden 区使用率，O 是老年代使用率，M 是元空间使用率，YGC 是 Young GC 次数，YGCT 是 Young GC 总耗时，FGC 是 Full GC 次数，FGCT 是 Full GC 总耗时，GCT 是所有 GC 总耗时。通过这些数字可以快速判断内存状态：Eden 持续高可能是 Young GC 频繁的前兆，老年代持续升高可能即将触发 Full GC，Full GC 次数异常增长说明内存泄漏或配置不合理。

### **Q30** 线上突然 CPU 飙到 100%，你的排查流程是什么？（`top -Hp` → `printf '%x'` → `jstack` → 定位线程和代码行）
?
1. CPU 飙高的排查有一套标准流程。
2. 第一步，用 top 命令找到 CPU 使用率最高的 Java 进程 PID。
3. 第二步，用 top -Hp PID 查看这个进程里每个线程的 CPU 使用率，找到 CPU 使用率最高的那几个线程的线程 ID。这个 ID 是十进制的。
4. 第三步，把线程 ID 转成十六进制，用 printf '%x\n' 线程ID 即可，因为 jstack 输出的 nid 是十六进制的。
5. 第四步，用 jstack PID 打出线程栈信息，在里面搜索第五步得到的十六进制线程 ID。搜索到的线程栈就是 CPU 占用最高的线程当前正在执行的代码位置。
6. 第五步，根据栈信息定位到具体的代码行，分析是什么原因。常见的原因有：死循环、频繁的 Young GC 导致的 GC 线程占用、正则表达式回溯、HashMap 死循环等。如果是 GC 线程 CPU 高，看 GC 日志。如果是业务线程，看对应代码逻辑。

### **Q31** 线上 OOM（`java.lang.OutOfMemoryError: Java heap space`），你手上只有一台挂掉的机器，怎么排查？（`-XX:+HeapDumpOnOutOfMemoryError` 参数、MAT/JProfiler 分析 Dump）
?
1. 排查 OOM 的核心是先拿到堆转储文件，再分析。
2. 前提是 JVM 启动时加了 -XX:+HeapDumpOnOutOfMemoryError 参数，这样 OOM 发生时会自动生成一个 heap dump 文件。同时配合 -XX:HeapDumpPath 指定 dump 文件路径，避免文件过大撑满磁盘。
3. 拿到 dump 文件后，用 MAT 或者 JProfiler 分析。MAT 打开 dump 后，先看 Leak Suspects 报告，MAT 会自动分析可能的泄漏点，给出嫌疑对象和引用链。然后看 Dominator Tree，按对象占用内存大小排序，找出最大的几个对象，沿着它们的引用链向上追溯，看是被哪个 GCRoot 引用着，从而定位出哪里创建了这些对象没有释放。
4. 常见的 OOM 原因有几种：一是真的数据量太大，比如一次性查了太多数据（需要分批查询）；二是代码里用了静态集合如 HashMap，往里 add 但从不 remove，内存越积越多；三是第三方库的内存泄漏；四是频繁创建大对象且这些对象无法被及时回收。根据分析结果针对性修复。
5. 如果没有加 HeapDumpOnOutOfMemoryError 参数，可以事后用 jmap -dump:live,format=b,file=heap.hprof PID 手动导出堆转储。但手动导出时进程可能已经很卡了不一定能成功。所以强烈建议启动时就把这个参数加上。

## 十、JIT 编译优化

### **Q32** JIT 即时编译和解释执行的区别？C1（Client Compiler）和 C2（Server Compiler）的分工？分层编译（Tiered Compilation，JDK8 默认开启）是怎么逐层升级的？
?
1. 解释执行是边读字节码边翻译成机器码然后执行，每次执行都要翻译，没有预热过程但执行效率低。JIT 即时编译是把热点代码一次编译成机器码缓存起来，以后直接执行机器码，不需要再翻译，执行效率高。
2. C1 是客户端编译器，编译速度快，但生成的机器码优化程度低，追求快速进入编译执行状态，适合启动时间敏感的场景。C2 是服务端编译器，编译速度慢但编译过程中做了大量优化——方法内联、循环展开、逃逸分析等——生成的机器码质量高，适合长时间运行的服务端应用。
3. 分层编译是 C1 和 C2 的混合模式，默认开启。它把编译分为五层：第 0 层解释执行，第 1 层 C1 编译但不收集 profiling 数据，第 2 层 C1 编译并收集有限的 profiling 数据，第 3 层 C1 编译并收集全部 profiling 数据，第 4 层 C2 编译。一个方法先在解释模式下运行，达到一定调用次数后进入 C1 的第 2 或第 3 层，C1 编译时收集方法的执行信息如类型分布、分支概率。这些 profiling 数据传给 C2 的第四层，C2 基于精确的运行时数据进行深度优化，生成最优的机器码。如果 C2 编译的假设后来被推翻，还可以反优化退回到解释执行或 C1。这个逐层升级的机制兼顾了启动快和长期运行快两个目标。

### **Q33** 逃逸分析（Escape Analysis）是什么？标量替换（Scalar Replacement）、栈上分配（Stack Allocation）、同步消除（Lock Elision）分别是基于逃逸分析的什么优化？
?
1. 逃逸分析是 JIT 编译器分析一个对象的动态作用域的技术。看这个对象有没有在方法外部被引用——对象作为返回值返回了，或者赋值给了类字段或静态变量，就是逃逸出了方法。如果对象只在方法内部使用，不逃逸，就可以对它做三种优化。
2. 标量替换是把一个不逃逸的对象拆解成它的成员变量，每个成员变量当作独立的局部变量来分配，不需要在堆上分配整个对象。比如一个 Point 对象只有 x 和 y 两个 int 字段，如果它不逃逸，编译器可以不用创建 Point 对象，直接分配两个 int 局部变量 x 和 y。这样就完全避免了对象创建和 GC。
3. 栈上分配是把不逃逸的对象分配在栈上而不是堆上。对象和方法同生命周期——方法结束栈弹出，对象也随之销毁，不需要 GC 参与回收。不过 HotSpot 并没有真正实现栈上分配，而是通过标量替换来达到类似效果，因为标量替换后对象就不存在了，也就不存在分配在哪的问题。
4. 同步消除是基于逃逸分析判断一个不逃逸的对象，其内部的同步锁永远不可能被多个线程访问到，因为没有线程能看到它。JIT 编译器可以直接把这个锁消除掉，省掉加锁开销。比如 StringBuilder 内部的 synchronized 方法，在新版的 JIT 中如果分析到 StringBuilder 不逃逸，同步块会被消除。

## 十一、实战场景

### **Q34** 你现在负责一个 8C16G 的服务，JDK11、G1、堆 10G，Young GC 平均 80ms 每 3 秒一次，Mixed GC 平均 200ms 每 15 分钟一次，Full GC 从不触发。老板要求 GC 暂停时间 P99.9 降到 50ms 以下，你有哪些手段？
?
1. 当前状态分析：Young GC 80ms 已经超了 50ms 目标，Mixed GC 200ms 更是远超。目标是把所有 GC 暂停控制在 50ms 以下，P99.9。
2. 手段从温和到激进排列。
3. 第一，调整 MaxGCPauseMillis。当前 G1 的默认 GC 停顿目标是 200ms，所以 Mixed GC 做到了 200ms。把 -XX:MaxGCPauseMillis 设为 50，G1 会主动减少每次回收的 Region 数量来控制停顿。但这样做会导致每次回收回收得少，垃圾累积速度可能超过回收速度，反而可能引发 Full GC。所以要配合下面的手段。
4. 第二，增加 Worker 线程数。G1 的并行工作线程数默认约等于 CPU 核心数，8 核情况下是 8。可以考虑调整 -XX:ConcGCThreads 和 -XX:ParallelGCThreads。ParallelGCThreads 一般设为核心数的 80%-100%，可以根据实际情况微调。
5. 第三，调低 IHOP。当前是 15 分钟一次 Mixed GC，说明老年代是慢慢涨才触发并发标记的。把 -XX:InitiatingHeapOccupancyPercent 从默认 45 调低到 35 甚至 30，让并发标记更早启动，每次 Mixed GC 回收的更早，老年代垃圾不多时就能回收掉，每次回收的 Region 少了停顿也就下来了。但代价是 Mixed GC 会更频繁。
6. 第四，缩小堆。10G 堆在当前业务下可能太大了，导致单次 GC 的扫描范围大。如果能调低堆到 6G 或 8G（需要先看老年代占用情况），配合 MaxGCPauseMillis=50，G1 每次回收总量小了，停顿就短了。
7. 第五，升级 JDK 和 GC。从 JDK11 的 G1 升级到 JDK21 的 G1 或 JDK21 的分代 ZGC。JDK17 之后的 G1 在老年代回收和并发标记上有优化。如果升级到 ZGC，STW 直接做到亚毫秒级，远超 50ms 目标。这是最彻底的方案，但需要充分的预发验证。
8. 第六，在应用层面减少对象分配。优化那些频繁创建对象的代码路径，减少 Young GC 的触发频率和每次需要复制的对象数量。
9. 建议的组合策略：先把 MaxGCPauseMillis 设到 50，IHOP 降到 35，观察一周。如果还达不到目标，升级到 JDK21 用 ZGC。在无法升级 JDK 的情况下，考虑适当缩堆并优化业务代码减少对象创建。
