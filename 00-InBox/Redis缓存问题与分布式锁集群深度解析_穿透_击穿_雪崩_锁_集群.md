# 第一部分：缓存三大经典问题

## 1. 缓存穿透：查询不存在的数据

### 1.1 什么是缓存穿透

**缓存穿透**是指用户**查询一个根本不存在的数据**，由于缓存中不存在（也不会被缓存），每次请求都会打到数据库，导致数据库压力骤增。

```
┌─────────────────────────────────────────────────────────────┐
│                      缓存穿透流程                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   用户请求                                                    │
│     │                                                       │
│     ▼                                                       │
│   ┌─────────┐     查询 userId=999999（不存在）               │
│   │  Controller  │                                          │
│   └─────┬───────┘                                           │
│         │                                                   │
│         ▼                                                   │
│   ┌─────────────┐                                           │
│   │   Redis 缓存  │ ──→ miss（缓存中没有，因为从未写入过）     │
│   └─────┬───────┘                                           │
│         │                                                   │
│         ▼                                                   │
│   ┌─────────────┐                                           │
│   │    MySQL     │ ──→ 查不到（数据不存在）                   │
│   └─────┬───────┘                                           │
│         │                                                   │
│         ▼                                                   │
│   ┌─────────────┐                                           │
│   │  返回 null   │ ←── 不会写入缓存！                         │
│   └─────────────┘                                           │
│                                                             │
│   恶意用户不断请求 userId=999999 → 每次都打到 MySQL           │
│   → MySQL 压力骤增 → 可能宕机                                │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 穿透的核心危害

```
正常情况（缓存命中率 95%）：
  10000 请求/秒 → Redis 命中 9500 → MySQL 仅承受 500 请求/秒

穿透情况（恶意请求不存在的 ID）：
  10000 请求/秒 → Redis 全 miss → MySQL 承受 10000 请求/秒
  → MySQL 连接池耗尽 → 服务雪崩
```

### 1.3 解决方案一：空值缓存

**思路**：即使数据库查不到数据，也将 `null` 值缓存起来，设置较短的过期时间。

```java
public User getUserById(Long userId) {
    String key = "user:" + userId;
    
    // 1. 查缓存
    String cached = redis.get(key);
    if (cached != null) {
        if ("NULL".equals(cached)) {
            return null;  // 空值标记，直接返回 null
        }
        return JSON.parseObject(cached, User.class);
    }
    
    // 2. 查数据库
    User user = userMapper.selectById(userId);
    
    if (user == null) {
        // 3. 缓存空值，设置较短 TTL（如 60 秒）
        redis.setex(key, 60, "NULL");
        return null;
    }
    
    // 4. 缓存正常数据
    redis.setex(key, 3600, JSON.toJSONString(user));
    return user;
}
```

**优点**：
- 实现简单，改动最小
- 对少量不存在的 Key 有效

**缺点**：
- 如果攻击者每次请求不同的不存在的 ID（如随机生成 100 万个 ID），缓存中会存大量空值，**占用内存**
- 数据库新增了该 ID 的数据后，缓存中的空值不会及时更新（需要等 TTL 过期）

### 1.4 解决方案二：布隆过滤器

**思路**：在缓存之前加一层布隆过滤器，只放行"可能存在"的请求。

```
┌─────────────────────────────────────────────────────────────┐
│                   布隆过滤器防护架构                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   用户请求                                                    │
│     │                                                       │
│     ▼                                                       │
│   ┌──────────────────┐                                      │
│   │  布隆过滤器（BitSet）│                                     │
│   │  判断 Key 是否存在  │                                      │
│   └────────┬─────────┘                                       │
│            │                                                 │
│       ┌────┴────┐                                            │
│       │         │                                            │
│   不存在     可能存在                                         │
│       │         │                                            │
│       ▼         ▼                                            │
│   直接返回    查 Redis → 查 MySQL                              │
│   null（拦截）                                               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 1.4.1 布隆过滤器原理

**布隆过滤器**是一种概率型数据结构，特点是：
- **说"不存在"，一定不存在**（无假阴性）
- **说"存在"，可能存在也可能不存在**（有假阳性）

```
┌─────────────────────────────────────────────────────────────┐
│                    布隆过滤器原理                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   数据：user:1001                                            │
│     │                                                       │
│     ├──→ hash1("user:1001") = 3  ──→ bit[3] = 1            │
│     ├──→ hash2("user:1001") = 7  ──→ bit[7] = 1            │
│     └──→ hash3("user:1001") = 11 ──→ bit[11] = 1           │
│                                                             │
│   数据：user:1002                                            │
│     │                                                       │
│     ├──→ hash1("user:1002") = 7  ──→ bit[7] = 1（已存在）   │
│     ├──→ hash2("user:1002") = 12 ──→ bit[12] = 1           │
│     └──→ hash3("user:1002") = 3  ──→ bit[3] = 1（已存在）   │
│                                                             │
│   判断 user:1003 是否存在：                                   │
│     ├──→ hash1("user:1003") = 3  ──→ bit[3] = 1 ✓          │
│     ├──→ hash2("user:1003") = 7  ──→ bit[7] = 1 ✓          │
│     └──→ hash3("user:1003") = 15 ──→ bit[15] = 0 ✗        │
│                                                             │
│   → bit[15] = 0，说明 user:1003 一定不存在！                 │
│                                                             │
│   判断 user:1004 是否存在：                                   │
│     ├──→ hash1("user:1004") = 3  ──→ bit[3] = 1 ✓          │
│     ├──→ hash2("user:1004") = 7  ──→ bit[7] = 1 ✓          │
│     └──→ hash3("user:1004") = 11 ──→ bit[11] = 1 ✓        │
│                                                             │
│   → 全部命中，说明 user:1004 "可能"存在（也可能误判）         │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 1.4.2 布隆过滤器参数计算

```
n = 预期元素数量（如 1 亿用户）
p = 期望误判率（如 0.01 = 1%）

m = 位数组大小（bit 数）：
    m = -n * ln(p) / (ln2)²
    = -10^8 * ln(0.01) / (ln2)²
    = -10^8 * (-4.605) / 0.4805
    ≈ 9.58 * 10^8 bit
    ≈ 114 MB

k = 哈希函数个数：
    k = (m/n) * ln2
    = (9.58 * 10^8 / 10^8) * 0.693
    ≈ 6.64
    → 取 7 个哈希函数
```

**1 亿用户，1% 误判率，仅需 114 MB 内存，7 个哈希函数。**

#### 1.4.3 Redisson 布隆过滤器实现

```java
// 使用 Redisson 的 RBloomFilter
Config config = new Config();
config.useSingleServer().setAddress("redis://127.0.0.1:6379");
RedissonClient redisson = Redisson.create(config);

RBloomFilter<Long> bloomFilter = redisson.getBloomFilter("user:bloom");
// 初始化：预期 1 亿元素，误判率 0.01
bloomFilter.tryInit(100000000L, 0.01);

// 系统启动时，加载所有用户 ID 到布隆过滤器
List<Long> allUserIds = userMapper.selectAllIds();
for (Long userId : allUserIds) {
    bloomFilter.add(userId);
}

// 查询时先过布隆过滤器
public User getUserById(Long userId) {
    // 1. 布隆过滤器判断
    if (!bloomFilter.contains(userId)) {
        return null;  // 一定不存在，直接返回
    }
    
    // 2. 查缓存
    String key = "user:" + userId;
    String cached = redis.get(key);
    if (cached != null) {
        return JSON.parseObject(cached, User.class);
    }
    
    // 3. 查数据库
    User user = userMapper.selectById(userId);
    if (user != null) {
        redis.setex(key, 3600, JSON.toJSONString(user));
    }
    return user;
}
```

#### 1.4.4 Redisson 布隆过滤器底层实现

Redisson 的 `RBloomFilter` 基于 Redis 的 **BitSet**（String 类型）实现：

```lua
-- 加锁操作（防止并发初始化）
-- tryInit(expectedInsertions, falseProbability)

-- 计算位数组大小和哈希函数个数
-- 然后存储到 Redis 中：
--   {bloom}:size = 95850576
--   {bloom}:hashIterations = 7

-- add(value) 操作：
-- 1. 计算 k 个哈希值
-- 2. 对每个哈希值取模，得到 bit 位置
-- 3. 使用 SETBIT 命令设置对应位
-- 4. 如果所有位已经是 1，返回 false（可能已存在）

-- contains(value) 操作：
-- 1. 计算 k 个哈希值
-- 2. 对每个哈希值取模，得到 bit 位置
-- 3. 使用 GETBIT 命令检查对应位
-- 4. 如果有任何一位是 0，返回 false（一定不存在）
-- 5. 如果全部是 1，返回 true（可能存在）
```

**布隆过滤器 Lua 脚本源码（Redisson 简化版）**：

```lua
-- add(value) 操作的 Lua 脚本
-- 参数：KEYS[1] = bloom filter name
--       ARGV = [size, hashIterations, hash1, hash2, ..., hashK]

local size = tonumber(ARGV[1])
local hashIterations = tonumber(ARGV[2])
local bitsSet = 0

-- 计算 k 个哈希位置并设置 bit
for i = 3, #ARGV do
    local bitPos = tonumber(ARGV[i]) % size
    -- SETBIT key bitPos 1，返回原值
    local oldValue = redis.call('SETBIT', KEYS[1], bitPos, 1)
    if oldValue == 0 then
        bitsSet = bitsSet + 1
    end
end

-- 如果所有位都已经是 1，说明可能已存在
if bitsSet == 0 then
    return 0  -- 已存在（可能误判）
end
return 1  -- 新增成功
```

#### 1.4.5 布隆过滤器的问题

| 问题 | 说明 | 解决方案 |
|------|------|----------|
| **不支持删除** | 删除一个 bit 可能影响其他元素 | 使用 **布谷鸟过滤器**（Cuckoo Filter） |
| **误判率** | 说"存在"可能有 1% 误判 | 调整参数降低误判率（代价是更多内存） |
| **容量固定** | 初始化后无法扩容 | 预估足够的容量，或使用分层布隆 |
| **数据更新延迟** | 新增数据需手动加入过滤器 | 定期全量同步 + 增量同步 |

### 1.6 穿透方案对比

| 方案 | 适用场景 | 优点 | 缺点 |
|------|----------|------|------|
| **空值缓存** | 不存在的 Key 较少且固定 | 实现简单 | 大量不存在的 Key 会占内存 |
| **布隆过滤器** | 数据量大、Key 多样 | 内存极省、查询极快 | 有误判率、不支持删除 |

**生产推荐**：接口拦截 + 布隆过滤器 + 空值缓存（三层防护）。

## 2. 缓存击穿：热点 Key 过期

### 2.1 什么是缓存击穿

**缓存击穿**是指**某个热点 Key 在过期的瞬间**，大量并发请求同时打到数据库，导致数据库压力骤增。

```
┌─────────────────────────────────────────────────────────────┐
│                      缓存击穿流程                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   时间线：T0 时刻缓存过期                                     │
│                                                             │
│   T-1s:  1000 请求/秒 → Redis 命中 → 正常                    │
│   T0:    热点 Key 过期！                                     │
│   T+0.001s: 请求 1 → Redis miss → 查 MySQL → 写缓存           │
│   T+0.001s: 请求 2 → Redis miss → 查 MySQL → 写缓存           │
│   T+0.001s: 请求 3 → Redis miss → 查 MySQL → 写缓存           │
│   ...                                                       │
│   T+0.001s: 请求 1000 → Redis miss → 查 MySQL → 写缓存         │
│                                                             │
│   → 1000 个请求同时打到 MySQL → MySQL 瞬间压力飙升            │
│   → 热点数据如：首页推荐、秒杀商品、热门文章                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 击穿 vs 穿透的区别

| 维度 | 缓存穿透 | 缓存击穿 |
|------|----------|----------|
| **数据是否存在** | 数据**不存在**于数据库 | 数据**存在**于数据库 |
| **缓存状态** | 从未缓存过 | 缓存**过期**了 |
| **触发条件** | 恶意请求不存在的 Key | 热点 Key 恰好过期 |
| **影响范围** | 特定不存在的 Key | 某个热点 Key |
| **解决思路** | 不让请求到数据库 | 不让大量请求同时查数据库 |

### 2.3 解决方案一：互斥锁（Mutex Lock）

**思路**：缓存未命中时，只让一个请求去查数据库并重建缓存，其他请求等待。

```java
public User getHotUser(Long userId) {
    String key = "user:" + userId;
    String lockKey = "lock:user:" + userId;
    
    // 1. 查缓存
    String cached = redis.get(key);
    if (cached != null) {
        return JSON.parseObject(cached, User.class);
    }
    
    // 2. 缓存未命中，尝试获取互斥锁
    // SET lockKey 1 NX EX 10（10 秒自动过期，防止死锁）
    boolean locked = redis.set(lockKey, "1", "NX", "EX", 10);
    
    if (locked) {
        try {
            // 3. 获取锁成功，再次检查缓存（双重检查）
            cached = redis.get(key);
            if (cached != null) {
                return JSON.parseObject(cached, User.class);
            }
            
            // 4. 查数据库
            User user = userMapper.selectById(userId);
            
            // 5. 写入缓存
            redis.setex(key, 3600, JSON.toJSONString(user));
            return user;
        } finally {
            // 6. 释放锁
            redis.del(lockKey);
        }
    } else {
        // 7. 获取锁失败，等待后重试
        try {
            Thread.sleep(50);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        return getHotUser(userId);  // 递归重试
    }
}
```

**执行流程**：

```
┌─────────────────────────────────────────────────────────────┐
│                   互斥锁执行流程                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   请求 1 ──→ Redis miss ──→ 获取锁成功 ──→ 查 MySQL ──→ 写缓存 ──→ 返回  │
│                                                             │
│   请求 2 ──→ Redis miss ──→ 获取锁失败 ──→ sleep 50ms ──→ 重试  │
│                                        ──→ Redis hit ──→ 返回  │
│                                                             │
│   请求 3 ──→ Redis miss ──→ 获取锁失败 ──→ sleep 50ms ──→ 重试  │
│                                        ──→ Redis hit ──→ 返回  │
│                                                             │
│   请求 N ──→ Redis miss ──→ 获取锁失败 ──→ sleep 50ms ──→ 重试  │
│                                        ──→ Redis hit ──→ 返回  │
│                                                             │
│   核心：只有一个请求查数据库，其他请求等待后读缓存              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**优点**：
- 只有一个请求打到数据库，保护数据库
- 数据一致性好

**缺点**：
- 其他请求需要等待，**响应时间变长**
- 如果持锁者挂了（锁未释放），其他请求会一直重试（需要设置锁的自动过期时间）

### 2.4 解决方案二：逻辑过期

**思路**：不设置物理 TTL，在 Value 中记录逻辑过期时间。发现逻辑过期后，异步刷新缓存。

```java
// 缓存 Value 结构
public class CacheData<T> {
    private T data;              // 实际数据
    private long expireTime;     // 逻辑过期时间（时间戳）
    // getter/setter...
}

public User getWithLogicalExpire(Long userId) {
    String key = "user:" + userId;
    String json = redis.get(key);
    
    if (json == null) {
        return null;  // 缓存不存在（理论上不会，因为不设物理 TTL）
    }
    
    CacheData<User> cacheData = JSON.parseObject(json, 
        new TypeReference<CacheData<User>>(){});
    
    // 1. 未逻辑过期，直接返回
    if (cacheData.getExpireTime() > System.currentTimeMillis()) {
        return cacheData.getData();
    }
    
    // 2. 已逻辑过期，尝试获取互斥锁
    String lockKey = "lock:user:" + userId;
    boolean locked = redis.set(lockKey, "1", "NX", "EX", 10);
    
    if (locked) {
        // 3. 获取锁成功，开启异步线程刷新缓存
        CACHE_REFRESH_EXECUTOR.submit(() -> {
            try {
                User user = userMapper.selectById(userId);
                CacheData<User> newData = new CacheData<>(
                    user, System.currentTimeMillis() + 3600_000);
                redis.set(key, JSON.toJSONString(newData));  // 不设物理 TTL
            } finally {
                redis.del(lockKey);
            }
        });
    }
    
    // 4. 无论是否获取锁，都返回旧数据（牺牲一致性换可用性）
    return cacheData.getData();
}
```

**执行流程**：

```
┌─────────────────────────────────────────────────────────────┐
│                   逻辑过期执行流程                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   缓存 Value：{ data: User, expireTime: 1700000000000 }     │
│   （不设物理 TTL，永远不过期）                                 │
│                                                             │
│   请求 1 ──→ 查到缓存 ──→ 检查 expireTime                    │
│              ├─ 未过期 → 直接返回 ✓                           │
│              └─ 已过期 → 获取锁 → 异步刷新 ──→ 返回旧数据 ✓     │
│                                                             │
│   请求 2 ──→ 查到缓存 ──→ 检查 expireTime                    │
│              └─ 已过期 → 获取锁失败 ──→ 返回旧数据 ✓           │
│                                                             │
│   请求 3 ──→ 查到缓存 ──→ 检查 expireTime                    │
│              └─ 已过期 → 获取锁失败 ──→ 返回旧数据 ✓           │
│                                                             │
│   特点：                                                     │
│   ✓ 所有请求都能立即响应（不等待）                             │
│   ✓ 只有一个异步线程刷新缓存                                  │
│   ✗ 短暂返回旧数据（最终一致）                                │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**优点**：
- 不会有任何请求等待，**响应时间稳定**
- 不会打到数据库

**缺点**：
- 短暂返回旧数据（**最终一致**而非强一致）
- 需要预先加载缓存（否则缓存不存在）
- 实现较复杂

### 2.5 解决方案三：热点 Key 永不过期

**思路**：对于极热点的 Key（如首页推荐），干脆不设置过期时间，通过后台定时任务主动刷新。

```java
// 后台定时刷新任务
@Scheduled(fixedRate = 1800000)  // 每 30 分钟刷新一次
public void refreshHotKeys() {
    List<String> hotKeys = getHotKeys();  // 从监控中获取热点 Key
    for (String key : hotKeys) {
        Object data = loadFromDB(key);
        redis.set(key, JSON.toJSONString(data));  // 不设 TTL
    }
}
```

**优点**：不会击穿
**缺点**：数据可能有延迟（不是最新），需要主动管理刷新

### 2.6 击穿方案对比

| 方案 | 一致性 | 可用性 | 复杂度 | 适用场景 |
|------|--------|--------|--------|----------|
| **互斥锁** | 强 | 一般（等待） | 中 | 数据一致性要求高 |
| **逻辑过期** | 最终 | 高 | 高 | 热点数据、容忍短暂不一致 |
| **永不过期** | 最终 | 极高 | 低 | 极热点数据（首页推荐等） |

## 3. 缓存雪崩：大量 Key 同时失效

### 3.1 什么是缓存雪崩

**缓存雪崩**是指**大量 Key 在同一时间过期**，或者 **Redis 服务宕机**，导致大量请求打到数据库，数据库被压垮。

```
┌─────────────────────────────────────────────────────────────┐
│                      缓存雪崩流程                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   场景一：大量 Key 同时过期                                   │
│                                                             │
│   T0 时刻：10000 个 Key 同时过期（TTL 相同）                   │
│   T+0.001s: 10000 请求全部 miss → 10000 请求打到 MySQL         │
│   → MySQL 连接池耗尽 → 服务不可用                              │
│                                                             │
│   ┌────────────────────────────────────────────┐             │
│   │  Redis                                       │             │
│   │  key1: expired  ──×──→ MySQL  ──→ 请求 1     │             │
│   │  key2: expired  ──×──→ MySQL  ──→ 请求 2     │             │
│   │  key3: expired  ──×──→ MySQL  ──→ 请求 3     │             │
│   │  ...                                        │             │
│   │  keyN: expired  ──×──→ MySQL  ──→ 请求 N     │             │
│   └────────────────────────────────────────────┘             │
│                                                             │
│   场景二：Redis 宕机                                         │
│                                                             │
│   Redis 挂了 → 所有请求 miss → 全部打到 MySQL → MySQL 崩溃     │
│   → 连锁反应 → 整个系统雪崩                                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 雪崩 vs 击穿的区别

| 维度 | 缓存击穿 | 缓存雪崩 |
|------|----------|----------|
| **失效 Key 数量** | 1 个热点 Key | 大量 Key |
| **影响范围** | 单个热点数据 | 大面积数据 |
| **触发条件** | 热点 Key 过期 | 大量 Key 同时过期 / Redis 宕机 |
| **危害程度** | 较大 | 极大（可能导致系统雪崩） |

### 3.3 解决方案一：随机 TTL

**思路**：给每个 Key 的 TTL 加上随机值，避免同时过期。

```java
// 错误做法：所有 Key 设相同 TTL
redis.setex(key, 3600, value);  // 1 小时后同时过期！

// 正确做法：TTL 加随机偏移
int baseTTL = 3600;  // 基础 TTL 1 小时
int randomTTL = baseTTL + ThreadLocalRandom.current().nextInt(600);  // 1~1.1 小时
redis.setex(key, randomTTL, value);
```

```java
// 更通用的做法：封装一个工具方法
public void setWithRandomTTL(String key, String value, 
                              int baseTTL, int randomRange) {
    int ttl = baseTTL + ThreadLocalRandom.current().nextInt(randomRange);
    redis.setex(key, ttl, value);
}

// 批量预热时使用
public void preloadCache(List<User> users) {
    for (User user : users) {
        String key = "user:" + user.getId();
        // 基础 TTL 1 小时，随机增加 0~10 分钟
        setWithRandomTTL(key, JSON.toJSONString(user), 3600, 600);
    }
}
```

### 3.4 解决方案二：多级缓存

**思路**：在 Redis 之外增加本地缓存（如 Caffeine），即使 Redis 宕机，本地缓存仍能扛住部分流量。

```
┌─────────────────────────────────────────────────────────────┐
│                     多级缓存架构                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   请求                                                       │
│     │                                                       │
│     ▼                                                       │
│   ┌──────────────────┐                                      │
│   │  L1: 本地缓存      │  Caffeine / Guava Cache              │
│   │  （进程内）         │  TTL: 60s，容量：10000               │
│   └────────┬─────────┘                                      │
│            │ miss                                            │
│            ▼                                                 │
│   ┌──────────────────┐                                      │
│   │  L2: Redis 缓存   │  分布式缓存                           │
│   │  （跨进程）         │  TTL: 3600s                         │
│   └────────┬─────────┘                                      │
│            │ miss                                            │
│            ▼                                                 │
│   ┌──────────────────┐                                      │
│   │  MySQL 数据库      │                                      │
│   └──────────────────┘                                      │
│                                                             │
│   Redis 宕机时：L1 本地缓存仍能扛住部分流量                     │
│   → 减轻 MySQL 压力 → 防止雪崩                                │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

```java
// Spring Boot + Caffeine + Redis 多级缓存实现
@Configuration
public class CacheConfig {
    
    @Bean
    public Cache<String, String> localCache() {
        return Caffeine.newBuilder()
            .maximumSize(10000)
            .expireAfterWrite(60, TimeUnit.SECONDS)
            .build();
    }
}

@Service
public class MultiLevelCacheService {
    
    @Autowired
    private Cache<String, String> localCache;  // L1
    
    @Autowired
    private RedisTemplate<String, String> redisTemplate;  // L2
    
    @Autowired
    private UserMapper userMapper;
    
    public User getUser(Long userId) {
        String key = "user:" + userId;
        
        // 1. L1 本地缓存
        String cached = localCache.getIfPresent(key);
        if (cached != null) {
            return JSON.parseObject(cached, User.class);
        }
        
        // 2. L2 Redis 缓存
        cached = redisTemplate.opsForValue().get(key);
        if (cached != null) {
            localCache.put(key, cached);  // 回填 L1
            return JSON.parseObject(cached, User.class);
        }
        
        // 3. MySQL
        User user = userMapper.selectById(userId);
        if (user != null) {
            String json = JSON.toJSONString(user);
            redisTemplate.opsForValue().set(key, json, 3600, TimeUnit.SECONDS);
            localCache.put(key, json);  // 回填 L1
        }
        return user;
    }
}
```

### 3.5 解决方案三：熔断降级

**思路**：当数据库压力过大时，通过熔断器保护数据库，返回降级数据。

```java
@Service
public class UserServiceWithCircuitBreaker {
    
    @CircuitBreaker(fallbackMethod = "fallbackUser")
    @Cacheable(value = "user", key = "#userId")
    public User getUser(Long userId) {
        return userMapper.selectById(userId);
    }
    
    // 降级方法：返回默认用户或缓存中的旧数据
    public User fallbackUser(Long userId, Exception e) {
        // 返回降级数据
        User defaultUser = new User();
        defaultUser.setId(userId);
        defaultUser.setName("系统繁忙，请稍后重试");
        defaultUser.setAvatar("/default-avatar.png");
        return defaultUser;
    }
}
```

### 3.6 解决方案四：Redis 高可用

防止 Redis 宕机导致的雪崩：

| 方案 | 说明 | 适用场景 |
|------|------|----------|
| **主从 + Sentinel** | 主节点宕机自动切换从节点 | 中小规模 |
| **Redis Cluster** | 多节点分片，部分宕机不影响 | 大规模 |
| **同城双活** | 两个机房各部署一套 Redis | 容灾要求高 |

### 3.7 雪崩方案对比

| 方案 | 解决的问题 | 优点 | 缺点 |
|------|------------|------|------|
| **随机 TTL** | Key 同时过期 | 实现简单 | 不防 Redis 宕机 |
| **多级缓存** | Key 过期 + Redis 宕机 | 多重防护 | 本地缓存一致性 |
| **熔断降级** | 数据库压力过大 | 保护数据库 | 用户体验降级 |
| **Redis 高可用** | Redis 宕机 | 根本解决 | 成本高 |

# 第二部分：缓存一致性

## 5. Cache Aside Pattern（旁路缓存）

### 5.1 四种缓存策略

```
┌─────────────────────────────────────────────────────────────┐
│                   四种缓存读写策略                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. Cache Aside（旁路缓存）—— 最常用                         │
│     读：先查缓存，miss 再查 DB，然后回写缓存                   │
│     写：先更新 DB，再删除缓存                                  │
│                                                             │
│  2. Read Through（读穿透）                                   │
│     读：只查缓存，缓存 miss 时由缓存服务查 DB 并回写           │
│     写：不操作                                                │
│                                                             │
│  3. Write Through（写穿透）                                  │
│     读：查缓存                                                │
│     写：同时写缓存和 DB（同步）                                │
│                                                             │
│  4. Write Behind / Write Back（写回）                        │
│     读：查缓存                                                │
│     写：只写缓存，异步刷 DB                                    │
│     （性能最高，但宕机可能丢数据）                             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 Cache Aside 的并发问题

**Cache Aside** 是最常用的策略：**读时查缓存→查 DB→回写缓存；写时更新 DB→删除缓存。**

但即使是最常用策略，在并发场景下也有一致性问题：

#### 5.2.1 问题一：先删缓存再更新 DB

```
┌─────────────────────────────────────────────────────────────┐
│           先删缓存再更新 DB 的问题                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   线程 A（写）        线程 B（读）        缓存       数据库    │
│      │                   │                  │          │      │
│      │ 删除缓存           │                  │ ← del    │      │
│      │──────────────────→│                  │          │      │
│      │                   │                  │          │      │
│      │ 更新 DB            │                  │          │      │
│      │──────────────────────────────────────────────→ UPDATE  │
│      │（执行中...）       │ 查缓存 miss       │          │      │
│      │                   │←─────────────────│          │      │
│      │                   │ 查 DB（旧值）      │          │      │
│      │                   │────────────────────────────→SELECT│
│      │                   │←─────────────────────────── 旧值   │
│      │                   │ 写缓存（旧值！）    │          │      │
│      │                   │──────────────────→│ SET 旧值 │      │
│      │                   │                  │          │      │
│      │ 更新 DB 完成       │                  │          │      │
│      │←────────────────────────────────────────────── DONE   │
│      │                   │                  │          │ 新值 │
│      │                   │                  │ 旧值！    │      │
│                                                             │
│   结果：缓存中是旧值，DB 中是新值 → 数据不一致！               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**结论**：**先删缓存再更新 DB 是错误的**！读线程可能在 DB 更新完成前查到旧值并写入缓存，导致缓存长时间不一致（直到 TTL 过期）。

#### 5.2.2 问题二：先更新 DB 再删缓存

```
┌─────────────────────────────────────────────────────────────┐
│           先更新 DB 再删缓存（推荐）                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   线程 A（写）        线程 B（读）        缓存       数据库    │
│      │                   │                  │          │      │
│      │ 更新 DB            │                  │          │      │
│      │──────────────────────────────────────→ UPDATE     │    │
│      │ 更新完成           │                  │          │ 新值 │
│      │←────────────────────────────────────── DONE       │    │
│      │                   │                  │          │      │
│      │ 删除缓存           │                  │          │      │
│      │──────────────────→│                  │ ← del    │      │
│      │                   │ 查缓存 miss       │          │      │
│      │                   │←─────────────────│          │      │
│      │                   │ 查 DB（新值）      │          │      │
│      │                   │────────────────────────────→SELECT│
│      │                   │←─────────────────────────── 新值   │
│      │                   │ 写缓存（新值）     │          │      │
│      │                   │──────────────────→│ SET 新值 │      │
│      │                   │                  │          │      │
│                                                             │
│   结果：缓存和 DB 都是新值 → 数据一致！                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**但这种方案也有极小概率出问题**：

```
┌─────────────────────────────────────────────────────────────┐
│     先更新 DB 再删缓存的极小概率问题                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   线程 A（读）        线程 B（写）        缓存       数据库    │
│      │                   │                  │          │      │
│      │ 查缓存 miss       │                  │          │      │
│      │←─────────────────│                  │          │      │
│      │ 查 DB（旧值）      │                  │          │      │
│      │──────────────────────────────────────→ SELECT 旧值│    │
│      │（CPU 时间片用完）  │                  │          │      │
│      │     ↓              │ 更新 DB           │          │      │
│      │     │              │──────────────────────────→UPDATE  │
│      │     │              │ 更新完成          │          │ 新值 │
│      │     │              │←───────────────────────────DONE   │
│      │     │              │ 删除缓存          │          │      │
│      │     │              │──────────────────→│ ← del  │      │
│      │     ↓              │                  │          │      │
│      │ 写缓存（旧值！）    │                  │          │      │
│      │──────────────────→│                  │ SET 旧值 │      │
│      │                   │                  │ 旧值！    │      │
│                                                             │
│   结果：缓存中是旧值！                                        │
│   但概率极低：读线程必须在查 DB 后被挂起，                      │
│   写线程在这个间隙完成更新+删缓存，                             │
│   然后读线程恢复并写入旧值                                    │
│                                                             │
│   缓解方案：延迟双删                                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 5.3 结论

| 策略 | 操作顺序 | 问题 | 推荐度 |
|------|----------|------|--------|
| 先删缓存再更新 DB | del cache → update DB | 高概率不一致 | ✗ 不推荐 |
| 先更新 DB 再删缓存 | update DB → del cache | 极低概率不一致 | ✓ 推荐 |
| 先更新 DB 再更新缓存 | update DB → set cache | 并发写顺序不确定 | ✗ 不推荐 |

**业界共识**：先更新 DB 再删缓存 + 延迟双删兜底。

## 6. 延迟双删策略

### 6.1 延迟双删原理

**思路**：先删缓存 → 更新 DB → 延迟一段时间后再删一次缓存。

```java
public void updateUser(User user) {
    String key = "user:" + user.getId();
    
    // 1. 第一次删除缓存
    redis.del(key);
    
    // 2. 更新数据库
    userMapper.updateById(user);
    
    // 3. 延迟第二次删除（异步）
    CompletableFuture.runAsync(() -> {
        try {
            Thread.sleep(500);  // 延迟 500ms
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        redis.del(key);
    });
}
```

```
┌─────────────────────────────────────────────────────────────┐
│                   延迟双删执行流程                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   时间线                                                     │
│                                                             │
│   T0:   删除缓存（第一次删）                                   │
│   T1:   更新 DB                                               │
│   T2:   DB 更新完成                                            │
│         此时有其他线程可能把旧值写入缓存                        │
│   T3:   延迟 500ms 后再次删除缓存（第二次删）                   │
│         → 清除可能被其他线程写入的旧值                           │
│   T4:   后续读请求会 miss → 查 DB（新值）→ 写缓存（新值）       │
│                                                             │
│   延迟时间的选择：                                            │
│   - 需要大于一次读请求的耗时（查 DB + 写缓存）                  │
│   - 通常 500ms ~ 1s 足够                                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 6.2 延迟时间如何选择

```
延迟时间 > 读请求的耗时

读请求耗时 = 查缓存 miss + 查 DB + 写缓存
          ≈ 1ms + 5ms + 1ms = 7ms

但考虑到网络延迟、GC 停顿、线程调度等：
  - 保守值：500ms
  - 推荐值：1s
  - 特殊场景（读写分离延迟大）：2~5s
```

### 6.3 延迟双删的问题

| 问题 | 说明 | 解决方案 |
|------|------|----------|
| **延迟时间难定** | 太短不够，太长浪费 | 监控读请求 P99 耗时 |
| **第二次删除可能失败** | Redis 网络问题 | 重试机制 / 消息队列 |
| **增加写延迟** | 第二次删是异步的 | 不影响主流程 |
| **不保证强一致** | 最终一致 | 对强一致场景用分布式事务 |

### 7.3 Canal + Redis 代码示例

```java
// Canal Client 消费 Binlog 变更
@Component
public class CanalClient {
    
    @Autowired
    private RedisTemplate<String, String> redisTemplate;
    
    private CanalConnector connector;
    
    @PostConstruct
    public void init() {
        // 创建 Canal 连接
        connector = CanalConnectors.newSingleConnector(
            new InetSocketAddress("127.0.0.1", 11111),
            "example", "", ""
        );
        connector.connect();
        connector.subscribe(".*\\..*");  // 订阅所有库所有表
    }
    
    @Scheduled(fixedDelay = 100)  // 每 100ms 拉取一次
    public void process() {
        Message message = connector.getWithoutAck(1000);  // 批量获取
        long batchId = message.getId();
        int size = message.getEntries().size();
        
        if (batchId != -1 && size > 0) {
            for (Entry entry : message.getEntries()) {
                if (entry.getEntryType() == EntryType.ROWDATA) {
                    RowChange rowChange = RowChange.parseFrom(entry.getStoreValue());
                    
                    for (RowData rowData : rowChange.getRowDatasList()) {
                        String tableName = entry.getHeader().getTableName();
                        
                        // 根据表名处理缓存
                        if ("t_user".equals(tableName)) {
                            handleUserCache(rowChange, rowData);
                        }
                    }
                }
            }
        }
        connector.ack(batchId);  // 确认消费
    }
    
    private void handleUserCache(RowChange rowChange, RowData rowData) {
        EventType eventType = rowChange.getEventType();
        
        // 获取主键 ID
        List<Column> columns = eventType == EventType.DELETE 
            ? rowData.getBeforeColumnsList() 
            : rowData.getAfterColumnsList();
        
        Long userId = columns.stream()
            .filter(c -> c.getName().equals("id"))
            .map(c -> Long.parseLong(c.getValue()))
            .findFirst().orElse(null);
        
        if (userId != null) {
            // 删除缓存
            redisTemplate.delete("user:" + userId);
        }
    }
}
```

| 方案 | 一致性 | 实现复杂度 | 性能影响 | 适用场景 |
|------|--------|------------|----------|----------|
| **先更新 DB 再删缓存** | 最终一致 | 低 | 低 | 大多数场景 |

**生产推荐**：先更新 DB 再删缓存 + 延迟双删（兜底），对一致性要求极高的场景加 Canal。

### 9.2 分布式锁的三个核心要求

```
┌─────────────────────────────────────────────────────────────┐
│              分布式锁三大核心要求                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   1. 互斥性（Mutual Exclusion）                              │
│      同一时刻只有一个客户端能持有锁                            │

│   4. 高可用（High Availability）                             │
│      锁服务本身不能是单点故障                                 │
│                                                             │
│   5. 高性能（High Performance）                              │
│      加锁/解锁操作要快                                         │
│                                                             │
│   6. 阻塞/非阻塞                                             │
│      支持阻塞等待和立即返回两种模式                           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 10. SETNX 实现与问题

### 10.1 SETNX 命令

```bash
# SETNX = Set if Not eXists
SETNX key value
# 返回 1：设置成功（获取锁成功）
# 返回 0：设置失败（锁已被其他人持有）

# 获取锁
SETNX mylock "thread_1"    # → 1（成功）

# 其他人获取锁
SETNX mylock "thread_2"    # → 0（失败，锁已被持有）

# 释放锁
DEL mylock                  # → 1（删除成功）
```

### 10.2 SETNX 的问题：死锁

```
┌─────────────────────────────────────────────────────────────┐
│                SETNX 死锁问题                                 │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   线程 A                                     │
│     │ SETNX lock "A" → 1（获取锁成功）                        │
│     │ 执行业务逻辑...                                         │
│     ✗ 线程 A 挂了（OOM、机器宕机等）                           │
│     │ 没有执行 DEL lock                                       │
│     │                                                       │
│   线程 B                                                    │
│     │ SETNX lock "B" → 0（获取锁失败）                        │
│     │ 重试... SETNX lock "B" → 0（还是失败）                  │
│     │ 永远获取不到锁！→ 死锁！                                 │
│                                                             │
│   原因：锁没有过期时间，持有者宕机后锁永远不释放               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 10.3 第一次改进：SETNX + EXPIRE

```bash
# 先获取锁
SETNX lock "thread_A"       # → 1（成功）
# 再设置过期时间
EXPIRE lock 30              # 30 秒后自动过期

# 问题：SETNX 和 EXPIRE 是两条命令，不是原子操作！
# 如果 SETNX 成功后、EXPIRE 执行前进程挂了 → 还是死锁！
```

```
┌─────────────────────────────────────────────────────────────┐
│           SETNX + EXPIRE 非原子性问题                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   线程 A                                                    │
│     │ SETNX lock "A" → 1（成功）                             │
│     │ ✗ 进程挂了（EXPIRE 没执行）                              │
│     │                                                       │
│   → lock 永远不过期 → 死锁！                                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 11. SET NX EX 原子加锁

### 11.1 原子加锁命令

Redis 2.6.12+ 支持在 SET 命令中直接附加 NX 和 EX 参数：

```bash
# 原子操作：不存在才设置，同时设置过期时间
SET key value NX EX 30
# NX：Not eXists，不存在才设置
# EX 30：过期时间 30 秒
# 返回 OK：成功
# 返回 nil：失败（锁已被持有）

# 获取锁（原子操作）
SET lock "thread_A" NX EX 30   # → OK（成功）

# 释放锁
DEL lock                        # → 1（成功）
```

### 11.2 新问题：锁被别人释放

```
┌─────────────────────────────────────────────────────────────┐
│               锁被别人释放的问题                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   线程 A                                                    │
│     │ SET lock "A" NX EX 30 → OK（获取锁，30s 过期）          │
│     │ 执行业务（耗时 35s）                                     │
│     │                                                       │
│   线程 B                                                    │
│     │ SET lock "B" NX EX 30 → nil（锁还在，获取失败）         │
│     │ 重试...                                                │
│     │ 30s 后锁自动过期                                        │
│     │ SET lock "B" NX EX 30 → OK（获取锁成功！）              │
│     │                                                       │
│   线程 A（终于执行完了）                                      │
│     │ DEL lock → 1（删除成功）                                │
│     │                                                       │
│   → 线程 A 删除了线程 B 的锁！                                │
│   → 线程 B 以为持有锁，但锁已被释放                            │
│   → 又会导致其他线程获取锁成功 → 并发问题！                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 11.3 第二次改进：Value 设为唯一标识

```java
public class RedisLock {
    
    private Jedis jedis;
    
    public boolean tryLock(String lockKey, int expireSeconds) {
        // 生成唯一标识（UUID + 线程 ID）
        String requestId = UUID.randomUUID() + ":" + Thread.currentThread().getId();
        
        // SET key value NX EX（原子操作）
        String result = jedis.set(lockKey, requestId, "NX", "EX", expireSeconds);
        return "OK".equals(result);
    }
    
    public boolean unlock(String lockKey, String requestId) {
        // 释放锁前先检查 value 是否匹配
        String currentValue = jedis.get(lockKey);
        if (requestId.equals(currentValue)) {
            jedis.del(lockKey);
            return true;
        }
        return false;  // 锁已被其他人持有，不能释放
    }
}
```

### 11.4 新问题：Get + Del 非原子性

### 11.5 第三次改进：Lua 脚本原子释放

```lua
-- 释放锁的 Lua 脚本（原子操作）
-- KEYS[1] = lockKey
-- ARGV[1] = requestId

if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

```java
public boolean unlock(String lockKey, String requestId) {
    String luaScript = 
        "if redis.call('get', KEYS[1]) == ARGV[1] then " +
        "  return redis.call('del', KEYS[1]) " +
        "else " +
        "  return 0 " +
        "end";
    
    Object result = jedis.eval(luaScript, 
        Collections.singletonList(lockKey),
        Collections.singletonList(requestId));
    
    return Long.valueOf(1).equals(result);
}
```

## 12. 锁续期问题（看门狗）

### 12.1 锁过期的问题

```
┌─────────────────────────────────────────────────────────────┐
│                  锁过期问题                                   │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   线程 A                                                    │
│     │ T0: SET lock "A" NX EX 30 → OK                        │
│     │ T0~T25s: 执行业务（比预期慢）                           │
│     │ T30s: 锁自动过期！                                      │
│     │                                                        │
│   线程 B                                                    │
│     │ T31s: SET lock "B" NX EX 30 → OK（获取锁成功）         │
│     │ T31s~T60s: 执行业务                                    │
│     │                                                        │
│   线程 A                                                    │
│     │ T35s: 业务执行完成                                      │
│     │ T35s: DEL lock（如果是 Lua 脚本，不会误删）             │
│     │     → 但线程 A 和线程 B 同时执行了业务！                 │
│     │                                                        │
│   问题：锁在 30s 时过期，但业务到 35s 才完成                   │
│   → 30~35s 之间线程 B 获取了锁 → 并发执行！                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 12.2 看门狗机制

**看门狗**是一个后台线程，定期检查持锁线程是否还在执行，如果在执行就自动续期。

```
┌─────────────────────────────────────────────────────────────┐
│                   看门狗机制                                  │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   线程 A                    看门狗线程                       │
│     │                         │                             │
│   T0: 加锁成功，TTL=30s         │                             │
│     │                         │                             │
│     │ 执行业务...              T10: 检查线程 A 还活着          │
│     │                         │     → 续期 EXPIRE lock 30   │
│     │                         │     → TTL 恢复为 30s        │
│     │                         │                             │
│     │ 执行业务...              T20: 检查线程 A 还活着          │
│     │                         │     → 续期 EXPIRE lock 30   │
│     │                         │     → TTL 恢复为 30s        │
│     │                         │                             │
│   T25: 业务完成               T25: 检查线程 A 不再持锁        │
│     │ DEL lock（Lua 释放）     │     → 停止续期               │
│     │                         │                             │
│   如果线程 A 宕机：            T10: 检查线程 A 已死            │
│     → 看门狗也停了              │     → 不再续期               │
│     → 锁在 30s 后自动过期       │     → 锁 30s 后自动释放      │
│     → 防死锁！                  │                             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 12.3 看门狗的关键参数

```
默认配置（Redisson）：
  lockWatchdogTimeout = 30s     → 锁的初始 TTL
  续期间隔 = TTL / 3 = 10s      → 每 10s 检查并续期一次
  
续期时序：
  T0:   加锁，TTL = 30s
  T10:  续期，TTL = 30s（重置）
  T20:  续期，TTL = 30s（重置）
  T30:  续期，TTL = 30s（重置）
  ...
  
如果持锁线程宕机：
  T0:   加锁，TTL = 30s
  T10:  看门狗也停了（不续期）
  T30:  锁自动过期 → 其他线程可获取
```

## 13. Redlock 算法

### 13.1 为什么需要 Redlock

单 Redis 实例的分布式锁存在**主从切换丢锁**的问题：

```
┌─────────────────────────────────────────────────────────────┐
│              主从切换丢锁问题                                 │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   1. 客户端在 Master 上加锁成功                               │
│      Master: SET lock "A" NX EX 30 → OK                     │
│                                                             │
│   2. Master 将锁同步到 Slave（异步复制）                      │
│      Master → Slave（复制中...）                              │
│                                                             │
│   3. Master 宕机！                                           │
│      复制还没完成，Slave 上没有这把锁                          │
│                                                             │
│   4. Sentinel 将 Slave 提升为新 Master                        │
│      新 Master 上没有这把锁！                                 │
│                                                             │
│   5. 客户端 B 在新 Master 上加锁成功                          │
│      SET lock "B" NX EX 30 → OK                              │
│                                                             │
│   → 两个客户端同时持有锁！锁失效！                             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 13.2 Redlock 算法流程

**Redlock** 由 Redis 作者 Antirez 提出，使用多个**独立的 Redis 实例**（不是主从），通过过半成功来保证锁的可靠性。

```
┌─────────────────────────────────────────────────────────────┐
│                   Redlock 算法流程                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   假设有 5 个独立的 Redis 实例（N=5，过半数=3）              │
│                                                             │
│   客户端                                                    │
│     │                                                       │
│     │ 1. 记录开始时间 T_start                                │
│     │                                                       │
│     │ 2. 依次向 5 个实例发送加锁请求                           │
│     │    SET lock "uuid" NX EX 30                           │
│     │                                                       │
│     │    Redis 1: → OK  ✓                                    │
│     │    Redis 2: → OK  ✓                                    │
│     │    Redis 3: → nil ✗（锁已被其他人持有）                  │
│     │    Redis 4: → OK  ✓                                    │
│     │    Redis 5: → OK  ✓                                    │
│     │                                                       │
│     │ 3. 4/5 成功 ≥ 3（过半）→ 加锁成功！                     │
│     │                                                       │
│     │ 4. 计算锁的实际有效时间                                 │
│     │    elapsed = T_now - T_start                           │
│     │    lock_validity = TTL - elapsed                       │
│     │    如果 lock_validity > 0 → 锁有效                     │
│     │    如果 lock_validity ≤ 0 → 锁无效（耗时太长）          │
│     │                                                       │
│     │ 5. 加锁失败时：向所有实例发送 DEL                       │
│     │    （即使有些实例没加锁成功，也发送 DEL 避免残留）       │
│     │                                                       │
│   释放锁：                                                   │
│     向所有实例发送 Lua 脚本释放锁                             │
│     （不管之前是否加锁成功，都尝试释放）                       │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 13.3 Redlock 的关键细节

```
1. 为什么是 5 个实例？
   - N 个实例，需要 ⌈N/2 + 1⌉ 个成功
   - 5 个实例需要 3 个成功（容忍 2 个故障）
   - 3 个实例需要 2 个成功（容忍 1 个故障）
   - 更多实例 → 更高可用性，但性能更低

2. 为什么有超时计算？
   - 如果加锁过程耗时超过 TTL，锁可能已经过期
   - 此时加锁"成功"但没有意义 → 必须释放

3. 加锁请求要设置超时
   - 单个请求超时：几十毫秒
   - 如果某个实例响应慢，不能阻塞太久

4. 实例必须独立
   - 5 个实例不能是主从关系
   - 独立部署、独立网络、独立电源
```

### 13.4 Redlock 的争议

Martin Kleppmann（《Designing Data-Intensive Applications》作者）对 Redlock 的质疑：

```
┌─────────────────────────────────────────────────────────────┐
│               Redlock 争议                                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   Martin Kleppmann 的质疑：                                   │
│                                                             │
│   场景：客户端 A 获取锁后，发生 GC 停顿                        │
│   1. 客户端 A 加锁成功，TTL=10s                               │
│   2. GC Stop-the-World 60s                                   │
│   3. 锁 10s 后过期                                           │
│   4. 客户端 B 加锁成功                                        │
│   5. GC 结束，客户端 A 认为自己还持有锁                        │
│   6. 两个客户端同时操作共享资源！                              │
│                                                             │
│   核心问题：                                                  │
│   Redlock 依赖时钟同步，但分布式系统时钟不保证精确同步          │
│   GC 停顿、进程暂停、时钟漂移都可能导致锁失效                  │
│                                                             │
│   Martin 的建议：                                             │
│   使用 fencing token（递增序号）                              │
│   每次加锁返回一个递增的 token，操作资源时带上 token          │
│   资源服务端拒绝旧 token 的请求                                │
│                                                             │
│   Antirez 的回应：                                            │
│   - GC 停顿是极端场景                                        │
│   - Redis 单线程模型可以保证 fencing token                    │
│   - Redlock 在实践中足够可靠                                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 13.5 Redlock 结论

| 场景 | 推荐 |
|------|------|
| 短时间持锁（秒级）、可容忍极小概率错误 | Redisson（单 Redis + 看门狗） |
| 需要更高可靠性 | Redlock（多 Redis 实例） |
| 强一致性要求（如金融） | Zookeeper / etcd（CP 系统） |
| 性能优先 | Redis 分布式锁 |

### 14.2 tryLock 源码分析

```java
// Redisson.tryLock() 核心源码（简化版）

public class RedissonLock implements RLock {
    
    // 看门狗超时时间（默认 30 秒）
    protected long lockWatchdogTimeout = 30_000;
    
    // 看门狗续期间隔 = TTL / 3 = 10 秒
    protected long internalLockLeaseTime;
    
    @Override
    public boolean tryLock(long waitTime, long leaseTime, TimeUnit unit) throws InterruptedException {
        long time = unit.toMillis(waitTime);
        long current = System.currentTimeMillis();
        long threadId = Thread.currentThread().getId();
        
        // 1. 尝试获取锁
        Long ttl = tryAcquire(waitTime, leaseTime, unit, threadId);
        
        // ttl == null 表示获取锁成功
        if (ttl == null) {
            return true;
        }
        
        // 2. 获取锁失败，计算剩余等待时间
        time -= System.currentTimeMillis() - current;
        if (time <= 0) {
            // 等待超时
            acquireFailed(threadId);
            return false;
        }
        
        // 3. 订阅锁释放消息（通过 Redis Pub/Sub）
        //    当其他线程释放锁时，会发布消息通知等待线程
        RFuture<RedissonLockEntry> subscribeFuture = subscribe(threadId);
        if (!await(subscribeFuture, time, TimeUnit.MILLISECONDS)) {
            // 等待锁释放超时
            return false;
        }
        
        // 4. 循环尝试获取锁
        while (true) {
            long currentTime = System.currentTimeMillis();
            ttl = tryAcquire(waitTime, leaseTime, unit, threadId);
            
            if (ttl == null) {
                return true;  // 获取锁成功
            }
            
            time -= System.currentTimeMillis() - currentTime;
            if (time <= 0) {
                acquireFailed(threadId);
                return false;  // 等待超时
            }
            
            // 5. 等待锁释放（最多等 ttl 时间）
            //    使用 Semaphore 实现信号量等待
            try {
                threadSemaphore.acquire();  // 阻塞等待
            } catch (InterruptedException e) {
                // ...
            }
        }
    }
    
    private Long tryAcquire(long waitTime, long leaseTime, TimeUnit unit, long threadId) {
        return tryAcquireAsync(waitTime, leaseTime, unit, threadId).getNow();
    }
    
    private RFuture<Long> tryAcquireAsync(long waitTime, long leaseTime, 
                                          TimeUnit unit, long threadId) {
        // 如果指定了 leaseTime，不会启动看门狗
        if (leaseTime != -1) {
            return tryLockInnerAsync(waitTime, leaseTime, unit, threadId, RedisCommands.EVAL_LONG);
        }
        
        // 没有指定 leaseTime，使用看门狗默认时间
        RFuture<Long> ttlRemainingFuture = tryLockInnerAsync(
            waitTime, 
            commandExecutor.getConnectionManager().getCfg().getLockWatchdogTimeout(),
            TimeUnit.MILLISECONDS, 
            threadId, 
            RedisCommands.EVAL_LONG
        );
        
        ttlRemainingFuture.onComplete((ttl, e) -> {
            if (e != null) {
                return;
            }
            
            // 加锁成功，启动看门狗
            if (ttl == null) {
                scheduleExpirationRenewal(threadId);
            }
        });
        
        return ttlRemainingFuture;
    }
}
```

### 14.3 tryLockInnerAsync —— Lua 脚本加锁

```java
// Redisson 加锁的 Lua 脚本

<T> RFuture<T> tryLockInnerAsync(long waitTime, long leaseTime, 
                                 TimeUnit unit, long threadId,
                                 RedisStrictCommand<T> command) {
    internalLockLeaseTime = unit.toMillis(leaseTime);
    
    return evalWriteAsync(getName(), LongCodec.INSTANCE, command,
        // Lua 脚本开始
        "if (redis.call('exists', KEYS[1]) == 0) then " +           // 锁不存在
        "   redis.call('hset', KEYS[1], ARGV[2], 1); " +          // Hash 设置 field=threadId, value=1
        "   redis.call('pexpire', KEYS[1], ARGV[1]); " +           // 设置过期时间
        "   return nil; " +                                        // 返回 nil（成功）
        "end; " +
        "if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then " + // 锁存在且是当前线程持有
        "   redis.call('hincrby', KEYS[1], ARGV[2], 1); " +       // 重入次数 +1
        "   redis.call('pexpire', KEYS[1], ARGV[1]); " +          // 刷新过期时间
        "   return nil; " +                                        // 返回 nil（成功）
        "end; " +
        "return redis.call('pttl', KEYS[1]);",                     // 锁被其他线程持有，返回 TTL
        // 参数
        Collections.singletonList(getName()),                      // KEYS[1] = lock name
        internalLockLeaseTime,                                     // ARGV[1] = lease time
        getLockName(threadId)                                      // ARGV[2] = UUID:threadId
    );
}
```

**Lua 脚本解读**：

```
KEYS[1] = "myLock"          （锁名称）
ARGV[1] = 30000             （过期时间 30 秒，毫秒）
ARGV[2] = "uuid:threadId"   （客户端标识）

执行逻辑：
  1. 如果锁不存在（exists == 0）
     → hset myLock "uuid:threadId" 1   （Hash 结构存储）
     → pexpire myLock 30000           （设置过期时间）
     → 返回 nil（成功）

  2. 如果锁存在且是当前线程持有（hexists == 1）
     → hincrby myLock "uuid:threadId" 1  （重入次数 +1）
     → pexpire myLock 30000              （刷新过期时间）
     → 返回 nil（成功，可重入）

  3. 如果锁被其他线程持有
     → pttl myLock（返回剩余 TTL）
     → 客户端收到 TTL > 0，知道获取失败
```

**为什么用 Hash 而不是 String？**

```
String 结构：
  key: myLock
  value: "uuid:threadId"
  → 只能记录一个值，无法记录重入次数

Hash 结构：
  key: myLock
  field: "uuid:threadId"
  value: 3                    （重入次数）
  → 可以记录重入次数，支持可重入
```

### 14.4 看门狗续期源码

```java
// Redisson 看门狗续期源码

public class RedissonLock {
    
    // 续期定时任务
    private void scheduleExpirationRenewal(long threadId) {
        ExpirationEntry entry = new ExpirationEntry();
        ExpirationEntry oldEntry = EXPIRATION_RENEWAL_MAP.putIfAbsent(getEntryName(), entry);
        if (oldEntry != null) {
            entry = oldEntry;
        }
        
        // 如果第一次添加
        if (entry.addThreadId(threadId) == 1) {
            // 启动定时续期任务
            renewExpiration(threadId);
        }
    }
    
    private void renewExpiration(long threadId) {
        ExpirationEntry entry = ExpirationEntry.getEntry(getEntryName());
        if (entry == null) {
            return;
        }
        
        // 创建定时任务，延迟 internalLockLeaseTime / 3 执行
        // 即每 30s / 3 = 10s 续期一次
        Timeout task = commandExecutor.getConnectionManager().newTimeout(new TimerTask() {
            @Override
            public void run(Timeout timeout) throws Exception {
                ExpirationEntry ent = ExpirationEntry.getEntry(getEntryName());
                if (ent == null) {
                    return;
                }
                
                Long threadId1 = ent.getFirstThreadId();
                if (threadId1 == null) {
                    return;
                }
                
                // 执行 Lua 脚本续期
                RFuture<Boolean> future = renewExpirationAsync(threadId1);
                future.onComplete((res, e) -> {
                    if (e != null) {
                        log.error("Can't update lock " + getName() + " expiration", e);
                        EXPIRATION_RENEWAL_MAP.remove(getEntryName());
                        return;
                    }
                    
                    if (res) {
                        // 续期成功，继续下一次定时任务
                        renewExpiration(threadId);
                    }
                    // 续期失败（锁已被释放或被其他人持有），停止续期
                });
            }
        }, internalLockLeaseTime / 3, TimeUnit.MILLISECONDS);
        
        // 将定时任务存入 entry
        entry.getTaskId().set(task.getTaskId());
    }
    
    // 续期的 Lua 脚本
    protected RFuture<Boolean> renewExpirationAsync(long threadId) {
        return evalWriteAsync(getName(), LongCodec.INSTANCE, RedisCommands.EVAL_BOOLEAN,
            "if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then " +   // 锁还在且是当前线程持有
            "   redis.call('pexpire', KEYS[1], ARGV[1]); " +              // 重置过期时间
            "   return 1; " +                                              // 返回 1（续期成功）
            "end; " +
            "return 0;",                                                  // 返回 0（续期失败，锁不存在或被释放）
            Collections.singletonList(getName()),
            internalLockLeaseTime,
            getLockName(threadId)
        );
    }
}
```

**看门狗续期时序**：

```
T0:    加锁成功，TTL=30s，启动看门狗
T10:   看门狗检查：hexists == 1（锁还在）
       → pexpire 30000（续期 30s）
       → 继续下一次定时
T20:   看门狗检查：hexists == 1（锁还在）
       → pexpire 30000（续期 30s）
       → 继续下一次定时
T30:   执行 unlock
       → 看门狗检查：hexists == 0（锁已释放）
       → 返回 0，停止续期

如果持锁线程宕机：
T0:    加锁成功，TTL=30s，启动看门狗
T5:    线程宕机，看门狗也停了（因为看门狗是持锁线程的后台线程）
T30:   锁自动过期（30s TTL 到期）
→ 防死锁
```

### 14.5 解锁源码

```java
// Redisson 解锁源码

public class RedissonLock {
    
    @Override
    public RFuture<Void> unlockAsync(long threadId) {
        return evalWriteAsync(getName(), LongCodec.INSTANCE, RedisCommands.EVAL_NULL,
            // Lua 脚本开始
            "if (redis.call('hexists', KEYS[1], ARGV[3]) == 0) then " +     // 锁不存在
            "   return nil; " +                                             // 返回 nil（无锁可解）
            "end; " +
            "local counter = redis.call('hincrby', KEYS[1], ARGV[3], -1); " + // 重入次数 -1
            "if (counter > 0) then " +                                      // 重入次数 > 0
            "   redis.call('pexpire', KEYS[1], ARGV[2]); " +                // 刷新过期时间
            "   return 0; " +                                                // 返回 0（还有重入次数，不删锁）
            "else " +
            "   redis.call('del', KEYS[1]); " +                              // 删除锁
            "   redis.call('publish', KEYS[2], ARGV[1]); " +               // 发布锁释放消息
            "   return 1; " +                                                // 返回 1（完全释放）
            "end; ",
            Arrays.asList(getName(), getChannelName()),  // KEYS[1]=lockName, KEYS[2]=channelName
            LockPubSub.UNLOCK_MESSAGE,                    // ARGV[1]=unlock message
            internalLockLeaseTime,                        // ARGV[2]=lease time
            getLockName(threadId)                         // ARGV[3]=uuid:threadId
        );
    }
}
```

**解锁 Lua 脚本解读**：

```
KEYS[1] = "myLock"          （锁名称）
KEYS[2] = "redisson__lock__channel__{myLock}"  （Pub/Sub 频道）
ARGV[1] = 0                  （unlock 消息内容）
ARGV[2] = 30000              （过期时间）
ARGV[3] = "uuid:threadId"    （客户端标识）

执行逻辑：
  1. 如果锁不存在（hexists == 0）
     → 返回 nil（无锁可解）

  2. 重入次数 -1
     counter = hincrby myLock "uuid:threadId" -1

  3. 如果 counter > 0（还有重入次数）
     → pexpire myLock 30000（刷新过期时间）
     → 返回 0（不完全释放，减少一层重入）

  4. 如果 counter == 0（完全释放）
     → del myLock（删除锁）
     → publish channel 0（通知等待线程）
     → 返回 1（完全释放）
```

### 14.6 Redisson 锁完整流程图

```
┌─────────────────────────────────────────────────────────────┐
│              Redisson 分布式锁完整流程                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   tryLock()                                                 │
│     │                                                       │
│     ├── tryAcquire() → Lua 脚本                              │
│     │     ├── 锁不存在 → hset + pexpire → 返回 nil（成功）    │
│     │     ├── 锁存在且是当前线程 → hincrby + pexpire → 成功  │

│     │                                                       │

│     │                                                       │

│           ├── 超时 → 返回 false                              │
│           └── 获取成功 → 返回 true                           │
│                                                             │

│               → 停止看门狗                                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 15. Redisson 公平锁源码

### 15.1 公平锁原理

公平锁按照请求顺序获取锁，先到先得。Redisson 通过 Redis **List**（等待队列）+ **Hash**（重入计数）+ **ZSet**（超时队列）实现。

```java
// 公平锁使用
RLock fairLock = redisson.getFairLock("myFairLock");
fairLock.lock();
try {
    // 业务逻辑
} finally {
    fairLock.unlock();
}
```

### 15.2 公平锁加锁 Lua 脚本

```lua
-- Redisson 公平锁加锁 Lua 脚本（简化版）

-- KEYS[1] = 锁名称
-- KEYS[2] = 等待队列名称 (redisson_lock_queue:{lockName})
-- KEYS[3] = 超时队列名称 (redisson_lock_timeout:{lockName})
-- ARGV[1] = 过期时间
-- ARGV[2] = uuid:threadId
-- ARGV[3] = 当前时间戳

-- 1. 如果锁不存在且队列为空（或队首是当前线程），可以获取锁
if (redis.call('exists', KEYS[1]) == 0) and
   ((redis.call('exists', KEYS[2]) == 0) or
    (redis.call('lindex', KEYS[2], 0) == ARGV[2])) then
    
    -- 设置锁
    redis.call('hset', KEYS[1], ARGV[2], 1)
    redis.call('pexpire', KEYS[1], ARGV[1])
    
    -- 从等待队列移除
    redis.call('lpop', KEYS[2])
    redis.call('zrem', KEYS[3], ARGV[2])
    
    return nil
end

-- 2. 如果锁存在且是当前线程持有（可重入）
if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then
    redis.call('hincrby', KEYS[1], ARGV[2], 1)
    redis.call('pexpire', KEYS[1], ARGV[1])
    return nil
end

-- 3. 如果是第一次排队，加入等待队列
if (redis.call('exists', KEYS[2]) == 0) then
    redis.call('zadd', KEYS[3], ARGV[3], ARGV[2])  -- ZSet 记录超时时间
    redis.call('rpush', KEYS[2], ARGV[2])           -- List 尾部加入
end

-- 4. 返回等待时间
local timeout = redis.call('zscore', KEYS[3], ARGV[2])
if timeout then
    return timeout - ARGV[3]
end
return ARGV[3]
```

### 15.3 公平锁 vs 非公平锁

| 维度 | 非公平锁 | 公平锁 |
|------|----------|--------|
| 获取顺序 | 随机竞争 | FIFO 先到先得 |
| 吞吐量 | 高 | 低（需维护队列） |
| 饥饿 | 可能 | 不会 |
| 实现 | 简单（Lua 脚本） | 复杂（List + ZSet + Hash） |
| 适用场景 | 大多数 | 严格公平要求 |

```lua
-- 读锁加锁 Lua 脚本（简化版）

-- 如果锁不存在，或模式是读
if ((redis.call('exists', KEYS[1]) == 0) or
    (redis.call('hget', KEYS[1], 'mode') == 'read')) then
    
    -- 设置模式为读
    redis.call('hset', KEYS[1], 'mode', 'read')
    -- 设置当前线程的读锁
    redis.call('hset', KEYS[1], ARGV[2], 1)

    redis.call('pexpire', KEYS[1], ARGV[1])

end

    redis.call('hincrby', KEYS[1], ARGV[2], 1)
    redis.call('pexpire', KEYS[1], ARGV[1])
    return nil
end

-- 锁被写锁持有，返回等待时间
return redis.call('pttl', KEYS[1])
```

### 17.2 最佳实践

```java
// 生产环境最佳实践
public class LockBestPractice {
    
    @Autowired
    private RedissonClient redisson;
    
    public void doBusinessWithLock(String resourceId) {
        RLock lock = redisson.getLock("resource:" + resourceId);
        
        boolean locked = false;
        try {
            // 不指定 leaseTime → 启动看门狗自动续期
            locked = lock.tryLock(10, TimeUnit.SECONDS);
            
            if (!locked) {
                throw new BusinessException("系统繁忙，请稍后重试");
            }
            
            // 执行业务逻辑
            doBusiness(resourceId);
            
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new BusinessException("加锁被中断");
        } finally {
            // 必须检查是否持有锁，避免释放别人的锁
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
    
    // 使用注解简化（AOP）
    @DistributedLock(key = "#orderId", waitTime = 5, leaseTime = 30)
    public void processOrder(String orderId) {
        // 业务逻辑
    }
}
```

## 18. RDB 持久化源码（fork + COW）

### 18.1 RDB 原理

**RDB（Redis Database）** 是 Redis 的二进制快照持久化方式，通过 `fork()` 子进程将内存数据以二进制格式写入磁盘。

```
┌─────────────────────────────────────────────────────────────┐
│                      RDB 持久化流程                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   Redis 主进程                                               │
│     │                                                       │
│     │ BGSAVE                                                │
│     │                                                       │
│     ├──→ fork()                                             │
│     │    │                                                  │
│     │    ├── 子进程（RDB 持久化）                             │
│     │    │     │                                             │
│     │    │     │ 遍历所有 Key                                 │
│     │    │     │ 将数据写入 RDB 文件（dump.rdb）               │
│     │    │     │ 写完后替换旧文件（rename）                    │
│     │    │     │ 通知主进程完成                                │
│     │    │     └── 退出                                       │
│     │    │                                                  │
│     │    └── 主进程                                          │
│     │          继续处理客户端请求                              │
│     │          （通过 COW 实现数据隔离）                      │
│     │                                                       │
│     │ ←── 子进程完成通知                                      │
│     │                                                       │
│                                                             │
│   关键：fork() + COW（Copy-On-Write）                      │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 18.2 fork + COW 机制

**fork()** 是操作系统的系统调用，创建一个子进程。关键点是 fork 时不会立即复制父进程的全部内存，而是通过 **COW（Copy-On-Write）** 机制实现延迟复制。

```
┌─────────────────────────────────────────────────────────────┐
│              fork() + COW 机制                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   fork() 之前：                                              │
│   ┌──────────────────────────────────────┐                  │
│   │  父进程内存（4 GB）                    │                  │
│   │  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐    │                  │
│   │  │Page1│ │Page2│ │Page3│ │Page4│ ... │                  │
│   │  │A=1  │ │B=2  │ │C=3  │ │D=4  │    │                  │
│   │  └─────┘ └─────┘ └─────┘ └─────┘    │                  │
│   └──────────────────────────────────────┘                  │
│                                                             │
│   fork() 之后（COW 阶段）：                                   │
│   父进程和子进程共享相同的物理页（只读）                        │
│                                                             │
│   ┌────────────────────────┐  ┌────────────────────────┐   │
│   │  父进程（虚拟内存视图）    │  │  子进程（虚拟内存视图）    │   │
│   │  Page1 Page2 Page3 ...│  │  Page1 Page2 Page3 ...│   │
│   └───────────┬────────────┘  └───────────┬────────────┘   │
│               │                             │               │
│               └──────────┬──────────────────┘               │
│                          │                                  │
│               ┌──────────▼──────────┐                       │
│               │  物理内存页（共享）    │                       │
│               │  Page1 Page2 Page3  │                       │
│               └─────────────────────┘                       │
│                                                             │
│   父进程修改 Page2 时（COW 触发）：                            │
│   操作系统为子进程复制一份 Page2 的副本                        │
│                                                             │
│   ┌────────────────────────┐  ┌────────────────────────┐   │
│   │  父进程                  │  │  子进程                  │   │
│   │  Page1 Page2' Page3 ...│  │  Page1 Page2 Page3 ...│   │
│   │        ↑ 新页（B=5）     │  │     ↑ 旧页（B=2）       │   │
│   └────────────────────────┘  └────────────────────────┘   │
│                                                             │
│   核心：子进程看到的是 fork 时刻的快照数据                     │
│         父进程的修改不影响子进程的数据                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 18.3 fork 的开销

```
fork() 的开销：
  1. 复制页表（不是复制整个内存页）
     - 4 GB 内存 → 约 1M 个页表项（4KB/页）
     - 复制页表耗时约 100~500ms（取决于内存大小）
  
  2. COW 期间内存翻倍风险
     - 如果 fork 后父进程大量写操作，每个修改的页都会被复制
     - 极端情况下内存翻倍（4GB → 8GB）
     - 可能导致 OOM 或触发 swap
  
  3. 子进程写 RDB 文件的 I/O 开销
     - 4 GB 数据 → 写 4 GB 文件
     - 如果磁盘慢，可能需要数秒到数十秒
```

## 19. AOF 持久化源码（appendfsync 三策略）

### 19.1 AOF 原理

**AOF（Append Only File）** 以追加方式记录所有写命令到文件。恢复时按顺序重放所有命令重建数据。

```
┌─────────────────────────────────────────────────────────────┐
│                      AOF 持久化流程                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   客户端                                                    │
│     │ SET name "zhang"                                      │
│     ▼                                                       │
│   Redis 主进程                                              │
│     │                                                       │
│     ├── 1. 执行命令（修改内存中的数据）                      │
│     │                                                       │
│     ├── 2. 将命令追加到 AOF Buffer                          │
│     │   aof_buf += "*3\r\n$3\r\nSET\r\n$4\r\nname..."       │
│     │                                                       │
│     ├── 3. 根据 appendfsync 策略写入文件                     │
│     │   ├── always: 每条命令都 fsync（最安全，最慢）          │
│     │   ├── everysec: 每秒 fsync 一次（折中，推荐）           │
│     │   └── no: 由 OS 决定何时 fsync（最快，不安全）          │
│     │                                                       │
│     └── 4. 文件越来越大 → AOF 重写（Rewrite）                │
│                                                             │
│   恢复过程：                                                 │
│   读取 appendonly.aof → 逐条重放命令 → 恢复数据               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 19.2 appendfsync 三种策略

```
┌─────────────────────────────────────────────────────────────┐
│              appendfsync 三种策略对比                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   ┌─────────────┬──────────┬──────────┬──────────┐         │
│   │   策略       │  always  │ everysec │   no     │         │
│   ├─────────────┼──────────┼──────────┼──────────┤         │
│   │ 写入方式     │ 每条命令  │ 每秒一次  │ OS 决定   │         │
│   │              │ fsync    │ fsync    │          │         │
│   ├─────────────┼──────────┼──────────┼──────────┤         │
│   │ 数据安全性   │ 最高      │ 高       │ 低       │         │
│   │ （最多丢）   │ 不丢      │ 1 秒     │ 不可控   │         │
│   ├─────────────┼──────────┼──────────┼──────────┤         │
│   │ 性能         │ 最差      │ 好       │ 最好     │         │
│   │              │ (TPS 降半)│          │          │         │
│   ├─────────────┼──────────┼──────────┼──────────┤         │
│   │ 推荐度       │ ✗        │ ✓ 推荐   │ ✗        │         │
│   └─────────────┴──────────┴──────────┴──────────┘         │
│                                                             │
│   everysec 是折中方案：                                      │
│   - 后台线程每秒执行一次 fsync                                │
│   - 如果 fsync 耗时长，不影响主线程                           │
│   - 最多丢失最近 1 秒的数据                                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 19.3 AOF Rewrite（重写）

AOF 文件会随着运行时间越来越大，**Rewrite** 通过重新生成一份精简的 AOF 文件来缩小体积。

```
┌─────────────────────────────────────────────────────────────┐
│                   AOF Rewrite 流程                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   原始 AOF 文件内容：                                        │
│     SET name "zhang"                                        │
│     SET name "li"                                            │
│     SET name "wang"                                          │
│     LPUSH list "a"                                           │
│     LPUSH list "b"                                           │
│     LPUSH list "c"                                           │
│                                                             │
│   → 文件中有 6 条命令，但最终只需要 2 条                      │
│                                                             │
│   Rewrite 后的 AOF 文件内容：                                 │
│     SET name "wang"         ← 只保留最终值                   │
│     LPUSH list "c" "b" "a"  ← 合并为一条                     │
│                                                             │
│   → 文件从 6 条缩减为 2 条                                    │
│                                                             │
│   Rewrite 过程（fork + 双写）：                              │
│                                                             │
│   1. fork() 子进程                                          │
│   2. 子进程遍历内存，生成新的 AOF 文件（temp-rewriteaof）    │
│   3. 主进程继续处理命令，同时写入 AOF Buffer 和              │
│      AOF Rewrite Buffer（双写）                              │
│   4. 子进程完成 → 通知主进程                                  │
│   5. 主进程将 Rewrite Buffer 中的增量命令追加到新文件          │
│   6. 原子替换旧文件（rename）                                 │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 19.4 AOF Rewrite 触发条件

```
自动触发条件：
  auto-aof-rewrite-percentage 100   → 文件大小增长 100% 时触发
  auto-aof-rewrite-min-size 64mb    → 文件至少 64MB 才触发

  举例：
    当前文件 100MB，阈值 100% → 下次触发大小为 200MB
    文件增长到 200MB → 触发 Rewrite
    Rewrite 后假设缩小到 50MB
    下次触发大小为 max(50*2, 64) = 100MB
  
手动触发：
  BGREWRITEAOF 命令
```

## 20. 混合持久化（RDB + AOF）

### 20.1 混合持久化原理

Redis 4.0 引入 **混合持久化**，结合 RDB 和 AOF 的优点：AOF 文件前半部分是 RDB 格式（快照），后半部分是增量 AOF 命令。

```
┌─────────────────────────────────────────────────────────────┐
│                混合持久化文件结构                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   ┌──────────────────────────────────────────────────┐       │
│   │              appendonly.aof                       │       │
│   ├──────────────────────────────────────────────────┤       │
│   │                                                  │       │
│   │  RDB 部分（前半部分）                               │       │
│   │  ┌────────────────────────────────────────────┐  │       │
│   │  │ REDIS0011 <rdb binary data>                │  │       │
│   │  │ (全量数据快照，二进制格式)                   │  │       │
│   │  └────────────────────────────────────────────┘  │       │
│   │                                                  │       │
│   │  AOF 增量部分（后半部分）                           │       │
│   │  ┌────────────────────────────────────────────┐  │       │
│   │  │ *3\r\n$3\r\nSET\r\n$4\r\nname\r\n...        │  │       │
│   │  │ *3\r\n$3\r\nSET\r\n$3\r\nage\r\n...         │  │       │
│   │  │ (RDB 快照后的增量命令，文本格式)              │  │       │
│   │  └────────────────────────────────────────────┘  │       │
│   │                                                  │       │
│   └──────────────────────────────────────────────────┘       │
│                                                             │
│   恢复过程：                                                 │
│   1. 读取 RDB 部分 → 快速恢复全量数据                         │
│   2. 重放 AOF 增量命令 → 补全最新变更                         │
│                                                             │
│   优点：                                                     │
│   ✓ 恢复速度快（RDB 二进制加载快）                            │
│   ✓ 数据完整性高（AOF 增量补全）                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 20.2 开启混合持久化

```
# redis.conf
aof-use-rdb-preamble yes   # 开启混合持久化（Redis 4.0+，默认 yes）

# 执行 BGREWRITEAOF 时：
#   如果开启混合持久化 → 生成 RDB + AOF 混合格式
#   如果关闭 → 生成纯 AOF 格式
```

## 21. RDB vs AOF 对比

| 维度 | RDB | AOF | 混合持久化 |
|------|-----|-----|-----------|
| **数据安全性** | 差（丢分钟级数据） | 好（丢 1 秒） | 好（丢 1 秒） |
| **恢复速度** | 快（二进制加载） | 慢（命令重放） | 快（RDB + 少量 AOF） |
| **文件大小** | 小 | 大 | 中 |
| **性能影响** | 中（fork） | 低（追加写） | 中 |
| **可读性** | 差（二进制） | 好（文本命令） | 差 |
| **推荐场景** | 灾难恢复、备份 | 数据安全要求高 | 生产推荐（4.0+） |

**生产推荐**：混合持久化（`aof-use-rdb-preamble yes` + `appendonly yes` + `appendfsync everysec`）。

### 22.1 主从复制架构

```
┌─────────────────────────────────────────────────────────────┐
│                   Redis 主从复制架构                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   ┌──────────┐                                              │
│   │  Master   │  ←── 读写请求                                 │
│   │  (可读可写) │                                              │
│   └─────┬────┘                                              │
│         │                                                   │
│         │ 主从复制                                           │
│         │                                                   │
│    ┌────┼────────────┐                                      │
│    │    │            │                                      │
│    ▼    ▼            ▼                                      │
│  ┌────┐ ┌────┐    ┌────┐                                   │
│  │Slave│ │Slave│    │Slave│  ←── 只读请求                    │
│  │ 1  │ │ 2  │    │ 3  │                                    │
│  └────┘ └────┘    └────┘                                   │
│                                                             │
│   作用：                                                     │
│   1. 读写分离（Master 写，Slave 读）→ 提升读性能             │
│   2. 数据备份 → 数据冗余                                     │
│   3. 故障转移基础 → Sentinel/Cluster 依赖                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 22.2 全量同步流程

```
┌─────────────────────────────────────────────────────────────┐
│              Redis 全量同步流程                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   Slave                              Master                 │
│     │                                  │                   │
│     │ 1. SLAVEOF <master_ip> <port>     │                   │
│     │ ──────────────────────────────────→│                   │
│     │                                  │                   │
│     │ 2. PSYNC ? -1                      │                   │
│     │ ──────────────────────────────────→│                   │
│     │    (首次连接，不知道 master_replid   │                   │
│     │     和 offset，传 ? 和 -1)          │                   │
│     │                                  │                   │
│     │ ←──── +FULLRESYNC <replid> <offset>│                   │
│     │    (Master 告诉 Slave 需要全量同步) │                   │
│     │                                  │                   │
│     │                                  │ 3. BGSAVE            │
│     │                                  │    fork 子进程       │
│     │                                  │    生成 RDB 文件     │
│     │                                  │                   │
│     │ ←──── $<RDB file size>           │                   │
│     │ ←──── <RDB binary data>           │                   │
│     │    (Master 发送 RDB 文件给 Slave)   │                   │
│     │                                  │                   │
│     │ 4. 接收 RDB 文件                   │                   │
│     │    清空旧数据                      │                   │
│     │    加载 RDB 文件到内存              │                   │
│     │                                  │                   │
│     │ ←──── 增量命令（RDB 期间的新写操作）│                   │
│     │    (Master 在 BGSAVE 期间产生的     │                   │
│     │     写命令缓存在 replication        │                   │
│     │     backlog 中，RDB 发完后发给 Slave)│                  │
│     │                                  │                   │
│     │ 5. 执行增量命令                    │                   │
│     │    数据同步完成                     │                   │
│     │                                  │                   │
│     │ ←──→ 命令传播（持续）              │                   │
│     │    Master 每执行一条写命令            │                   │
│     │    就异步发给所有 Slave             │                   │
│     │                                  │                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 22.3 PSYNC 命令详解

```bash
# PSYNC 命令格式
PSYNC <master_replid> <offset>

# 参数说明：
#   master_replid: Master 的复制 ID（每个 Master 有唯一 ID）
#   offset: Slave 当前同步到的偏移量

# 返回值：
#   +FULLRESYNC <replid> <offset>  → 需要全量同步
#   +CONTINUE                       → 增量同步
#   +CONTINUE <new_replid>          → 增量同步（Master 切换后）
#   -ERR                            → 不支持 PSYNC
```

### 22.4 全量同步的开销

```
全量同步的开销：
  1. Master 执行 BGSAVE → fork 开销（内存越大越慢）
  2. 传输 RDB 文件 → 网络 I/O（文件越大越慢）
  3. Slave 清空数据 + 加载 RDB → 阻塞（期间无法提供服务）
  4. Master 缓存增量命令 → 消耗内存

4GB 数据全量同步耗时：
  - fork: ~200ms
  - RDB 传输: ~5s（千兆网络）
  - Slave 加载: ~3s
  - 总计: ~8s
  
  这期间 Master 的写命令会被缓存
  如果增量命令太多 → backlog 溢出 → 再次全量同步 → 死循环！
```

## 23. 增量同步（replication backlog）

### 23.1 增量同步原理

**增量同步**是指 Slave 断线重连后，只同步断线期间的增量数据，而不需要全量同步。

```
┌─────────────────────────────────────────────────────────────┐
│              Redis 增量同步流程                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   Slave                              Master                 │
│     │                                  │                   │
│     │ 1. 网络断开                        │                   │
│     │     × ←──── ×                     │                   │
│     │                                  │                   │
│     │     （断线期间 Master 继续写命令）  │                   │
│     │                                  │ offset = 1000     │
│     │                                  │ backlog:          │
│     │                                  │  [800~1200]       │
│     │                                  │                   │
│     │ 2. 网络恢复                        │                   │
│     │     ←──── →                     │                   │
│     │                                  │                   │
│     │ 3. PSYNC <replid> 900            │                   │
│     │    （Slave 记得上次同步到 900）     │                   │
│     │ ──────────────────────────────────→│                   │
│     │                                  │                   │
│     │                                  │ 检查 900 是否在    │
│     │                                  │ backlog 范围内    │
│     │                                  │ backlog: [800~1200]│
│     │                                  │ 900 ∈ [800, 1200] │
│     │                                  │ → 可以增量同步！   │
│     │                                  │                   │
│     │ ←──── +CONTINUE                  │                   │
│     │                                  │                   │
│     │ ←──── 增量命令 [901~1200]         │                   │
│     │    (发送 offset 900~1200 之间的   │                   │
│     │     命令给 Slave)                  │                   │
│     │                                  │                   │
│     │ 4. 执行增量命令                    │                   │
│     │    Slave offset 更新为 1200        │                   │
│     │                                  │                   │
│     │ ←──→ 命令传播（持续）              │                   │
│     │                                  │                   │
│   如果 offset 不在 backlog 范围内：                           │
│     → +FULLRESYNC（退化为全量同步）                            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 23.2 Replication Backlog

**Replication Backlog** 是 Master 上的一个环形缓冲区，用于存储最近的写命令。

```
┌─────────────────────────────────────────────────────────────┐
│              Replication Backlog 环形缓冲区                  │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   backlog 是一个固定大小的环形缓冲区（默认 1MB）              │
│                                                             │
│        ┌─────────────────────────────────┐                  │
│        │  backlog [1MB 环形缓冲区]         │                  │
│        │                                   │                  │
│        │  ┌───┬───┬───┬───┬───┬───┬───┐  │                  │
│        │  │800│801│802│...│...│...│1200│ │                  │
│        │  └───┴───┴───┴───┴───┴───┴───┘  │                  │
│        │    ↑                  ↑          │                  │
│        │  最早命令           最新命令     │                  │
│        │  (会被覆盖)         (master_repl_offset)│          │
│        └─────────────────────────────────┘                  │
│                                                             │
│   写入：                                                     │
│     Master 执行写命令 → 追加到 backlog 尾部                   │
│     如果 backlog 满了 → 覆盖最旧的数据（环形覆盖）            │
│                                                             │
│   读取：                                                     │
│     Slave 重连 → PSYNC replid offset                         │
│     Master 检查 offset 是否在 backlog 范围内：               │
│       - 在范围内 → 发送 offset~repl_offset 的命令（增量同步）  │
│       - 不在范围内 → 全量同步（旧数据已被覆盖）               │
│                                                             │
│   关键参数：                                                  │
│     repl-backlog-size 1mb    → backlog 大小                 │
│     repl-backlog-ttl 3600    → backlog 空闲多久后释放        │
│                                                             │
│   生产建议：                                                  │
│     如果 Slave 断线时间长或写量大，1MB 不够用                  │
│     → 调大到 64MB~256MB                                      │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 23.3 backlog 大小计算

```
backlog 大小 = 断线时间 × 每秒写入量

示例：
  每秒写入 10000 个命令，每条命令平均 100 字节
  → 每秒写入量 = 10000 × 100 = 1 MB/s
  
  假设最长断线时间 60 秒
  → backlog 大小 = 60 × 1MB = 60MB
  
  生产推荐设置为计算值的 2 倍：120MB
```

### 24.1 心跳机制

```
│     │                               │                      │
│     │ ── 命令传播 ──→               │                      │

```

### 24.2 命令传播

```
Master 执行写命令后的传播流程：

  1. Master 执行 SET name "zhang"
  2. 将命令追加到 replication backlog
  3. 将命令发送给所有 Slave（异步，不等待 ACK）
  4. 等待 Slave 的 REPLCONF ACK 报告 offset
  5. 如果 Slave offset 落后太多，可以告警
```

### 24.3 主从复制延迟问题

```
┌─────────────────────────────────────────────────────────────┐
│                主从复制延迟问题                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   主从复制是异步的：                                          │
│   Master 写入 → 立即返回 → 异步发给 Slave                    │
│                                                             │
│   问题场景：                                                  │
│   1. 读写分离时，写 Master 后立即读 Slave                     │
│      → 可能读到旧数据（复制还没完成）                         │
│                                                             │
│   2. Master 宕机，数据还没完全复制到 Slave                     │
│      → 部分数据丢失                                          │
│                                                             │
│   解决方案：                                                  │
│   1. 读写分离不强求实时一致：                                  │
│      - 写后等待一段时间再读 Slave                              │
│      - 或写后直接读 Master                                    │
│                                                             │
│   2. 等待复制完成（WAIT 命令）：                              │
│      SET name "zhang"                                        │
│      WAIT 2 100  → 等待 2 个 Slave 确认，超时 100ms          │
│      → 返回确认的 Slave 数量                                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 25. 主从复制源码分析

### 25.1 复制的核心结构

```c
// Redis 源码：server.h（简化）

typedef struct redisServer {
    // ... 其他字段 ...
    
    // 复制相关
    char replid[CONFIG_RUN_ID_SIZE+1];    // Master 的复制 ID
    long long master_repl_offset;         // Master 的复制偏移量
    
    // Replication Backlog
    char *repl_backlog;                   // backlog 缓冲区
    long long repl_backlog_size;          // backlog 大小
    long long repl_backlog_histlen;       // backlog 中实际数据长度
    long long repl_backlog_idx;           // 当前写入位置（环形）
    long long repl_backlog_off;           // backlog 中第一条命令的 offset
    
    // Slave 列表
    list *slaves;                         // 连接的 Slave 列表
```

### 25.2 PSYNC 判断逻辑

```c
// Redis 源码：replication.c（简化）

// Master 处理 PSYNC 命令
void syncCommand(client *c) {
    // 1. 检查 replid 是否匹配
    if (strcasecmp(c->argv[1]->ptr, server.replid) != 0 &&
        strcasecmp(c->argv[1]->ptr, server.replid2) != 0) {
        // replid 不匹配（可能是不同的 Master）
        // → 需要全量同步
        goto need_full_resync;
    }
    
    // 2. 检查 offset 是否在 backlog 范围内
    long long psync_offset = strtoll(c->argv[2]->ptr, NULL, 10);
    
    if (!server.repl_backlog ||
        psync_offset < server.repl_backlog_off ||
        psync_offset > (server.repl_backlog_off + server.repl_backlog_histlen)) {
        // offset 不在 backlog 范围内
        // → 需要全量同步
        goto need_full_resync;
    }
    
    // 3. 可以增量同步
    // 回复 +CONTINUE
    addReply(c, shared.continue);
    
    // 发送 backlog 中 psync_offset ~ master_repl_offset 之间的命令
    replicationSendPartialToSlave(c, psync_offset);
    return;
    
need_full_resync:
    // 全量同步
    // 1. 回复 +FULLRESYNC replid offset
    // 2. 执行 BGSAVE 生成 RDB
    // 3. 发送 RDB 给 Slave
    addReplyPrintf(c, "+FULLRESYNC %s %lld\r\n",
                   server.replid, server.master_repl_offset);
    
    if (server.rdb_child_pid != -1) {
        // 已经有 BGSAVE 在执行
        // 复用现有的 RDB（如果支持 diskless）
    } else {
        // 启动 BGSAVE
        startBgsaveForReplication();
    }
}
```

## 28. Raft 选举 Leader 哨兵

### 28.1 选举流程

当 Master 被判定为 ODOWN 后，Sentinel 需要选出一个 Leader 来执行故障转移。选举使用 **Raft 算法**。

```
┌─────────────────────────────────────────────────────────────┐
│              Sentinel Leader 选举流程（Raft）                │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   1. Sentinel 1 发现 ODOWN，发起选举                         │
│      → 成为 Candidate                                       │
│      → 给自己投票（epoch + 1）                               │
│      → 向其他 Sentinel 发送 "请选我当 Leader" 请求            │
│        SENTINEL is-master-down-by-addr <ip> <port> <epoch>  │
│                                                             │
│   2. 其他 Sentinel 收到请求                                  │
│      → 如果还没投过票（epoch 匹配），投给请求者               │
│      → 返回 "我选你"                                         │
│                                                             │
│   3. Sentinel 1 收集选票                                     │
│      → 如果获得多数票（≥ ⌈N/2⌉ + 1）                       │
│      → 成为 Leader                                          │
│      → 开始执行故障转移                                      │
│                                                             │
│   4. 如果一轮选举没有结果（平票）                              │
│      → 等待随机时间（2s + random）                           │
│      → 重新发起选举                                          │
│                                                             │
│   关键规则：                                                  │
│   - 每个 epoch 只能投一票                                    │
│   - 先到先得（谁先请求，票给谁）                              │
│   - 获得多数票即当选                                         │
│   - 随机等待避免活锁                                         │
│                                                             │
│   3 个 Sentinel 的情况：                                     │
│   - 需要 2 票即可当选（⌈3/2⌉ + 1 = 2）                     │
│   - 最多容忍 1 个 Sentinel 故障                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 28.2 为什么是 ⌈N/2⌉ + 1

```
N = 3：需要 2 票 → 容忍 1 个故障
N = 5：需要 3 票 → 容忍 2 个故障
N = 2：需要 2 票 → 容忍 0 个故障（不能容忍任何故障）

→ 所以 Sentinel 数量推荐奇数（3 或 5），不推荐偶数
→ 2 个 Sentinel 时，任何一个故障都无法完成选举
```

### 29.2 选择新 Master 的源码逻辑

```c
// Redis 源码：sentinel.c（简化）

// 选择新 Master 的 Slave
void sentinelFailoverSelectSlave(void) {
    sentinelInstance *slave = sentinelSelectSlave();
    
    if (slave == NULL) {
        // 没有可用的 Slave
        // 等待下一次尝试
        return;
    }
    
    // 选中了新 Master
    // 发送 SLAVEOF NO ONE
    sentinelSendSlaveOf(slave, NULL, 0);  // SLAVEOF NO ONE
}

// 选择最优 Slave 的具体逻辑
sentinelInstance *sentinelSelectSlave(void) {
    sentinelInstance *instance, *selected = NULL;
    
    // 遍历所有 Slave
    di = dictGetIterator(master->slaves);
    while ((de = dictNext(di)) != NULL) {
        instance = dictGetVal(de);
        
        // 跳过不可用的 Slave
        if (instance->flags & SRI_S_DOWN) continue;     // 主观下线
        if (instance->flags & SRI_O_DOWN) continue;     // 客观下线
        if (instance->flags & SRI_DISCONNECTED) continue; // 断开连接
        if (instance->slave_priority == 0) continue;   // 优先级 0 = 不参选
        
        // 1. 比较优先级（priority 越小越优先）
        if (selected == NULL || 
            instance->slave_priority < selected->slave_priority) {
            selected = instance;
            continue;
        }
        
        // 2. 优先级相同，比较 offset（越大越好，数据最新）
        if (instance->slave_priority == selected->slave_priority) {
            if (instance->slave_repl_offset > selected->slave_repl_offset) {
                selected = instance;
            }
        }
        
        // 3. offset 也相同，比较 run_id（越小越优先，纯随机）
        // ...
    }
    
    return selected;
}
```

# 第七部分：Redis Cluster

## 31. 16384 槽位设计

### 31.1 Redis Cluster 架构

```
┌─────────────────────────────────────────────────────────────┐
│                  Redis Cluster 架构                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   ┌──────────────────────────────────────────────┐          │
│   │              16384 个 Slot（槽位）              │          │
│   │  0    1    2    ...          16382  16383     │          │
│   │  ┌───┬───┬───┬───┬───┬───┬───┬───┬───┐      │          │
│   │  │ 0 │ 1 │ 2 │...│...│...│...│...│16383│   │          │
│   │  └───┴───┴───┴───┴───┴───┴───┴───┴───┘      │          │
│   └──────────────────────────────────────────────┘          │
│                                                             │
│   Slot 分配（3 个节点为例）：                                │
│   ┌──────────────┐  ┌──────────────┐  ┌──────────────┐     │
│   │  Node A       │  │  Node B       │  │  Node C       │     │
│   │  Slot 0~5460  │  │ Slot 5461~10922│ │ Slot 10923~16383│  │
│   │              │  │              │  │              │     │
│   │  Master       │  │  Master       │  │  Master       │     │
│   │    │         │  │    │         │  │    │         │     │
│   │    ▼         │  │    ▼         │  │    ▼         │     │
│   │  Slave A'    │  │  Slave B'    │  │  Slave C'    │     │
│   └──────────────┘  └──────────────┘  └──────────────┘     │
│                                                             │
│   每个 Master 负责一部分 Slot                               │
│   每个 Key 通过 CRC16 计算所属 Slot                          │
│   slot = CRC16(key) % 16384                                  │
│                                                             │
│   特点：                                                     │
│   1. 去中心化：无代理层，节点间直接通信                       │
│   2. 数据分片：16384 个槽分布在不同节点                      │
│   3. 高可用：每个 Master 有 Slave，宕机自动切换               │
│   4. 水平扩展：加节点时迁移 Slot                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 31.2 为什么是 16384

```
┌─────────────────────────────────────────────────────────────┐
│              为什么 Cluster 有 16384 个 Slot？               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   Redis 作者 Antirez 的解释：                                │
│                                                             │
│   1. 心跳消息大小                                            │
│      每个节点在 Gossip 消息中携带自己负责的 Slot 位图         │
│      16384 bits = 16384 / 8 = 2KB                           │
│      如果是 65536 bits = 65536 / 8 = 8KB                    │
│      → 心跳消息太大，浪费带宽                                │
│                                                             │
│   2. 集群规模                                                │
│      Redis 作者建议集群不超过 1000 个节点                    │
│      16384 / 1000 ≈ 16 个 Slot/节点                         │
│      足够分散                                                │
│      如果 65536 / 1000 ≈ 65 个 Slot/节点                    │
│      → 位图过大                                              │
│                                                             │
│   3. 位图压缩                                                │
│      16384 bits = 2KB，在大多数场景下压缩效果较好             │
│      如果节点很少（如 3 个），位图很稀疏，压缩后很小          │
│                                                             │
│   总结：16384 是在心跳消息大小和集群规模之间的折中            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 31.3 Key 到 Slot 的映射

```java
// Redis Cluster 计算 Slot 的算法

public int getSlot(String key) {
    // 1. 处理 Hash Tag：如果 key 中有 {xxx}，只取 xxx 的部分计算
    //    例如 "user:{1001}:profile" → 只对 "1001" 计算 slot
    //    这样 "user:{1001}:name" 和 "user:{1001}:age" 在同一个 slot
    //    → 支持 Multi-Key 操作（MSET、事务等）
    int start = key.indexOf('{');
    if (start != -1) {
        int end = key.indexOf('}', start + 1);
        if (end != -1 && end != start + 1) {
            key = key.substring(start + 1, end);  // 提取 { } 中的内容
        }
    }
    
    // 2. CRC16 计算
    int crc = CRC16.crc16(key.getBytes());
    
    // 3. 取模
    return crc % 16384;
}
```

### 31.4 Hash Tag 机制

```
┌─────────────────────────────────────────────────────────────┐
│                Hash Tag 机制                                 │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   问题：Redis Cluster 不支持跨 Slot 的 Multi-Key 操作        │
│   → MSET key1 val1 key2 val2  会报错（如果 key1, key2       │
│     在不同 Slot）                                            │
│                                                             │
│   解决：使用 Hash Tag {tag}                                  │
│   只有 { } 中的内容参与 Slot 计算                            │
│                                                             │
│   示例：                                                     │
│   key = "user:{1001}:name"   → CRC16("1001") % 16384 = 5   │
│   key = "user:{1001}:age"    → CRC16("1001") % 16384 = 5   │
│   key = "user:{1001}:email"  → CRC16("1001") % 16384 = 5   │
│                                                             │
│   → 三个 Key 都在 Slot 5 → 可以使用 MGET / 事务              │
│                                                             │
│   常见 Hash Tag 设计：                                       │
│   user:{userId}:profile    → 同一用户数据在同一 Slot         │
│   order:{orderId}:detail   → 同一订单数据在同一 Slot         │
│   {productId}:stock       → 同一商品数据在同一 Slot         │
│                                                             │
│   注意：Hash Tag 可能导致数据倾斜                            │
│   → 某个 Tag 的数据量过大 → 某个节点负载过高                 │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 32. Gossip 协议

### 32.1 Gossip 原理

**Gossip 协议**（八卦协议）是一种最终一致性协议，节点间通过互相交换信息来传播集群状态。

```
┌─────────────────────────────────────────────────────────────┐
│                Gossip 协议工作原理                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   集群有 6 个节点：A B C D E F                               │
│                                                             │
│   每个节点维护一份集群状态：                                  │
│   ┌────────────────────────────────────────┐               │
│   │  Node A 的集群状态视图                   │               │
│   │  ┌─────┬───────┬───────┬───────┐      │               │
│   │  │Node │  Slot  │  IP   │ Status│      │               │
│   │  ├─────┼───────┼───────┼───────┤      │               │
│   │  │  A  │0~5460 │10.1.1 │ online│      │               │
│   │  │  B  │5461~..│10.1.2 │ online│      │               │
│   │  │  C  │10923~ │10.1.3 │ online│      │               │
│   │  │  D  │ Slave │10.1.4 │ online│      │               │
│   │  │  E  │ Slave │10.1.5 │ online│      │               │
│   │  │  F  │ Slave │10.1.6 │ online│      │               │
│   │  └─────┴───────┴───────┴───────┘      │               │
│   └────────────────────────────────────────┘               │
│                                                             │
│   Gossip 过程：                                              │
│   1. Node A 随机选一个节点（如 Node C）                      │
│   2. Node A 向 Node C 发送 PING（携带自己的集群状态）        │
│   3. Node C 对比自己的状态，发现差异                         │
│   4. Node C 回复 PONG（携带自己的集群状态）                  │
│   5. 双方都更新自己的集群状态                                 │
│                                                             │
│   经过多轮 Gossip，所有节点的状态最终一致                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 32.2 Gossip 消息类型

```
┌─────────────────────────────────────────────────────────────┐
│                Gossip 消息类型                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   1. PING                                                   │
│      携带发送者的集群状态（部分节点信息）                     │
│      用于检测节点是否存活 + 传播集群状态                      │
│                                                             │
│   2. PONG                                                   │
│      回复 PING，携带自己的集群状态                            │
│                                                             │
│   3. MEET                                                   │
│      新节点加入集群时发送                                     │
│      收到后节点会将新节点加入集群                             │
│                                                             │
│   4. FAIL                                                   │
│      通知某节点已下线                                         │
│      通常是某个节点经过 PING 超时后广播                       │
│                                                             │
│   5. PUBLISH                                                │
│      用于 Pub/Sub 消息在集群中传播                           │
│                                                             │
│   PING/PONG 消息内容：                                       │
│   ┌──────────────────────────────────────┐                 │
│   │  Header: sender_id, slot_bitmap      │                 │
│   │  Gossip section: N 个节点信息          │                 │
│   │    node_id, ip, port, flags, ...      │                 │
│   └──────────────────────────────────────┘                 │
│                                                             │
│   每个 PING 携带少量节点信息（最多 3 个）                    │
│   → 减少消息大小                                             │
│   → 多轮 Gossip 后传播完整状态                               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 32.3 Gossip 触发条件

```
cluster-node-timeout 15000   # 节点超时时间（默认 15s）

每 100ms 做一次 Gossip：
  1. 每个节点每 100ms 执行一次 clusterCron()
  2. 在 clusterCron 中选择一个节点发送 PING
  3. 优先选择长时间未通信的节点
  4. 如果有节点超过 cluster-node-timeout/2 未通信 → 强制 PING

节点下线检测：
  1. PING 超时（cluster-node-timeout）→ 标记为 PFAIL（疑似下线）
  2. 通过 Gossip 传播 PFAIL 状态
  3. 如果半数以上节点标记为 PFAIL → 标记为 FAIL（确定下线）
  4. 广播 FAIL 消息
  5. 触发故障转移（如果下线的是 Master）
```

## 33. MOVED 与 ASK 重定向

### 33.1 MOVED 重定向

当客户端向错误节点发送命令时，节点返回 MOVED 重定向。

```bash
# 客户端向 Node A 发送 SET key value
# 但 key 属于 Node B 的 Slot

> SET user:1001 "zhang"
(error) MOVED 5461 192.168.1.12:6379
#      ↑     ↑
#      Slot  目标节点地址

# 客户端收到 MOVED 后：
# 1. 连接 192.168.1.12:6379
# 2. 重新发送 SET user:1001 "zhang"
# 3. 更新本地 Slot 路由表
```

### 33.2 ASK 重定向

在 Slot 迁移过程中，节点返回 ASK 重定向。

```bash
# Slot 5461 正在从 Node B 迁移到 Node C
# 客户端向 Node B 发送 GET user:1001

> GET user:1001
(error) ASK 5461 192.168.1.13:6379
#      ↑    ↑
#      Slot  目标节点地址（Node C）

# ASK 和 MOVED 的区别：
# MOVED：永久重定向，客户端更新本地路由表
# ASK：临时重定向，不更新路由表
#   → 因为 Slot 还在迁移中，下次可能还在旧节点
```

### 33.3 Smart Client（智能客户端）

```
┌─────────────────────────────────────────────────────────────┐
│              Smart Client 工作流程                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   1. 启动时获取 Slot 路由表                                  │
│      → CLUSTER SLOTS 命令                                   │
│      → 获取每个 Slot 对应的节点信息                          │
│      → 构建本地路由表                                        │
│                                                             │
│   2. 命令发送                                                │
│      → 根据 Key 计算 Slot                                    │
│      → 查本地路由表找到对应节点                              │
│      → 直连对应节点发送命令                                  │
│                                                             │
│   3. 收到 MOVED 重定向                                       │
│      → 更新本地路由表                                        │
│      → 重试请求到新节点                                      │
│                                                             │
│   4. 收到 ASK 重定向                                         │
│      → 不更新路由表（临时）                                   │
│      → 向目标节点发送 ASKING 命令                            │
│      → 再发送原命令                                          │
│      → ASKING 告诉目标节点"我知道 Slot 在迁移"               │
│                                                             │
│   5. 定期刷新路由表                                          │
│      → 每 60s 或收到 MOVED 时刷新                            │
│      → 保持路由表最新                                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

```
┌─────────────────────────────────────────────────────────────┐
│                Slot 迁移过程                                 │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   迁移 Slot 5461 从 Node B → Node C                         │
│                                                             │
│   1. 标记 Slot 5461 正在迁移                                 │
```

## 35. 故障检测与故障转移

### 35.1 故障检测流程

```
┌─────────────────────────────────────────────────────────────┐
│              Redis Cluster 故障检测流程                      │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   1. PFAIL（疑似下线）                                       │
│      → Node A 向 Node B 发送 PING                           │
│      → 超过 cluster-node-timeout（15s）未收到 PONG          │
│      → Node A 标记 Node B 为 PFAIL                          │
│      → 通过 Gossip 传播 PFAIL 状态                           │
│                                                             │
│   2. FAIL（确定下线）                                        │
│      → 如果半数以上的 Master 节点都标记 Node B 为 PFAIL      │
│      → 第一个发现者将 Node B 标记为 FAIL                    │
│      → 广播 FAIL 消息给所有节点                              │
│      → 所有节点将 Node B 标记为 FAIL                         │
│                                                             │
│   3. 故障转移                                                │
│      → Node B 的 Slave（如 Slave B'）发起故障转移            │
│      → 从节点选出一个 Slave 提升为 Master                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 35.2 Slave 选举

```
┌─────────────────────────────────────────────────────────────┐
│              Slave 选举流程                                   │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   1. Slave 检测到 Master 下线                                │
│      → 等待一段时间（延迟，避免同时选举）                     │
│      → 延迟 = 500ms + random(0~500ms)                      │
│      → 如果 Slave 的 offset 落后较多 → 延迟更长             │
│      → 数据越新的 Slave越早发起选举                          │
│                                                             │
│   2. Slave 发起选举                                          │
│      → 更新自己的集群纪元（epoch + 1）                       │
│      → 向其他 Master 发送投票请求                            │
│      → "请投我一票，我要成为新 Master"                       │
│                                                             │
│   3. Master 投票                                             │
│      → 每个 Master 在一个 epoch 只能投一票                   │
│      → 先到先得                                              │
│      → 只有持有 Slot 的 Master 才能投票                      │
│      → 投票时检查 Slave 的 offset（数据要足够新）            │
│                                                             │
│   4. 获得多数票                                              │
│      → 需要 ⌊N/2⌋ + 1 票（N = Master 数量）                │
│      → 3 个 Master 需要 2 票                                │
│      → 5 个 Master 需要 3 票                                │
│                                                             │
│   5. 当选新 Master                                           │
│      → 广播 PONG 消息                                        │
│      → 告知所有节点自己是新 Master                           │
│      → 接管旧 Master 的所有 Slot                            │
│                                                             │
│   选举限制：                                                  │
│   - 只有 Master 才能投票                                    │
│   - 只有 Master 下线才会触发选举                             │
│   - 如果没有 Slave → 对应 Slot 不可用                       │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 35.3 Cluster vs Sentinel

| 维度 | Sentinel | Cluster |
|------|----------|---------|
| 架构 | 主从 + 哨兵监控 | 多 Master 分片 |
| 数据分片 | 不支持 | 16384 Slot |
| 容量 | 单节点内存限制 | 水平扩展 |
| 故障转移 | 哨兵负责 | 集群内部自治 |
| Multi-Key | 支持 | 限制（需 Hash Tag） |
| 适用场景 | 数据量中等、需高可用 | 大数据量、高并发 |

## 37. 缓存预热

### 37.1 为什么要缓存预热

```
系统刚启动时 → 缓存为空 → 所有请求打到数据库 → 数据库压力骤增

预热方案：
  1. 系统启动时加载热点数据到缓存
  2. 使用随机 TTL 避免同时过期
  3. 逐步放开流量（灰度发布）
```

### 37.2 缓存预热代码

```java
@Component
public class CacheWarmer implements ApplicationRunner {
    
    @Autowired
    private RedisTemplate<String, String> redisTemplate;
    
    @Autowired
    private UserMapper userMapper;
    
    @Override
    public void run(ApplicationArguments args) {
        // 1. 预热热点用户数据
        List<Long> hotUserIds = userMapper.selectHotUserIds(1000);
        for (Long userId : hotUserIds) {
            User user = userMapper.selectById(userId);
            String key = "user:" + userId;
            // 随机 TTL 防止同时过期
            int ttl = 3600 + ThreadLocalRandom.current().nextInt(600);
            redisTemplate.opsForValue().set(key, JSON.toJSONString(user), ttl, TimeUnit.SECONDS);
        }
        
        // 2. 预热布隆过滤器
        RBloomFilter<Long> bloomFilter = redisson.getBloomFilter("user:bloom");
        bloomFilter.tryInit(100000000L, 0.01);
        List<Long> allUserIds = userMapper.selectAllIds();
        for (Long userId : allUserIds) {
            bloomFilter.add(userId);
        }
    }
}
```

## 38. 缓存降级策略

### 38.1 降级场景

```
┌─────────────────────────────────────────────────────────────┐
│                缓存降级策略                                  │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   场景                        降级策略                       │
│   ─────────────────────────────────────────────              │
│   Redis 正常                  正常走缓存                     │
│   Redis 响应慢（>50ms）        降级到本地缓存（Caffeine）     │
│   Redis 不可用                 降级到数据库 + 熔断            │
│   数据库也慢                  返回降级数据（默认值）          │
│   数据库不可用                 返回 503 + 重试提示            │
│                                                             │
│   降级原则：                                                  │
│   1. 优先保核心功能，非核心功能降级                          │
│   2. 读操作可以降级（返回默认值）                             │
│   3. 写操作不能降级（必须保证数据不丢）                      │
│   4. 降级后要能自动恢复                                       │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 38.2 降级实现

```java
@Service
public class UserServiceWithFallback {
    
    @Autowired
    private CaffeineCache localCache;
    
    @Autowired
    private RedisTemplate<String, String> redisTemplate;
    
    @Autowired
    private UserMapper userMapper;
    
    @Autowired
    private CircuitBreaker circuitBreaker;
    
    public User getUser(Long userId) {
        String key = "user:" + userId;
        
        try {
            // 1. 查 Redis（带超时）
            String cached = redisTemplate.opsForValue().get(key);
            if (cached != null) {
                return JSON.parseObject(cached, User.class);
            }
        } catch (Exception e) {
            // Redis 不可用 → 降级到本地缓存
            User localUser = localCache.getIfPresent(key);
            if (localUser != null) {
                return localUser;
            }
            // 本地缓存也没有 → 查数据库（带熔断）
            return getUserFromDBWithCircuitBreaker(userId, key);
        }
        
        // 2. 查数据库
        return getUserFromDBWithCircuitBreaker(userId, key);
    }
    
    private User getUserFromDBWithCircuitBreaker(Long userId, String key) {
        return circuitBreaker.executeSupplier(() -> {
            User user = userMapper.selectById(userId);
            if (user != null) {
                try {
                    redisTemplate.opsForValue().set(key, JSON.toJSONString(user), 
                        3600, TimeUnit.SECONDS);
                } catch (Exception ignored) {
                    // Redis 不可用，只写本地缓存
                    localCache.put(key, JSON.toJSONString(user));
                }
            }
            return user;
        }, () -> {
            // 熔断降级：返回默认用户
            return getDefaultUser(userId);
        });
    }
    
    private User getDefaultUser(Long userId) {
        User user = new User();
        user.setId(userId);
        user.setName("系统繁忙");
        user.setAvatar("/default.png");
        return user;
    }
}
```

```java
// 基于 Redis + Lua 的令牌桶限流
public class RateLimiter {
    
    @Autowired
    private RedisTemplate<String, String> redisTemplate;
    
    private static final String LUA_SCRIPT = 
        "local key = KEYS[1]\n" +
        "local capacity = tonumber(ARGV[1])\n" +
        "local refillRate = tonumber(ARGV[2])\n" +
        "local now = tonumber(ARGV[3])\n" +
        "local requested = tonumber(ARGV[4])\n" +
        "\n" +
        "local bucket = redis.call('hmget', key, 'tokens', 'timestamp')\n" +
        "local tokens = tonumber(bucket[1])\n" +
        "local timestamp = tonumber(bucket[2])\n" +
        "\n" +
        "if tokens == nil then\n" +
        "    tokens = capacity\n" +
        "    timestamp = now\n" +
        "end\n" +
        "\n" +
        "-- 补充令牌\n" +
        "local delta = math.max(0, now - timestamp) * refillRate\n" +
        "tokens = math.min(capacity, tokens + delta)\n" +
        "\n" +
        "local allowed = tokens >= requested\n" +
        "if allowed then\n" +
        "    tokens = tokens - requested\n" +
        "end\n" +
        "\n" +
        "redis.call('hmset', key, 'tokens', tokens, 'timestamp', now)\n" +
        "redis.call('expire', key, 60)\n" +
        "\n" +
        "return {allowed and 1 or 0, tokens}";
    
    public boolean tryAcquire(String key, int capacity, int refillRate, int requested) {
        long now = System.currentTimeMillis() / 1000;
        DefaultRedisScript<List> script = new DefaultRedisScript<>(LUA_SCRIPT, List.class);
        List<Long> result = redisTemplate.execute(script, 
            Collections.singletonList(key),
            String.valueOf(capacity), 
            String.valueOf(refillRate),
            String.valueOf(now),
            String.valueOf(requested));
        return result.get(0) == 1L;
    }
}

// 使用
// 容量 100，每秒补充 10 个令牌，每次请求消耗 1 个
boolean allowed = rateLimiter.tryAcquire("api:user:rate", 100, 10, 1);
```

```java
        "local key = KEYS[1]\n" +
        "local now = tonumber(ARGV[1])\n" +

        "\n" +
        "return 1";

            Collections.singletonList(key),
            String.valueOf(now),
            String.valueOf(windowMs),

        return result == 1L;
    }
}
```

## 41. 面试高频题 20 问

### Q1: 缓存穿透和缓存击穿的区别？

```
缓存穿透：查询不存在的数据（数据在 DB 中也没有），每次请求都打到 DB。
缓存击穿：热点 Key 过期瞬间，大量并发请求同时打到 DB。

区别：穿透是数据不存在，击穿是数据存在但缓存过期了。
```

### Q2: 布隆过滤器的原理？为什么会有误判？

```
布隆过滤器使用 k 个哈希函数将元素映射到位数组的 k 个位置。
判断"存在"时检查 k 个位置是否都为 1。

误判原因：不同元素的哈希位置可能重叠。
  元素 A 设置了 bit[3], bit[7], bit[11]
  元素 B 设置了 bit[7], bit[12], bit[3]
  → 判断元素 C（实际不存在）时，如果 C 的哈希位置恰好是 [3,7,11]
  → 误判为"存在"

不会假阴性：如果任何一位是 0，说明该元素一定没被设置过。
```

### Q3: Redis 分布式锁的演进过程？

```
v1: SETNX → 死锁问题
v2: SETNX + EXPIRE → 非原子性
v3: SET NX EX → 锁过期后误删
v4: SET NX EX + UUID → GET+DEL 非原子
v5: SET NX EX + Lua 脚本释放 → 锁过期续期
v6: Redisson 看门狗 → 主从切换丢锁
v7: Redlock 多实例 → 最可靠
```

### Q4: Redisson 看门狗的原理？

```
看门狗是一个定时任务，每 TTL/3（默认 10s）检查一次：
  - 如果锁还被当前线程持有 → 续期（pexpire 重置 TTL）
  - 如果锁已释放或被其他人持有 → 停止续期

如果持锁线程宕机 → 看门狗也停了 → 锁在 30s 后自动过期 → 防死锁。
```

### Q5: Redlock 算法的过程？

```
1. 获取当前时间 T_start
2. 依次向 N 个独立 Redis 实例发送 SET NX EX
3. 如果超过 ⌈N/2⌉ 个成功且耗时 < TTL → 加锁成功
4. 如果失败 → 向所有实例发送 DEL（清理）
5. 释放锁 → 向所有实例发送 Lua 脚本释放

关键：N 个实例必须独立部署（不是主从），5 个实例容忍 2 个故障。
```

### Q6: 为什么 Redisson 用 Hash 而不是 String 存锁？

```
Hash 结构：field = "uuid:threadId", value = 重入次数
  → 支持可重入（同一线程可多次获取锁，计数 +1）
  → 解锁时计数 -1，减到 0 才真正删除锁

String 结构只能存一个值，无法记录重入次数。
```

### Q7: RDB 和 AOF 的区别？怎么选？

```
RDB：二进制快照，恢复快，可能丢数据。适合备份和灾难恢复。
AOF：追加写命令，数据安全（最多丢 1s），恢复慢。适合数据安全要求高。

推荐：Redis 4.0+ 用混合持久化（RDB + AOF），兼顾恢复速度和数据安全。
```

### Q8: fork 在 RDB 中的作用？有什么问题？

```
fork 创建子进程写 RDB 文件，主进程继续处理请求。
通过 COW 实现数据隔离（子进程看到 fork 时刻的快照）。

问题：
  1. fork 本身有开销（复制页表，大内存时可能 100~500ms）
  2. COW 期间如果主进程大量写操作 → 内存翻倍
  3. 大内存实例 fork 可能导致请求延迟
```

### Q9: Redis 主从复制的流程？

```
全量同步：
  1. Slave 发送 PSYNC ? -1（首次连接）
  2. Master 执行 BGSAVE 生成 RDB
  3. Master 发送 RDB 给 Slave
  4. Master 发送缓冲期间的增量命令
  5. Slave 加载 RDB 并执行增量命令

增量同步：
  1. Slave 发送 PSYNC replid offset（重连）
  2. Master 检查 offset 在 backlog 范围内
  3. Master 发送 offset~master_repl_offset 的命令
```

### Q10: Redis Sentinel 的故障转移过程？

```
1. 主观下线（SDOWN）：单个 Sentinel 认为 Master 不可达
2. 客观下线（ODOWN）：≥ quorum 个 Sentinel 同意下线
3. Raft 选举 Leader Sentinel
4. Leader 选择新 Master（优先级 > offset > run_id）
5. 向新 Master 发送 SLAVEOF NO ONE
6. 其他 Slave 指向新 Master
7. 通知客户端
```

### Q11: Redis Cluster 为什么是 16384 个 Slot？

```
1. 心跳消息：16384 bits = 2KB（如果 65536 则 8KB，太大）
2. 集群规模：推荐 ≤1000 节点，16384/1000≈16 个 Slot/节点，足够分散
3. 带宽折中：在消息大小和集群规模之间取得平衡
```

### Q12: MOVED 和 ASK 重定向的区别？

```
MOVED：永久重定向，Slot 已迁移，客户端更新本地路由表。
ASK：临时重定向，Slot 正在迁移中，客户端不更新路由表，下次还是问旧节点。

ASK 时客户端需要先发送 ASKING 命令再发送原命令。
```

### Q13: 缓存一致性怎么保证？

```
推荐方案：先更新 DB 再删缓存 + 延迟双删
  1. 更新 DB
  2. 删除缓存
  3. 延迟 500ms 再删一次

高一致性要求：加 Canal 监听 Binlog 异步删缓存
强一致性要求：用分布式事务（不推荐用 Redis 缓存）
```

### Q14: 缓存雪崩怎么解决？

```
1. 随机 TTL：TTL + random(0~600s)，避免同时过期
2. 多级缓存：L1 Caffeine + L2 Redis，Redis 宕机有 L1 兜底
3. 熔断降级：DB 压力大时返回降级数据
4. Redis 高可用：主从 + Sentinel / Cluster
```

### Q15: Redis 持久化 fork 的 COW 原理？

```
fork() 后父子进程共享物理内存页（只读）。
当父进程修改某页时，操作系统为子进程复制该页的副本。
子进程看到的是 fork 时刻的内存快照。

好处：不需要复制整个内存，只有被修改的页才复制。
风险：如果所有页都被修改 → 内存翻倍 → OOM。
```

### Q16: Redis Cluster 怎么做故障转移？

```
1. PFAIL：PING 超时 → 疑似下线
2. FAIL：半数 Master 同意 → 确定下线
3. Slave 选举：数据最新的 Slave 发起选举
4. Master 投票：每个 Master 一个 epoch 投一票
5. 获得多数票 → 成为新 Master
6. 接管旧 Master 的 Slot
7. 广播 PONG 通知所有节点
```

### Q17: Redisson 锁的 Lua 脚本做了什么？

```
加锁：
  if 锁不存在 → hset + pexpire → 返回 nil（成功）
  if 锁存在且是当前线程 → hincrby +1 + pexpire → 返回 nil（重入成功）
  else → 返回 TTL（失败）

解锁：
  if 锁不存在 → 返回 nil
  if 重入次数 > 0 → hincrby -1 + pexpire → 返回 0（不完全释放）
  if 重入次数 == 0 → del + publish → 返回 1（完全释放）
```

### Q18: Redis 的 appendfsync 三种策略？

```
always：每条命令都 fsync，最安全但性能最差（TPS 降半）
everysec：每秒 fsync 一次，最多丢 1 秒数据（推荐）
no：由 OS 决定何时 fsync，性能最好但不安全
```

### Q19: 延迟双删的延迟时间怎么定？

```
延迟时间 > 一次读请求的耗时（查缓存 miss + 查 DB + 写缓存）

保守值：500ms
推荐值：1s

如果读写分离延迟大（如 MySQL 主从延迟）：2~5s
```

### Q20: 如何设计一个生产级缓存方案？

```
1. 防穿透：布隆过滤器 + 空值缓存
2. 防击穿：互斥锁 / 逻辑过期
3. 防雪崩：随机 TTL + 多级缓存 + 熔断降级
4. 一致性：先更新 DB 再删缓存 + 延迟双删
5. 高可用：Redis Cluster + Sentinel
6. 持久化：混合持久化（RDB + AOF）
7. 监控：缓存命中率、慢查询、内存使用率
8. 预热：系统启动时加载热点数据
```

| `allkeys-lfu` | 所有 Key 中淘汰最少使用 |
| `allkeys-random` | 所有 Key 中随机淘汰 |
| `volatile-lru` | 设置了 TTL 的 Key 中淘汰最久未使用 |
| `volatile-lfu` | 设置了 TTL 的 Key 中淘汰最少使用 |
| `volatile-random` | 设置了 TTL 的 Key 中随机淘汰 |
| `volatile-ttl` | 设置了 TTL 的 Key 中淘汰最快过期的 |

## 附录 E：Redisson 分布式锁核心 Lua 脚本

### 加锁

```lua
if (redis.call('exists', KEYS[1]) == 0) then
    redis.call('hset', KEYS[1], ARGV[2], 1);
    redis.call('pexpire', KEYS[1], ARGV[1]);
    return nil;
end;
if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then
    redis.call('hincrby', KEYS[1], ARGV[2], 1);
    redis.call('pexpire', KEYS[1], ARGV[1]);
    return nil;
end;
return redis.call('pttl', KEYS[1]);
```

### 续期

```lua
if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then
    redis.call('pexpire', KEYS[1], ARGV[1]);
    return 1;
end;
return 0;
```

### 解锁

```lua
if (redis.call('hexists', KEYS[1], ARGV[3]) == 0) then
    return nil;
end;
local counter = redis.call('hincrby', KEYS[1], ARGV[3], -1);
if (counter > 0) then
    redis.call('pexpire', KEYS[1], ARGV[2]);
    return 0;
else
    redis.call('del', KEYS[1]);
    redis.call('publish', KEYS[2], ARGV[1]);
    return 1;
end;
```
