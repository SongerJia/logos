|知识点|笔记时重点写什么|
|---|---|
|**缓存穿透**|热 **定义**：查询一个不存在的 key（如 `id = -1` 或恶意攻击的大量不存在 id），每次都打到数据库。**解决方案**：①缓存空值（设短 TTL，如 5 分钟）②布隆过滤器（Bloom Filter，提前把所有可能存在的 key 哈希进去，不存在的直接拦截）③限流（对同一个 IP 的查询频率做限制）|
|**缓存击穿**|热 **定义**：一个热点 key 过期瞬间，大量并发请求同时打到数据库。**解决方案**：①互斥锁（只有一个线程查 DB 并写缓存，其余等待）②逻辑过期（缓存不设置 TTL，而是存一个 `expire_time` 字段，后台线程异步更新）|
|**缓存雪崩**|热 **定义**：大量 key 同时过期，或 Redis 宕机，导致所有请求打到数据库。**解决方案**：①过期时间加随机值（错开过期时间）②多级缓存（本地缓存 + Redis + DB）③熔断降级（Hystrix/Sentinel，缓存失效时直接返回默认值）④Redis 集群高可用（Sentinel/Cluster）|
|**缓存与数据库一致性**|热 **最高频架构题**。四种方案：①先更新 DB 再删除缓存（**推荐，Cache Aside Pattern**）②先删除缓存再更新 DB（有并发问题）③先更新 DB 再更新缓存（脏数据问题）④先更新缓存再更新 DB（事务失败导致不一致）。**为什么推荐方案一？** 因为删除比更新缓存更便宜，且下一次读请求会自动加载最新数据。⚠ **删除缓存失败怎么办？** 引入消息队列重试删除，或订阅 MySQL binlog（Canal）异步删除|
|**旁路缓存模式 Cache Aside**|读：先读缓存 → 命中返回 → 未命中读 DB → 结果写入缓存。写：先更新 DB → 再删除缓存。**这是业界标准做法**，要能手画读写流程图|
|**缓存预热**|系统上线时缓存为空，大量请求打到 DB。**解决方案**：上线前批量导入热点数据（离线计算好写脚本）、或者让少量流量先跑起来（灰度发布）|
|**缓存更新策略对比**|核 Cache Aside（旁路，推荐）/ Read/Write Through（穿透，缓存层负责同步 DB）/ Write Behind（异步回写，性能好但可能丢数据）。**做成对比表：数据一致性 / 复杂度 / 性能**|
