|知识点|笔记时重点写什么|
|---|---|
|**主从复制原理（异步模式）**|热 Master 的 binlog dump 线程 → Slave 的 IO 线程请求 binlog 并写入 relay log → Slave 的 SQL 线程重放 relay log 到本地数据库。**三个线程协作模型**要能手画出来。延迟来源：网络传输 + IO 写入 + SQL 重放|
|**binlog 三种格式对比**|STATEMENT / ROW / MIXED（已在 05 模块详细展开，这里侧重于**对复制的 影响**：ROW 格式下从库完全忠实还原，但大数据量 DML 时 binlog 会暴增；STATEMENT 在有不确定函数时可能导致主从不一致）|
|**GTID（全局事务标识符）**|热 UUID:sequence_number 格式，唯一标识每一个事务。优势：故障切换不再需要计算 binlog 位置（`CHANGE MASTER TO MASTER_AUTO_POSITION=1`）。GTID 复制模式下 Slave 只执行 Master 已提交的事务，跳过已执行的。**MySQL 5.6+ 推荐 GTID 模式**|
|**主从延迟问题与解决方案**|热 **工程中最常见的 MySQL 问题**。延迟原因：Slave 单线程 SQL 重放是大瓶颈（MySQL 5.6 前）。解决方案：①并行复制（MTS，基于 LOGICAL_CLOCK / WRITESET 方案）②半同步复制（semi-sync，Master 等待至少一个 Slave 确认 ACK 后才提交）③业务规避（主库写后读主库）④监控告警（Seconds_Behind_Master 阈值报警）|
|**半同步复制**|核 after_sync（Master 先写 binlog + sync 到磁盘，等 Slave ACK 后才提交事务）vs after_commit（Master 先提交事务再等 Slave ACK）。前者更安全（保证主从一致），后者性能略好。rpl_semi_sync_master_timeout 超时降级为异步|
|**一主多从 / 级联复制**|一主多从适合读密集场景（从库分担读压力）。级联复制（Master → Relay A → Slave B/C/D）减轻 Master 的 binlog dump 压力。**但级联增加了延迟链路**，需要权衡|
