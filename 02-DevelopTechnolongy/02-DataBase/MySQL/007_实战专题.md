|知识点|说明|
|---|---|
|**字符集与乱码问题**|utf8 vs utf8mb4（utf8 最多 3 字节，存不了 emoji；utf8mb4 才是真正的 UTF-8）。连接字符集 `character_set_connection`、服务端 `character_set_server`、客户端 `character_set_client`。三处统一才能防乱码。**新项目一律用 utf8mb4**|
|**数据类型选择最佳实践**|用 INT 还是 BIGINT？用 CHAR 还是 VARCHAR？用 DECIMAL 还是 DOUBLE（金额必须 DECIMAL！）？DATETIME vs TIMESTAMP（TIMESTAMP 受时区影响且有 2038 年问题）。**做一个类型选择速查表**|
|**大表处理方案**|定义：单表超千万行或超 5GB 就算大表。处理思路：历史数据归档（冷数据迁移到归档库）、分区表（RANGE/LIST/HASH 分区，InnoDB 原生支持）、最终走向分库分表|
|**Online DDL 变更**|`ALTER TABLE` 加字段的锁风险。MySQL 5.6+ 支持 Online DDL（INPLACE 算法，部分操作不锁表）。pt-online-schema-change 工具（创建影子表→同步数据→切换表名）。**生产环境加索引/加字段的标准操作流程**|
|**MySQL 参数调优速查**|innodb_buffer_pool_size（设为物理内存 60%-70%）、innodb_log_file_size（256MB-2GB）、max_connections（不是越大越好）、innodb_flush_log_at_trx_commit=1（安全优先）、sync_binlog=1（双一保障持久性）、innodb_io_capacity（SSD 可调高到 2000-4000）。**按 8G/16G/32G 机器给三套推荐配置**|
|**备份与恢复策略**|逻辑备份（mysqldump / mydumper，适合小数据量）vs 物理备份（xtrabackup / mysqlbackup，适合大数据量，热备不停机）。全量 + 增量备份策略。恢复演练（定期验证备份可用性）。**备份没做过恢复演练等于没备份**|
