|#|模式|架构特点|一致性|复杂度|适用场景|FlowPulse 使用|
|---|---|---|---|---|---|---|
|**4.3.1**|**主从复制 Master-Slave**|一个Master负责写 → 异步/同步复制到多个Slave → 读请求分发到Slave；VIP或Proxy实现故障转移|最终一致(异步)/强一致(半同步)|低|读多写少、允许短暂延迟|MySQL MGR / Redis Sentinel / RocketMQ Broker|
|**4.3.2**|**主备切换 Master-Standby**|主节点工作 → 备节点热待命(实时同步) → 主挂了备接管(ZooKeeper选举/VIP漂移/元数据服务协调)|强一致(同步)|中|写操作不能丢、要求快速切换|Seata Server HA / Nginx Keepalived|
|**4.3.3**|**多活/双活 Multi-Active**|多个数据中心同时对外服务；用户就近访问( DNS/GSLB 路由)；跨数据中心数据同步是最大挑战(CDC/双向同步)|因果一致/最终一致|高|跨地域容灾、全球化业务|V2.0 规划：杭州主 + 上海备(同城双活)|
|**4.3.4**|**共识集群 Consensus Cluster**|基于Raft/Paxos/ZAB协议；所有写入需要多数派确认(Quorum)；Leader处理读写的线性一致|强一致(Linearizable)|中高|元数据服务/配置中心/分布式锁|**Nacos CP模式(Raft)** / etcd / ZooKeeper|

> **💡 面试必答：三种模式的选型决策树**
> 
> ```
> 写多还是读多？
> ├── 读多写少 → 主从复制 (MySQL Slave / Redis Sentinel)
> ├── 写多读也多且不能丢 → 共识集群 (etcd / Nacos CP)
> ├── 要求极致可用(机房级容灾) → 多活/双活 (成本极高)
> └── 只需要一个备用(切换即可) → 主备切换 (Keepalived / Seata HA)
> ```
