|#|策略|核心流程|优点|缺点|面试追问|FlowPulse 采用|
|---|---|---|---|---|---|---|
|**4.7.1**|**滚动发布 Rolling Update**|K8s默认策略：逐个替换Pod(旧→新)；通过ReadinessProbe确保新Pod就绪后才销毁下一个旧Pod；支持MaxUnavailable/MaxSurge控制节奏|零停机、资源效率高、K8s原生支持|有版本共存期(新旧同时在线)、回滚需逐步回滚|"RollingUpdate过程中数据库Schema变更怎么办？"|**日常发布默认策略**：`maxSurge: 25%, maxUnavailable: 25%`|
|**4.7.2**|**蓝绿部署 Blue-Green**|维护两套完全相同的环境(蓝=当前生产/绿=新版本)；切换瞬间完成(DNS/LB权重切换)；回滚同样瞬间(切回蓝色)|回滚极快(秒级)、零风险回滚、完整测试环境|资源翻倍(两套全量环境)、数据迁移挑战(双写/切换)|"蓝绿部署期间数据库怎么处理？双写吗？"|**重大版本升级采用**：V1.0→V2.0时蓝绿部署，确保可秒级回滚|
|**4.7.3**|**金丝雀发布 Canary Release**|先发布少量新版本实例(1%/5%/10%流量)；观察指标无误后逐步放大流量比例(25%→50%→100%)；可按User/Header/Cookie/Weight分流|风险可控(只影响少量用户)、可精准验证|发布周期较长、需要完善的监控和快速回滚能力|"金丝雀发布怎么做灰度引流？基于Header还是Cookie？"|**首次上线+重要功能**：内部用户(白名单Header)→1%随机用户→全量|
|**4.7.4**|**Feature Flag (功能开关)**|代码中预埋开关；运行时动态控制功能的开启/关闭/灰度比例；解耦部署和发布(代码部署了但不一定对所有用户开放)|极致灵活(随时关闭有问题的功能)、无需重新部署|代码复杂度增加(大量if判断)、开关管理本身成为负担|"Feature Flag多了之后怎么管理？有专门的平台吗？"|Spring Cloud Config / Nacos配置中心管理开关：`flowpulse.engine.v2-mode: false`|

> **💡 FlowPulse 发布策略选择指南**
> 
> ```
> 发布场景                    推荐策略          理由
> ─────────────────────────────────────────────────────
> 日常Bugfix / 小功能          Rolling Update   快速、零停机、K8s默认
> 数据库Schema变更             蓝绿部署          避免新旧代码同时操作不同Schema
> 引擎核心逻辑重构              金丝雀 + 蓝绿     先小流量验证再全量，保留快速回滚能力
> 新增可选Feature             Feature Flag      随时可关，不影响主干
> 紧急Hotfix(生产事故)          滚动 + 紧急回滚   速度优先，先止血再说
> ```
