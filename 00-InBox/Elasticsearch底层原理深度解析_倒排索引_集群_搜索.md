### 1.2 核心概念

| 概念 | 说明 | 类比 |
|------|------|------|
| **Cluster** | 集群，由多个节点组成 | 数据库实例组 |
| **Node** | 集群中的一个服务器节点 | 一台数据库服务器 |
| **Index** | 逻辑索引，相当于数据库 | Database |
| **Type** | 类型（ES 7.x 已废弃） | Table |
| **Document** | 文档，最小数据单元 | Row |
| **Field** | 字段 | Column |
| **Shard** | 分片，Index 的物理分片 | 分表 |
| **Replica** | 副本，Shard 的复制 | 读写分离 |
| **Segment** | Lucene 中的物理段，不可变 | 数据文件 |
| **Mapping** | 映射，定义字段类型 | Table Schema |
| **Cluster State** | 集群状态（元数据 + 路由表） | Master 元数据 |

## 第二部分：倒排索引原理（核心）

### 2.1 正向索引 vs 倒排索引

**正向索引**（MySQL B+Tree）：
```
文档ID → 文档内容
Doc1 → "The quick brown fox"
Doc2 → "The lazy dog"
Doc3 → "The quick dog"

查询 "quick" → 遍历所有文档 → O(N)
```

**倒排索引**（Elasticsearch）：
```
词项 → 文档ID列表
"quick" → [Doc1, Doc3]
"brown" → [Doc1]
"fox"   → [Doc1]
"dog"   → [Doc2, Doc3]
"lazy"  → [Doc2]
"the"   → [Doc1, Doc2, Doc3]

查询 "quick" → 直接查倒排表 → O(1)
```

### 2.3 FST（Finite State Transducer）详解

FST 是 Lucene 用来存储 Term Index 的数据结构，它将所有 Term 的前缀和后缀进行压缩。

```
假设有以下 Term（排序后）：
cat
can
dog
dogs

构建 FST：

         ┌──→ (g) ──→ [终态: dog]
         │
(c)──→ (a) ──→ (n) ──→ [终态: can]
 │         │
 │         └──→ (t) ──→ [终态: cat]
 │
(d)──→ (o) ──→ (g) ──→ [终态: dog]
                 │
                 └──→ (s) ──→ [终态: dogs]

特点：
1. 共享前缀：cat/can 共享 "ca"
2. 共享后缀：dog/dogs 共享 "dog"
3. 最终状态标记 Term 结束
4. 节点上存储输出（output）：指向 Term Dictionary 的位置
```

**FST 的优势**：

| 特性 | HashMap | Trie（前缀树） | FST |
|------|---------|----------------|-----|
| 共享前缀 | ❌ | ✅ | ✅ |
| 共享后缀 | ❌ | ❌ | ✅ |
| 内存占用 | 高 | 中 | 低 |
| 查询速度 | O(1) | O(k) | O(k) |
| 支持前缀搜索 | ❌ | ✅ | ✅ |
| 支持通配符 | ❌ | ✅ | ✅ |

> k = key 长度

**源码层面**（Lucene `FST.java`）：
```java
// Lucene FST 核心类
public class FST<T> {
    // FST 的输入（弧上的 label）
    final int[] bytesArray;
    // 节点信息
    final BytesStore bytes;
    
    // 查找 Term
    public T get(BytesRef input) {
        // 从初始节点开始
        int arc = getFirstArc(getArc(0));
        // 逐字符遍历 FST
        for (int i = 0; i < input.length; i++) {
            arc = findTargetArc(input.bytes[input.offset + i], arc, getArc(1));
            if (arc == 0) return null;  // 不存在
        }
        // 返回最终输出
        return readFinalOutput(arc);
    }
}
```

### 2.4 Term Dictionary 存储

Term Dictionary 存储在 `.tim` 文件中，按 Term 的字典序排列。

```
.tim 文件结构：
┌───────────────────────────────────────┐
│  Term Dictionary Header               │
├───────────────────────────────────────┤
│  Block 0                              │
│  ┌─────────────────────────────┐      │
│  │ "apple"   → ptr=100         │      │
│  │ "banana"  → ptr=200         │      │
│  │ "cherry"  → ptr=300         │      │
│  │ ... (25 terms per block)    │      │
│  └─────────────────────────────┘      │
├───────────────────────────────────────┤
│  Block 1                              │
│  ┌─────────────────────────────┐      │
│  │ "date"    → ptr=400         │      │
│  │ "elder"   → ptr=500         │      │
│  │ ...                          │      │
│  └─────────────────────────────┘      │
├───────────────────────────────────────┤
│  ...                                  │
├───────────────────────────────────────┤
│  Term Dictionary Footer               │
│  (指向各 Block 的索引)                 │
└───────────────────────────────────────┘

特点：
1. 每 25 个 Term 为一个 Block
2. Block 的第一个 Term 存储在 FST 中（.tip 文件）
3. 查找时先查 FST 定位 Block，再在 Block 内二分查找
```

**Lucene 8.x 的优化 — SIMD**：
```
Lucene 8 引入了 SIMD（Single Instruction Multiple Data）指令优化
Term Dictionary 的二分查找：
- 使用 AVX2 指令一次比较 8 个 Term
- 比 JDK Arrays.binarySearch 快 2-3 倍
- 源码: Lucene80PostingsReader.java
```

### 2.5 Posting List 存储与压缩

Posting List 是倒排索引最核心的数据——每个 Term 对应的文档列表。

```
原始 Posting List（DocID 数组）：
[73, 300, 302, 332, 343, 372, 400, 453, 473, 500, 523, 600, 630, 703, 730, 800]

问题：如果 DocID 跨度很大，直接存数组浪费空间
```

#### 2.5.1 Frame of Reference（FOR）压缩

```
Step 1: 计算差值（Delta Encoding）
原始: [73, 300, 302, 332, 343, 372, 400, 453, 473, 500]
差值: [73,  227,   2,   30,   11,   29,   28,   53,   20,   27]

Step 2: 分块（每 256 个一组）并计算每块所需 bit 数
Block 1: [73, 227, 2, 30, 11, 29, 28, 53, 20, 27]
         最大值 = 227 → 需要 8 bits

Step 3: 每个值用 8 bit 存储
┌────────────────────────────────────────────────┐
│  Block Info: bit_count=8, block_size=10        │
├────────────────────────────────────────────────┤
│  73     │ 227    │ 2      │ 30     │ 11     │ │
│  (8bit) │ (8bit) │ (8bit) │ (8bit) │ (8bit) │ │
├────────────────────────────────────────────────┤
│  29     │ 28     │ 53     │ 20     │ 27     │ │
│  (8bit) │ (8bit) │ (8bit) │ (8bit) │ (8bit) │ │
└────────────────────────────────────────────────┘

压缩效果：原始 10 × 32 bit = 320 bit → 压缩后 80 + 10×8 = 160 bit
压缩率 ≈ 50%
```

#### 2.5.2 Roaring Bitmaps（ roaring 位图）

当 Posting List 中的 DocID 非常密集时（如连续的 ID），Lucene 使用 **Roaring Bitmap** 压缩。

```
将 DocID 空间分成 65536 个桶（高 16 位为桶号）：

DocID = 65536 × bucket_id + offset

┌───────────────────────────────────────────────────────┐
│  Bucket 0 (DocID 0-65535)                              │
│  ┌─────────────────────────────────────────┐          │
│  │  Container 选择策略:                    │          │
│  │  - 如果元素数 > 4096: 使用 Bitmap       │          │
│  │    → 65536 bit = 8KB                    │          │
│  │  - 如果元素数 ≤ 4096: 使用 Sorted Array  │          │
│  │    → 4096 × 16 bit = 8KB                │          │
│  └─────────────────────────────────────────┘          │
├───────────────────────────────────────────────────────┤
│  Bucket 1 (DocID 65536-131071)                         │
│  ...                                                   │
├───────────────────────────────────────────────────────┤
│  Bucket N                                              │
│  ...                                                   │
└───────────────────────────────────────────────────────┘

为什么阈值是 4096？
- Bitmap: 固定 65536 bit = 8192 bytes
- Array: N × 16 bit（offset 是 16 位）
- 当 N × 16 bit < 8192 bit → N < 512 ❌（实际 N < 4096）
- 实际 Lucene 的计算：
  Array 需要 2 × N bytes，Bitmap 需要 8192 bytes
  当 N > 4096 时，Bitmap 更优

Roaring Bitmap 的优势：
1. 稀疏数据 → Array 节省空间
2. 密集数据 → Bitmap 快速位运算
3. 两个 Bitmap 的 AND/OR 运算非常高效（SIMD 加速）
```

### 2.6 BM25 评分算法

```
BM25（Best Matching 25）是 ES 默认的评分算法（Lucene 6+）

score(D, Q) = Σ IDF(qi) × (f(qi, D) × (k1 + 1))
                        / (f(qi, D) + k1 × (1 - b + b × |D| / avgdl))

参数说明：
- qi: 查询词 i
- f(qi, D): 词 qi 在文档 D 中的出现频率
- |D|: 文档 D 的长度
- avgdl: 所有文档的平均长度
- k1: 词频饱和参数（默认 1.2）
- b: 长度归一化参数（默认 0.75）

IDF(qi) = ln(1 + (N - n(qi) + 0.5) / (n(qi) + 0.5))

- N: 文档总数
- n(qi): 包含词 qi 的文档数
```

**BM25 vs TF-IDF**：

```
                    TF-IDF                        BM25
                ─────────────                  ─────────
TF 计算:    TF = raw_freq                     TF = raw_freq × (k1+1) / (raw_freq + k1×(...))
            线性增长，无上限                  有饱和值，词频到一定程度不再增加分数

IDF 计算:   IDF = log(N/n)                   IDF = ln(1 + (N-n+0.5)/(n+0.5))
            可能出现负值（n > N/2）           始终为正值

文档长度:    不考虑（或简单归一化）            考虑文档长度，长文档会被惩罚

效果:       高频词得分过高                    更符合信息检索理论，效果更好
```

```
TF-IDF vs BM25 词频得分曲线对比：

score
  │
1.0│        ─────── BM25（有饱和值）
  │      ╱
0.8│    ╱
  │  ╱     ─────── TF-IDF（线性增长）
0.6│╱
  │
0.4│
  │
0.2│
  │
0.0└────┬────┬────┬────┬────┬──── TF
   0    2    4    6    8   10
```

### 3.2 为什么 Segment 不可变

```
不可变（Immutable）带来的好处：
┌─────────────────────────────────────────────────────┐
│  1. 不需要锁 → 读取无并发问题                         │
│  2. 可以被内核文件系统缓存 → 高效读取                  │
│  3. 不需要为删除的文档维护额外数据结构                 │
│  4. 简化了系统设计 → 不需要 MVCC                      │
└─────────────────────────────────────────────────────┘

不可变带来的问题：
┌─────────────────────────────────────────────────────┐
│  1. 删除文档 → 在 .live 文件中标记删除（tombstone）   │
│  2. 更新文档 → 标记旧文档删除 + 写入新文档             │
│  3. Segment 越来越多 → 搜索时需遍历所有段              │
│  → 解决方案：Segment Merge                           │
└─────────────────────────────────────────────────────┘
```

### 3.4 Segment Merge（段合并）

```
为什么需要合并：
1. 减少 Segment 数量 → 减少搜索时需要遍历的段
2. 物理删除标记为删除的文档 → 释放磁盘空间
3. 合并小段 → 减少文件句柄数量

合并过程：
         合并前                           合并后
┌────────────────────┐         ┌────────────────────┐
│ Segment 0 (1000 docs)│       │                    │
│ .doc .tim .tip      │       │  Segment 3         │
├────────────────────┤        │  (2800 docs)       │
│ Segment 1 (800 docs)│ ──→   │  .doc .tim .tip    │
│ .doc .tim .tip      │        │                    │
├────────────────────┤        │  Segment 0,1,2     │
│ Segment 2 (1000 docs)│       │  被标记为已删除      │
│ .doc .tim .tip      │        │  等待物理删除        │
└────────────────────┘         └────────────────────┘
```

#### 3.4.1 合并策略

```
Lucene 提供两种合并策略：

1. TieredMergePolicy（默认，ES 使用）
   ─────────────────────────────────
   - 分层合并，每层最多允许 max_segments_per_tier 个段
   - 默认每层最多 10 个段
   - 合并时选择大小相近的段进行合并
   - 倾向合并小段

   参数：
   index.merge.policy.max_merge_at_once = 10  // 一次最多合并多少段
   index.merge.policy.segments_per_tier = 10  // 每层最多多少段
   index.merge.policy.max_merged_segment = 5gb // 单段最大大小

2. LogByteSizeMergePolicy（旧版）
   - 按日志大小合并
   - 合并条件：段大小超过阈值就合并
```

#### 3.4.2 合并触发时机

```
┌──────────────────────────────────────────────────────────┐
│                  Segment Merge 触发时机                    │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  1. IndexWriter 自动触发                                  │
│     - 每次 flush 后检查是否需要合并                         │
│     - 后台线程 ConcurrentMergeScheduler 执行合并           │
│                                                          │
│  2. Force Merge（手动触发）                                │
│     POST /index/_forcemerge?max_num_segments=1           │
│     - 强制合并到指定段数                                    │
│     - 注意：会阻塞 I/O，不要在高峰期执行                    │
│     - 建议在低峰期执行 max_num_segments=1                  │
│                                                          │
│  3. 索引关闭/打开时                                       │
│     - 不会主动触发，但会检查是否需要合并                     │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

```java
// Elasticsearch TransportShardBulkAction.java（简化）

public class TransportShardBulkAction extends TransportWriteAction {
    
    @Override
    protected void performOperationOnPrimary(...) {
        // 1. 根据操作类型分发
        switch (request.opType()) {
            case INDEX:
                executeIndexRequestOnPrimary(...);
                break;
            case DELETE:
                executeDeleteRequestOnPrimary(...);
                break;
            case UPDATE:
                executeUpdateRequestOnPrimary(...);
                break;
        }
    }
    
    private BulkItemResponse executeIndexRequestOnPrimary(...) {
        // 2. 解析文档
        SourceToParse sourceToParse = new SourceToParse(
            index, id, source, routing, MediaTypeRegistry.JSON
        );
        
        // 3. 调用 IndexShard.index() 
        IndexResult indexResult = primary.index(sourceToParse);
        
        // 4. 返回结果
        return new BulkItemResponse(...);
    }
}

// IndexShard.java（简化）
public class IndexShard {
    
    public IndexResult index(SourceToParse source) {
        // 调用 Lucene IndexWriter
        Engine.IndexResult result = engine.index(source);
        return result;
    }
}

// InternalEngine.java（简化，Lucene 写入核心）
public class InternalEngine {
    
    public IndexResult index(SourceToParse source) {
        // 1. 获取文档号（如果文档已存在，就是更新操作）
        IndexWriter writer = indexWriter;
        
        // 2. 解析文档 → 构建 Lucene Document
        ParsedDocument doc = docMapper.parse(source);
        
        // 3. 写入 Lucene（会写入 Index Buffer + Translog）
        writer.updateDocument(doc);
        
        // 4. 返回结果
        return new IndexResult(doc);
    }
}
```

### 4.3 Lucene IndexWriter 写入

```java
// Lucene IndexWriter.java（核心写入逻辑，简化）

public class IndexWriter {
    
    // 全局文档 ID 计数器
    private DocumentsWriter documentsWriter;
    
    public long updateDocument(Document doc) {
        // 1. 获取下一个文档 ID
        DocumentsWriterPerThread dwpt = documentsWriter.getDWPT();
        
        // 2. 在 DWPT 中处理文档
        long seqNo = dwpt.updateDocument(doc);
        
        return seqNo;
    }
}

// DocumentsWriterPerThread.java（每个线程一个 DWPT，简化）
public class DocumentsWriterPerThread {
    
    // 当前 Segment 的文档号
    private int numDocsInRAM;
    
    public long updateDocument(Document doc) {
        // 1. 如果文档已存在，先标记旧文档删除
        // 2. 遍历文档的所有 Field
        for (IndexableField field : doc) {
            // 3. 对每个 Field 调用对应的 Consumer
            fieldConsumer.processField(field);
        }
        
        // 4. 增加 RAM 中的文档计数
        numDocsInRAM++;
        
        // 5. 检查是否需要 flush
        if (numDocsInRAM >= maxBufferedDocs ||
            bytesUsed >= ramBufferSizeMB) {
            flush();
        }
        
        return seqNo;
    }
    
    private void flush() {
        // 1. 将 Index Buffer 中的数据写成新的 Segment
        // 2. Segment 写到 Directory（文件系统）
        // 3. 但此时 Segment 还在内存中（未 fsync）
        // 4. 更新 SegmentInfos
    }
}
```

### 5.2 Query Phase 详解

```java
// Elasticsearch QueryPhase 简化源码

public class QueryPhase {
    
    public void execute(SearchContext context) {
        // 1. 解析查询
        Query query = context.query();
        
        // 2. 创建 Collector（结果收集器）
        Collector collector = createCollector(context);
        
        // 3. 遍历所有 Segment 执行查询
        IndexSearcher searcher = context.searcher();
        searcher.search(query, collector);
        
        // 4. 收集 Top N 结果
        TopDocs topDocs = collector.topDocs();
        
        // 5. 返回 DocID + Score
        context.queryResult().topDocs(topDocs);
    }
}

// Lucene IndexSearcher.search() 简化源码

public class IndexSearcher {
    
    public void search(Query query, Collector collector) {
        // 1. 重写 Query（将模糊查询转为精确查询）
        Query rewritten = query.rewrite(this);
        
        // 2. 创建 Weight（查询权重，包含 Scorer）
        Weight weight = createWeight(rewritten, ScoreMode.COMPLETE, 1);
        
        // 3. 遍历所有 Segment
        for (LeafReaderContext leaf : leafContexts) {
            // 3.1 为每个 Segment 创建 Scorer
            Scorer scorer = weight.scorer(leaf);
            
            if (scorer == null) continue;  // 该 Segment 无匹配
            
            // 3.2 创建 LeafCollector
            LeafCollector leafCollector = collector.getLeafCollector(leaf);
            
            // 3.3 遍历匹配的文档
            DocIdSetIterator iterator = scorer.iterator();
            while (iterator.nextDoc() != DocIdSetIterator.NO_MORE_DOCS) {
                // 3.4 计算分数
                float score = scorer.score();
                
                // 3.5 收集结果
                leafCollector.collect(iterator.docID(), score);
            }
        }
    }
}
```

```
┌──────────────────────────────────────────────────────────────┐

│  1. 创建大小为 10 的最小堆                                     │
│  2. 遍历所有匹配文档                                           │
```

### 5.5 Fetch Phase 详解

```java
// Elasticsearch FetchPhase 简化源码

public class FetchPhase {
    
    public void execute(SearchContext context) {
        // 1. 获取 Query Phase 的 TopDocs
        TopDocs topDocs = context.queryResult().topDocs();
        
        // 2. 提取 DocID 列表
        int[] docIds = extractDocIds(topDocs);
        
        // 3. 遍历每个 Segment 获取文档
        for (ScoreDoc scoreDoc : topDocs.scoreDocs) {
            int docId = scoreDoc.doc;
            float score = scoreDoc.score;
            
            // 4. 从 Stored Fields 加载文档
            StoredFieldsReader storedFields = reader.storedFields();
            storedFields.visitDocument(docId, fieldVisitor);
            
            // 5. 从 Source 加载 _source
            String source = getSource(docId);
            
            // 6. 构建返回结果
            SearchHit hit = new SearchHit(docId, source, score);
            context.fetchResult().hit(hit);
        }
    }
}
```

### 5.6 搜索性能优化 — DFS Query Then Fetch

```
标准 Query Then Fetch 的问题：
- BM25 的 IDF 在每个分片独立计算
- 不同分片的 IDF 可能不同
- 某些分片可能 IDF 偏差，导致全局排序不准确

DFS Query Then Fetch（三阶段）：
┌──────────────────────────────────────────────────────────────┐
│  Phase 0: DFS（Distributed Frequency Search）                │
│  └─ 从所有分片收集 Term 的文档频率（DocFreq）                  │
│     └─ 计算全局 IDF                                           │
│                                                              │
│  Phase 1: Query                                              │
│  └─ 使用全局 IDF 计算分数                                     │
│  └─ 取 Top N 的 DocID + Score                                │
│                                                              │
│  Phase 2: Fetch                                              │
│  └─ 取完整文档                                                │
└──────────────────────────────────────────────────────────────┘

使用方式：
GET /index/_search?search_type=dfs_query_then_fetch

适用场景：分片数据分布不均匀时，提高评分准确性
缺点：多一轮请求，性能略低
默认不开启，大多数场景标准 Query Then Fetch 足够准确
```

### 5.8 Doc Values 在聚合中的作用

```
聚合为什么用 Doc Values 而不用倒排索引？

倒排索引聚合过程（低效）：
1. 查找 "category" 字段的倒排索引
2. 遍历所有 Term
3. 对每个 Term，遍历其 Posting List
4. 累计每个 Term 的文档数
→ 需要遍历整个倒排索引，效率低

Doc Values 聚合过程（高效）：
1. 加载 "category" 字段的 Doc Values
2. Doc Values 是有序的（按 DocID 排序）
3. 遍历 Doc Values，用 HashMap 统计每个值出现的次数
4. 排序取 Top N
→ 顺序读取，对 CPU Cache 友好，效率高

┌──────────────────────────────────────────────────────────────┐
│  Doc Values 在排序/聚合中的优势                                │
│                                                              │
│  ┌─────────────┐         ┌─────────────────┐                │
│  │ 倒排索引     │         │ Doc Values       │                │
│  │ (列式存储)   │         │ (正向索引)       │                │
│  │             │         │                 │                │
│  │ Term→Docs   │         │ Doc→Value       │                │
```

## 第七部分：集群管理与 Master 选举

### 7.1 Zen2 发现与选举机制（ES 7.x）

```
ES 7.x 使用 Zen2（改进版）替代了旧的 Zen 机制。

Zen2 的核心改进：
1. 解决了 "脑裂" 问题
2. 引入了 voting configuration（投票配置）
3. 自动管理投票成员数量
4. 支持大规模集群（旧的 Zen 不支持 > 集群半数节点）

选举流程：
┌──────────────────────────────────────────────────────────────┐
│                    Zen2 选举流程                               │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  ┌─────────────────────────────────────────────┐            │
│  │  Phase 1: Ping                              │            │
│  │  ─────────                                  │            │
│  │  所有节点互相 Ping，收集集群中活跃的节点       │            │
│  │  包括 cluster_state.version                  │            │
│  └─────────────────────────────────────────────┘            │
│                       │                                      │
│                       ▼                                      │
│  ┌─────────────────────────────────────────────┐            │
│  │  Phase 2: 选举                              │            │
│  │  ─────────                                  │            │
│  │  规则:                                       │            │
│  │  1. 只有 master_eligible 节点参与选举        │            │
│  │  2. cluster_state.version 最高的优先         │            │
│  │  3. version 相同则选 node_id 最小的          │            │
│  │  4. 需要获得 voting configuration 的多数票    │            │
│  │     majority = (voting_members + 1) / 2      │            │
│  └─────────────────────────────────────────────┘            │
│                       │                                      │
│                       ▼                                      │
│  ┌─────────────────────────────────────────────┐            │
│  │  Phase 3: 发布                              │            │
│  │  ─────────                                  │            │
│  │  新 Master 发布 Cluster State               │            │
│  │  所有节点确认收到后，选举完成                  │            │
│  └─────────────────────────────────────────────┘            │
│                                                              │
│  Voting Configuration（投票配置）:                            │
│  ┌────────────────────────────────────────────────┐          │
│  │  - ES 自动维护一个 voting configuration         │          │
│  │  - 通常为集群中所有 master_eligible 节点          │          │
│  │  - 当节点数 > 3 时，自动裁剪到 3 个投票成员       │          │
│  │  - 保证 majority 总是集群半数                    │          │
│  │  - 裁剪算法: 选择最近活跃的 3 个 master 节点      │          │
│  └────────────────────────────────────────────────┘          │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 7.2 脑裂问题与解决

```
脑裂场景（旧 Zen 的问题）：

┌──────────────────────────────────────────────────────────────┐
│                  脑裂问题                                     │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  5 个节点: [A, B, C, D, E]                                   │
│  A 是 Master                                                 │
│                                                              │
│  网络分区: [A, B] | [C, D, E]                                │
│                                                              │
│  ┌───────────┐          ┌───────────────────┐               │
│  │ [A, B]    │          │ [C, D, E]         │               │
│  │ A 认为只有 │          │ C, D, E 互相能通信  │               │
│  │ 2 个节点   │          │ 认为有 3 个节点    │               │
│  │ A 不再是   │          │ 3 > 5/2=2.5       │               │
│  │ Master    │          │ 选举 C 为新 Master │               │
│  │ (不满足    │          │                   │               │
│  │  quorum)  │          │                   │               │
│  └───────────┘          └───────────────────┘               │
│                                                              │
│  问题: 两个 Master → 数据不一致                               │
│  原因: 旧 Zen 的 minimum_master_nodes 需要手动配置            │
│                                                              │
└──────────────────────────────────────────────────────────────┘

Zen2 的解决方案:

┌──────────────────────────────────────────────────────────────┐
│                  Zen2 自动防脑裂                               │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  1. Voting Configuration 自动管理                             │
│     ┌────────────────────────────────────────┐              │
│     │ 5 个 master 节点: [A, B, C, D, E]      │              │
│     │ Voting Config: {A, B, C}               │              │
│     │ Majority = (3+1)/2 = 2                 │              │
│     │                                        │              │
│     │ 网络分区: [A, B] | [C, D, E]           │              │
│     │ [A, B] 中有 2 个投票成员 → 2 ≥ 2        │              │
│     │ [C, D, E] 中有 1 个投票成员 → 1 < 2     │              │
│     │                                        │              │
│     │ → [A, B] 可以维持 Master               │              │
│     │ → [C, D, E] 无法选举新 Master           │              │
│     │ → 不会出现两个 Master                   │              │
│     └────────────────────────────────────────┘              │
│                                                              │
│  2. 自动调整 Voting Configuration                             │
│     ┌────────────────────────────────────────┐              │
│     │  - 节点加入集群时，自动加入 Voting Config│              │
│     │  - 节点离开时，如果超过 3 个投票成员      │              │
│     │    自动裁剪                              │              │
│     │  - 保证 Voting Config 始终为奇数          │              │
│     └────────────────────────────────────────┘              │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 7.4 Master 发布 Cluster State

```
┌──────────────────────────────────────────────────────────────┐
│              Master 发布 Cluster State 流程                   │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  ① Master 变更 Cluster State                                 │
│     例: 创建新索引 → 增加 metadata.indices                     │
│     version: 42 → 43                                        │
│                                                              │
│  ② Master 发送 Cluster State 给所有节点                       │
│     ┌──────────────────┐                                     │
│     │ Master           │                                     │
│     │ version=43       │                                     │
│     │ ──→ Node B       │ "这是新的 Cluster State v43"         │
│     │ ──→ Node C       │ "请确认"                             │
│     │ ──→ Node D       │                                     │
│     └──────────────────┘                                     │
│                                                              │
│  ③ 每个节点检查是否接受                                       │
│     ┌──────────────────┐                                     │
│     │ Node B           │ "我的 version=42 < 43"              │
│     │                  │ "接受！"                             │
│     │ ←── ACK ────────│                                     │
│     └──────────────────┘                                     │
│                                                              │
│  ④ Master 收集多数确认                                        │
│     需要 majority 的 ACK                                      │
│     如果收到 majority ACK → commit                           │
│     如果超时未收到 → 放弃                                     │
│                                                              │
│  ⑤ Master 发送 commit 指令                                   │
│     "所有节点，请应用 v43"                                    │
│     ┌──────────────────┐                                     │
│     │ Master           │ ──→ "Commit v43"                   │
│     │                  │ ──→ Node B: Apply v43              │
│     │                  │ ──→ Node C: Apply v43              │
│     └──────────────────┘                                     │
│                                                              │
│  ⑥ 所有节点应用新的 Cluster State                             │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐    │
│  │  两阶段提交（2PC）:                                  │    │
│  │  Phase 1: Prepare → 各节点确认可以应用                │    │
│  │  Phase 2: Commit → 各节点正式应用                    │    │
│  │                                                      │    │
│  │  如果 Phase 1 失败（未获得多数确认）:                  │    │
│  │  → Master 放弃，不应用变更                            │    │
│  │  → Master 降级为普通节点，触发重新选举                 │    │
│  └──────────────────────────────────────────────────────┘    │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

```
│  分配流程:                                                    │
│  ┌────────────────────────────────────────────────┐          │
│  │  Master 的 AllocationDecider（决策器）链       │          │
│  │                                                │          │
│  │  ├── SameShardAllocator                       │          │
│  │  │   └─ 主副本不能在同一节点                    │          │
│  │  │                                            │          │
│  │  ├── FilterAllocationDecider                   │          │
│  │  │   └─ 根据 node.attr 过滤（如 data/box_type）│          │
│  │  │                                            │          │
│  │  ├── DiskThresholdDecider                      │          │
│  │  │   └─ 磁盘水位线检查                          │          │
│  │  │   └─ high.watermark=85% → 不分配           │          │
│  │  │   └─ flood_stage=95% → 只读                │          │
│  │  │                                            │          │
│  │  ├── ThrottlingAllocationDecider               │          │
│  │  │   └─ 限制恢复速度                            │          │
│  │  │                                            │          │
│  │  └── AwarenessAllocationDecider                │          │
│  │      └─ 机架/机房感知                          │          │
│  │      └─ cluster.routing.allocation.awareness   │          │
│  └────────────────────────────────────────────────┘          │
│                                                              │
│  再平衡（Rebalance）:                                        │
│  ┌────────────────────────────────────────────────┐          │
│  │  当节点负载不均匀时，Master 自动迁移分片          │          │
│  │                                                │          │
│  │  cluster.routing.allocation.balance:           │          │
│  │    shard: 0.45    // 每节点分片数权重            │          │
│  │    index: 0.55    // 每节点某索引的分片数权重     │          │
│  │    threshold: 1.0 // 不平衡阈值                │          │
│  │                                                │          │
│  │  weight(node) = shard_balance × nodeShards     │          │
│  │               + index_balance × indexShards    │          │
│  │                                                │          │
│  │  如果 max(weight) - min(weight) > threshold   │          │
│  │  → 触发分片迁移                                 │          │
│  └────────────────────────────────────────────────┘          │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 第八部分：分片路由与数据分布

### 8.1 分片路由公式

```
┌──────────────────────────────────────────────────────────────┐
│                    分片路由公式                                │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  shard = hash(routing_value) % number_of_primary_shards     │
│                                                              │
│  routing_value 默认为文档 _id                                 │
│  也可以自定义: PUT /index/_doc/1?routing=user123             │
│                                                              │
│  hash 函数: MurmurHash3                                      │
│                                                              │
│  示例:                                                       │
│  index = "my_index", number_of_primary_shards = 3           │
│                                                              │
│  DocID="1" → hash("1") = 3289472 → 3289472 % 3 = 2 → Shard 2│
│  DocID="2" → hash("2") = 8293847 → 8293847 % 3 = 1 → Shard 1│
│  DocID="3" → hash("3") = 1938472 → 1938472 % 3 = 0 → Shard 0│
│                                                              │
│  关键推论:                                                   │
│  ┌──────────────────────────────────────────────────────┐    │
│  │  1. 主分片数一旦确定就不能修改                        │    │
│  │     → 因为路由公式依赖它，修改会导致数据找不到        │    │
│  │     → 要增加分片数只能 reindex                       │    │
│  │                                                      │    │
│  │  2. 自定义 routing 可以将相关数据路由到同一分片      │    │
│  │     → 例: 按 user_id routing，同一用户数据在同一分片  │    │
│  │     → 减少跨分片查询                                 │    │
│  └──────────────────────────────────────────────────────┘    │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 8.2 路由到分片的具体过程

```
┌──────────────────────────────────────────────────────────────┐
│              请求路由到分片的完整过程                          │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  写入请求: PUT /my_index/_doc/1                              │
│                                                              │
│  ┌─────────────────────────────────────────────┐            │
│  │  Coordinator Node                            │            │
│  │                                             │            │
│  │  ① 计算 shard = hash("1") % 3 = 2           │            │
│  │                                             │            │
│  │  ② 查 Cluster State 路由表                   │            │
│  │     Shard 2 Primary → Node C                │            │
│  │     Shard 2 Replica  → Node A              │            │
│  │                                             │            │
│  │  ③ 选择目标节点                              │            │
│  │     写入: 只能写 Primary → Node C            │            │
│  │     读取: Round-robin 在 Primary/Replica 间选│            │
│  │                                             │            │
│  │  ④ 转发请求到 Node C                         │            │
│  └─────────────────────────────────────────────┘            │
│                                                              │
│  搜索请求: GET /my_index/_search                             │
│                                                              │
│  ┌─────────────────────────────────────────────┐            │
│  │  Coordinator Node                            │            │
│  │                                             │            │
│  │  ① 需要查询所有分片                          │            │
│  │     Shard 0: Primary→A, Replica→B            │            │
│  │     Shard 1: Primary→B, Replica→C            │            │
│  │     Shard 2: Primary→C, Replica→A            │            │
│  │                                             │            │
│  │  ② 对每个分片，Round-robin 选择一个副本      │            │
│  │     Shard 0 → 选 A (Primary)                │            │
│  │     Shard 1 → 选 C (Replica)                │            │
│  │     Shard 2 → 选 A (Replica)                │            │
│  │                                             │            │
│  │  ③ 并行发送查询到 A, C, A                    │            │
│  └─────────────────────────────────────────────┘            │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 8.3 分片数选择

```
┌──────────────────────────────────────────────────────────────┐
│                分片数选择建议                                  │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  分片数 = 数据量 / 单分片推荐大小                       │ │
│  │                                                        │ │
│  │  单分片推荐大小: 30GB - 50GB                           │ │
│  │                                                        │ │
│  │  示例:                                                 │ │
│  │  100GB 数据 → 3-4 个分片                               │ │
│  │  1TB 数据  → 20-30 个分片                              │ │
│  │  10TB 数据 → 200-300 个分片                            │ │
│  └────────────────────────────────────────────────────────┘ │
│                                                              │
│  为什么单分片推荐 30-50GB?                                   │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  1. Segment Merge 时间: 分片越大，合并时间越长           │ │
│  │  2. 故障恢复时间: 分片越大，恢复时间越长                │ │
│  │  3. 搜索性能: 分片越大，单分片查询越慢                  │ │
│  │  4. 管理: 分片越大，管理越困难                         │ │
│  └────────────────────────────────────────────────────────┘ │
│                                                              │
│  副本数选择:                                                 │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  number_of_replicas = 1（默认）                        │ │
│  │  → 1 个 Primary + 1 个 Replica = 2 份数据             │ │
│  │  → 任何 1 个节点宕机不丢数据                           │ │
│  │                                                        │ │
│  │  number_of_replicas = 2                                │ │
│  │  → 1 个 Primary + 2 个 Replica = 3 份数据             │ │
│  │  → 任何 2 个节点宕机不丢数据                           │ │
│  │  → 读取吞吐量 ×3                                      │ │
│  │  → 但写入吞吐量不变（写入要同步到所有副本）            │ │
│  └────────────────────────────────────────────────────────┘ │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 8.4 分片迁移

```
┌──────────────────────────────────────────────────────────────┐
│                    分片迁移过程                                │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  场景: 新节点 Node D 加入集群，需要迁移部分分片               │
│                                                              │
│  迁移前:                                                     │
│  ┌──────────┬──────────┬──────────┐                         │
│  │  Node A  │  Node B  │  Node C  │                         │
│  │ P0 R2    │ P1 R0    │ P2 R1    │                         │
│  └──────────┴──────────┴──────────┘                         │
│                                                              │
│  迁移过程（以迁移 P2 为例）:                                  │
│                                                              │
│  Step 1: Master 决定将 P2 从 Node C 迁移到 Node D            │
│     Cluster State 更新: P2.relocating_node = "Node D"       │
│                                                              │
│  Step 2: Node D 开始从 Node C 恢复数据                        │
│     ┌──────────────────────────────────────────┐            │
│     │ Node C (Source)                          │            │
│     │  ① 将 Segment 文件传输给 Node D           │            │
│     │     (通过 Recovery API)                  │            │
│     │                                          │            │
│     │  ② 同时，Node C 继续接收新写入            │            │
│     │     这些新写入也会转发给 Node D           │            │
│     └──────────────────────────────────────────┘            │
│     ┌──────────────────────────────────────────┐            │
│     │ Node D (Target)                          │            │
│     │  ① 接收 Segment 文件                      │            │
│     │  ② 接收 Translog                          │            │
│     │  ③ 重放 Translog                          │            │
│     │  ④ 标记为 STARTED                         │            │
│     └──────────────────────────────────────────┘            │
│                                                              │
│  Step 3: 迁移完成                                             │
│     Cluster State 更新:                                      │
│       P2.primary = true, node = "Node D"                    │
│       P2.relocating_node = null                             │
│     Node C 上的 P2 被删除                                     │
│                                                              │
│  迁移后:                                                     │
│  ┌──────────┬──────────┬──────────┬──────────┐              │
│  │  Node A  │  Node B  │  Node C  │  Node D  │              │
│  │ P0 R2    │ P1 R0    │ R1       │ P2       │              │
│  └──────────┴──────────┴──────────┴──────────┘              │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 第九部分：近实时搜索 NRT

### 9.1 近实时搜索原理

```
ES 是 "近实时"（Near Real-Time）搜索，不是完全实时。

┌──────────────────────────────────────────────────────────────┐
│                近实时搜索的时间线                              │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  时间轴:                                                     │
│                                                              │
│  T0 ─────────── 用户写入文档                                  │
│  │                                                           │
│  T0+ε ──────── 写入 Index Buffer + Translog                   │
│  │              返回成功给用户                                │
│  │              → 此时文档还不可搜索！                        │
│  │                                                           │
│  T0+1s ──────── Refresh（默认 1 秒）                          │
│  │              Index Buffer → 新 Segment（内存）            │
│  │              → 此时可搜索了                               │
│  │                                                           │
│  T0+30s ─────── 可选: 自定义 refresh_interval                 │
│  │                                                           │
│  T0+30min ───── Flush（默认 30min 或 Translog > 512MB）       │
│  │              Segment → fsync → 落盘                       │
│  │              Translog 清空                                │
│  │              → 此时即使崩溃也不丢数据                      │
│  │                                                           │
│  对比:                                                       │
│  ┌──────────────────────────────────────────────────────┐   │
│  │            可搜索？    可持久化？    崩溃后恢复？     │   │
│  │  T0+ε:     ❌          ✅ (Translog)  ✅              │   │
│  │  T0+1s:    ✅          ✅             ✅              │   │
│  │  T0+30min: ✅          ✅             ✅              │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  关键配置:                                                   │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  refresh_interval:                                   │   │
│  │    默认 1s（新数据 1 秒后可搜索）                     │   │
│  │    批量写入时可设为 30s 或 -1（关闭自动 refresh）     │   │
│  │                                                      │   │
│  │  translog.durability:                                │   │
│  │    request（默认）: 每次请求 fsync（最安全）          │   │
│  │    async: 异步 fsync（5s 间隔，可能丢 5s 数据）      │   │
│  │                                                      │   │
│  │  translog.flush_threshold_size:                      │   │
│  │    默认 512MB（Translog 超过此大小触发 flush）       │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 9.2 Refresh vs Flush

```
┌──────────────────────────────────────────────────────────────┐
│              Refresh vs Flush 对比                            │
├─────────────────────────┬────────────────────────────────────┤
│         Refresh         │              Flush                 │
├─────────────────────────┼────────────────────────────────────┤
│ Index Buffer → Segment  │ Segment → fsync → 磁盘            │
│ (内存中)                │                                    │
│                         │                                    │
│ 目的: 让新文档可搜索     │ 目的: 持久化到磁盘                  │
│                         │                                    │
│ 触发: 默认 1s            │ 触发: 默认 30min 或 512MB          │
│                         │                                    │
│ 清空 Index Buffer?      │ 清空 Translog?                    │
│ ✅ 是                   │ ✅ 是                              │
│                         │                                    │
│ 清空 Translog?          │                                    │
│ ❌ 否                   │                                    │
│                         │                                    │
│ 崩溃后数据丢失?          │ 崩溃后数据丢失?                    │
│ ❌ 不丢（Translog 有）   │ ❌ 不丢（已落盘）                  │
│                         │                                    │
│ 耗时: 毫秒级            │ 耗时: 秒到分钟                     │
│                         │                                    │
│ 性能影响: 小            │ 性能影响: 大（fsync I/O）          │
└─────────────────────────┴────────────────────────────────────┘
```

### 9.3 手动控制 Refresh

```bash
# 关闭自动 refresh（批量写入时推荐）
PUT /my_index/_settings
{
  "refresh_interval": -1
}

# 批量写入完成后手动 refresh
POST /my_index/_refresh

# 恢复自动 refresh
PUT /my_index/_settings
{
  "refresh_interval": "1s"
}

# 写入时强制 refresh（不推荐，性能差）
POST /my_index/_doc/1?refresh=true
{
  "title": "Hello"
}

# 写入时等 refresh 后再返回（不推荐）
POST /my_index/_doc/1?refresh=wait_for
{
  "title": "Hello"
}
```

### 9.4 Indexing Buffer

```
┌──────────────────────────────────────────────────────────────┐
│                    Indexing Buffer                            │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  Index Buffer 是 JVM Heap 中的一块区域，用于暂存新写入的文档  │
│                                                              │
│  ┌─────────────────────────────────────────────┐            │
│  │  JVM Heap                                   │            │
│  │  ┌─────────────────────────────────────┐    │            │
│  │  │  Indexing Buffer (默认 10% Heap)     │    │            │
│  │  │                                     │    │            │
│  │  │  ┌──────────┐  ┌──────────┐        │    │            │
│  │  │  │ DWPT 0   │  │ DWPT 1   │  ...   │    │            │
│  │  │  │ (Thread0)│  │ (Thread1)│        │    │            │
│  │  │  │          │  │          │        │    │            │
│  │  │  │ 新文档   │  │ 新文档   │        │    │            │
│  │  │  └──────────┘  └──────────┘        │    │            │
│  │  └─────────────────────────────────────┘    │            │
│  │  ┌─────────────────────────────────────┐    │            │
│  │  │  其他 Heap (Query Cache, etc.)      │    │            │
│  │  └─────────────────────────────────────┘    │            │
│  └─────────────────────────────────────────────┘            │
│                                                              │
│  每个 DocumentWriterPerThread (DWPT) 对应一个写入线程        │
│  DWPT 中缓存该线程写入的文档                                  │
│  当 DWPT 的内存超过阈值时，触发 refresh                       │
│  → DWPT 中的数据被写入新的 Segment                           │
│                                                              │
│  配置:                                                       │
│  indices.memory.index_buffer_size: 10%   # 默认 10% Heap     │
│  indices.memory.min_index_buffer_size: 48mb                  │
│  indices.memory.max_index_buffer_size: 50%                    │
│                                                              │
│  调优建议:                                                   │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  纯写入场景: 增大 Indexing Buffer                     │   │
│  │  → 减少 Refresh 次数 → 减少 Segment 数量            │   │
│  │  → 减少 Merge 开销                                   │   │
│  │  → 提高写入吞吐量                                    │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 第十部分：版本控制与并发

### 10.1 ES 版本体系

```
┌──────────────────────────────────────────────────────────────┐
│                    ES 版本控制体系                              │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  1. _version（内部版本号）                                   │
│     ─────────────────────                                    │
│     每次文档更新，version + 1                                │
│     删除后再创建，version 继续递增（不重置）                   │
│                                                              │
│     PUT /index/_doc/1?version=3&version_type=internal       │
│     → 如果当前 version != 3，返回 409                       │
│                                                              │
│  2. _version（外部版本号）                                   │
│     ─────────────────────                                    │
│     使用外部系统（如数据库）的版本号                           │
│                                                              │
│     PUT /index/_doc/1?version=1000&version_type=external    │
│     → 如果当前 version >= 1000，返回 409                    │
│                                                              │
│  3. _seq_no + _primary_term（ES 6.7+ 推荐）                  │
│     ─────────────────────────────────────                    │
│     _seq_no: 分片内递增的序列号                              │
│     _primary_term: 主分片变更时递增                          │
│                                                              │
│     PUT /index/_doc/1?if_seq_no=5&if_primary_term=1         │
│     → 如果当前 _seq_no != 5 或 _primary_term != 1，返回 409 │
│                                                              │
│     优势:                                                    │
│     - 更轻量（不依赖 _version 字段）                         │
│     - 支持_primary_term 区分不同主分片代次                   │
│     - 主分片切换后，_primary_term 变化，旧版本自动失效        │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 10.2 乐观并发控制

```
┌──────────────────────────────────────────────────────────────┐
│                乐观并发控制（OCC）                              │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  场景: 两个线程同时更新同一文档                                │
│                                                              │
│  Thread A: 读取文档 → _seq_no=5, _primary_term=1            │
│  Thread B: 读取文档 → _seq_no=5, _primary_term=1            │
│                                                              │
│  Thread A: PUT /index/_doc/1?if_seq_no=5&if_primary_term=1  │
│            → 版本匹配 → 写入成功 → _seq_no=6                │
│                                                              │
│  Thread B: PUT /index/_doc/1?if_seq_no=5&if_primary_term=1  │
│            → 版本不匹配（当前是 6）→ 返回 409                 │
│                                                              │
│  Thread B: 重新读取文档 → _seq_no=6                         │
│            合并修改后重试                                     │

│            → 写入成功 → _seq_no=7                            │
│                                                              │
│  源码层面:                                                   │
│  ┌────────────────────────────────────────────────┐          │
│  │  InternalEngine.index() 方法:                   │          │
│  │  1. 获取当前版本                                │          │
│  │  2. 比较 if_seq_no / if_primary_term           │          │
│  │  3. 如果不匹配 → 抛出 VersionConflictEngine   │
│  │     Exception                                 │          │
│  │  4. 如果匹配 → 写入文档                        │          │
│  │  5. 递增 _seq_no                              │          │
│  │  6. 写入 Translog                             │          │
│  └────────────────────────────────────────────────┘          │
│                                                              │
```

## 第十三部分：面试高频题 20 问

### Q1：ES 为什么是近实时的？如何做到实时？

**答**：ES 写入文档后先写入 Index Buffer（内存）和 Translog（磁盘），此时文档还不可搜索。默认 1 秒后触发 Refresh，将 Index Buffer 生成新的 Segment（内存中），此时才可搜索。所以 ES 是"近实时"（NRT）。

要做到实时：
- 写入时加 `?refresh=true`，强制立即 Refresh（性能差，不推荐）
- 写入时加 `?refresh=wait_for`，等待下一次 Refresh 后返回（阻塞式）
- 对于强实时场景，考虑用 Redis 缓存最新数据 + ES 搜索

### Q2：倒排索引的原理是什么？为什么比 MySQL 的 B+Tree 快？

**答**：倒排索引由三部分组成：
1. **Term Index**（.tip）：FST（有限状态转换器）存储，共享前缀和后缀压缩，加载到内存
2. **Term Dictionary**（.tim）：所有 Term 的有序列表，按 Block 存储
3. **Posting List**（.doc）：每个 Term 对应的文档列表，使用 FOR 压缩和 Roaring Bitmap

搜索流程：Term → FST 定位 Block → Block 内二分查找 → 获取 Posting List → 返回文档列表

为什么比 MySQL B+Tree 快：
- MySQL 的 `LIKE '%keyword%'` 需要全表扫描
- ES 通过倒排索引直接定位文档列表，O(k) 复杂度（k=词长度）
- ES 的 Term Index 在内存中，不需要磁盘 I/O
- ES 使用 Roaring Bitmap 做多条件交集，极其高效

### Q3：ES 的分片数可以修改吗？为什么？

**答**：主分片数一旦确定就不能修改。因为 ES 的路由公式是 `shard = hash(routing) % number_of_primary_shards`，如果修改主分片数，已有数据的路由会全部失效，导致找不到数据。

如果需要增加分片数：
1. 创建新索引（更多分片）
2. 使用 Reindex API 迁移数据
3. 使用 Alias 切换流量

副本分片数可以动态修改：`PUT /index/_settings {"number_of_replicas": 2}`

### Q4：什么是 Refresh 和 Flush？区别是什么？

**答**：
- **Refresh**：将 Index Buffer（内存）中的数据生成新的 Segment（内存中），使文档可被搜索。默认 1 秒。不涉及 fsync，不清空 Translog。
- **Flush**：将内存中的 Segment fsync 到磁盘，写入新的 Commit Point，清空 Translog。默认 30 分钟或 Translog 达到 512MB。

| | 可搜索 | 持久化 | 清空 Translog | 耗时 |
|---|---|---|---|---|
| Refresh | ✅ | ❌ | ❌ | 毫秒 |
| Flush | ✅ | ✅ | ✅ | 秒-分钟 |

### Q5：ES 如何保证数据不丢？

**答**：通过 **Translog（WAL）** + **Flush** 机制：
1. 写入时同时写入 Index Buffer 和 Translog（磁盘 fsync）
2. Translog 记录了所有未 Flush 的操作
3. 崩溃恢复时，加载最后 Commit Point 的 Segment，重放 Translog
4. `translog.durability=request`（默认）：每次请求都 fsync，最安全

### Q6：什么是 Segment？为什么 Segment 不可变？

**答**：Segment 是 Lucene 的物理存储单元，一个 Lucene Index 由多个 Segment + Commit Point 组成。Segment 一旦创建就不可修改。

不可变的好处：
1. 不需要锁 → 读取无并发问题
2. 可以被 OS 文件系统缓存 → 高效读取
3. 简化了设计 → 不需要 MVCC

不可变的问题：删除/更新需要标记 + 合并时清理 → Segment Merge

### Q7：ES 的 BM25 和 TF-IDF 有什么区别？

**答**：BM25 是 ES 6+ 默认评分算法，相比 TF-IDF：
1. **词频饱和**：BM25 的 TF 有饱和值（k1 参数），词频到一定程度不再增加分数；TF-IDF 线性增长
2. **文档长度归一化**：BM25 考虑文档长度，长文档会被惩罚（b 参数）；TF-IDF 不考虑
3. **IDF 始终为正**：BM25 的 IDF = ln(1 + (N-n+0.5)/(n+0.5))，始终为正；TF-IDF 的 IDF = log(N/n) 可能为负

### Q8：ES 如何解决脑裂问题？

**答**：ES 7.x 使用 Zen2 机制自动防脑裂：
1. 自动维护 Voting Configuration（投票成员列表），通常为奇数
2. Master 选举需要 Voting Configuration 的多数票
3. 当节点数 > 3 时，自动裁剪到 3 个投票成员
4. 不需要手动配置 `minimum_master_nodes`（7.x 废弃）

### Q9：如何优化 ES 的写入性能？

**答**：
1. 使用 Bulk API 批量写入（5-15MB）
2. 写入时关闭 Refresh（`refresh_interval: -1`）
3. 写入时关闭副本（`number_of_replicas: 0`）
4. 增大 Indexing Buffer（`indices.memory.index_buffer_size: 30%`）
5. 多线程并行写入
6. 使用 auto-generated ID
7. `translog.durability: async`（可接受丢数据时）

### Q10：ES 的 Query Then Fetch 是什么？

**答**：ES 搜索分两阶段：
1. **Query Phase**：Coordinator 将查询广播到所有分片，每个分片执行查询返回 Top N 的 DocID + Score
2. **Fetch Phase**：Coordinator 合并所有分片结果，全局排序取 Top N，然后根据 DocID 去对应分片取完整文档

这样可以减少网络传输：Query Phase 只传 DocID + Score（不传完整文档），Fetch Phase 只取需要的文档。

### Q11：什么是 Doc Values？为什么需要它？

**答**：Doc Values 是 Lucene 的正向索引（DocID → Field Value），以列式存储。倒排索引擅长搜索（Term → DocID），但不擅长排序/聚合（需要 DocID → Value）。

Doc Values 的优势：
1. 列式存储 → 对 CPU Cache 友好
2. 顺序访问 → 适合全量扫描
3. 压缩存储 → 内存占用小

默认对除 text 外的所有类型开启。

### Q12：ES 的 _source 和 Stored Fields 有什么区别？

**答**：
- **_source**：原始 JSON 文档，存储在 Stored Fields（.fdt 文件）中。用于返回查询结果。
- **Stored Fields**：Lucene 的存储字段机制，可以按字段单独存储。ES 默认将整个 `_source` 作为一个 Stored Field。

可以禁用 `_source`（不推荐）或禁用特定字段的存储（`store: false`），但禁用后无法获取原始文档。

### Q13：ES 的 Filter 和 Query 有什么区别？

**答**：
- **Filter**：只判断是否匹配，不计算分数。结果会被缓存。适合精确匹配。
- **Query**：计算相关性分数。不缓存。适合全文搜索。

Filter 比 Query 快 2-5 倍，因为：
1. 不计算分数
2. 结果被缓存（BitSet）
3. 可以跳过打分逻辑

### Q14：什么是深分页？如何解决？

**答**：深分页是指 `from + size` 很大的分页查询（如 from=10000, size=10）。ES 需要从每个分片取 `from + size` 条记录，Coordinator 合并 `(from + size) × shard_num` 条记录后排序。

解决方案：
1. **search_after**：基于上一页最后一条记录的排序值查询下一页
   ```
   GET /index/_search
   {
     "size": 10,
     "sort": [{ "timestamp": "desc" }, { "_id": "desc" }],
     "search_after": ["2024-01-15T10:00:00", "doc_123"]
   }
   ```
2. **Scroll API**：创建快照，逐批拉取（适合全量导出，不适合实时搜索）
3. **限制 from + size ≤ 10000**：`index.max_result_window` 默认 10000

### Q15：ES 的聚合为什么比 MySQL GROUP BY 快？

**答**：
1. ES 使用 **Doc Values**（列式存储），顺序访问对 CPU Cache 友好
2. ES 聚合在**每个分片并行执行**，Coordinator 合并结果
3. ES 可以利用 **Cardinality Aggregation**（HyperLogLog）做近似去重，O(1) 空间
4. MySQL GROUP BY 需要 filesort 或临时表
5. ES 可以缓存聚合结果

但精确 COUNT(DISTINCT) 大数据量时，ES 的 cardinality 是近似值（误差 ~1%）。

### Q16：什么是 ES 的 IK 分词器？ik_smart 和 ik_max_word 有什么区别？

**答**：IK 是开源中文分词器。
- **ik_smart**：最短路径分词，只返回一种切分结果。粗粒度。
  - "我爱北京天安门" → [我, 爱, 北京, 天安门]
- **ik_max_word**：返回所有可能切分。细粒度。
  - "我爱北京天安门" → [我, 爱, 北京, 天安门, 天安, 门]

最佳实践：索引时用 ik_max_word（多分一些词，召回率高），搜索时用 ik_smart（少分一些词，精确度高）。

### Q17：ES 如何实现分布式锁？

**答**：ES 可以通过乐观锁实现分布式锁：
1. 创建一个 index 用于存储锁
2. 使用 `if_seq_no + if_primary_term` 实现乐观锁
3. 或者使用 `version_type=external` + 外部版本号

但 ES 不是最佳分布式锁方案。推荐使用 Redis（Redisson）或 Zookeeper。

### Q19：ES 什么情况下会变慢？如何排查？

**答**：常见变慢原因及排查：

1. **JVM GC 频繁** → `_nodes/stats` 检查 GC 次数和时间
2. **磁盘 I/O 瓶颈** → 检查 iostat，Segment Merge 太多
3. **Heap 不足** → 大量 Field Data 或 Aggregation 占用 Heap
4. **分片不均匀** → `_cat/shards` 检查分片分布
5. **热点查询** → 慢查询日志，`search.slowlog`
6. **Mapping 不合理** → text 字段开了 fielddata
7. **Segment 太多** → `_forcemerge` 合并

排查工具：
```bash
# 集群健康
GET /_cluster/health

# 节点状态
GET /_nodes/stats

# 分片分布
GET /_cat/shards?v

# 索引统计
GET /index/_stats

# 慢查询日志
GET /index/_settings
{ "index.search.slowlog.threshold.query.warn": "5s" }
```

### Q20：ES 和 Kafka 如何配合使用？

**答**：经典日志架构：

```
应用 → Filebeat → Kafka → Logstash → ES → Kibana
                     │
                     └─ Kafka 做缓冲，削峰填谷

详细流程:
1. Filebeat 采集应用日志
2. 发送到 Kafka（缓冲 + 解耦）
3. Logstash 从 Kafka 消费
4. Logstash 解析/过滤/转换
5. 写入 ES（Bulk API）
6. Kibana 可视化查询
```

为什么需要 Kafka：
- 削峰填谷：日志突增时 Kafka 缓冲，避免 ES 被打挂
- 解耦：采集和存储解耦
- 重放：ES 出问题时 Kafka 保留数据
- 多消费：同一份数据可被多个系统消费
