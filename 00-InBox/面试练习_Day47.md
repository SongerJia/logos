## 话题一：MySQL InnoDB B+树索引原理（12分钟）

**面试官：你们 MySQL 的索引是什么数据结构？为什么 InnoDB 选择 B+树而不是 B 树或者红黑树？**

 你回答...

**追问1：** B+树和 B 树有什么区别？为什么这个区别对数据库很重要？

> 你回答...（提示：B树：每个节点都存数据 → 叶子和非叶子节点都存 key+data / B+树：只有叶子节点存数据，非叶子节点只存 key → 叶子节点通过双向链表连接 / 区别的意义：①B+树非叶子节点不存数据 → 每个节点能存更多 key → 树更矮 → 磁盘 IO 次数更少（树的层数 = IO 次数）②B+树叶子节点有序链表 → 范围查询极快（只需要找到起点然后沿链表扫描）/ B树范围查询需要中序遍历整棵树 → 很多随机 IO / 红黑树：二叉树 → 树太高 → 每层一次 IO → 深度太大不适合磁盘存储 / InnoDB B+树通常 3-4 层 → 千万级数据只需 3-4 次 IO）

**追问2：** 你说 B+树非叶子节点能存更多 key，具体一个节点能存多少？InnoDB 的页大小是多少？

> 你回答...（提示：InnoDB 页大小默认 16KB（可配置 4K/8K/32K）/ 非叶子节点存的是主键 + 指针 / 假设主键 bigint 8 字节 + 指针 6 字节 = 14 字节 / 16384 / 14 ≈ 1170 个 key / 叶子节点存完整行数据，假设每行 1KB → 16 行 / 三层 B+树：1170 × 1170 × 16 ≈ 2190 万条记录 → 3 次 IO 查千万级数据 / 这就是为什么 InnoDB B+树通常 3 层就够了）

**追问3：** 聚簇索引和二级索引有什么区别？什么是回表？

> 你回答...（提示：聚簇索引：叶子节点存完整行数据 → 主键索引就是聚簇索引 → 一张表只有一个 / InnoDB 的数据文件本身就是按聚簇索引组织的 / 二级索引（非聚簇索引）：叶子节点存主键值 → 不是行数据 / 普通索引都是二级索引 / 回表：通过二级索引查到主键 → 再用主键去聚簇索引查完整行 → 两次 B+树查找 / 这就是为什么"覆盖索引"能优化——查询列都在二级索引里 → 不需要回表 / MyISAM 没有聚簇索引 → 主键索引和普通索引叶子都存行指针 → 不需要回表但范围查询慢）

**追问4：** 联合索引在 B+树里是怎么存储的？最左前缀原则的底层原因是什么？

> 你回答...（提示：联合索引 (a, b, c) 在 B+树里也是有序的 → 先按 a 排序 → a 相同按 b 排序 → b 相同按 c 排序 / B+树本身就是有序结构 → 联合索引就是多级排序 / 最左前缀原则的底层原因：B+树是按 a→b→c 的顺序排序的 / 查询条件有 a → 能利用 B+树的有序性 → 快速定位 / 没有 a → B+树对 b 无序 → 无法用索引 → 全表扫描 / 范围查询后失效：WHERE a > 1 AND b = 2 → a 是范围查询 → a > 1 的范围内 b 不是全局有序的 → b 无法走索引）

**追问5：** InnoDB 的页（Page）你了解吗？什么是 Change Buffer？

> 你回答...（提示：Page 是 InnoDB 最小的磁盘 IO 单位 → 16KB / 页结构：File Header + Page Header + records（用户记录）+ Page Directory（页目录，二分查找用）/ 页内记录按主键有序 → 二分查找 / Change Buffer：对非唯一二级索引的修改先缓存 → 不立即读磁盘页 → 后台 merge → 减少随机 IO / 为什么只对非唯一索引：唯一索引必须读页检查唯一性 → 无法跳过 / Change Buffer 提升写性能但对崩溃恢复有要求 → 依赖 redo log / `innodb_change_buffer_max_size` 控制最大占比默认 25%）

**追问6：** 你知道 InnoDB 的自适应哈希索引（AHI）吗？为什么要有这个？

> 你回答...（提示：AHI = Adaptive Hash Index / InnoDB 自动监控热点查询 → 如果某些索引页被频繁等值查询 → 在内存中建 hash 索引 → O(1) 查找 / B+树是 O(log n) → hash 是 O(1) → 热点数据快 / 但 AHI 占内存 → 只对等值查询有效 → 范围查询用不上 / `innodb_adaptive_hash_index` 默认开启 / 高并发下 AHI 的锁竞争可能是瓶颈 → 有时需要关闭 / 一般不用管，了解即可）

## 话题二：synchronized 锁升级全过程（10分钟）

**面试官：你了解 synchronized 吗？在 JDK 6 之后 synchronized 做了哪些优化？**

 你回答...

**追问1：** synchronized 锁的是什么？它锁的是方法还是对象？

> 你回答...（提示：synchronized 锁的是对象 / 修饰实例方法 → 锁当前对象 this / 修饰静态方法 → 锁 Class 对象 / 修饰代码块 → 锁括号里的对象 / 每个对象都有一个 monitor（管程）→ synchronized 就是获取对象的 monitor / 但 JDK 6 之后做了"锁升级"优化 → 不是一开始就加 monitor（太重）→ 根据竞争程度逐步升级）

**追问2：** 对象头你了解吗？Mark Word 里有什么？

> 你回答...（提示：Java 对象内存布局：对象头 + 实例数据 + 对齐填充 / 对象头 = Mark Word + Klass Pointer（指向类元信息）/ Mark Word 64 位（64位JVM）→ 存储：hashCode / GC 年龄 / 锁标志位 / 线程ID 等 / Mark Word 在不同锁状态下存储不同内容 → 无锁→存 hashCode / 偏向锁→存线程ID / 轻量级锁→存指向栈中锁记录的指针 / 重量级锁→存指向 monitor 的指针 / 锁标志位 2 bit + 1 bit 标记偏向 / 锁升级就是 Mark Word 内容的变化）

**追问3：** 偏向锁、轻量级锁、重量级锁分别是什么？升级过程是怎样的？

> 你回答...（提示：升级链：无锁 → 偏向锁 → 轻量级锁 → 重量级锁（不可降级）/ 偏向锁：第一个线程获取锁 → Mark Word 记录线程ID → 同一线程再次进入不需要 CAS → 几乎无开销 / 出现竞争 → 升级 / 轻量级锁：两个线程交替执行（没有真正的并发冲突）→ 用 CAS 操作 Mark Word → 指向线程栈中的 Lock Record → 自旋等待 → 不阻塞线程 / 自旋失败或第三个线程竞争 → 升级 / 重量级锁：真正的并发竞争 → 依赖操作系统 mutex → 线程阻塞挂起 → 上下文切换 / 重量级锁就是传统的 synchronized 行为 / JDK 6 之前没有锁升级 → 一上来就是重量级锁 → 所以 synchronized 以前很慢）

**追问4：** 偏向锁在什么场景下效果最好？JDK 15 为什么要废弃偏向锁？

> 你回答...（提示：偏向锁适合：同一个线程反复进入同步块 → 单线程场景或交替执行场景 / 不适合：多线程并发竞争 → 偏向锁反而要撤销（revoke）→ 撤销需要 STW / JDK 15 废弃偏向锁的原因：①现代应用多核并发 → 偏向锁收益降低 ②偏向锁撤销的 STW 开销 ③维护成本高 → 维护一套复杂的偏向锁逻辑不如简化 / JDK 18 默认关闭偏向锁 → `-XX:+UseBiasedLocking` 需要手动开启 / 了解即可 → 面试重点掌握升级过程和 Mark Word）

**追问5：** 什么是锁消除和锁粗化？

> 你回答...（提示：锁消除：JIT 编译时的逃逸分析 → 对象不会被其他线程访问 → 去掉同步锁 / 经典案例：StringBuffer.append → synchronized 方法 → 但 StringBuffer 是局部变量 → 逃逸分析 → 锁消除 → 无开销 / 锁粗化：连续多个 synchronized 块 → 合并成一个大的 synchronized 块 → 减少加锁解锁次数 / 比如 for 循环里每次 append → JIT 把整个循环合并成一个锁 / 这两个优化都是 JIT 在运行时做的 → 不需要代码修改）

**追问6：** synchronized 和 ReentrantLock 有什么区别？什么场景用哪个？

> 你回答...（提示：synchronized：①JVM 层面关键字 ②自动加锁释放 ③不可中断 ④非公平锁 ⑤锁升级优化 ⑥wait/notify 需要 monitor / ReentrantLock：①API 层面类 ②手动 lock/unlock（必须 finally）③可中断（lockInterruptibly）④可公平可非公平 ⑤可超时（tryLock）⑥Condition 精确唤醒 / 选择：①简单同步 → synchronized（JDK 6 后性能和 ReentrantLock 差不多）②需要可中断/超时/公平/多条件变量 → ReentrantLock ③读写场景 → ReentrantReadWriteLock ④生产建议：优先 synchronized → 简单不易出错 → 需要高级功能才用 ReentrantLock）

## 话题四：Redis 集群与高可用（10分钟）

**面试官：你们 Redis 在生产环境是怎么部署的？单机还是集群？Redis 的高可用方案你了解哪些？**

 你回答...

**追问1：** Redis 的主从复制是什么？和 MySQL 的主从复制有什么区别？

> 你回答...（提示：Redis 主从：一个 master + 多个 slave / 写 master → 同步到 slave / slave 只读 / 全量同步：slave 首次连接 → master 做 bgsave 生成 RDB → 发给 slave → slave 加载 / 增量同步：master 维护 replid + offset → slave 断线重连 → 发送 replid + offset → master 从 backlog 找差异 → 增量发送 / vs MySQL：MySQL 用 binlog → Redis 用 RDB + repl_backlog / Redis 同步更快但持久性不如 MySQL / 注意：Redis 主从是异步复制 → master 写完立即返回 → 不等 slave → 会有数据丢失风险）

**追问2：** 哨兵模式是什么？它和主从有什么区别？解决了什么问题？

> 你回答...（提示：主从的问题：master 挂了需要人工切换 → 哨兵解决这个问题 / Sentinel = 监控 + 自动故障转移 / 哨兵职责：①监控 master/slave 存活 ②通知运维 ③自动故障转移：选一个 slave 升级为 master → 其他 slave 指向新 master ④配置提供：客户端连哨兵获取 master 地址 / 哨兵本身也要高可用 → 至少 3 个哨兵 → 多数投票决定 master 是否下线 / 故障转移过程：①主观下线（单个哨兵发现 master 不响应）②客观下线（多数哨兵确认）③选新 master（优先级 → offset → runid）④切换客户端指向 / 适合：读多写少 → master 写 → slave 读 → 自动故障转移）

**追问3：** Redis Cluster 和哨兵模式有什么区别？Cluster 是怎么做数据分片的？

> 你回答...（提示：哨兵：一主多从 → 数据全在一台 master → 存储上限受单机内存限制 → 没有分片 / Cluster：多 master + 多 slave → 数据分散在多个节点 → 水平扩展 → 突破单机内存限制 / 分片方式：16384 个 hash slot → CRC16(key) % 16384 → 确定在哪个 slot → slot 分布在不同节点 / 比如 3 个 master → 每个 5461-5462 个 slot / 客户端缓存 slot 映射 → 直接连对应节点 → moved 重定向 → 客户端更新缓存 / Cluster 兼顾高可用 + 分片 → 每个 master 可以有自己的 slave → master 挂了 slave 自动顶上 / 哨兵模式适合数据量小 + 高可用 / Cluster 适合数据量大 + 高可用 + 水平扩展）

**追问4：** Gossip 协议你了解吗？Redis Cluster 节点之间怎么通信的？

> 你回答...（提示：Gossip = 流言协议 → 每个节点定期随机选几个节点 → 发送自己知道的信息 → 信息像流言一样扩散 → 最终所有节点信息一致 / Redis Cluster 的 Gossip：每个节点每秒 ping 几个随机节点 → ping 里带自己知道的所有节点状态 → 收到 ping 的节点也回 pong → 信息扩散 / Gossip 的特点：①去中心化 → 不需要中心节点 ②最终一致性 → 不是强一致 ③消息量可控 → 每次只选几个节点 ④收敛速度 → O(log n) 轮扩散到所有节点 / Gossip 类型：ping/pong/meet/fail → meet 是加入集群 / fail 是某节点被多数判定为下线 → 广播给所有节点 / 脑裂问题：网络分区 → 两个子网各自选举 → 但 Redis Cluster 要求多数节点存活 → 少数派自动降级 → 拒绝写入）

**追问5：** Redis 集群模式下的脑裂问题怎么处理？

> 你回答...（提示：脑裂 = 网络分区 → 两个子网各选 master → 数据不一致 / Redis Cluster 处理：①每个 slot 只有一个 master → 分区后少数派（< 半数节点）的 master 进入 fail 状态 → 拒绝写入 ②半数以上才能继续服务 → 保证只有一个 master / min-slaves-to-write：master 至少有 N 个 slave 连着才能写 → 否则拒绝写入 → 防止脑裂时写入丢失 / 但 Redis 的脑裂处理不如 ZooKeeper 严格 → ZK 用 ZAB 协议 → 过半机制 → 更安全 / 金融场景 → 如果强一致要求高 → 用 ZK 分布式锁而不是 Redis / Redis Cluster 的 CAP 选择：AP → 可用性优先 → 可能丢少量数据 / 如果要 CP → 不用 Redis Cluster → 用 ZK 或 etcd）

**追问1：** API 网关在微服务架构里做什么？为什么需要网关？

**追问2：** Spring Cloud Gateway 和 Zuul 有什么区别？为什么 Spring 官方推荐 Gateway？

**追问3：** Gateway 的过滤器你了解吗？怎么自定义一个过滤器做鉴权？

> 💡 **今日重点提示**：
> 1. **B+树索引原理**是 MySQL 面试的底层基石。核心问题：为什么 B+树而不是 B 树/红黑树？→ B+树非叶子节点不存数据→节点存更多key→树更矮→IO更少 + 叶子链表→范围查询快。InnoDB 页 16KB，三层 B+树可存 2000 万行→3次 IO。聚簇索引叶子存行数据，二级索引叶子存主键→需要回表。联合索引在 B+树里按字段顺序排序→最左前缀的底层原因。Change Buffer 优化非唯一索引写入，AHI 加速等值查询
> 2. **synchronized 锁升级**是并发面试的高阶题。核心链路：对象头 Mark Word → 偏向锁（记线程ID，无开销）→ 轻量级锁（CAS 自旋，不阻塞）→ 重量级锁（OS mutex，阻塞挂起），不可降级。偏向锁适合单线程重复进入，JDK 15 废弃因为现代应用多核并发收益降低。锁消除（JIT 逃逸分析去锁）和锁粗化（合并连续同步块）是 JIT 运行时优化。synchronized vs ReentrantLock：简单用 synchronized，需要可中断/超时/公平/Condition 用 ReentrantLock
> 3. **二叉树中序遍历非递归**是经典栈题。核心模式：一路向左压栈→弹出访问→转右子树重复。递归本质是 JVM 方法栈，迭代用显式栈模拟。时间 O(n) 空间 O(h)。后序非递归最难——用双栈或记录上一个访问节点。Morris 遍历可以 O(1) 空间但修改树结构
> 4. **Redis 集群与高可用**第一次系统考察。三种方案：主从（读写分离，master 挂要手动切）→ 哨兵（自动故障转移，但数据在单 master）→ Cluster（分片 + 高可用，16384 hash slot，CRC16 路由）。Gossip 协议：去中心化、最终一致、每秒 ping 随机节点扩散信息。脑裂：少数派自动降级拒绝写入。CAP 选择：Redis 是 AP → 可能丢少量数据，强一致用 ZK
> 5. **Spring Cloud Gateway**是微服务网关的标准方案。和 Zuul 区别：Gateway 基于 WebFlux + Netty 非阻塞，Zuul 1.x 基于 Servlet BIO。核心三件套：Route（路由）+ Predicate（断言匹配）+ Filter（前置/后置过滤）。GlobalFilter 做鉴权/日志，GatewayFilter 绑定特定路由。动态路由：Nacos 存路由配置 → 热加载。两层架构：Nginx（SSL/负载/安全）→ Gateway（路由/鉴权/限流）→ 微服务，不互相替代
> 6. **金融云**和互联网云不同：数据不出境 + 等保三级 + 核心系统不上云 + RTO/RPO 严格。银行容器化改造：渐进式从边缘到核心，存量系统改造成本高，更关注稳定性和合规而非新技术
> 7. **分布式缓存一致性**是今天的核心设计题。穿透（不存在）→ 布隆过滤器 + 缓存空值。击穿（热点过期）→ 互斥锁 + 不过期。雪崩（批量过期）→ 随机过期 + 多级缓存。更新策略：先更新DB再删缓存最安全（但非完美）。兜底：延迟双删 + binlog 订阅（Canal）+ 过期时间。标准答案："缓存强一致不现实，通过最终一致性 + 过期兜底 + 分布式锁（强一致场景）解决"。这是 CAP 理论的实践
> 8. **AQS 源码**是 JUC 同步器的基石。核心：state（volatile int，CAS 修改）+ CLH 双向队列（等待线程排队）。获取流程：CAS 抢锁→失败入队→自旋检查前驱是否 head→是则再抢→失败 park→前驱释放 unpark→再抢→成功。非公平锁：新线程直接 CAS 抢（可能插队）。公平锁：先检查队列是否有人等待。state 含义因同步器而异：ReentrantLock=重入次数，Semaphore=许可数，CountDownLatch=剩余计数。ABA 问题用 AtomicStampedReference 解决
