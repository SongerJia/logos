|---|---|
|**主从复制原理**|热 完整流程：①从库 `slaveof master_host port` ②主库 `BGSAVE` 生成 RDB 发给从库 ③从库清空旧数据加载 RDB ④主库将缓冲区（`replication_buffer`）中的写命令发给从库 ⑤后续主库每执行写命令异步同步给从库。**增量同步依赖 repl_backlog（复制积压缓冲区）**|
|**Sentinel 哨兵机制**|热 三个核心功能：监控（每隔 1 秒 PING）、自动故障转移（选举 Leader Sentinel → 选新主 → 通知其他从库切换）、配置提供者（客户端问 Sentinel 要主库地址）。**故障转移流程必须能手画**：SDOWN（主观下线）→ ODOWN（客观下线，≥ quorum 个 Sentinel 确认）→ 选举 Leader → Leader 选新主 → 通知切换|
|**Sentinel 选举：Raft 协议**|核 Sentinel 集群用 Raft 选 Leader。每个 Sentinel 都可以成为 Leader，先到先得（epoch + runid）。**为什么不用 Paxos？（Raft 更简单，故障转移场景够用）**|
|**Cluster 集群：数据分片**|热 **16384 个槽位**（slot），每个 key 通过 `CRC16(key) % 16384` 计算所属槽位。每个主节点负责一部分槽位。客户端请求错误节点时返回 `MOVED` 重定向；扩缩容时 `ASK` 临时重定向。**16384 这个数字要背下来（为什么不是 16383 或 16385？因为 CRC16 输出 16bit，取模 2^14 = 16384）**|
|**Cluster 扩缩容**|新增节点 → `CLUSTER MEET` 加入集群 → `CLUSTER ADDSLOTS` 分配槽位 → **数据迁移**：`CLUSTER GETKEYSINSLOT` 获取槽位上的 key → 逐个 `MIGRATE` 到新节点。**迁移过程中客户端请求可能收到 ASK 或 MOVED**|
|**Cluster 读写分离**|Cluster 模式下从节点默认不接受读请求（返回 `MOVED`）。需要客户端显式开启 `readonly` 命令。注意：从节点数据可能滞后（异步复制），读从有数据一致性风险|
|** failover：人工 vs 自动**|自动 failover：Sentinel 触发（主从架构）/ Cluster 触发（集群架构，从节点检测主节点失联后发起选举）。手动 failover：`CLUSTER FAILOVER`（集群）/ `SENTINEL FAILOVER`（哨兵）。**区别：手动不触发选举直接切换，用于计划内维护**|
|**集群脑裂问题**|热 网络分区导致两个主节点都接受写请求，分区恢复后数据冲突。**解决方案**：`min-replicas-to-write`（写入时至少同步到 N 个从节点才认为写入成功）+ `min-replicas-max-lag`（最大复制延迟）。**这会牺牲可用性换取一致性，是 CAP 取舍的典型场景**|
