|#|知识点|重要度|笔记三层建议|跨模块关联|
|---|---|---|---|---|
|8.1|**502 Bad Gateway 排查**|🔴 必背|① 含义：Nginx 作为网关收到请求，但无法从上游获得有效响应 ② 常见原因：上游服务挂了 / 防火墙拦截 / upstream 配置错误 / 后端超时未响应 ③ 排查路径：curl 本地 upstream → 检查 upstream 健康状态 → 查看 error.log → 检查防火墙/安全组|→ M2 健康检查、M6 timeout 配置|
|8.2|**504 Gateway Timeout 排查**|🟡 应掌握|① 含义：Nginx 等待上游响应超时 ② 原因：后端接口执行太慢（慢 SQL / 外部调用阻塞）/ read_timeout 设置过短 ③ 排查：先确认是所有接口还是特定接口慢 → 检查后端日志 → 调整 timeout 或优化后端|→ MySQL 慢查询优化、→ RPC 超时配置|
|8.3|**日志格式设计与分析**|🟡 应掌握|① 自定义 log_format（包含 request_time / upstream_response_time / body_bytes_sent / $request_id）② 结合 ELK / Prometheus 做可视化监控 ③ 面试：你们 Nginx 日志是怎么收集和分析的？有没有做链路追踪 ID 透传？|→ SkyWalking 链路追踪、→ ELK 日志平台|
|8.4|**常见性能瓶颈排查思路**|🟡 应掌握|① 工具箱：`nginx -T`（查看完整配置）/ `ab` / `wrk`（压测）/ `netstat -ntp`（连接数）/ `strace`（系统调用跟踪）② 排查套路：先看 QPS → 看 CPU/内存 → 看连接数 → 看 error_log → 定位具体指标 ③ 面试：线上 Nginx CPU 飙高了你怎么排查？（完整思路）|→ JVM 调优思路（类比：先看指标 → 再定位热点）|
