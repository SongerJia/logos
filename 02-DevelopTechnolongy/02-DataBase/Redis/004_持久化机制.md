|知识点|笔记时重点写什么|
|---|---|
|**RDB 快照持久化**|热 `SAVE`（阻塞主线程）/ `BGSAVE`（fork 子进程，Copy-On-Write 机制）。触发方式：save 配置（如 `save 900 1` 表示 900 秒内至少 1 次写就触发）/ 手动执行 / 主从全量同步时。优点：文件紧凑、恢复快；缺点：最后一次快照后的数据会丢失|
|**AOF 追加日志持久化**|热 记录每一条写命令（协议格式，可读可重放）。三种刷盘策略：`always`（每条命令 fsync，最慢最安全）/ `everysec`（每秒 fsync，推荐，最多丢 1 秒数据）/ `no`（依赖 OS 刷盘，最快最不安全）。AOF 重写（`BGREWRITEAOF`）：合并冗余命令，减小文件体积|
|**RDB + AOF 混合持久化**|核 Redis 4.0+ 默认开启（`aof-use-rdb-preamble yes`）。AOF 重写时先写一份 RDB 快照，再追加重写期间的增量 AOF 命令。**重启时先加载 RDB 再重放 AOF 增量**，兼顾速度和安全性。**这是生产环境推荐配置**|
|**AOF 重写流程（源码级）**|核 fork 子进程 → 子进程遍历内存写新的 RDB（混合模式下）或 AOF → 重写期间的新命令写入 `aof_rewrite_buf` 缓冲区 → 子进程完成，父进程将缓冲区内容追加到新 AOF → 原子替换旧 AOF 文件。**理解 fork + COW 是理解 Redis 持久化的关键**|
|**持久化恢复优先级**|同时开启 RDB 和 AOF 时，**优先加载 AOF**（数据更完整）。AOF 文件损坏时可用 `redis-check-aof` 修复工具。RDB 文件损坏可用 `redis-check-rdb` 检查|
