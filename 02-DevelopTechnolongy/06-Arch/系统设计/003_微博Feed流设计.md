|B7-16|**推模式实现细节**|★★★|L1: 发微博→写入个人微博列表(msg_id_list)→获取粉丝列表(fan_uids)→批量写入每个粉丝的inbox(ZSet score=msg_time)；L2: 粉丝量大时的优化：只推给活跃粉丝(近期登录过的)/异步推送(MQ分发写入inbox任务)；3. 存储方案： inbox用Redis Cluster分片(按user_id取模)|1000万粉丝的大V发一条微博要写多少次 inbox？异步推送延迟多久？|FlowPulse大规模消息通知的推模式|
|B7-17|**拉模式实现细节**|★★☆|L1: 打开Feed → 获取关注列表 → 逐个查最近微博 → 合并排序(归并排序) → 分页返回；L2: 优化：关注列表缓存在Redis Set → 批量mget → 内存排序；L3: 问题：关注了1000人，拉取很慢且很多 inactive 用户没有新内容|关注人太多怎么优化？缓存 Timeline 的热度内容？|小规模消息通知可用拉模式|
|B7-18|**Feed存储与分页**|★★☆|L1: inbox/outbox 用 Redis ZSet(score=时间戳，天然有序) → ZREVRANGE 分页；L2. 存储容量规划(每用户保存1000条Feed × 100万用户 = 10亿条)；L3. 冷热分离(最近7天Redis/历史MySQL)|ZSet内存占用怎么算？翻页到第100页还快吗？|FlowPulse通知历史记录存储|
