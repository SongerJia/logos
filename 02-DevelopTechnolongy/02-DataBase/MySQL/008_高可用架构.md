| 知识点                               | 笔记时重点写什么                                                                                                                                                          |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **MHA（Master High Availability）** | 核 自动故障转移工具。组件：Manager（管理节点，负责监控和切换）+ Node（部署在每台机器上的脚本）。故障检测 → 选新主（选最新数据的从库）→ 补齐日志（让其他从库追上新主的 binlog）→ VIP 漂移 → 通知（发邮件/钉钉/调用 API）。**切换过程通常 10~30 秒**               |
| **MGR（MySQL Group Replication）**  | MySQL 原生的高可用方案（5.7.17+）。单主模式（默认，只有一个节点可写）vs 多主模式（所有节点可写但有冲突检测开销）。基于 Paxos 协议（类）的共识算法保证数据一致性。**比 MGA 更轻量，官方原生支持，是未来趋势**                                            |
| **读写分离方案**                        | 代码层（动态 DataSource 切换）、中间件层（ShardingSphere-JDBC / MyCat / Cobar）、代理层（MySQL Proxy / Atlas / MaxScale）。各方案的优缺点对比：代码侵入性、运维复杂度、功能丰富度、社区活跃度。**国内项目 ShardingSphere 最主流** |
| **VIP / DNS / 负载均衡切换**            | VIP（Keepalived 实现 IP 漂移）、DNS（切换域名解析指向）、LB（F5 / LVS / Nginx 四层代理）。VIP 是最简单的方式但只能单活；DNS 切换有缓存延迟；LB 可以做健康检查。**推荐 Keepalived + VIP 作为入门方案**                           |
| **跨机房容灾**                         | 同城双活（光纤直连，<1ms 延迟，实时同步）、异地多活（跨城市，需处理数据冲突和路由策略）、两地三中心（同城 + 异地灾备）。MySQL 场景下通常用异步复制 + 应用层补偿保证最终一致性                                                                   |
