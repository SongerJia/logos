## 一、RPC 基础概念

### **Q1** 什么是 RPC（Remote Procedure Call）？RPC 和 HTTP 调用的本质区别是什么？
?
1. RPC 是远程过程调用，核心思想是让调用远程服务像调用本地方法一样简单。客户端调用一个接口方法，底层通过代理、序列化、网络传输、反序列化这一套机制，把请求发到远程服务端执行，拿到结果返回给客户端，整个过程对业务代码透明。
2. RPC 和 HTTP 调用的本质区别不在协议层面，而在于设计哲学和使用方式。RPC 是面向方法的，关注的是调用哪个服务的哪个方法，传什么参数，返回什么结果。HTTP 是面向资源的，关注的是对哪个资源的什么操作，GET、POST、PUT、DELETE 对应资源的增删改查。
3. 从实现角度看也有几个关键差异。一是传输协议，RPC 可以自定义协议，不一定跑在 HTTP 之上，比如 Dubbo 用自己精简的二进制协议，头部只有十几个字节，而 HTTP 协议的头部可能有几百字节甚至上千字节，传输效率差很多。二是序列化方式，RPC 一般用高效的二进制序列化比如 Hessian、Protobuf、Kryo，HTTP 通常用 JSON 这种文本格式，序列化效率和体积都有差距。三是连接模型，RPC 通常用长连接加连接池复用，减少握手开销，HTTP 默认是短连接，每次请求都要三次握手，当然 HTTP 也可以配 Keep-Alive 用长连接。四是服务治理，RPC 框架通常自带注册发现、负载均衡、容错、限流这些能力，HTTP 调用的治理需要额外组件配合。

### **Q2** RPC 调用的一次完整链路？这里的动态代理在 Dubbo 中是怎么实现的？
?
1. 一次 RPC 调用的完整链路从客户端到服务端大致是这样几个步骤。
2. 客户端这边，业务代码调用一个接口方法，实际上调用的是 Dubbo 生成的代理对象。代理对象把方法名、参数类型、参数值这些调用信息封装成一个 RPC 请求对象。接着通过序列化把请求对象转成二进制数据。然后从注册中心拉取的服务提供者列表中选择一个目标地址，通过负载均衡策略选出一台机器。最后通过 Netty 网络框架把二进制数据发送过去。
3. 服务端这边，Netty 收到数据后交给 Dubbo 的线程池处理。首先反序列化把二进制还原成请求对象。然后根据请求中的接口名和方法名定位到具体的实现类和方法。通过反射调用目标方法执行业务逻辑。拿到返回结果后序列化发送回客户端。客户端收到响应反序列化出结果返回给业务代码。
4. Dubbo 中动态代理默认用 Javassist 来做字节码生成。JDK 动态代理需要接口，Cglib 基于继承实现、效率比 Javassist 低一点。Dubbo 用 Javassist 直接生成字节码，不需要反射调用，比 JDK 代理和 Cglib 性能更好。生成的代理类实现了业务接口，在 invoke 方法中组装 RPC 请求、选择服务提供者、发起远程调用、返回结果，对业务代码完全透明。

### **Q3** 为什么微服务内部调用倾向 RPC，对外 API 倾向 HTTP/RESTful？
?
1. 这是由两者使用场景和诉求的不同决定的。
2. 内部调用对性能要求高，服务之间调用非常频繁，每次调用几十上百字节的 Header 开销积累下来影响很大，RPC 的二进制协议和高效的序列化可以做得很轻量。内部调用还需要完善的服务治理，注册发现、负载均衡、熔断限流、流量路由这些能力 RPC 框架原生支持得很好。内部服务通常是一个技术栈，Java 服务调 Java 服务，Dubbo 可以很好地工作。内部接口也不需要对外暴露，不需要考虑多语言兼容性。
3. 对外 API 的核心诉求是通用性。HTTP 是互联网最通用的协议，任何语言、任何平台都能调用，客户端可能是浏览器、移动 App、第三方系统，不可能要求他们统一接入 Dubbo。RESTful 风格语义清晰，URL 设计直观，用 JSON 返回结果可读性好，方便前端和第三方对接。对外 API 的治理更多在网关层，认证鉴权、限流、日志、跨域，API 网关来处理这些比 RPC 框架更合适。而且对外接口量小，频次低，HTTP 的协议开销相对可以接受。
4. 所以不是技术优劣的问题，而是场景匹配的问题。内部调用追求性能和治理，用 RPC。对外提供追求通用和简单，用 HTTP。

## 二、Dubbo 核心架构

### **Q4** Dubbo 的四大核心组件和调用流程? Dubbo 的服务注册和发现是"推"还是"拉"？
?
1. 四大核心组件是注册中心、服务提供者 Provider、服务消费者 Consumer、监控中心 Monitor。
2. 调用流程是这样的。第一步，Provider 启动时向注册中心注册自己提供的服务，包括服务接口名、IP、端口等信息。第二步，Consumer 启动时向注册中心订阅需要的服务，获取 Provider 列表并缓存到本地。第三步，Consumer 调用服务时通过负载均衡选择一个 Provider，直接发起远程调用。第四步，Provider 和 Consumer 定时向监控中心上报调用次数、耗时等统计数据。
3. Dubbo 的服务发现是拉模式，但不是纯轮询。Consumer 启动时主动从注册中心拉取服务列表，同时注册一个 Watcher 监听变化。当 Provider 列表变化时，注册中心主动推送变更事件给 Consumer，Consumer 更新本地缓存。所以准确说是启动时拉一次，后续通过事件通知增量更新，结合了拉和事件通知。

### **Q5** Dubbo 的服务暴露过程? 服务引用的过程?
?
1. 服务暴露是 Provider 把本地服务注册到注册中心的过程。
2. 大致分几步。第一步是解析配置，Dubbo 启动时解析 XML 或者注解中的服务配置，包括接口名、超时时间、协议端口等。第二步是把服务实现类包装成 Invoker 对象，Invoker 是 Dubbo 的核心模型，代表一个可调用的对象。第三步是通过 Protocol 协议层把 Invoker 暴露出去，比如用 Dubbo 协议就启动 Netty 服务监听一个端口等待请求。第四步是向注册中心注册服务地址信息，把接口名加 IP 端口等元数据写入注册中心。
3. 服务引用是 Consumer 从注册中心获取服务并生成本地代理的过程。第一步是解析 Consumer 端的引用配置，指定要引用的接口名。第二步是从注册中心拉取该接口的 Provider 列表，然后在本地通过 RegistryDirectory 维护这个列表，并监听变更。第三步是把远程的 Provider 列表封装成集群 Invoker，内部包含了负载均衡和容错策略。第四步是用动态代理生成接口的代理对象，业务代码注入的就是这个代理对象，调用代理方法时就触发远程调用。

> **Q6** Dubbo 的 URL 总线设计? 为什么 Dubbo 要用 URL 作为配置总线？

URL 总线是 Dubbo 架构中一个独特的设计。Dubbo 在整个框架中几乎所有配置信息都用 URL 来表示和传递，URL 格式是 protocol://username:password@host:port/path?key1=value1&key2=value2。

Dubbo 用 URL 作为配置总线的理由很充分。一是统一性，不管是最初的 XML 配置、注解配置，还是注册中心的服务地址、RPC 请求的元数据，都统一用 URL 表达，一个数据结构贯穿整个调用链，逻辑统一不割裂。二是可扩展性，URL 本质是 key-value 的集合，新增配置项只需要新增参数键值对，不需要改数据结构。三是可传递性，URL 本身就是网络协议的标准表达，天然适合在不同组件之间传递，注册中心存储的是 URL、Provider 向 Consumer 传递的也是 URL、配置中心的配置合并也是 URL。四是可读和可调试性，URL 格式是文本，一行就能看到所有关键信息，排查问题直接打印 URL 就知道这次调用的全貌。

缺点是参数多了 URL 会很臃肿，某些配置项的值需要转义。但总的来说在纯 Java 体系内 URL 总线的设计非常巧妙。

## 三、Dubbo SPI 扩展机制

> **Q7** Dubbo SPI 和 Java SPI 有什么区别？Dubbo SPI 的"自适应扩展"（Adaptive Extension）是什么？怎么通过 `@Adaptive` 注解动态选择实现？

Java SPI 是 JDK 自带的扩展机制，通过 META-INF/services 下的文件声明接口的实现类，然后用 ServiceLoader 加载。缺点很明。JDK 的 SPI 会一次性加载所有实现类，不管你用不用，浪费资源。扩展点失败没有异常信息，只有日志。不支持 IoC 和 AOP。扩展点的名称不支持自定义。

Dubbo SPI 对 Java SPI 做了大幅增强。第一是按需加载，不会一次性加载所有实现，通过 getExtension 按名称获取时才会实例化。第二是支持 IoC 依赖注入，扩展类中如果有其他扩展的 setter 方法会自动注入。第三是支持 AOP 包装增强，每个实现类可以有一个或多个 Wrapper 类包裹，实现类似切面的功能。第四是扩展点有别名，实现类可以在 SPI 注解里起一个好记的名字，方便按名获取。第五是失败时抛出明确的异常信息。

自适应扩展是 Dubbo SPI 的特色能力，它能根据运行时上下文的参数动态选择使用哪个扩展实现。用 @Adaptive 注解标注在接口方法上或者实现类上。标注在实现类上表示这个实现类就是自适应类直接调用。标注在接口方法上时，Dubbo 会自动生成一个自适应实现类，这个生成类的逻辑是根据 URL 中的参数来决定调用哪个具体的扩展实现。比如 Protocol 接口的 export 方法标注了 @Adaptive，那么自适应实现会根据 URL 中的 protocol 参数来决定是走 DubboProtocol 还是 HttpProtocol，等于运行时动态绑定。

> **Q8** Dubbo 的 SPI 扩展机制中，"Wrapper 类"（包装类 / AOP 增强）是怎么工作的？"Wrapper" 类必须满足什么条件？

Wrapper 类是实现 Dubbo SPI AOP 能力的关键机制。当一个扩展实现类被加载后，Dubbo 会检查所有也实现了同样的扩展接口的类，看哪些类的构造方法接受这个扩展接口作为单一参数，这些类就是 Wrapper 类。Dubbo 会用 Wrapper 包装原始的扩展实现，多层 Wrapper 依次嵌套，形成装饰器链，调用时从最外层 Wrapper 开始逐层进到最内层的真实实现。

Wrapper 类必须满足的条件是，实现同样的扩展接口，同时构造方法接受该扩展接口类型的参数。比如 Protocol 接口有一个 ProtocolFilterWrapper，它的构造函数是 ProtocolFilterWrapper(Protocol protocol)，参数是 Protocol 类型，那它就是一个 Wrapper。它的实现就可以在 protocol.export 前后插入过滤器的处理逻辑。

典型应用是 Dubbo 中的 Filter 链就是通过 ProtocolFilterWrapper 作为 Wrapper 来实现的。ProtocolListenerWrapper 是另一个 Wrapper，负责在暴露和引用前后触发事件监听。这些 Wrapper 让框架在核心流程中插入了扩展能力，而核心流程本身不需要知道这些扩展的存在。

## 四、注册中心

> **Q9** Dubbo 支持哪些注册中心？为什么 Dubbo 早期默认 ZK，现在推荐 Nacos？

Dubbo 支持的注册中心包括 ZooKeeper、Nacos、Redis、Consul、Etcd 等，也支持基于文件的本地注册用于测试。

早期默认 ZooKeeper 有几个原因。ZK 在分布式协调领域生态最成熟，业界有大量成功案例。它的 CP 特性保证了服务列表的一致性，这个在注册中心场景非常重要。ZK 的 Watcher 机制天然适合做服务上下线的实时通知。当时几乎没有其他更好的选择，社区习惯也是用 ZK 搭配 Dubbo。

现在推荐 Nacos 有几个原因。一是功能更全面，Nacos 不光是注册中心，也是配置中心，一套组件同时搞定服务发现和配置管理，架构更简洁。二是 AP 加 CP 的混合模式，ZooKeeper 是 CP 模型，网络分区时宁可不可用也要保一致性，而 Nacos 可以选择 AP 模式，网络分区时仍然可用，对注册中心来说可用性比强一致性更重要。三是运维友好，ZK 的运维门槛比较高，JVM 参数调优、选举机制、会话超时、磁盘清理都要关注，Nacos 开箱即用，控制台功能也比 ZK 丰富。四是云原生支持，Nacos 对 Kubernetes、Service Mesh 的支持更好，是阿里云微服务体系的标准组件，符合当下技术趋势。Dubbo 3.x 之后社区主推的也是 Nacos 和 Zookeeper 并行的路线。

> **Q10** ZooKeeper 作为注册中心时，网络分区导致 Provider 节点被 ZK 删除了，但实际上 Provider 还活着，怎么办？怎么缓解？

这种现象的根本原因是 ZK 的会话超时机制。Provider 和 ZK 之间有心跳维持会话，当网络出现抖动或者 Provider Full GC 导致心跳超时，ZK 认为 Provider 失联了，删除它的临时节点。但 Provider 实际上还活着，只是暂时和 ZK 断联了。Consumer 从 ZK 收到节点删除事件，移除这个 Provider，导致流量不再打过去。

解决方案有几层。一是调整 ZK 的会话超时时间，适当调大，比如从默认的十几秒调大到三十秒甚至一分钟，减少因为短暂网络抖动或者 GC 被踢出的概率。但这只能缓解不能根治。

二是 Provider 端做优雅的自我保护。即使被 ZK 踢出了，Provider 不立即关闭已启动的服务端口，继续保持服务能力。Consumer 端的本地缓存中可能还有这个 Provider，短时间内仍可以继续调用。等网络恢复了，Provider 重新向 ZK 注册临时节点，恢复正常。

三是在 Consumer 端启用缓存和容错。Dubbo 的 Consumer 从注册中心拿到服务列表后会缓存到本地，即使注册中心挂了 Consumer 也可以靠缓存继续调用。所以即使 ZK 短暂故障或者 Provider 临时节点被误删，Consumer 在一段时间内仍然能工作。

四是考虑迁移到 Nacos。Nacos 有 AP 模式，不依赖会话机制，临时节点不会因为心跳超时被删除，避免了网络分区导致的误踢出问题。配合健康检查机制，Nacos 能更准确地判断服务是否真的不可用。

## 五、负载均衡策略

> **Q11** Dubbo 内置的 5 种负载均衡策略分别是什么？什么场景用哪个？

第一种是 RandomLoadBalance 随机，带权重的随机算法，默认策略。权重越高的 Provider 被选中的概率越大。适合 Provider 配置不同但大多数场景通用的情形，也是用的最多的。

第二种是 RoundRobinLoadBalance 轮询，按顺序依次分发请求。也支持权重，权重高的轮到的次数多。适合 Provider 配置一致、请求处理耗时均匀的场景。注意普通的加权轮询可能有流量突刺的问题，Dubbo 实现的是平滑加权轮询，流量分配更均匀。

第三种是 LeastActiveLoadBalance 最少活跃数，每次选当前活跃请求数最少的 Provider。在活跃数相同的情况下用加权随机来选。适合请求处理时间差异大的场景，避免慢的 Provider 积压更多请求。比如某个 Provider 处理复杂业务耗时较长，它上面的活跃请求数就多，新的请求会选择活跃数少的 Provider。

第四种是 ConsistentHashLoadBalance 一致性哈希，根据请求参数做哈希映射到固定的 Provider。同一个参数值的请求永远落到同一个 Provider 上。适合需要会话粘滞性的场景，比如服务内部有状态缓存，希望相同用户的请求都打到一个节点上提高缓存命中率。

第五种是 ShortestResponseLoadBalance 最短响应时间，Dubbo 2.7 引入的。综合了最少活跃数和响应时间，选取预估响应时间最短的 Provider。在活跃连接数接近的时候能更精准地选择最快的节点。

> **Q12** Dubbo 的加权随机负载均衡，"权重"是怎么发挥作用、怎么配置的？如果权重配置 200 : 100，实际流量分布会是严格的 2:1 吗？

权重发挥作用的核心是在计算随机值时，不同权重的 Provider 在随机空间中占据的范围不同。假设两个 Provider，A 权重两百 B 权重一百，总权重三百。生成一个零到二百九十九的随机数，零到一百九十九落在 A 的范围选 A，二百到二百九十九落在 B 的范围选 B。这样 A 被选中的概率是三分之二，B 是三分之一。

权重配置方式有几种。可以在 Dubbo 管理控制台动态配置。可以通过配置文件或者注解在 Provider 端指定 weight 参数。还可以基于系统运行时的负载自动调整权重，Dubbo 支持根据 CPU 使用率动态调整。

但两百比一百配置不等于严格的二比一流量分布。随机算法本身就有概率波动，样本量小的时候偏差比较明显，比如只有一百次请求可能分布是六十八比三十二而不是六十七比三十三。请求量越大越接近理论比值，大数定律保证了这一点。而且还有环境因素，比如 Consumer 的网络到某个 Provider 更快也会造成微小偏差。如果有 Provider 响应慢可能导致 Consumer 端的请求超时重试，实际流量会比预期更多。所以权重要配合实际流量监控来校调，不能只看理论值。

## 六、集群容错

> **Q13** Dubbo 的 6 种集群容错模式? 每个模式的典型应用场景是什么？

第一种 Failover，失败自动重试。调用失败后换另一个 Provider 重试，默认重试两次共三次调用。这是默认策略，适合幂等的查询操作，比如根据 ID 查询用户信息。不适合非幂等的写操作。

第二种 Failfast，快速失败。调用失败后立即报错不重试。适合非幂等的写操作，比如扣款、下单，重试会导致重复扣款。

第三种 Failsafe，安全失败。调用失败后直接忽略返回空结果。适合不重要的旁路操作，比如写日志、发送通知，失败了也无所谓不影响主流程。

第四种 Failback，失败自动恢复。调用失败后把请求放入一个定时重试队列，后台定时重发。适合对实时性要求不高但必须成功的场景，比如数据同步、消息通知。

第五种 Forking，并行调用。同时向多个 Provider 发起相同请求，只要有一个成功就返回，通常配置 fork 数为二。适合实时性要求极高的读操作，牺牲额外的资源换降低延迟，比如广告竞价场景。

第六种 Broadcast，广播调用。向所有 Provider 逐一发起调用，任意一个失败就报错。适合通知所有 Provider 更新缓存的场景，比如后台管理触发全量缓存刷新。

> **Q14** Failover + 重试 3 次 = 什么问题？这是一个典型的"非幂等操作 + 重试 = 重复数据"问题。怎么解决？

问题很明确，非幂等的写操作在 Failover 重试下会出现业务数据重复。比如创建一个订单，第一次调用超时了但服务端其实创建成功了，Consumer 端因为超时认为调用失败，换另一个 Provider 重试，结果创建了两个订单。或者扣减库存，扣减成功但网络超时，重试导致多扣了一次。

解决方案分为几个层面。第一是从业务层面保证幂等，这个是最根本的方案。在服务端实现幂等的业务逻辑，根据请求中的唯一业务标识比如订单号、请求 ID 去重，如果已经处理过直接返回成功不再重复处理。

第二是合理选择集群策略。非幂等的写操作设置为 Failfast 不要用 Failover，或者把重试次数设为零。如果必须重试，确保业务实现了幂等。

第三是引入全局去重机制。每个 RPC 请求生成一个全局唯一的 TraceID 或 RequestID，服务端基于这个 ID 做去重。配合 Redis 或者数据库的唯一索引，确保同一个请求 ID 只处理一次。

第四是服务端做乐观锁控制。比如通过版本号或者状态字段来更新数据，即使重复请求也不会产生副作用。比如 Update 订单状态 where 状态为待支付，第二次执行的时候状态已经不是待支付了，不会产生效果。

> **Q15** Dubbo 的熔断机制（Circuit Breaker）在 2.7+ 版本中怎么实现的？这和 Sentinel 的熔断有什么区别？

Dubbo 2.7 之后集成了 Sentinel 作为熔断限流的实现。Dubbo 框架本身不实现熔断逻辑，而是提供了对 Sentinel 的自动集成。当 Consumer 端引入 Sentinel 依赖后，Dubbo 自动将 RPC 调用纳入 Sentinel 的资源管理，可以配置熔断规则对某个接口或方法生效。

工作原理是 Sentinel 统计每个被保护的资源在一定时间窗口内的调用结果。当错误率或者慢调用比例超过阈值就触发熔断，熔断状态下不再发起远程调用，直接抛出降级异常，经过一段恢复时间后半开试探，放行少量请求如果成功就关闭熔断恢复。

和 Sentinel 原生熔断的区别在于，Dubbo 集成 Sentinel 是基于 RPC 框架层面的自动熔断，不需要业务代码写任何 Sentinel 的资源配置。Dubbo 的 Sentinel 过滤器会自动把接口方法注册为 Sentinel 资源，熔断指标统计的是 RPC 调用的成功失败慢调用这些。而 Sentinel 本身是一个更通用的流控和熔断框架，不光能用在 RPC 场景，也能用在 HTTP 调用、数据库访问、消息发送等任意需要保护的场景，并且 Sentinel 的控制台提供实时监控和动态规则下发能力。两者的关系是 Dubbo 把 Sentinel 内置为熔断实现，利用了 Sentinel 丰富的熔断策略和动态配置能力。

## 七、通信协议与序列化

> **Q16** Dubbo 支持哪些通信协议？什么时候该换协议？

Dubbo 支持的协议比较多，常用的有几个。

Dubbo 协议是默认协议，基于 TCP 长连接加 Netty NIO 通信，使用 Hessian 序列化。单连接模型，适合小数据量、高并发的服务调用，性能好。连接数少，消费者数量远多于提供者时不会占满服务端连接。但不适合传大文件，单个请求超过几百 KB 时表现不好。

Triple 协议是 Dubbo 3.x 的主推协议，基于 HTTP/2 和 gRPC 标准，使用 Protobuf 序列化。支持请求流、响应流、双向流，跨语言能力强，适合需要多语言互通和流式调用的场景。

REST 协议基于 HTTP 和 RESTful 风格，可以用 JSON 和 XML 序列化。适合需要对外暴露 HTTP 接口的场景，方便非 Java 客户端调用。

Hessian 协议和 Dubbo 协议类似，但序列化使用 Hessian2，也是基于 HTTP。适合需要穿透防火墙和负载均衡的场景，因为走 HTTP 协议更容易被基础设施兼容。

Thrift 协议跨语言效果好，适合异构系统。gRPC 协议基于 HTTP/2 和 Protobuf，流式调用场景首选。

换协议的时机主要是，当系统接入多语言客户端时从 Dubbo 协议迁到 Triple 或 gRPC 协议。当需要穿透网关或者和 HTTP 体系打通时从 Dubbo 协议迁到 REST 协议。当传输大报文或者文件时不适合 Dubbo 协议的单连接长连接模型。当需要流式处理时 Dubbo 协议不支持换为 Triple 协议。简而言之，Dubbo 协议适合纯 Java 微服务内部调用，其他场景按需选协议。

> **Q17** Dubbo 支持哪些序列化方式？Kryo 比 Hessian2 快在哪？Kryo 的缺点是什么？

Dubbo 支持的序列化方式包括 Hessian2 默认、Kryo、Protobuf、JSON、Java 原生序列化、FST 等。

Kryo 比 Hessian2 快主要是几个方面。第一，Kryo 是基于字节码生成的技术，序列化和反序列化时不依赖反射而是提前生成或动态生成类对应的序列化代码，免去了反射调用的开销。Hessian2 还是基于反射来读写字段。第二，Kryo 序列化产生的字节体积更小，因为它使用变长整数编码、引用去重等压缩技术。第三，Kryo 的对象图遍历效率更高，对循环引用和共享引用的处理更优化。

Kryo 的缺点也很明显。一是线程不安全，Kryo 实例不是线程安全的，不能多个线程共用一个实例，Dubbo 通过 Kryo 池来解决这个问题，每次借用和归还实例有一定开销。二是序列化结果依赖于类的注册顺序，如果服务端和客户端的类注册顺序不一致可能导致反序列化失败。三是版本兼容性差，加字段或者改字段类型容易导致反序列化出错，不像 JSON 和 Hessian 那样有天然的容错性。四是不支持跨语言，Kryo 是 Java 专用的，而 Protobuf 和 Hessian 可以跨语言。

所以 Kryo 适合纯 Java 体系内部高性能场景，但如果需要考虑跨语言或版本兼容性，Protobuf 和 Hessian2 更好。

> **Q18** 序列化协议选型对比? 什么时候选 JSON？

序列化协议选型主要看四个维度，性能、体积、兼容性、跨语言支持。

Protobuf 性能最好，体积最小，跨语言支持好，版本兼容性靠字段编号保证。缺点是需要定义 proto 文件并编译，开发流程多一步，不像 Java 对象直接用。

Hessian2 是 Dubbo 默认，性能不错体积适中，跨语言支持一般，版本兼容性好，对象直接序列化，开发体验好。

Kryo 性能接近 Protobuf 体积比 Hessian2 小，缺点是跨语言不支持、版本兼容性差、线程不安全需要池化。

JSON 序列化在以下场景用最合适。一是需要对浏览器或者前端暴露接口时，JSON 是浏览器原生支持的格式。二是调试阶段，JSON 可读性好，排查问题时方便看传输的数据内容。三是消息需要跨系统流转且接收方可能是各种语言，JSON 通用性最强。四是和历史系统对接，很多老旧系统只支持 JSON。五是数据结构比较简单字段不多，JSON 的序列化性能差距不明显。

业务系统内部微服务调用通常用 Hessian2 或者 Protobuf，兼具性能和兼容性。

## 八、Dubbo 的线程模型

> **Q19** Dubbo 的服务端线程模型? 如果所有业务线程都在处理，新来的请求会怎样？怎么根据业务特点配置线程池？

Dubbo 服务端的线程模型核心是 IO 线程和业务线程分离。Netty 的 IO 线程负责网络数据的读写和编解码，不处理业务逻辑。业务逻辑交给 Dubbo 的业务线程池处理，默认是一个固定大小的线程池，大小是两百。

当所有业务线程都在忙，新来的请求会在业务线程池的任务队列中排队等待。Dubbo 默认的任务队列长度是零，也就是有界队列，意思是当线程全忙时新任务不排队直接通过拒绝策略处理。默认的拒绝策略是 AbortPolicy 抛出异常，Consumer 端会收到超时或者连接断开的错误然后根据集群策略决定是否重试。

配置线程池要根据业务特点来。CPU 密集型的业务线程数设为核心数的两倍左右，任务队列可以设为零用拒绝快速失败。IO 密集型的业务比如调数据库调第三方接口，可以设更大的线程数，甚至可以到五百甚至上千，因为线程大部分时间在等待不占 CPU。混合型的建议用动态线程池根据监控调整。

配置上，可以通过 threadpool 属性选线程池类型，fixed 固定大小、cached 缓存可伸缩、limited 固定但有任务队列积压的能力。线程数用 threads 设定，队列长度用 queues 设定。

> **Q20** Dubbo 的"Dispatcher 策略"? 为什么默认是 `all`？什么时候用 `direct`？

Dubbo 的 Dispatcher 策略决定了消息怎么从 IO 线程派发到业务线程池。

all 是默认策略，所有请求消息包括请求和响应都在业务线程池中处理，IO 线程只负责网络收发。优点是 IO 线程不阻塞，不会被慢业务的处理拖住整个连接。缺点是每个请求都要线程切换一次，有上下文切换开销。

direct 策略是所有消息直接在 IO 线程中处理，不经过业务线程池。优点是省去了线程切换开销，处理链路最短。缺点是 IO 线程如果被慢业务逻辑阻塞，整个连接上的其他请求都会排队等待，吞吐大幅下降。这种只在业务逻辑非常简单、执行极快、几乎不涉及 IO 的场景使用，比如简单的缓存读取或者直接返回常量。

message 策略是只把请求消息派发到业务线程池，响应消息直接在 IO 线程返回。

execution 策略是只把请求消息派发到线程池，响应和连接事件在 IO 线程处理，和 message 类似但对连接的关注不同。

connection 策略是在 IO 线程里处理连接事件和编解码，其他都在业务线程池。

默认用 all 是因为大多数业务场景业务逻辑有一定耗时，放在业务线程池处理不影响 IO 线程效率和整体吞吐。direct 只有极端追求低延迟且业务逻辑极其简单时才用。

## 九、Dubbo 服务治理

> **Q21** Dubbo 怎么实现服务的"版本管理"和"灰度发布"？Dubbo 3.x 的"应用级服务发现"对灰度有什么改进？

Dubbo 的版本管理通过在服务暴露和引用时指定 version 参数实现。Provider 端配置 version 为 1.0.0，Consumer 端指定 version 为 1.0.0，双方精确匹配才能调用。需要发布新版本时，Provider 端暴露新版本 2.0.0 同时保留 1.0.0，Consumer 端逐步切换到 2.0.0。

灰度发布的核心是利用路由规则。Dubbo 支持条件路由和标签路由。条件路由可以在管理控制台配置规则，比如只把内测用户的 IP 段路由到新版本 Provider。标签路由是给 Provider 打标签，Consumer 也打标签，标签匹配的才路由过去。这样新版本先导一小部分流量过去验证，验证没问题逐步扩大流量比例，直到百分百。

Dubbo 3.x 应用级服务发现的改进很大。2.x 是接口级发现，一个接口一个注册路径，大型微服务系统一个应用可能有上百个接口，注册中心数据量大，路由规则配置复杂。3.x 改为应用级注册，以应用名为粒度注册，大大减少了注册中心的数据量和变更频率。应用级服务发现配合元数据中心，可以通过应用名加接口名定位到具体的服务，路由和灰度规则可以基于应用粒度配置而不是接口粒度，灰度策略的制定和维护简单了很多。同时应用级服务发现天然适配 Kubernetes 的 Service 模型，对 K8s 部署灰度更友好。

> **Q22** Dubbo 的参数回调（Callback）和事件通知（oninvoke / onreturn / onthrow）是干什么的？参数回调有什么坑？

参数回调是 Consumer 端把自己的一个接口实现传给 Provider，Provider 在处理请求时可以回过头来调用 Consumer 的方法。本质上是双方互为客户端和服务端。典型场景是 Consumer 提交一个异步任务给 Provider，Provider 处理完后通过回调接口把结果返回给 Consumer。

事件通知是在 Consumer 调用 Provider 时注册三个回调方法。oninvoke 在发起调用之前触发，onreturn 在调用成功返回之后触发，onthrow 在调用抛出异常时触发。可以用来做调用监控、日志记录、返回结果的后处理。

参数回调的坑有几个。一是连接模型的冲突，Dubbo 协议默认是单长连接，同一个 Consumer 到 Provider 只有一条连接，Consumer 回调 Provider 的同时 Provider 也在回调 Consumer，如果都在同一连接上数据传输可能互相干扰。二是回调接口的线程安全问题，回调是在 Provider 的线程池中执行的，如果同时回调多个 Consumer 的方法要做好并发控制。三是网络可达性问题，回调要求 Provider 能反向连接到 Consumer，如果 Consumer 在 NAT 后面或者在容器里 IP 动态变化，Provider 连不到 Consumer 导致回调失败。四是超时和异常处理，回调本身也可能超时或失败，需要做超时设置和异常兜底。

更推荐的做法是用异步消息或者响应式编程来代替参数回调，比如 Provider 把结果发到 MQ，Consumer 消费 MQ 拿结果，解耦更彻底更可靠。

## 十、Dubbo 3.x 新特性

> **Q23** Dubbo 3.x 的"应用级服务发现"（Application-Level Service Registry）和 Dubbo 2.x 的"接口级服务发现"有什么区别？这解决了 2.x 的什么痛点？接口→应用的映射是怎么维护的？

2.x 的接口级发现是以接口名为粒度注册。每个服务的每个接口都在注册中心创建一个对应的节点，记录这个接口的 Provider 地址列表。一个应用往往暴露几十上百个接口，注册中心就有几十上百个节点。当 Provider 的任何一个接口发生变更比如重启或者扩容，注册中心的数据都要更新一遍，产生海量变更事件。Consumer 端要订阅所有调用的接口，消费者依赖的接口多了订阅数量也爆炸。

3.x 的应用级发现改为以应用名为粒度注册，一个应用只在注册中心注册一条记录，包含了这个应用提供的所有服务的元数据引用。注册中心的数据量大幅减少，变更事件也大幅减少，Consumer 端只需要订阅应用名，不关心具体的接口列表。

要解决的核心痛点是注册中心的性能瓶颈。大型微服务系统接口数量可能成千上万，接口级发现导致注册中心数据量和推送量难以承受，Zookeeper 尤其明显。应用级发现把注册数据的规模从接口数量级降到应用数量级，是数量级的优化。

接口到应用的映射通过元数据中心来维护。Provider 启动时把接口列表、方法签名等元数据发布到元数据中心而不是注册中心。Consumer 启动时先从注册中心获取应用级别的 Provider 地址，再从元数据中心获取这个应用提供了哪些接口，把两者关联起来得到完整的可调用服务列表。这个映射变更频率低，不需要注册中心实时推送。

> **Q24** Dubbo 3.x 的"Triple 协议"是什么？和 Dubbo 2.x 的 `dubbo://` 协议比，Triple 协议解决了什么问题？

Triple 协议是 Dubbo 3.x 定义的新一代通信协议，基于 HTTP/2 并兼容 gRPC 协议规范，使用 Protobuf 作为默认序列化。

和 2.x 的 dubbo 协议比，Triple 协议解决的核心问题有三个。第一是跨语言互通，dubbo 协议是自定义二进制协议，只有 Java 的客户端能调用，其他语言需要另外开发。Triple 协议完全兼容 gRPC 标准，任何支持 gRPC 的语言都能直接调用 Dubbo 服务，实现了真正的多语言生态。

第二是流式调用，dubbo 协议是一问一答模型，不支持请求流、响应流和双向流。Triple 协议基于 HTTP/2 的多路复用和流特性，天然支持这三种流模式，适合文件传输、实时数据推送、流式处理等场景。

第三是网关和基础设施的兼容性，dubbo 协议是自定义 TCP 协议，从四层负载均衡到七层网关都很难识别和路由。Triple 协议走 HTTP/2，标准的 HTTP 基础设施如 Nginx、Envoy 都能识别并做七层路由和负载均衡，穿透性好。配合云原生架构天然就兼容 Service Mesh 的 Sidecar 代理模式。

在性能方面 Triple 也不差，HTTP/2 有头部压缩和多路复用，性能接近 dubbo 协议的水平，加上 Protobuf 高效序列化，实际性能差距很小。

> **Q25** Dubbo 3.x 对云原生（Kubernetes / Service Mesh）的支持? 这和传统的 Dubbo + ZK/Nacos 有什么区别？

Dubbo 3.x 对云原生的支持主要体现在几个方面。一是应用级服务发现，天然映射到 Kubernetes 的 Service 概念，一个 Dubbo 应用对应一个 K8s Service。二是支持 Kubernetes 原生服务发现，Dubbo 可以直接利用 K8s 的 API Server 做服务注册发现，不需要额外的注册中心，直接读取 Pod 和 Service 的信息。三是 Triple 协议兼容 HTTP/2 和 gRPC，可以直接在 Istio 或 Envoy 这样的 Service Mesh 中透明代理，Mesh 可以接管流量管理、负载均衡、熔断限流。四是新一代的统一路由规则，和 Mesh 体系的路由规则模型对齐，可以用统一的规则在 Dubbo SDK 侧和 Mesh Sidecar 侧分别控制流量。

和传统 Dubbo 加 ZK 或 Nacos 的区别在于职责分工不同。传统模式下，Dubbo SDK 承担了几乎所有治理能力，注册发现、负载均衡、路由、容错都在 SDK 里。云原生模式下，SDK 变得薄了，注册发现可以交给 K8s，负载均衡熔断路由可以交给 Service Mesh 的 Sidecar，Dubbo 变成更纯粹的业务 RPC 框架。传统模式运维效率低，要管理注册中心集群、要单独维护 Dubbo 的各种治理规则。云原生模式运维靠 K8s 和 Mesh 统一管理，实现基础设施标准化。但传统模式可控性更高，不依赖 K8s 和 Mesh 体系，适合非容器化部署的场景。

## 十一、RPC vs HTTP / gRPC / Spring Cloud

> **Q26** RPC 框架（Dubbo）和 HTTP 框架（Spring Cloud + Feign + Ribbon）」选型对比。什么时候选 Dubbo？什么时候选 Spring Cloud？

Dubbo 和 Spring Cloud 代表着两种不同的微服务体系。

什么时候选 Dubbo。第一是纯 Java 技术栈，服务都是 Java 写的，不需要考虑多语言调用，Dubbo 的性能和治理能力可以充分发挥。第二是对性能要求高，内部服务调用量很大，Dubbo 的自定义协议和二进制序列化比 HTTP 加 JSON 性能好很多。第三是需要复杂的服务治理，Dubbo 的负载均衡、路由、容错、降级、流量控制这块的原生能力非常成熟。第四是公司本身是阿里技术栈系，Dubbo 是标配。

什么时候选 Spring Cloud。第一是技术栈多样，系统中有 Java、Python、Go、Node 等多种语言，HTTP 加 JSON 是最通用的选择。第二是需要对外开放 API，Spring Cloud Gateway 加 RESTful 接口天然适合对外暴露。第三是团队对 Spring 生态熟悉，Spring Cloud 全家桶开箱即用，生态组件丰富。第四是需要和云平台深度集成，Spring Cloud 的各个组件和各大云厂商都有很好的整合。第五是需要使用 HTTP 的缓存、代理、网关等基础设施，整个链路都是基于 HTTP 的。

两者也可以混用。内部服务之间用 Dubbo 获得高性能和强治理，对外的 API 网关用 Spring Cloud Gateway 暴露 REST 接口。

> **Q27** gRPC 的四大核心特性? gRPC 和 Dubbo Triple 协议的区别？

gRPC 的四大核心特性是，基于 HTTP/2，使用 Protobuf 作为接口定义语言和序列化，支持四种调用模式一元、服务端流、客户端流、双向流，原生跨语言支持。

gRPC 和 Dubbo Triple 协议的区别有几个层面。从协议层面看，Triple 协议是兼容 gRPC 的，Triple 可以理解为一个扩展的 gRPC 实现。Triple 同时支持 Protobuf 和 Hessian 等多种序列化，gRPC 只能用 Protobuf。Triple 还兼容 Dubbo 2.x 的传统调用方式，可以逐步迁移。

从服务治理来看这是最大的差异。gRPC 本身只是一个通信框架，注册发现、负载均衡、熔断限流这些需要额外组件支撑，或者靠 Service Mesh 的 Sidecar 来做。Dubbo Triple 背靠 Dubbo 完整的服务治理生态，注册中心、配置中心、路由规则、流量控制、监控大盘全都有。如果只是需要跨语言 RPC 通信，gRPC 足够。如果需要完整的服务治理体系，Dubbo Triple 更有优势。

从生态来看，gRPC 是 CNCF 的项目云原生标准之一，和 Kubernetes、Istio、Envoy 有很好的整合。Dubbo Triple 更偏 Java 生态，虽然兼容 gRPC 但在云原生社区的影响力不如 gRPC 原生。

> **Q28** 一个接口用 HTTP RESTful ID 足够清晰，为什么要加一层 RPC？

这个问题的前提是已经有一个设计良好的 RESTful 接口，那 RPC 的价值体现在哪。

首先性能考虑。RESTful 用 JSON 序列化，文本格式体积大解析慢，HTTP 协议头部开销不小。内部微服务之间的调用频率远高于外部 API，一点点性能差距在高频调用下会放大很多。RPC 的二进制协议和序列化在这种场景下优势明显。

其次是治理能力。RESTful 接口的治理依赖网关和外部组件，注册发现、负载均衡、熔断都在网关层或者 Sidecar 层做，增加了调用链路。RPC 框架把治理能力内置在 SDK 里，调用链路短，响应速度快。

第三是接口契约的管理。RESTful 接口设计比较自由，靠文档和约定约束，没有编译期的检查。RPC 的接口通过 IDL 和接口定义强制契约，编译期就能发现接口不匹配的问题。

第四是调用模式的丰富度。RESTful 是一问一答的请求响应模型，RPC 支持异步调用、流式调用、回调，适合更丰富的交互模式。

但 RESTful 也有其不可替代的场景，对外暴露 API、多语言前端调用、需要利用 HTTP 缓存和 CDN 的场景。所以也不是说所有的 RESTful 都要改成 RPC，而是区分内部调用和外部调用，内部高频率的用 RPC，外部通用性强的保留 RESTful。

## 十二、综合场景

> **Q29** Dubbo Provider 突然挂了，Consumer 多久能感知到？怎么加快？

感知时间取决于多个环节的延迟叠加。

第一个环节是注册中心感知 Provider 下线。如果是优雅关闭，Provider 主动从注册中心摘除自己，注册中心立刻通知 Consumer，Consumer 收到通知后从本地列表中移除，这个过程一到两秒。如果是宕机，ZooKeeper 需要等待会话超时才能感知到节点消失，默认会话超时四十秒，如果没调过可能要三十秒到一分钟才能发现。

第二个环节是 Consumer 收到通知后的更新。Consumer 通过 ZK 的 Watcher 收到变更通知，更新本地缓存列表，这个过程很快，一两百毫秒。

第三个环节是已经发出去正在处理的请求。Consumer 在感知到 Provider 下线前可能已经把请求发出去了，这个请求会超时等待默认一秒，这段时间内客户端的调用会失败。

整体下来优雅关闭秒级感知，宕机场景可能三十秒到一分钟。

加快的方法有几个。一是调小 ZK 会话超时时间和心跳间隔，但不要太激进，否则网络抖动会导致误判。二是启用 Dubbo 的应用级服务发现，减少注册数据的变更延迟。三是 Consumer 端开启健康检查，Consumer 主动定期对 Provider 做心跳探测，发现连不通就提前剔除。四是结合容器编排平台的探活机制，K8s 的 Readiness Probe 检测到 Pod 不健康后通过钩子触发 Dubbo 下线。五是 Consumer 端配置更短的连接超时，尽快发现连接问题不再等待。

> **Q30** Dubbo Consumer 调 Provider 超时，到底是因为什么？怎么定位是哪个原因？

超时的原因要从调用链路的每个环节逐一排查。

第一是 Provider 端业务处理确实慢。可能是业务逻辑本身耗时比如复杂 SQL 查询、循环计算。可能调了下游的第三方接口对方响应慢。可能是数据库连接池耗尽排队等连接。可能是发生了 Full GC 业务线程暂停。

第二是网络问题。可能是 Consumer 和 Provider 之间的网络延迟高或者丢包。可能是跨机房的网络抖动。可能是带宽被打满。

第三是 Consumer 端的问题。超时时间设置太短，Provider 正常处理但 Consumer 等不及就超时了。Consumer 线程池满了，发送请求排队时间长。

第四是序列化问题。请求或响应数据太大，序列化反序列化耗时过长。大数据包在网络上传输也慢。

定位的方法是从外到内。先看 Dubbo 监控大盘或者日志，确认是哪个接口、哪个 Provider 超时。然后用 Arthas 或者 Provider 端的日志看请求是否到达了 Provider，如果到了看耗时多少。如果请求没到说明是网络或者注册中心的问题。如果到了但是耗时高，在 Provider 端用 Trace 工具看耗时分布，定位是业务逻辑、数据库的慢 SQL、还是第三方接口的慢响应。如果耗时正常但 Consumer 仍然超时，检查 Consumer 端的超时配置是否合理，看网络延迟是否异常。最后用 jstack 抓线程栈，看 Provider 的 Dubbo 业务线程是否在等待某个资源。

> **Q31** 设计一个 RPC 框架，需要考虑哪些方面？

设计一个 RPC 框架需要考虑的方面很多，可以从调用链路的各个关键环节来梳理。

第一是代理层。框架需要对业务代码透明，通过动态代理把本地方法调用转换为远程调用，用户只用接口不用感知网络通信。

第二是序列化层。需要支持可扩展的序列化方式，默认提供高效二进制序列化，也支持 JSON 方便调试。序列化要处理好版本兼容、循环引用、性能这些方面。

第三是协议层。需要设计一个高效的应用层协议，定义好请求和响应的报文格式，包括魔数、版本号、消息类型、序列化方式、请求 ID、数据长度、负载数据这些字段。协议要足够简洁，头部尽量小，同时有扩展空间。

第四是网络传输层。底层用 Netty 实现高性能 NIO 通信，支持长连接复用、心跳保活、连接池管理。服务端要有 IO 线程和业务线程的分离，避免慢业务阻塞 IO。

第五是注册中心。服务提供者启动时注册自己，消费者启动时发现服务列表。注册中心要支持多种实现，ZooKeeper、Nacos、Etcd 都可以接入，做可插拔设计。

第六是集群层。在 Consumer 端封装集群调用逻辑，包括负载均衡、路由策略、容错策略，失败重试、快速失败、降级处理都需要在这一层实现。

第七是服务治理层。需要支持流量控制、熔断降级、灰度路由、权重调整、超时控制、并发控制等能力，能通过管理控制台动态下发规则。

第八是监控层。调用链追踪、指标上报、慢请求告警，方便排查问题和容量规划。

第九是扩展点设计。框架核心流程需要有足够的 SPI 扩展点，负载均衡、路由、协议、序列化、注册中心等都做成可插拔的。

第十是易用性。和 Spring 生态无缝集成，注解驱动开发，最少化配置，开箱即用。
