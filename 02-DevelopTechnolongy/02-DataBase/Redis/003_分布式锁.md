|知识点|笔记时重点写什么|
|---|---|
|**SETNX 实现分布式锁**|热 基础实现：`SET lock_key unique_value NX PX 30000`（SET 的 NX + PX 参数是原子操作，2.6.12+ 支持）。**三个必须解决的问题**：①死锁（设 TTL）②锁被其他线程释放（value 用唯一标识，释放前用 Lua 脚本原子检查 value 是否匹配）③锁超时但任务未完成（锁续期，看门狗机制）|
|**Redlock 红锁算法**|热 单机 Redis 锁不可靠（主从切换时主节点宕机导致锁丢失）。Redlock：向 N（通常 5）个独立 Redis 节点申请锁，超过半数（≥ N/2+1）成功才认为加锁成功。**争议**：Martin Kleppmann 批评 Redlock 不可靠（时钟漂移问题），Antirez 反驳。面试时两边观点都要能说|
|**Redisson 看门狗机制**|核 Redisson 的分布式锁实现（Java 客户端）。加锁成功默认 TTL=30s，看门狗后台线程每 10s 检查锁是否还持有，若是则续期到 30s。**自动续期避免了"任务没做完锁过期"的问题**。这是 Redisson 比手写 SETNX 强大的核心原因|
|**锁的可重入性**|Redisson 的 `RLock` 支持可重入（内部维护重入计数器）。实现原理：Hash 结构存储 `key=threadID, value=重入次数`。**手写实现也需要考虑这个**，否则同一线程二次加锁会死锁|
|**锁的公平性与等待队列**|Redisson 的 `RedissonFairLock` 基于 Redis 的 List 实现等待队列（FIFO）。**普通分布式锁是无序竞争的，公平锁保证先到先得**，但性能略差|
|**Redlock 的 Java 实现**|推荐使用 Redisson 的 `RedissonRedLock`（封装了向多个节点申请锁的逻辑）。**注意**：Redlock 依赖系统时钟，如果节点时钟发生跳跃会导致锁失效——这是一个已知的理论缺陷|
