|知识点|笔记时重点写什么|
|---|---|
|**EXPLAIN 执行计划详解**|热 **必须每个字段都懂**。id（执行顺序，相同从上往下，不同值大的先执行）、select_type（SIMPLE / PRIMARY / SUBQUERY / DERIVED）、table、partitions、type（访问类型：**ALL < index < range < ref < eq_ref < const < system**，这个顺序要背下来）、possible_keys/key/key_len/rows/filtered/Extra。**key_len 的计算方法要能手算**（int=4, bigint=8, varchar(n)=n*3+2, 允许NULL再+1）|
|**慢 SQL 排查与优化方法论**|热 开启慢查询日志（`slow_query_log=ON`, `long_query_time=1`）→ 用 mysqldumpslow 分析 → EXPLAIN 看执行计划 → 找到瓶颈点（type=ALL? rows太大? Extra 出现 Using filesort?）→ 优化（加索引/改SQL/重构）。**写成固定排查步骤模板**|
|**Using filesort 与 Using temporary**|热 **两个最危险的 Extra 值**。filesort（ORDER BY 无法利用索引排序，需要在内存/磁盘中额外排序）：解决方法是建联合索引覆盖 ORDER BY 字段。temporary（GROUP BY 或 DISTINCT 需要创建临时表）：解决方法是优化 GROUP BY 使其走索引或减少分组维度|
|**COUNT(*) vs COUNT(1) vs COUNT(列)**|InnoDB 中三者几乎无性能差异（都会遍历整棵索引树）。`COUNT(列)` 如果列允许 NULL 则不计入 NULL 行。**真正的问题是**：`SELECT COUNT(*) FROM 大表` 本身就很慢（InnoDB 不能像 MyISAM 那样直接读元数据），解决方案：Redis 缓存 / 维护计数表 / 用估算值|
|**分页深分页优化**|热 `LIMIT 1000000, 10` 的性能灾难（MySQL 需要扫描前 100 万行再抛弃）。优化方案：①延迟关联（先 `SELECT id LIMIT 1000000,10` 再 `JOIN` 回原表）②游标/书签记录（记住上一页最后一条的 id，`WHERE id > last_id LIMIT 10`）③ES 替代（超深分页场景）|
|**JOIN 优化**|小表驱动大表原则（Nested Loop Join 的驱动表选择）。被驱动表的关联字段要有索引。LEFT JOIN 右表条件写在 ON 还是 WHERE 的结果不同（ON 过滤在连接前，WHERE 过滤在连接后）。STRAIGHT_JOIN 强制指定驱动表|
|**SQL 书写规范（阿里手册）**|热 禁止 `SELECT *`（浪费内存和网络带宽）、WHERE 条件中禁止函数计算（导致索引失效）、超过 3 张表考虑反范式、IN 列表不超过 500 个、批量 INSERT 每次 ≤ 500 行、TRUNCATE 代替 DELETE 清空表。**这些规范本身就是面试加分项**——说明你有工程素养|
