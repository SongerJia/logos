|知识点|笔记时重点写什么|
|---|---|
|**B+ 树结构与原理**|热 **必须能手画**。非叶子节点只存键值（不存数据），叶子节点存全部数据（或主键），叶子之间用双向链表连接。为什么用 B+ 不用 B 树？（查询稳定 O(log n)、范围查询好、磁盘 IO 少因为更矮胖）。3 层 B+ 树能存多少条数据？（16KB 页 × 非叶子节点每行 ~1KB → 约 1170 子节点 → 叶子层 1170×1170 ≈ 137 万条。3 层 ≈ 2000 万条！**这个数字要背下来**）|
|**聚簇索引 vs 非聚簇索引（二级索引）**|热 **最高频概念题之一**。InnoDB 的聚簇索引就是主键索引（叶子节点存完整行数据）；二级索引的叶子节点存的是**主键值**（不是行地址！）。所以二级索引查数据需要"回表"。画一张图：二级索引 B+树找到主键 → 回到聚簇索引找整行数据|
|**回表优化：覆盖索引**|热 如果 SELECT 的字段全部包含在索引中（如 `SELECT id, name FROM user WHERE name='xx'`，且 (name) 是索引），则无需回表。这就是覆盖索引。`EXPLAIN` 中 Extra 列会显示 `Using index`。**工程上最常见的优化手段之一**|
|**联合索引与最左前缀原则**|热 **必背规则**。建立联合索引 `(a, b, c)`，则 `WHERE a=1` ✅、`WHERE a=1 AND b=2` ✅、`WHERE b=2` ❌、`WHERE a=1 AND c=3` ✅（a 用了，c 跳过了 b 但 a 还是用到了）。**给每种组合一个例子**，特别是跳过中间列的情况|
|**索引下推 ICP（Index Condition Pushdown）**|热 MySQL 5.6 引入的优化。在索引遍历过程中，对索引中包含的字段先做 WHERE 条件判断，过滤掉不符合条件的记录，减少回表次数。`EXPLAIN` 的 Extra 显示 `Using index condition`。典型场景：联合索引 `(name, age)`，`WHERE name LIKE '张%' AND age > 18` — 在遍历 name 索引时就过滤掉 age<=18 的|
|**索引失效的 N 种场景**|热 **必背清单**：①对索引列使用函数 `YEAR(create_time)=2024` ❌ ②隐式类型转换（字符串字段传数字）❌ ③`LIKE '%xx'` 左模糊 ❌ ④`OR` 连接的条件中有未索引列 ❌ ⑤`<>` / `NOT IN` / `NOT EXISTS` 可能不走索引 ⑥优化器评估全表扫描更快时主动放弃索引。**每个失效场景配一条正确写法**|
|**前缀索引与索引选择性**|字符串过长时取前 N 个字符建索引（如 `INDEX idx_name(name(10))`）。**选择性 = distinct count / total rows**，越接近 1 越好。前缀索引不能用于覆盖索引（无法做 ORDER BY / GROUP BY）、不能用于 JOIN ON 条件。什么时候该用？长文本字段（URL / 邮箱 / 身份证）|
|**Hash 索引 vs B+Tree 索引**|InnoDB 自适应 Hash Index（自动维护，不可手动干预）：等值查询 O(1)，但不支持范围查询、不支持排序、不支持最左前缀。Memory 引擎才显式支持 Hash 索引。**对比表**是标准考法|
|**唯一索引与普通索引的查询差异**|核 唯一索引查到一条就返回；普通索引可能查到匹配值后继续向右遍历（因为可能有重复值）。**插入时的差异更大**：唯一索引需要判断是否冲突，涉及"change buffer"和磁盘读取的权衡——普通索引可以利用 change buffer 延迟写入，唯一索引不行（必须读盘判断唯一性）|
|**索引设计原则**|选择性高的列优先放联合索引前面、区分度低的列不放索引（如性别）、小表不建索引（全表更快）、单表索引不超过 5~6 个、避免冗余索引（`(a)` 和 `(a,b)` 中 `(a)` 冗余了）。**做成检查清单形式**|
