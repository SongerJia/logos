|#|知识点|笔记三层写法建议|关联|
|---|---|---|---|
|4.1|**SQL 解析过程（ANTLR）**|是什么：SQL → AST（抽象语法树）的过程，5.x用的是自研解析器；为什么：只有先解析才能知道这条SQL涉及哪些表哪些字段；面试：「ShardingSphere怎么解析SQL的？」|编译原理/AST|
|4.2|**SQL 路由引擎（单路由/混合路由/广播路由）**|是什么：根据解析结果决定SQL发往哪些数据节点的三种路由类型；为什么：路由决定了性能——能单路由就不广播；面试：「什么情况下会触发全路由（全表扫描）？」|3.2 Standard分片策略|
|4.3|**SQL 改写（将逻辑表名改写为真实表名）**|是什么：`SELECT * FROM t_order WHERE id = 1` → `SELECT * FROM ds0.t_order_0 WHERE id = 1`；为什么：应用层写的是逻辑表名，底层要操作真实物理表；面试：「分页查询的SQL改写是什么样的？」|4.5 分页改写|
|4.4|**分页查询的特殊处理**|是什么：全量获取各分片结果后在内存归并排序再截取——**性能陷阱**；为什么：`LIMIT 1000000, 10` 在分库分表环境下是灾难级的；面试：「深度分页怎么优化？」|MySQL 深度分页优化|
|4.5|**ORDER BY 的归并（内存排序）**|是什么：各分片各自排序后 Pull 到应用层做归并排序（PriorityQueue）；为什么：各分片只能保证局部有序，全局有序需要归并；面试：「分库分表后ORDER BY是怎么实现的？大数据量会有什么问题？」|归并排序算法|
|4.6|**GROUP BY / COUNT / SUM 等聚合归并**|是什么：聚合操作的流式归并与内存归并两种方式；为什么：COUNT(*) 需要把各分片的计数相加，AVG 需要先SUM再COUNT再除；面试：「分库分表后 GROUP BY 还准吗？」|MapReduce 思想|
|4.7|**不支持的操作（限制）**|是什么：不支持跨分片的子查询/跨实例JOIN/不携带分片键的复杂查询/部分窗口函数；为什么：理论上有些操作在分布式场景下代价太大；面试：「分库分表后有哪些SQL不能直接用？怎么规避？」|1.6 痛点全景|
