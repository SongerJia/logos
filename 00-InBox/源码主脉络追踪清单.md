# 源码主脉络追踪清单（Spring + mall）

> 用途：面对一个几十万行的仓库，不再"通读式瘫痪"，而是**按五条主动脉逐条 trace**。
> 核心纪律：**一条脉络只追主干，忽略 80% 分支；一条追完用一张时序图固化，再追下一条。**
> 适用：Spring Framework（地基）、mall（业务系统样板）。RocketMQ / Dubbo 后续可直接套同一套五线法。

---

## 0. 五条主脉络总览（任意系统通用）

| # | 主脉络 | 一句话 | 自问 |
|---|---|---|---|
| 1 | **启动脉络** | 它怎么"起来" | 配置怎么加载？组件怎么注册？上下文怎么初始化？ |
| 2 | **核心调用脉络** | 最关键的一条端到端链路 | 调用方最常触发的是什么？一次请求怎么走完？ |
| 3 | **核心数据/存储脉络** | 状态存在哪 | 中央状态容器是哪个 Map / 文件？ |
| 4 | **生命周期/状态机脉络** | 对象怎么生老病死 | Bean/连接/消息从创建到销毁经过哪些阶段？ |
| 5 | **扩展点脉络** | 它怎么留口子给别人改 | SPI/插件/钩子在哪？ |

> 前 3 条撑起 70% 全貌，优先追。后 2 条是"高手"和"会用"的分水岭。

## Part 1 · Spring Framework 五条主脉络

### 1.1 启动脉络：`refresh()` 是总开关

入口：`AbstractApplicationContext.refresh()`。Spring 容器启动 = 这一方法的 12 个 `xxx()` 步骤。**只追最关键的 5 步**，其余先跳过。

```
AbstractApplicationContext.refresh()
├─ obtainFreshBeanFactory()        ← ① 拿到 BeanFactory，解析 XML/注解成 BeanDefinition
├─ invokeBeanFactoryPostProcessors() ← ② 执行 BFPP，ConfigurationClassPostProcessor 在这里扫描 @Component
├─ registerBeanPostProcessors()   ← ③ 把 BPP 注册进容器（注意：此时 BPP 自己还没实例化完）
├─ finishBeanFactoryInitialization() ← ④ 实例化所有非懒加载单例（preInstantiateSingletons）
└─ finishRefresh()                ← ⑤ 发布 ContextRefreshedEvent，容器就绪
```

**追踪顺序（照着点断点）**：
1. `new AnnotationConfigApplicationContext(AppConfig.class)` → 进 `refresh()`。
2. 在 `obtainFreshBeanFactory` 打断电，看 `DefaultListableBeanFactory` 里 `beanDefinitionMap` 何时被填满。
3. 在 `finishBeanFactoryInitialization` → `preInstantiateSingletons()` 打断电，看单例如何被逐个 `getBean`。

**真实踩坑**：
- `BeanFactoryPostProcessor` 和 `BeanPostProcessor` 执行时序不同（② 先于 ③）。在 BFPP 里 `@Autowired` 另一个 BFPP 会失败——因为 BPP 还没注册。这是"循环依赖 + 处理器"的经典坑。
- `finishBeanFactoryInitialization` 是单例爆炸点：项目启动时卡死/内存飙升，90% 是这里实例化了某个重 Bean（如连接池、大缓存）。

### 1.2 核心调用脉络：`getBean()` 是心脏

用户最常触发的是 `context.getBean("userService")`。追这一条就够。

```
getBean(name)
  → doGetBean(name)
    → getSingleton(name)            ← 先查一级缓存 singletonObjects
      → 命中则直接返回
    → 未命中 → markBeanAsInCreation  ← 标记"正在创建"（解决循环依赖的关键）
    → getSingleton(()->createBean)  ← 三级缓存之"工厂"
      → createBean(beanName)
        → doCreateBean
          → createBeanInstance()    ← 反射 newInstance / 构造器
          → populateBean()          ← ① 属性填充（@Autowired 在这里注入）
          → initializeBean()        ← ② 生命周期回调（见 1.4）
```

**ASCII 时序（精华版）**：

```
调用方 ──getBean("userService")──→ ApplicationContext
                                      │
                                      ▼
                              doGetBean
                                      │
                  ┌───────────────────┼───────────────────┐
                  ▼                   ▼                   ▼
           ① 查一级缓存       ② 查二级(早期引用)    ③ 查三级(对象工厂)
           singletonObjects  earlySingletonObjects  singletonFactories
                  │                   │                   │
                  └──── 都未命中 ───────┴──────→ createBean（反射实例化）
                                                  │
                                                  ▼
                                          populateBean(@Autowired)
                                                  │
                                                  ▼
                                       initializeBean(Aware/BPP/@PostConstruct)
                                                  │
                                                  ▼
                                          放入一级缓存，返回
```

**真实踩坑（循环依赖）**：A 依赖 B，B 依赖 A。
- Spring 用**三级缓存**解决：实例化 A 后，先把"未初始化的早期引用"放进三级缓存（`singletonFactories`），B 创建时从三级缓存拿到 A 的早期引用，B 初始化完，A 再填充 B。
- **构造器注入无法解决循环依赖**：因为实例化阶段就卡住，还没机会进三级缓存 → `BeanCurrentlyInCreationException`。这是面试高频点。

### 1.3 数据存储脉络：三大 Map 是 Spring 的"数据库"

```
DefaultListableBeanFactory
├─ beanDefinitionMap: Map<String, BeanDefinition>   ← ① 配置元数据（类名、scope、注入点）
├─ singletonObjects: Map<String, Object>            ← ② 成品单例（一级缓存，对外暴露）
└─ (在 DefaultSingletonBeanRegistry 中)
   ├─ earlySingletonObjects: Map<String,Object>     ← ③ 早期引用（二级缓存）
   ├─ singletonFactories: Map<String,ObjectFactory> ← ④ 对象工厂（三级缓存，破解循环依赖）
   └─ singletonsCurrentlyInCreation: Set<String>    ← ⑤ 正在创建的集合（防重入）
```

**记忆口诀**：`Definition` 存"图纸"，`singletonObjects` 存"成品"，三级缓存存"半成品"。

**真实踩坑**：
- `singletonObjects` 是 **ConcurrentHashMap**，但 `beanDefinitionMap` 在启动早期是普通 HashMap（此时单线程，无并发问题），启动后才加锁保护。看源码时别被"为什么这里没用线程安全容器"迷惑。
- 三级缓存不是"性能优化"，是"为了能让 AOP 代理 + 循环依赖共存"的妥协设计（早期引用可能是代理对象）。

### 1.4 生命周期脉络：Bean 的"生老病死"

```
实例化(Instantiation)
  → 属性填充(populateBean, @Autowired)
  →  Aware 回调(setBeanName / setBeanFactory / setApplicationContext)
  →  BeanPostProcessor.postProcessBeforeInitialization
  →  @PostConstruct / InitializingBean.afterPropertiesSet
  →  BeanPostProcessor.postProcessAfterInitialization  ← AOP 代理在这里织入
  →  【使用中】
  →  @PreDestroy / DisposableBean.destroy
```

**伪代码（你 mini-Spring 第 3~4 周就要手写这段）**：

```java
Object bean = createBeanInstance(beanClass);          // 反射 new
populateBean(bean, beanDefinition);                    // 注入依赖
invokeAware(bean);                                      // setXxxAware
for (BeanPostProcessor bpp : bpps)
    bean = bpp.postProcessBeforeInitialization(bean);  // 前置
invokeInitMethods(bean);                               // @PostConstruct
for (BeanPostProcessor bpp : bpps)
    bean = bpp.postProcessAfterInitialization(bean);   // 后置（AOP 在此返回代理）
singletonObjects.put(name, bean);                      // 入库
```

**真实踩坑**：
- `@PostConstruct` 在 `InitializingBean.afterPropertiesSet` **之前**执行（先注解后接口）。
- AOP 代理对象：经过 `postProcessAfterInitialization` 后，`singletonObjects` 里存的是**代理**不是原对象。你 debug 时看到 `userService` 变成 `$Proxy` 别慌，这是正常代理织入。

### 1.5 扩展点脉络：Spring 为什么"万能"

| 扩展点 | 作用 | 在哪生效 |
|---|---|---|
| `BeanFactoryPostProcessor` | 改 BeanDefinition（容器级） | refresh ② |
| `BeanPostProcessor` | 改 Bean 实例（对象级） | 1.4 前后置 |
| `@Import` + `ImportSelector` | 批量注册 Bean | 扫描阶段 |
| `FactoryBean` | 自定义复杂对象创建 | getBean 时调 getObject |
| `ApplicationListener` | 监听容器事件 | finishRefresh |

**记忆**：BFPP 动"图纸"，BPP 动"成品"，`FactoryBean` 动"创建方式"。

## Part 2 · mall 业务系统五条主脉络（对照样板）

mall 是标准 Spring Boot 电商，五线法和 Spring 同源，只是"业务语义"更重。

### 2.1 启动脉络
无特殊（Spring Boot 标准 `SpringApplication.run(MallAdminApplication.class)`）。重点在自动装配（`@EnableAutoConfiguration` → `spring.factories` → 加载 MyBatis/Redis/RabbitMQ 等 starter）。

### 2.2 核心调用脉络：下单链路（最能体现业务骨架）

```
CartController.add()                 ← 加购
  → OrderController.generateConfirmOrder()  ← 确认订单（算价/优惠/运费）
  → OrderService.createOrder()       ← 核心
     ├─ 生成订单号（雪花算法）
     ├─ 写 oms_order + oms_order_item
     ├─ 扣 pms_sku_stock（库存）
     ├─ 清理购物车
     └─ 触发支付（生成支付记录 / 调支付网关）
  → OmsPortalOrderManager（订单状态机驱动）
```

**ASCII 时序（下单主干）**：

```
[用户] ──addCart──→ [CartController]
                      │
[用户] ──confirm────→ [OrderController] ──generateConfirmOrder──→ 算价/优惠/运费
                      │
[用户] ──submit─────→ [OrderService.createOrder]
                      ├─→ 写 oms_order / oms_order_item
                      ├─→ 扣 pms_sku_stock（库存 -1，带乐观锁 version）
                      ├─→ 清购物车条目
                      └─→ 生成支付单 / 发起支付
                      │
                      ▼
                [订单状态机] 待支付 → 已支付 → 已发货 → 完成
```

### 2.3 数据存储脉络：核心表

```
oms_order           订单主表（status 状态字段是状态机载体）
oms_order_item      订单明细（SKU、数量、单价、优惠分摊）
pms_sku_stock       库存表（stock、lock_stock、版本号 version 防超卖）
oms_cart_item       购物车
pms_product/pms_sku 商品与 SKU（SPU/SKU 一对多）
ums_member          会员
```

**真实踩坑（超卖）**：扣库存必须用 **乐观锁** `update pms_sku_stock set stock=stock-1 where id=? and stock>=1`，否则高并发下会卖负。`lock_stock`（锁定库存）用于"已下单未支付"占位，支付超时释放。

### 2.4 生命周期脉络：订单状态机

```
[待支付] ──支付成功──→ [已支付/待发货]
   │                      │
   │ 取消/超时未支付        │ 发货
   ▼                      ▼
[已取消]              [已发货/待收货] ──确认收货──→ [已完成]
                           │
                     申请退款 ──→ [退款中] ──→ [已退款]
```

（完整版见路线图模块 B 订单状态机）

### 2.5 扩展点脉络
- Spring Event：`ApplicationEventPublisher` 发布订单创建事件（解耦积分/通知）。
- MyBatis 拦截器：分页、逻辑删除、审计字段自动填充。
- AOP：接口鉴权、操作日志、幂等防重（订单重复提交）。

## Part 3 · 通用追踪纪律（照做不跑偏）

1. **先看模块图/架构图**，一级模块就是脉络起点。
2. **找"名词最大"的类**：`XxxContext` / `XxxManager` / `XxxEngine` / `XxxFactory` / `Bootstrap` —— 脉络枢纽。
3. **找入口**：`main()` / `@SpringBootApplication` / `XxxStarter`。
4. **用 arthas 偷懒**：`trace com.xxx.Service.method` 直接吐调用链，比肉眼强十倍。
5. **三个自检问题定位主脉络**：① 这系统不跑这个就废了的是什么？② 用户最常触发什么？③ 状态容器在哪？
6. **一条追完 → 一张时序图 → 再追下一条**，禁止并行追（会乱成毛线）。
7. **每条追完 → 写对应 mini 切片**：Spring 的 getBean 链路 = 你 mini-Spring 第 3 天 80 行骨架；mall 的下单链路 = 你写业务系统时必画的时序图。

## Part 4 · 真实踩坑汇总（源码阅读专属）

| 坑 | 现象 | 根因 | 对策 |
|---|---|---|---|
| 通读式瘫痪 | 打开仓库不知道从哪看 | 企图"先全懂再动手" | 从跑起来 + 追一条链开始 |
| 追分支陷进去 | 一小时卡在一个 try-catch | 没忽略 80% 分支 | 主干优先，分支标 TODO 后看 |
| 三级缓存看不懂 | 循环依赖为什么需要三级 | 不理解 AOP+循环依赖共存 | 先看 1.2 三级缓存图 |
| 代理对象困惑 | debug 看到 `$Proxy` | AOP 在 BPP 后置织入 | 知道这是正常代理即可 |
| 启动卡死 | 项目启动慢/内存爆 | 重 Bean 在 finishBeanFactoryInitialization 实例化 | 排查懒加载/重依赖 |
| 库存卖负 | 下单并发超卖 | 扣库存无乐观锁 | version 乐观锁 + lock_stock |

## 举一反三 · 这套五线法怎么平移

- **RocketMQ**：启动(BrokerStartup) → 核心调用(producer.send→commitlog→consumequeue→consumer.pull) → 存储(commitlog 物理文件 + consumequeue 索引) → 生命周期(半消息→提交→消费→ack) → 扩展(MessageHook/Filter)。
- **Dubbo**：启动(ServiceConfig.export) → 核心调用(Invoker 动态代理→Codec→网络) → 存储(注册中心 URL 树) → 生命周期(暴露→注册→发现→调用→下线) → 扩展(Filter/LoadBalance SPI)。
- **迁移到业务建模**：把"核心调用脉络"换成"用户旅程"，把"数据存储脉络"换成"领域模型 ER"，把"生命周期脉络"换成"状态机"——和路线图模块 B 的三张图法完全同构。**技术源码和业务建模，底层都是"追主干五线法"。**

小张一句到位：**源码不是书，是顺着主动脉从入口类追到状态容器——启动、核心调用、数据存储、生命周期、扩展点五条线，先追通一条，剩下全是变体；通读才是真浪费时间。**
