|**5.4.1**|**SQL 执行分析**|EXPLAIN 分析执行计划(type/all/ref/range/index) → Extra列(Using filesort/Using temporary/Using index condition) → Slow Query Log 定位慢SQL|关键指标：Rows Examined(扫描行数) vs Rows Returned(返回行数)；比值>100:1需优化|"EXPLAIN的type字段各等级的含义？all和index区别？"|MyBatis-Plus内置SQL分析插件 + Druid SQL监控面板|
|**5.4.2**|**索引优化原则**|最左前缀匹配 → 覆盖索引避免回表 → 索引选择性高(基数大)的列放前面 → 避免索引失效(函数运算/隐式转换/LIKE '%xx')|联合索引(a,b,c) 的命中规则：(a)✅ (a,b)✅ (b,c)❌ (a,c)部分✅(只用a)|"什么情况下联合索引会完全失效？ORDER BY能用上索引吗？"|wf_task_instance: `UNIQUE KEY uk_inst_node (instance_id, node_key)` — 高频查询条件|
|**5.4.3**|**分库分表 ShardingSphere**|**垂直拆分**：按业务域拆库(auth库/wf库/scheduler库) → **水平拆分**：按分片键(ShardingKey)路由到不同表|ShardingSphere-JDBC(客户端代理，轻量) vs ShardingSphere-Proxy(服务端代理，透明)；分片算法：Hash取模 / Range范围 / 时间|"分片键怎么选？如果不带分片键的查询怎么做？"|**V1.0不需要水平分片**（数据量可控）；预留ShardingSphere接入能力，wf_task_history按月分表|
|**5.4.4**|**读写分离与连接池调优**|ProxySQL/HAProxy路由写请求到Master、读请求到Slave → 连接池(HikariCP/Druid)复用连接减少建连开销|HikariCP参数：minimumIdle / maximumPoolSize / connectionTimeout / idleTimeout / maxLifetime|"HikariCP为什么比Druid快？它的连接池管理策略有什么特点？"|**HikariCP** 作为默认连接池(maxPoolSize=10, minIdle=5) + ProxySQL读写分离|
|**5.4.5**|**MySQL 参数调优**|innodb_buffer_pool_size(建议物理内存60-70%) → innodb_log_file_size(1-2GB) → max_connections(按QPS*RT计算) → query_cache_size(MySQL 8已移除) → slow_query_log(开启!)|调优方法论：先观察Status/Variables → 改一个参数 → 观察效果 → 迭代；不要一次性改太多|"MySQL的buffer pool设置多大合适？innodb_flush_log_at_trx_commit三个值的区别？"|8G机器推荐配置：`buffer_pool_size=4G` / `log_file_size=512M` / `flush_log_at_trx_commit=1`(强一致)|
