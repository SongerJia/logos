## 一、数据结构 & 底层编码（必问基础）

### **Q1** Redis 的 5 种基本数据类型，每种至少说 2 个应用场景。String 除了缓存还能做什么？
?
1. 五种基本类型是 String、Hash、List、Set、ZSet。
2. String 是最基础的类型。除了做缓存，还有四个高频场景：第一，分布式锁，SET key value NX EX 30，一个命令完成加锁加过期；第二，计数器，INCR 原子递增做文章阅读数、限流计数器；第三，分布式 ID 生成器，INCR 自增序列号；第四，存储 JSON 序列化后的对象，比如用户信息。
3. Hash 适合存对象属性，比如用户信息把字段分开存，可以单个字段更新不覆盖全局；还适合做购物车，用 field 存商品 ID，value 存数量。
4. List 适合做消息队列，LPUSH 入队 RPOP 出队；也适合做最新列表，比如朋友圈前 N 条动态，LTRIM 控制长度。
5. Set 适合做标签系统，SADD 加标签，SINTER 计算共同好友的共同标签；还适合做抽奖，SRANDMEMBER 随机抽取。
6. ZSet 适合做排行榜，用分数做排序字段；也适合做延时队列，用时间戳做分数，ZRANGEBYSCORE 按时间范围取出到期任务。

### **Q2** `String` 的三种底层编码：`int`、`embstr`、`raw`，分别在什么条件下切换？`embstr` 为什么比 `raw` 省内存？
?
1. 三种编码的切换规则：当 value 可以用 long 类型表示的整数时，用 int 编码，直接存整数而不是字符串。当 value 是字符串且长度不超过 44 字节时，用 embstr 编码。当字符串长度超过 44 字节，自动切换为 raw 编码。注意 Redis 7 之前阈值是 39 字节，7 之后因为 listpack 替代了 ziplist，SDS 头部缩小，阈值变成了 44。
2. embstr 比 raw 省内存的核心原因是它只分配一次内存，RedisObject 和 SDS 在连续的内存块中，只需要一次 malloc。而 raw 需要两次分配，RedisObject 和 SDS 是分开的两块内存。分配次数的差异带来了三个好处：少了内存碎片、少了内存分配开销、释放时也只需要一次。
3. 还有一个注意点：embstr 是只读的，任何修改操作比如 APPEND，都会自动转换为 raw。int 也一样，一旦 APPEND 字符串，会转为 raw。

### **Q3** `Hash` 的两种底层编码：`listpack`（Redis 7）和 `hashtable`，什么时候从 `listpack` 升级为 `hashtable`？
?
1. Hash 默认使用 listpack 紧凑编码，当同时满足以下两个条件时触发升级为 hashtable：第一，Hash 中某个 field 的长度超过 64 字节；第二，Hash 中 field 数量超过 512 个。这两个阈值可以通过 hash-max-listpack-value 和 hash-max-listpack-entries 配置。
2. 为什么需要升级？listpack 本质是连续的紧凑数组，查询只能顺序扫描。当元素多了以后，查询复杂度变成 O(n)，而 hashtable 是 O(1)。所以这是一种空间换时间的策略：小数据量时用紧凑编码省内存，数据量大了切换为哈希表保证查询性能。
3. Redis 7 之前用的是 ziplist，7 开始统一换成了 listpack。listpack 相比 ziplist 的改进是每个 entry 记录了自身长度，解决了 ziplist 连锁更新的问题。

### **Q4** `ZSet` 的底层编码：`listpack`（Redis 7）+ `skiplist` + `hashtable`，为什么跳表 + 哈希表要一起用？各解决了什么问题？
?
1. ZSet 默认用 listpack 紧凑编码，当元素数超过 128 或元素大小超过 64 字节时，切换为 skiplist + hashtable 的组合结构。
2. 跳表和哈希表配合使用，是因为两者分工不同。跳表解决的是范围查询和排序问题：ZRANGE、ZRANK、ZRANGEBYSCORE 这些需要按分数顺序遍历的操作，跳表的多级索引可以做到 O(log n) 定位后再顺序遍历。哈希表解决的是按成员精确查找的问题：ZSCORE、ZREM 这些操作需要快速定位到某个 member 对应的节点，哈希表 O(1) 直接拿到。
3. 如果只用跳表不用哈希表，ZSCORE 操作就得在跳表里一层层找，虽然还是 O(log n)，但常数更大，因为层间跳跃有指针跳转开销。如果只用哈希表不用跳表，范围查询就没法高效了，只能全量排序。两者配合，各自发挥优势，并且它们指向的是同一个节点对象，不额外占用内存拷贝。

### **Q5** 跳表（SkipList）的查询、插入、删除时间复杂度？为什么 Redis 用跳表不用红黑树或 B+ 树？（至少说 2 个理由）
?
1. 查询、插入、删除的时间复杂度都是平均 O(log n)，最坏可能退化到 O(n)，但 Redis 通过随机层数来保证概率上的平衡，实际表现稳定。
2. Redis 用跳表而不用红黑树，主要有四个理由。第一，实现简单。红黑树的插入删除涉及复杂的旋转和变色逻辑，调试和维护成本高。跳表的插入只需要随机生成层数然后修改前后指针，代码少、不易出错。第二，跳表天然支持范围查询。红黑树做 ZRANGE 需要中序遍历，而跳表找到起点后顺着最底层的链表一路往前走就行，效率更高。第三，跳表对并发更友好。红黑树一次插入可能导致整棵树的旋转影响到很多节点，而跳表修改只影响局部的前后指针，做范围锁更简单。虽然 Redis 本身是单线程，但如果后续做持久化或增量同步时需要扫描，跳表的结构更合适。第四，跳表的层数随机化机制天然提供了近似平衡，不需要像红黑树那样维护复杂的平衡条件。
3. B+ 树不合适的原因是它是按页存储的磁盘数据结构，Redis 是纯内存操作，不需要按页读取，B+ 树的页分裂回收反而增加了不必要的复杂度。

### **Q6** 3 种特殊数据类型：Bitmap、HyperLogLog、GEO，各自做什么的？HyperLogLog 的误差率是多少？底层用了什么算法？
?
1. Bitmap 本质是 String 类型按位操作，每一位代表一个状态，占用极省内存。典型场景是用户签到统计，一年 365 天只需要 46 个字节。另一个场景是布隆过滤器的底层实现。
2. HyperLogLog 做基数统计，就是统计一个集合里有多少个不重复的元素，但不存储元素本身。比如统计一个页面的独立访客数 UV，不管你来多少次，只算一次。它的误差率是标准误差 0.81%，也就是一万个 UV 可能多算或少算 81 个左右。底层用的是伯努利试验的数学原理加调和平均数：通过统计元素哈希值的二进制表示中第一个 1 出现的位置，推断集合的基数。12KB 内存就能估算 2^64 个不同元素，省内存能力是惊人的。
3. GEO 做地理位置计算。底层使用 ZSet 存储，用 Geohash 算法把经纬度编码成一个整数作为 ZSet 的 score。支持添加位置、计算两点距离、查找附近的人等功能，本质上就是 ZSet 的范围查询。

## 二、过期 & 淘汰策略

### **Q7** Redis 的过期删除策略是什么？惰性删除 + 定期删除如何配合？定期删除的频率和每次扫描数量？
?
1. Redis 用的是惰性删除加定期删除的组合策略，而不是定时器到点就删。
2. 惰性删除的意思是，key 设置了过期时间，但不会到期自动触发删除。只有当客户端访问这个 key 时，Redis 才检查它是否过期，过期了就立刻删除并返回空。这解决了定时删除和客户端访问无关也要消耗 CPU 的问题。
3. 但惰性删除有个漏洞：如果一个 key 过期后永远没人访问，它就永远留在内存里，造成内存泄漏。所以需要定期删除来兜底。定期删除是 Redis 内部有一个定时任务，每秒执行十次，每次随机会从设置了过期时间的 key 中抽取 20 个，检查并删除其中过期的。如果某次抽取发现超过 25% 的 key 都过期了，就继续循环抽取，直到过期比例低于 25% 或者执行时间超过 25 毫秒为止。
4. 两者配合的逻辑是：大部分过期 key 被定期删除的随机抽样扫掉，极少数漏网的在下次被访问时被惰性删除清理掉，保证内存不会无限增长。

### **Q8** 8 种内存淘汰策略分别是什么？`allkeys-lru` 和 `volatile-lru` 的区别？LRU 和 LFU 的区别？Redis 的近似 LRU 和标准 LRU 有什么不同？
?
1. 八种策略分成三个大类。
2. 第一类是不淘汰：noeviction，内存满了直接拒绝写请求返回错误，只允许读和删除。
3. 第二类是在设置了过期时间的 key 里淘汰：volatile-lru 淘汰最久未使用的、volatile-lfu 淘汰使用频率最低的、volatile-random 随机淘汰、volatile-ttl 淘汰剩余存活时间最短的。
4. 第三类是在所有 key 里淘汰：allkeys-lru、allkeys-lfu、allkeys-random。
5. allkeys-lru 和 volatile-lru 的区别在于候选范围：allkeys 是从所有 key 中挑，volatile 只从设置了过期时间的 key 中挑。生产环境通常推荐 allkeys-lru，因为只淘汰有过期时间的 key 可能导致某些长期不用的没有过期的 key 一直占着内存。
6. LRU 和 LFU 的区别在于淘汰依据：LRU 看的是最近一次访问时间，谁最久没被用过就淘汰谁，只关心时间维度。LFU 看的是访问频率，谁用的次数最少就淘汰谁，更关心访问热度。LRU 的问题是一次突发访问就会把一个冷数据提到最前面，即使后面再也没人访问，要先淘汰完比它更久没被访问的数据。LFU 通过频率计数避免了这个问题，冷数据偶尔被访问一次仍然会被淘汰。
7. Redis 用的是近似 LRU，不是标准 LRU。标准 LRU 需要维护一个双向链表，每次访问都要移动节点到链表头部，内存和 CPU 开销都很大。Redis 的近似 LRU 实现非常轻量：每个 key 的 RedisObject 里记录一个 24 位的访问时间戳，淘汰时随机采样 N 个 key，取其中时间戳最小的淘汰。allkeys-lru 默认采样 5 个，这个数字可以通过 maxmemory-samples 调整，加到 10 效果就非常接近标准 LRU 了。

### **Q9** 一个 key 设置了 TTL 但从未被访问，过期后一定会立刻删除吗？如果没有设置淘汰策略，内存满了怎么办？
?
1. 不会立刻删除。前面说过，Redis 用的是惰性删除加定期删除，过期不等于删除。如果 key 过期后从未被访问，可能要靠定期删除的随机抽样扫到它才被清理，有概率延迟。
2. 如果内存满了且没有设置淘汰策略，默认是 noeviction，所有写操作都会被拒绝。DEL 和读操作还可以正常执行，但 SET、LPUSH 这些写操作会返回 OOM 错误。生产环境一定要配置 maxmemory 和淘汰策略，不然 Redis 内存超过物理内存会导致系统 swap，性能急剧下降甚至被 OOM Killer 杀掉。

## 三、缓存经典三兄弟（穿透/击穿/雪崩）

### **Q10** 缓存穿透：描述场景、原因、至少 3 种解决方案。布隆过滤器（Bloom Filter）的原理是什么？为什么能判断"一定不存在"，但只能说"可能存在"？
?
1. 缓存穿透是指查询一个不存在的数据，缓存里没有，数据库里也没有。每次请求都直接穿过缓存打到数据库，大量恶意请求甚至可以打垮数据库。
2. 原因通常是查询不存在的 ID 或者恶意攻击构造的非法 key。
3. 解决方案有三种。第一，布隆过滤器：预先把所有合法的 key 存入布隆过滤器，请求来了先过布隆过滤器，如果判断不存在就直接拦截返回空，不用查缓存也不用查数据库。第二，缓存空值：如果查数据库发现不存在，也往缓存里写一个空值，设置较短的过期时间，比如 60 秒。下次同样 key 的请求就能被缓存挡住。但要注意空值缓存可能引起缓存中大量无效 key，需要控制过期时间和数量。第三，接口层做参数校验：在网关或 Controller 层对请求参数做合法性校验，比如 ID 必须大于 0，不符合的直接拒绝。
4. 布隆过滤器的原理：它底层是一个很长的二进制位数组加多个哈希函数。添加元素时，用多个哈希函数算出多个位置，把这些位置都置为 1。查询元素时，同样用这些哈希函数算出位置，如果所有位置都是 1，说明可能存在；如果有一个位置是 0，说明一定不存在。
5. 为什么能判断"一定不存在"？因为如果这个元素曾经被添加过，它对应所有哈希位置肯定都是 1。只要有一个位置是 0，说明它肯定没被添加过，所以一定不存在。
6. 为什么只能说"可能存在"？因为存在哈希冲突，不同的元素可能哈希到同样的位置。如果 A 元素把位置 3、7、12 置为 1，B 元素把位置 4、7、15 置为 1，那查询 C 的时候它的哈希位置恰好是 3、7、15，三个位置都是 1，C 就会被误判为存在，这就是假阳性。布隆过滤器不能删除元素也是这个原因，删了一个元素把对应位置清零，会影响其他元素。

### **Q11** 缓存击穿：一个热点 key 过期瞬间大量请求打到 DB，你怎么处理？互斥锁方案和"逻辑过期"方案各自的优缺点？
?
1. 缓存击穿是指一个热点 key，过期的那一刻同时有大量并发请求进来，缓存里没有，所有请求都穿透去查数据库，数据库瞬间压力暴增。
2. 解决方案主要有两种。
3. 互斥锁方案：当缓存未命中时，不是所有请求都去查数据库，而是用 SETNX 抢一把分布式锁，只有抢到锁的那个线程去查数据库、回写缓存，其他没有抢到锁的线程休眠一段时间后重试读缓存。优点是实现简单，保证只有一次数据库查询。缺点是锁等待会引入一些延迟，极端情况下锁超时或者持有锁的线程挂了会让所有线程都等满重试时间。
4. 逻辑过期方案：热点 key 不设置真正的 Redis 过期时间，而是在 value 里面加一个逻辑过期时间字段。当缓存命中时，先检查逻辑时间是否过期，如果还没过期直接返回。如果逻辑时间过期了，一样用互斥锁单线程去查数据库，但其他线程不等待，直接返回旧的过期数据。数据库更新完成后，释放锁并把新数据写到缓存。优点是用户感知不到等待，始终能拿到一个数据，不阻塞。缺点是返回的数据可能是旧的，不适合对实时性要求极高的场景。
5. 实际项目里更推荐逻辑过期方案，因为用户体验更好，永远有数据返回，不会卡住。

### **Q12** 缓存雪崩：大量 key 同时过期或 Redis 宕机，分别怎么应对？过期时间加随机值有效吗？多级缓存怎么搭？
?
1. 缓存雪崩有两种情况。
2. 第一种，大量 key 同一时间过期，缓存大面积失效，请求全部涌向数据库。解决方案是用过期时间加随机值，让不同 key 的过期时间分散开。比如原本设置 1 小时过期，改成 3600 加随机 300 秒，防止集中过期。这个方案非常有效且实现简单。
3. 第二种，Redis 本身宕机或者不可用，所有请求直接打到数据库。解决方案分为几个层面：首先是 Redis 高可用，用主从加哨兵或者 Cluster 集群保证 Redis 本身不宕机。其次是多级缓存架构，浏览器缓存、Nginx 本地缓存、JVM 本地缓存 Caffeine、Redis 远程缓存、数据库五层，每一层都有兜底。最后是限流和降级，当发现 Redis 不可用时，触发限流保护数据库，或者降级返回默认数据。
4. 多级缓存的典型搭建方式：最外层 CDN 缓存静态资源，Nginx 层面用 proxy_cache 做一层本地缓存，应用层面用 Caffeine 做 JVM 内缓存设置短过期时间比如 1 分钟，Redis 做分布式缓存设置较长过期时间比如 30 分钟。查询顺序从 Caffeine 到 Redis 到数据库，每一层命中了就回种上层。

## 四、缓存一致性 & 读写策略

### **Q13** Cache Aside（旁路缓存）模式：先删缓存再写 DB，还是先写 DB 再删缓存？为什么？延迟双删又是什么？每种方案有什么风险？
?
1. 这个问题有个非常经典的结论：先写数据库再删缓存，绝大多数场景下都这样做。
2. 先删缓存再写数据库的风险在于：线程 A 删了缓存，还没来得及写数据库，线程 B 来读，发现缓存没命中，去查数据库取到旧值，然后线程 B 把旧值写入缓存。此时线程 A 再写数据库，数据库变成了新值，但缓存里却是线程 B 写的旧值，造成数据不一致。这个时序在并发场景下是可能发生的。
3. 先写数据库再删缓存也有风险，但概率极低：线程 A 读缓存未命中，去查数据库拿到旧值，还没来得及写缓存，线程 B 写数据库更新为新值、删了缓存，然后线程 A 把旧值写回缓存。这个时序要求读操作恰好卡在写操作的两个步骤之间，概率远小于第一种情况，而且对缓存的命中率有要求——必须缓存未命中才能触发这个路径。
4. 延迟双删是在先删缓存再写数据库的基础上做的增强：先删缓存，再写数据库，然后 sleep 几百毫秒，再删一次缓存。目的是清理在写数据库期间被其他线程写入的脏数据。但 sleep 时间很难确定，设置太短可能清理不干净，太长影响响应时间，一般不建议用。
5. 生产环境的推荐做法是先写数据库后删缓存，删除失败可以加 MQ 重试或者 Canal 订阅 binlog 做最终一致性的兜底。

### **Q14** 如果业务要求"强一致性"，Redis 缓存能做到吗？Canal 订阅 `binlog` 异步更新缓存的方案是什么？和 Cache Aside 比有哪些优劣？
?
1. Redis 缓存本身做不到强一致性，因为缓存和数据库是两个独立的存储系统，任何先 A 后 B 或者先 B 后 A 的操作都有时序窗口。Redis 缓存最适合的是最终一致性的场景。
2. Canal 方案的工作原理：Canal 伪装成 MySQL 的从库，订阅主库的 binlog，当数据库有数据变更时，Canal 实时解析 binlog，把变更事件推送到 MQ，然后由专门的缓存更新服务消费这些事件来更新或删除 Redis 缓存。
3. 和 Cache Aside 对比，Canal 方案有三个优势：第一，解耦了业务代码，业务只需要关心写数据库，缓存更新完全由 Canal 驱动，不侵入业务逻辑。第二，可靠性更高，Cache Aside 中如果删缓存失败了，这次不一致可能一直存在，而 Canal 基于 binlog 的机制可以保证数据库的每次变更都能被捕获。第三，适合跨系统缓存同步，多个服务都要更新缓存时，Canal 做一个统一的中转。
4. Canal 方案的缺点：第一，引入了额外的组件 Mastray Canal、MQ、缓存更新服务，架构复杂度增加。第二，是异步的，有延迟，从数据库变更到缓存更新有一个时间差，这个时间差内读到的还是旧数据。第三，需要维护一条数据同步链路，出问题排查成本高。

### **Q15** 缓存预热怎么做？新服务上线时，冷缓存导致 DB 压力暴增，你有哪些预热手段？
?
1. 缓存预热的核心思路是：在服务正式接收流量之前，先把热点数据加载到缓存中。
2. 具体手段有几种。第一，启动预热任务：服务启动时，在 Spring 的 ApplicationRunner 或者 CommandLineRunner 里面写一个预热线程，批量从数据库查询热点数据写入 Redis，等预热完成后再放开流量入口。第二，离线预热脚本：在服务部署之前，用一个独立的脚本或者定时任务把数据提前灌入 Redis，适用于数据量特别大的场景。第三，定时刷新预热：用定时任务每天凌晨或者业务低峰期，跑一遍热门数据的查询并更新缓存，保持缓存的活跃度。第四，利用 Redis 的 RDB 文件恢复：新节点部署时，直接把生产节点的 RDB 文件拷贝过来启动，快速恢复缓存状态。
3. 预热时需要注意控制频率和并发，避免预热本身成为数据库的负担。通常需要分批查询、加间隔时间。

## 五、持久化（RDB / AOF / 混合）

### **Q16** RDB 和 AOF 的区别？各有什么优缺点？RDB 的 `save` 和 `bgsave` 区别？`bgsave` 过程中 fork 子进程，如果数据 10G，fork 会阻塞多久？
?
1. RDB 是快照持久化，把某个时刻内存中的全量数据写入磁盘的二进制文件。AOF 是追加日志持久化，把每次写操作命令追加到 AOF 文件末尾，重启时回放这些命令恢复数据。
2. RDB 的优点：文件小、恢复速度快，适合做全量备份和灾难恢复。缺点：因为是定期快照，两次快照之间如果宕机，这一段时间的数据就丢了，数据安全性差。
3. AOF 的优点：数据安全性高，everysec 策略最多丢 1 秒数据。缺点：文件大、恢复速度慢，因为要逐条回放命令。
4. save 和 bgsave 的区别：save 命令在主线程执行持久化，执行期间 Redis 不处理任何客户端请求，生产环境绝对不能用。bgsave 会 fork 一个子进程来执行持久化，主线程继续处理请求，不阻塞服务。
5. bgsave 的 fork 操作本身是阻塞的，需要拷贝父进程的页表。对于 10GB 内存的实例，fork 通常阻塞在几毫秒到几十毫秒之间。这里的关键是要理解 fork 使用的是操作系统的 copy-on-write 机制：fork 瞬间不是拷贝 10GB 数据，而是复制页表，真正的物理内存只有在父进程或子进程修改时才会复制。但如果内存中大量使用了，实际阻塞时间取决于页表大小，通常在 10ms 到 50ms 左右，具体取决于内存大小和硬件性能。

### **Q17** AOF 重写（Rewrite）的流程？为什么不直接覆盖原来的 AOF 文件？重写期间新的写命令怎么处理？
?
1. AOF 重写的目的是压缩 AOF 文件体积。比如一个计数器 INCR 了 100 次，AOF 里就有 100 条命令，但重写后就变成一条 SET 计数器 100。
2. 重写流程：首先，Redis 主进程 fork 出一个子进程。子进程根据当前内存中的数据状态，生成一个新的 AOF 文件，这个文件包含了恢复当前数据所需的最小命令集合。在子进程重写期间，主进程继续接收客户端请求，把新的写命令同时写入 AOF 缓冲区和 AOF 重写缓冲区。子进程完成重写后，向主进程发送一个信号，主进程把 AOF 重写缓冲区中的增量命令追加到新的 AOF 文件末尾，然后原子的用新文件替换旧文件。
3. 不直接覆盖原文件的原因有两个：第一，如果直接覆盖过程中系统崩溃，旧的 AOF 被破坏、新的没写完，数据全丢。先写临时文件再原子替换，即使重写过程中崩溃，旧文件还在，数据不会丢。第二，重写是很耗时的 IO 操作，直接覆盖会长时间占用原文件的写入锁，影响正常 AOF 的追加。

### **Q18** Redis 4.0 混合持久化：RDB + AOF 混合，格式是什么？解决了什么问题？
?
1. 混合持久化解决了 RDB 数据安全性差和 AOF 恢复慢的矛盾。
2. 格式上，混合持久化文件的前半部分是 RDB 格式的二进制快照数据，后半部分是 AOF 格式的增量命令。也就是说，生成的 AOF 文件不是纯命令，而是 RDB 头加 AOF 尾。
3. 重写时，子进程先把当前的内存数据以 RDB 格式写入 AOF 文件的前半部分，这个过程和 RDB 一样快。然后主进程把重写缓冲区里的增量命令以 AOF 格式追加到文件后面。这样，一个文件里既有全量快照又有增量命令，恢复时先加载 RDB 部分快速恢复大部分数据，再回放 AOF 部分恢复增量，既保证了恢复速度快，又保证了数据不丢失。

### **Q19** `appendfsync` 的三种策略（always / everysec / no）各自的优缺点？默认 `everysec` 丢数据最多丢多少？
?
1. always：每次写命令都同步刷盘，数据安全最高，一个命令都不丢，但性能最差，因为每次写盘都是磁盘 IO 操作。适合对数据安全性要求极高的场景。
2. everysec：每秒同步一次，由后台线程每秒调用一次 fsync。性能好，最多丢 1 秒的数据。这是默认策略，绝大多数场景都用这个，性能和安全性平衡得最好。
3. no：不主动同步，由操作系统决定什么时候把缓冲区数据写入磁盘，通常是 30 秒左右刷一次。性能最好，但丢失数据可能是几十秒的量，生产一般不推荐。
4. 默认 everysec 丢数据最多丢 2 秒的数据。这里容易误以为是 1 秒，实际最多可能是 2 秒。原因：假设在第 0.9 秒主进程写入了一条命令到 AOF 缓冲区，按理第 1 秒就该刷盘。但如果后台的刷盘线程因为磁盘繁忙在第 1 秒没来得及完成，推迟到了第 2 秒才实际执行，而 Redis 此时宕机了，那第 0.9 秒到第 1.9 秒大约 2 秒的数据都会丢失。所以准确的说法是：everysec 策略在极端情况下最多丢 2 秒数据，不过这种情况极少发生。

## 六、主从 & Sentinel

### **Q20** Redis 主从复制的完整流程：全量同步和增量同步，什么情况下会触发全量同步？
?
1. 全量同步发生在从节点首次连接主节点，或者从节点的复制偏移量和主节点相差太多，复制积压缓冲区已经找不到对应数据的时候。
2. 全量同步流程分四步：第一步，从节点发送 PSYNC ? -1 命令给主节点，表示我是新来的，需要全量同步。第二步，主节点执行 bgsave 生成 RDB 快照，同时把生成 RDB 期间的新写命令写入 replication buffer。第三步，主节点把 RDB 文件发送给从节点，从节点清空当前数据后加载这个 RDB。第四步，主节点把 replication buffer 里的增量命令发给从节点执行，追上最新的数据状态。
3. 增量同步发生在从节点短暂断连后重连的时候。从节点发送 PSYNC 主节点 runid 当前偏移量，主节点检查复制积压缓冲区，如果从节点的偏移量还在缓冲区范围内，就直接把从那个偏移量之后的增量命令发给从节点。复制积压缓冲区是一个固定大小的环形缓冲区，默认 1MB。
4. 触发全量同步的情况：从节点首次连接、从节点的 runid 和主节点的对不上、从节点的偏移量不在积压缓冲区里了——这种情况通常是断连时间太长，积压缓冲区被新命令覆盖了。

### **Q21** Sentinel 哨兵模式下，主观下线（SDOWN）和客观下线（ODOWN）的区别？哨兵选主（Failover）的流程是怎样的？
?
1. 主观下线 SDOWN 是单个哨兵自己判断的：当哨兵给一个节点发 PING 命令，在 down-after-milliseconds 时间内没收到有效回复，这个哨兵就认为该节点主观下线了。因为是单个哨兵的判断，可能是网络抖动误判。
2. 客观下线 ODOWN 是多个哨兵达成的共识：当一个哨兵认为主节点 SDOWN 后，会向其他哨兵发送 is-master-down-by-addr 命令询问，如果达到 quorum 个哨兵都认为主节点挂了，就标记为客观下线。这时候哨兵才真正认为主节点真的死了，开始故障转移。
3. 故障转移流程：第一步，哨兵集群选出领导者，用 Raft 算法，获得半数以上票的哨兵成为领导者。第二步，领导者从所有健康的从节点中选出一个作为新主节点，选择规则是优先级最高、数据最新的从节点。第三步，领导者向新主节点发送 SLAVEOF NO ONE 命令，让它成为独立的主节点。第四步，领导者让其他从节点都去复制新的主节点。第五步，通知客户端主节点地址已经变更。

### **Q22** 主从 + 哨兵模式有什么缺陷？为什么很多大厂用 Cluster 而不只用哨兵？脑裂（Split-Brain）发生时会发生什么？
?
1. 主从加哨兵模式有三个核心缺陷。第一，只有一个主节点处理写请求，写性能无法水平扩展，单机写的吞吐量就是集群的上限。第二，所有数据在每个节点上都是全量存储，内存容量受限于单机，不能通过加节点来增加总存储容量。第三，故障转移有短暂的服务不可用窗口，主从切换期间写操作会失败。
2. Cluster 解决了这三个问题：16384 个哈希槽分布在多个主节点上，每个节点只负责部分数据，写操作由多个主节点分担，做到了水平扩展；总内存是所有节点内存的加和，不再是单机瓶颈；Cluster 自带故障转移，主节点挂了由它的从节点顶上。
3. 脑裂是指主节点和哨兵集群网络隔离，哨兵选出了新主节点，但原来的主节点还认为自己活着继续接收写请求。此时会出现两个主节点同时接受写操作，当网络恢复后，旧主节点被降为从节点，它在网络隔离期间接收的所有写数据全部丢失。解决脑裂的配置是设置 min-replicas-to-write 和 min-replicas-max-lag：主节点发现至少有一个从节点的延迟不超过 10 秒才接收写请求，否则拒绝写入。这能保证网络隔离时主节点发现自己联系不上从节点后主动停写，避免脑裂写入后数据丢失。

## 七、Cluster 集群

### **Q23** Redis Cluster 的 16384 个哈希槽怎么分配的？客户端怎么知道该去哪个节点？MOVED 和 ASK 重定向的区别？
?
1. 16384 个哈希槽在 Cluster 部署时分配给各个主节点，比如三个主节点，每个分到大约 5461 个槽。分配通过 CLUSTER ADDSLOTS 命令执行。
2. 客户端定位节点的方式有三种。第一种是重定向：客户端随机连接任意一个节点发请求，如果这个 key 对应的槽不在当前节点上，节点返回 MOVED 错误，并告诉客户端正确的节点地址，客户端重新向正确节点发起请求。第二种是 Smart 客户端：客户端在第一次连接时执行 CLUSTER SLOTS 命令，拿到槽与节点的映射关系，缓存到本地，之后每次请求直接发到正确的节点。第三种是代理层，比如 Codis，由代理统一做路由。
3. MOVED 重定向是说这个槽永久性地迁移到了另一个节点，客户端收到后应该更新自己的槽映射缓存，后续请求直接发到新节点。
4. ASK 重定向是说这个槽正在迁移过程中，目标 key 的数据已经部分迁移到目标节点了，客户端收到后只对当前这个 key 的请求临时转向目标节点，不应该更新本地缓存，因为槽的迁移还没完成。
5. 两者的区别：MOVED 是永久转移，ASK 是临时重定向。MOVED 要更新缓存，ASK 不更新缓存。

### **Q24** Cluster 的节点间通信用什么协议？Gossip 协议的优势和劣势？
?
1. Redis Cluster 节点间通信用的是 Gossip 协议，去中心化的。每个节点定期随机选几个其他节点交换自己知道的集群信息，信息逐渐扩散到整个集群。
2. Gossip 协议的优势：第一，去中心化，没有单点故障，任何节点挂了不影响集群信息传播。第二，扩展性好，新节点加入只需要和少数节点交换信息，自动被集群感知到，不需要全局广播。第三，容错性好，即使消息在传递过程中丢失了，下次轮次会被其他节点重新扩散过来。
3. Gossip 协议的劣势：第一，信息传播有延迟，一个节点挂了，需要多轮传播才能让所有节点感知到，通常需要几秒到几十秒。第二，消息冗余，同一个消息可能被多个节点同时通知，存在带宽浪费。第三，集群规模不宜过大，节点数的平方级的消息量，官方建议不超过 1000 个节点。

### **Q25** Cluster 模式下，一个 key 的所有操作都必须落在同一个节点吗？事务（MULTI）和 Lua 脚本在 Cluster 下有什么限制？`hash_tag {}` 怎么用的？
?
1. 是的，同一个 key 的所有操作都在同一个节点上，因为 key 被 CRC16 编码后分配的槽是固定的，一个槽只有一个主节点负责。
2. 事务 MULTI 在 Cluster 模式下有个严格的限制：一个事务里所有的 key 必须落在同一个哈希槽上，否则会报错 CROSSSLOT。因为事务要求原子执行，如果 key 分布在两个节点上，没法跨节点保证原子性。
3. Lua 脚本同样有这个限制，脚本中操作的所有 key 必须属于同一个槽。而且 Redis 要求执行 EVAL 命令时必须显式写出所有操作的 key 参数，Redis 用这些 key 来校验是否在同一个槽。如果脚本中操作了不在 key 参数里声明的 key，Redis 检测不到，执行会失败。
4. hash_tag 就是用来突破这个限制的。语法是在 key 中用大括号包住相同的一段字符串，比如 {user:1001}:name 和 {user:1001}:age，Redis 计算槽的时候只对大括号里的 user:1001 做 CRC16，这样两个 key 就落到同一个槽上了。典型场景是操作同一个用户的多个字段时，把所有 key 加上相同的前缀大括号，确保它们同一个槽，就可以在同一事务或 Lua 脚本中操作。

## 八、线程模型 & 性能

### **Q26** Redis 为什么单线程还这么快？
?
主要四个原因。第一，纯内存操作。读写都是内存级的，不涉及磁盘 IO，内存读写速度是纳秒级的，远快于磁盘的毫秒级，这是快的根本原因。第二，IO 多路复用。Redis 使用 epoll 这样的 IO 多路复用机制，一个线程可以同时监听成千上万个客户端连接，哪个连接有数据可读就处理哪个，非阻塞网络 IO 模型让单线程也能处理高并发连接。第三，单线程无锁。因为只有一个线程执行命令，不存在多线程竞争的问题，不需要加锁、不需要上下文切换，省去了大量的 CPU 开销。第四，高效的数据结构。Redis 自己实现了一套专门针对内存场景优化的数据结构，比如 SDS 简单动态字符串、跳表、压缩列表等，比通用的数据结构更快，时间复杂度基本都在 O(1) 到 O(log n) 级别。

### **Q27** Redis 6.0 的多线程到底是什么？命令执行还是单线程吗？多线程用在什么环节？为什么不是全链路多线程？
?
1. Redis 6.0 的多线程默认是关闭的，需要配置开启。而且命令执行仍然是单线程的，多线程只用在网络 IO 的读写环节。
2. 具体来说，以前是主线程既负责读取客户端发送的数据包，又负责解析协议执行命令，又负责把结果写回客户端。6.0 之后，多个 IO 线程负责从 socket 读取数据包和写回响应结果，主线程只负责解析协议和执行命令。也就是说，最核心的命令执行逻辑依然是单线程串行的。
3. 多线程只用在网络 IO 的原因：Redis 的性能瓶颈其实不在 CPU 计算，而在网络 IO 和内存带宽。命令执行本身是 O(1) 或 O(log n) 的，极快。瓶颈在于接收和发送大量的 TCP 数据包，这个过程需要系统调用的 read 和 write。把网络收发多线程化，主线程的压力减轻了，可以处理更多的客户端连接。
4. 不用全链路多线程的原因：保持命令执行的顺序性和原子性，避免引入锁竞争。Redis 的一大优势就是单线程执行命令逻辑，不用考虑线程安全问题，代码简洁性能高。如果连命令执行都多线程化，所有数据结构都需要加锁，复杂度大幅上升，得不偿失。

### **Q28** Redis 大 Key 的危害？怎么发现大 Key？大 Key 必须 `DEL` 时，为什么可能阻塞？怎么优雅删除？
?
1. 大 Key 的危害有四点。第一，占用大量内存，导致内存不均，Cluster 模式下某个节点内存特别高，其他节点内存很低，分布不均衡。第二，操作大 Key 会阻塞 Redis：DEL 一个 String 类型的大 Key 是 O(1) 的，影响不大，但 DEL 一个包含百万个元素的 Set 或者 Hash，是 O(n) 的，会直接阻塞主线程数秒甚至更久。第三，大 Key 的网络传输开销大，一次查询要返回几 MB 的数据，占用带宽并导致其他请求排队。第四，大 Key 在做 RDB 主从同步时，发送 RDB 文件或加载 RDB 都可能因为文件中包含大 Key 而变慢。
2. 发现大 Key 有两种方式。命令行工具：BIGKEYS 命令会扫描所有 key 的类型和大小，但它是阻塞的，生产环境慎用。MEMORY USAGE key 可以精确看某个 key 内存大小，不阻塞。另一种是统计手段：用 Redis 的慢查询日志监控命令耗时，配合客户端监控 key 的大小。
3. DEL 大 Key 会阻塞的原因：DEL 命令删除一个包含大量元素的集合时，Redis 要逐个释放元素的内存，时间复杂度 O(n)，这段时间主线程被占用，其他所有请求无法处理。
4. 优雅删除的方式：Redis 4.0 之后提供了 UNLINK 命令，它和 DEL 的区别是 UNLINK 是异步删除的。它会先从键空间解除 key 的引用，让客户端访问不到，然后把真正的内存回收操作交给后台线程慢慢处理，不阻塞主线程。如果版本低于 4.0，可以用 SCAN 系列命令分批删除集合中的元素，比如 HSCAN 每次删 100 个，然后 sleep 一小段时间。

## 九、分布式锁 & 实战

### **Q29** Redis 分布式锁：`SET key value NX PX 30000`，一个命令为什么比 `SETNX` + `EXPIRE` 两步好？解锁为什么必须用 Lua 脚本？
?
1. SET key value NX PX 30000 是一条命令，原子性地完成加锁和设置过期时间两个动作。而 SETNX 加 EXPIRE 是两条命令，中间存在空隙：如果 SETNX 执行成功后、EXPIRE 执行前，客户端挂了或者网络中断了，这个锁就成了永远不过期的死锁，别的客户端永远获取不了锁。一条命令兼具两件事，避免了非原子的风险。
2. 解锁为什么必须用 Lua 脚本？因为解锁需要做两件事：先判断 value 是不是自己设的，是的话才 DEL。如果分两步做，判断完之后、DEL 之前，锁刚好过期了又被别的客户端抢到，此时执行 DEL 就删了别人的锁。Lua 脚本在 Redis 中是原子执行的，保证判断和删除是一个不可分割的操作。逻辑是先 GET key，看值是不是自己的请求 ID，如果不是说明锁不是自己持有的不能删，如果是就 DEL。

### **Q30** Redisson 的"看门狗"（Watchdog）机制是怎么实现锁自动续期的？如果 Redisson 节点宕机了，看门狗还能续期吗？
?
1. Redisson 的看门狗机制解决了锁持有时间不够导致锁提前释放的问题。业务代码加锁时如果不指定过期时间，Redisson 默认给锁设置 30 秒过期，然后启动一个后台定时任务，每隔 10 秒检查一下：如果锁还在当前客户端持有，就把过期时间续到 30 秒。这样只要业务逻辑不主动释放锁，锁就一直被自动续期，业务跑多久锁就在多久。
2. 看门狗是基于 Netty 的时间轮定时任务实现的，在应用进程内部作为一个后台线程运行。
3. 如果 Redisson 所在的应用节点宕机了，看门狗线程也一起死了，锁不会再被续期。锁会在 Redis 中自然过期 30 秒后被自动删除，其他节点就可以加锁了。这是一种安全的释放机制：应用挂了，锁最多再活 30 秒，不会出现永久死锁。

### **Q31** RedLock 算法（Redis 官方推荐的分布式锁）的流程？为什么 Martin Kleppmann 说 RedLock 不安全？争议的核心是什么？
?
1. RedLock 的思路是在多个独立的 Redis 主节点上同时加锁，半数以上成功才算加锁成功。
2. 流程：第一步，客户端获取当前时间戳。第二步，按照顺序依次向 N 个 Redis 节点发送 SET NX PX 加锁请求，每个请求的超时时间要远小于锁的过期时间，防止在一个慢节点上卡住。第三步，统计成功的节点数，如果超过半数，且总耗时小于锁的过期时间，加锁成功，锁的有效期等于设置的过期时间减去总耗时。第四步，如果加锁失败，向所有节点发送释放锁命令。
3. Martin Kleppmann 说 RedLock 不安全的核心论点是：RedLock 依赖的是系统时间的绝对准确性，而分布式系统中时钟是不可靠的。他的攻击场景是这样的：客户端 A 在五个节点中的三上加锁成功，此时客户端 A 发生一次长时间的 GC 停顿，停顿期间锁过期了。停顿结束后 A 认为自己还持有锁继续操作，而另一个客户端 B 已经获取了锁，两者同时操作共享资源，破坏了互斥性。RedLock 依赖锁的过期时间来做安全边界，而 GC 停顿、网络延迟等都可以让这个边界失效。Kleppmann 的结论是分布式锁的安全应该基于递增的 fencing token，每次持有锁都带一个令牌，资源层用版本号校验，而不是只靠过期时间来保证。
4. Redis 官方作者 Antirez 的回应是：这个攻击场景不仅适用于 RedLock，任何基于自动过期的分布式锁都面临同样问题，这不是 RedLock 特有的缺陷。

## 十、Redis 新版本 & 现代生态

### **Q32** Redis 7.0 有哪些重要的新特性？挑 3 个说清楚。
?
1. 第一个，Redis Functions。这是 Lua 脚本的替代方案。Lua 脚本的痛点是脚本散落在各个客户端，管理混乱，而且脚本内容不持久化，重启就没了。Redis Functions 把脚本逻辑定义在服务端，通过 FUNCTION LOAD 加载后持久化到 AOF 和 RDB 中，重启不会丢失。而且 Functions 支持版本管理，更新脚本用 FUNCTION LOAD REPLACE 替换。语言仍然是 Lua，但管理方式从客户端侧移到了服务端侧，同时引入了权限控制。
2. 第二个，ACL v2。ACL 从第一版的基础用户名密码控制，升级到支持细粒度的命令和 key 级别的权限控制。比如可以创建一个只读用户，限制只能执行 GET 命令，而且只能访问特定前缀的 key，对生产环境的安全治理非常有意义。还可以对 Pub/Sub 频道做权限控制。
3. 第三个，AOF v2。AOF 文件在 7.0 中被重构为按时间戳的多文件管理，一个 base 文件加多个增量文件，解决了之前单文件 AOF 越来越大、重写代价高的问题。新的 multi-part AOF 通过 manifest 文件追踪所有 AOF 分片，更灵活。

### **Q33** Redis Stack 是什么？RediSearch、RedisJSON、RedisTimeSeries、RedisBloom 分别解决什么问题？什么时候选 Redis Stack 而不是单独的 Elasticsearch？
?
1. Redis Stack 是 Redis 官方推出的一个包含了多种扩展模块的增强版本，把原来需要单独安装的模块打包在一起。
2. RediSearch 做全文搜索和二级索引。能在 Redis 内部对 JSON 或 Hash 数据做全文检索、模糊搜索、聚合查询，性能比传统搜索引擎快，因为数据全在内存里。RedisJSON 做 JSON 文档存储和查询，支持 JSONPath 表达式直接操作嵌套 JSON 字段，不用取出整个 JSON 序列化再反序列化。RedisTimeSeries 做时序数据存储，专门优化了时间序列的压缩和范围查询，适合监控数据、IoT 传感器数据。RedisBloom 提供布隆过滤器、布谷鸟过滤器、Top-K、Count-Min Sketch 等概率数据结构。
3. 什么时候选 Redis Stack 而不是 Elasticsearch：当数据量在几百万到千万级别，对搜索性能要求很高，数据已经在 Redis 里了，不想再维护一个 Elasticsearch 集群时，RediSearch 是一个很好的选择。但如果需要复杂的中文分词、同义词、相关性打分等高级搜索能力，或者数据量到百亿级别，还是应该用 Elasticsearch。另外，如果团队已经有 Elasticsearch 运维经验，引入 RediSearch 有学习成本。

## 十一、实战场景

### **Q34** 你设计一个秒杀系统，怎么用 Redis 做库存扣减？对比优劣。如何处理"超卖"和"少卖"？
?
1. 秒杀库存扣减的关键是原子性和性能兼顾。
2. 方案一是 DECR 直接扣减。先用 DECR 减去 1，判断返回值，如果大于等于 0 表示扣减成功，如果小于 0 说明库存不足要加回来。但这里有个问题：DECR 和判断是两步操作，如果 DECR 返回 -1 后还没来得及 INCR 加回来，另一个请求又 DECR 变成了 -2，虽然不会超卖，但库存计数器变成了负数，不准确。如果业务可以容忍计数器短暂为负，这个方案最简单。
3. 方案二是 Lua 脚本原子扣减。把库存判断和扣减写在一个 Lua 脚本里一起执行：先 GET 库存，如果大于 0 就 DECR 并返回成功，否则返回失败。Lua 脚本在 Redis 中原子执行，不存在并发问题。这是最推荐的方案。
4. 方案三是预扣库存加异步确认。用户在 Redis 中抢到库存后，生成一个预扣记录并放入 MQ，异步写入数据库。如果支付超时，释放库存回 Redis。
5. 超卖问题：Redis 层面用 Lua 脚本的原子判断加扣减能解决。数据库层面用乐观锁 UPDATE stock = stock - 1 WHERE stock > 0，或者直接在数据库层面用悲观锁 SELECT FOR UPDATE 串行化。
6. 少卖问题：少卖指的是库存还没卖完系统就报已售罄了。可能的原因：第一，某个 Redis 节点预扣了库存但用户取消了，库存没及时回补；第二，Lua 脚本只查了当前 Redis 节点的库存，Cluster 模式下库存分散在多个节点。解决方式：定期对账，把未支付的预扣超时释放；库存尽量集中在单个 Redis 节点上用 hash_tag 保证所有库存操作在同一个 slot。

### **Q35** Redis 突然响应变慢，你怎么排查？可能的原因有哪些？你的排查流程是什么？
?
1. 六种常见原因，按可能性从高到低排查。
2. 第一步，查慢查询日志。SLOWLOG GET 10，看最近 10 条慢查询。如果发现 KEYS *、SMEMBERS 大集合、HGETALL 大 Hash 等，考虑就是复杂度过高的命令导致的。解决方式：KEYS 改 SCAN，大集合分批获取。
3. 第二步，查大 Key。用 BIGKEYS 或 MEMORY USAGE 看有没有超大 Key。如果有个 String 几百 MB，或者 Hash 几百万字段，操作这些 key 时就会阻塞。
4. 第三步，查持久化影响。如果开启了 RDB 的 bgsave 或 AOF 重写，fork 子进程的时间点可能堵塞主线程。INFO stats 里可以看 latest_fork_usec 字段，如果 fork 时间超过 100ms，内存太大的问题。另外，AOF 的 fsync 如果是 always 策略，磁盘性能跟不上也会拖慢 Redis。
5. 第四步，查内存 swap。INFO memory 看 used_memory 和 RSS 是否接近。如果 RSS 远大于 used_memory，说明内存碎片严重。如果 RSS 小于 used_memory，说明 Redis 被 swap 到了磁盘，此时性能会骤降。解决方式是设置 maxmemory、控制内存使用、关闭系统的 swap 或者设置 swapiness 为很低的值。
6. 第五步，查 CPU 竞争。看 Redis 进程的 CPU 使用率，如果 CPU 本身就很忙，可能是有其他进程和 Redis 抢 CPU。多核情况下，Redis 是单线程的，一个核被抢走直接影响所有请求。解决方式是把 Redis 绑定到固定核心，确保不被其他进程抢占。
7. 第六步，查网络延迟。用 redis-cli 的 --latency 和 --latency-history 看网络延迟有没有突增。集群模式下也可能是客户端路由出了问题，请求被转发到了不通的节点。
8. 排查流程总结：先看慢查询定位命令层面，再看大 Key 排除数据层面，然后查持久化和系统层面，最后查网络。通常上面几步走完就能定位到问题。
