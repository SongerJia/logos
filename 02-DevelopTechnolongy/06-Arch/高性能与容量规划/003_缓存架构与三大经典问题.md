|---|---|---|---|---|---|
|**5.3.1**|**缓存穿透 Cache Penetration**|查询一个**不存在**的数据(恶意攻击或不存在的ID)：每次都穿透缓存直达DB，DB承受大量无效查询|①布隆过滤器(Bloom Filter)预判不存在 ②缓存空对象(短TTL如60s) ③接口层校验(参数合法性)|"布隆过滤器的原理？为什么会有误判？误判率怎么控制？"|流程实例查询：先走BloomFilter判断instanceId是否存在 → 不存在直接返回404|
|**5.3.2**|**缓存击穿 Cache Breakdown**|一个**热点key**突然过期(或被主动删除)，瞬间大量并发请求同时打到DB|①互斥锁(只让一个线程回源重建) ②逻辑过期(不物理删除TTL，后台异步刷新) ③永不过期(手动管理)|"Redis分布式锁和本地锁在防击穿场景的区别？"|热点流程定义(ProcessDefinition)：逻辑过期 + Redisson分布式锁重建|
|**5.3.3**|**缓存雪崩 Cache Avalanche**|大量key**同时过期**或Redis宕机，所有请求瞬间打到DB导致崩溃|①TTL加随机值(打散过期时间) ②多级缓存(Local+Redis) ③熔断降级(缓存不可用时降级) ④Redis高可用(Sentinel/Cluster)|"TTL随机值的范围一般取多少？为什么不能太大太小？"|所有缓存Key的TTL = baseTime + random(0, 300s)，防止集体过期|
|**5.3.4**|**多级缓存设计 L1+L2**|L1本地缓存(Caffeine/Guava) → L2分布式缓存(Redis) → L3数据库(MySQL)；逐级穿透，L1读最快但一致性最难保证|L1: Caffeine(最大容量/TTL/异步刷新)；L2: Redis Cluster(持久化/高可用)；缓存失效策略: Write-Through / Write-Behind / Write-Around|"L1和L2的数据一致性问题怎么解决？ Canal监听 binlog？"|**Caffeine(L1)** 存放用户权限/流程定义(变更频率低) → **Redis(L2)** 存放运行时数据(任务列表/实例状态)|
|**5.3.5**|**缓存更新策略选型**|Cache Aside(旁路缓存)：读时先读cache→miss则读DB并写回cache；写时先更新DB再删cache(延时双删)|Read-Through / Write-Through(缓存组件负责同步) / Write-Behind(异步批量写回) / Refresh-Ahead(提前刷新)|"Cache Aside策略中，先删缓存还是先更新DB？为什么？"|采用 **Cache Aside + 延时双删**：Update DB → Delete Redis → Sleep 200ms → Delete Redis(防止并发读到旧值)|
