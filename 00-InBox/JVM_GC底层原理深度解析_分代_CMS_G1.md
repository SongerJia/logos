# 第一部分 JVM 内存结构全景

## 1.1 运行时数据区

JVM 在执行 Java 程序时，将其管理的内存划分为若干个区域，每个区域有不同的用途和生命周期：

```
┌──────────────────────────────────────────────────────────────────┐
│                    JVM 运行时数据区                                │
├─────────────────┬─────────────────┬─────────────────┬─────────────┤
│   线程私有                                          │  线程共享      │
├─────────────────┼─────────────────┼─────────────────┼─────────────┤
│                 │                 │                 │              │
│  程序计数器      │  虚拟机栈        │  本地方法栈      │  堆          │
│  (PC Register)  │  (VM Stack)     │  (Native Stack) │  (Heap)      │
│                 │                 │                 │              │
│  当前线程执行    │  方法栈帧        │  Native 方法    │  对象实例     │
│  的字节码行号    │  局部变量表      │  的栈帧         │  数组         │
│                 │  操作数栈        │                 │              │
│                 │  动态链接        │                 │  ┌─────────┐ │
│                 │  方法出口        │                 │  │新生代    │ │
│  不会OOM        │  栈深度溢出      │  栈深度溢出      │  │Eden+S0+S1│ │
│                 │  SOE/OOM        │  SOE/OOM        │  ├─────────┤ │
│                 │                 │                 │  │老年代    │ │
│                 │                 │                 │  │Old Gen  │ │
│                 │                 │                 │  └─────────┘ │
│                 │                 │                 │              │
│                 │                 │                 │  方法区/      │
│                 │                 │                 │  元空间       │
│                 │                 │                 │  (Metaspace) │
│                 │                 │                 │              │
│                 │                 │                 │  类信息       │
│                 │                 │                 │  常量池       │
│                 │                 │                 │  静态变量     │
│                 │                 │                 │  JIT 代码     │
│                 │                 │                 │              │
├─────────────────┴─────────────────┴─────────────────┴─────────────┤
│                      直接内存 (Direct Memory)                      │
│                   NIO DirectByteBuffer / Netty 堆外内存             │
└──────────────────────────────────────────────────────────────────┘
```

## 1.2 各区域详解

### 1.2.1 程序计数器（PC Register）

```
- 作用: 记录当前线程执行的字节码行号
- 特点: 线程私有，不会 OOM
- 如果执行 Native 方法，值为 undefined (undefined)
- 是唯一不会发生 OOM 的区域
```

### 1.2.2 虚拟机栈（VM Stack）

```
- 作用: 存储方法调用的栈帧
- 线程私有，生命周期与线程相同

每个栈帧包含:
┌──────────────────────────────────┐
│          栈帧 (Frame)             │
├──────────────────────────────────┤
│  局部变量表 (Local Variable Table)│
│  ├── this (非 static 方法)       │
│  ├── 方法参数                    │
│  └── 方法内局部变量               │
│  (以 Slot 为单位, 32位占1个Slot)  │
├──────────────────────────────────┤
│  操作数栈 (Operand Stack)        │
│  ├── 字节码指令的操作数           │
│  └── 方法返回值                  │
├──────────────────────────────────┤
│  动态链接 (Dynamic Linking)      │
│  ├── 指向运行时常量池的方法引用    │
│  └── 支持多态/虚方法分发           │
├──────────────────────────────────┤
│  方法返回地址 (Return Address)   │
│  └── 正常返回/异常返回到调用者     │
└──────────────────────────────────┘

异常:
- StackOverflowError: 栈深度超过限制
- OutOfMemoryError: 栈无法扩展
```

**栈帧结构示例**:

```java
public int add(int a, int b) {
    int c = a + b;
    return c;
}

// 对应的栈帧:
// ┌──────────────────────────┐
// │ 局部变量表: [this, a, b, c]│  // 4个Slot
// │ 操作数栈:   [→ a, b, a+b]│  // 执行过程中变化
// │ 返回地址:   → 调用者位置  │
// └──────────────────────────┘
```

### 1.2.3 本地方法栈（Native Stack）

```
- 作用: 为 Native 方法服务
- 与虚拟机栈类似，区别在于服务对象不同
- HotSpot 将虚拟机栈和本地方法栈合二为一
- 可能抛出 SOE 和 OOM
```

### 1.2.4 堆（Heap）

```
- 作用: 存储对象实例和数组
- 线程共享
- GC 的主要区域（"GC 堆"）
- 物理上可以不连续，逻辑上连续

┌───────────────────────────────────────────┐
│                  堆 (Heap)                │
├───────────────────────┬───────────────────┤
│      新生代 (Young)    │    老年代 (Old)    │
│      -Xmn              │                   │
│  ┌──────┬──────┬──────┐│                   │
│  │ Eden │  S0  │  S1  ││    Old Gen       │
│  │ 8    │  1   │  1   ││                   │
│  └──────┴──────┴──────┘│                   │
│  -XX:NewRatio=2        │                   │
│  (Old:Young = 2:1)     │                   │
│  -XX:SurvivorRatio=8   │                   │
│  (Eden:S=8:1:1)        │                   │
└───────────────────────┴───────────────────┘
```

### 1.2.5 方法区 / 元空间（Metaspace）

```
JDK 7 及之前: 永久代 (PermGen) — 堆的一部分，有上限
JDK 8+:      元空间 (Metaspace) — 本地内存，不受堆大小限制

存储内容:
- 类元信息 (Klass, 方法、字段描述)
- 运行时常量池 (字符串常量池在 JDK 7+ 移到堆)
- 静态变量 (JDK 7+ 移到堆)
- JIT 编译后的本地代码

-XX:MaxMetaspaceSize=256m    // 元空间上限
-XX:MetaspaceSize=64m         // 初始元空间大小（触发首次 GC 的阈值）
```

### 1.2.6 直接内存（Direct Memory）

```
- 不是 JVM 运行时数据区的一部分
- NIO 使用 Native 函数直接分配堆外内存
- 不受堆大小限制，受物理内存限制
- Netty 的 PooledByteBufAllocator 大量使用直接内存
- 通过 -XX:MaxDirectMemorySize 限制

OOM 类型: OutOfMemoryError: Direct buffer memory
```

## 1.3 JDK 版本演进

| 版本 | 永久代 | 字符串常量池 | 静态变量 | 默认 GC |
|------|--------|-------------|---------|---------|
| JDK 6 | PermGen (堆内) | PermGen | PermGen | Parallel Scavenge + Parallel Old |
| JDK 7 | PermGen (堆内) | **移到堆** | **移到堆** | Parallel Scavenge + Parallel Old |
| JDK 8 | **废弃 → Metaspace** | 堆 | 堆 | Parallel Scavenge + Parallel Old |
| JDK 9 | Metaspace (本地内存) | 堆 | 堆 | **G1** |
| JDK 10+ | Metaspace | 堆 | 堆 | G1 |

```java
// JDK 8 的元空间 OOM
// -XX:MaxMetaspaceSize=64m
public class MetaspaceOOM {
    public static void main(String[] args) {
        while (true) {
            Enhancer enhancer = new Enhancer();
            enhancer.setSuperclass(OOM.class);
            enhancer.setUseCache(false);
            enhancer.setCallback((MethodInterceptor) (obj, method, args1, proxy) ->
                proxy.invokeSuper(obj, args1));
            enhancer.create();
        }
        // CGLib 动态生成大量类 → Metaspace OOM
    }
}
```

# 第二部分 分代假说与堆内存布局

## 2.1 分代假说（Generational Hypothesis）

GC 分代的**理论基础**——绝大多数对象都是"朝生夕死"的：

```
分代假说（Weak Generational Hypothesis）:
┌─────────────────────────────────────────────────────────────────┐
│  1. 绝大多数对象都是朝生夕死的（die young）                        │
│     → 新生代 GC 频繁但回收效率高                                   │
│                                                                 │
│  2. 熬过越多次 GC 的对象越难以死亡（older objects rarely die）    │
│     → 老年代 GC 不频繁但回收耗时                                  │
└─────────────────────────────────────────────────────────────────┘

对象存活率与年龄的关系:
存活率
  ↑
  │  ■
  │  ■■
  │  ■■■        ← 新生代: 98% 对象在一次 Minor GC 后死亡
  │  ■■■■
  │  ■■■■■■
  │  ■■■■■■■■■■■■     ← 老年代: 存活率高，标记-整理算法
  │  ■■■■■■■■■■■■■■■■■■■■■■■
  └──────────────────────────────→ 对象年龄
     0   1   2   3   4   5+
    (新生代)          (老年代)
```

**基于分代假说的设计决策**:

| 区域 | 特点 | GC 算法 | GC 频率 |
|------|------|---------|---------|
| 新生代 | 对象朝生夕死 | 复制算法（标记-复制） | 高 |
| 老年代 | 对象存活率高 | 标记-清除或标记-整理 | 低 |

## 2.2 堆内存布局详解

```
┌─────────────────────────────────────────────────────────────────────┐
│                           堆 (Heap)                                 │
│                     -Xms (初始) -Xmx (最大)                         │
├──────────────────────────┬──────────────────────────────────────────┤
│      新生代 (Young)       │            老年代 (Old)                  │
│      -Xmn                 │                                          │
│                          │      -XX:NewRatio=2                       │
│  ┌────────┬─────┬─────┐  │      (Old : Young = 2 : 1)              │
│  │  Eden  │ S0  │ S1  │  │                                          │
│  │  80%   │ 10% │ 10% │  │      -XX:SurvivorRatio=8                 │
│  └────────┴─────┴─────┘  │      (Eden : S = 8 : 1 : 1)              │
│                          │                                          │
│  新对象首先分配在 Eden    │      长期存活的对象                       │
│  Minor GC 后存活对象      │      大对象直接分配                       │
│  进入 Survivor            │      动态年龄判断提前晋升                  │
│                          │                                          │
│  Default: -XX:+UsePS     │                                          │
│  Default: -XX:+UseG1GC   │      G1 中没有物理上的新生代/老年代        │
│  (JDK 9+)               │      只有逻辑上的                          │
└──────────────────────────┴──────────────────────────────────────────┘

默认堆大小:
  初始: -Xms = 物理内存 / 64
  最大: -Xmx = 物理内存 / 4
  推荐: -Xms = -Xmx (避免动态扩展带来的开销)
```

## 2.3 新生代为什么用两个 Survivor？

**核心问题**: 为什么不是 Eden + 1 个 Survivor，而是 Eden + 2 个 Survivor？

```
方案 A: Eden + 1 个 Survivor (❌)

GC 前:
┌──────────────┬──────────┐
│    Eden      │ Survivor │
│ [A][B][C][D] │    [E]   │  ← E 是上次 GC 存活的
└──────────────┴──────────┘

GC 时: 需要把 Eden 和 Survivor 中的存活对象 [E] + [B][D] 都复制到...
复制到哪里？自己不能复制到自己（会覆盖自己）。
→ 只能用标记-清除，但碎片化严重。

方案 B: Eden + 2 个 Survivor (✅)

GC 前:
┌──────────────┬──────────┬──────────┐
│    Eden      │   S0     │   S1     │
│ [A][B][C][D] │    [E]   │  (空)    │  ← S1 是空的，作为 To 区
└──────────────┴──────────┴──────────┘

GC 时: Eden + S0 的存活对象 → S1 (To 区)
┌──────────────┬──────────┬──────────┐
│    Eden      │   S0     │   S1     │
│   (清空)     │  (清空)  │   [E][B][D]│  ← 存活对象都在 S1
└──────────────┴──────────┴──────────┘

GC 后: S0 和 S1 角色互换
┌──────────────┬──────────┬──────────┐
│    Eden      │   S0     │   S1     │
│ (新对象分配)  │  (To区)  │  (From区) │  ← 下次 GC 时 S1→S0
└──────────────┴──────────┴──────────┘

优势:
1. 无碎片: 复制算法保证内存连续
2. 无停顿: 清空 Eden 和 From Survivor 即可，不需要整理
3. 空间换时间: 浪费 10% 的 Survivor 空间，换来无碎片
```

## 2.4 对象年龄与晋升

```
对象在 Survivor 区每熬过一次 Minor GC，年龄 +1

晋升到老年代的条件:
┌────────────────────────────────────────────────────────────┐
│  1. 年龄达到阈值 -XX:MaxTenuringThreshold (默认 15)        │
│     → 直接晋升到老年代                                     │
│                                                          │
│  2. 动态年龄判断 (Dynamic Age Detection)                  │
│     → Survivor 中相同年龄对象大小之和 > Survivor 空间的 50% │
│     → 该年龄及以上的对象全部晋升                           │
│     → 这就是为什么有时年龄没到阈值也会晋升                 │
│                                                          │
│  3. 大对象直接进老年代                                    │
│     → -XX:PretenureSizeThreshold (只对 Serial/ParNew有效) │
│     → 超过阈值的对象直接分配在老年代                       │
│     → 避免在 Eden 和 Survivor 之间来回复制                 │
│                                                          │
│  4. Survivor 空间不够                                     │
│     → Minor GC 后存活对象太多 Survivor 放不下               │
│     → 通过担保机制直接进老年代                             │
└────────────────────────────────────────────────────────────┘

对象头中的年龄信息:
┌────────────────────────────────────────────────┐
│  Mark Word (64 bits)                            │
│  ┌──────┬──────┬──────┬──────┬──────┬────────┐│
│  │ hash │ age  │ lock │ ...  │ ...  │  ...   ││
│  │ 31b  │ 4bit │ 2bit │      │      │        ││
│  └──────┴──────┴──────┴──────┴──────┴────────┘│
│         ↑                                      │
│   age: 0~15 (4 bit 最多表示 15)                │
│   所以 MaxTenuringThreshold 最大值是 15          │
│   G1 中最大可以是 15                            │
└────────────────────────────────────────────────┘
```

## 3.1 对象分配全景图

```

    │

                                     空间分配担保  分配成功

```

## 3.2 栈上分配（Stack Allocation）

```
逃逸分析（Escape Analysis）:
- JDK 6u23+ 默认开启 (-XX:+DoEscapeAnalysis)
- 分析对象是否逃出方法/线程的作用域

三种逃逸级别:
1. 全局逃逸 (Global Escape): 对象被其他线程或方法访问
   → 必须在堆上分配
2. 方法逃逸 (Arg Escape): 对象作为方法参数传递
   → 可以在堆上分配
3. 无逃逸 (No Escape): 对象只在方法内部使用
   → 可以栈上分配 / 标量替换

标量替换（Scalar Replacement）:
- 将对象拆解为基本类型变量
- 直接存储在栈帧的局部变量表中
- 不创建真正的对象

// 逃逸分析示例
public class EscapeAnalysis {

    // 1. 无逃逸 → 可以栈上分配
    public long calculate() {
        Point p = new Point(1, 2);  // p 只在方法内使用
        return p.x + p.y;
    }
    // 优化后: 不创建 Point 对象，直接 return 1 + 2 = 3

    // 2. 方法逃逸 → 不能栈上分配
    public Point createPoint() {
        Point p = new Point(1, 2);
        return p;  // p 被返回，逃逸了
    }

    // 3. 线程逃逸 → 不能栈上分配
    public void addToList() {
        Point p = new Point(1, 2);
        list.add(p);  // p 被存入共享集合，线程逃逸
    }
}
```

## 3.3 TLAB（Thread Local Allocation Buffer）

```
TLAB = Thread Local Allocation Buffer

为什么需要 TLAB?
- 多线程同时在 Eden 区分配对象
- 需要加锁或 CAS，竞争激烈
- TLAB 给每个线程分配一块私有内存

┌─────────────────────────────────────────────────────┐
│                    Eden 区                           │
│                                                     │
│  ┌─────────┬─────────┬─────────┬─────────┬────────┐│
│  │ Thread1 │ Thread2 │ Thread3 │ Thread4 │  共享  ││
│  │  TLAB   │  TLAB   │  TLAB   │  TLAB   │  区域  ││
│  │         │         │         │         │        ││
│  │ 指针碰撞 │ 指针碰撞 │ 指针碰撞 │ 指针碰撞 │ CAS分配 ││
│  │ (无锁)  │ (无锁)  │ (无锁)  │ (无锁)  │(有竞争)││
│  └─────────┴─────────┴─────────┴─────────┴────────┘│
└─────────────────────────────────────────────────────┘

TLAB 参数:
- -XX:+UseTLAB          // 开启 TLAB（默认开启）
- -XX:TLABSize=256k     // TLAB 大小
- -XX:-ResizeTLAB      // 禁止自动调整 TLAB 大小

TLAB 分配流程:
1. 线程首次分配 → 向 Eden 申请一块 TLAB
2. 后续分配 → 在自己的 TLAB 中指针碰撞（无锁）
3. TLAB 用完 → 申请新的 TLAB 或回退到 CAS 分配

指针碰撞（Bump the Pointer）:
┌───────────────────────────────┐
│  TLAB                          │
│  [已分配对象][已分配]  ←─ pointer
│  └──────────────┘   ↑         │
│     已使用区域        │         │
│                    分配:       │
│                    pointer +=   │
│                    object_size │
│                    (无锁操作)   │
│  ┌───────────────────┐         │
│  │    空闲区域        │         │
│  └───────────────────┘         │
└───────────────────────────────┘
```

## 3.4 大对象分配

```
大对象 = 需要大量连续内存空间的对象（长数组、大字符串等）

-XX:PretenureSizeThreshold=1048576  // 1MB，超过直接进老年代
// 注意: 只对 Serial 和 ParNew 收集器有效
// Parallel Scavenge 和 G1 有自己的大对象处理机制

G1 中的大对象:
- 超过 Region 大小一半的对象 = Humongous 对象
- 可能跨越多个连续 Region
- 在 Mixed GC 时被回收

┌───────────────────────────────────────────┐
│              G1 堆内存                     │
│  ┌──┬──┬──────────────┬──┬──┬──┐         │
│  │E │E │  Humongous    │O │O │E │         │
│  │  │  │  (跨3个Region) │  │  │  │         │
│  └──┴──┴──────────────┴──┴──┴──┘         │
│  Region大小 = 2的幂, 1~32MB               │
│  大对象 > Region/2 → 分配为 Humongous     │
└───────────────────────────────────────────┘
```

## 3.5 空间分配担保（Space Allocation Guarantee）

```
Minor GC 前的检查:

1. Minor GC 前，检查老年代最大可用连续空间
2. 是否大于新生代所有对象总空间?
   ┌─── Yes → 安全，直接 Minor GC
   │
   └─── No → 检查是否允许担保失败?
            (-XX:-HandlePromotionFailure, JDK 6 update 24 后废弃)
        ┌─── 不允许 → Full GC
        │
        └─── 允许 → 检查老年代最大连续空间
                    是否大于历次晋升到老年代对象的平均大小?
              ┌─── Yes → 尝试 Minor GC（有风险）
              │
              └─── No → Full GC

JDK 6 Update 24 之后:
- HandlePromotionFailure 参数不再生效
- 只要老年代连续空间大于新生代对象总大小或历次平均晋升大小
- 就允许 Minor GC（规则简化为: 总是允许尝试）

空间分配担保失败（Promotion Failure）:
- Minor GC 后，存活对象太多，Survivor 放不下
- 需要老年代空间接收
- 如果老年代也放不下 → Full GC
```

# 第四部分 GC Roots 与可达性分析

## 4.1 GC Roots

```
可达性分析（Reachability Analysis）:
- 从 GC Roots 开始，沿引用链向下搜索
- 被搜索到的对象 = 存活
- 搜索不到的对象 = 可回收

GC Roots 包括:
┌────────────────────────────────────────────────────────────────┐
│  1. 虚拟机栈中的局部变量表中的引用                              │
│     (方法参数、方法内局部变量)                                   │
│     → 这是最大的 GC Roots 来源                                  │
│                                                                │
│  2. 方法区中类静态变量的引用                                    │
│     (static 变量引用的对象)                                      │
│                                                                │
│  3. 方法区中常量的引用                                          │
│     (final static 常量引用的对象)                               │
│                                                                │
│  4. 本地方法栈中 JNI 引用                                      │
│     (Native 方法中的引用)                                       │
│                                                                │
│  5. Java 虚拟机内部的引用                                      │
│     (基本类型对应的 Class 对象、常驻异常对象、                  │
│      系统类加载器、同步锁 monitor 引用的对象)                   │
│                                                                │
│  6. JMXBean、JVMTI 中注册的引用                                │
│  7. 跨代引用 (RSet/卡表记录的老年代指向新生代的引用)             │
└────────────────────────────────────────────────────────────────┘

图示:

     GC Root            GC Root          GC Root
     (栈帧)             (静态变量)        (常量)
       │                   │                │
       ▼                   ▼                ▼
     ┌───┐               ┌───┐           ┌───┐
     │ A │──────────┐    │ C │           │ D │
     └───┘          │    └───┘           └─┬─┘
       │            │       │               │
       ▼            ▼       ▼               ▼
     ┌───┐        ┌───┐  ┌───┐           ┌───┐
     │ B │        │ E │  │ F │           │ G │ ← 可达
     └───┘        └───┘  └───┘           └───┘
                               ↑
                          ┌───┐
                          │ H │ ← 不可达，将被回收
                          └───┘
```

## 4.2 跨代引用问题

```
问题: 新生代 GC 时，如何知道哪些老年代对象引用了新生代对象?

方案 1: 暴力扫描整个老年代
- 每次 Minor GC 都扫描老年代 → 代价极大 ❌

方案 2: 记忆集（Remembered Set）
- 记录老年代 → 新生代的引用
- 只扫描 RSet 即可 ✅

┌──────────────────────────────────────────────┐
│                  堆内存                       │
│  ┌─────────────┐  ┌─────────────────────┐   │
│  │   新生代     │  │       老年代        │   │
│  │             │  │                     │   │
│  │  ┌───┐     │  │  ┌───┐  ┌───┐     │   │
│  │  │ y1│     │←─┼──│old1│──│old2│     │   │
│  │  └───┘     │  │  └───┘  └───┘     │   │
│  │  ┌───┐     │  │  ┌───┐            │   │
│  │  │ y2│     │←─┼──│old3│            │   │
│  │  └───┘     │  │  └───┘            │   │
│  │             │  │                     │   │
│  └─────────────┘  └─────────────────────┘   │
│                                              │
│  Remembered Set (RSet):                      │
│  ┌───────────────────────────────────┐       │
│  │ y1 ← [old1]                       │       │
│  │ y2 ← [old3]                       │       │
│  │ Minor GC 时只需扫描 RSet 指向的对象 │       │
│  └───────────────────────────────────┘       │
└──────────────────────────────────────────────┘

卡表（Card Table）— RSet 的实现方式:
- 将老年代划分为固定大小的 Card（通常 512 字节）
- 每个 Card 对应卡表中的一个 byte
- 老年代对象写操作引用了新生代 → 标记对应 Card 为 dirty
- Minor GC 时只扫描 dirty Card

写屏障（Write Barrier）:
// 伪代码 — 每次引用类型字段赋值后执行
void oop_field_store(oop* field, oop value) {
    *field = value;            // 先赋值
    // 写后屏障: 检查是否是跨代引用
    if (crosses_generations(field, value)) {
        card_table.mark_dirty(field);
    }
}
```

## 4.3 三色标记算法

```
三色标记（Tri-color Marking）— 并发标记的基础

┌──────────────────────────────────────────────────────────┐
│  白色（White）: 尚未被垃圾收集器访问                       │
│               → GC 开始时所有对象都是白色                  │
│               → GC 结束后仍为白色 = 可回收                 │
│                                                          │
│  灰色（Gray）: 已被访问，但该对象引用的其他对象未全部访问    │
│               → 正在处理中                                │
│                                                          │
│  黑色（Black）: 已被访问，且该对象引用的所有对象都已访问    │
│               → 存活对象，不会被回收                       │
└──────────────────────────────────────────────────────────┘

标记过程:
初始: 所有对象都是白色
  │
  ▼
1. GC Roots → 标记为灰色
  │
  ▼
2. 取一个灰色对象，将其引用的白色对象标记为灰色
   然后自己标记为黑色
  │
  ▼
3. 重复步骤 2，直到没有灰色对象
  │
  ▼
4. 剩下的白色对象 = 可回收

        GC Root
        (灰色)
         │
    ┌────┴────┐
    ▼         ▼
  ┌───┐     ┌───┐
  │ A │     │ B │      A, B: 灰色 → 黑色
  │灰→黑│    │灰→黑│
  └─┬─┘     └───┘
    │
    ▼
  ┌───┐     ┌───┐
  │ C │     │ D │      C: 灰色 → 黑色, D: 白色 → 可回收
  │灰→黑│    │ 白 │
  └───┘     └───┘
```

**并发标记的漏标问题**:

```
并发标记期间，应用线程还在运行，可能修改引用关系:

场景: 漏标（对象被错误回收）

时刻 T1:
    A (黑色) ──→ B (黑色) ──→ C (白色)
                              C 应该被标记（A→B→C 链可达）

时刻 T2 (并发期间):
    A (黑色) ──→ C (新增引用)    ← A 新增了对 C 的引用
    B (黑色)     (断开引用)       ← B 断开了对 C 的引用

    A (黑) ──→ C (白)            ← C 被漏标了！
    B (黑)     (C 变成不可达?)

结果: C 实际上被 A 引用（存活），但被错误回收 → 程序崩溃

漏标的两个必要条件:
1. 黑色对象新增了到白色对象的引用
2. 灰色对象断开了到白色对象的引用（或该引用被删除）

解决方案:
┌───────────────────────────────────────────────────────┐
│  CMS / G1: 增量更新（Incremental Update）              │
│  → 黑色对象新增引用白色对象时，把黑色对象变回灰色       │
│  → 重新标记阶段（Remark）再扫描一遍                    │
│  → 写后屏障                                            │
│                                                       │
│  G1 (实际使用): SATB（Snapshot At The Beginning）      │
│  → 在并发标记开始时拍快照                              │
│  → 并发期间引用消失的对象也视为存活                     │
│  → 写前屏障: 记录原引用到 SATB 队列                    │
│  → 会产生浮动垃圾（下次 GC 回收）                      │
│                                                       │
│  ZGC / Shenandoah: 读屏障                              │
│  → 读白色对象时发现不可达 → 需要进一步处理              │
│  → 更精确但开销更大                                    │
└───────────────────────────────────────────────────────┘
```

# 第五部分 安全点与安全区域

## 5.1 为什么需要安全点（Safepoint）

```
GC 需要暂停所有应用线程（STW, Stop-The-World）
但不能在任意位置暂停 — 需要在"安全点"暂停

为什么不能在任意位置暂停?
1. GC Roots 可能不一致（栈帧引用关系不完整）
2. 对象引用关系可能处于中间状态
3. 指令可能正在执行中间操作

安全点 = 程序执行到某个位置时，所有 GC Roots 状态确定
       → 可以安全地暂停并进行 GC
```

## 5.2 安全点的选择

```
安全点的位置选择原则:
- "是否具有让程序长时间执行的特征" → 指令序列复用（Osr）
- 通常是: 方法调用、循环跳转、异常跳转等

HotSpot 采用:
- 抢占式（Preemptive Suspension）: JDK 5 之前
  → GC 时强制暂停所有线程
- 主动式（Voluntary Suspension）: JDK 5 之后
  → 每个线程主动检查是否需要 GC

主动检查机制:
- JVM 在安全点位置插入一个"轮询标记"（Poll Page）
- 线程执行到安全点时检查轮询标记
- 如果标记为"需要 GC"，线程自己挂起

┌──────────────────────────────────────────────┐
│  Thread 执行流                                │
│                                              │
│  指令1  ──→ 指令2 ──→ [安全点] ──→ 指令3     │
│                              │                │
│                              ▼                │
│                        ┌──────────┐           │
│                        │ 检查 Poll │          │
│                        │  Page    │           │
│                        └────┬─────┘          │
│                             │                 │
│                    ┌────────┴────────┐        │
│                    │                 │        │
│              不需要GC            需要GC        │
│                    │                 │        │
│                    ▼                 ▼        │
│              继续执行          挂起等待        │
│                                  GC 完成      │
└──────────────────────────────────────────────┘
```

## 5.3 安全区域（Safe Region）

```
问题: 线程处于 Sleep 或 Blocked 状态时，无法主动检查安全点
      → 会长时间阻塞 GC

解决: 安全区域

安全区域 = 在一段代码片段中，引用关系不会发生变化
         → 在这个区域内任何地方开始 GC 都是安全的

┌──────────────────────────────────────────────────┐
│  Thread 状态与安全机制                             │
│                                                  │
│  Running → 安全点 (Safepoint)                     │
│           主动检查 Poll Page                      │
│                                                  │
│  Blocked / Sleeping → 安全区域 (Safe Region)     │
│           进入安全区域时，标记自己                 │
│           GC 时不需要等待这些线程                  │
│           离开安全区域时，检查 GC 是否完成         │
│           如果 GC 未完成，等待                    │
└──────────────────────────────────────────────────┘

典型场景:
- Thread.sleep()
- Object.wait()
- IO 阻塞（Socket.read()）
-JNI 调用中的 Native 代码
```

## 5.4 安全点与 GC 停顿的关系

```
STW 时间 = 所有线程到达安全点的时间 + GC 执行时间

问题: "安全点偏差"（Safepoint Bias）
- 大循环中没有安全点 → 其他线程等待时间过长
- 典型案例: 大数组遍历的 int 循环

// JDK 8 的安全点问题
// -XX:+SafepointTimeout 可以打印等待超时
for (int i = 0; i < Integer.MAX_VALUE; i++) {
    // 这个循环没有方法调用，没有安全点
    // 其他线程如果要 GC，必须等这个循环结束！
    count += i;
}

// 解决方案
// 1. 使用 long 循环代替 int 循环（HotSpot 在 long 循环中插入了安全点检查）
// 2. JDK 10+: -XX:+UseCountedLoopSafepoints 在计数循环中生成安全点
```

# 第六部分 四种引用类型

## 6.1 四种引用

```
┌────────────────────────────────────────────────────────────────┐
│  引用类型   │  回收时机              │  应用场景                  │
├────────────┼───────────────────────┼───────────────────────────┤
│  强引用     │  永不回收（除非置null）│  普通对象引用               │
│  (Strong)  │  OOM 也不回收          │  Object obj = new Object()│
├────────────┼───────────────────────┼───────────────────────────┤
│  软引用     │  内存不足时回收        │  内存敏感的缓存             │
│  (Soft)    │  GC 后内存仍不足才回收  │  SoftReference< byte[] >   │
├────────────┼───────────────────────┼───────────────────────────┤
│  弱引用     │  下一次 GC 就回收      │  弱缓存、ThreadLocal        │
│  (Weak)    │  不管内存是否充足       │  WeakReference< Object >   │
├────────────┼───────────────────────┼───────────────────────────┤
│  虚引用     │  随时回收              │  跟踪对象被 GC 的过程       │
│  (Phantom) │  不影响对象生命周期     │  堆外内存释放（DirectByteBuffer）│
└────────────────────────────────────────────────────────────────┘
```

## 6.2 软引用（Soft Reference）

```java
// 软引用 — 内存敏感的缓存
SoftReference<byte[]> cacheRef = new SoftReference<>(new byte[1024 * 1024]);

byte[] data = cacheRef.get();
if (data == null) {
    // 被回收了，重新创建
    data = new byte[1024 * 1024];
    cacheRef = new SoftReference<>(data);
}

// GC 行为:
// 1. 每次 Full GC 前检查软引用
// 2. 如果堆内存不足，回收软引用指向的对象
// 3. -XX:SoftRefLRUPolicyMSPerMB=1000
//    每MB空闲堆空间允许软引用存活 1000ms
//    （JDK 8 参数，控制软引用存活时间）

// 应用场景:
// - 图片缓存（Android 开发常用）
// - 大对象缓存（内存充足时保留，不足时自动释放）
```

## 6.3 弱引用（Weak Reference）

```java
// 弱引用 — 下次 GC 就回收
WeakReference<Object> weakRef = new WeakReference<>(new Object());

// WeakHashMap — Key 是弱引用
WeakHashMap<Object, String> map = new WeakHashMap<>();
Object key = new Object();
map.put(key, "value");
key = null;  // 释放强引用
System.gc(); // 触发 GC
// map 中 key 对应的 Entry 会被自动移除

// 应用场景:
// - ThreadLocal 的 Entry（继承 WeakReference）
// - 防止内存泄漏的缓存
// - 监听器/观察者（防止对象无法回收）

// ThreadLocal 源码:
static class Entry extends WeakReference<ThreadLocal<?>> {
    Object value;
    Entry(ThreadLocal<?> k, Object v) {
        super(k);  // Key 是弱引用
        value = v;  // Value 是强引用！→ 内存泄漏风险
    }
}
// ThreadLocal 内存泄漏: Key 被回收但 Value 还在
// 解决: 使用后 remove()
```

## 6.4 虚引用（Phantom Reference）

```java
// 虚引用 — 最弱的引用，不能通过 get() 获取对象
ReferenceQueue<byte[]> queue = new ReferenceQueue<>();
PhantomReference<byte[]> phantomRef = new PhantomReference<>(new byte[1024], queue);

phantomRef.get();  // 永远返回 null！

// 必须配合 ReferenceQueue 使用
// 当对象被回收时，虚引用会被放入队列
// 可以在队列中检测到对象被回收

// 应用场景: 堆外内存释放
// DirectByteBuffer 使用 Cleaner（虚引用的变体）释放堆外内存
public class DirectByteBuffer extends MappedByteBuffer {
    private final Cleaner cleaner;  // 基于 PhantomReference

    // 当 DirectByteBuffer 被 GC 回收时
    // Cleaner 会被放入 ReferenceQueue
    // Cleaner 的 thunk 会调用 Unsafe.freeMemory() 释放堆外内存
}

// JDK 9+ Cleaner API
Cleaner cleaner = Cleaner.create();
cleaner.register(object, () -> {
    // object 被 GC 回收时执行
    System.out.println("Object cleaned up");
});
```

## 6.5 引用队列（Reference Queue）

```
软引用、弱引用、虚引用都可以配合引用队列使用:

对象创建 → 被引用 → GC 检测到可回收
                      │
                      ▼
              ┌───────────────┐
              │  Reference     │
              │  Queue         │
              └───────┬───────┘
                      │
                      ▼
            引用对象被放入队列
            应用程序可以从队列中取出
            执行清理操作

// 伪代码流程
SoftReference<Object> ref = new SoftReference<>(obj, queue);
// ... GC 发生 ...
// ref 指向的对象被回收
// ref 被放入 queue
Reference<?> polled = queue.poll();
if (polled != null) {
    // 执行清理逻辑
}
```

# 第七部分 垃圾收集算法

## 7.1 标记-清除算法（Mark-Sweep）

```
算法: 先标记所有需要回收的对象，再统一清除

GC 前:
┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
│A │B │C │D │E │F │G │H │I │J │
│活│死│活│死│死│活│死│活│死│活│
└──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘

标记阶段: 标记 B, D, E, G, I 为可回收

清除阶段:
┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
│A │  │C │  │  │F │  │H │  │J │
│活│空│活│空│空│活│空│活│空│活│
└──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
  ↑      ↑   ↑      ↑      ↑
  碎片   碎片 碎片   碎片   碎片

优点:
- 简单，不需要移动对象
- 适合老年代（对象存活率高）

缺点:
- 效率低（标记和清除都要遍历整个堆）
- 内存碎片（清除后空间不连续）
- 分配大对象时找不到连续空间 → 提前 Full GC

适用: CMS 的老年代回收
```

## 7.2 标记-复制算法（Mark-Copy）

```
算法: 将内存分为两块，每次只用一块，GC 时把存活对象复制到另一块

GC 前:
┌──────────────┬──────────────┐
│   From 区     │    To 区     │
│ [A][B][C][D]  │              │
│  活  死 活 死  │   (空)       │
└──────────────┴──────────────┘

复制阶段: 把存活对象 A, C 复制到 To 区
┌──────────────┬──────────────┐
│   From 区     │    To 区     │
│ [A][B][C][D]  │   [A][C]     │
│  活  死 活 死  │   复制过来    │
└──────────────┴──────────────┘

清空阶段: 清空 From 区
┌──────────────┬──────────────┐
│              │    To 区     │
│   (清空)      │   [A][C]     │
│              │              │
└──────────────┴──────────────┘

交换: From ↔ To
┌──────────────┬──────────────┐
│   From 区     │              │
│   [A][C]      │   (To 空了)  │
│              │              │
└──────────────┴──────────────┘

优点:
- 无碎片（复制后内存连续）
- 高效（存活对象少时只需要少量复制）
- 分配快（指针碰撞）

缺点:
- 浪费一半空间（空间利用率 50%）
- 存活对象多时复制开销大

优化: 新生代用 Eden + 2 个 Survivor
- 空间利用率: 90%（Eden 80% + Survivor 10%，浪费 10%）
- 因为新生代 98% 对象都死了，复制开销很小

适用: 新生代（Serial, ParNew, Parallel Scavenge, G1）
```

## 7.3 标记-整理算法（Mark-Compact）

```
算法: 标记存活对象 → 移动到内存一端 → 清理边界外的空间

GC 前:
┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
│A │B │C │D │E │F │G │H │I │J │
│活│死│活│死│死│活│死│活│死│活│
└──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘

标记阶段: 标记 A, C, F, H, J 为存活

整理阶段: 把存活对象向一端移动
┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
│A │C │F │H │J │  │  │  │  │  │
│活│活│活│活│活│空│空│空│空│空│
└──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘

优点:
- 无碎片
- 不浪费空间

缺点:
- 移动对象开销大（需要更新所有引用）
- STW 时间长（移动期间必须暂停应用）

适用: 老年代（Serial Old, Parallel Old）

// HotSpot 的实现: 移动对象时需要更新所有指向该对象的引用
// 这就是为什么标记-整理需要更长的 STW 时间
```

## 7.4 分代收集算法

```
根据对象存活周期将堆分为新生代和老年代
不同代使用不同的算法:

┌────────────────────────────────────────────┐
│                 堆内存                     │
│  ┌─────────────────┬─────────────────┐    │
│  │    新生代        │     老年代      │    │
│  │  (对象存活率低)   │  (对象存活率高)  │    │
│  │                 │                 │    │
│  │  复制算法        │  标记-清除      │    │
│  │  (少量复制)      │  或标记-整理     │    │
│  │                 │  (少量碎片/移动) │    │
│  │  Minor GC       │  Major GC       │    │
│  │  频繁但快        │  不频繁但慢      │    │
│  └─────────────────┴─────────────────┘    │
│                                          │
│  CMS 的老年代: 标记-清除（碎片化）         │
│  G1 的所有区域: 标记-清除 + 复制（Region间复制）│
└────────────────────────────────────────────┘

跨代引用处理: Remembered Set + Card Table
- 新生代 GC 时不需要扫描整个老年代
- 只需要扫描 RSet 中记录的 Card
```

# 第八部分 Minor GC / Major GC / Full GC

## 8.1 三种 GC 的区分

```
┌──────────────────────────────────────────────────────────────────┐
│  Minor GC (Young GC)                                              │
│  ──────────────────────                                           │
│  回收区域: 新生代（Eden + Survivor）                                │
│  触发条件: Eden 区满                                               │
│  频率: 频繁                                                        │
│  速度: 快（复制算法，存活对象少）                                    │
│  STW: 短（几毫秒 ~ 几十毫秒）                                       │
│  是否 STW: 是                                                      │
├──────────────────────────────────────────────────────────────────┤
│  Major GC                                                         │
│  ──────────────────────                                           │
│  回收区域: 老年代                                                   │
│  触发条件: 老年代空间不足                                           │
│  频率: 不频繁                                                      │
│  速度: 较慢                                                        │
│  STW: 较长                                                        │
│  注意: Major GC 通常伴随至少一次 Minor GC（非绝对）                 │
├──────────────────────────────────────────────────────────────────┤
│  Full GC                                                          │
│  ──────────────────────                                           │
│  回收区域: 整个堆（新生代 + 老年代）+ 方法区                         │
│  触发条件:                                                         │
│    1. 调用 System.gc()                                            │
│    2. 老年代空间不足                                               │
│    3. 方法区/元空间不足                                             │
│    4. 空间分配担保失败                                              │
│    5. CMS Concurrent Mode Failure                                 │
│    6. CMS 浮动垃圾过多，老年代空间不够                               │
│  频率: 很低                                                        │
│  速度: 最慢                                                        │
│  STW: 最长（几百毫秒 ~ 几秒）                                       │
│  是否 STW: 是                                                      │
└──────────────────────────────────────────────────────────────────┘

关键区别:
- Minor GC 只收集新生代 → 总是 STW
- Major GC 只收集老年代 → 不是所有收集器都支持（CMS 可以单独收集老年代）
- Full GC 收集整个堆 → 总是 STW
- "Major GC" 在很多语境下等价于 "Full GC"（不是所有收集器都明确区分）
```

## 8.2 Minor GC 过程详解

```
Minor GC 完整流程:

Step 1: Eden 区满
┌─────────────────────────────────────────┐
│            新生代                        │
│  ┌──────────┬─────┬─────┐               │
│  │   Eden   │ S0  │ S1  │   老年代      │
│  │ [满]     │[E,F]│     │  [old1,old2] │
│  └──────────┴─────┴─────┘               │
└─────────────────────────────────────────┘

Step 2: 检查空间分配担保
- 老年代可用空间 > 新生代所有对象大小?
- 如果是 → 安全进行 Minor GC
- 如果否 → 检查是否允许担保失败
  - 允许 → 尝试 Minor GC（可能 Full GC）
  - 不允许 → 直接 Full GC

Step 3: 标记 + 复制
- 从 GC Roots + RSet 开始标记新生代存活对象
- 将存活对象从 Eden + S0 复制到 S1
- 年龄 +1

Step 4: 复制完成
┌─────────────────────────────────────────┐
│            新生代                        │
│  ┌──────────┬─────┬─────┐               │
│  │   Eden   │ S0  │ S1  │   老年代      │
│  │ [清空]    │[清空]│[E,F]│  [old1,old2] │
│  │          │     │+age│               │
│  └──────────┴─────┴─────┘               │
└─────────────────────────────────────────┘

Step 5: 检查晋升
- 年龄 >= MaxTenuringThreshold? → 晋升到老年代
- Survivor 空间不够? → 通过担保机制进老年代
- 动态年龄判断? → 满足条件的对象晋升

Step 6: GC 完成
┌─────────────────────────────────────────┐
│            新生代                        │
│  ┌──────────┬─────┬─────┐               │
│  │   Eden   │ S0  │ S1  │   老年代      │
│  │ [可分配]  │     │[F]  │[old1,old2,E]│
│  └──────────┴─────┴─────┘               │
│  (E 晋升到老年代, F 留在 S1)              │
└─────────────────────────────────────────┘

注: S0 和 S1 角色互换，下次 GC 时 S1 → S0
```

## 8.3 Full GC 触发条件详解

```
1. System.gc() 或 Runtime.getRuntime().gc()
   - 建议 JVM 进行 Full GC，但不保证立即执行
   - -XX:+DisableExplicitGC 可以禁用（不推荐，影响 NIO DirectByteBuffer 回收）
   - -XX:+ExplicitGCInvokesConcurrent (CMS/G1: 用并发方式处理)

2. 老年代空间不足
   - 大对象直接进老年代但空间不够
   - Minor GC 后存活对象晋升老年代但空间不够
   - 担保失败

3. 元空间不足
   - -XX:MaxMetaspaceSize 设置过小
   - 动态加载大量类（CGLib、JSP 编译）

4. CMS Concurrent Mode Failure
   - CMS 并发回收期间老年代空间不够
   - 退化为 Serial Old 单线程 Full GC
   - STW 时间极长（可能几秒）

5. 空间分配担保失败
   - Minor GC 前，老年代可用空间 < 新生代对象总大小
   - 且不允许担保失败 → Full GC

6. G1 的 Humongous 分配失败
   - 大对象无法分配连续的 Humongous Region

避免 Full GC 的策略:
- 合理设置堆大小
- 设置 SurvivorRatio 和 MaxTenuringThreshold
- 避免 System.gc()（或用 -XX:+DisableExplicitGC）
- CMS: 调低 CMSInitiatingOccupancyFraction
- G1: 调低 InitiatingHeapOccupancyPercent
```

# 第九部分 Serial / Parallel GC

## 9.1 Serial GC

```
Serial GC (-XX:+UseSerialGC)
- 单线程收集器
- GC 时暂停所有应用线程
- 新生代: Serial (复制算法)
- 老年代: Serial Old (标记-整理算法)

适用场景:
- 客户端模式（桌面应用）
- 小堆（< 100MB）
- 单核 CPU

优点: 简单高效（无多线程通信开销）
缺点: STW 时间长

┌──────────────────────────────────────┐
│  应用线程  ──→ 执行 ──→ 执行 ──→ ... │
│                                      │
│  GC 线程                              │
│         STW ▓▓▓▓▓▓▓▓▓▓▓▓▓           │
│         ↑ 单线程执行                  │
│                                      │
│  应用线程  ──→ 执行 ──→ 执行          │
└──────────────────────────────────────┘

Serial GC 是 JDK 8 在以下情况下的默认:
- -XX:+UseSerialGC 显式指定
- 单核 CPU + 小内存
```

## 9.2 Parallel GC（Parallel Scavenge + Parallel Old）

```
Parallel GC (-XX:+UseParallelGC, JDK 8 默认)
- 多线程收集器
- 注重吞吐量（Throughput）
- 新生代: Parallel Scavenge (复制算法, 多线程)
- 老年代: Parallel Old (标记-整理算法, 多线程)

核心参数:
- -XX:ParallelGCThreads=N     // GC 线程数（默认 = CPU 核数）
- -XX:MaxGCPauseMillis=200    // 最大 GC 停顿目标（毫秒）
- -XX:GCTimeRatio=99          // GC 时间占比目标（1/(1+99) = 1%）
- -XX:+UseAdaptiveSizePolicy  // 自适应调整新生代大小

适用场景:
- 后台计算型应用
- 批处理任务
- 大数据分析

┌──────────────────────────────────────┐
│  应用线程  ──→ 执行 ──→ 执行 ──→ ... │
│                                      │
│  GC 线程    ┌──┬──┬──┐               │
│  (多线程)   │T1│T2│T3│ STW           │
│             └──┴──┴──┘ ▓▓▓▓▓        │
│             并行标记+复制             │
│                                      │
│  应用线程  ──→ 执行 ──→ 执行          │
└──────────────────────────────────────┘

vs ParNew GC:
- ParNew (-XX:+UseParNewGC) 也是多线程新生代收集器
- 区别: ParNew 可与 CMS 配合，Parallel Scavenge 不能
- JDK 14 移除了 CMS + ParNew 的组合
```

## 9.3 Parallel GC 的自适应调整

```
-XX:+UseAdaptiveSizePolicy (默认开启)

JVM 根据运行数据自动调整:
1. 新生代大小
2. Eden 和 Survivor 的比例
3. 晋升年龄阈值
4. 老年代大小

目标: 在 MaxGCPauseMillis 和 GCTimeRatio 约束下
      自动找到最优的内存布局

示例:
- 如果 GC 停顿超过 200ms → 缩小新生代
- 如果 GC 时间占比超过 1% → 放大新生代
- 如果 Survivor 太频繁溢出 → 调大 Survivor

注意:
- -XX:+UseAdaptiveSizePolicy 与 -XX:SurvivorRatio 可能冲突
- 如果手动设置 SurvivorRatio，建议关闭自适应
- -XX:-UseAdaptiveSizePolicy
```

# 第十部分 CMS GC 四阶段详解

## 10.1 CMS 概述

```
CMS (Concurrent Mark Sweep) — 以获取最短回收停顿时间为目标的收集器

-XX:+UseConcMarkSweepGC  // JDK 8
// JDK 9 开始废弃，JDK 14 移除

特点:
1. 基于 标记-清除 算法（老年代）
2. 并发标记 + 并发清除（大部分时间与应用线程并发执行）
3. 四个阶段，其中两个 STW，两个并发
4. 适合对响应时间敏感的应用（Web 服务器）

┌──────────────────────────────────────────────────────┐
│              CMS 四阶段                               │
│                                                      │
│  1. 初始标记 (Initial Mark)    ── STW              │
│     只标记 GC Roots 直接引用的对象                     │
│     速度极快（毫秒级）                                │
│                                                      │
│  2. 并发标记 (Concurrent Mark) ── 并发              │
│     从初始标记的对象开始，遍历整个对象图               │
│     与应用线程并发执行（可能很长）                      │
│     不需要暂停应用                                    │
│                                                      │
│  3. 重新标记 (Remark)          ── STW              │
│     修正并发标记期间应用线程导致的标记变化             │
│     使用增量更新（Incremental Update）               │
│     速度较快（比初始标记稍慢）                         │
│                                                      │
│  4. 并发清除 (Concurrent Sweep)── 并发              │
│     清除标记为死亡的对象                               │
│     与应用线程并发执行                                 │
│     不需要暂停应用                                    │
└──────────────────────────────────────────────────────┘

时间线:
应用线程 ▓▓▓▓▓ ─ STW ─ ▓▓▓▓▓▓▓▓▓▓▓▓▓▓ ─ STW ─ ▓▓▓▓▓▓▓▓▓▓▓▓▓▓
              初始标记        并发标记      重新标记      并发清除
              (短)           (长,并发)     (短)        (长,并发)

GC 线程                      ────────────────────  ────────────
                            并发标记              并发清除
```

## 10.2 阶段一：初始标记（Initial Mark）

```
初始标记 (Initial Mark) — STW

目标: 标记 GC Roots 能直接关联到的对象

// HotSpot 源码: CMSCollector::checkpointRootsInitialWork()

void checkpointRootsInitialWork() {
    // 1. 使用单线程或多线程标记 GC Roots
    //    -XX:+CMSParallelInitialMarkEnabled (默认开启)
    
    // 2. 只标记直接引用，不递归遍历
    //    例如:
    //    GC Root → A (标记)
    //    A → B → C (不标记 B 和 C，留给并发标记阶段)
    
    // 3. 标记新生代对象引用的老年代对象
    //    通过 Card Table 快速扫描
    //    只扫描 dirty card，不需要扫描整个新生代
    
    // 标记过程中:
    // - 遍历所有线程栈帧中的引用
    // - 遍历全局引用
    // - 遍历 JNI 引用
    // - 遍历 Card Table 中标记为 dirty 的 Card
    //    (老年代引用新生代的记录)
    
    // 结果: 获得初始存活对象集合
}

为什么 STW 时间极短?
- 只标记直接引用，不做深度遍历
- 使用 Card Table 快速定位跨代引用
- 多线程并行（-XX:+CMSParallelInitialMarkEnabled）

典型停顿时间: 几毫秒 ~ 几十毫秒
```

## 10.3 阶段二：并发标记（Concurrent Mark）

```
并发标记 (Concurrent Mark) — 与应用线程并发

目标: 从初始标记的对象开始，深度遍历整个对象引用链

// HotSpot 源码: CMSCollector::markFromRoots()

void markFromRoots() {
    // 1. 创建 CMSCollector 的工作线程
    //    -XX:ConcGCThreads=N (默认 = ParallelGCThreads 的 1/4)
    
    // 2. 从初始标记的对象开始 BFS/DFS 遍历
    //    标记所有可达对象
    
    // 3. 处理三色标记
    //    白色(未访问) → 灰色(已访问但引用未处理完) → 黑色(完成)
    
    // 4. 并发标记期间，应用线程可能修改引用关系
    //    CMS 使用"增量更新"(Incremental Update):
    //    - 写后屏障 (post-write barrier)
    //    - 如果黑色对象新增引用白色对象 → 记录到 MOD-Union Table
    //    - 重新标记阶段处理这些变化
    
    // 5. 预清理（Precleaning）— 可选
    //    -XX:+CMSPrecleaningEnabled (默认开启)
    //    在并发标记后、重新标记前进行一些预处理
    //    减少 Remark 阶段的 STW 时间
    //    扫描 dirty card，提前处理一部分引用变化
}

并发标记的特点:
- 与应用线程同时运行
- 不影响应用吞吐量（但占用 CPU）
- 持续时间可能很长（几秒 ~ 几十秒）
- 期间应用线程继续分配对象
  → 如果分配速度太快，老年代可能在 GC 完成前就满了
  → 触发 Concurrent Mode Failure

并发标记期间的问题:
1. 应用线程修改引用关系 → 增量更新处理
2. 应用线程创建新对象 → 新对象在老年代或新生代
3. 应用线程使对象死亡 → 浮动垃圾（下次 GC 回收）
```

## 10.4 阶段三：重新标记（Remark）

```
重新标记 (Remark) — STW

目标: 修正并发标记期间应用线程导致的标记变化

// HotSpot 源码: CMSCollector::checkpointRootsFinalWork()

void checkpointRootsFinalWork() {
    // 1. 暂停所有应用线程 (STW)
    
    // 2. 处理 MOD-Union Table
    //    并发标记期间黑色对象新增的引用
    //    重新标记这些对象引用的白色对象
    
    // 3. 重新扫描新生代
    //    并发标记期间新生代可能变化很大
    //    需要重新扫描新生代中引用老年代的对象
    //    通过 Card Table dirty card 快速定位
    
    // 4. 处理预清理阶段未完成的标记
    
    // 5. 最终确认所有存活对象
}

为什么需要 Remark?
- 并发标记期间应用线程在运行
- 引用关系可能发生变化:
  a. 黑色对象新增了到白色对象的引用 → 漏标
  b. 灰色对象断开了到白色对象的引用 → 浮动垃圾
- Remark 修正 a 情况（增量更新）

CMS 的增量更新 vs G1 的 SATB:
┌─────────────────────────────────────────────────┐
│  CMS: 增量更新 (Incremental Update)              │
│  - 写后屏障                                      │
│  - 黑色对象新增引用白色 → 把黑色变回灰色           │
│  - Remark 阶段重新扫描这些变灰的对象               │
│  - 需要扫描的内容可能很多                          │
│                                                  │
│  G1: SATB (Snapshot At The Beginning)            │
│  - 写前屏障                                      │
│  - 并发标记开始时拍快照                            │
│  - 引用消失时记录原引用到 SATB 队列               │
│  - Remark 阶段处理 SATB 队列                     │
│  - 更精确，扫描内容更少                            │
│  - 但会产生更多浮动垃圾                            │
└─────────────────────────────────────────────────┘

减少 Remark STW 的优化:
1. -XX:+CMSPrecleaningEnabled
   → 并发标记后预清理，减少 Remark 工作量

2. -XX:+CMSClassUnloadingEnabled
   → 并发标记期间也回收元空间中的无用类

3. -XX:CMSMaxAbortablePrecleanTime=5000
   → 预清理最长等待时间 5s

典型停顿时间: 几十毫秒 ~ 几百毫秒
```

## 10.5 阶段四：并发清除（Concurrent Sweep）

```
并发清除 (Concurrent Sweep) — 与应用线程并发

目标: 清除未被标记（白色）的对象

// HotSpot 源码: CMSCollector::sweep()

void sweep(bool is_alive) {
    // 1. 遍历老年代的所有内存块
    //    分为:
    //    - 完全空闲的块 → 加入空闲列表
    //    - 完全存活的块 → 不处理
    //    - 部分存活的块 → 标记空闲区域，加入空闲列表
    
    // 2. 维护空闲列表（Free List）
    //    CMS 的老年代使用空闲列表管理内存
    //    新对象分配时从空闲列表中找到合适的块
    //    (不能使用指针碰撞，因为有碎片)
    
    // 3. 并发清除期间应用线程可能产生新对象
    //    这些新对象在并发标记时没有被标记
    //    但它们是存活的，不会被误清除
    //    (因为并发清除只清除"确定死亡"的对象)
}

并发清除的问题:
1. 浮动垃圾（Floating Garbage）
   - 并发标记期间产生的垃圾
   - 本轮 CMS 无法回收
   - 只能等下一轮 CMS

2. 空间碎片
   - 标记-清除算法不移动对象
   - 清除后空间不连续
   - 大对象可能分配失败（即使总空间足够）
   - 需要进行碎片整理（Compact）

3. Concurrent Mode Failure
   - 并发清除期间应用线程继续分配
   - 如果老年代空间不足
   - → 退化为 Serial Old 单线程 Full GC
   - → STW 时间极长（可能几秒 ~ 几十秒）
```

## 10.6 CMS 的内存分配方式

```
CMS 老年代使用 空闲列表（Free List）+ CAS 分配

普通 GC (Parallel Old): 指针碰撞
┌────────────────────────────────────┐
│  老年代                             │
│  [存活对象][存活对象] ← pointer    │
│  └──────────────────┘             │
│     已分配区域        分配:        │
│                     pointer +=     │
│                     obj_size       │
│  ┌──────────────────┐              │
│  │    空闲区域       │              │
│  └──────────────────┘              │
└────────────────────────────────────┘
→ 无碎片，分配快，但需要移动对象

CMS: 空闲列表
┌────────────────────────────────────┐
│  老年代                             │
│  [存活] [空] [存活] [空空] [存活]  │
│         ↑           ↑              │
│    Free List: [块1][块2][块3]      │
│                                    │
│  分配: 从 Free List 找到合适大小    │
│        的块 → CAS 占用              │
└────────────────────────────────────┘
→ 有碎片，分配慢，但不需要移动对象
→ 这就是 CMS 标记-清除算法的代价

空闲列表的数据结构:
- 多个链表，按块大小分组
- 例如: 32B链表, 64B链表, 128B链表...
- 分配时快速找到最合适的块
- Best-Fit 分配策略
```

## 10.7 CMS 的 Concurrent Mode Failure

```
Concurrent Mode Failure — CMS 最严重的问题

场景:
1. CMS 正在执行并发标记/并发清除
2. 应用线程需要分配老年代空间（大对象或晋升）
3. 老年代剩余空间不足
4. → CMS 无法完成回收
5. → 退化为 Serial Old 单线程 Full GC
6. → STW 时间极长（可能几秒 ~ 几十秒）

时间线:
应用线程 ▓▓▓▓▓ ─ STW(初始标记) ─ ▓▓▓▓▓▓▓▓▓▓▓▓ ─ STW(Remark) ─ ▓▓▓▓▓▓ ─ !!!
                                                                Concurrent Mode Failure
应用线程          ═════════════════════════════════════════════ STW(Serial Old Full GC)
                                                          ↑
                                                     老年代空间不足
                                                     CMS 来不及回收

如何避免 Concurrent Mode Failure:
1. -XX:CMSInitiatingOccupancyFraction=70
   → 老年代使用率达到 70% 就开始 CMS GC
   → 留出 30% 空间给并发期间分配
   → 默认值: JDK 5 是 68%, JDK 6+ 是 92%（自适应）

2. -XX:+UseCMSInitiatingOccupancyOnly
   → 禁止 JVM 自适应调整触发阈值
   → 使用 CMSInitiatingOccupancyFraction 的固定值

3. -XX:+CMSScavengeBeforeRemark
   → Remark 前先执行一次 Minor GC
   → 减少新生代对老年代的引用
   → 减少 Remark 的工作量

4. 增大老年代大小
   → -XX:NewRatio=1 (老年代:新生代 = 1:1)
   → 或增大整个堆

5. 控制对象分配速率
   → 避免在高峰期大量创建大对象
```

## 10.8 CMS 的碎片整理

```
CMS 的标记-清除算法导致碎片化

碎片整理触发条件:
1. 没有足够大的连续空间分配大对象
2. -XX:+UseCMSCompactAtFullCollection (默认开启)
   → Full GC 时进行碎片整理
3. -XX:CMSFullGCsBeforeCompaction=0
   → 多少次 Full GC 后进行碎片整理（0 = 每次）
   → 默认值: 0（JDK 8）

碎片整理的问题:
- 碎片整理需要移动对象 → STW
- 无法并发执行
- STW 时间可能很长

这就是 CMS 的矛盾:
- 设计目标是低延迟（并发 GC）
- 但碎片化最终导致 STW Full GC
- STW 时间可能比 Parallel GC 还长

解决方案:
- 定期触发 Full GC + 碎片整理
- 或者升级到 G1（G1 本身就是标记-清除 + 复制，无碎片问题）
```

# 第十一部分 CMS 缺陷与调优

## 11.1 CMS 的四大缺陷

```
┌──────────────────────────────────────────────────────────────────┐
│  缺陷 1: 浮动垃圾（Floating Garbage）                              │
│  ───────────────────────────────                                   │
│  并发标记期间，应用线程可能使某些对象变为垃圾                        │
│  但这些对象在标记阶段已经被标记为存活                               │
│  → 本轮 CMS 无法回收                                              │
│  → 只能等下一轮 CMS                                              │
│                                                                  │
│  示例:                                                            │
│  并发标记时: A→B→C (B, C 被标记为存活)                             │
│  并发清除时: A 断开了对 B 的引用 (B, C 变成垃圾)                   │
│  → B, C 已被标记为存活，本轮不回收                                 │
│  → 下轮 CMS 才能回收（可能几分钟后）                               │
├──────────────────────────────────────────────────────────────────┤
│  缺陷 2: 空间碎片（Fragmentation）                                │
│  ───────────────────────────────                                   │
│  标记-清除算法不移动对象                                           │
│  清除后的空间不连续                                                │
│  → 大对象可能分配失败（即使总空间足够）                             │
│  → 触发 Full GC + 碎片整理                                        │
│  → STW 时间极长                                                   │
├──────────────────────────────────────────────────────────────────┤
│  缺陷 3: Concurrent Mode Failure                                  │
│  ───────────────────────────────                                   │
│  并发回收期间老年代空间不足                                         │
│  → 退化为 Serial Old 单线程 Full GC                               │
│  → STW 时间可能几秒 ~ 几十秒                                      │
│  → 这是最严重的问题                                               │
├──────────────────────────────────────────────────────────────────┤
│  缺陷 4: 对 CPU 资源敏感                                          │
│  ───────────────────────────────                                   │
│  并发标记和并发清除占用 CPU                                        │
│  → 默认占用 1/4 CPU (-XX:ConcGCThreads)                           │
│  → 在 CPU 核心数少的服务器上影响吞吐量                              │
│  → CPU < 2 核时不建议使用 CMS                                     │
└──────────────────────────────────────────────────────────────────┘
```

## 11.2 CMS 关键调优参数

## 11.3 CMS 调优实战

```
场景: Web 服务，堆 4G，使用 CMS，但偶发 STW 5秒+

诊断步骤:

1. 查看 GC 日志
   -Xloggc:/var/log/gc.log -XX:+PrintGCDetails -XX:+PrintGCDateStamps

2. 识别问题: Concurrent Mode Failure
   日志中会出现: "concurrent mode failure" 或 "promotion failed"

3. 分析原因:
   - 老年代空间不足
   - 对象晋升速度过快

   # 让对象在 Survivor 中多存活几轮再晋升

   -XX:+CMSScavengeBeforeRemark

5. 验证: 观察 GC 日志中的停顿时间变化

推荐 CMS 配置（4G 堆）:
-XX:+UseConcMarkSweepGC
-XX:+UseCMSInitiatingOccupancyOnly
-XX:CMSInitiatingOccupancyFraction=70
-XX:+CMSScavengeBeforeRemark
-XX:+CMSClassUnloadingEnabled
-XX:SurvivorRatio=6
-XX:MaxTenuringThreshold=15
-XX:NewRatio=2
-XX:ParallelGCThreads=8
-XX:ConcGCThreads=2
```

# 第十二部分 G1 GC 架构设计

## 12.1 G1 概述

```
G1 (Garbage First) — 面向服务端应用的垃圾收集器

-XX:+UseG1GC  // JDK 9+ 默认

设计目标:
1. 停顿时间可预测（-XX:MaxGCPauseMillis=200）
2. 适合大堆（6GB+）
3. 无碎片（使用复制算法）
4. 整体上"标记-清除"+ 局部"复制"算法

G1 vs CMS:
┌────────────┬─────────────────────┬─────────────────────┐
│            │  CMS                │  G1                  │
├────────────┼─────────────────────┼─────────────────────┤
│  堆布局    │  固定新生代/老年代   │  Region（灵活）      │
│  算法      │  标记-清除           │  标记-复制（Region间）│
│  碎片      │  有碎片             │  无碎片               │
│  停顿      │  不可预测           │  可设置目标停顿       │
│  大对象    │  直接进老年代       │  Humongous Region     │
│  回收策略  │  整个老年代          │  回收价值最高的Region │
│  适用堆大小│  < 6GB             │  6GB+                │
│  JDK 版本 │  8 (废弃)          │  9+ (默认)           │
└────────────┴─────────────────────┴─────────────────────┘
```

## 12.2 Region 内存布局

```
G1 将堆划分为多个大小相等的 Region

┌────┬────┬────┬────┬────┬────┬────┬────┐
│ E  │ E  │ S  │ O  │ O  │ H  │ H  │ H  │
├────┼────┼────┼────┼────┼────┼────┼────┤
│ O  │ E  │ O  │ O  │ E  │ O  │ -  │ O  │
├────┼────┼────┼────┼────┼────┼────┼────┤
│ E  │ O  │ O  │ E  │ O  │ H  │ O  │ E  │
├────┼────┼────┼────┼────┼────┼────┼────┤
│ O  │ O  │ E  │ -  │ O  │ O  │ E  │ O  │
└────┴────┴────┴────┴────┴────┴────┴────┘

E = Eden Region (新生代)
S = Survivor Region (新生代)
O = Old Region (老年代)
H = Humongous Region (大对象)
- = Free Region (空闲)

Region 大小:
- 1MB ~ 32MB (2 的幂)
- -XX:G1HeapRegionSize=16m
- 默认: 堆大小 / 2048，向下取最近的 2 的幂
  - 4G 堆 → 2MB Region → 2048 个 Region
  - 16G 堆 → 8MB Region → 2048 个 Region
  - 32G 堆 → 16MB Region → 2048 个 Region

Region 的特点:
1. 每个 Region 可以动态切换角色
   Eden → Survivor → Old（通过复制）
2. 新生代和老年代不是物理连续的
3. 新生代大小是动态调整的（不需要 -Xmn）
4. 大于 Region 一半的对象 → Humongous
5. Humongous 可以跨多个连续 Region

Region 角色转换:
┌──────┐    GC     ┌──────┐    GC     ┌──────┐
│ Eden │ ───────→ │ Surv │ ───────→ │ Old  │
└──────┘   复制    └──────┘   晋升    └──────┘
                        ↑
                    Eden + Surv
                    中的存活对象复制过来
```

## 12.3 Remembered Set（RSet）

```
G1 的 RSet — 记录"谁引用了我"

每个 Region 都有一个 RSet
RSet 记录: 其他 Region 中指向本 Region 的引用

┌─────────────┐          ┌─────────────┐
│  Region A   │          │  Region B   │
│  (Old)      │          │  (Eden)     │
│             │  obj.x → │             │
│  obj ───────┼────────→│  x          │
│             │          │             │
│  RSet(A):   │          │  RSet(B):   │
│  { }        │          │  {A}        │ ← 记录 Region A 引用了我
│  (没人引用A) │          │             │
└─────────────┘          └─────────────┘

为什么需要 RSet?
- GC 时只扫描某个 Region
- 需要知道哪些其他 Region 引用了这个 Region 的对象
- 不需要扫描整个堆 → 减少 GC 时间

RSet 的实现: 卡表（Card Table）
- 每个 Region 内部划分为多个 Card（512 字节）
- 每个 Card 对应卡表中的一个 byte
- 写引用时，如果跨 Region → 标记目标 Region 的 RSet 中的 Card 为 dirty

写屏障（Write Barrier）:
// 伪代码 — 每次引用类型字段赋值后执行
void post_write_barrier(oop* field, oop value) {
    Region* src_region = get_region(field);
    Region* dst_region = get_region(value);
    if (src_region != dst_region) {
        // 跨 Region 引用
        dst_region->rset->add_card(src_region, card_of(field));
    }
}

RSet 的代价:
1. 内存开销: RSet 通常占堆的 1% ~ 20%
   - -XX:G1RSetRegionEntries 控制每个 Region 的 RSet 槽位数
   - -XX:G1RSetSparseRegionEntries 控制稀疏 RSet 槽位数
2. 写屏障开销: 每次引用赋值都要检查
3. RSet 精度: 通常使用 "Card 级别"（512 字节）
```

## 12.4 Collection Set（CSet）

```
CSet = Collection Set = 本次 GC 要回收的 Region 集合

G1 的核心思想: "Garbage First"
- 选择回收价值最高的 Region
- 回收价值 = 垃圾占比高 + 回收时间短

CSet 选择算法:
1. 遍历所有 Region
2. 计算每个 Region 的"回收效率"
   回收效率 = 垃圾大小 / 预计回收时间
3. 按回收效率排序
4. 选择 Region 直到预计总时间达到 MaxGCPauseMillis

┌──────────────────────────────────────────────────────┐
│  Region 回收效率排序                                 │
│                                                      │
│  Region 5: 90% 垃圾, 预计 5ms   ← 选择 ✓             │
│  Region 12: 85% 垃圾, 预计 6ms  ← 选择 ✓             │
│  Region 3: 70% 垃圾, 预计 8ms   ← 选择 ✓             │
│  Region 8: 50% 垃圾, 预计 10ms  ← 选择 ✓             │
│  Region 1: 30% 垃圾, 预计 12ms  ← 超出时间预算 ✗     │
│  ...                                                 │
│                                                      │
│  目标: MaxGCPauseMillis = 200ms                      │
│  已选: 5+6+8+10 = 29ms < 200ms → 继续选              │
│  29+12 = 41ms < 200ms → 继续...                      │
│  直到累计时间接近 200ms                               │
└──────────────────────────────────────────────────────┘

CSet 的组成:
- Young GC: 所有 Eden + Survivor Region
- Mixed GC: 所有 Young + 部分 Old Region（回收价值最高的）
```

## 12.5 SATB（Snapshot At The Beginning）

```
SATB = Snapshot At The Beginning

G1 使用 SATB 解决并发标记的漏标问题

SATB 的核心思想:
- 在并发标记开始时，记录一个"存活对象快照"
- 快照 = 并发标记开始时所有可达对象
- 并发期间，如果引用被删除 → 原引用对象仍视为存活

实现: 写前屏障（Pre-Write Barrier）

// 伪代码 — 引用被覆盖前执行
void pre_write_barrier(oop* field, oop old_value) {
    // 并发标记期间才启用
    if (concurrent_marking) {
        // 记录旧的引用到 SATB 队列
        satb_queue.push(old_value);
    }
    // 然后执行正常赋值
    *field = new_value;
}

SATB 的工作过程:

并发标记开始时:
    A(黑) ──→ B(灰) ──→ C(白)
    快照: {A, B, C} 都视为存活

并发期间应用线程执行:
    A ──→ B (断开引用)
    A ──→ C (新增引用)

    SATB 队列记录: B 的旧引用（B 被断开了 → B 仍视为存活）

并发标记结束时:
    A(黑) ──→ C(黑)     ← A 新增了对 C 的引用
    B(灰)                ← B 被断开了，但 SATB 快照中 B 仍存活
    
    结果: A, B, C 都被标记为存活
    → 不会漏标 C（A 新增引用 C）
    → 但 B 可能已经变成垃圾了 → 浮动垃圾

SATB vs 增量更新:
┌───────────────────────────────────────────────┐
│  SATB (G1)                                    │
│  - 写前屏障                                   │
│  - 记录旧引用（即将被覆盖的）                   │
│  - 快照时刻的存活对象一定不会被漏标             │
│  - 优点: 不需要重新扫描灰色对象                 │
│  - 缺点: 产生更多浮动垃圾                       │
│  - Remark 速度快                               │
│                                               │
│  增量更新 (CMS)                               │
│  - 写后屏障                                   │
│  - 记录新引用（黑色对象新增的）                 │
│  - 黑色对象新增引用 → 变回灰色 → 重新扫描       │
│  - 优点: 浮动垃圾少                             │
│  - 缺点: Remark 需要重新扫描                   │
│  - Remark 速度慢                               │
└───────────────────────────────────────────────┘
```

# 第十三部分 G1 GC 回收过程详解

## 13.1 G1 的 GC 类型

```
G1 有三种 GC 类型:

1. Young GC (Minor GC)
   - 回收所有 Young Region（Eden + Survivor）
   - 存活对象复制到新的 Survivor 或 Old Region
   - 总是 STW
   - 触发条件: Eden 区满（动态阈值）

2. Mixed GC
   - 回收所有 Young + 部分 Old Region（回收价值最高的）
   - 是 G1 的特色（"Garbage First"）
   - 存活对象复制到空闲 Region
   - 总是 STW
   - 触发条件: 堆使用率超过 IHOP 阈值

3. Full GC
   - 单线程执行（JDK 10 之前）/ 多线程执行（JDK 10+）
   - STW 时间极长
   - G1 的兜底方案（尽量避免）
   - 触发条件: Mixed GC 来不及 / Metaspace 不足 / 大对象分配失败

G1 的目标: 尽量用 Young GC 和 Mixed GC，避免 Full GC
```

## 13.2 Young GC 过程

```
G1 Young GC 过程:

Step 1: 选择 CSet
- CSet = 所有 Young Region（Eden + Survivor）
- 不包括 Old Region

Step 2: 标记存活对象
- 从 GC Roots 开始
- 从 RSet 中找到其他 Region 指向 Young Region 的引用
- 标记存活对象

Step 3: 复制存活对象
- 将存活对象从 Young Region 复制到新的 Region
- 新 Region 可能是 Survivor 或 Old（如果对象年龄达到阈值）
- 复制后更新引用

Step 4: 清空旧 Region
- 所有 Young Region 的内容被覆盖
- 旧 Region 变成 Free Region

┌──────────────────────────────────────────────┐
│  Young GC 前                                  │
│  ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐           │
│  │E │E │S │O │E │O │S │E │O │- │           │
│  └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘           │
│  Eden: 4个, Survivor: 2个                     │
└──────────────────────────────────────────────┘
              │ Young GC
              ▼
┌──────────────────────────────────────────────┐
│  Young GC 后                                  │
│  ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐           │
│  │- │- │S'│O │- │O │S'│- │O │S'│           │
│  └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘           │
│  旧 Eden 变 Free, 存活对象复制到新 Survivor   │
│  年龄达标的对象晋升到 Old Region              │
└──────────────────────────────────────────────┘

G1 Young GC 的特点:
- 完全 STW（没有并发阶段）
- 时间可预测（CSet 大小可控）
- 无碎片（复制算法）
- 停顿时间: 几十毫秒 ~ 几百毫秒
```

## 13.3 Mixed GC 过程

```
Mixed GC = Young GC + 部分 Old Region 回收

触发条件:
- IHOP (-XX:InitiatingHeapOccupancyPercent=45)
- 堆使用率超过 45% → 开始并发标记 → 标记完成后触发 Mixed GC

Mixed GC 分为: 并发标记阶段 + 回收阶段

=== 并发标记阶段（与 CMS 类似）===

1. 初始标记 (Initial Mark) — STW
   - 搭载在一次 Young GC 中（piggyback）
   - 标记 GC Roots 直接引用的对象
   - 额外开销极小

2. 根区域扫描 (Root Region Scan) — 并发
   - 扫描 Survivor Region 中引用 Old Region 的对象
   - 不需要 STW

3. 并发标记 (Concurrent Mark) — 并发
   - 从初始标记的对象开始深度遍历
   - 使用 SATB 处理并发修改
   - 计算 Region 的存活对象统计信息

4. 重新标记 (Remark) — STW
   - 处理 SATB 队列
   - 最终确定所有存活对象
   - 比 CMS 快（SATB 的优势）

5. 清理 (Cleanup) — 部分 STW
   - 统计每个 Region 的存活对象大小
   - 排序 Region（按回收价值）
   - 完全空的 Region 直接回收
   - STW 时间很短

=== 回收阶段 ===

6. 混合回收 (Mixed GC) — STW
   - 选择 CSet = 所有 Young + 部分 Old
   - Old Region 选择标准: 回收价值最高
   - 复制存活对象到新 Region
   - 回收多个 Old Region（分多次 Mixed GC）

Mixed GC 可能执行多次:
- 一次 Mixed GC 回收部分 Old Region
- 连续多次 Mixed GC 直到清理完所有高价值 Old Region
- 然后回到纯 Young GC 模式

时间线:
Young GC ──→ [并发标记] ──→ Cleanup ──→ Mixed GC ──→ Mixed GC ──→ Mixed GC ──→ Young GC
  (正常)      (STW短)      (STW短)    (STW+Old)    (STW+Old)    (STW+Old)     (正常)
                           ↑                                                        ↑
                       开始Mixed                                              Mixed结束

G1 Mixed GC 的 CSet 组成:
┌──────────────────────────────────────────────┐
│  CSet = Young Region + Old Region            │
│                                              │
│  Young Region: 全部                          │
│  ┌──┬──┬──┬──┐                              │
│  │E │E │S │S │  ← 所有 Young                │
│  └──┴──┴──┴──┘                              │
│                                              │
│  Old Region: 按回收价值选择                  │
│  ┌──┬──┬──┐                                 │
│  │O1│O3│O7│  ← 垃圾最多的 Old Region        │
│  └──┴──┴──┘                                 │
│  (O1: 85%垃圾, O3: 70%垃圾, O7: 60%垃圾)    │
└──────────────────────────────────────────────┘
```

## 13.4 G1 的停顿时间预测模型

```
G1 的核心能力: 预测 GC 停顿时间

预测模型:
1. 记录历史数据
   - 每个 Region 的存活对象大小
   - 复制每个 Region 的平均耗时
   - RSet 扫描的耗时

2. 计算每个 Region 的回收成本
   cost(Region) = copy_time(live_size) + rset_scan_time(rset_size)

3. 选择 CSet
   - 按 cost/回收量 排序
   - 选择 Region 直到累计 cost ≤ MaxGCPauseMillis

-XX:MaxGCPauseMillis=200
// 目标停顿时间 200ms
// G1 会尽量让每次 GC 不超过 200ms
// 但不保证（如果堆太大、Region 太多，可能超）

-XX:GCPauseIntervalMillis=1000
// 两次 GC 之间的最小间隔（较少使用）

注意:
- MaxGCPauseMillis 是"软目标"，不是硬保证
- 设置太低（如 10ms）会导致 GC 频繁但回收量少
- 合理值: 100ms ~ 300ms
```

## 13.5 G1 大对象处理

```
G1 的 Humongous 对象

定义: 大小 > Region/2 的对象

┌──────────────────────────────────────────────┐
│  Region 大小: 8MB                              │
│  Humongous 阈值: 4MB                           │
│                                              │
│  对象大小 3MB → 普通 Old Region 分配           │
│  对象大小 5MB → Humongous Region              │
│  对象大小 20MB → 3 个连续 Humongous Region   │
│  ┌──────────┬──────────┬──────────┐          │
│  │  H(5MB)  │  H(8MB)  │  H(7MB)  │          │
│  │  连续     │  连续     │  连续     │          │
│  └──────────┴──────────┴──────────┘          │
└──────────────────────────────────────────────┘

Humongous 对象的回收:
- 在并发标记阶段确定哪些 Humongous Region 完全无引用
- 在 Cleanup 阶段直接回收
- 不需要等到 Mixed GC

问题:
- 太多大对象 → Region 碎片化（连续 Region 不足）
- 解决: 调整 Region 大小
  -XX:G1HeapRegionSize=16m
  → 更大的 Region → 减少大对象占比

大对象最佳实践:
- 避免创建超过 Region/2 的大对象
- 大数组考虑分块处理
- Region 大小与对象大小匹配
```

# 第十四部分 G1 调优参数与最佳实践

## 14.1 G1 核心参数

```
=== 基本参数 ===

-XX:+UseG1GC                    // 启用 G1
-XX:MaxGCPauseMillis=200        // 目标停顿时间
-XX:G1HeapRegionSize=16m        // Region 大小（通常不需要手动设置）

=== 堆大小 ===

-Xms8g -Xmx8g                  // 初始堆 = 最大堆（避免动态扩展）
-XX:+AlwaysPreTouch             // 启动时预分配物理内存页（避免运行时缺页）

=== 触发参数 ===

-XX:InitiatingHeapOccupancyPercent=45
// 堆使用率超过 45% → 开始并发标记 → 触发 Mixed GC
// 默认: 45（JDK 9+），旧版本为 45
// 值越小 → Mixed GC 越早触发 → 老年代回收更积极
// 但太小会导致频繁 Mixed GC

-XX:G1HeapWastePercent=5
// 允许浪费的堆空间百分比（默认 5%）
// 当可回收空间 < 5% 时，停止 Mixed GC

-XX:G1MixedGCCountTarget=8
// Mixed GC 的目标次数（默认 8）
// 将 Old Region 回收分摊到 8 次 Mixed GC 中
// 值越大 → 每次回收越少 → 停顿越短

-XX:G1MixedGCLiveThresholdPercent=85
// Old Region 存活对象超过 85% 时不参与 Mixed GC
// 存活对象太多 → 复制开销大 → 不回收
// 默认: 85

=== 年轻代 ===

-XX:G1NewSizePercent=5          // 新生代最小占比（默认 5%）
-XX:G1MaxNewSizePercent=60      // 新生代最大占比（默认 60%）
// G1 会在这两个值之间动态调整新生代大小
// 以满足 MaxGCPauseMillis 目标

-XX:G1YoungSurvivorRatio=8      // Eden:Survivor = 8:1:1（类似 SurvivorRatio）

=== 线程数 ===

-XX:ParallelGCThreads=8         // STW 阶段的线程数
-XX:ConcGCThreads=2            // 并发阶段的线程数

=== RSet ===

-XX:G1RSetRegionEntries=0       // 每个 Region 的 RSet 槽位数（0 = 自动）
-XX:G1RSetSparseRegionEntries=0 // 稀疏 RSet 槽位数（0 = 自动）

=== 其他 ===

-XX:G1ReservePercent=10         // 保留空间（默认 10%）
// 防止疏散失败（Evacuation Failure）
// 留出空间给复制时的"to"空间

-XX:G1HeapRegionSize=16m        // Region 大小
```

## 14.2 G1 调优最佳实践

```
原则 1: 不要设置太多参数
- G1 的设计理念是"自适应"
- 只需要设置: 堆大小 + MaxGCPauseMillis
- 其他参数让 G1 自己调整

原则 2: -Xms = -Xmx
- 避免堆动态扩展带来的开销
- 避免扩容时触发 Full GC

原则 3: 合理设置 MaxGCPauseMillis
- 不要设太小（如 10ms）→ GC 频繁但回收量少
- 不要设太大（如 1000ms）→ 失去低延迟意义
- 推荐值: 100ms ~ 300ms

原则 4: 监控 G1 的 GC 效果
- 查看 GC 日志
- 关注: Young GC 频率、Mixed GC 频率、Full GC 是否出现
- 如果出现 Full GC → 需要调优

推荐 G1 配置（8G 堆）:
-Xms8g -Xmx8g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:+AlwaysPreTouch
-XX:+PrintGCDetails
-XX:+PrintGCDateStamps
-XX:+PrintAdaptiveSizePolicy
-Xlog:/var/log/gc.log

推荐 G1 配置（32G 堆）:
-Xms32g -Xmx32g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:InitiatingHeapOccupancyPercent=35
-XX:G1HeapRegionSize=16m
-XX:+AlwaysPreTouch
-XX:ConcGCThreads=4
-XX:ParallelGCThreads=16
```

## 14.3 G1 常见问题与解决

```
问题 1: 频繁 Young GC
原因: 新生代太小，Eden 快速填满
解决:
- -XX:G1NewSizePercent=20  // 增大最小新生代
- 或降低对象分配速率

问题 2: Mixed GC 不触发
原因: IHOP 阈值太高，老年代堆积
解决:
- -XX:InitiatingHeapOccupancyPercent=35  // 降低阈值
- 确保并发标记能正常完成

问题 3: 疏散失败（Evacuation Failure）
原因: 复制时没有足够的 Free Region
解决:
- -XX:G1ReservePercent=20  // 增大保留空间
- 或增大堆

问题 4: 大量 Humongous 对象
原因: 大对象占用多个 Region
解决:
- -XX:G1HeapRegionSize=32m  // 增大 Region
- 或减少大对象分配

问题 5: Full GC
原因: Mixed GC 来不及 / 大对象分配失败 / Metaspace 不足
解决:
- 检查是否因为 Metaspace → -XX:MaxMetaspaceSize
- 检查是否因为大对象 → 调整 Region 大小
- 降低 IHOP 阈值让 Mixed GC 更早触发
- 增大堆

问题 6: GC 停顿超过 MaxGCPauseMillis
原因: RSet 太大 / 存活对象太多 / Region 太多
解决:
- -XX:MaxGCPauseMillis=300  // 放宽目标
- 或减小堆（减少 Region 数量）
```

# 第十五部分 ZGC / Shenandoah 简介

## 15.1 ZGC

```
ZGC (Z Garbage Collector) — JDK 11 实验, JDK 15 生产可用

-XX:+UseZGC -XX:+UnlockExperimentalVMOptions (JDK 11-14)
-XX:+UseZGC (JDK 15+)

设计目标:
1. 停顿时间 < 10ms（不管堆大小）
2. 支持超大堆（TB 级别）
3. 停顿时间不随堆增大而增加

核心技术:
1. 染色指针（Colored Pointer）
   - 64 位指针中借用高位存储 GC 元数据
   - JDK 15: 使用 4 bit 存储 Marked0/Marked1/Remapped/Finalizable
   
   ┌─────────────────────────────────────────┐
   │  64 位指针                                │
   │  ┌──┬──┬────────────────────────────┐  │
   │  │4b│4b│  42位对象地址               │  │
   │  └──┴──┴────────────────────────────┘  │
   │   ↑  ↑                                  │
   │  未用 GC元数据                          │
   └─────────────────────────────────────────┘

2. 读屏障（Load Barrier）
   - 每次从堆中读取对象引用时执行
   - 检查指针颜色 → 决定是否需要修正
   - 实现"并发移动"（移动对象时不需要 STW）

3. 并发转移（Concurrent Relocation）
   - 对象移动与应用线程同时进行
   - 通过读屏障保证应用线程总是访问正确的地址

4. 转发表（Forwarding Table）
   - 记录对象从旧地址到新地址的映射
   - 应用线程访问旧地址 → 读屏障 → 转发表 → 新地址

ZGC 的 GC 阶段:
1. 标记开始 (Pause Mark Start) — STW（< 1ms）
2. 并发标记 (Concurrent Mark) — 并发
3. 标记结束 (Pause Mark End) — STW（< 1ms）
4. 并发转移准备 (Concurrent Relocate Set Selection) — 并发
5. 转移开始 (Pause Relocate Start) — STW（< 1ms）
6. 并发转移 (Concurrent Relocate) — 并发

特点:
- STW 阶段只有 3 个，每个 < 1ms
- 总停顿 < 10ms（不管堆多大）
- 支持 16TB 堆
- JDK 21 开始支持分代 ZGC（进一步降低 GC 频率）

适用场景:
- 超大堆应用（> 32GB）
- 对延迟极其敏感的应用
- JDK 17+ 生产环境
```

## 15.2 Shenandoah

```
Shenandoah GC — Red Hat 开发, JDK 12+ 可用

-XX:+UseShenandoahGC (JDK 12-14 实验, JDK 15+ 生产)

设计目标: 与 ZGC 类似
1. 停顿时间 < 10ms
2. 支持大堆
3. 停顿时间与堆大小无关

核心技术:
1. Brooks 转发指针（Brooks Pointer）
   - 每个对象头中额外一个指针
   - 指向自身（移动前）或新对象（移动后）
   - 访问对象 → 读转发指针 → 跳转到正确地址

   ┌──────────────┐
   │  对象头        │
   │  ┌──────────┐│
   │  │Brooks Ptr││ → 指向自己（未移动）
   │  └──────────┘│
   │  Mark Word   │
   │  Class Pointer│
   ├──────────────┤
   │  实例数据     │
   └──────────────┘

2. 并发整理（Concurrent Compaction）
   - 与 ZGC 类似，移动对象不需要 STW
   - 使用 Brooks 指针实现并发移动

ZGC vs Shenandoah:
┌──────────────┬─────────────────┬─────────────────┐
│              │  ZGC            │  Shenandoah      │
├──────────────┼─────────────────┼─────────────────┤
│  并发移动    │  染色指针+读屏障  │  Brooks 指针      │
│  指针开销    │  4 bit 高位      │  一个完整指针      │
│  内存开销    │  小              │  较大（每对象+8B）  │
│  读屏障      │  是              │  是               │
│  最大堆      │  16TB            │  无限制           │
│  JDK 版本   │  15+ 生产        │  15+ 生产         │
│  分代支持    │  JDK 21+         │  JDK 21+         │
└──────────────┴─────────────────┴─────────────────┘
```

## 15.3 各收集器选择指南

```
┌──────────────────────────────────────────────────────────────┐
│                    GC 选择决策树                               │
│                                                              │
│  堆大小 < 1GB?                                                │
│  ├── Yes → Serial GC (-XX:+UseSerialGC)                     │
│  │       适合: 容器、微服务、开发环境                          │
│  │                                                           │
│  └── No                                                      │
│      │                                                       │
│      对延迟敏感?                                              │
│      ├── No (注重吞吐量)                                      │
│      │   → Parallel GC (-XX:+UseParallelGC)                  │
│      │   适合: 批处理、大数据、离线计算                        │
│      │                                                       │
│      └── Yes (注重延迟)                                       │
│          │                                                   │
│          堆大小 > 32GB 或 JDK 17+?                           │
│          ├── Yes → ZGC (-XX:+UseZGC)                        │
│          │       适合: 超大堆、对延迟极其敏感                  │
│          │                                                   │
│          └── No                                              │
│              → G1 GC (-XX:+UseG1GC)                          │
│              适合: 大多数服务端应用 (JDK 9+ 默认)              │
│                                                              │
│  特殊情况:                                                    │
│  - JDK 8 + 需要低延迟 → CMS (已废弃，建议升级到 JDK 11+ G1)  │
│  - JDK 8 + 注重吞吐量 → Parallel GC                          │
└──────────────────────────────────────────────────────────────┘

总结:
- JDK 8: Parallel GC (默认) 或 CMS (低延迟，已废弃)
- JDK 9-14: G1 (默认) 或 ZGC (实验)
- JDK 15+: G1 (默认) 或 ZGC (生产可用)
- JDK 17+: G1 (默认) 或 ZGC (推荐低延迟)
- JDK 21+: G1 (默认) 或 ZGC 分代 (推荐)
```

## 16.2 GC 日志解读

```
=== Minor GC 日志 ===

2024-01-15T10:30:45.123+0800: 1.234:
[GC (Allocation Failure)
 [PSYoungGen: 65536K->7168K(76288K)]
  65536K->7280K(251392K), 0.0156789 secs]
 [Times: user=0.05 sys=0.00, real=0.02 secs]

解读:
- 2024-01-15T10:30:45.123: 时间戳
- 1.234: JVM 启动后 1.234 秒
- GC (Allocation Failure): Eden 区分配失败触发 GC
- PSYoungGen: Parallel Scavenge 新生代
- 65536K->7168K(76288K):
  新生代使用量: GC前 65536K → GC后 7168K
  新生代总大小: 76288K
- 65536K->7280K(251392K):
  整个堆使用量: GC前 65536K → GC后 7280K
  整个堆总大小: 251392K
- 0.0156789 secs: GC 耗时 15ms
- user=0.05: 用户态 CPU 时间
- sys=0.00: 内核态 CPU 时间
- real=0.02: 实际时间（STW 时间）


=== Full GC 日志 ===

2024-01-15T10:31:00.456+0800: 16.567:
[Full GC (Ergonomics)
 [PSYoungGen: 7168K->0K(76288K)]
 [ParOldGen: 86016K->53248K(175104K)]
 93184K->53248K(251392K), 0.2345678 secs]
 [Times: user=0.89 sys=0.01, real=0.23 secs]

解读:
- Full GC (Ergonomics): 自适应策略触发
- PSYoungGen: 新生代 7168K→0K（全部回收或晋升）
- ParOldGen: Parallel Old 老年代 86016K→53248K
- 93184K→53248K: 整个堆
- 0.2345678 secs: Full GC 耗时 234ms


=== CMS GC 日志 ===

2024-01-15T10:32:00.789+0800: 76.789:
[GC (CMS Initial Mark)
 [CMS: 120000K->120000K(150000K)]
  150000K->150000K(251392K), 0.001234 secs]

2024-01-15T10:32:00.790+0800: 76.790:
[CMS-concurrent-mark-start]
2024-01-15T10:32:01.234+0800: 77.234:
[CMS-concurrent-mark: 0.444/0.444 secs]

2024-01-15T10:32:01.235+0800: 77.235:
[GC (CMS Final Remark)
 [CMS: 120000K->115000K(150000K)]
  150000K->115000K(251392K), 0.005678 secs]
 [Times: user=0.02 sys=0.00, real=0.01 secs]
2024-01-15T10:32:01.236+0800: 77.236:
[CMS-concurrent-sweep-start]
2024-01-15T10:32:01.567+0800: 77.567:
[CMS-concurrent-sweep: 0.331/0.331 secs]

解读:
- CMS Initial Mark: 初始标记（STW 1ms）
- CMS-concurrent-mark: 并发标记（0.444s 并发）
- CMS Final Remark: 重新标记（STW 5ms）

=== G1 GC 日志 ===

2024-01-15T10:33:00.123+0800: 136.789:
[GC pause (G1 Evacuation Pause) (young)
 8192M->4096M(8192M), 0.015678 secs]
  [Eden: 5120.0M(5120.0M)->0.0B(4096.0M) Survivors: 512.0M Old: 2560.0M]
  [Metaspace: 256M->256M(512M)]
  [Times: user=0.06 sys=0.00, real=0.02 secs]

解读:
- G1 Evacuation Pause (young): Young GC
- 8192M->4096M(8192M): 堆使用量 8G→4G（总 8G）

## 16.3 GC 日志分析工具

```
1. GCViewer (开源)
   - 解析 GC 日志文件，生成图表
   - 显示 GC 频率、停顿时间、堆使用量

2. GCEasy (gceasy.io)
   - 在线工具，上传 GC 日志
   - 自动分析停顿时间、吞吐量、内存泄漏

3. JFR (Java Flight Recorder)
   - JDK 11+ 内置
   - 记录运行时事件，包括 GC
   - JMC (JDK Mission Control) 可视化

4. JConsole / VisualVM
   - 实时监控 GC 情况
   - 查看堆使用量、GC 次数、GC 时间

5. jstat
   jstat -gc <pid> 1000
   // 每秒打印一次 GC 统计信息
   // S0C  S1C  S0U  S1U  EC   EU   OC   OU   MC   MU   CCSC CCSU YGC YGCT FGC FGCT GCT

6. jcmd
   jcmd <pid> GC.heap_info
   jcmd <pid> GC.run          // 建议 GC
   jcmd <pid> GC.class_histogram

关键指标:
- 吞吐量 = 应用运行时间 / 总时间（应用+GC）
  → 目标: > 95%
- 平均停顿时间
  → 目标: < 200ms
- 最长停顿时间
  → 目标: < 500ms
- Full GC 频率
  → 目标: 接近 0
```

## 17.3 常见内存泄漏场景

```
场景 1: 集合类泄漏
// Map 作为缓存，从不清理
static Map<String, Object> cache = new HashMap<>();
// 持续往 cache 中 put 但从不 remove
// → Map 中的对象永远不会被 GC

场景 2: ThreadLocal 泄漏
// ThreadLocal 的 Entry: WeakReference<ThreadLocal> + value
// ThreadLocal 被回收但 value 还在
// → value 对象永远不会被 GC
// 解决: 使用后 threadLocal.remove()

场景 3: 监听器未注销
// 注册了事件监听器但从未注销
button.addActionListener(listener);
// listener 持有外部对象引用 → 外部对象无法回收
// 解决: 不用时 removeActionListener

场景 4: 内部类持有外部类引用
// 非静态内部类隐式持有外部类引用
class Outer {
    class Inner { }  // Inner 持有 Outer.this
}
// 如果 Inner 被长期持有 → Outer 也无法回收
// 解决: 使用静态内部类

场景 5: 数据库连接/IO 资源未关闭
// 连接池中的连接未归还
// 文件流未关闭
// → 底层资源泄漏
// 解决: try-with-resources

场景 6: 静态集合
// static 集合的生命周期 = 类的生命周期 = JVM 生命周期
static List<Object> list = new ArrayList<>();
// list 中的对象永远不会被 GC
// 解决: 定期清理或使用 WeakHashMap

场景 7: 缓存过期策略缺失
// 自定义缓存没有过期策略
// 缓存越来越大直到 OOM
// 解决: 使用 Caffeine/Guava Cache，设置 maximumSize 和 expireAfterWrite
```

## 17.4 CPU 100% + GC 频繁排查

```
排查步骤:

Step 1: 确认是否是 GC 导致 CPU 高
top -Hp <pid>
# 查看哪个线程 CPU 高
# 如果是 GC 线程 → GC 问题

Step 2: 查看 GC 统计
jstat -gcutil <pid> 1000
# 每秒打印 GC 情况
# 如果 YGC（Young GC 次数）快速增长 → Minor GC 频繁
# 如果 FGC（Full GC 次数）增长 → Full GC 频繁

Step 3: 查看堆使用情况
jmap -heap <pid>
# 查看堆各区域使用情况

Step 4: Dump 分析

# 用 MAT 分析

Step 5: 查看线程
jstack <pid> > thread.txt
# 查看是否有死循环或大对象分配

常见原因:
1. 代码死循环创建大量对象 → GC 频繁
2. 大查询返回过多数据 → 堆满
3. 内存泄漏 → Full GC 频繁但回收量少
4. 缓存无限增长 → 堆满
5. 大文件读取到内存 → 堆满
```

# 第十九部分 面试高频题 30 问

## Q1: 说一下 JVM 的内存结构

> JVM 运行时数据区分为线程私有和线程共享两部分。线程私有包括程序计数器（记录字节码行号，不会 OOM）、虚拟机栈（方法调用的栈帧，包含局部变量表和操作数栈，可能 SOE/OOM）、本地方法栈（Native 方法）。线程共享包括堆（对象实例和数组，GC 主要区域，分新生代和老年代）和方法区/元空间（类信息、常量池、静态变量、JIT 代码）。JDK 8 后永久代被元空间替代，使用本地内存。

## Q2: 为什么堆要分代？

> 基于分代假说：1) 绝大多数对象朝生夕死，2) 熬过多次 GC 的对象越难死亡。根据这个特点，将堆分为新生代和老年代，不同代使用不同算法。新生代用复制算法（98% 对象死亡，复制开销小），老年代用标记-清除或标记-整理（存活率高，不适合复制）。分代后 Minor GC 频繁但快，Full GC 不频繁，整体效率高。

## Q3: 新生代为什么用两个 Survivor？

> 如果只有一个 Survivor，GC 时需要把 Eden 和 Survivor 的存活对象复制到 Survivor 自己（不能复制到自己），只能用标记-清除，产生碎片。两个 Survivor 形成 From/To 模式，GC 时把 Eden+From 的存活对象复制到 To，然后清空 From，角色互换。这样无碎片、无停顿（只需清空）。代价是浪费 10% 空间（一个 Survivor），但换来无碎片和高效分配。

## Q4: 对象什么时候会进入老年代？

> 四种情况：1) 年龄达到 MaxTenuringThreshold（默认 15）自动晋升；2) 动态年龄判断，Survivor 中相同年龄对象大小之和超过 Survivor 空间的 50%，该年龄及以上对象全部晋升；3) 大对象超过 PretenureSizeThreshold 直接进老年代（避免在 Eden/Survivor 间复制）；4) Minor GC 后 Survivor 放不下存活对象，通过担保机制进老年代。

## Q5: 什么是 GC Roots？哪些对象可以作为 GC Roots？

> GC Roots 是可达性分析的起点。包括：1) 虚拟机栈中局部变量表中的引用（最大的来源）；2) 方法区中类静态变量引用的对象；3) 方法区中常量引用的对象；4) 本地方法栈中 JNI 引用；5) JVM 内部引用（基本类型 Class 对象、系统类加载器、锁 monitor 引用的对象）；6) 跨代引用（通过 RSet/卡表记录）。

## Q6: 三色标记是什么？漏标怎么解决？

> 三色标记将对象分为白色（未访问）、灰色（已访问但引用未处理完）、黑色（已完成）。漏标发生在并发标记期间：黑色对象新增了到白色对象的引用，同时灰色对象断开了到白色对象的引用。CMS 用增量更新（写后屏障，黑色对象新增引用变回灰色，Remark 重新扫描）；G1 用 SATB（写前屏障，记录旧引用，快照中存活对象一定不漏标）；ZGC/Shenandoah 用读屏障。

## Q7: 什么是安全点？为什么需要安全区域？

> 安全点是程序中可以安全暂停进行 GC 的位置（方法调用、循环跳转等），线程主动检查 Poll Page 决定是否暂停。安全区域针对 Blocked/Sleeping 线程，它们无法主动检查安全点。线程进入安全区域时标记自己，GC 时不需要等待这些线程；离开时检查 GC 是否完成，未完成则等待。这样 GC 不会被阻塞线程卡住。

## Q8: 四种引用有什么区别？

> 强引用：永不回收，Object obj = new Object()。软引用：内存不足时回收，适合缓存。弱引用：下次 GC 就回收，适合 ThreadLocal 和弱缓存。虚引用：不影响对象生命周期，get() 返回 null，用于跟踪对象被 GC 的过程（如 DirectByteBuffer 的堆外内存释放）。

## Q9: Minor GC 和 Full GC 的区别？

> Minor GC 只回收新生代，Eden 满时触发，使用复制算法，STW 时间短（几毫秒~几十毫秒）。Full GC 回收整个堆+方法区，触发条件包括 System.gc()、老年代不足、元空间不足、担保失败、CMS Concurrent Mode Failure，STW 时间长（几百毫秒~几秒）。Full GC 是要尽量避免的。

## Q10: CMS 的四个阶段是什么？

> 1) 初始标记（STW）：只标记 GC Roots 直接引用的对象，速度极快。2) 并发标记：从初始标记对象开始深度遍历，与应用线程并发，使用增量更新处理并发修改。3) 重新标记（STW）：修正并发标记期间的标记变化，处理 MOD-Union Table。4) 并发清除：清除未标记对象，与应用线程并发。整体只有两个短 STW 阶段。

## Q11: CMS 有什么缺陷？

> 四大缺陷：1) 浮动垃圾：并发期间产生的垃圾本轮无法回收；2) 空间碎片：标记-清除算法不移动对象，大对象可能分配失败；3) Concurrent Mode Failure：并发期间老年代空间不足，退化为 Serial Old 单线程 Full GC，STW 极长；4) CPU 敏感：并发阶段占用 CPU，核心少时影响吞吐量。

## Q12: G1 和 CMS 的区别？

> G1 用 Region 替代固定新生代/老年代布局，无碎片（复制算法），停顿时间可预测（MaxGCPauseMillis）。CMS 用标记-清除有碎片，停顿不可预测。G1 的 Mixed GC 选择回收价值最高的 Region（Garbage First），CMS 回收整个老年代。G1 用 SATB，CMS 用增量更新。G1 适合 6GB+ 堆，JDK 9+ 默认。

## Q13: G1 的 Region 是什么？

> G1 将堆划分为大小相等的 Region（1~32MB，2 的幂），每个 Region 可以动态切换角色（Eden→Survivor→Old）。大对象超过 Region/2 为 Humongous，可能跨多个连续 Region。G1 的"Garbage First"就是选择垃圾最多的 Region 先回收，通过 CSet（Collection Set）控制回收范围，实现可预测的停顿时间。

## Q14: G1 的 RSet 是什么？

> RSet（Remembered Set）记录"谁引用了我"，每个 Region 有一个 RSet，记录其他 Region 指向本 Region 的引用。这样 GC 时不需要扫描整个堆，只需扫描目标 Region 的 RSet。RSet 通过写屏障维护，有内存开销（通常 1%~20% 的堆）。G1 的 RSet 实现使用卡表（Card Table），每个 Card 512 字节。

## Q15: G1 的 Mixed GC 是什么？

> Mixed GC = Young GC + 部分 Old Region 回收。当堆使用率超过 IHOP（默认 45%）时触发并发标记，标记完成后进行多次 Mixed GC。每次 Mixed GC 回收所有 Young Region + 回收价值最高的几个 Old Region（垃圾最多的），分摊回收压力。通过 G1MixedGCCountTarget 控制分摊次数。这就是 G1 "Garbage First" 的核心。

## Q16: SATB 和增量更新的区别？

> SATB（G1）：写前屏障，在引用被覆盖前记录旧引用，相当于在标记开始时拍快照，快照中的存活对象一定不会被漏标。优点是 Remark 速度快，缺点是产生更多浮动垃圾。增量更新（CMS）：写后屏障，黑色对象新增引用白色时变回灰色，Remark 阶段重新扫描。优点是浮动垃圾少，缺点是 Remark 需要重新扫描。

## Q17: ZGC 为什么能实现 < 10ms 停顿？

> ZGC 使用染色指针（在 64 位指针的高位存储 GC 元数据）和读屏障（每次从堆中读取引用时检查指针颜色），实现并发转移——移动对象时不 STW，应用线程通过读屏障和转发表访问正确地址。STW 阶段只有 3 个（标记开始/结束/转移开始），每个 < 1ms。JDK 21+ 支持分代 ZGC 进一步降低 GC 频率。

## Q18: 什么是空间分配担保？

> Minor GC 前检查老年代可用空间是否大于新生代所有对象总大小。如果大于，安全进行 Minor GC；如果不大于但允许担保失败（基于历次晋升平均大小），尝试 Minor GC，如果 Survivor 放不下就通过担保机制进老年代；如果老年代也放不下 → Full GC。JDK 6u24 后规则简化为总是允许尝试。

## Q19: 什么是 TLAB？

> TLAB（Thread Local Allocation Buffer）是每个线程在 Eden 区的私有缓冲区。多线程分配对象时不需要竞争整个 Eden，只需在自己的 TLAB 中指针碰撞（无锁分配），TLAB 用完后才 CAS 分配。避免了多线程分配竞争，默认开启。这就是 JVM 中对象分配"极快"的原因。

## Q20: 如何选择 GC 收集器？

> 堆 < 1GB 用 Serial；注重吞吐量用 Parallel GC（JDK 8 默认）；注重延迟、堆 < 32GB 用 G1（JDK 9+ 默认）；堆 > 32GB 或 JDK 17+ 对延迟极其敏感用 ZGC。JDK 8 低延迟用 CMS（已废弃，建议升级到 JDK 11+ 使用 G1）。

## Q21: -XX:MaxGCPauseMillis 设为 10ms 会怎样？

> 对 G1 来说，目标太低会导致每次 GC 只回收少量 Region（为了控制停顿时间），GC 频率大幅增加，吞吐量下降。同时可能无法满足目标（CSet 太小导致回收量不足，需要更多次 GC）。合理值是 100~300ms。对 ZGC 可以设为 10ms 因为 ZGC 的 STW 不受堆大小影响。

## Q22: 如何排查 Full GC 频繁？

> 1) 查看 GC 日志确认 Full GC 原因（老年代不足/Metaspace/System.gc/担保失败）；2) jstat -gcutil 观察 GC 趋势；3) jmap -heap 查看堆各区域使用；4) Dump 堆用 MAT 分析是否有内存泄漏；5) 检查是否有大对象直接进老年代；6) 检查 MaxTenuringThreshold 和 SurvivorRatio 设置；7) 对于 CMS 检查 CMSInitiatingOccupancyFraction。

## Q23: 什么是栈上分配？

> 通过逃逸分析（-XX:+DoEscapeAnalysis，JDK 6u23+ 默认开启），如果对象没有逃逸出方法作用域，可以直接在栈帧的局部变量表中分配（甚至标量替换为基本类型），不需要在堆上分配。方法结束后栈帧弹出，对象自动销毁，不需要 GC。这减少了 GC 压力，是 JVM 的重要优化。

## Q24: ThreadLocal 为什么会内存泄漏？

> ThreadLocal 的 Entry 继承 WeakReference<ThreadLocal>，Key 是弱引用。当 ThreadLocal 实例被回收后，Key 变成 null，但 Value（强引用）还在 Entry 中。Thread 持有 ThreadLocalMap，ThreadLocalMap 持有 Entry，Entry 的 Value 无法被回收 → 内存泄漏。解决：使用后显式 remove()。

## Q25: 如何分析 GC 日志？

> 关注几个指标：1) GC 频率（Minor GC 间隔）；2) GC 停顿时间（real 值）；3) 回收量（GC前后堆使用量差值）；4) 吞吐量（应用时间/总时间）；5) Full GC 是否出现。用 GCViewer/GCEasy 工具分析。如果 Full GC 出现，需要定位原因：看日志中是 "Allocation Failure"、"System.gc()"、"CMS Concurrent Mode Failure" 还是 "Metaspace"。

## Q26: 什么是晋升年龄？最大为什么是 15？

> 对象在 Survivor 中每熬过一次 Minor GC 年龄+1，达到 MaxTenuringThreshold 后晋升老年代。最大值 15 是因为对象头的 Mark Word 中年龄字段只有 4 bit，4 bit 最多表示 0~15。G1 中也是如此。

## Q27: 什么情况下应该用 G1 而不是 CMS？

> 1) 堆 > 6GB（G1 在大堆上表现更好）；2) 需要可预测的停顿时间（MaxGCPauseMillis）；3) 遇到 CMS 碎片化问题；4) 遇到 Concurrent Mode Failure；5) JDK 9+（G1 是默认）。G1 的 Region 化设计和"Garbage First"策略比 CMS 更适合大堆。

## Q28: G1 调优的关键参数有哪些？

> 最重要的是 -Xms=-Xmx（避免动态扩展）和 -XX:MaxGCPauseMillis=200（目标停顿）。其次是 -XX:InitiatingHeapOccupancyPercent=45（Mixed GC 触发阈值），值越低 Mixed GC 越早触发。其他参数让 G1 自适应调整即可，不要设太多参数。如果出现 Full GC，可以降低 IHOP 或增大堆。

## Q29: 什么是 Concurrent Mode Failure？怎么避免？

> CMS 并发回收期间，应用线程继续分配老年代空间，如果老年代空间不足，CMS 无法完成回收，退化为 Serial Old 单线程 Full GC，STW 时间可能几秒~几十秒。避免方法：1) 降低 CMSInitiatingOccupancyFraction（如 70%）；2) 增大老年代；3) 控制对象分配速率；4) 或升级到 G1（无此问题）。

## Q30: JVM 调优的通用原则是什么？

> 1) 先保证正确性，再调优性能；2) -Xms = -Xmx，避免动态扩展；3) 不要设太多参数，先用默认值；4) 基于监控数据调优，不要凭感觉；5) 每次只改一个参数；6) 关注吞吐量和停顿时间的平衡；7) 避免过早优化——如果 GC 没有问题就不要调优；8) 升级 JDK 版本可能是最好的"调优"（G1/ZGC 更优秀）。
