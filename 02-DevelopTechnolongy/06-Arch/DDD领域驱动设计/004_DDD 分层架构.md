|#|架构模式|层次结构|核心原则|优缺点|面试追问|FlowPulse 采用|
|---|---|---|---|---|---|---|
|**7.4.1**|**传统三层 → DDD四层**|**表现层**(Controller/API) → **应用层**(Application Service/用例编排) → **领域层**(Entity/VO/Aggregate/Domain Service/Domain Event/Repository Interface) → **基础设施层**(Repository Impl/External Client/MQ Producer)|**依赖倒置**：领域层不依赖任何外层！基础设施层实现领域层定义的接口|清晰/易测试/领域隔离；但层次多了初学者容易混淆|"Application Service是薄的还是厚的？应该放什么逻辑？"|**workflow-engine 四层架构** ↓|
|**7.4.2**|**六边形架构 Hexagonal / Ports & Adapters**|Alistair Cockburn提出；核心=领域模型；外围=端口(Port=接口) + 适配器(Adapter=实现)；入站端口(Driving/API)/出站端口(Driven/Repository)|端口=领域层的接口定义；适配器=技术实现的替换品；可以方便地切换实现(如MySQL换Mongo只需换Adapter)|测试极友好(Mock端口即可)；但对简单项目过度工程化|"六边形架构和分层架构的本质区别是什么？Port和Adapter分别对应什么？"|**推荐给工作流引擎核心模块**：领域层定义Repository接口(出站Port) + ApplicationService接口(入站Port)|
|**7.4.3**|**洋葱架构 Onion Architecture**|Jeffrey Palermo提出；同心圆结构：中心=领域实体 → 外圈=领域服务 → 再外=应用服务 → 最外=基础设施；依赖方向始终向内(内圈不知道外圈)|和六边形的本质相同(依赖倒置)，表达形式不同(圆形 vs 六边形)|视觉上更直观表达"核心不受污染"；实际项目中常与六边形混用|"洋葱架构和六边形架构选哪个？有实质区别吗？"|理解层面；FlowPulse用改良版四层(DDD标准)+关键位置引入Port概念|
|**7.4.4**|**整洁架构 Clean Architecture**|Robert C. Martin Uncle Bob提出；最严格的依赖规则：Entities → Use Cases → Interface Adapters → Frameworks & Drivers；内圈定义抽象/外圈实现细节|强调"源码依赖方向必须指向高层策略"；比洋葱更强调用例(Use Case)作为一等公民|最严格但也最"重"；适合超大型系统|"Clean Architecture和Onion Architecture的区别？"|参考其思想：确保Spring/MyBatis等技术框架只在最外层出现，绝不侵入领域层|

> **FlowPulse workflow-engine 项目包结构（DDD四层）**

```
com.flowpulse.workflow-engine/
├── api/                          ← 接口层 (对外暴露的DTO/请求响应)
│   ├── dto/
│   │   ├── request/
│   │   │   ├── StartProcessRequest.java
│   │   │   └── CompleteTaskRequest.java
│   │   └── response/
│   │       ├── ProcessInstanceVO.java
│   │       └── TaskVO.java
│   └── WebhookApi.java           ← 对外HTTP接口(可选)
│
├── application/                   ← 应用层 (用例编排/事务控制)
│   ├── ProcessApplicationService.java    ★ 编排核心用例
│   │   // startProcess(): 加载定义 → 校验权限 → 创建实例 → 初始化任务 → 发布事件
│   │   // completeTask(): 校验任务归属 → 执行任务完成逻辑 → 推进流程 → 发布事件
│   ├── TaskApplicationService.java
│   └── assembler/                ← DTO ↔ 领域对象转换(Mapper)
│       ├── ProcessInstanceAssembler.java
│       └── TaskInstanceAssembler.java
│
├── domain/                       ★ 领域层 (纯业务!零技术框架依赖)
│   ├── model/                    ← 领域模型
│   │   ├── aggregate/            ← 聚合
│   │   │   ├── ProcessDefinition.java      ★ 聚合根
│   │   │   └── ProcessInstance.java         ★ 聚合根
│   │   ├── entity/               ← 实体
│   │   │   ├── Node.java                 (基类)
│   │   │   ├── UserTaskNode.java
│   │   │   ├── ServiceTaskNode.java

│   │   │   ├── TaskInstance.java
│   │   │   └── ExecutionPointer.java      (引擎内部指针)
│   │   ├── transition/           ← 实体
│   │   │   └── Transition.java
│   │   └── valueobject/          ← 值对象
│   │       ├── ProcessStatus.java
│   │       ├── TaskStatus.java
│   │       ├── NodeType.java
│   │       ├── ExecutionStrategy.java    ★ 创新点一
│   │       └── Expression.java
│   ├── service/                  ← 领域服务

│   │   └── DomainEventPublisher.java    (端口/接口!)
│   ├── repository/               ← 资源库接口(端口!)
│   │   ├── ProcessDefinitionRepository.java
│   │   ├── ProcessInstanceRepository.java
│   │   └── TaskInstanceRepository.java
│   └── factory/
│       └── ProcessInstanceFactory.java
│
├── infrastructure/               ← 基础设施层 (技术实现)

│   │   ├── mybatis/

│   │   │   ├── ProcessDefinitionMapper.xml

│   │   │   ├── ProcessInstanceRepositoryImpl.java

└── WorkflowEngineApplication.java
```
